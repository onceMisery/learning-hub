总体结论

  技术骨架正确、Java 对照密集、happy path 扎实，作为一张"Java→Rust 迁移地图"是合格的。但有两个系统性问题：

  1. 漏了一批"Java 开发者头两周必撞、且正是本系列该负责讲"的高频坑 ——
  不是边角料，是会让读者写出错误代码或跑不起来的东西。
  2. 文风高度模板化，真人痕迹极少 —— 太干净、太对称、太没立场，读起来像审过的公司 wiki，而不是趟过坑的人写给同行的笔记。

  一、技术硬伤（P0 · 必须先修）

  照抄会翻车、或被懂行读者当场抓包，最伤可信度。

  - P0-1　第6章：「Rust 从一开始就原生支持异步」是史实错误。async/await 是 1.39（2019 末）才稳定，远晚于 1.0（2015）。
  - P0-2　第6章：rand 的 deck.shuffle(&mut rng) 编译不过。shuffle 来自 SliceRandom，需补 use rand::seq::SliceRandom;。
  - P0-3　第6章：sqlx 示例占位符矛盾。连接串是 Postgres 却用 ?；Postgres 应为 $1。
  - P0-4　全书：版本号不一致（reqwest 0.11/0.12、sqlx 0.7/0.8、axum 0.7）。统一，并补"axum 0.7→0.8 路由 :id→{id}"。
  - P0-5　第5章：assert_equal! 宏把参数求值两遍，有副作用的表达式会重复执行。应先 let left = $left; 绑定。
  - P0-6　第4章：把 s.chars() 称遍历字符"正确方式"属误导。chars() 产出码点≠人眼字符（"é" 拆 2 个、复合 emoji
  拆更多），需点名 unicode-segmentation。
  - P0-7　第3章：Java 21 穷尽性表述不准。switch 表达式自 14 起就强制穷尽。改为区分"switch 语句（不强制）vs 表达式/sealed
  模式（强制）"。
  - P0-8　第4章：闭包引用分层示例自相矛盾。filter(|x| *x…) 与 take_while(|x| **x…) 签名相同却一个 *x 一个
  **x，必须统一+解释。
  - P0-9　第4章：avg_age 示例把同一 filter 跑两遍算平均，纯浪费却不提。改一趟 fold 或加注。

  二、知识遗漏（P1 必撞坑 / P2 补充）

  第01章
  - P1 整数溢出：Java 静默回绕，Rust debug 溢出 panic、release 回绕。补 wrapping_/checked_/saturating_add。
  - P2 usize 与索引类型转换（.len() 返回 usize）。

  第02章
  - P1 Drop/RAII 替代 finally；说明"不能手动调 .drop()，用 std::mem::drop(x)"。
  - P2 部分移动 partial move；Copy 与 Clone 的 derive 关系。

  第03章
  - P1 引用分层与 match ergonomics（全书最大盲区）：Shape::Circle(r) 的 r 是 &f64，靠 2018 默认绑定模式，从没讲。
  - P1 ? 的 From 错误转换 + 自定义错误：对 io::Error 用 ? 报 From not implemented；本章只给 Box<dyn
  Error>，给不出真解法，需前向引用第6章。
  - P1 Option::as_ref()：Option<String> 想 .map() 不消耗须 as_ref()，否则报 cannot move out of ... behind a shared
  reference。
  - P1 孤儿规则 + newtype：不能给外部类型实现外部 trait（如给 Vec<T> impl Display）。
  - P1 Turbofish ::<> 从没解释，全书用了 7+ 处。
  - P2 对象安全规则、Default+builder（Rust 无命名/默认参数/重载）、关联类型、String + 语义。

  第04章
  - P1 闭包参数引用分层（&T vs &&T）：filter/take_while/find 收 &Item、map/any/all 收 Item。从 Java 迁移最高频困惑。
  - P1 Vec 的 sort/sort_by/sort_by_key/retain，浮点不能直接 sort（f64 无 Ord）。
  - P1 collect() 收进 Result<Vec<_>, E>：遇错短路，错误处理最顺手写法。
  - P1 返回/存储闭包：-> impl Fn 或字段存 Box<dyn Fn>（回调/策略/工厂）。
  - P1 Vec 迭代中修改被编译期拦截 = Java 的 ConcurrentModificationException，但提前到编译期，绝佳对照。
  - P2 迭代器惰性"什么都不发生"演示、分组无 group_by（用 fold/itertools）、字形簇。

  第05章
  - P1 Weak + 循环引用泄漏（严重）：Java GC 能回收循环引用，Rust Rc 循环内存只涨不降。补 downgrade/upgrade，子强父弱。
  - P1 Drop/RAII 正经讲一节 + std::mem::drop。
  - P1 Deref/解引用强制转换：为什么 &String 能传 &str、&Vec<T> 能传 &[T]。
  - P1 锁中毒 poisoning：.lock().unwrap() 里 unwrap 在解什么。
  - P1 mod foo; 必须显式声明：新建 .rs 不声明就不参与编译（Java 丢进包目录即生效，反差大）。
  - P2 expect 优于裸 unwrap、.map_err()、unwrap_or。

  第06章
  - P1 tokio 运行时选择：多线程 vs current_thread、features=["full"] 的编译/体积代价。
  - P1 spawn_blocking / 阻塞拖垮运行时：async 里做阻塞/重 CPU 占死 worker。虚拟线程习惯带过来是灾难。
  - P1 async Send 约束：跨 .await 存活的变量都必须 Send，是 future cannot be sent between threads safely 报错的根因。
  - P1 sqlx 编译期检查需连真库（或 cargo sqlx prepare），否则 CI 无库编译失败。
  - P2 block_on 桥接、async-trait、Stream+join_all/FuturesUnordered、函数染色、Pin 露而不讲。

  第07章
  - P1 测试默认并行执行（最重要心智）：与 JUnit 默认串行相反，多测试共享临时文件/环境变量会 flaky。
  - P1 无 setup/teardown（@BeforeEach），靠辅助函数 + Drop guard。
  - P1 assert_eq! 对自定义类型需 #[derive(Debug, PartialEq)]。
  - P2 参数化测试 rstest、dbg! 宏、文档测试细节。

  第08章（遗漏最严重）
  - P1 std::sync::Mutex 不可重入 → 自死锁：Java 锁可重入，Rust
  不可，同线程二次加锁永久阻塞。用户点名的"死锁"全篇零覆盖。
  - P1 guard 生命周期延长致死锁：if let/match 把临时 guard 延长到整块。
  - P1 原子类型 AtomicUsize 等：计数器该对照 AtomicInteger，文档却上 Mutex。
  - P1 OnceLock/LazyLock 全局/惰性单例（对标 Java 静态初始化/holder）。
  - P1 边界：Rust 只消除 data race，死锁/逻辑竞态照样发生（否则给虚假安全感）。
  - P2 中毒动机 + parking_lot、Send/Sync 原理（auto trait、MutexGuard: !Send）、channel 选型（mpsc
  单消费者/crossbeam/tokio）。

  第09章
  - P1 anyhow vs thiserror 分工：库用 thiserror 类型化错误，应用用 anyhow + .context()；#[from]+?
  机制。用了两者却没说何时用哪个。
  - P1 泛型 vs dyn：UserService<R> 泛型泄漏进 AppState 签名，服务多就爆炸；真实项目用 Arc<dyn UserRepository>。
  - P1 中间件/tower：Filter/Interceptor/AOP 对应 tower/TraceLayer，全篇只有 #[instrument]。
  - P2 请求校验 validator、优雅停机、derive(Clone) 泛型过约束、async trait 为何需 Send。

  第10章（FFI 核心几乎全缺）
  - P1 #[repr(C)]：跨 FFI struct 必须加，否则字段重排、一过边界 UB。
  - P1 CString 悬垂：CString::new("hi").as_ptr() 里 CString 立即 drop，ptr 悬垂。补
  into_raw/from_raw、"哪侧分配哪侧释放"。
  - P1 panic 不能穿越 extern "C"（UB），用 catch_unwind。
  - P1 UB 严重性：不是"顶多崩溃"，编译器可能静默删掉边界检查，比 Java Unsafe 恶劣。
  - P2 Miri、unsafe 真实场景、Buffer 示例缺构造/Drop、迭代器零成本对照例。

  第11章 Todo API（代码能跑，问题在只覆盖 happy path）
  - P1 JSON 反序列化失败绕过统一错误响应：坏 JSON 由 Json<T> 自己拒绝，返回默认 400，不走 AppError，格式变两套。对照
  @ControllerAdvice。
  - P1 AppError 缺 Internal/500 变体：碰 sqlx::Error 无处安放。补 Internal(anyhow::Error)，500
  只给通用文案、细节走日志。
  - P1 状态共享 std vs tokio Mutex：std 的 guard 不能跨 .await。
  - P2 测试只断言状态码不验 body、缺 delete/404 路径；extractor 顺序陷阱；无 TraceLayer 访问日志；请求校验。

  第12章 部署
  - P1 Docker 无依赖缓存层（最严重）：改一行代码所有依赖重编。给 cargo-chef 版 Dockerfile。
  - P1 distroless（gcr.io/distroless/cc-debian12）：glibc 动态链接甜点，比只提的 debian-slim/scratch 更该推荐。
  - P2 musl 分配器多线程性能坑（换 jemalloc/mimalloc）、scratch 的 CA/时区/DNS 具体处理、metrics+链路追踪（对标
  Micrometer/Actuator）、panic=abort 杀全进程 + CatchPanicLayer、.dockerignore+--locked。

  附录·速查表
  - P1 缺 ?（受检异常传播 ↔ foo()?）、mut/let、Lombok/Object
  方法↔derive/trait（toString↔Display、equals/hashCode↔PartialEq/Eq/Hash、Comparable↔Ord）。
  - P2 Stream 操作表太短、懒加载单例、unwrap↔orElseThrow、生命周期 'a、match↔switch。

  附录·供应链（最扎实）
  - P2 CI cargo install 从源码编译慢（用 cargo-binstall/install-action）、deny.toml 缺
  [advisories]、传递依赖漏洞修法（cargo update -p X --precise）、cargo-vet/SBOM。
