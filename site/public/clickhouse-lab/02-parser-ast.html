SQL 解析器与 AST：先把句子拆成树

两条 SQL 都报错，但一条停在 Parser，一条停在 Analyzer。先把文本拆成 token，再拼成 AST；这棵树忠实记录「你写了什么」，但还不回答「它指的是什么」。

1

表象观察：两种报错，两个站点

同样是「SQL 写错了」，错误发生的层完全不同。

「先分清是文本结构错了，还是名字/类型错了。」
SQL→Lexer/Parser→AST→Analyzer→QueryTree

少右括号、关键字拼错、引号不配对，停在 Parser；列名拼错、类型不匹配、聚合嵌套错误，能过 Parser，停在 Analyzer。前者看文本，后者看元数据。

2

静态分解：Token、AST、QueryTree 各是什么

对象谁产生回答什么例子
TokenLexer这段字符是什么类型SELECT / region / 'paid'
ASTParser用户写了什么结构ASTSelectQuery(select, from, where...)
QueryTreeAnalyzer名字指的是什么、类型是什么ColumnNode(shop.orders.region)
QueryPlanPlanner引擎决定怎么执行ReadFromMergeTree → AggregatingStep

解析器只造第二行；第三、四行在后面的章节。

3

动态分析：一条 SQL 的解析顺序

「解析是单向的：先 WITH，再 SELECT/FROM，最后 GROUP BY/ORDER BY/LIMIT。」
阶段读什么产物
WITHCTE / 标量别名with 子树
SELECT投影表达式 + 别名select 表达式列表
FROM表/子查询/表函数/JOINtables 子树
WHERE/GROUP BY/HAVING过滤与聚合对应子节点
ORDER BY/LIMIT/SETTINGS排序、截断、查询设置对应子节点

PREWHERE 是 ClickHouse 自己的语法，位置在 WHERE 之前；它不是标准 SQL，解析器单独处理。

4

动静融合：AST 节点和别名规则

写法解析结果Analyzer 怎么处理
COUNT(*) AS ordersASTFunction(count, alias=orders)输出列名 = orders
ORDER BY ordersASTIdentifier(orders)优先匹配真实列，再匹配别名
WHERE double_amount > 100ASTIdentifier(double_amount)ClickHouse 扩展：可解析别名
SELECT amount AS region, region两个 ASTIdentifier真实列优先（prefer_column_name_to_alias=false）

EXPLAIN AST 能看到结构，但看不到最终绑定；要看绑定用 EXPLAIN SYNTAX 或 EXPLAIN PLAN。

5

环境场景：解析器的边界与安全

max_query_size256 KiB；防止超长 SQL 拖垮解析器。
max_parser_depth1000 层；防止递归爆栈。
max_ast_elements5 万节点；防止巨型 AST。
查询参数{name:Type} 把值变字面量，避免 SQL 注入。
MySQL 对比Bison/LALR vs 手写递归下降；错误提示和扩展性不同。
FORMAT输出格式声明，不是 SELECT 子句；位置写错会报语法错误。
6

复盘自测

一页带走

解析分两步：Lexer 切 token，递归下降 Parser 拼 AST。

· 解析分两步：Lexer 切 token，递归下降 Parser 拼 AST。

· AST 只记录「写了什么」，不裁决别名/类型/表绑定。

· 语法错误停在 Parser，语义错误停在 Analyzer。

· AST/QueryTree/QueryPlan 是三棵不同的树，EXPLAIN 工具也不同。

· 解析器有硬限制：256 KiB、1000 层、5 万节点。
