表象观察：EXPLAIN PIPELINE 为什么有十几个算子

一条 SQL 变成图，图里的节点比 SQL 子句多得多。

「Plan 是步骤，Pipeline 是数据流；一个步骤可能变成多个 Processor。」
Plan→Source→Transform→Aggregate→Sink

ReadFromMergeTree 可能生成 8 个读取流；ResizeProcessor 合并/拆分；AggregatingTransform 做部分聚合；MergingAggregatedTransform 再合并。每个都是独立 Processor。

2

静态分解：Processor、Port、Chunk

对象职责关键方法/字段
IProcessor处理数据的最小单元prepare / work / schedule
PortProcessor 之间的连接点push / pull / hasData / canPush
Chunk列向量块columns + num_rows
PipelineExecutor调度整张图execute / executeStepImpl

Processor 不认 SQL，只认输入口/输出口；所以同一套算子能复用于不同查询。

3

动态分析：任务驱动与背压

「prepare 串行，work 并行；端口满，上游停。」
状态含义下一步
NeedData输入口没数据先跑上游
Ready可以 work执行计算
PortFull输出口满等下游消费
Finished端口关闭结束

背压让管道里的中间结果不会无限增长；但聚合/排序会在算子内部物化，内存仍然可能超。

动静融合：Plan step 与 Processor 的对应

Plan stepProcessor说明
ReadFromMergeTreeMergeTreeSelectPool / Read多流读取
ExpressionStepExpressionTransform计算/过滤
AggregatingStepAggregatingTransform部分聚合
MergingAggregatedStepMergingAggregatedTransform合并状态
LimitStepLimitTransform截断并通知上游

用 EXPLAIN PIPELINE graph=1 看真实连接；用 compact=1 看简洁版。

环境场景：并行度、内存与屏障

max_threads默认自动=硬件线程；调大不一定更快。
max_block_size65409 行；块太小调度多，太大缓存差。
max_streams_to_max_threads_ratio默认 1；控制读取流数与线程数比例。
聚合/排序/JOIN会在算子内部物化，形成事实上的屏障。
Spark 对比Spark stage 间有 shuffle barrier；ClickHouse 更像连续数据流。
LIMIT排序后的 LIMIT 通常不能提前停止读取。

复盘自测

一页带走

QueryPlan 是步骤树，QueryPipeline 是 Processor + Port 图。

· QueryPlan 是步骤树，QueryPipeline 是 Processor + Port 图。

· 每个 step 通过 updatePipeline 变成 Processor；Chunk 是列向量块。

· 背压来自端口满；线程不绑定算子，任务驱动调度。

· 聚合通常两阶段：本地部分聚合 + 合并状态。

· 排序/聚合/JOIN 会物化，是流水线里的事实屏障。
