查询分析器与优化器：把树修成能执行的形状

AST 只说明你写了什么；QueryTree 绑定名字和类型；QueryPlan 决定先读什么、再算什么。优化器的大部分工作不是「换算法」，而是把过滤、列、granule 裁到更少。

表象观察：同一条 SQL，两种计划形状

一个 PREWHERE、一个 LIMIT、一个投影，可能让读取量差一个数量级。

「计划形状决定读多少，SQL 文本只决定语义。」
AST→QueryTree→QueryPlan→优化后计划

同样查 4 列，优化前可能读 60 列；同样按 status 过滤，优化前可能在聚合后才过滤。优化器把「读」和「算」挪到更早、更少数据的位置。

2

静态分解：Analyzer 与 Optimizer 各管什么

阶段输入输出典型动作
QueryTreeBuilderASTQueryTree结构翻译
QueryAnalyzerQueryTree绑定后的 QueryTree绑表/列/别名、类型推断
QueryTreePassQueryTree改写后的 QueryTree常量折叠、函数改写、列裁剪
PlannerQueryTreeQueryPlan生成 Read/Filter/Agg/Sort 步骤
OptimizerQueryPlan更便宜的 QueryPlan下推、裁剪、合并、read-in-order

前四步是「理解 SQL」，第五步是「改成便宜形状」。

3

动态分析：优化器的四个常用动作

「优化器不是魔法，多数动作是「把工作挪早 / 挪少」。」
动作做什么收益代价/边界
过滤下推FilterStep 挪到 Read 上面少读 part/granule/列复杂表达式/子查询可能下不去
列裁剪删掉没人用的输出列少读 .binSELECT * 会抵消
PREWHERE先读高选择性列，排掉行少读宽列选择性低时反而多一次读列
read-in-order按存储顺序读省排序、可提前 LIMITORDER BY 必须是排序键前缀

这些动作由设置控制：query_plan_filter_push_down=true、optimize_read_in_order=true、optimize_move_to_prewhere=true。

4

动静融合：用 EXPLAIN 看优化器做了什么

命令看什么典型用途
EXPLAIN SYNTAX改写后的 SQL别名展开、函数改写
EXPLAIN PLAN步骤树读了哪些列、哪个索引、多少 granule
EXPLAIN ANALYZE实际执行后的步骤树看每步真实耗时/行数

先看 EXPLAIN PLAN 的 Granules，再看 EXPLAIN ANALYZE 的耗时；不要只凭 SQL 猜。

5

环境场景：规则驱动 vs 代价驱动

MySQL CBO依赖统计/直方图，选代价最低的索引和 JOIN 顺序。
ClickHouse 规则下推/裁剪/read-in-order 都是模式匹配，计划稳定、易解释。
表设计优先排序键/分区键选错，事后加索引很难救。
FINAL 的代价去重合并会让 read-in-order/PREWHERE 等优化受限。
LIMIT 的边界无 ORDER BY 可提前停；有 ORDER BY 通常要读完候选行。
别名冲突真实列优先，写错会绑到另一列；用 EXPLAIN SYNTAX 核对。
