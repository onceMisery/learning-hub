1

表象观察：三个查询，三种慢法

前缀过滤、模糊匹配、重聚合，需要三件不同工具。

「主键管前缀，skip index 管非前缀，projection 管另一种布局。」
WHERE 前缀→主键→跳 granule

不在前缀里的条件，主键帮不上忙；skip index 用 minmax/set/bloom 再跳；固定排序/重聚合用 projection 换一份数据。

2

静态分解：主键、skip index、projection

工具解决什么代价
主键稀疏索引排序键前缀过滤排序键设计决定一切
skip index非前缀条件跳 granule存储/写入/假阳性
projection另一种排序/预聚合额外存储/写入放大/物化

主键索引不是 MySQL 二级索引；它只定位 granule。

3

动态分析：主键前缀规则

「排序键 (region, status, event_time)：region 是前缀，status 是第二，event_time 是第三。」
WHERE能用前缀结果
region='east'region能用
region='east' AND status='paid'region,status能用
status='paid'无不能用
event_time > ...无不能用

ORDER BY 与 PRIMARY KEY 可以不同，但 PRIMARY KEY 必须是 ORDER BY 的前缀。

4

动静融合：skip index 与 projection

类型适合注意
minmax范围/有序没排序时 min/max 覆盖全域
set(max_rows)低基数等值/IN高基数装不下
bloom_filter高基数等值假阳性
ngrambf/tokenbf子串/整词短字符串效果差
projection固定排序/重聚合存储/写入/物化

skip index 只保证「一定没有」；命中后仍要回表过滤。

5

环境场景：常见坑与验证

函数包裹toDate(event_time)=... 可能让主键失效。
OR两个分支无法同时满足前缀，可能退化成全扫。
高基数 skipset(100) 装不下 user_id；bloom 假阳性高。
未物化ADD PROJECTION 只对新 part 生效。
FINAL去重合并让很多优化受限。
验证EXPLAIN indexes=1 + force_data_skipping_indexes。

复盘自测

一页带走

主键是稀疏索引，只对排序键前缀有效。

· 主键是稀疏索引，只对排序键前缀有效。

· skip index 按 GRANULARITY 跳 granule，只保证「一定没有」。

· projection 是另一种排序/聚合布局，占存储、放大写入。

· EXPLAIN indexes=1 看 Parts/Granules；force 验证索引是否被用。

· 表设计（排序键/分区键）比事后加索引重要。
