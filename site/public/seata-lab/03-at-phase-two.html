SEATA · AT 二阶段

提交与回滚：两条时间线

提交可以先返回，因为删 undo 是可重试的清理；回滚必须等数据改完，因为反向 SQL 会碰到锁、约束和脏写。

1

表象观察：先把它当黑盒

不急着拆类，只看它对外表现出什么。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

从 TM 看，提交和回滚都只有一个返回值。从 RM 看，它们是两条完全不同的事：提交是删日志，回滚是改数据。

业务异常 / 超时→ TC 决议 →提交：AsyncCommitting → 异步删 undo ↳回滚：Rollbacking → 反向 SQL

黑盒视角最容易误判的两句话：「commit 返回了，所以二阶段完成了」和「undo_log 还在，所以提交失败了」。这两句都不成立。

动态分析：一步一停看顺序

重点不是记住箭头，而是记住每一步「谁在等谁」。

动态分析看三件事：顺序、状态、触发条件。
路径关键动作返回时机失败处理
提交AsyncCommitting → clean 锁改完状态就返回分支提交重试；删 undo 重入队
提交收尾BranchCommit → AsyncWorker入队即回 PhaseTwo_Committed队列满时紧急清队列再入队
回滚Rollbacking → 逆序分支等所有分支回滚结果可重试失败每秒重试
回滚校验before/after/current 对账反向 SQL 之前脏写/唯一键冲突不可重试
墓碑undo_log 不存在时插 GlobalFinished一阶段后到时撞唯一键阻止已决议回滚的分支再提交

把「返回时机」这一列记住：提交是状态承诺，回滚是数据操作。监控上，TC 返回 Committed 之后仍可能有分支在重试；回滚返回 Rollbacked 之前，数据可能已经被改过多次。

5

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，前面看到的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
异步提交队列client.rm.asyncCommitBufferLimit 默认 10000；满了会拖慢 BranchCommit 线程。
undo 数据校验client.undo.dataValidation 默认 true；关掉就没有脏写拦截。
重试上限maxCommit/RollbackRetryTimeout 默认 -1；无限重试会长期占锁。
TC 会话存储回滚状态要落库；TC 重启后靠它继续驱动。
数据库约束反向 INSERT 可能撞唯一键，Seata 会判为不可重试。

边界：本页默认单 TC、AT 分支；XA 的 prepare/commit 与 TCC/Saga 的二阶段不走这套 undo 回放。批量删除与队列容量只给默认量级。

复盘自测

四个问题，检查你是否能在边界上做判断。

自测不是复述结论，而是检查你能否在边界上做判断。

一页带走

提交先承诺，回滚先改数据。

· 不要把「TC 返回 Committed」当成「所有分支收尾完成」；也不要用 undo_log 是否存在判断提交成败。

· 回滚是逆序的：分支逆序、分支内 SQL 也逆序；脏写校验只看镜像抓到的列。

· 回滚失败默认不释放全局锁；手工清理之前先校准数据。
