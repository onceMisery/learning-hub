1

表象观察：先把它当黑盒

不急着拆类，只看它对外表现出什么。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

站在业务代码的角度，`executeUpdate()` 返回了 1，就算成功。它不告诉你镜像查了几次、锁有没有抢到、undo_log 写没写。

UPDATE ...→ DataSourceProxy / ConnectionProxy →beforeImage + 业务 SQL + afterImage ↳注册分支 + undo_log + 本地 COMMIT

这条链路里，真正会让业务线程停下来等的是「注册分支 + 抢全局锁」。SQL 本身反而先跑完了。所以并发冲突的表现通常是：update 成功，commit 报 `LockKeyConflict`。

动态分析：一步一停看顺序

重点不是记住箭头，而是记住每一步「谁在等谁」。

动态分析看三件事：顺序、状态、触发条件。
动作发生在哪谁在等失败会怎样

注意「注册 + 锁」在「业务 SQL」之后。全局锁保护的是提交窗口，不是执行窗口；真正让并发写排队的是 beforeImage 拿到的本地行锁。

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，前面看到的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
主键镜像按主键回查，锁键按主键构造；无主键用不了 AT。
可解析的 SQL存储过程、特殊方言、动态拼接可能退化成 PlainExecutor。
undo_log 表每个参与库都要建；唯一键 (xid, branch_id)。
TC 锁存储file/db/redis/raft 决定锁放在哪、多 TC 是否共享。
数据库隔离级别AT 默认读到未全局提交的数据；需要时用 SELECT FOR UPDATE 收紧。

边界：本页只画 AT 的写路径；批量 SQL、Savepoint、多数据源、不同数据库的 FOR UPDATE 行为未展开。锁键数量受 RPC 传输上限约束。

复盘自测

一页带走

SQL 先跑，镜像随后，锁在提交前，undo 在同一事务。

· 全局锁不是 SQL 执行锁；它保护的是本地提交到全局决议之间的窗口。

· 分支在 commit 前懒注册；只读、无主键、解析失败、无代理都会让分支消失。

· 回滚的素材是 beforeImage + afterImage；默认只抓更新列，不是整行。
