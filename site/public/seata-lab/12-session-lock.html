会话与锁：什么时候放

会话锁保护同一个 XID，全局行锁保护同一行。AT 提交时提前放行锁，回滚失败则默认保留。

表象观察：先把它当黑盒

不急着拆类，只看它对外表现出什么。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

TC 的账本有两层：一层是事务状态，一层是哪一行被谁占着。前者是会话，后者是锁。

GlobalSession→LockManager→file / db / redis / raft

最容易讲错的是释放时机：AT 提交在 commit 受理时就放全局锁，不等二阶段完成；回滚失败则默认保留。

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，前面看到的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
store.session.modefile/db/redis/raft；决定会话和锁的存储。
rollbackFailedUnlockEnable默认 false；回滚失败不释放锁。
锁键table:pk；复合主键用 _ 连接。
多 TCfile 模式锁不共享；db/redis/raft 才有多节点语义。
会话锁超时GlobalSession 内部锁有等待超时，不是永久阻塞。

边界：本页不展开 db/redis/raft 三种锁的具体存储结构；只讲释放时机和两把锁的区别。

一页带走

会话锁管同一 XID，全局行锁管同一行。

· AT 提交在 commit 受理时提前放全局锁，不等二阶段完成。

· 回滚失败默认保留锁；这是保护，不是泄漏。

· file 锁不跨机；db/redis/raft 才有集群语义。
