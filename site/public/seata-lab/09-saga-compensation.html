正向状态链，反向补偿链

Saga 不是长事务，是一串短事务。失败时不是数据库回滚，而是按已成功状态栈逆序调用补偿。

1

表象观察：先把它当黑盒

不急着拆类，只看它对外表现出什么。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

Saga 把一个长流程拆成很多本地事务：创建订单、扣库存、创建履约。每一步都提交，整个流程没有全局锁。

state 1→state 2→失败↺补偿链

失败时不是数据库回滚，而是按业务语义撤销。补偿方法可能失败，也可能不幂等，所以 Saga 的难点在补偿设计。

动态分析：一步一停看顺序

重点不是记住箭头，而是记住每一步「谁在等谁」。

动态分析看三件事：顺序、状态、触发条件。
阶段状态机TC数据可见性
正向逐个 ServiceTask全局生命周期每个本地事务后可见
失败Catch 匹配等结果中间态保留
补偿CompensationTrigger → 逆序补偿BranchRollback → engine.compensate补偿服务改业务状态
提交TC commit 可能 forwardBranchCommit → engine.forward继续执行剩余 state

Saga 的 TC 会话通常只有一个虚拟分支，真正的状态推进和补偿都在引擎本地；不要用分支数判断进度。

5

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，前面看到的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
状态机定义JSON DSL 要版本化、校验、持久化。
状态日志存储Saga 引擎要能 reload 状态机实例。
补偿服务必须幂等，能承受 TC/引擎重试。
中间态每个本地事务提交后可见，查询侧要处理。
TC只维护全局生命周期；默认不逐 state 注册分支。

边界：本页以简单线性状态机为例；分支、子状态机、重试配置和 RecoverStrategy=Forward 未展开。
