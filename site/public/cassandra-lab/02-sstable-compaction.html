1

表象观察：先把它当黑盒

不急着拆类，只看它对外表现出什么。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

站在使用者的角度，这一层对外的表现是三句话：写永远快——落盘是后台的事；读偶尔变慢——账本越攒越多、点查要问的本数在涨；删除不立刻腾空间——盘上个头纹丝不动，要等很久才缩。三件事指向同一个后台角色：压缩（compaction，是并账，不是文件压缩）。

Memtable 满→ flush 出一本不可变 SSTable →账本架上越攒越多→压缩归并收敛 ↳墓碑另等 gc_grace 过线

黑盒承诺：写路径永远不等旧账；同一行数据的多个版本由压缩负责收敛；删除在逻辑上立即生效（读时被墓碑压住），物理上晚十天。它不承诺「磁盘占用恒等于数据量」——合并期间新旧账并存，空间一度翻倍是正常形态。

先记住一个反直觉的点：SSTable 写完之后一个字节都不会再改。下一节拆开看这本账的组成。

动态分析：一步一停看顺序

重点不是记住箭头，而是记住每一步「谁在等谁」。

动态分析看三件事：顺序、状态、触发条件。
相位谁在等谁失败会怎样
写入 / 写墓碑写线程等 Memtable 接客内存胀满 → flush 跟不上，见第 2 章
flush #2 / #3flush 线程等 SSTable 写完写一半崩溃 → 半成品作废，重誊即可
策略评估CompactionManager 等策略挑输入STCS 凑不满就继续攒，不阻塞任何读写
归并裁决归并线程读旧账写新文件中途失败 → 新文件作废，旧账无损
换账原子替换（瞬间）替换前读旧账、替换后读新账，答案一致
gc 窗口压缩等 gc_grace 过线副本未归队 → 墓碑继续保留，宁多勿失
墓碑退场等归并输入覆盖全部旧数据有更老数据未带上 → 只能继续搬运

这张表里最值得盯的是两行高亮：「策略评估」决定账本架的形状——STCS 按大小凑批、LCS 按层级归并；「gc 窗口」是 Cassandra 独有的等待——RocksDB 的墓碑沉到底层就能丢，这里还要等失联副本归队。

注意墓碑的三段人生：写入时它是普通数据、归并时它是「当权的版本」、窗口期它是「只能搬不能清的客人」。同一份记录在三个阶段被三种眼光看待——排障时先问「这个墓碑几岁了」，再判断为什么空间还不缩。

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，前面看到的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
compaction 策略默认 STCS 4/32（CompactionParams.java:99-102）；读多换 LCS、时序换 TWCS、跟官方推荐走 UCS。
gc_grace_seconds864000s=10 天（TableParams.java:446）；删得多的表可调小，但先想清楚副本失联窗口。
副本与修复gc_grace 存在的理由：hint 补送与修复要把墓碑送到失联副本（第 13 章）。
磁盘余量归并期间新旧账并存，STCS 大账合并的空间翻倍最猛；预留 40%~50% 余量。
tombstone_warn_threshold1000（Config.java:636）；单次查询扫过即告警，提醒删除模式已经伤到读。

一页带走

写完封账不改，后台凑批并账；墓碑先等十天，过线才能退场。

· SSTable 是一组组件文件（Data/Index/Summary/Filter/TOC…），文件名里的 id 越大账越新；写完一个字节都不改。

· 压缩 = CompactionManager 派活 + 策略挑输入 + CompactionIterator 归并：旧版本丢弃、读写全程不阻塞、原子替换换账。

· 默认 STCS 4/32 凑批；LCS 160MB 分层、层内不重叠；墓碑清除要过 gc_grace（10 天）+ 无更老数据遮挡两道闸。
