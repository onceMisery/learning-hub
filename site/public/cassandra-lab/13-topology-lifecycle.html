1

表象观察：先把它当黑盒

新机器一启动、还没进环，数据目录就在进流量；死机器一台，摘掉它线上毫无感觉。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

黑盒视角三句话：node6 启动后 43 分钟自己变成 UN——没有敲任何入列命令（auto_bootstrap 默认开）；UJ 期间它已经在收写（数据目录进流量），但客户端读永远找不到它；node4 强摘前后线上读写无感——QUORUM 的账从它卡死那一刻就重算了。三件「没人指挥却自己发生的事」，背后是同一本账本在推进。

新节点启动 / 死节点强摘（输入）→ 拓扑变更（黑盒） →入列：分 token → 拉 150GB → 三段式 JOIN → UN →强摘：placement 重算 → 幸存者互拷 180GB → LEFT →全程：线上读写不停（双归属窗口 / QUORUM 重算）

反直觉的点先记一个：removenode 不是「把 node4 的数据搬走」——死节点一个字节都交不出来。它是让幸存者从另外两个活副本把第三份重新抄齐。数据流向和直觉相反。

表里两格绿色是两章的扣合点：repair 与拓扑变更共用同一套 streaming，且搬完必补修。RocksDB 对照（第 1 章）：它的「搬家」是同机换目录（db_paths 按层放盘、MANIFEST 原子切账），没有跨网搬运、也没有双归属——单机独占一个目录（LOCK 文件），一致性只涉及一台。

5

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，拓扑变更的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
seed 可达新节点至少要认识一个 seed（yaml:755-764）；seed 全挂则报到失败、入列卡在 STARTING。
schema 一致入列前要等全集群表结构对齐（CassandraRelevantProperties:91-96）——否则数据搬来了表结构不认识。
网络带宽150GB/40 分钟 ≈ 62MB/s 持续；万兆以下网卡会拉长窗口，双归属期写放大更久。
磁盘余量缩容后每台 225GB：接手前余量必须够；removenode 一次摘多台接近平方级叠加。
LockedRanges并发变更动同一批 range 会被 CMS 拒绝——排期错峰，别指望锁兜底。
断点续传已交割 range 记在 system 表，重启跳过（BootstrapAndJoin:378-381）；nodetool bootstrap resume 接管。

边界：本页环图为单环示意（实际 vnode 16 段）；replace 走 PrepareReplace 继承 token，本页只在算术卡对照。

复盘自测

六个问题，检查你是否能在边界上做判断。

自测不是复述结论，而是检查你能否在边界上做判断。

一页带走

先进写表拉数据、再换读表退旧主；死者零参与、幸存者翻拷、搬完必补修。

· 入列线：t0 Register 领 NodeId → t1 allocateTokens 挑 16 个均衡位 → t2 StartJoin(E95) 进写表 + StreamPlan(BOOTSTRAP) 16 份流拉 150GB（双归属窗口：收写不服务读）→ t3 MidJoin(E96) 进读表 → t4 FinishJoin(E97) 旧副本退写表 → Auto Repair 增量补账 → UN。

· 强摘线：预检（:131 不能摘自己 / :136 活着请 decommission）→ PrepareLeave(REMOVENODE) placement 重算 → 4 台各从另两个活副本进 45GB（RESTORE_REPLICA_COUNT）→ 广播 LEFT。镜像律：decommission 数据从退场者流出，removenode 数据在幸存者间翻拷。

· 账：5→6 每老机出 30GB（1/6）、node6 进 150GB；5→4 四台各进 45GB；replace 环不变、新机独进 180GB。RocksDB 对照：单机按层放目录（db_paths）+ LOCK 独占，没有拓扑——跨网搬运与双归属窗口是集群才有的命题。
