1

表象观察：先把它当黑盒

不急着拆哈希，只看数据摊位表现出的规律。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

站在业务的角度，Cassandra 的摊位规则表现出三个事实：按分区键查，毫秒出；按普通列查，被拒或全表扫；换一行数据，副本名单完全换一批机器。

分区键 id=47（输入）→ 分区器 + 令牌环（黑盒） →副本名单 {node2, node4, node5} →id=48 → {node4, node1, node5}（毫不相干）

黑盒对外承诺：任何分区键都能就地算出摊位，不问任何人；哈希把任何键分布打均匀，任何节点只承担约 1/N。它不承诺跨分区的范围有序——分区内有序、分区间无序，是这套均匀性的代价。

反直觉的点先记一个：「数据放在哪」跟「哪台机器空」毫无关系——座次由哈希决定，负载均衡靠的是哈希的均匀性，不是调度。

动静融合：角色 × 场景

同一机制在「写入、读取、扩容、节点失败」四个场景里扮演不同角色。

把部件放回阶段里，才能看清谁在什么时候接力。
场景定位链干什么谁受影响
写入 id=47协调者现算 token，名单发 Mutation只有 3 台收到流量，node1 无感
读取 id=47同一条链，同一份名单读写的名单永远一致（无副本漂移）
新节点入环智能分配挑 16 个新 token 位每段数据的顺时针序列被「插队」改写
node4 失败它的 16 段各自由顺时针下家接手负载摊 16 份，而不是压垮一台
热分区同一分区键无法拆散单节点过热——只能改分区键设计

最后一行是这套机制的硬边界：一个分区 = 一个不可拆的槽。大分区（同一个键下百万行）会让单节点读慢、修复贵——建模时把大实体拆成多个分区键，是 Cassandra 的必修课。

六个问题，检查你是否能在边界上做判断。

一页带走

哈希定摊位，顺时针数副本；分区内有序，分区间无序。

· 定位链：分区键 → murmur3 → 64 位 token → 环上落点 → 顺时针 RF 个 = 自然副本。

· 均匀不靠调度靠雪崩：id=47 与 id=48 摊位毫不相干，任何键分布都被打匀。

· vnode 16 段 + 智能分配：失败负载摊 16 份；热分区是硬边界，只能靠建模拆。
