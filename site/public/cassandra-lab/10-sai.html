1

表象观察：先把它当黑盒

同一句 WHERE name='阿福2'，有无索引的两个世界，表观差异只有三件事。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

黑盒视角三句话：无索引时引擎直接拒绝（name 定不了位，除非加 ALLOW FILTERING 全表扫）；有索引时同一句毫秒返回，且返回的还是最新版本（ts=1005 的阿福2）；写入侧几乎无感——每次 INSERT 多了一笔看不见的小记账，没有额外的索引维护作业在跑。

SELECT … WHERE name='阿福2'（输入）→ SAI（黑盒） →有索引：裁文件 → 读 posting → 回表，返回 1 行 →无索引：拒绝或全表扫 300 万行 →写侧：每索引列 +1 笔内存账，flush +3 个小文件

反直觉的点先记一个：索引文件不在「索引目录」里，就躺在 SSTable 身边，文件名带着宿主的名字（nb-11-big-SAI+aa+…）。删掉一本 SSTable，它的索引文件跟着消失——这就是「存储附着」四个字的全部含义。

动态分析：一步一停看顺序

两条线各八个关键时刻——建索引看「索引何时知道一行」，查询看「哪些书根本不用翻」。

动态分析看三件事：顺序、状态、触发条件。
相位建索引线（W）查询线（Q）

盯两张高亮行：W 线 270° 的「两阶段」解释了为什么索引和数据永远不脱节（同一本 SSTable、同一个事务里写完）；Q 线 450° 的交集是 SAI 多条件的底气——posting 有序可跳，交集才不必逐行。

同一批部件在不同阶段接力——内存层只在 memtable 活着，盘上层活得和 SSTable 一样久。

表里两格绿色是同构点：flush/压缩时「索引跟着不可变文件走」两边都在做，只是 RocksDB 把索引写在 SST 内部（服务键），SAI 写在旁边（服务值）。多出来的内存层是 SAI 特有——RocksDB 的 memtable 本身有序，无需二级。

5

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，索引的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
压缩线程池索引构建以 compaction 面目出现（README:43）——压缩堆积时，新建索引的构建也排队。
memtable 生灭通知Group:277-288 听 renewed/switched/discarded，内存索引随 memtable 生灭，不泄漏。
墓碑后置过滤索引不记删除（Group:182）：命中行可能已被墓碑遮蔽，FilterTree 复核是最后一道闸。
查询配额QueryContext:86-93 到点抛 QueryCancelled——索引查询不许没完没了，运维抓超时看这里。
流式传输 / 快照索引文件随 SSTable 整体搬运、进快照（README:33-34）——bootstrap 不用在目标端重建索引。
列型与选项SUPPORTED_TYPES（:168-174）几乎全开；文本默认整词，normalize/case_sensitive 可调。

边界：本页画的是单列等值查询 + 单机视角；IN / CONTAINS / 范围、集合列与 analyzed 文本在正文有文字交代，向量索引留给第 12 章。

复盘自测

六个问题，检查你是否能在边界上做判断。

自测不是复述结论，而是检查你能否在边界上做判断。

一页带走

写进内存账、flush 长文件；查询先裁本、posting 再回表。

· 建索引线：apply:438 顺手带索引 → 内存 InMemoryTrie（TrieMemoryIndex:61，第 4 章同款）→ flush 两阶段（数据 + RowMapping → complete():189 写 -SAI+aa 文件族）→ 压缩随行重写（handleNotification:258-289）。

· 查询线：executeLocally 分岔（ReadCommand:536-554）→ View.match 裁 SSTable（S11✓ S12/S13✗）→ posting [rowId 1] → 回表 id=47 → FilterTree 复核。对照：无索引 3 本全开、300 万行逐行筛。

· posting list：升序 rowId 差分 + 128/块 FoR + 跳表；advance 让交集小侧到头、大侧免读。索引是本地结构，一致性仍走 QUORUM。RocksDB 的索引在 SST 内部服务「键在哪」——按值找行它得靠应用层自建反查表，那就是手工版的 SAI。
