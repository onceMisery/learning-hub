一条连接的字节舞步

cqlsh 连上 node3:9042 之后，那句 UPDATE users SET name='阿福2' WHERE id=47 在 TCP 上是一串什么模样的字节？看握手四步怎么走、59 字节的 QUERY 帧怎么装、stream id 怎么让两条查询挤一条连接乱序回家、心跳为什么只要 9 个字节——帧头 9 字节会逐字段高亮给你看。

1

表象观察：先把它当黑盒

不急着拆字节，只看「客户端与节点之间的对话」对外表现出的规律。

先把系统当黑盒：只看输入、输出和边界，不急着解释内部。

对着 9042 端口抓包，表观现象就四条：开头总有几个看不懂的小包（握手）；之后每句查询对应一来一回（多的时候同时好几个来回交错）；连接闲着也会周期性冒小包（心跳）；全部是二进制，没有一个可读的字。

一条 TCP 连接（输入）→ 原生协议黑盒（9B 信封 + opcode + stream） →握手 4 步后才能查询 →一条连接同时跑多句查询（乱序回家） →空闲心跳 9 字节保活

黑盒对外承诺的只有一件事：带同一 stream 号的应答，一定属于那次请求。它不承诺应答按发出顺序回来，也不承诺一次往返只占一个包——把这两条「不承诺」看清，驱动超时排查就少走一半弯路。

反直觉的点先记一个：握手的 242 字节比第一句查询本身还贵——这就是所有驱动都拼命维持长连接的原因。

重点不是背字节，而是记住每一步「谁发、多大、为什么」。

动态分析看三件事：顺序、状态、触发条件。

5

环境场景：它依赖什么才能成立

拆掉任意一个外部依赖，前面看到的行为都会变。

任何机制都有环境前提；拆掉外部依赖，它就不再成立。
TCP 连接可达防火墙/LB 空闲回收是头号敌人；心跳 OPTIONS（9 B）就是对它的回答。
idle 裁剪配置native_transport_idle_timeout 默认 0 不裁；配 60s 就会掐静默连接（PipelineConfigurator:264-275）。
帧上限 16MiBConfig.java:354-355；超限进 discard 模式，报「Request is too big」。
协议版本协商v3/v4/v5 正式、v6-beta；SUPPORTED 清单里全报，选错直接拒。
驱动连接池每节点一小池长连接 + 每条连接的 stream 号域，两头摊薄固定成本。
rpc_keepaliveTCP 层保活默认开（yaml:1167）；内核级、小时级，最后一道底。

边界：本页画的是 v5、无认证、单连接形态；AUTHENTICATE 两轮、EVENT 推送订阅（REGISTER=11）、v5 帧衣的 CRC 细节在正文有文字交代。

一页带走

9 字节信封装一切，同号还号复用忙，握手谈完再干活。

· 帧头五字段：version（版本+方向）/flags/stream（2B）/opcode/length；一次 UPDATE 往返 72 B，握手一场 242 B——长连与 prepared 都在摊这笔固定成本。

· stream id 是多路复用的全部秘密：在途不重号、应答同号还号、回家可以乱序；正号段 32768 路，EVENT 用 -1。

· 压缩 STARTUP 里谈：v4 信封级 snappy/lz4（flags 0x01），v5 帧级仅 lz4、握手不穿帧衣；单帧上限 16MiB。RocksDB 这层是零——函数调用没有线路形态。
