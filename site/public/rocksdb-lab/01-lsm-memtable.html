先把改动攒在内存里：跳表怎么排队，64MB 怎么判满

随机写为什么慢？B+ 树每次更新都原地改一个散落的叶子页。LSM 把改动先攒在内存账本里排好队，攒满一笔写成一个大文件，之后谁也不再改它。这页拆开账本本身：跳表、Arena 与三档判满。

1

表象观察：随机写为什么被治好了

先不拆账本，只看输入输出：写路径的形态变了。

「观察一个系统，先分清它的静态结构、动态过程和外部依赖。」

压测机上盘能跑 1.2 GB/s 顺序写，业务却卡在 4 万 QPS 随机写——iostat 里全是 4KB 散乱写。B+ 树更新一行要原地改某个叶子页，N 个键的随机写就是 N 个不相邻的 4KB I/O。LSM 的答案是：先把改动攒在内存里排好队，攒满一笔写成一个大文件，之后谁也不再原地修改它。

随机写到达→Memtable（内存账本，追加尾部）→满 64MB flush 成 L0 SST→压实誊抄归并

一句话本质：把随机写换成顺序写——读变复杂了（要从新到旧查好几层），换来写永远落在当前账本的末尾。B+ 树写 3 个键是 3 个不相邻的 4KB 写；LSM 写 3 个键是 0 次写盘，满 64MB 后一次顺序写。

动静融合：部件 × 阶段

竖看是一个阶段的全体协同，横看是一个部件的完整职责。

「把部件放回阶段里，才能看清谁在什么时候接力。」
部件写入判满换本flush读取（同刻）
跳表找层、落链、追加新版本—转只读按序导出点查直接走链
Arena整块供应、指针推进占用计入 data_size随本子封账随本子释放—
mutable接客中三档判满的判定对象变身 immutable—第一个被问
immutable 队列——push_front 入队队尾挑出刷写按新到旧被问
历史链表———刷完暂住GetFromHistory 仍可读

涌现属性：「读不阻塞写」不属于任何单个部件——mutable 照常接客、immutable 只读可查、Arena 两级锁让并发写不互相弹跳，三者叠加才涌现出来。而「刚 flush 完的数据依然可见」，是历史链表补上的最后一块。

5

环境场景：账本之外还有什么

拆掉任何一个外部依赖，前面看到的行为都会变。

「环境属性 = 外在关系 + 依赖 + 失效后果。」
宿主内存预算单列族 64MB×2=128MB 上限；12 个列族 ≈1.5GB——只是一项，还不算块缓存。
WAL（第 3 章）memtable 在内存里，进程挂了就没了；能补回来的只有先落账的 WAL。
flush 线程与 L0出口的速度决定队列积压；flush 停不下来时 immutable 顶到上限就停写。
allow_concurrent_memtable_write默认允许并发写：ConcurrentArena 两级锁是组提交能并发灌账本的内存侧前提。
MemTableRepFactory 备选HashSkipListRep / VectorRep：攒完就走的负载可以不用跳表。
max_write_buffer_size_to_maintain历史链表的留任额度；额度归零前，刚 flush 的数据对老读者依然可见。

边界：本页画的是默认 SkipListRep + 单列族的 happy path；写停顿的完整机制（信用制限速、三类触发源）在第 3 章展开。

一页带走

写入即有序，批发不零售；三档判满，新的在前。

· LSM 用读的复杂度换写的顺序性：随机写全落内存账本尾部，落盘只有整册写出和整册誊抄。

· 跳表赢在无锁读、天然有序、覆盖写只追加；节点高度掷骰（1/4 晋升、12 层封顶），内存由 Arena 整块供应。

· 判满是三档判断，不是「>64MB 就刷」；满了 mutable 转 immutable，push_front 排队，新的在前。

· 内部键 = user_key + 8 字节（seq<<8 | type）：user_key 升序、seq 降序——最新版本永远排在同键最前。

· 边界与简化：已用内存曲线与节点 seq 为演示值；HashSkipListRep/VectorRep 备选与写停顿机制本页不展开。
