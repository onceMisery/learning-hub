一次 Put 要过几道关：组提交、WAL 与 sync 分支

写进来的每一笔都要过一串关卡：建 WriteBatch → 排队 → 组车 → 停顿检查 → 写 WAL → 写 memtable → 发布 seq → 返回。任何一关都可能成为 P99 的来源。这页把每道关放电影，sync=false 与 sync=true 两条分支都画出来。

1

表象观察：P99 抬到 80 ms，慢在哪一关

先不拆关卡，只看它对外表现出什么。

「观察一个系统，先分清它的静态结构、动态过程和外部依赖。」

大促当晚写入 P99 从 2 ms 抬到 80 ms，日志反复出现 Stopping writes because we have 2 immutable memtables。盘很闲、线程也不忙——是 compaction 跟不上，RocksDB 在写路径上主动踩了刹车。要读懂它，得先知道一次 Put 不是「写进去」一个动作，而是一串关卡。

Put→WriteBatch 组包→排队 + 组车→停顿检查→写 WAL→写 memtable→发布 seq 返回

一句话本质：进站上火车——领票（WriteBatch）、候车（WriteThread）、组车（组提交）、闸机（写停顿）、打孔（写 WAL）、搬行李（写 memtable）、开车（发布 seq）。链上每段都有独立计时器（write_wal_time、write_memtable_time、write_delay_time……），P99 一拆就知道慢在哪一关。

涌现属性：「N 个请求只付一次 fsync」不属于任何单个部件——它是队列的到达率、leader 的收编规则和 sync 隔离三者叠加的结果。反过来，sync 混杂会把车拆散：监控上 WRITE_DONE_BY_OTHER 掉下来，就是组提交失效的信号。

5

环境场景：关卡之外还有什么

拆掉任何一个外部依赖，前面看到的行为都会变。

「环境属性 = 外在关系 + 依赖 + 失效后果。」
调用方 WriteOptionssync / disableWAL / no_slowdown / low_pri：写路径的「公平」是业务自己声明的。
OS page cachesync=false 只保证数据进 page cache：进程崩不丢，掉电丢——承诺边界由它决定。
文件系统 fdatasync真正落盘的动作；use_fsync 可切换成连元数据一起刷的 fsync。
max_total_wal_size日志切换的判据：单列族在 memtable 满时切，多列族要等所有 flush 跟上。
WriteBufferManager多库共享内存预算时的全局闸机：超预算拦下所有写，等 flush 降水位。
监控计数器WAL_FILE_SYNCED 对比 sync 写 QPS 看 fsync 分摊；STALL_MICROS 是 P99 的头号嫌疑。

边界：本页画的是默认路径（三模式开关全关）与 3 线程小 demo；two_write_queues / pipelined_write / unordered_write 的拓扑变化本页不展开。

一页带走

组车分摊 fsync，先打孔再搬行李。

· 关卡序列：WriteBatch → 排队 → 组车 → 停顿检查 → 写 WAL → 写 memtable → SetLastSequence → 返回；P99 沿这条链找最慢的一关。

· 组提交：同车的写合成一次 Append、至多一次 fsync；sync 写绝不和非 sync 写同车。

· WAL：32KB 块 + 7 字节头（CRC+len+type）；大记录拆 FIRST/MIDDLE/LAST；sync=false 进程崩不丢、掉电丢。

· 写停顿：immutable ≥ 2 直接停（默认没有渐进段）；恢复按 1.4 倍逐步回松。

· 边界与简化：块内字节数与分片大小为示意值；三种进阶写模式与 WBM 全局闸机本页不展开。
