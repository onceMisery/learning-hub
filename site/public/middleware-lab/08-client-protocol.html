客户端与协议：sendAsync 之后，线上到底发生了什么

同一段 Java 代码，在线上会被翻译成一串命令：lookup、连接、建 producer、发送、收 ack；消费侧又是另一组反向命令。这页把客户端栈、命令方向和帧格式摊开，让你看到 sendAsync 之后真正发生了什么。

点上下带里任意一个命令帧，右下角立刻摊开它的字节构成（帧头 / 命令体 / metadata / payload）、方向、它触发的状态变化、它在等哪个 requestId 或 sequenceId；点右上「PING 超时 · 断开连接」看未完成的 sendAsync 有几条要重试、重连后 CONNECT→PRODUCER→SUBSCRIBE→FLOW 怎么重放。鼠标停在部件上看职责。

读法：中间是 ClientCnx / ServerCnx 的连接状态机（ready / 半连接 / 关闭）和 requestId 配对表；上下两条带是同一条 TCP 连接的双向帧流——上带帧从左往右（客户端发命令），下带帧从右往左（Broker 回 / 推消息）。每个方块长度 ∝ 这条帧的真实字节数：控制帧只有帧头 + 命令体，SEND / MESSAGE 还多出 magic、CRC32c、metadata 和 payload（一帧能装好几条消息，因为客户端默认合批）。带子之间的细线是「一次请求怎么走完」的往返配对：SEND 到 Broker 就回一条 SEND_RECEIPT，靠 producerId + sequenceId 对上号；MESSAGE 被消费就从下带拐回上带一条 CommandAck，这就是本章的 ack 闭环。下面数字都由同一个时钟推出来：帧序号只增、receiverQueue 与 availablePermits 此消彼长、FLOW 把许可还回去、ping 攒够一轮没等到 pong 就 +1 超时并断开。
口径：Pulsar 5.1.0-SNAPSHOT。默认值取自 Producer/Consumer/ClientConfigurationData、broker.conf 与 PulsarApi.proto：batchingMaxMessages 1000 / 128KB / 1ms、sendTimeout 30s、receiverQueueSize 1000、ackGroup 100ms·1000 条、ackTimeout 0（不开）、connectionsPerBroker 1、protocolVersion v21。帧字节、批次条数、ping 间隔、pending / permits 的读数都是演示值（标注「演示」），不代表真实 RTT 或抓包字节。控制命令靠 requestId 关联响应，CommandSend 不带 requestId、靠 producerId + sequenceId 匹配 SEND_RECEIPT。

1

表象观察：客户端只看见一个 sendAsync

先不管类，只看从应用到线上，信息被翻译了几次。

「对事物的观察包括了静态结构 + 动态生命周期 + 环境场景三个方面的内容。」

应用看到的是一个消息对象和 sendAsync；客户端看到的是 pending 队列、批次、sequenceId；线上看到的是 CommandSend、MessageMetadata 和一段 payload；Broker 看到的是 entry，最后才落到 Bookie 的 ledger。

sendAsync→ ProducerImpl：pending / batch→ ClientCnx：命令帧→ Broker：entry / ledger→ sendReceipt

三个常见误判：把 entry 当成 message；把 payload 当成 Protobuf；把 sendAsync 返回当成 Broker 已落盘。后面的图和帧解剖会逐条拆开。

动态分析：十个命令走完一次往返

用 10 个步骤点看命令方向、关键字段和响应关系。

「它如何演变与运作？关注时间轴上的发展规律、行为模式和内部流程。核心方法是流程分析、行为追溯。」
阶段方向命令关键点
① lookup客户端 → BrokerCommandLookupTopicrequestId 关联响应；owner 可能 Redirect
② 响应Broker → 客户端LookupResponseConnect 或 Redirect；正常流程
③ 握手客户端 → BrokerCommandConnect协议版本、认证、客户端版本
④ 协商Broker → 客户端CommandConnectedmin(server, client)、maxMessageSize、feature flags
⑤ 建 producer客户端 → BrokerCommandProducerproducerId、schema、epoch
⑥ schema 版本Broker → 客户端ProducerSuccessproducerName、schemaVersion、topicEpoch
⑦ 发送客户端 → BrokerCommandSendsequenceId、numMessages、metadata + payload
⑧ 写账本Broker 内部PersistentTopic → MLentry 写 writeQuorum 个 Bookie
⑨ 回执Broker → 客户端CommandSendReceiptproducerId + sequenceId 匹配；批共享 highestSequenceId
⑩ 消费双向Subscribe / Flow / Message / Ack信用链和 ack 分组；消费侧反向命令

两个最容易看漏的点：① CommandSend 没有 requestId，它靠 producerId + sequenceId 匹配回执；② 一条 CommandSend 可能对应多条 message，因为客户端默认开批处理。看 Broker 的写入指标时，别把“1 条 entry”当成“1 条消息”。

4

动静融合：命令 × 方向 × 状态

把命令序列和帧解剖叠起来，才能定位“卡在哪一层”。

「动静融合的关键是建立映射：将组成部件与操作步骤一一对应，理解各部件如何协同产生外在行为。」
现象更可能的原因先看哪里
sendAsync future 超时30s 内没收到 SEND_RECEIPT；或批一直没触发sendTimeout、pending/批次、Broker/Bookie 写延迟
Broker 只写了 1 条客户端把 100 条合成了一个 entrynum_messages、highest_sequence_id、批配置
producer 创建失败schema 不兼容、topic 不存在、权限不足ProducerSuccess 错误、schema registry 日志
消费端解析失败consumer schema 与消息 schemaVersion 不匹配MessageMetadata.schema_version、AutoConsume
升级客户端后行为变了协议版本/feature flags 不同CommandConnected 的版本与能力

点题一句：客户端协议不是“发字节”，而是“命令 + 元数据 + payload 三层”。命令决定动作，元数据决定怎么解释 payload，payload 才是业务数据。三层任何一层错位，都会表现成“消息发不出去或消费不了”。

5

环境场景：协议之外还得有什么

命令能跑通，前提是这些系统在环境里就位。

「对事物的认识 = 空间属性 + 时间属性 + 环境属性（外在关系和依赖）。」
DNS / serviceUrl客户端只认 serviceUrl；地址解析失败，lookup 连第一步都走不到。
Proxy / 认证Proxy 做 TLS/鉴权/转发；CommandConnect 带认证信息，权限错误在最前面被拒。
Schema registry 存储默认 BookkeeperSchemaStorage；schema 定位在元数据，数据在 BookKeeper。
协议版本v15 GetOrCreateSchema、v17 ack receipt、v21 AutoConsume；老客户端只协商到 min。
Broker / BookieSEND_RECEIPT 背后是 writeQuorum/ackQuorum；Bookie 慢会放大 sendTimeout。
监控pendingMessages、批次大小、schemaVersion、协议版本、sendReceipt 延迟。
6

复盘自测

能说清“命令、帧、payload 三层”，才算真的懂。

一页带走

命令管动作，metadata 管解释，payload 才是数据；sendReceipt 只认 producerId + sequenceId，批处理让一条命令装很多条消息。

· 客户端不是“直接发消息”：pending + 批次 + ClientCnx 命令帧，才到 Broker。

· 控制命令靠 requestId；CommandSend 靠 producerId + sequenceId 匹配回执。

· 一条 CommandSend 可能装多条 message；批默认 1000 条 / 128KB / 1ms。

· Schema 随 CommandProducer 注册，未缓存才走 GetOrCreateSchema；版本写进 MessageMetadata。

· payload 不是 Protobuf；协议版本 v15/v17/v21 决定命令能力。

· 边界与简化：本页为原理示意；默认值/阈值/时序以 Pulsar 5.1.0-SNAPSHOT 的配置与源码为准；异常、重试与批处理细节未展开。
