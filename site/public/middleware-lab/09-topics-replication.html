主题与复制：没有账本的消息，和跨集群的副本

同一套 API，persistent 把消息写进 ledger，non-persistent 只在内存里分发；同一套复制配置，persistent 用 cursor + backlog 续传，non-persistent 只能即发即走。这页把两条命运放在同一相位上对照。

读法：左右两个格子间是集群 A 与集群 B，各自都有 Broker、ManagedLedger、Bookie 和自己的游标；中间那条走廊同时走三样东西——琥珀点是 replicator 把消息从 A 搬到 B，蓝点是 replicated subscription 的快照 UPDATE（方向 B→A，链一断就停发），最下面一条红虚线是 non-persistent 的旁路：不写 Bookie、不进 ledger 列表、没有 cursor，链断当场 drop。看数先看法旗：下面泳道一格一条消息，五面旗子压在同一个序号轴上，A 的 publishEq 与 B 的 publishEq 之间那段差就是复制滞后（通道 + 跨地域网络 + B 侧凑齐 ack 的流水线深度）；断链之后 A 那两面旗继续走、B 两面旗停住，中间压出来的红带就是欠在本地等重放的条数，蓝带是 B 侧已落账还没 ack 的在途。B 侧的写是远程 Producer 代写的，命令带 ReplicationCluster=A，所以 B 自己的 repl.A 游标读到 0 条、订阅也按 replicated 标记过滤——走廊里那条打叉的反向虚线就是这个意思。ack 闭环在两个集群的下沿各走一条：consumer 把 ack 发回去，markDelete 才跳格；换到 non-persistent 那一档，这条回路直接变成 no-op。
口径：Pulsar 5.1.0-SNAPSHOT。默认值取自 conf/broker.conf 与 ServiceConfiguration：replicationProducerQueueSize 1000、replicationConnectionsPerBroker 16、快照频率 1s / 超时 30s / 缓存 30；复制游标名 pulsar.repl.<remote>、初始 latest；GeoPersistentReplicator 远端写成功才 cursor.asyncDelete、失败 rewind（所以至少一次、可续传）；NonPersistentReplicator 用 blockIfQueueFull(false)，不可写 / 队列满就计入 msgDrop、backlog 恒 0；NonPersistentTopic.publishMessage 回 callback.completed(null,0,0)，NonPersistentSubscription.acknowledgeMessageAsync 是空实现，非持久化订阅不支持 replicated subscription。每轮条数、每本 12 条 ledger、E2/W2/A2、各类延迟与「0.5 轮一拍快照」都是演示值（页面已标演示），真实副本数与触发阈值由 broker 配置决定，这里不冒充默认值；事务不跨集群、Cluster Migration 属集群重定向，本页不演。

1

表象观察：同一套 API，两种命运

先不拆类，只问一句：消费者断开后，这条消息还在不在？

「对事物的观察包括了静态结构 + 动态生命周期 + 环境场景三个方面的内容。」

persistent 和 non-persistent 的客户端 API 几乎一样：producer 发、consumer 收。但一个是“先记账再分发”，一个是“直接分发、没有账本”。这个差别在正常路径上看不出来，在消费者断开、Broker 重启、跨集群复制时才暴露。

persistent：ledger + cursor →可重放 / 可续读 →复制可补 backlog non-persistent：直接分发 →断开即丢 →复制 best-effort

这一页的主图走 persistent，副图走 non-persistent；两条路径共用同一个相位，方便你对照“同一时刻，另一边在做什么”。

动态分析：八个阶段，两条命运

用 8 个步骤点看发布、分发、断开、复制和断链。

「它如何演变与运作？关注时间轴上的发展规律、行为模式和内部流程。核心方法是流程分析、行为追溯。」
阶段persistentnon-persistent关键差别
① 集群/策略config store + replication_clusters同样需要 policy远端 URL 来自 ClusterResources
② 本地发布asyncAddEntry → ledgerpublish → 直接分发是否写账本
③ 本地分发dispatcher 按 permits 读 cursorpermits=0 / 无 consumer → drop是否有 cursor/重投
④ ackmarkDelete 异步推进ack no-op是否有进度账
⑤ 消费者断开cursor 保留，可续读订阅删除，消息丢失重放能力
⑥ 启动复制cursor pulsar.repl.B @latest直接 push 到远程 producer是否有复制 backlog
⑦ 远端写入成功删 cursor，失败 rewind不可写/队列满 → drop至少一次 vs best-effort
⑧ 快照/断链backlog 增长，恢复续传断链即丢复制语义

最该记住的是第 ⑤ 和第 ⑦：persistent 的“断开”是延迟，non-persistent 的“断开”是丢消息；persistent 的“复制失败”是 backlog，non-persistent 的“复制失败”是 drop。不要在 non-persistent 上做容灾假设。

4

动静融合：三种存储，三种承诺

把主图的账本/游标和副图的即时分发叠起来看。

「动静融合的关键是建立映射：将组成部件与操作步骤一一对应，理解各部件如何协同产生外在行为。」
承诺persistentnon-persistent
消息还在吗ledger 在，直到保留/删除只在内存/分发瞬间
能重放吗能，cursor 可从位点续读不能，无 cursor
ack 有用吗推进 markDeleteno-op
复制能补吗能，cursor + backlog不能，链断即丢
跨集群重复窗口replicated subscription 快照缩小没有 replicated subscription

点题一句：“持久化”不是一种存储实现，而是一组承诺：可重放、可续传、可对齐。non-persistent 放弃这三项，换来更短路径和更低成本；它不是“性能更好的 persistent”，而是另一种取舍。

5

环境场景：复制依赖什么

复制不是“打开开关”，它需要一整套集群元数据和远端连接。

「对事物的认识 = 空间属性 + 时间属性 + 环境属性（外在关系和依赖）。」
config storetenant/cluster/namespace 策略；replication_clusters 与 allowed_clusters 必须匹配。
ClusterResources远端 brokerServiceUrl / brokerServiceUrlTls；没有 URL 就没有 replication client。
replication client每个远端一套 producer；连接数默认 16，队列默认 1000。
replicated subscription快照默认 1s、超时 30s、缓存 30；多集群 ack 对齐。
本地保留策略persistent 复制要留足 backlog 时间；ledger 被裁掉就补不回来。
监控replication backlog、replication delay、np msgDropRate、快照超时。
6

复盘自测

能说清“持久化是承诺，不是实现”，才算真的懂。

一页带走

persistent 先记账再分发，non-persistent 只分发不记账；复制 persistent 靠 cursor/backlog，non-persistent 靠尽力而为；快照只缩小重复窗口，不改至少一次。

· non-persistent 没有 ledger/cursor：publish 立即分发，ack no-op，无 consumer/permit 或链断就 drop。

· persistent 的 ack 推进 markDelete；消费者断开可续读；复制有 cursor + backlog，可续传。

· non-persistent 复制是 best-effort：maxPending 1000、不阻塞、失败即丢；backlog 恒 0。

· Replicated Subscription 用快照对齐多集群 ack；仍是至少一次，只缩小重复窗口。

· Cluster Migration 是集群重定向，不是 geo-replication；事务不跨集群。

· 边界与简化：本页为原理示意；默认值/阈值/时序以 Pulsar 5.1.0-SNAPSHOT 的配置与源码为准；异常、重试与批处理细节未展开。
