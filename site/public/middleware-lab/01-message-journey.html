一条消息的旅程：从 sendAsync 到 cursor ack

Pulsar 的官方架构图按部署分成四层，但告诉不了你「消息在哪一段停住」。这页按请求路径把系统重切成四段职责，让一枚琥珀色令牌替你走一遍：lookup 找归属、Broker 收消息、ManagedLedger 记账、Bookie 凑 quorum、Dispatcher 分发、Cursor 推进。每一站都能定格看。

1

表象观察：先把它当黑盒

不急着拆类，只看它对外表现出什么。

「对事物的观察包括了静态结构 + 动态生命周期 + 环境场景三个方面的内容。」

从客户端看，Pulsar 只做一件事：sendAsync 进去，sendReceipt 出来。中间它换了多少个线程、写了几本账、复制了几份，调用方一概不知道。这个黑盒对外承诺两件事：消息不会凭空消失；消费端至少能看到一次。

sendAsync（异步）→ Pulsar（黑盒） →sendReceipt / 异常（生产端） ↳消费端 receive()（消费端）

黑盒视角的结论：这是一台带持久化承诺的异步转发装置。接下来打开它，看承诺是靠哪些部件兑现的。

2

静态分解：四段职责里各有什么

先看总览图的三条路径，再点部件卡片——动画中对应部分会亮成琥珀色。

「它由什么构成？核心方法是分解、分类、结构化——分解需符合 MECE 法则，同层必须粒度一致。」
读法：先按颜色找三条路径，再看每个方块里的职责标签。查找只发生在建连前；生产主链写 Bookie；消费主链用 permits 推、用 ack 回。四段职责是按请求路径重切的，不是官方部署四层（实例 / 集群 / Broker / Bookie）。
口径：Pulsar 5.1.0-SNAPSHOT 集群默认 E=2 / W=2 / A=2；查找的 Redirect 细节见下方时序图。
接入段 —— 负责「把协议接住」
路由段 —— 负责「这块地归谁」
存储段 —— 负责「把消息记住」
消费段 —— 负责「把消息送出去」

静态分解只回答「有什么」。一条消息怎样穿过这些部件？切到时间维度。

3

动态分析：九步走完一条消息

盯住琥珀色令牌，用下方 9 个步骤点逐帧定格。

「它如何演变与运作？关注时间轴上的发展规律、行为模式和内部流程。核心方法是流程分析、行为追溯。」

操作：点步骤条圆点，或按「下一步」。建议走两遍：第一遍只看令牌路径，第二遍同时看元数据高亮、entry 格子、Bookie 指示灯和游标条。

阶段相位关键动作这一步在干什么
① 查找归属0°–80°CommandLookupTopic客户端问任意 Broker：bundle 归谁
② 建立连接80°–160°Connect / Redirect拿到 owner 地址，建 producer / consumer
③ 发送消息160°–240°sendAsync进 pending 队列，拿信号量许可，走 Netty
④ Broker 校验240°–320°fencing / 去重 / 限速硬约束提前拒绝，比写一半失败便宜
⑤ 写账本320°–410°asyncAddEntry交给批处理 executor，OpAddEntry 写当前 ledger
⑥ quorum410°–500°writeQuorum / ackQuorum默认 E=2：写 2 份、收 2 个 ack，没有第三个副本
⑦ 回 ack500°–590°sendReceipt更新 lastConfirmedEntry 与 entry cache
⑧ 分发590°–680°Dispatcher按 permits 读取，推给消费者本地队列
⑨ 推进游标680°–720°ack / markDelete异步持久化；崩溃窗口内会重投
读法：时间从上往下。Broker A 只是被任意问到的一台；它查元数据拿到 owner 后，要么直接 Connect（自己就是 owner），要么 Redirect 到 Broker B，客户端带 authoritative=true 再问一次。Redirect 可能发生 1–2 次，是正常流程。琥珀 = 请求 / Redirect，绿 = Connect，灰色虚线 = 角色时间线。
口径：Pulsar 5.1.0-SNAPSHOT TopicLookupBase.lookupTopicAsync / NamespaceService.getBrokerServiceUrlAsync；行号以本地 checkout 为准。

两个容易看漏的点：① 第 ⑤ 步写的是当前 ledger，元数据里的 ledger 列表不会每条消息都更新，只在账本创建、关闭、删除时更新；② 第 ⑥ 步的 ack 只代表 ackQuorum 个副本确认。集群默认 E=W=A=2，所以两份都写、都确认；只有把 E 调到 3、W 仍为 2 时，才会出现一个在 ensemble 里但不在本次 writeQuorum 的第三个 Bookie——它不是 standby，也不持有这条 entry 的副本。

读法：左边是集群默认 2/2/2，两个 Bookie 都写、都 ack；右边只用于讲差异，E=3 时第三个在 ensemble 里，但不在本次 writeQuorum，也不是 standby。公式的顺序不能反：A ≤ W ≤ E。
口径：Pulsar 5.1.0-SNAPSHOT conf/broker.conf:1417–1423、standalone.conf:946–952；源码默认 ServiceConfiguration.java:2568–2581。

动静融合：部件 × 阶段的角色矩阵

把第 2 节的结构和第 3 节的流程叠起来，才是理解的完成态。

「动静融合的关键是建立映射：将组成部件与操作步骤一一对应，理解各部件如何协同产生外在行为。」

点题一句：「Broker 无状态」这个外在特性，不是 Broker 一个部件的属性，而是「数据在 Bookie、索引在元数据、Broker 只持有缓存与归属」整体协同的结果。拆开看，每个部件都很普通；合起来，才能做到存储与计算独立伸缩。

5

环境场景：它依赖什么才能工作

主体之外，还有一圈支撑系统。

「对事物的认识 = 空间属性 + 时间属性 + 环境属性（外在关系和依赖）。」
元数据存储ZooKeeper / RocksDB / Oxia。ledger 索引、游标位点、bundle 锁都在这；它慢了，topic 加载和 ledger 切换先疼。
BookKeeper 集群独立的一套复制与恢复系统；Bookie 的磁盘、GC、网络直接反映到 produce 延迟。
Proxy / 负载均衡Proxy 可选；负载均衡决定 bundle 归属，leader 挂了要重新选。
认证与授权lookup、produce、consume 各自鉴权；权限错了会在很靠前的地方被拒。
DNS 与服务发现客户端只认 serviceUrl；地址解析失败，lookup 连第一步都走不到。
监控与留痕topic 加载耗时、ledger 切换次数、Bookie 写延迟、消费 backlog——排障的四个入口。

动画里的链路能跑通，前提是这六个系统在环境里就位。拆掉任何一个，外在行为立即消失。

6

复盘自测

用自己的话能讲清楚，才算真的懂。

一页带走

先问归属再连接，写完账本才回执；数据在 Bookie，索引在元数据，进度在游标。

· 路径：lookup → 连接 → 发送 → 校验 → 写账本 → quorum → ack → 分发 → 推进游标。

· 三本账：数据账每条消息都写，索引账换 ledger 才写，进度账按 ack 批量写。

· 三个数字：E=2 决定账本用几个 Bookie，W=2 决定每条消息写几份，A=2 决定收几个 ack 算成功。

· 一个边界：ack 是异步持久化的，所以语义是「至少一次」，不是「恰好一次」。

· 边界与简化：默认 E=2 / W=2 / A=2；Redirect 次数、Batch/压缩细节、四段职责与官方部署四层的关系见前文注脚；异常与重试未展开。
