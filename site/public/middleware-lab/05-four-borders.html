四道边界：一条消息要穿过四种「不确定」

正常路径讲完了，剩下的是边界：写了一半怎么办、数据太老怎么办、机器不均怎么办、流量太猛怎么办。这页课把事务、卸载、归属、背压做成四道闸门，让一枚令牌依次穿过，看每一道门在什么条件下才放行。

点任意一道闸门循环切换它的额度档位：正常 → 收紧 → 放开。看水位几轮涨满、背压往回传几道、近一轮挡下多少条、最终吞吐掉到多少；右下角「复位档位」一次清掉所有改动。鼠标停在闸门上看它的参数、隐形闸门与超时。

读法：中间那条横的是消息真正走的路：生产者 → ① 客户端 pending 队列 → ② Broker 限速与配额 → ③ 分发批次 → ④ consumer 的 receiverQueue 与 permits → 消费者处理 → ack 回来释放 permits，攒一批发 CommandFlow 把额度还给 ③。每道闸门里那条槽是水位（当前占用 / 这一档的上限，红刻度 = 92%），槽下面三行是近一轮的账：通过多少、挡下多少、卡住时是什么表现。关键在于挡下的消息不会消失，它占着上一道的位子：④ 的额度用完 ③ 就取不到位子，③ 的水位涨满 ② 就交接不出去，② 满 ① 的 pending 队列就顶到上限——sendAsync 的 future 于是开始挂住，这就是背压往回传的机制。琥珀点 = 在途消息，哪一段转得快就说明那一段通过得多；绿点往左回 = ack 与 CommandFlow；红点往左跑 = 背压回传，跑到哪一道，压力就传到哪一道；蓝点 = 已落盘但事务没提交，读路径在等 maxReadPosition。下方四条横道是近 16 轮的水位曲线（越靠上越下游），红点标出各道堵满的时刻，四颗红点连成的折线就是传导链；最底一行是这一轮的总账与结论。点闸门改额度，数字立刻回答：传到生产者要几轮、挡下多少条、吞吐掉到多少。
口径：Pulsar 5.1.0-SNAPSHOT。本页速率、上限、时延、超时全是演示值：进场约 200 条/轮带波动，四道闸门的容量与每轮通过上限见框内标注，一条 ledger 128 条、第 3 本起算冷读、24 条一个事务、sendTimeout 0.6 轮、ackTimeout 0.45 轮、事务超时 1 轮；「超时失败」「重投」按驻留时长是否超过对应超时估算，真实实现是逐条定时器。真实默认值量级不同但确实存在：客户端 maxPendingMessages 与 pending 内存上限、sendTimeout 默认 30s；Broker 侧 publishRateLimiter 默认 0（关闭）、backlog quota 默认 -1（关闭）、策略默认 producer_request_hold 且每 60s 检查一次、未 ack 上限 50000/200000；ServerCnx 每连接 pending publish 默认 1000、降到 500 才恢复，IO 线程 pending 字节默认 max(64MB, 直接内存/2)、过半就 setAutoRead(false)（停掉的是同一 IO 线程上的所有连接）；账本交接 addEntryHandoverMaxBatchItems=1024 / 5MB；dispatcherMaxReadBatchSize 默认 500；客户端 receiverQueueSize 默认 1000。事务默认关闭（transactionCoordinatorEnabled=false），本页当作打开来演示。

表象观察：正常路径之外，还有四种「停」

先不看实现，只看一条消息可能停在哪。

「对事物的观察包括了静态结构 + 动态生命周期 + 环境场景三个方面的内容。」

一条消息从生产到消费，除了「写进去、读出来」，还会遇到四种边界：事务没提交、账本被卸载、bundle 没归属、消费端没许可。每一种都让消息停住，但停的原因完全不同。

四类不确定（并列，不是先后顺序） 写了一半 数据太老 机器不均 流量太猛

这页课把四种边界做成四道闸门，看它们各自的放行条件。

3

动态分析：令牌穿过四道门

用 12 个步骤点看每一道门什么时候放行（含事务消费与回滚）。

「它如何演变与运作？关注时间轴上的发展规律、行为模式和内部流程。核心方法是流程分析、行为追溯。」
阶段相位门放行条件
① 事务写入0°–60°事务消息已写，但不可见
② 消费侧 ack 挂起60°–120°事务ack 先落 pending ack store，不推进 markDelete
③ commit marker120°–180°事务marker 写进 ledger
④ abort 分支180°–240°事务写 abort marker；pending ack 撤销，消息重新可见
⑤ 变得可见240°–300°事务maxReadPosition 推过 marker
⑥ 账本卸载300°–360°卸载offloadContext.complete=true
⑦ 冷读360°–420°卸载读路径切到对象存储
⑧ bundle 归属420°–480°归属锁被某个 Broker 拿到
⑨ lookup 重定向480°–540°归属客户端拿到 owner 地址
⑩ 闸门① 客户端540°–600°背压maxPendingMessages 与内存还有余量
⑪ 闸门② Broker600°–660°背压令牌桶有余量，交接批次不超限
⑫ 闸门③④ 许可660°–720°背压permits > 0，批次不超 maxReadBatch

注意第 ⑥ 步：卸载不是「删数据」，而是「多一个读路径」。Bookie 上的副本还在，直到 deletionLag 到期才删；这期间读 Bookie 或读对象存储都可以。

事务的两条腿：生产侧管可见性，消费侧管 ack。

生产侧：消息带 txnid 写进 ledger，但 maxReadPosition 不前进，所以消费者读不到。提交时写一个 commit marker，位置推过去，消息才可见。

消费侧：consumer.ack(txnId, msgId) 走 PendingAckHandle.individualAcknowledgeMessage()，把位置写进 <topic>-<sub>__transaction_pending_ack；提交时 commitTxn() 追加 commit mark，把 pending 的 ack 真正应用到 cursor。

回滚不是「什么都不做」：TopicTransactionBuffer 会往 ledger 追加一个 abort marker（:550 Markers.newTxnAbortMarker），读路径在 :219 认出它，就知道这批消息要跳过。所以 abort 同样要写一次账本。

事务的边界要记住：读已提交而不是可串行化；有超时（太长会一直占着 maxReadPosition，堵住后面的消息）；不跨集群；靠 lowWaterMark 清理 abort 索引与快照。

背压不是一句「限流」，是四道串联但不共享队列的闸门。

① 客户端队列：maxPendingMessages + 内存上限，满了阻塞或失败，压力留在应用线程。

② Broker 发布限速：publishRateLimiter 令牌桶，超限就 throttle 这条连接；不丢消息，只让发送方慢下来。

③ 账本交接批次：addEntryHandoverMaxBatchItems=1024、addEntryHandoverMaxBatchBytesSize=5MB，超过就分批，防止一次吃太多 direct memory。

④ 分发许可：totalAvailablePermits + maxReadBatch，没有许可就停止从 Bookie 读。四道门各有各的超时（sendTimeout / topicLoadTimeoutSeconds / metadataOperationsTimeoutSeconds / ackTimeout / 事务超时），只调一个，通常只是把问题挪到下一层。

4

动静融合：四种边界在保护什么

每道门都在用一种代价，换一种确定性。

「动静融合的关键是建立映射：将组成部件与操作步骤一一对应，理解各部件如何协同产生外在行为。」
边界保护什么代价
事务多条消息原子可见超时、lowWaterMark、额外 marker
分层存储Bookie 容量不被历史数据占满冷读延迟、对象存储流量费
bundle 归属同一时刻只有一个 ownerlookup redirect、锁竞争
背压下游不被上游打爆吞吐下降、队列等待

点题一句：这四道门没有一道是「免费的正确性」。事务用延迟换原子性，卸载用读延迟换容量，归属用 redirect 换一致性，背压用吞吐换稳定。工程上真正要做的，是知道自己在为哪一项付钱。

5

环境场景：四道门各自的支撑

每道门能关上，背后都有一个系统在配合。

「对事物的认识 = 空间属性 + 时间属性 + 环境属性（外在关系和依赖）。」
事务协调者分配 TxnID、记录状态、驱动 commit / abort；TC 日志本身也要能重放。
对象存储承载卸载后的 ledger；首字节延迟和流量费是主要成本。
元数据存储bundle 归属锁、ledger 列表、游标位点；它慢了，归属和加载都疼。
负载均衡 leader决定 bundle 归谁；leader 挂了要重新选。
限速与许可publishRateLimiter、dispatchRateLimiter、receiverQueue，三层一起工作。
监控事务超时数、卸载延迟、redirect 次数、permits 余量。
6

复盘自测

知道每道门在保护什么，才算真的懂。

一页带走

事务保原子（生产靠 marker，消费靠 pending ack），卸载保容量，归属保唯一，背压保稳定；每道门都有代价。

· 事务生产：maxReadPosition + commit marker；提交前已落盘，但消费者读不到。

· 事务消费：ack 先挂到 pending ack store，提交才应用到 cursor；回滚写 abort marker，消息重新可见。

· 卸载：offloadContext.complete 决定读路径，deletionLag 决定何时删 Bookie 副本。

· 归属：bundle 锁 + ledger fencing，lookup 负责把 owner 告诉客户端。

· 背压：四道闸门（客户端队列 / 发布限速 / 交接批次 / 分发许可）串联但各自独立，每层都有超时。

· 边界与简化：本页为原理示意；默认值/阈值/时序以 Pulsar 5.1.0-SNAPSHOT 的配置与源码为准；异常、重试与批处理细节未展开。
