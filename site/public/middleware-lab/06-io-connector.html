连接器：Source 拉进来，Sink 推出去

Functions 解决的是「消息进来、算一下、消息出去」。可如果数据源压根不是 Pulsar，或者目的地是 MySQL、Elasticsearch，怎么办？这页课把两种连接器摆在同一条链路上：左边 Source 从外部系统读，右边 Sink 写回外部系统，中间还是那个 function 实例循环——连调度、状态、失败处理都共用一套。

1

表象观察：一个 jar 进去，一条数据出来

先不拆类，只看连接器对外是什么。

「对事物的观察包括了静态结构 + 动态生命周期 + 环境场景三个方面的内容。」

从运维视角看，连接器只有一个动作：提交一个包，数据就开始流动。方向有两种——从外面读进来（Source），或者写到外面去（Sink）。至于它跑在哪台 Worker、怎么重试、状态存哪，提交的人一概不知道。

输入侧 外部系统→ Source 连接器→ Pulsar topic
输出侧 Pulsar topic→ Sink 连接器→ 外部系统

黑盒视角的结论：连接器是一台协议翻译机。接下来打开它，看翻译这件事是靠哪些部件完成的。

动态分析：一条 Record 的九步

盯住琥珀色令牌，用下方 9 个步骤点逐帧定格。

「它如何演变与运作？关注时间轴上的发展规律、行为模式和内部流程。核心方法是流程分析、行为追溯。」
阶段相位关键动作这一步在干什么
① 提交0°–80°admin 提交配置走和函数一样的 Worker 调度
② 加载80°–160°NarClassLoader一个 NAR 一个类加载器，隔离依赖
③ open160°–240°open(config, ctx)拿 topic、schema、metrics
④ read240°–320°source.read()拉模型阻塞；PushSource 由外部推
⑤ Record320°–400°key / value / schema / sequence后面幂等就靠这两个 id
⑥ 循环400°–480°readInput → process → sendOutputSOURCE/SINK 时切 classloader
⑦ process480°–560°IdentityFunctionSink 场景是直通，不算
⑧ write560°–640°sink.write(record)目的地是 Pulsar 就走 PulsarSink
⑨ ack / fail640°–720°record.ack() / srcRecord.fail()失败触发重投，超限进 DLQ

最容易看漏的是第 ⑥ 步：连接器不是另一套运行时，它就是 function 实例。JavaInstanceRunnable 在 :605 调 source.read()、在 :545 调 sink.write()，中间的 process 对 Sink 来说是 IdentityFunction 直通。调度、并行度、rebalance、DLQ 全都和函数共用。

4

动静融合：三种语义，三种 ack 时机

把结构（谁在写）和时间（什么时候 ack）叠起来看。

「动静融合的关键是建立映射：将组成部件与操作步骤一一对应，理解各部件如何协同产生外在行为。」
语义ack 时机重复丢失代价
ATMOST_ONCE读出来就先 ack不会可能丢最快，适合可丢的指标
ATLEAST_ONCE处理 + 写成功后才 ack可能重复不会要幂等
EFFECTIVELY_ONCE写出成功后 ack，靠 sequenceId 去重Broker 侧挡掉不会必须带 partitionId + recordSequence
MANUAL业务自己决定看实现看实现灵活，也最容易写错

点题一句：语义不是连接器的属性，而是「ack 发生在哪个时间点」的属性。同一个 Sink 连接器，换个语义配置，ack 的时机就变了——这才是四种语义的真正区别。

5

环境场景：连接器依赖什么

主体之外，还有一圈支撑系统。

「对事物的认识 = 空间属性 + 时间属性 + 环境属性（外在关系和依赖）。」
包管理NAR 上传后存进 BookKeeper 与元数据，Worker 按 URL 下载；PackageUrlValidator 限制协议，挡住 file:// 这类越权读取。
外部系统的凭证数据库账号、云厂商密钥通常走 secrets；凭证过期会让连接器在 open 阶段就失败。
外部系统的反压数据库慢，Sink 的 write 就会慢，积压会一路传导到 topic 的 backlog——连接器不隔离压力。
状态后端BK Table 服务或元数据存储；状态大或要跨实例共享时，老实上 Redis / 数据库。
重试与 DLQ写失败必须有出口；没有 DLQ 的 Sink 会被一条脏数据卡死。
监控source 异常数、sink 异常数、处理耗时、backlog、DLQ 条数。

拆掉任何一个，连接器都会以不同的方式停住：包下载失败停在 ②，凭证错停在 ③，外部系统慢卡在 ⑧。

6

复盘自测

能说清「连接器就是特殊函数」，才算真的懂。

一页带走

契约只有 read 和 write，运行时就是函数实例；ack 在哪一刻发，决定了是哪一种语义。

· 契约：Source.open + read（拉）/ PushSource.consume（推）；Sink.open + write（推）。

· 运行时：JavaInstanceRunnable 的同一个循环，componentType 决定切不切 classloader。

· 打包：NAR + NarClassLoader，一个 NAR 一个类加载器，依赖不打架。

· 语义：ATMOST / ATLEAST / EFFECTIVELY_ONCE / MANUAL，差别就是 ack 的时机。

· 状态：按实例隔离，rebalance 不迁移；要跨实例共享就用外部存储。

· 边界与简化：本页为原理示意；默认值/阈值/时序以 Pulsar 5.1.0-SNAPSHOT 的配置与源码为准；异常、重试与批处理细节未展开。
