表象观察：四种「谁收下一条」

先不看 dispatcher 实现，只看消费者看到的行为。

「对事物的观察包括了静态结构 + 动态生命周期 + 环境场景三个方面的内容。」

同一个 topic、同一个订阅名，消费者数量一样，消息的走法却可以完全不同：有时全给一个，有时轮流给，有时按 key 绑定。订阅类型就是「谁有资格收下一条」的规则。

四种模式（并列，同一订阅只能选一种） Exclusive：一个吃全部 Failover：一个主收，其余待命 Shared：轮询 Key_Shared：按 key 绑定

这四种规则对应四种代价：顺序、扩展、故障切换，最多同时要两个。下面把 dispatcher 打开。

动态分析：一条消息的十步

先点步骤点走完一条消息（含两次重投），再切换订阅类型看落点变化。

「它如何演变与运作？关注时间轴上的发展规律、行为模式和内部流程。核心方法是流程分析、行为追溯。」
阶段相位这一步在干什么
① 消息进场0°–80°带 key 的消息进入 partition
② 攒批80°–160°客户端可能攒批、压缩，再发
③ 写 entry160°–240°Broker 把一批写成一个 entry

试试：动画播放时依次点四个订阅按钮。Exclusive 只亮 C1；Failover 只亮 active，其余待命；Shared 三个轮流；Key_Shared 里 A/B 去 C1、C 去 C2，C3 待命。

重投三兄弟：同一个「至少一次」，三种触发方式。

① ack 丢失 —— Broker 在持久化 ack 前崩溃，重启后从旧位点读。这是「至少一次」的根源，窗口取决于进度账多久刷一次。

② ack 超时 —— 客户端 UnAckedMessageTracker（:117 取 ackTimeoutMillis，:177 调 redeliverUnacknowledgedMessages）到点后主动要求重投。批量重投，不看单条进度。

③ 负向 ack —— 业务自己调 negativeAcknowledge()，NegativeAcksTracker 记下这批 id 再发重投请求。粒度最细，也最可控。

Broker 侧收到重投请求后，把位置记进 MessageRedeliveryController（:77 add、:194 取待重投集合），下一次读就先读这些位置。重试次数记在消息的 reconsumeTimes 上，超过 maxRedeliverCount（客户端 ConsumerImpl:747）就发往 <topic>-<subscription>-RETRY，再超就进 -DLQ。

三种重投都会产生重复，只是窗口大小不同。要真正做到「处理一次」，只能在消费端按业务 key 做幂等，或者把「处理 + 写结果 + ack」放进一个事务。

动静融合：四种模式的代价矩阵

顺序、扩展、故障切换，是一组不可能三角。

「动静融合的关键是建立映射：将组成部件与操作步骤一一对应，理解各部件如何协同产生外在行为。」
模式顺序扩展故障切换典型场景
Exclusive最强最差消费者挂了才能换单分区严格有序、低频控制消息
Failover强中等按 priority + name 接班主备、分区级有序
Shared不保证最好自动分摊日志、通知、无顺序任务
Key_Sharedkey 内有序好hash range 重分配订单、账务、按用户维度有序

点题一句：「同一 key 有序 + 多消费者并行」不是免费得到的。Key_Shared 用 hash range 把 key 绑到消费者，consumer 增减时 range 要重分配，重分配期间可能有一小段重投。这就是它比 Shared 贵的地方。

5

环境场景：订阅之外还得有什么

订阅类型只是规则，规则能跑起来还要这些条件。

「对事物的认识 = 空间属性 + 时间属性 + 环境属性（外在关系和依赖）。」
分区键设计同一订单要落同一分区，否则 Key_Shared 也保不了序。
消费者命名Failover 按 priority + name 排序；名字随机，主备可能和你想的不一样。
ackTimeout太短会频繁重投，太长会卡住 backlog；要和业务处理时间匹配。
receiverQueueSize太小吞吐上不去，太大内存和重投量都涨。
死信 / 重试毒消息要有出口，否则 Shared 也会被一条消息堵住。
监控每个消费者的 permits、队列长度、ack 延迟、重投次数。
6

复盘自测

先选对模式，再谈参数。

一页带走

要顺序先定 key，要扩展先加分区；四种订阅，最多同时要两个。

· Exclusive：一个消费者，顺序最强，扩不动。

· Failover：主备，按 priority + name 排序接班。

· Shared：轮询，吞吐最好，顺序不保证。

· Key_Shared：key 内有序，consumer 变化会重分配 hash range。

· 重投三兄弟：ack 丢失（崩溃窗口）、ack 超时（客户端计时器）、负向 ack（业务主动）。

· 毒消息必须有出口：retry topic 重试，超过 maxRedeliverCount 进 DLQ。

· 边界与简化：本页为原理示意；默认值/阈值/时序以 Pulsar 5.1.0-SNAPSHOT 的配置与源码为准；异常、重试与批处理细节未展开。
