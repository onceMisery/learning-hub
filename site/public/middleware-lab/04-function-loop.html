INTERACTIVE LESSON · 控制面与数据面

函数循环：Worker 管放哪，实例管怎么跑

把计算搬进消息系统，听起来像「把 jar 扔给 Pulsar」。真正跑起来是两套东西：控制面负责提交、调度、拉起；数据面负责读消息、处理、写结果、ack。这页课把两条线摆在一起，顺便看清 ack 到底发生在哪一步。

点任意一条实例行把它点挂：控制面立刻出手——心跳变红、未 ack 到点重投、兄弟实例接手、输出多写几条当场见数。点 worker 框让 leader 挪一个实例过去（StateStore 不跟着搬）；点右侧幂等门可关去重，看重复怎么写进 output topic。鼠标停在部件上看职责。

读法：上下两层是两条不同的线。上层控制面：提交 → metadata topic → SchedulerManager（leader，RoundRobin 按实例数摊平）→ assignment topic → RuntimeManager → RuntimeSpawner；随主图每轮走一遍提交序列，其余时间只剩心跳，实例挂 / 挪实例才有额外动作。下层数据面：左侧竖列是输入 topic 进场流（暗=已 ack，亮=未 ack，红环=超时待重投，橙环=重试中的毒消息），竖列边的尺从 0 到 60 是积压刻度；底部 x 尺上的绿针 = 游标（连续已 ack 位），琥珀区 = 还没过账的积压。三条实例行各跑 readInput→process→handleResult，通道上的琥珀点走到哪儿处理到哪儿；成功后才写输出（行右 → 幂等门 → out topic），写完才 ack，绿色回点沿底部 ack 回路飞回游标那格、游标才推进——游标只认连续前缀：队头一条在重投或重试，后面的全过不来。行尾「读/写/败/未」是这一轮的账；行首绿字「E37 接手」标出重投落到谁家；行中「state N」= 这家实例的 StateStore 计数，重启或被挪走就清零。
口径：Pulsar 5.1.0-SNAPSHOT。parallelism=3、2 个 worker、输入 12 条/轮、process 0.12 轮、ackTimeout≈0.4 轮、maxMessageRetries=2、挂 1.2 轮后拉起、重平衡一次挪 1 个实例（真实里存活检查按周期跑、rebalance 由 leader 定期执行、重启可更快，这里为演示放宽），全为演示值；assignment 是追加日志、需 compaction；默认语义 ATLEAST_ONCE，EFFECTIVELY_ONCE 要把输出与 ack 收进同一事务；分区 topic 每分区各有游标，这里画一个订阅一套游标；「幂等门」是把业务幂等键画成一道门，生产上得自己做。

1

表象观察：一个 jar 进去，一条结果出来

先把它当成「消息进来、结果出去」的黑盒。

「对事物的观察包括了静态结构 + 动态生命周期 + 环境场景三个方面的内容。」

从使用方看，Functions 只要求三件事：给一个包、指定输入 topic、指定输出 topic。剩下的调度、重启、扩缩容由 Pulsar 负责。函数代码本身只有一个方法：process(input, context)。

函数包（NAR）→ Worker 调度→ 实例循环→ 输出 topic

黑盒视角的结论：这是一台把「消息处理」变成可调度单元的装置。接下来拆开看控制面和数据面。

3

动态分析：从提交到 ack 的九步

前四步在控制面，后五步在数据面。

「它如何演变与运作？关注时间轴上的发展规律、行为模式和内部流程。核心方法是流程分析、行为追溯。」
阶段相位在哪这一步在干什么
① 提交函数0°–80°控制面校验名称、并行度、输入输出
② 写元数据80°–160°控制面函数定义 / 包位置写 metadata topic
③ leader 调度160°–240°控制面拆实例，按实例数摊到 worker
④ 拉起实例240°–320°控制面写 assignment，RuntimeSpawner.start()
⑤ 读消息320°–400°数据面consumer 按 permits 读一条
⑥ process400°–480°数据面调用户函数，同步或 Future
⑦ 写输出480°–560°数据面handleResult 发到输出 topic
⑧ ack560°–640°数据面ATLEAST_ONCE 成功后才 ack
⑨ 失败 → DLT640°–720°数据面超过重试次数进死信

最容易被忽略的是 ⑧：ack 的时机决定了处理语义。ATMOST_ONCE 读出来先 ack，崩了就丢；ATLEAST_ONCE 成功后才 ack，崩了会重投；EFFECTIVELY_ONCE 把输出和 ack 放进同一个事务，代价最高。

4

动静融合：控制面与数据面的分工

两条线各管一段，谁也不能替谁。

「动静融合的关键是建立映射：将组成部件与操作步骤一一对应，理解各部件如何协同产生外在行为。」
能力控制面数据面
提交 / 更新函数负责—
决定实例跑在哪SchedulerManager—
读消息 / 处理 / 写输出—实例循环
失败重启RuntimeSpawner 拉起实例内重试 / DLT
状态—StateStore

点题一句：「函数自动扩容」这个外在特性，不是实例自己的属性，而是「metadata topic + assignment topic + SchedulerManager + RuntimeSpawner」整体协同的结果。实例只会跑循环，它不知道自己在哪个 worker 上。

5

环境场景：Functions 依赖什么

一个函数能跑起来，背后是一圈支撑系统。

「对事物的认识 = 空间属性 + 时间属性 + 环境属性（外在关系和依赖）。」
Package ManagementNAR 包上传、存储、按 URL 下载；URL 协议受 PackageUrlValidator 限制。
metadata / assignment topic函数定义与分配状态都在这；assignment 需要 compaction 或清理。
Worker 成员关系leader 选举、worker 存活检测；没有成员关系，rebalance 无从谈起。
StateStore 后端BookKeeper Table 或元数据存储；状态重要时，最好外置。
日志 / 指标函数日志写 log topic；worker stats 暴露实例数、重试数、处理延迟。
DLT / 重试策略maxMessageRetries、retainOrdering、dead letter topic，三件套要一起配。
6

复盘自测

先分清控制面和数据面，再谈语义。

一页带走

Worker 管放哪，实例管怎么跑；ack 的时机，就是语义的边界。

· 控制面：提交 → metadata topic → SchedulerManager → assignment → RuntimeSpawner。

· 数据面：readInput → process → handleResult → 输出 → ack。

· 三种语义：ATMOST_ONCE 先 ack，ATLEAST_ONCE 成功后 ack，EFFECTIVELY_ONCE 用事务。

· 一个出口：失败超过重试次数进 DLT，否则毒消息会堵住订阅。

· 边界与简化：本页为原理示意；默认值/阈值/时序以 Pulsar 5.1.0-SNAPSHOT 的配置与源码为准；异常、重试与批处理细节未展开。
