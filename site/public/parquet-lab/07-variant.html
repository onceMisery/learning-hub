5

环境场景：Variant 的适用边界

不是所有 JSON 都值得拆；拆多了也是成本。

「环境属性 = 查询热点 + 类型稳定性 + 兼容性。」
适合事件表字段稀疏、类型多变，但有几条固定热路径。
适合渐进演进先整行 Variant，再把 top 3–5 字段拆成 typed_value。
不适合稳定表字段固定、类型固定；普通列更简单。
不适合超宽对象几千个字段，metadata 字典和 field_id 列表会很大。
不适合写敏感shredding 判断和双写会增加写路径成本。
schema 冲突不同文件可以拆不同字段；读取器要能统一重建。
6

复盘自测

能说清“metadata 是字典、typed_value 是热字段列”，才算懂 Variant。

一页带走

字段名进字典，热字段进列；缺失和 null 必须分开。

· Variant = metadata（字段名字典）+ value（自描述二进制），group 标 VARIANT(1)。

· value 用 1 字节头区分 primitive / short string / object / array。

· object 的 field_id 按字段名字典序；offset 相对第一个 value，值可乱序。

· shredding 把热字段拆成 typed_value；value 兜底，缺失/null 要分清。

· 拆分带来列裁剪和谓词下推，代价是列数、写入复杂度和 schema 冲突。
