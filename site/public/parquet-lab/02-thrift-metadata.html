1

表象观察：footer 是一份可以按字段号读的目录

先问：为什么不同语言的读取器，能读同一个十几年前的文件？

「观察结构，先看它的边界和接口；Thrift 就是 footer 的接口。」

Parquet 没有把元数据写成某家公司的私有格式，而是写成 parquet.thrift。每个字段有编号，读取器按编号找自己认识的部分，不认识的跳过。新增字段只要不撞号，老读取器就不会崩。

FileMetaData→SchemaElement→RowGroup→ColumnChunk→ColumnMetaData

这条链上的每个节点，都有对应的磁盘偏移。读取器不是「猜」数据在哪，而是「按目录找」。

2

静态分解：五个结构，三类字段

点部件卡片，主图里对应的节点会亮起。

「分解到同一层：结构、字段、约束各归各的。」
从根到叶
字段必填？读不到会怎样
schemarequired不知道列和类型，文件无法读
row_groupsrequired不知道数据在哪
ColumnChunk.meta_dataoptional，但事实必须主流实现会拒绝；加密列改用 encrypted_column_metadata
column_ordersoptionalmin/max 含义未定义，不能裁剪

「optional」不等于「可以不写」。看字段注释里的 MUST / 事实标准。

3

动态分析：从尾部一路找到页

用 8 个步骤看目录怎么被逐层展开。

「动态分析看的是状态迁移：每一步把什么变成了什么。」
阶段读到的结构得到的信息下一步
① 尾部最后 8 字节footer 长度seek 到 footer
② 解 ThriftFileMetaDataschema / row_groups还原 schema 树
③ schemaSchemaElement[ ]叶子 path / 类型对应列块
④ 行组RowGroupnum_rows / columns遍历列块
⑤ 列块ColumnChunkmeta_data / 索引偏移定位起点
⑥ 偏移ColumnMetaDatadata / dictionary offset读页头
⑦ 页头PageHeader长度 / 编码 / CRC读页体
⑧ 解码页体 + levels值 / NULL 位置还原行

目录展开的顺序，就是读取器的调用链。任何一步拿不到必需字段，后面的偏移都无从谈起。

4

动静融合：字段 id、顺序与偏移

把树上的节点和磁盘上的区间对照起来。

「融合的关键是映射：哪个字段指向哪一段字节。」
字段指向哪里常见错误
row_groups[i].columns[j]第 i 行组第 j 列（按叶子顺序）按名字匹配而不是按顺序
meta_data.data_page_offset第一个数据页忽略前面的字典页
meta_data.dictionary_page_offset字典页（可选）把列块起点当成数据页
column_index_offsetfooter 附近的 ColumnIndex从列块内部找索引
file_offset已废弃，语义不一致拿它定位列块

读法：先按「叶子顺序」对齐列块，再按「最小偏移」找列块起点，最后按「页头长度」推进。

5

环境场景：Thrift 兼容性依赖什么

IDL 只是约定；真正让老文件可读的是几条兼容规则。

「环境属性 = 协议 + 版本 + 生态实现。」
字段 id 不复用删除字段不要把 id 给新语义；否则老读取器会把新字段当旧字段。
unknown 要跳过Thrift 天生跳过未知字段；Parquet 还要求未知 LogicalType 降级。
ConvertedType 双写writer 同时写新旧注解，老读取器才能看懂。
32767 扩展位每个 struct 保留一个 binary 扩展字段，给厂商实验。
版本字段不是开关writer 写 1，reader 接受 1/2；真正特性看字段是否存在。
加密列元数据列密钥不同时，ColumnMetaData 单独加密，读取器要先解密。
6

复盘自测

能说清「叶子顺序 + 偏移」这两件事，才算会读 footer。

一页带走

先有字段号，再有偏移；叶子顺序对不上，后面全错。

· footer 是一棵 Thrift 树：FileMetaData → SchemaElement / RowGroup → ColumnChunk → ColumnMetaData。

· schema 是深度优先拍平的列表；列块与叶子同序；path_in_schema 负责对名字。

· 定位列块用 dictionary_page_offset / data_page_offset + total_compressed_size，不用废弃的 file_offset。

· min/max 的含义由 column_orders 决定；没有它就不要裁剪。

· 兼容性靠字段 id、未知类型降级、新旧注解双写和 32767 扩展位。
