文件布局与结构：一个查询只读三页，凭什么

1

表象观察：一条查询只读三页

先不看代码，只问：文件里到底有什么，reader 凭什么跳过其余部分？

「观察一个系统，先分清它的静态结构、动态过程和外部依赖。」

同一张 events 表，按天切成 1 GB 的文件。查询只命中几十行，却可能扫完整个文件；也可能像开头那条 SQL 一样，只读三页。差别不在 SQL，而在文件有没有给出「不用读」的证据。

文件→行组→列块→页 →footer 目录→只读候选页

这张流程图里的每一层都有自己的「目录」：footer 记行组和列块的偏移，行组统计记值域，页索引记每页的 min/max。目录越细，能跳过的 I/O 越多，元数据也越大。

2

静态分解：四层结构与三个尺寸

点部件卡片，动画中对应的结构会高亮。

「分解要 MECE：同一层粒度一致，不重不漏。」
文件里的四层
尺寸规范建议调大了调小了
Row Group512 MB–1 GB写缓存高、单任务内存高、裁剪粗元数据多、并行碎片多
Column Chunk由行组和列宽决定单列读取时间长固定开销占比高
Page~8 KB（很多实现默认 1 MB）跳过粒度粗、解压慢页头/索引开销高

三个尺寸不是一回事：行组管并行与内存，列块管投影与压缩，页管编码与跳过。

3

动态分析：写一遍，读一遍

用 8 个步骤看 writer 怎么写、reader 怎么反向找。

「动态分析看的是时间轴上的顺序、状态变化和因果链。」
阶段writerreader关键状态
① 魔数写 PAR1—文件还不完整
②–③ 行组按列写列块，页背靠背—只有数据，没有目录
④ footer写 FileMetaData + 长度 + PAR1—文件可读
⑤ 尾部—读最后 8 字节拿到 footer 长度
⑥ 解析—Thrift 解析 schema / offsets知道每列在哪
⑦ 裁剪—统计 / 布隆 / 页索引只留候选页
⑧ 读取—页头 + 页体 + 解码还原行

写是正向的，读是反向的。writer 从文件头往尾写；reader 从文件尾往头找目录，再跳回数据。这个不对称是理解 Parquet 所有偏移字段的起点。

4

动静融合：目录与数据的对应

把动画里的文件带和读取步骤叠起来看。

「动静融合的关键是映射：每个部件在每一步里负责什么。」
读取步骤用到的结构拿到的信息省掉了什么
读末尾 8 字节文件尾部footer 长度全文件扫描
解析 footerFileMetaDataschema / row_groups / offsets猜列的位置
裁行组Statistics值域 / null 数不命中的行组
裁页ColumnIndex / BloomFilter每页 min/max / 可能存在不命中的页
读列块ColumnMetaData + PageHeader页偏移 / 压缩后大小 / 编码不需要的列
还原行def / rep levelNULL 与嵌套位置不做全量反序列化

读法：先问「这一步省掉了哪一层 I/O」，再看它依赖哪个元数据。没有元数据，就没有跳过。

5

环境场景：文件之外还有什么

Parquet 文件不是孤岛；它依赖存储、清单和读端预算。

「环境属性 = 外在关系 + 依赖 + 失效后果。」
对象存储 / HDFS块大小、随机读成本、原子 rename 能力，直接影响行组大小和失败恢复。
表格式清单Iceberg / Delta / Hive Metastore 存文件级统计与 schema，让裁剪在打开文件之前就开始。
写入端内存单遍写要在内存里攒够一个行组；行组越大，写端峰值越高。
读取端预算行组、页、批次大小共同决定单任务峰值；一次读太多，RSS 会像「泄露」。
并发度行组是并行单位；行组太少，多核吃不饱；行组太多，调度和元数据成本上升。
编码/压缩支持reader 不支持 ALP/新编码时，文件可能打不开；跨团队共享要先确认兼容性。
6

复盘自测

能说清「写是正向、读是反向」，才算真的懂布局。

一页带走

写是正向的，读是反向的；footer 是反向找路的起点。

· footer 在尾部，是单遍写的必然结果；读取从最后 8 字节开始。

· 文件 → 行组 → 列块 → 页，四层各有各的「目录」和跳过粒度。

· 页是编码/压缩/跳过的单位，不是 I/O 块；页头必须能独立解析。

· 行组大小、列块大小、页大小是三笔不同的账，不能一起调。

· 边界与简化：动画里的字节数、行组数、页数都是演示值；真实布局以 parquet-format 规范为准。
