# 数据模型：物理类型、逻辑注解与 Dremel 层级

先看一条真实的事件记录：

```json
{
  "event_id": 991203,
  "event_type": "signup",
  "event_ts": "2026-10-01T08:15:30.123Z",
  "amount": 199.90,
  "user": { "name": "林", "age": 31 },
  "tags": ["new", "promo"],
  "location": { "type": "Point", "coordinates": [121.47, 31.23] },
  "payload": { "utm": "wx", "referrer": null }
}
```

这里至少有七种「类型」：整数、字符串、时间戳、小数、结构体、数组、地理点，还有一个随时可能变形的 JSON。Parquet 的物理类型只有 8 种，它靠两层东西把这件事接住：**LogicalType 负责解释，Dremel 的 definition/repetition level 负责嵌套**。

这一章把这两层拆开。先看 8 种物理类型为什么够用，再看逻辑注解怎么把「字节」变成「字符串/小数/时间/地理」，最后用一张表把嵌套结构压成三列，看看 NULL 和空数组到底是怎么区分的。

---

## 一、8 种物理类型，为什么够用

`README.md:131-145` 列出的物理类型只有这些：

| 物理类型 | 字节 | 用途 | 备注 |
| --- | --- | --- | --- |
| BOOLEAN | 1 bit | 布尔 | 位打包 |
| INT32 | 4 | 32 位有符号整数 | 也承载 8/16 位整数 |
| INT64 | 8 | 64 位有符号整数 | 也承载时间戳、微秒时间 |
| INT96 | 12 | 老式时间戳 | 已废弃，新文件不要写 |
| FLOAT | 4 | IEEE 单精度 | |
| DOUBLE | 8 | IEEE 双精度 | |
| BYTE_ARRAY | 变长 | 任意字节串 | 字符串、JSON、BSON、WKB 都走它 |
| FIXED_LEN_BYTE_ARRAY | 定长 | 固定长度字节 | UUID、FLOAT16、DECIMAL、WKB 定长场景 |

为什么没有 INT16、UINT32、DATE、TIMESTAMP、STRING？

因为**存储格式只负责「怎么放字节」，不负责「这些字节是什么语义」**。一个 16 位整数完全可以用 INT32 存，再用编码把高位省掉；一个字符串就是 UTF-8 字节，用 BYTE_ARRAY 存；一个时间戳就是一个 64 位整数，单位是毫秒、微秒还是纳秒，由注解说明。物理类型越少，编解码器要实现的组合越少，跨语言实现越容易对齐。

这也是 Parquet 和 Avro 的一个根本差别：Avro 的 schema 直接描述业务类型，Parquet 的 schema 描述存储类型 + 注解。前者更贴近应用，后者更贴近磁盘。

`INT96` 是历史遗留。它原本用来存 Hive/Impala 的纳秒时间戳，由 8 字节纳秒 + 4 字节儒略日组成，排序规则和普通整数不一样。新 writer 不该再写 INT96；读到它时，按 `ColumnOrder.INT96_TIMESTAMP_ORDER` 或老规则解释。第六章讲排序时会再遇到它。

## 二、LogicalType：给字节加一层解释

逻辑类型可以想成**贴在字节上的标签**。字符串、小数、时间、列表、地图、地理……每个标签还可能带参数：小数保留几位、时间用什么单位、整数有没有符号。有了这层标签，同样的字节就能被解释成不同的业务含义。

| 标签 | 贴在哪 | 老标签（兼容用） | 排序规则 |
| --- | --- | --- | --- |
| STRING | BYTE_ARRAY | UTF8 | 无符号逐字节 |
| ENUM | BYTE_ARRAY | ENUM | 无符号逐字节 |
| UUID | FIXED_LEN_BYTE_ARRAY(16) | 无 | 无符号逐字节 |
| INTEGER(8/16/32/64, signed) | INT32 / INT64 | INT_8/16/32/64 | 有符号 |
| INTEGER(8/16/32/64, unsigned) | INT32 / INT64 | UINT_8/16/32/64 | 无符号 |
| DECIMAL(p,s) | INT32 / INT64 / FIXED / BYTE_ARRAY | DECIMAL | 按数值有符号 |
| DATE | INT32 | DATE | 有符号 |
| TIME(unit, UTC?) | INT32 / INT64 | TIME_MILLIS / TIME_MICROS | 有符号 |
| TIMESTAMP(unit, UTC?) | INT64 / FIXED(12) | TIMESTAMP_MILLIS / TIMESTAMP_MICROS | 有符号 |
| JSON | BYTE_ARRAY | JSON | 无符号逐字节 |
| BSON | BYTE_ARRAY | BSON | 无符号逐字节 |
| FLOAT16 | FIXED_LEN_BYTE_ARRAY(2) | 无 | 按数值，NaN 特殊 |
| LIST / MAP | group | LIST / MAP | 未定义 |
| VARIANT | group | 无 | 未定义 |
| GEOMETRY / GEOGRAPHY | BYTE_ARRAY | 无 | 未定义 |

这张表最后三行的「未定义」不是随便写的。它直接影响统计裁剪：LIST、MAP、VARIANT、GEOMETRY 这些类型的 min/max 没有统一排序，writer 不应该写，reader 也不该拿它做比较。第五章会展开。

## 三、数字：整数、小数、半精度

**整数**用 `INTEGER(bitWidth, isSigned)` 描述。`bitWidth` 可以是 8、16、32、64；8/16/32 位都放在 INT32 里，64 位放在 INT64 里。为什么不用更窄的物理类型？因为编码层可以按实际位宽打包，物理容器宽一点不影响磁盘占用。

这里有一个容易踩的坑：**无符号整数的排序**。`UINT32` 的值 4,000,000,000 在 INT32 里是负数。如果 writer 按有符号比较写 min/max，reader 按无符号比较去裁剪，结果会漏数据。所以逻辑类型不仅影响显示，还影响统计的排序规则；`ColumnOrder` 必须和逻辑类型匹配。

**DECIMAL** 是「未缩放整数 × 10^-scale」。比如 `199.90` 的 unscaled value 是 19990，scale 是 2，precision 是 5。物理类型可以选：

- `INT32`：precision 1–9；
- `INT64`：precision 1–18；
- `FIXED_LEN_BYTE_ARRAY`：长度 n 能存 `floor(log10(2^(8n-1)-1))` 位十进制；
- `BYTE_ARRAY`：precision 不限，但必须给出，且用最少的字节。

`BYTE_ARRAY` 和 `FIXED_LEN_BYTE_ARRAY` 的 unscaled value 是**大端二进制补码**，和 Variant 里的小端十进制不一样。这个差异在跨格式转换时经常导致符号错乱，第七章会再提一次。

DECIMAL 的排序是「按表示的数值有符号比较」。如果物理类型是 INT32/INT64，直接按整数比较就对；如果是定长字节，要先把最高位翻转再按无符号比较，或者直接按大端补码的数值比较。

**FLOAT16** 是 2 字节 IEEE 半精度，放在 `FIXED_LEN_BYTE_ARRAY(2)` 里。它的排序和 FLOAT/DOUBLE 一样有 NaN、-0/+0 的坑，writer 最好用 `IEEE754TotalOrder`。

## 四、时间：同一个时间戳，三种含义

时间类型是 Parquet 数据模型里最容易「看起来对、算起来错」的一块。

**DATE** 是 INT32，存「从 1970-01-01 起的天数」，没有时区。排序按有符号整数。

**TIME** 是「一天中的时间」，不带日期。它有两个参数：

- `unit`：`MILLIS`（INT32）、`MICROS`（INT64）、`NANOS`（INT64）；
- `isAdjustedToUTC`：true 表示这个时间已经归一化到 UTC，false 表示本地时间（local semantics）。

**TIMESTAMP** 是「从 Unix epoch 起的计数」，单位同样是 MILLIS/MICROS/NANOS，也有 `isAdjustedToUTC`。载体可以是 INT64，也可以是 12 字节的 `FIXED_LEN_BYTE_ARRAY`（老 INT96 风格的 96 位计数，但注解是 TIMESTAMP）。

`isAdjustedToUTC` 不是装饰。它区分两种语义：

- **true（instant semantics）**：这个值表示时间线上的一个瞬间，比如「2026-10-01T08:15:30.123Z」。不管在哪个时区读，都是同一时刻。
- **false（local semantics）**：这个值表示「本地时钟读数」，比如「2026-10-01 08:15:30」，不绑定某个瞬间。读的时候要结合时区规则解释。

为什么 Parquet 不直接存「带时区的时间戳」？因为时区规则会变（夏令时、政治边界调整），存成「瞬间 + 时区名」会让格式依赖外部数据库。Parquet 选择只存计数 + 一个布尔，把时区解释留给上层引擎。

老文件里常见的 `TIMESTAMP_MILLIS` / `TIMESTAMP_MICROS` 对应的是 `isAdjustedToUTC=true`。`NANOS` 没有对应的 ConvertedType，所以只能靠 `LogicalType`。读到不认识的 `unit`，规范要求当成「不支持的特性」处理，而不是当成坏数据（`LogicalTypes.md:361-380`）。

一个实际影响：如果一列是 local timestamp，而查询按 UTC 瞬间去裁剪，min/max 的前提就不成立。统计值本身没有错，错的是「拿它当瞬间比较」。这类问题在跨时区数据湖里非常常见。

## 五、字符串、二进制与「看起来像字符串」的东西

**STRING** 是 UTF-8 字节，排序是无符号逐字节比较。注意这不是「按 Unicode 码点排序」，也不是「按 locale 排序」。`"Z"`（0x5A）排在 `"a"`（0x61）前面，和人类语言的字典序不一样。统计裁剪时，如果引擎用 locale 比较，就会和 writer 的 min/max 对不上。

**ENUM** 也是 UTF-8 字节，排序同样逐字节。它只是告诉上层「这是枚举」，不强制取值集合。

**UUID** 是 16 字节定长，按大端存放。例如 `00112233-4455-6677-8899-aabbccddeeff` 存成 `00 11 22 33 44 55 66 77 88 99 aa bb cc dd ee ff`。排序是无符号逐字节，这恰好和 UUID 的字符串字典序一致（因为都是大端）。

**JSON / BSON** 是 BYTE_ARRAY，内容分别是 UTF-8 JSON 文本和 BSON 二进制。Parquet 不解析它们，只负责存。想让引擎按 JSON 路径裁剪，得靠上层（比如 Variant 或 shredding），这也是第七章的动机。

**UNKNOWN** 是「永远为 null」的类型，可以注解任意物理类型。它通常出现在 schema evolution 里：一列被删除或类型未知，但列块还在。读取器看到 UNKNOWN，直接返回 null，不用解码。

**FILE** 是 2025 年之后新增的逻辑类型，用来描述「文件引用」（路径、大小、校验和等），字段定义在 `LogicalTypes.md:664-847`。它把「数据湖里存文件指针」这件事标准化，避免每个系统自己拼 JSON。这个类型还比较新，读到不认识它的老引擎会按 BYTE_ARRAY 处理。

## 六、嵌套：LIST 为什么必须是三层

先看一个反例。假设你想存「一组字符串」，最直觉的画法是：

```text
列表（可空）
└─ 元素（可以直接重复的字符串）
```

这是两层：外面一层可空的组，里面直接放重复的字符串。它能表示 `null`（外层不存在）、`[]`（外层在，里面一个都没有）、`["a","b"]`（外层在，有两个值）。但它表示不了 `[null, "a"]`，因为「重复的字符串」本身不能为空。

要表示「元素可空」，必须在中间再加一层：

```text
列表（可空）
└─ 中间层：一串元素（可空列表）
   └─ 元素（可空）
```

这就是规范要求的三层结构（`LogicalTypes.md:876-930`）：

- 最外层决定「列表本身可不可空」；
- 中间层决定「空列表还是有元素」；
- 最内层决定「元素可不可空」。

三层各管一件事，缺一层就少一种状态。用「走到第几层」看更清楚（外层可选、元素可选，数字是累计层数）：

| 记录 | 走到第几层 | 含义 |
| --- | --- | --- |
| `null` | 0 | 列表不存在 |
| `[]` | 1 | 列表存在，但没有元素 |
| `[null]` | 2 | 列表存在，有一个元素，元素为 null |
| `["a"]` | 3 | 列表存在，有一个元素，值为 "a" |

注意 `[null]` 和 `[]` 的差别：前者已经走到中间层（2），后者只到外层（1）。如果没有中间这层，两者会塌成同一个数字，读取器就分不清了。

**MAP** 也是三层（`LogicalTypes.md:1021-1067`）：

```text
映射（可空）
└─ 中间层：一组键值对（可重复）
   ├─ 键（必填）
   └─ 值（可空）
```

外层决定「映射可不可空」，中间层决定「空映射还是键值对」，键必须填，值可以空。同一个键出现多次时，最后一个值生效；规范不建议用它表示「一个键对应多个值」。

老文件里还有两层、非标准命名的 LIST/MAP。规范给了一组向后兼容规则（`LogicalTypes.md:931-1020`、`1068-1099`），读取器要能识别，但新 writer 必须写标准三层。别把「能读老格式」当成「可以写老格式」。

### 6.1 行存里一条记录是连续的，列存里一条记录是拼出来的

还是上面那行订单。行存（JSON 文本、Avro、MySQL 行页）会把它序列化成一条连续记录：`order → item → sku/tag` 全在一起。读 `sku` 得先把整条订单解析出来；写一条订单就是追加一条记录。

Parquet 反过来：`sku` 是一条列流，`tag` 是另一条列流，`order` 和 `item` 只以 def/rep 的形式附着在流上。读 `sku` 只碰 `sku` 那条流；读完整的一行，才需要把几条流按 def/rep 拼回去。写一条订单也不止写一处，而是把值分散到各个列缓冲里。

| 动作 | 普通行数据库/行存 | Parquet |
| --- | --- | --- |
| 写一条记录 | 追加一条，顺序写 | 分散到多个列缓冲，攒够行组再落 |
| 读一个嵌套字段 | 整条记录解析 | 只读对应叶子列 |
| 读完整一行 | 连续读一条记录 | 从多个列流 gather，再按 def/rep 重建 |
| 改一个字段 | 原地改或重写记录 | 重写整个行组/文件 |
| 扫描一列 | 要跳过其他列 | 列块连续，顺序读 |

行存像按房间打包：一个箱子装一间房的东西；列存像按物品类型打包：所有书一箱、所有衣服一箱。找一件衬衫，行存要翻几个房间箱，列存只开衣服箱。

这解释了一个常见直觉为什么是错的：**列存不是「读一行更快」，而是「读一列更快」**。普通行数据库的点查、事务和原地更新仍然是它的强项；完整的 MySQL/PostgreSQL 对照见第 1 章 3.4。点查整行、频繁改单条记录，行存通常更合适；扫宽表里的少数几列、做聚合，列存才占便宜。Dremel 的整套 level 机制，就是为了让「列存读一列」和「还原一整行」这两件事同时成立。

## 七、Dremel：把一棵树压成三列

现在进入这一章最硬的部分。上面那些嵌套结构，在磁盘上不是树，而是**每个叶子列一条独立的流**。Parquet 用两个数字记录「这个值在树里的位置」，读的时候再拼回去。

把嵌套想成一栋楼：订单是整栋楼，商品是楼层，标签是房间。每个值都要回答两个问题：

- 我走到了第几层？（后面叫 `def`，层数）
- 我是从哪一层开始重复的？（后面叫 `rep`，重复层号）

用一个比 LIST 更复杂的例子：

```text
订单（可空）
└─ 商品（可重复）
   ├─ SKU（可空）
   └─ 标签（可重复）
      └─ 标签值（可空）
```

两条叶子路径：

- 从订单到 SKU：最多走 3 层，最多在「商品」这一层重复 1 次；
- 从订单到标签值：最多走 4 层，可能在「商品」和「标签」两层重复。

> 说明：这里的「标签」是简化写法，真实 LIST 还会多一层「列表/元素」的包装；为了看清层数，先把包装层去掉。

假设有 4 行订单：

```text
行 1：order = null
行 2：order = { item = [] }
行 3：order = { item = [ { sku: null, tag: [] } ] }
行 4：order = {
        item = [
          { sku: 100, tag: ["x", "y", "z"] },
          { sku: 200, tag: [] }
        ]
      }
```

`sku` 列的 level 流：

| 行 | 值 | 层数（def） | 重复层号（rep） | 解释 |
| --- | --- | --- | --- | --- |
| 1 | — | 0 | 0 | order 不存在 |
| 2 | — | 1 | 0 | order 存在，item 列表为空 |
| 3 | — | 2 | 0 | order、item 存在，sku 为 null |
| 4 | 100 | 3 | 0 | 第一项，sku 有值 |
| 4 | 200 | 3 | 1 | 第二项，重复在 item 层 |

`tag` 列的 level 流：

| 行 | 值 | 层数（def） | 重复层号（rep） | 解释 |
| --- | --- | --- | --- | --- |
| 1 | — | 0 | 0 | order 不存在 |
| 2 | — | 1 | 0 | order 存在，item 为空 |
| 3 | — | 2 | 0 | order、item 存在，tag 列表为空 |
| 4 | "x" | 4 | 0 | 第一项的第一个 tag |
| 4 | "y" | 4 | 2 | 同一项的下一个 tag，重复在 tag 层 |
| 4 | "z" | 4 | 2 | 同一项的再下一个 tag |
| 4 | — | 2 | 1 | 第二项，tag 列表为空，重复在 item 层 |

这张表是整章的钥匙。它说明三件事：

1. **NULL 不占值空间。** `sku` 列的行 1–3 都没有值，只留下层数 0/1/2；`tag` 列的空列表也只留下层数。1000 行全 null 的列，值区可以是 0 字节，只剩一段 RLE 的 def。
2. **重复层号告诉我们「在哪一层重复」。** 0 是新行；1 是同一个订单的下一个商品；2 是同一个商品的下一个标签。没有它，读取器不知道 `"y"` 是属于第一项还是第二项。
3. **层数告诉我们「停在哪一层」。** 2 表示订单和商品都在，但标签列表为空（或 SKU 为 null，取决于列路径）；4 表示整条路径都存在。层数的最大值，就是路径上「可空/可重复」的层数。

读取器还原行时，其实就在做四件事：

1. 看到重复层号是 0，开新的一行；
2. 重复层号是 1，关掉「标签」层，回到「商品」层；是 2，只回到「标签」层；
3. 层数没走到头，就在对应的层填 null 或空列表；
4. 层数走到头，就把值放进当前容器。

真正的实现会为每个重复层维护偏移量和长度，但逻辑就是这个。Dremel 的高明之处在于：**它把「树形结构」编码成了「一串值 + 每个值的层数/重复层号」**，既保持了列存的连续性，又能在读取时精确还原。

## 八、地理空间：GEOMETRY 与 GEOGRAPHY

Parquet 在 2025 年之后加了两个地理逻辑类型（`Geospatial.md:69-81`）：

- **GEOMETRY**：平面几何，边按线性/平面插值；适合投影坐标系、局部几何计算。
- **GEOGRAPHY**：球面/椭球面几何，必须指定边插值算法（`SPHERICAL`、`VINCENTY`、`THOMAS`、`ANDOYER`、`KARNEY`）；适合经纬度、跨洲距离。

两者的值都是 WKB（ISO 变体，支持 XY、XYZ、XYM、XYZM）。可以把 WKB 想成「几何图形的二进制画法」：点、线、多边形各有固定写法，阅读器按标签就能还原。默认坐标系是 `OGC:CRS84`，也就是经度/纬度、WGS84 基准；非默认坐标系可以用 `AUTHORITY:CODE`、`PROJJSON`、`srid:<n>` 或 `projjson:<key>` 指定。坐标轴顺序在 WKB 和 bbox 里**永远是 (x, y)**，x 是经度/easting，y 是纬度/northing，这条规则覆盖坐标系自己的轴顺序（`Geospatial.md:157-162`）。

地理列的统计只装两样东西：一个**外接矩形**，和一个「这一列出现过哪些几何类型」的列表。外接矩形可以想成「给一堆积木拍一张最小的外框照片」：它不描述形状细节，只描述「东西大概占多大地方」。

`bbox` 是每个维度的最小/最大值：x、y 必有，z、m 可选。计算时跳过 null/NaN；如果 X 或 Y 整个维度都缺失，就不产生 bbox。最特别的是经度：当 bbox 跨过反子午线（±180°）时，`xmin` 可以大于 `xmax`，表示「x ≥ xmin 或 x ≤ xmax」的环绕区间。很多读取器在这里直接按 `xmin <= x <= xmax` 判断，结果把跨日期变更线的数据全裁掉。

`geospatial_types` 是列里出现过的 WKB 类型码列表，比如 `[1, 3]` 表示同时有 Point 和 Polygon；空列表表示「不知道」。这些码来自 WKB 的 ISO 变体：1=Point、2=LineString、3=Polygon、4=MultiPoint、5=MultiLineString、6=MultiPolygon、7=GeometryCollection，前缀 1000/2000/3000 表示 XYZ/XYM/XYZM。列表里的值必须唯一。

地理统计能做什么？如果查询是「找某个 bbox 内的点」，读取器可以先比 bbox：行组/页的 bbox 和查询 bbox 不相交，就跳过。但 GEOMETRY/GEOGRAPHY 的 `ColumnOrder` 是未定义的，所以**不能用 min/max 对几何值本身做排序裁剪**，只能用 bbox 做空间相交判断。这是两种不同的统计，别混。

## 九、踩坑清单

| 现象 | 更可能的原因 | 先看哪里 |
| --- | --- | --- |
| 字符串 min/max 裁剪漏数据 | 引擎用 locale 比较，writer 用无符号逐字节 | `ColumnOrder`、`STRING` 排序规则 |
| 无符号整数统计裁剪漏数据 | 按有符号比较写/读 min/max | `INTEGER(bitWidth, false)`、`ColumnOrder` |
| 时间戳差 8 小时 | `isAdjustedToUTC` 语义用错，或把 local 当 instant | `TimestampType.isAdjustedToUTC`、`unit` |
| 小数读出来符号反了 | 把大端补码当成小端，或 scale 用反 | `DECIMAL` 定义、物理类型 |
| 空列表和 `[null]` 分不清 | LIST 少写了中间 `list` 层，或读取器不认 3 层 | `LIST` 结构、def level |
| MAP 的 key 为空 | key 写成了 optional | `MAP` 规范：key 必须 required |
| 老文件 LIST 读错 | 没按向后兼容规则识别 2 层/非标准命名 | `LogicalTypes.md:931-1020` |
| 地理 bbox 裁掉了跨日期变更线的数据 | `xmin > xmax` 时没做环绕判断 | `BoundingBox`、`Geospatial.md:82-129` |
| 新类型在老引擎里变成二进制 | 未知 LogicalType 被降级 | 这是兼容规则，不是 bug |

## 十、这一章留下的线索

- 物理类型只有 8 种，语义靠 LogicalType 注解；`ConvertedType` 是旧表示，writer 要双写；
- 数字、时间、小数的排序规则由逻辑类型决定，统计裁剪必须用同一套规则；
- LIST/MAP 的 3 层结构是为了区分「容器不存在 / 容器为空 / 元素为空」；
- Dremel 用 def/rep level 把树压成线性流，NULL 不占值空间；
- 地理类型用 WKB + bbox 统计，经度跨反子午线时 `xmin > xmax`。

下一章进入编码与压缩：同样是 `BYTE_ARRAY`，为什么字典、RLE、Delta、Byte Stream Split、ALP 能把同一列压出几倍的差距；以及压缩 codec 和编码的先后顺序。
