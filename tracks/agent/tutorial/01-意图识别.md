# 意图识别：Agent 的第一道分诊台

很多人聊到意图识别，答案只有一句：**"调一次大模型，让它判断用户想干嘛。"**

这句话没错，但它只是玩具系统的答案。Agent 一旦上线，问题马上变成这样：

- 用户说"继续"，你要不要为这两个字再付一次大模型调用？
- 你有 40 个意图，Prompt 塞不下；塞下了，准确率反而掉了，怎么办？
- 用户上一轮说"推荐一台 5000 以内的笔记本"，这一轮说"预算加到 8000，但别太重"——这句根本不是一个完整意图，你怎么识别？
- 用户说"帮我生成一个奥特曼动画"，你的候选意图里没有它，模型硬归了一个最像的，Agent 开始一本正经地胡说八道。
- 你说意图识别准确率 95%，那 5% 错在哪？你怎么知道的？

这些问题的答案，都不在"调一次大模型"里。这一篇把意图识别当成**一个工程模块**来讲：它站在哪、输出什么、核心实现思路是什么、怎么评估。

---

## 一、先定位：它不是分类器，是控制平面的第一个决策

![图 1：意图识别位于用户输入规范化之后、主循环之前，产出控制契约](../assets/01-意图识别的位置.svg)

意图识别的**标准位置**：用户输入规范化之后，主循环（Plan / ReAct / TAO）之前。实践中还有两种变体，但都不推荐作为主形态：

1. **和输入规范化混在一起做**：一次调用既消解指代又识别意图。小系统可以省事，但出了错你分不清是"没听懂"还是"分错类"，可调试性很差。
2. **完全放进主循环让模型自己想**：灵活，但边界模糊、无法单独评估、无法单独灰度。

注意变体 2 与标准形态不是竞争而是**组合**关系：跨长时间线的指代、"现在哪个最便宜"这类外部事实，本来就只能放进循环里深度处理。正确姿势是**入口做初步处理 + 循环内做深度处理**。一条实用判据：**越通用、越面向 C 端的 Agent，规范化与识别越要独立**；用户少、领域窄的专属 Agent 才可以合并省调用。最极端的形态是识别之后按意图分发到不同子 Agent，子 Agent 内部再细分——识别即路由。

**记住一句话：意图识别要能独立评估、独立灰度、独立回滚，所以它必须是一个独立的步骤。**

### 1.0 它在等什么样的输入

意图识别假设上游已经把输入洗干净了，但真实的用户输入至少有六类失真，不先处理，识别层做再多都是白搭：

| 失真类型 | 例子 | 处理要点 |
| --- | --- | --- |
| 指代 | "第二个适合生产环境吗？" | 消解成具体实体 |
| 缺失 | "市场占有率多少？"（没说哪个市场） | 补全或触发澄清 |
| 表达 | 病句、倒装、临时改口"不是，我说的是另一个" | 重写为规范句 |
| 词义 | RAG / 检索增强 / 知识库；同一缩写在 IT 与医疗行业含义完全不同 | 术语表归一 |
| 主观判断 | "最有性价比""再高级一点" | 量化成可判定标准 |
| 外部事实 | "现在最便宜的是哪个？" | 只能查了才知道，交给循环内处理 |

前四类在入口处理；后两类天然要跨阶段——初步处理负责把句子补全成"可判定语义"，量化结果作为关键事实进入上下文。**跨会话的指代（"我去了之前你推荐的那个公园"）无法在第一时间解出**，只能先以属性为线索召回历史细节、再在循环内完成消解——这就是上面"组合关系"的由来。指代消解与量化的完整工程，放到上下文管理那篇细讲。

### 1.1 它到底决定什么

| 决定项                | 售前域             | 售后域              |
| ------------------ | --------------- | ---------------- |
| 加载哪套 Spec（业务规范配置）/ Prompt | 预算、场景、品牌偏好、性价比  | 订单状态、退款期限、是否人工审核 |
| 上下文窗口装什么           | 用户画像、浏览行为、商品候选集 | 订单、物流、售后政策、退款记录  |
| 暴露哪些工具             | 商品检索、比价、推荐      | 订单查询、售后工单、退款接口   |
| 风险等级与是否人审          | 只读，低风险          | 涉及写操作，需要审批门      |

不做意图识别的后果不是"体验差一点"，而是：在售后场景塞一堆用户画像浪费窗口；在售前场景把退款接口暴露给模型制造风险。借用一句话：**方向错了，知识越多越反动。**

### 1.2 它不决定什么

同样重要。这一步**不要**做：

- 不回答用户的问题（最容易犯的错，模型一兴奋就把答案写出来了）；
- 不调用工具（它只负责"选路"，不负责"走路"）；
- 不生成最终方案，不擅自补充事实。

职责边界写不进代码，就写进提示词的"不能做什么"，再用校验层兜底（见第二节）。

### 1.3 从"标签"升级成"契约"

传统分类器输出一个标签就完了。Agent 里的意图识别输出的是一份**控制契约**——后续每一步都读它：

```text
IntentResult =
    reason              # 判断依据——刻意排在所有结论字段之前，见下方说明
    intent              # 意图枚举，只能取候选集内已定义的值
    slots               # 该流程需要的关键参数（槽位）
    missingSlots        # 必填槽位还差哪些
    clarificationQuestion # 建议的追问话术（可空，模型给的更自然，但要有人工兜底）
    constraints         # 硬约束：必须满足，且贯穿整个对话
    preferences         # 软偏好：尽量满足，不满足要明确告知
    confidence          # 置信度
    needClarification   # 是否需要向用户追问
```

![图 2：IntentResult 的字段构成——每一项都驱动下游的一个决策](../assets/02-输出契约-IntentResult.svg)

> **名词解释：槽位与 Slot Filling。**"槽位"（slot）一词来自语言学的框架理论——理解一句话就像填一张"框架"，框架里每个必需的论元就是一个槽。对话系统文献里把这叫 **Slot Filling（槽位填充）**：意图决定"走哪条流程"，槽位填充决定"这条流程要的参齐没齐"。类比表单：意图是决定调出哪张表，Slot Filling 就是把表上一个格一个格填完，缺的格子标出来追问。上面例子里的"订单号""预算""用途"都是槽位。这个概念在 2.3 节还会展开。

几个容易忽略的点：

- **字段顺序是架构问题，不是代码风格**。大模型从左到右逐字生成：结论字段排在推理字段之前，等于逼它没想清楚就先拍板、再倒过来编理由。把 reason 挪到 intent/confidence 前面，仅这一项改动就能带来一档可见的准确率提升（业界经验值 10%~15%）。
- **constraints / preferences 要作为一等公民**。用户说"帮我推荐一条裤子，不超过 100 块，最好是牛仔裤"，"不超过 100 块"是硬约束，"最好是牛仔裤"是软偏好。我必须吐槽：**约束识别是当下绝大多数 Agent 做得最差的一块**——你跟 Coding Agent 说"不要改 A 接口"，它转头就改了，用户怒气值瞬间拉满。把约束从意图里独立出来，是投入产出比极高的改进。
- **reason 不是给用户看的**，是给你排查线上 bad case 看的。每一次判断都要能追责。

## 二、核心思路一：意图是数据，模型输出是不可信输入

![图 3：一次识别内部——调用前渲染提示词，调用后用代码兜底校验](../assets/04-一次识别的内部流程.svg)

### 2.1 把意图写成配置，而不是写进 Prompt 字符串

```text
IntentSpec =
    id            # 意图标识
    description   # 一句话说明这个意图干什么
    boundary      # 边界：什么时候选它、什么时候不选它
    slots         # 槽位定义：名称 / 是否必填 / 类型 / 枚举取值
    fewShots      # 示例：只放最容易混淆的正反例
    tools         # 命中后才暴露的工具（用于工具裁剪）
    contextKeys   # 命中后才组装的上下文片段
    risk          # 风险等级，决定要不要插审批门
```

意图定义是数据，带来三个直接收益：**可以被校验**（模型输出的意图必须在集合里，否则拦掉）、**可以被裁剪**（候选集太大时按需收缩）、**可以被测试**（意图表一张表，测试集一张表，能对账）。

### 2.2 提示词四要素

提示词没有玄学，四件事写清楚就够：**候选意图、意图边界、槽位定义、few-shot**（给模型看几个"输入 → 期望输出"的例子，让它照例学边界，而不是靠规则描述去悟）。其中最容易被偷懒的是边界——只写"商品推荐：用户希望系统推荐商品"是不够的，必须写清：

- "3000 以内有什么手机推荐？" → 商品推荐
- "iPhone 16 的电池容量是多少？" → 商品查询
- "iPhone 16 和小米 15 哪个更适合拍视频？" → 商品比较

**意图识别的绝大多数错误，都是边界没写清。** few-shot 则分两部分：固定的写死边界样本（unsupported / unclear 怎么处理），动态的按当前输入检索注入，避免几十个无关样本干扰模型。

### 2.3 Slot Filling：意图和槽位一次调用一起出

接着 1.3 的名词解释展开：意图分类回答"走哪条流程"，**Slot Filling（槽位填充）回答"这条流程还缺哪些参数"**。四条配合关系：

- **槽位定义挂在意图上，不是全局的**：退款流程要订单号，推荐流程要预算和用途；
- **抽不全就别往下走**：missingSlots 非空就触发澄清，而不是让下游脑补默认值；
- **槽位反哺意图判定**："帮我退了那条裤子"里，"裤子"这个商品槽位是判 `order_refund` 的关键证据——所以**工程上意图与槽位要一次调用联合输出**。拆成两步不仅多花一次调用，还丢掉了两者互相印证的机会；
- **约束也算槽位**："不超过 100 块"是 price 槽位的上界，"别太重"是重量维度的软偏好。

槽位的值不只来自当前这句话，来源有四：**本轮输入、上下文与历史轮、用户画像、工具调用结果**（"现在最便宜的是哪个"只能查了才知道）。所以补全是个跨阶段机制：入口先填能填的，循环里持续补，直到 missingSlots 为空。

### 2.4 校验层：把模型输出当不可信输入

模型会返回你没定义的意图、会漏掉必填槽位、会把 confidence 写成字符串。所以校验层必须做四件事：

```text
validate(raw):
    1. 枚举校验   intent 不在候选集 => 不崩，降级为 unclear + 澄清
    2. 槽位白名单 只保留该意图声明过的槽位，枚举外的取值直接丢弃
    3. 必填重算   missingSlots 以代码重算为准，不信模型自己填的
    4. 数值归一   confidence 转成 0~1，非法值按 0 处理
```

> 一个通用原则：**能用代码确定性算出来的，就不要让模型猜。** 模型只负责它擅长的语义判断。

校验失败不是终点，要设计完整的处理链：

```text
onValidationFailure(raw, errors):
    自纠错 ≤ 2 次：把精确错误摘要喂回模型
        （"字段 tracking_id 必须为正整数，你填了 'TN123'"）——下一轮大概率能改对
    仍失败 => 降级：核心字段有效则部分采纳 + 非核心用安全默认值；
              核心字段无效则挂起转人工
```

三条纪律：**自纠错不超过两次**（同一个格式错误犯第三次，是能力边界不是软错误，继续重试纯烧钱）；回喂的是**结构化错误摘要**而不是全量 ValidationError 堆栈；把"抛异常停摆"和"盲目原样重试"都当成反模式。处理模型输出的总原则一句话：**接收时必须严格，执行时必须保守。**

### 2.5 结构约束选哪一档

"约束模型输出格式"其实有三档，各挡的错不一样：

| 档位 | 机制 | 能挡住 | 挡不住 |
| --- | --- | --- | --- |
| Prompt 约定 / 普通 Function Calling | 概率遵守 | 大部分明显跑偏 | 一切——防线根本没建起来 |
| JSON Mode | 强制合法 JSON | 语法错误、解析崩溃 | 字段名、类型、枚举照样能错 |
| Structured Outputs | Schema 编译成状态机，采样时做 Logits 遮蔽（每一步只允许采样符合语法的字符，把不合法 token 的概率清零） | 字段名/类型/枚举**物理出不了格** | **语义错误** |

前两档等于把校验层的责任全留给自己；第三档把格式错误物理消灭，但带来两个新坑：复杂 Schema 可能触发状态机停滞甚至请求失败；更隐蔽的是——**格式完美反而掩盖语义失效**，模型为了填满必填字段会"瞎填"一个合法但错误的值，这比 `json.loads()` 当场崩溃危险得多（崩溃至少暴露问题）。

配套的 Schema 设计经验值：嵌套超过 3 层错误率显著上升；非平凡字段必须写 description；单个枚举超过 10 个取值，选择准确率开始下滑；字段总数超过 50，整体质量开始掉。**开了 Structured Outputs 也不许撤校验层**——前门换成钢门，不等于后门可以拆掉。

## 三、核心思路二：三层级联 + 置信度闸门

最小版本最大的问题是成本：每一句"继续""好的"都要付一次调用的钱和延迟。解法是**便宜的先上，搞不定再往上抬**：

![图 4：三层级联——规则层、轻量模型层、深度推理层，由置信度闸门串起来](../assets/03-三层级联与置信度闸门.svg)

- **第 1 层：代码规则。** 页面引导（用户点了按钮）、延续性输入（"继续""下一步"）、命中即确定的强规则。特点是零成本、零延迟、100% 可预测。我见过太多系统把"继续"也丢给大模型，偶尔模型心血来潮判成新意图，用户当场懵掉。**能用 if 解决的意图，就不要用 token。** 两个补充：规则层吃的是**规范化之后**的输入（见 1.0），拿原始输入直接匹正则，命中率会惨不忍睹；规则层还有一个便宜变体——**向量匹配识别器**：专属领域里大量输入就是可枚举的几十种说法，把「历史输入向量 → 意图」存成内存字典或向量库，命中即出，性能极好。它更大的用途是**兜底沉淀**：行业黑话、口语表达被识别不出后，从多轮对话和投诉排查里离线挖出来，配成向量对入库，同批数据还能反哺微调。
- **第 2 层：轻量模型。** 各种 Flash / Mini 档，讲究快和省，承担绝大多数请求。经验上 80% 以上的输入是明确的，轻量模型完全够用——这也是"为什么不直接上深度推理模型"的答案。立场句放这：**用户能接受多等几秒拿到好结果，不能接受快几秒拿到坏结果**。级联的排序原则始终是效果优先、成本其次。
- **第 3 层：深度推理模型。** 只接复杂表达、强依赖上下文、多轮意图切换、需要补全隐含信息的输入——典型像"我刚才那个项目还是太普通了，你能不能按大厂后端的要求，帮我改得更像核心项目，顺便告诉我面试官会怎么追问"；这类输入要求它输出 reason 便于复盘。

闸门与仲裁的伪代码：

```text
cascade(输入):
    for layer in [规则层, 轻量层, 深度层]:
        result = layer(输入)
        留痕(trace, layer, result)
        if result == null:                continue   # 这层不发表意见
        if result.confidence >= 0.85:     return result          # 高置信：直接采纳
        if result.confidence >= 0.60:     return 澄清(result)     # 中置信：问一句比赌一把省
        # 低置信：抬一层
    return arbitrate(trace) or 澄清()    # 多识别器加权投票，票数接近就澄清
```

最后必须提醒：**模型输出的 confidence 不是校准过的概率，它更像一个自我感觉良好的分数。** 阈值（0.85 / 0.60）必须用测试集调出来，不能拍脑袋；最好把规则命中、向量相似度、历史意图稳定性等信号一起喂进判断。

另外给 `arbitrate` 打个成熟度标签：多识别器加权投票（各识别器权重 × 置信度累加，第一名领先不足就转澄清）属于**"值得知道、不建议先做"**的方案——理论意义大于实践，多数团队到上线也不会启用它；先把三层级联和阈值调优做扎实，收益大得多。

## 四、核心思路三：候选太多，先收缩再判断

意图从 5 个涨到 50 个，准确率会掉得比想象快：Prompt 放不下，候选越多分类混淆和上下文噪声越高。三种解法，按推荐顺序：

**① 检索收缩候选集（最实用）**

```text
shrinkCatalog(用户输入, topN):
    recalled = 向量检索(用户输入, topN)          # 先粗筛
    候选集 = recalled + [unsupported, unclear]   # 出口永远保留
    # topN 动态化：上下文宽裕时调大；第一次失败重试时，比上次更大
```

**①b 大模型粗筛（没有向量库时的孪生方案）**：先用一个低延迟、低成本的轻量模型跑一轮粗筛——它只携带目标与极少量上下文，所以有足够空间装下**全部**候选意图；筛出 topN 后再做第二轮完整识别。收缩的两条路：向量召回靠基础设施，粗筛靠多一次便宜调用，殊途同归。注意收缩本身有天花板：`shrinkCatalog` 的 Top-N 召回率封顶了最终 Top1——N 取小了，后面再准也白搭（指标口径见第八节）。

**② 层次意图**：按菜单组织成一、二、三级，先判一级再下钻（层次意图 ≈ 决策树，如果你有决策树经验可以直接迁移）。单次分类难度被摊薄，代价是多轮调用、性能变差。经验阈值：**候选枚举超过 20 就该开始考虑层级化，30 是硬门槛**——并且注意"单字段的枚举取值数"与"候选意图总数"是两个不同对象，阈值不可互抄。层次化要和槽位填充混着做——下钻过程中顺手把参数填了。

**③ 保证意图正交**。两个意图语义重叠时，先问自己：**这个差异，值不值得建成一个新意图？**（先评估重叠会不会真的引发处理失败——"比较还是推荐"两种解释用户都能接受时，可以不修。）再决定修法。

> **不要把所有差异都建模成不同的意图，很多差异应该建模成不同的参数或参数值。**

"商品推荐"和"商品比较"天然不正交（很多比较的最终目的就是推荐）。两种处理：拆成三个正交意图；或者**合并成一个意图 + 一个参数**，由代码根据参数决定走哪条流程。我更推荐后者——**用代码处理不确定性高的问题，效果通常比继续调 Prompt 好得多。**

**④ 词汇表：收缩的隐藏前提**。黑话、缩写、多义词先归一再进候选：同一缩写在 IT 行业指客户关系管理、在医疗行业指临床研究管理，词表不解决，检索和 Prompt 一起失效。做法：系统内维护词汇表（MySQL 或向量库均可），规范化前先检索注入；分**公共词表 + 个人词表**两级；沉淀靠离线任务把疑似新词标记计数，达到频次阈值升级入表（示例阈值：总次数 >100、讨论人数 >3、连续讨论 ≥10——数字按你的业务定，机制比数字重要）。它和候选意图检索、动态 few-shot 检索共用同一套检索基础设施，三件事可以并成一件事建。

## 五、核心思路四：多轮状态是一等公民

这是意图识别准确率低的**头号工程原因**：不是模型不行，是多轮状态和上下文管理稀烂。用户输入"预算可以加到 8000，但不要太重"，单独看根本不是完整意图。

![图 5：多轮对话中的意图继承、保守切换、槽位合并与约束累加](../assets/05-多轮状态流转.svg)

状态更新规则用伪代码表达就是六条：

```text
applyTurn(上一轮状态, 本轮结果):
    1. 继承     本轮判不出来 且 有上一轮意图 => 沿用上一轮意图，只更新槽位
    2. 保守切换  意图变了 但 置信度 < 0.8 => 保持上一轮，先向用户确认
    3. 槽位合并  新值覆盖旧值，未提及的保留，不要清空
    4. 约束累加  硬约束只增不减——但必须带作用域与失效条件，见下
    5. 取消     "算了不搞了""不查了" => 终止当前意图链并留痕，这不是 unclear，硬澄清很蠢
    6. 恢复     "还是回到刚才那个方案" => 找回此前挂起的意图与槽位快照继续执行
```

两个要点容易被漏。其一是**取消与恢复**：真实多轮里"补充信息、修改参数、取消任务、切换任务、恢复任务"是五种高频动作，只建模前两种的系统，会把"算了"判成 unclear 去追问。其二是**约束的作用域**：永久约束（"不要动 A 文件"）累加没错；但"修这条 SQL 时不要用参数化查询、用查询构建器"是**只对当前子任务生效的作用域约束**——不设计"从哪来、存哪里、何时注入、何时销毁"，它会被无脑累加、污染后面五十轮，还会在渐进压缩里悄悄丢失。

约束要每轮重申，还有一层机制原因：**注意力分布不均**。首尾权重最高、中间显著衰减（Lost in the Middle，TACL 2024），窗口越长，首轮写下的约束被海量工具返回推到中间的概率越高——**"在上下文里"和"被看见"是两回事**。工程手法是首尾三明治：约束钉在头部系统区，组装时在尾部再追加一份 constraint reminder，像交卷前提醒写名字。完整的上下文侧方案见上下文管理那篇。

## 六、识别不出来：拒识与澄清

很多系统的毛病是**不管用户输入什么，都强行归到某个业务意图上**。正确做法是留两个出口：

- `unsupported`：完全不在候选集里 → **拒识**。老实说"这个我做不了"，比胡说八道体面得多。
- `unclear`：能沾边但分不清，或缺关键参数 → **澄清**。

澄清必须由 missingSlots 驱动，而不是让模型自由发挥追问：

```text
buildClarification(result, spec):
    if result.clarificationQuestion: return 它     # 模型给的更自然，但要有人工兜底
    if result.missingSlots 为空:     return "能再具体说说你想做什么吗？"
    return "还差一点信息：" + 缺失槽位的人工可读描述
```

这里我有一个明确立场：**参数不全时，先问清楚，而不是先猜一个答案糊弄上去。好的回答比快的回答，用户体验更好。**

## 七、多意图：能不做就不做，要做就交给 Plan

用户会说"帮我优化一下这个项目，然后顺便告诉我面试官会怎么追问"。

先判断**这是不是真的多意图**："帮我查询上个月的数据，并且导出到 Excel"——本质意图是"导出"，"查询"只是过程性描述。这类要在提示词里明确要求模型忽略过程性描述，只抓最终目标。

真的是多意图时，**不要在意图识别阶段就把依赖关系统统算出来**——那会拖垮识别本身的准确率和性能。更合适的位置是显式的 Plan 机制：意图识别只负责标记"识别出 [A, B]"，Plan 负责解析依赖、安排顺序、处理步骤级依赖。识别层的输出结构可以带一个 relations 字段（`["A->B"]`，必要时附条件），但依赖分析只在进入深度推理层时才要求模型做。relations 还有一条工程推论：**两条意图完全独立，就意味着可以并发**——同时启动两个主循环各跑各的，这在单意图设计里想都不用想。

老实说，支持多意图有点吃力不讨好：它会破坏第一层规则识别和检索机制（几乎必然走到第三层），上下文膨胀更快，还要引入并发控制。**我的默认建议是不支持多意图**——或者识别出多个意图但一次只做一件，做完问一句"接下来要不要处理 B？"。用户其实不在意你能不能一次解决多件事，在意的是为后面的事干等；先给一个答案再问要不要继续，交互感反而更好，还可能省掉后面几次调用。

## 八、评估：先有测试集，再谈准确率

![图 6：评估与迭代闭环——测试集、指标、阈值调优、上线埋点、bad case 回流](../assets/06-评估与迭代闭环.svg)

### 8.1 测试集至少覆盖五类

标准表达、口语化表达、槽位缺失、拒识、易混淆样本。有余力再补：跨轮补充、约束识别、意图切换、多意图。你在传统软件工程里学的用例设计技巧，这里全部适用。

### 8.2 指标

- **Top1 准确率**：主看的指标；
- **Top-K 准确率**：系统每次返回 K 个候选，标准答案在列即命中。K=3、100 条样本 85 条命中即 Top3=85%。它同时是候选收缩的**天花板**——第四 `shrinkCatalog(topN)` 的 Top-N 召回率直接封顶最终 Top1，N 取小了后面再准也白搭；
- **分意图准确率**：80% 的请求都是商品推荐时，模型全猜推荐也有 80%——但退款、投诉这些低频高价值意图可能一塌糊涂，必须单独看；
- **拒识与澄清**：拒识准确率；**误拒率**（该识别的正常输入被拒了——把朋友当敌人，伤体验）；**漏拒率**（该拒的超范围输入被硬接了——放敌人进门，伤口碑，通常更危险）；澄清触发准确率；**澄清后收敛率**（追问之后，用户补一轮信息就能定下意图的比例，低了说明问不到点子上）；
- **槽位**：槽位准确率 / 召回率、必填槽位完整率、槽位更新准确率、**约束识别准确率**（当下做得最差的一块）。

几个经验值：专属领域 Agent 的 Top1 做到 99% 以上是正常的；通用 Agent 一般在 80%~90%。顺带一个口径提醒：只支持两三个意图的专属领域，随便调一次模型也能 90%+；通用 Agent 宣称 90% 往往有水分——分母里混着大量本来就该拒识的输入。

### 8.3 阈值要调，不要猜

```text
tuneThresholds(测试集):
    for accept in [0.80, 0.85, 0.90]:
        for clarify in [0.50, 0.60, 0.70]:
            跑一遍测试集 => (Top1, 平均调用层数, 澄清率)
    在三者构成的帕累托前沿上选点
```

另外，线上有一批**免费的负样本信号**：用户说"不是，我不是这个意思""你理解错了"——这些都是上一轮意图识别失败的强信号，应该自动采集进测试集。更进一步，把评估做成**运行时步骤**：每轮对话开始时，用第 N+1 轮的输入在线评估第 N 轮的效果（用户是纠正还是接受，就是最便宜的标注信号），并建立长期的成败监控，而不是上线前跑一次测试集就完事。

留痕的结构也值得抄细。一句话的 `留痕(trace, layer, result)` 在三个月后救不了你的命；至少要记成结构化字段：每层的候选集、置信度、是否下推、是否触发仲裁、最终采纳与原因，外加 Prompt 版本和意图表版本。否则三个月后准确率掉了，你根本不知道是模型变了、Prompt 变了还是意图表变了。

## 九、踩坑清单

1. **意图越拆越碎**：每来一个新需求就加一个意图。先想想能不能建模成参数。
2. **让模型自创意图**：没有枚举校验，等于把系统稳定性交给概率。
3. **把置信度当概率**：没校准过，阈值必须靠测试集调。
4. **忽略多轮状态**：第二轮开始准确率断崖下跌，绝大多数是这个原因。
5. **约束不贯穿**：用户说过的硬约束第三轮就丢了，这是用户最愤怒的失败模式。
6. **强行归类**：没有 unsupported 出口，模型只能硬选一个，然后一本正经地胡说。
7. **意图识别里顺手回答问题**：职责越界，主循环就失控了。
8. **不记版本**：Prompt、意图表改了，准确率变了却查不出原因。
9. **为省事跳过规则层**：把"继续""好的"也丢给大模型，又费钱又不稳。
10. **不评估就上线**：没有测试集，你连"优化了还是劣化了"都不知道。
11. **结论字段排在推理字段之前**：Schema 里 intent/confidence 在 reason 前面，模型先拍板再编理由，准确率被结构吃掉一档。
12. **约束没有作用域**：临时约束被永久累加，五十轮之后还在为第三轮的子任务服务。
13. **开了 Structured Outputs 就撤校验层**：格式被物理约束了，语义垃圾照样进来——前门换成钢门不等于可以拆后门。
14. **把"算了不搞了"当 unclear**：取消和恢复是两种正常状态流转，硬去澄清非常蠢。

## 十、扩展阅读：Codex 是如何实现意图识别的

前面讲的都是"我们自己该怎么搭"，这一节看一个真实的大型 Agent 产品是怎么落地的：OpenAI 的 Codex CLI。结论可能会让你意外——**它全程没有调用大模型去做意图分类**，但整套机制与本文的思路一一对应。

![图 7：Codex 的意图实现链路——代码判定、槽位解析、按意图装载运行时](../assets/10-Codex意图实现链路.svg)

> 版本说明：（开源仓库 openai/codex 的 main 分支，commit `44b857c`，提交日期 2026-09-22）阅读整理。

### 10.1 意图被建模成"任务类型"

Codex 里没有 `intent_recognizer` 这样的模块，它把意图落在**任务类型**上，而且候选集合只有四项：

```rust
// codex-rs/core/src/state/turn.rs:68
pub(crate) enum TaskKind {
    Regular,
    Review,
    Compact,
}
```

实现都在 `codex-rs/core/src/tasks/` 下，各自声明自己的 kind：`RegularTask`（`regular.rs:33`）、`ReviewTask`（`review.rs:47`）、`CompactTask`（`compact.rs:21`），外加 `UserShellCommandTask`（`user_shell.rs`，kind 仍报 `Regular`，见 `user_shell.rs:77`）。

### 10.2 判断与分类逻辑：几乎全在代码层

普通输入不做任何分类，直接走默认意图（`core/src/session/turn_input.rs:362` 的 `spawn_task(..., RegularTask::new())`）。而"代码审查"这个意图由三个入口显式触发：TUI 斜杠命令与弹窗（`AppCommand::Review { target: ReviewTarget }`，`tui/src/app_command.rs:185`）、CLI 子命令 `codex review`（参数见 `exec/src/cli.rs:274` 的 `ReviewArgs`）、以及 app-server 的程序化调用（`app-server/src/request_processors/turn_processor.rs:456`）。

CLI 侧的判定就是一段朴素的优先级判断（`exec/src/lib.rs:2305` 的 `build_review_request`）：先看 `--uncommitted`，再看 `--base`，再看 `--commit`，最后是自定义指令；一个都填不出来就 `anyhow::bail!`。这两点正好对应本文的两个结论：**意图的正交性由代码保证**（几个参数在 clap 层就声明了 `conflicts_with_all`，互相冲突时解析直接失败，不需要模型来区分）；**识别不出来就拒识**（而不是硬归一个最像的）。

### 10.3 槽位填充落在 ReviewTarget 上

`ReviewTarget`（`codex_protocol::protocol::ReviewTarget`）就是标准的"意图枚举 + 槽位"：`UncommittedChanges`（无槽位）、`BaseBranch { branch }`、`Commit { sha, title }`、`Custom { instructions }`。

补齐与渲染集中在 `codex-rs/prompts/src/review_request.rs`：`resolve_review_request()`（`:42`）调用 `review_prompt()`（`:59`），产出 `ResolvedReviewRequest { target, prompt, user_facing_hint }`（`:12`）。最有意思的是 `BaseBranch` 这一支——它先用 `codex_git_utils::merge_base_with_head` **把派生槽位算出来**（merge base SHA），再渲染模板（`:21`）；算不出来则退回到另一条模板（`:20`），改成让模型自己去求 merge base。这正是本文说的：**槽位的值可以来自工具调用的结果，而不只来自用户那句话。**

### 10.4 解析结果怎么驱动后续动作

`spawn_review_thread()`（`core/src/session/review.rs`）拿到结果后做的事，与本文"意图决定什么"逐条对应：换模型（优先 `config.review_model`）；裁剪能力（关掉 WebSearch / Goals，`WebSearchMode::Disabled`）；重算推理档位（review 模型不支持当前 effort 时取中间档）；装载 Spec（`prompts/templates/review/rubric.md` 作为审查规范，渲染出的 prompt 作为子 turn 的首条消息）；起独立子流程（`sess.spawn_task(tc, input, ReviewTask::new())`，`review.rs:220`）；最后发 `TurnItem::EnteredReviewMode` 事件让 UI 切模式。

### 10.5 整体流程与特点

用户输入 → 判断是否显式意图 → 是则走**代码层规则判定 + 槽位填充** → 槽位不合法就**拒识** → 意图确定后**换模型 / 裁工具 / 装 Spec / 定预算 / 起子流程** → 都不是则默认 `RegularTask`，把判断权完整交给模型。

四个可以搬进你方案的结论：**意图集合极小且封闭**，所以根本不需要模型分类；**能确定的意图一律用代码判定**（对应三层模型第一层）；**槽位靠结构化参数 + 工具结果补齐**（对应 Slot Filling）；**只有默认路径把判断权交给模型**——一句话概括：**能确定的意图用代码，确定不了的才交给模型。**

还有一个能印证第四节"收缩"思想的产品细节：Codex 的 Skills 采用渐进披露——先只把技能名、描述、路径放进上下文，模型决定使用某个技能时才加载完整说明。**先挂 handle、按需展开**，与候选收缩、P3 索引化是同一套工程直觉。

### 10.6 可延伸阅读的入口

- 意图枚举与任务类型：`codex-rs/core/src/state/turn.rs`、`codex-rs/core/src/tasks/`
- 参数 → 意图的判定：`codex-rs/exec/src/lib.rs` 的 `build_review_request`、`codex-rs/exec/src/cli.rs` 的 `ReviewArgs`
- 槽位解析与提示词渲染：`codex-rs/prompts/src/review_request.rs`、`codex-rs/prompts/templates/review/rubric.md`
- 按意图装载运行时：`codex-rs/core/src/session/review.rs` 的 `spawn_review_thread`
- 官方文档与版本：`https://github.com/openai/codex`（README 与 `docs/`），版本号以 `https://github.com/openai/codex/releases` 为准（仓库 `CHANGELOG.md` 也注明 changelog 在 releases 页面）

## 总结

回到开头的问题："意图识别怎么做？"如果只能说一句话，我希望是：

> **意图识别不是为了给用户输入贴标签，而是为了决定 Agent 后面该怎么想、加载什么上下文、调用什么工具、进入哪个业务流程——它产出的是一份可执行、可审计的控制契约。**

落到工程上，一个能长期演进的意图识别模块长这样：

- **意图是数据**，输出是**契约**（意图 + 槽位 + 硬约束 + 软偏好 + 缺失项 + 置信度）；
- **模型输出是不可信输入**，能由代码确定性算的绝不交给概率；
- **三层级联 + 置信度闸门**，规则层兜住确定性输入，轻量层扛大流量，深度层啃硬骨头；
- **候选集先收缩再判断**，意图保持正交，差异尽量建模成参数；
- **多轮状态是一等公民**，约束贯穿整个对话；
- **留好拒识与澄清两个出口**；
- **有测试集、有指标、有版本、有埋点**，否则一切优化都是玄学。

做好这些，你的 Agent 未必变聪明，但一定不会再"听不懂人话"。而对用户来说，后者往往更致命。

## 思考题

1. 你现在的 Agent 里，意图识别在哪一步做？如果把它从主循环里抽出来独立成一步，哪些 bad case 会变得可观测？
2. 挑出你系统里最容易混淆的两个意图，试着把它们的差异改写成"一个意图 + 一个参数"，看看准确率有没有变化。
3. 用户说过的硬约束，你的系统能记住几轮？如果答案是"看模型心情"，那 constraints 这个字段值得你今天就加上。
4. 对照 1.0 的六类失真清单：你的系统目前对哪一类完全没有防线？
