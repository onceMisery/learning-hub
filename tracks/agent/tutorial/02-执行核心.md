# 执行核心：把"边想边做"装进可恢复的循环

很多人讲 Agent 的执行，落成一句话：**"模型想一步、做一步、看一步，循环到完成。"**

玩具系统确实可以这样跑。但一进生产，问题就来了：

- 第 10 步发现第 3 步的前提假设是错的——重跑全部？从哪步开始重跑？
- ReAct 循环转了 847 圈，每圈日志都是绿的，账单却爆了。谁让它停？
- 113 个工具摆在模型面前，它选了 `run_test` 去做 `run_etl` 的活。这算 Prompt 问题还是架构问题？
- 模型宣布"任务已完成"，去账上一看，钱出了两次。
- 进程半夜崩了。重启之后，Agent 还知道自己跑到哪一步吗？

这一篇把执行核心拆成三层来讲：**Plan 是执行前写下的契约，TAO 循环是运行时的状态机，治理是套在两者外面的预算与护栏**。三层各有一套工程做法，缺任何一层，"智能"都会以你意想不到的方式烧钱或闯祸。

---

## 一、Plan 的本质：不是步骤清单，是运行时对象

先立一个判断标准：**一个 Plan 如果不能在运行时被检查、被纠正、被恢复，它就只是一段给模型自己看的独白。**

### 1.1 坏 Plan 长什么样

「分析需求 → 收集信息 → 执行任务 → 总结输出」——这类四步清单几乎人人会写，但它只回答了"做什么"，没回答五个更要命的问题：目标算不算达成？已知和缺失分别是什么？哪些约束不可违反？为什么这一步排在这？失败了怎么办？

这五个问题对应五类不确定性，Plan 存在的唯一理由就是把它们在执行前压缩掉一部分：

| 不确定性 | 不处理的后果 |
| --- | --- |
| 目标 | 方向不清，越努力越偏 |
| 上下文 | "那个项目"指哪个、哪些事实已确认，全靠模型猜 |
| 路径 | 多种方式都能达成，为什么选这条——排障时最需要"为什么" |
| 过程 | 运行期是否合规，没有方案，只能事后认栽 |
| 失败 | 失败形态无穷，不预先决定"重试还是追问还是重来"，现场必然慌乱 |

### 1.2 Plan 与 Workflow 的分界线

不是所有任务都需要 Plan。**Workflow 的分支在任务开始前就能穷举；需要 Plan / 循环的真正理由，是存在大量"只有运行时拿到观察结果才能确定"的决策。**同一个"推荐商品"目标：画像完整就直接检索；画像不全但用户愿意回答就先问；用户不愿补就用历史偏好出保守候选；接口挂了切缓存——这些岔路没法提前画完。

实践取向：**非必要时优先线性 Plan**（简单、可靠、易排查）；分支能枚举清楚的用 Workflow 落地更快。两者是"进可攻退可守"的关系，不是信仰之争。

### 1.3 G4C：一个合格 Plan 的五要素

| 要素 | 解决什么 | 缺失的直接后果 |
| --- | --- | --- |
| **Goal** 目标 | 要去哪、什么叫成功 | 目标漂移 |
| **Context** 现状 | 现在世界是什么状况 | 凭空规划、幻觉 |
| **Choice** 路径 | 怎么走、还有哪些路可走 | 步骤机械，无法因地制宜 |
| **Checkpoint** 检查点 | 怎么知道走偏了 | 偏了也发现不了，发现也只能整体重来 |
| **Correction** 纠偏 | 偏了怎么拉回 | 运行期没有纠错能力 |

几个容易忽略的写作判据：

- **Goal 要带标准**。"把页面优化得好一点"里的"好"必须让模型自己定义成可检验的形容词（首屏加载 < 2s、LCP 评分 ≥ 90）。很多不稳定输出和幻觉，源头就是 Prompt 里一个未定义的形容词。专属 Agent 可以预置分级标准，再接检索补标准。
- **Context 里要区分事实 / 假设 / 缺失信息**，并明确声明哪些是用户确认过的。
- **约束单独维护**。硬约束（"不许动生产库"）与软偏好（"尽量快"）分列两表，每次模型调用都重新注入系统提示词位——长上下文里，只有持续重申的约束还保有影响力。约束可以被用户新输入更新，但每条变更必须以用户输入为证据，模型不得自改。
- **Choice 要留理由**。除了 `selected_path + steps`，给每个 step 补一个 `reason`，排障和价值评估时都靠它。路径本身不重要，"为什么走这条路"才可用于事后分析。
- **Checkpoint 按三条规则布点**：业务状态推进到新阶段（里程碑）；关键中间产物影响下游处；历史上容易出错的步骤之后。数量上有朴素起点：**检查点数约为步骤数的 1/3**（平均每三步回看一次），检查点过密烧钱、过疏失察。每条检查结果带证据（检查点名 / 结论 / 逐条依据），后续根因分析直接消费。
- **Correction 有五种手段**：Retry（当前步重试 / 局部重试 / 从头再来）、Replan（认定计划本身有问题）、Clarify（问用户）、Rollback（回到某检查点之前）、Interrupt（明确终止交人）。宁可 Clarify 也不要用一个错误回答继续烧 token——错的回答不只浪费钱，还会污染后续步骤的世界观。失败场景多了不要全塞 Prompt，按上下文从知识库选择性注入。

## 二、Plan 的生成与评估：先给计划做一次 Code Review

### 2.1 生成侧

让模型"先规划后回答"，靠的是把 G4C 变成生成 Prompt 的硬要求：目标+形容词标准、双表约束、带理由的路径、按规则布检查点、按场景枚举纠偏手段。

更进一步的做法是**迭代式生成**：Plan 出来后不直接执行，先跑一遍结构化审查，不合格打回重写，设最大轮数（多数一次收敛），并监控平均审查轮数——均值上升说明生成机制在退化。相当于给计划补一次 Code Review。

### 2.2 评估侧：一串乘法在等着你

先记住可靠性算术：**单步 95% 正确率串成链，3 步 ≈ 85.7%，10 步 ≈ 59.9%，19 步 ≈ 37.7%**。把单步从 95% 提到 99%，成本指数级上涨；把 19 步的链压到 4 步 ≈ 81.5%，几乎免费。**缩短链路长度比提升单步精度便宜一两个数量级**——这是执行核心里性价比最高的一条经验。

由此推出关键设计：**决定失败概率的不是总步数，而是关键路径长度**（必须排队等前一步的最长串行链）。互相没有依赖的查询应当并发；DAG 上求最长路径（无依赖者深度 1，否则 1+max(前置深度)）就得到真实链长。

离线评估用另一个模型围绕 G4C 出诊断报告（总评分 + 各要素问题清单 + 建议），两条可直接量化的判据：是否违反硬约束、检查点是否足够。线上看五项指标：**Plan 完成率、步骤成功率、Replan 触发率**（常规埋点即可）、**用户纠正率**（"不是这个意思"的频率，最难采集）、**最终任务成功率**。三者必须分开：Plan 完成 ≠ 任务成功 ≠ 用户目标达成。

还有一个常被跳过的审查环节：给候选 Plan 出一份四维体检单——结构分（关键路径、并行度）、风险分（不可逆步骤数、外部依赖数）、兜底分（人审点、补偿覆盖、降级路径）、成本分（token、调用数、耗时），加权后分档放行：低分拒绝执行，中间档可跑但必须加兜底，高分直接过。注意判决不是纯阈值：结构分低于底线直接拒（拓扑硬伤没救）；风险高但兜底全的，放行但加审计。**审查器不改计划，它只负责说真话。**

## 三、DAG Plan：把计划变成数据结构

给人看的三步清单，回答不了四个问题：第二步依赖谁？第一步算不算真完成？第二步失败后第三步是等还是跳过？重启后从哪续接？所以生产环境的 Plan 要落成带状态机的节点表。

### 3.1 节点的最小字段集

```
PlanStep {
  step_id            # 稳定身份：恢复时认出"还是原来那一步"
  action, params     # 做什么
  depends_on[]       # 依赖
  -- 运行时
  status             # TODO / DOING / DONE / FAILED / BLOCKED / SKIPPED / OBSOLETE / UNKNOWN
  output_ref         # 产物引用：下游据此复用，不必重跑
  error
  -- 审计
  version_created
  replaces_step_id   # 新步骤声明它替代谁
}
```

生成顺序：先让模型识别步骤间依赖，再由依赖构图。Prompt 里补三样：依赖识别规则（越细越好）、本业务的反常规例子（哪些看似可并行其实禁止）、循环依赖自查——但模型自查完**代码必须再查一遍**，这项任务模型又慢又容易漏。节点表达首选 `nodes: [{id, depends_on}]`；只有依赖本身需要带属性时才升级为 `edges`。

### 3.2 执行与失败传播

就绪集的计算只有一行话：`status == TODO 且所有依赖均为 DONE` 的节点集合，可以并发执行。主循环受最大步数与 BLOCKED 双重退出约束。

某节点失败后，**沿反向邻接做 BFS，把未完成下游标成 OBSOLETE**；三条细节决定这套机制的成色：

1. 失败节点自身保持 FAILED（它是审计信号），不是直接标 OBSOLETE。
2. **已完成节点不标 OBSOLETE，但要继续向下遍历**——它的下游可能还是 PENDING。已完成节点的产物是工程资产，必须复用。
3. Replan 生成的补丁要过四条不变量：只能替换受影响范围内的步骤；DONE 步骤不得被覆盖；指向范围外节点的依赖不得被删除；新增步骤必须可从失败子图到达且数量封顶。合并前再做一次环检测。模型有时会"顺手"要求替换一个已完成步骤（"我觉得 S1 也有问题"），此时要么拒绝，要么把被替换者显式打成 OBSOLETE——绝不能让同一职责在图里同时存在两个有效节点。

优化手段沉淀到最后是三件事：**线上正确执行过的 Plan 抽成模板库**（先生成再执行，给可靠性一个基线）、失败 Trace 聚成"结构指纹"回流成审查规则、以及把关键写操作配上 `idempotency_key`、每 3~4 个串行步骤插一次状态落盘。规则计算、字段转换、事实查询这类步骤，优先交给确定性代码而不是模型。

## 四、Replan：失败点不等于根因点

Replan 的定义要抠三个词：**执行过程中、基于新信息、受控修正**。它不是"把旧计划丢了重来"，而是 Correction 的一种实现。

### 4.1 触发时机有三类，第三类最容易漏

1. 工具调用失败——任何失败都意味着原计划至少在这一段推不下去了。
2. 上下文变化——用户中途新增或修改了约束。
3. **计划所依赖的假设被违反**——所有工具都成功、每一步都没报错，但因为底层数据或状态不对，整个计划已经站不住。这类"无声的失效"只能靠检查点主动暴露。

一条工程纪律：**"要不要 Replan"和"怎么 Replan"拆成至少两步**。合并在一次模型调用里，两件事会同时变笨。前者甚至可以先用代码过滤（按异常类型分类，if-else 或责任链），代码判稳定、便宜、快；多数场景连模型判定都不需要。判断"这个错误值不值得 Replan"的两问：换一个路径能不能绕开（存在替代工具/算法）？替代方案用完了吗（没有可行的替代方案就是无路可走）？

### 4.2 四个点必须严格区分

| 概念 | 定义 | 例 |
| --- | --- | --- |
| 失败点 | 错误**暴露**的位置 | 第 6 步调用售后接口被拒 |
| 根因点 | 最初引入错误事实/假设的位置，可能离失败点很远 | 第 2 步查到"未发货"，第 4 步执行时其实已出库 |
| 回滚点 | 状态要恢复到的位置（通常是某个检查点） | 回到检查点 1 之后 |
| Replan 起点 | 从哪个节点重新生成计划 | 可与回滚点重合，也可更早 |

把失败点直接当根因点，是 Replan 反复失败的头号原因。上面这个退款案例值得咀嚼：A 步查状态判定可走极速退款；执行期间订单出库；B 步**确实读到了新状态**；C 步沿用 A 的旧结论发起退款被拒。如果系统没有为每一步记录**决策当时的状态快照**，事后排查只会误判成"C 步参数错了"。快照的价值就在这：让"结论过期"这种错误可以被机器发现。

### 4.3 回溯的尺度

回溯层级从浅到深五档：**动作级**（超时、格式错、网络抖动——先重试，Prompt 里明确"重试优先于回溯"）→ **步骤级**（本步路径不对但前序结果可信，换一个等价实现）→ **阶段级**（本阶段输入整体失效，回到阶段入口重规划，阶段由检查点圈定）→ **全局**（否定所有中间结果）→ **跨轮次**（几轮前被错记的事实被一路沿用，要定位它最早哪轮写入、污染了哪些摘要/画像/事实表，代价极高，必要时清空重建）。

操作方法是固定的四步：记录每步关键信息（输入/输出/依据的事实与证据/所依赖的假设/检查点结果）→ 给中间结果标可信状态 → 从失败点沿依赖反向排查 → 回到最近的可信检查点。可信状态最少三档即可开工，全量是五档：

```
Verified（已验证且仍可信） / Available（可用但未充分验证，孤证默认态）
Suspicious（存疑待复查） / Invalid（确认错误） / Dirty（自身未必错，但依赖了 Invalid）
```

每个输出条目挂上"依赖了谁"，上游一旦切 Invalid，下游级联标 Dirty，根因即可反查。反向排查的问题清单可以长期扩充：当前步执行错了吗→输入对吗→上游中间结果还可信吗→上游事实对吗→原计划假设成立吗→用户目标/约束变了吗。两个提醒：**检查点也可能被骗**——多个错误恰好互相掩盖时，检查点是"在当时的上下文下"通过的；以及**别盲信复用**——模型为了适配新计划，会忽略甚至扭曲一个错误的中间结果。

回溯的取向一句话：**宁可早一步，不可晚一步**——留着错误结果继续跑，比重跑几步贵得多。像异常处理一样渐进扩大：先试最便宜、影响最小的恢复，无效再每次向上一个检查点扩大。规模做大后可以走"跳跃式"：把历史故障的（问题 → 回溯位置 → 新计划）沉淀成案例库（向量库承载），命中直接定位。

评估恢复机制看五个数：**根因定位准确率**（垂直领域做到 80%+ 可行）、**Replan 起点准确率**（退太晚留错误、退太早浪费正确，两向偏差都算错）、**已有结果复用率**、**Replan 恢复成功率**（触发 100 次只成 20 次等于纯烧钱）、**Replan 振荡率**（在两个相似计划间来回横跳；典型成因：没记录失败路径、失败原因不明确、Prompt 缺控制信息）。

### 4.4 让岔路口保留在计划里

不必等失败才重新思考：Choice 节点里保留 `candidates`（路径/状态/理由），失败后回到岔路口选下一条**未尝试**的路径，省一次重新规划。**必须同时记录已尝试路径及其失败原因**，否则会"A 失败 → 又选 A → 再失败"原地打转；只有失败原因被确认修复，才允许重选。

副作用重的场景，Replan 可以先"试错再 commit"，即 TCC 式三阶段（Try-Confirm-Cancel，借自分布式长事务的补偿模式：先试探性预留，确认才提交，否则撤销）：

- **Try**：不是把新计划跑一遍，而是挑计划里**最重要、最不确定、失败代价最高**的部分做最小验证（严重依赖外部接口的，先试接口通不通；DAG 里被五个后续步骤依赖的单点先碰）。Try 必须低成本、无副作用（查询代替写入、dry-run 输出 SQL 而不执行）。
- **Confirm**：按计划执行，同时把 Try 的结果写回上下文供复用。
- **Cancel**：清理 Try 的临时状态（Try 数据放独立临时空间，别混进正式上下文）；把失败的假设与不可用的工具打上标记，让下一次规划绕开；然后再 Replan 或中断。

普通任务用不着 TCC；高失败成本、高外部依赖、高副作用的场景才值得。

最后说清代码与模型的分工，这条原则贯穿本篇：**能用代码做的判断就别交给模型**。模型负责语义（这个错误现象对应哪类业务根因、目标变没变、生成候选路径）；代码负责确定性活（遍历 DAG、找上下游、标 Dirty、定位最近检查点、查环、控制重试与 Replan 次数、执行回滚与补偿）。ReAct 之所以难以恢复，本质就是这些确定性的活全被塞进模型一段临时的思维独白里——第三步失败的系统在它的世界里根本没有"第二步"这个概念。**把计划变成带版本号和状态机的数据结构，Replan 才能从"推倒重来"变成"局部作废 + 换道"。**

## 五、TAO 循环：以大模型为变迁引擎的状态机

ReAct（Reasoning + Acting，2022 年提出）的运行形态——输入、思考、执行、取结果、再思考——大家都会背；TAO（Think / Action / Observation）则是把它落进工程的叫法，两者实践中同指一事。先给能力边界：**ReAct 在 6 步以内的多跳任务上表现很好；拿它裸跑复杂长程工程任务，就是"蒙眼狂奔"。**

**TAO 的本质是一个状态机，只是变迁引擎换成了大模型。**普通状态机的迁移由代码驱动，TAO 由模型驱动——所以工程重心不是三段 Prompt 怎么写，而是这个状态循环怎么维护：读取当前状态 → Think → 选 Action → 执行 → 生成 Observation → 更新状态 → 判断继续还是停止。

![图 1：TAO 循环的状态结构与六个出口](../assets/07-TAO循环状态机与六个出口.svg)

### 5.1 状态清单：先把"世界"结构化

一个最小可用的 TAO Runtime 至少要维护这些状态（多数只是同一份数据的另一种组织，按需取用）：

```
GoalState        final_goal / current_goal / success_criteria
                 —— Think 是局部决策，必须有持续存在的目标锚点；
                    每轮重检四问：当前动作推进目标吗？还差什么？成功标准满足了吗？可以停了吗？
ActionState      动作类型、工具、参数、结果；可加重试数、可回滚标记
                 —— 落库（热数据进缓存、冷数据进关系库），及时归档防膨胀
ObservationState 存"对返回值的解释"，不是原始返回（原始返回留在 ActionState）
FactState        已确认事实 / 用户明确认可的事实 / 未验证推测 / 已否定内容 / 当前缺口
                 —— 关键事实绝不能只靠对话摘要存：会压缩就会丢细节，
                    要单独提取、单独存储、每轮在 Prompt 里单独成块重申
ControlState     最大循环次数、已执行次数、预算余量 —— 唯一不能省的状态
```

可选扩展：PlanState（当前计划与版本）、EvidenceState（观点↔多证据绑定，合规类场景值得独立）、GapState、CheckpointState。

### 5.2 Think：四类判断，六个出口

Think 干的活可以压成"缺啥补啥"四个字——目标判断、状态判断（事实够不够、槽位缺不缺、假设被破没破、事实冲突）、路径判断（候选里选哪个）、停止判断；按业务再加风险判断。

每轮 Think 的输出必须是六个出口之一：

| 出口 | 触发条件 |
| --- | --- |
| Continue | 目标未完成且有可推进动作 |
| Finish | 成功标准已满足 |
| Clarify | 缺关键信息，继续猜会违反硬约束或产生高风险 |
| Retry | 路径没问题，偶发失败（超时、临时异常、格式错） |
| Replan | 路径/假设/工具选择本身有问题，需要回溯 |
| Error / Interrupt | 明确做不下去（关键工具不可用）——这个兜底必须有，否则模型不知道如何收尾会一直想 |

**停止条件是循环里最难的部分**，两个失败极端：停太早（判定标准含糊，追求"快"）和停不下来（不断搜索反思，为极小质量增益烧大量 token）。工程解法是把"成功"在设计阶段就写成可验证标准；再加三条：关键信息是否足够（可叠槽位填充）、继续执行能否明显提高质量（最难，靠长期沉淀规则）、预算是否耗尽。还有一条常被忽略：**是否应该先返回阶段性结果**——用户拿到部分答案后，往往根本不需要后续处理。

### 5.3 Action 与 Observation

Action ≠ 工具 ≠ 接口。它是**业务上独立完整的一步**的二次封装：内部可以聚合多个接口、做多路降级，甚至可以是一个子 Agent。别忘了**用户交互也是一种 Action**（"请放好证件""请确认授权"）。

Observation 的职责是存储 + 解读，**解读远比存储重要**。拿到返回值要回答：真的成功了吗（200 不代表成功）？得到哪些新事实、证据是什么？符合执行前的预期吗？还缺什么？有异常或违反约束吗？推翻了哪个假设（推翻假设多半只需换路，违反约束破坏性大得多）？世界状态怎么变了？任务实质进展了吗？最后这条最难，最简的落地是**以槽位填充计进展**：每填上一个槽位算一步。纯靠模型做"存储"不可取；务实形态是代码存储 + 模型做语义解读。

两个结构性强化：

- **双层循环**。内层解决"下一步怎么走"，外层解决"这条路还走得对不对"（目标漂移、约束违反）。外层可以异步跑，也可以内层每 N 轮或每到一个检查点同步触发一次。动机是：长任务的杀手从来不是某一步偶错，而是每一步都"看似合理"的小偏差一路累积。
- **Prompt 拓扑**。极简 Agent 可以一个 Prompt 包打天下；认真做的形态是 Think / Action 选择 / Observation 解读各一个 Prompt（工具海量时 Action 选择还要拆粗筛+精筛）。Think Prompt 的内容就是 5.1 的那些状态。

评估一个 TAO 循环，四层指标：**Think**（动作选择准确率——最重要、参数准确率、缺口识别准确率、约束违反率、停止判断准确率，基本靠离线+抽样人工核）、**Action**（执行成功率、延迟，传统工程指标）、**Observation**（事实提取准确率、证据绑定准确率、结果误读率、异常识别率）、**整体**（任务成功率、平均轮数、平均工具调用数、token 消耗——混用模型时要分模型统计、首字与总延迟）。注意轮数和质量的纠缠：轮数降了质量也降，不算优化。绝大多数 TAO 指标需要另一个模型来评，只有极少数能代码直采——这是下一篇文章的主题。

## 六、循环治理：预算、熔断、恢复

一句话总纲：**可靠的智能体 = 概率模型 + 确定性循环 + 持久化状态 + 故障恢复。**朴素 ReAct 只有前两项的一半。把带副作用的执行权交给概率模型后，自动化不会掩盖缺陷，只会以十倍效率放大缺陷——日志全绿、每步有输出、耗时正常，账上照样可能出款两次。

### 6.1 预算与熔断

- **硬预算四件套**：最大轮数、最大时长、最大 token、最大金额，每轮最先检查，越权必断；外层再加单日总预算闸门。
- **死循环识别两招**：动作指纹去重——对 `{name, params}` 规范化排序后哈希计数，同一参数重复超过 5 次即判打转；幽灵循环检测——滑动窗口内上下文哈希连续不变说明在空转。配合 4.4 的"已尝试路径与失败原因"记录，防的是同一件事。
- **终止权外置（Maker/Checker 分离）**：模型说"做完了"不算，系统验证才算。微观是一个 `goal_achieved(run)` 校验函数，宏观是换一个校验模型点头循环才允许终止。警惕新风险：执行方伪造"看似成功的证据"骗过校验方——所以校验要吃**硬证据**（外部回执、确定性验证器），不吃自然语言结论。
- **提议与执行分离**：模型只是提议者，循环才是决策者。一次调用从"模型吐出工具名"到"真的执行"，中间必须过：注册表强校验（未注册 = 不执行，这同时是防工具幻觉的白名单）、参数类型与取值匹配、权限上下文强注入（模型不知道当前用户的权限边界，不给它就会"忠诚地越权"）、高风险动作命中即转人工审批。子 Agent 的"已完成"声明一律不采信，同样过校验节点。
- **per-tool 熔断**：状态机 CLOSED→OPEN（连续失败 3 次）→HALF_OPEN（60 秒后放行一次探测）→ 探测成功回 CLOSED，否则回 OPEN。关键收益：**熔断中的工具直接从候选集里移除**——模型看不到它，就不会反复重试空转 token。注意别把工具级熔断和全局挂起混为一谈：一个工具坏了不该拖垮整个 Agent。
- **超时语义给"红绿灯"**：给模型的报错，可操作性比详细度重要——红灯（永久失败，别重试，给出替代动作）、黄灯（等 N 秒再试）、绿灯（成功）。重试策略：一次初始 + 最多三次退避；黄灯退避重试，红灯直接告知模型换策略。`rejected`（副作用未开始）和 `failed`（已执行且异常）必须区分；特别记住：**网络超时不代表远端没执行**。

### 6.2 恢复：事件溯源 + 双账本

拒绝隐式 `while True`。显式状态机（`RUNNING / SUSPENDED / COMPLETED / FAILED / CANCELLED`）+ 显式阶段（`PREPARE → THINK → DECIDE → EXECUTE → DONE`），状态显式才谈得上可观测、可调试。`PREPARE` 阶段按"系统指令 > 当前状态 > 知识 > 历史"分层装配上下文，系统区永不压缩——最关键的规则不能被长历史冲走。

断点恢复的标准配方是**事件溯源 + 定期快照**：`PlanCreated / StepStarted / StepCompleted / StepFailed / PlanReplanned` 逐条追加写（带单调序号与计划版本号，不可变），恢复 = 加载最近检查点 + 重放其后的增量事件——和数据库 WAL + Checkpoint 一个道理。**检查点不是聊天记录**：它要能完整恢复执行现场（当前计划、已完成步骤及产物引用、预算余量、崩溃现场），且写入必须原子。每轮 EXECUTE 结束自动落点；粒度决定恢复精度。

恢复还必须防重复副作用，所以要**双账本**：检查点记"流程确认到哪里"（管续跑），幂等账记"外部动作发生过几次"（管副作用）。最凶险的窗口是"外部已入账、本地还没写 DONE 就崩了"——重启后只见 DOING，此时必须先进 UNKNOWN/VERIFYING，用同一个幂等键去查外部系统的真实结果，确认失败才允许重跑。幂等表里再存一份请求摘要，拦"同键不同参数"（同一笔任务不能第一次出 100、重放出 200）。

并发纪律一句话：**只读动作可受控并发（墙钟 = 最慢一路），写入与删除按序串行，共享资源加锁**；多实例并行用工作树/分支隔离，兼防评估方基准被生产方污染。

## 七、工具与行动：候选集是架构问题

### 7.1 Action 的设计判据

粒度以业务完整性为准（一个 Action = 独立完整的一步），职责尽量正交；但业务完整性与正交会冲突（"退货并退款"与"仅退款"共享退款职责），做不到完全正交就把**边界写进描述**。经验规律：**Action 边界模糊时，哪怕只放少量，准确率也明显掉；边界清晰时多放几个问题不大。**工具数多了可以有意识地设计粗粒度 Action（内部按参数分派再二次筛选），但这是无奈之举。

描述字段的最低配置：`name / description / applicable_scenarios / inapplicable_scenarios / required_params`，可选 `preconditions / cost / risk / reversible`。三条铁律：

1. **参数越少、越易得越好**。需要推理才能得到的参数，把那段推理内嵌回代码；前置条件满足与否交代码判断，别交给模型（判反的概率不低）。
2. **返回值最小化**，只暴露调用方需要的东西。一个输出字段有几十种取值、还要教模型怎么读的接口，说明该拆了。
3. **cost 与 risk 只是决胜项**：两个动作难分高下时低风险者胜出；指望 risk 标记让模型放弃最合适的动作，不现实。

提供方责任：每个 Action 自己保证高可用——内部重试（耗尽后把重试轨迹返回给模型）、降级（取不到新数据用老数据）、把互为替代的接口封装进同一个 Action（切换在内部完成）。模型的负担轻一分，选错的概率就小一分。

### 7.2 六大契约：把执行权从概率手里拿回来

工具设计的本质不是实现功能，而是**划定能做什么、不能做什么、做错怎么兜底**。六个环节各有一条契约：

| 契约 | 核心要求 |
| --- | --- |
| 设计 | 原子化 + 正交，禁止"瑞士军刀"工具——权限拦截挂在工具名粒度上 |
| 决策 | 描述六要素：一句话用途 / 使用场景 / 与邻居的区别 / 参数语义 / 重要约束 / 示例。实现完美但描述模糊的工具，对模型等于隐形。**时间要按"80% 打磨描述、20% 写实现"来花** |
| 拦截 | 元数据自描述安全指纹：副作用等级（LOW/MEDIUM/HIGH）、是否强制幂等、预估延迟（超时上限 = 3 倍）、是否只读——把性质判断从自然语言猜测下沉为强类型声明。模型会看错，代码不能看错 |
| 执行 | 副作用工具必须幂等且服务端无状态；幂等键由循环注入（如 `{run_id}:{turn}:{call_index}`）、由服务端原子"检查+执行"去重；跨工具长事务用 Saga 补偿（另一式分布式长事务模式：每步配一个逆操作，失败时按反序逐步撤销） |
| 反馈 | 严格超时 + 红绿灯语义；第三方协议的错误码要有翻译层 |
| 资源 | Token 经济：返回体硬上限（如 4KB）、游标分页、limit 封顶，返回 `next_cursor / has_more / hint` |

真实事故的数字都很朴素：一个查不存在的订单被连续调 847 次；超时重试叠加无防重的邮件服务，同一客户收到 50 封通知；一次工具返回 10MB 日志撑爆窗口，后续对话全丢。

### 7.3 注意力稀释：候选集治理是数学题

一次推理里，模型的注意力预算归一化为 1：10 个工具每个约 10%，200 个工具每个只剩 0.5%。工具 schema 平均 200~600 token，113 个工具 ≈ 4 万 token——还没开始干活，窗口的一半和注意力的一整层已经没了。某次生产事故的直接成因就是 `run_test` 与 `run_etl` 描述几乎相同，模型在 1/113 的注意力里分不出两行字的差别，误迁了 340 万条记录。

三条对策：

1. **任何一次推理，可见工具数 ≤ 20**。越界是数学约束，不是 Prompt 能修的。
2. **分层懒加载 + 角色路由**：L1 常驻 5~8 个基础只读工具；L2 按角色注入 10~15 个领域工具；L3 冷门库（几十到几百个）按需检索 Top-K、用完即焚。每层过滤掉熔断中的工具，末尾硬截断。关键思想：**把"系统有多少工具"和"本轮模型看见多少工具"拆开**。
3. **检索用多维加权，不用向量预判**。工具名是形式化地址，不需要语义相似度——`restart_pod` 和 `restart_service` 向量很近，副作用完全不同。改用"名称分词精确 > 子串 > 全名归一 + 描述词边界匹配 + 领域标签精确"三维加权取 Top-K，权重按业务域滑动（运维域拉满名称维度，客服域抬高描述维度）。

描述模板也按"可召回、可区分"来写：一句话用途（动词+对象）→ 触发条件（用户说什么话时使用——这是召回锚点）→ 互斥声明（和哪个工具排他、边界词）→ 约束 → **不适用场景（负面示例的区分度比正面高）**。"更新 XX 系统的 XX 信息"式功能堆砌，在 200 个工具里毫无区分度。

### 7.4 选错工具的排查：五段定位法

先把一次"工具调用"拆成四个动作：**发现**（从全库搜出来）→ **建前沿**（组成本轮候选集）→ **选择**（模型挑一个）→ **准入**（系统批准这次执行）。三条"不等于"帮你对号入座：**工具库 ≠ 本轮可见集；语义选对 ≠ 本次已获准入；这次调用被拒 ≠ 原始目标完成。**

```
没搜到            → 发现层问题（描述、索引、触发条件）
库里都有但没进候选 → 前沿问题（路由、权限过滤、检索阈值）
候选都有但选错了   → 选择层问题（描述双胞胎、候选超量、缺本轮校验）
选对了不能执行     → 准入问题（注册表/配额/新鲜度/审批四关）
放行后结果错       → Handler 或副作用控制问题
```

排查顺序也按这个来：先看是不是"描述双胞胎/边界不清"（补适用与不适用场景、补互斥声明）；再看候选集是否过大、是否被角色路由正确降维；再看有没有做**本轮候选集校验**（模型常从上下文残留里挑一个"存在但本轮没提供"的动作——校验必须是"是否属于本轮候选"，不是"是否在库里"）；再看有没有排除"已尝试且失败"的项。分层指标配套：发现召回率、前沿召回率与大小、候选选择准确率、准入拒绝原因分布、重复副作用数、补偿债务年龄。

两个进阶件：筛选标准可以从"最可能完成任务"**改写为"信息增益最大"**——缺信息时强制优先补信息，防止模型在信息不足时硬下结论；准入链的标配四关是**注册表（拦幻觉工具）→ 配额（会话/工具/参数维度）→ 状态新鲜度（写入前重读最新业务状态）→ 审批**，且"判断点与执行点分离"：策略判断可以中心化成服务，执行必须贴着 handler。

## 八、推理模式：这件事该消耗多少"想"

推理已经从提示词技巧变成一种**需要被分配、约束、验证、停止的计算资源**。开工前先回答五个问题（推理契约）：要不要深入思考？什么拓扑（单链/并行/迭代）？给多少预算？由什么验证？何时停？预算包长这样：思考 token 上限 8000、端到端 12 秒、模型调用 4 次、工具调用 8 次、并行路径 3 条——答案稳定立即停手。

### 8.1 复杂度路由：先分诊，再看病

不要把模糊请求整体推进推理。先拆成原子任务（对象、动作、上游依赖三件事），逐原子分诊，看四个信号：**意图、证据状态、执行对象状态、动作风险**。三条纪律：

- 证据不是 ready（缺失/过期/冲突/未知）就不得进入自动决策或自动写入——**证据缺口不能用更大的模型来补**。
- 关键执行对象未确认，一票否决。
- **难度和风险是两回事**："把基数改回上个月的"很短但危险；"统计五千人十二个月的分布"很长但只读。风险不得搭复杂度的便车。

路由的输出不是"简单/复杂"的标签，而是一份**带版本号、可审计的控制单**：车道（直答/只读分析/结构化推理/规划执行/澄清人审）+ 思考模式 + 预算 + 人工闸口 + 阻塞项。车道管业务边界与写权限，模式管思考形状，两者不许焊死。路由本身分三层：工作流路由**永远在模型外面**（模型不能自行决定"我可以改薪资"）、模型路由、强度路由（同族模型调思考深度，正在部分取代换模型）。核心指标是**首次路由命中率**，两个失配方向分开治：低估难度就收紧升级前的预判，过度推理就收紧"判复杂"的触发条件——前提是每次路由和最终归宿都进 Trace。

### 8.2 思维链：为验证器留一条可检查的路

先分清三件事：模型内部推理（可能不暴露）、系统组织的外部慎思、供审计的决策记录——**不要把"有条理的自然语言"当成模型真实计算过程的证明**。工程化的 CoT 只服务第三种：一步只表达一个可验证命题，每步挂"主张 / 依赖 / 证据引用（带版本）/ 验证器 / 结果"。检验三问：这步有没有明确命题？能否被工具/规则/库/人独立检查？这步错了影响下游哪些？把观察、计算、查证全塞进一步，系统就不知道该用什么工具验证、也不知道错了影响谁。

差别一句话：普通 CoT 说"我认为合理"；生产级 CoT 说"第 6 步依赖 3/4/5，3 来自差异计算器，4 来自政策 v7，5 已过审批验证器，放行"。过闸看三道：证据闸门（存在性、来源权威、版本、有效期、归属——跨租户误用证据比推理错误更危险）、确定性验证闸门（金额交计算器、生效性交规则引擎、权限交权限系统；模型可以解释验证结果，但不得替代验证器）、升级闸门（证据冲突、同一事实被反复改写、工具结果与模型解释不一致 → 升级到并行/迭代/人工）。存的时候记录"决定"而不是"独白"，也别全量长存原始 CoT。

### 8.3 并行探索与扇出聚合：用多样性换可靠性

单链不可信，因为难题的答案分布是散开的，单跑只采到一个点。**三件事必须分开**：并行探索是"同一目标多路竞争候选解"；扇出聚合是"任务天然可分片，多路各查一块按维度收回"；层级委派是"责任拆分"（属于协作篇）。

并行探索要警惕假多样：同一个 prompt 采 10 次，如果都默认同一业务口径，那只是同一前提的 10 次复读——**执行型系统需要的是业务口径的多样性，不是随机噪声的多样性**。口径要注册表管理（出处、适用条件、所需证据、默认验证器、风险等级），模型可以提议新口径但必须说明来源过人审——口径是业务资产。各路上下文隔离，中途不共享中间结果（互相污染会造出虚假置信度）；每路产出一份结构化的 PathResult（口径、主张、证据、验证器状态、自评置信、成本）。聚合按分级来：全一致自动出；多数一致但有异议，只读结果可弱通过并标注异议，高风险写入必须过人审；平票、关键路失败、证据缺失 → 转人审或回炉。**自评置信只是弱信号，放行的权力属于证据与验证器。**有些分歧是制度分歧（三套法规各自合法），正确动作是把三套依据摊开交人选择——如实报告不确定性不是失败，用一次投票假装消化它才是。

扇出聚合最容易犯的错是**把维度折叠成布尔值**：三路子代理各查一个维度，两路的结论"看似相近"被折算成同一票，算出 2/3 假多数，还丢了第三路的差异信息。记住：**收回来不等于拼起来。**聚合器五步：盘点缺席（按分片 ID 算 missing，缺一维就判证据不足，绝不让主模型凭常识补写；成功数量不得掩盖未处理输入）→ 归一口径（术语/实体/金额与币种/月与结算周期不可混）→ 去重（区分"独立来源支持同一结论"与"同一来源被反复引用"）→ 处理冲突（同时满足"同一命题、同一对象版本、同一取值语义、各路足够独立"才可投票）→ 检查接缝（跨分片不变量：总额越界、同一对象重复出现、版本互不兼容——这类问题不属于任何一路，只能在聚合层发现）。三个收益各归各位：省墙钟（并行 ≈ 最慢一路 + 调度）、扩大证据面（≠ 增加票数）、局部失败显式化。三份同源判断，不会因为来自三个会话就变成三份独立证据。

### 8.4 迭代假设验证：像做科学一样排查

处理"根因深"的问题，三个关键词：**可证伪、外部证据、可停机**。每轮带一个能被推翻的命题进真实环境，不仅问"有什么证据支持我"，还要问"什么证据能证明我错"。推翻 → 换方向；只解释了一部分 → 锁住已解释的，追剩余缺口；连续几轮无新增解释 → 停止自动迭代交人。

三角色拆分（为压确认偏误：同一模型自己生成自己验证，会围着初始假设找补）：假设生成器（打开空间、给优先级，不负责证明）、验证执行器（把假设翻译成"查哪个指标、读哪段日志、拉哪个 diff"，拿证据不偏袒）、证据评估器（verified / falsified / partial / needs_more_evidence / human_required）。几个靠前假设全被证伪是正常工作方式——**初始概率只决定验证顺序，不决定真相**。出现改变因果结构的新事实（"有人远程改过参数"）时，正确动作不是在旧树上微调权重，而是生成一份交接工件（当前症状/已证伪假设/剩余假设/关键新证据/成本/下一步目标）并**重建假设树**。

停机三闸：预算上限、收敛判据（每轮回答"缺口解释了多少、还剩多少"）、反思哨兵（连续两轮证据增量≈0、只换说法无新数据，提前拉停）。失控的病理叫**推理动量**：第二轮不为证伪而为找支持，第三轮在找补上继续推，越自信越偏。停不下来时，正确动作不是再迭代一轮，而是交出"缩小过范围的半成品"：已解释哪些（各对应什么证据）、剩多少、试过并证伪了哪些、卡在哪、建议人先看什么。防漂移靠轨迹不靠记性：每轮记录假设→验证方式→工具与结果→锁定事实；已验证事实成为锁定项，后续假设与之冲突即报警。

## 九、行动护栏：段间契约与三明治

### 9.1 提示链 = 工件 + 闸门

按顺序调用几个 prompt 只是线性串接；真正的工程接口是"工件 + 闸门"。典型事故形态：**格式合法但事实错误的中间结果畅通无阻进入下游**——状态写着"已对账、差额 0"，唯独总额被换成了别的数；下游没算错，它只是忠实地使用了上游的错误。

闸门四层递进，必须在工件进入下游上下文之前执行，未通过不得入链，重新生成的也要再过同一道：**语法**（能否解析）→ **结构**（字段/类型/枚举）→ **语义**（业务不变量：金额非负、借贷平衡、状态迁移合法）→ **事实与来源**（与可信世界一致：数据库版本、签名、来源链）。工件不是临时对话：要有类型、schema 版本、币种与最小单位、来源引用——只回一句"对账完成没问题"，下游就得从自然语言里猜字段、猜单位。链段设计六问：角色、任务（只做一件事）、输入、输出契约、约束、证据；说不清交付物和验收方式，拆开只会增加延迟。

三条纪律：**重试必须带来新的信息**（至少改变一项：带上闸门的结构化失败原因、重读可信源、缩小范围、换模型或换确定性算法、回退到能重建事实的上游段、转人工——原样重跑只是再抽一次样）；**整链要算账**（一次通过率 ≈ 各段通过率连乘，七段各 95% 也只剩约 70%，成本与延迟逐段累加；规则计算、字段转换、事实查询优先交代码）；**防两种反向故障**——信息饥饿（后段只看前段摘要丢了关键证据 → 允许按 step_id 引用全部已成功工件）与上下文污染（把全部历史原文塞进每段 → 完整工件存工件库，链上只传引用）。反面清单也记一下：任务短、输出只给人看、步骤高度耦合无法定义中间契约的，一次调用更好。

### 9.2 护栏三明治：PRE → TOOL → POST

把一次高风险调用做成三阶段协议。**同一规则放在副作用之前还是之后，是两种完全不同的保护**：前置拒绝阻止工具运行；后置拒绝只能阻止结果发布——它撤不回已经发生的事。

![图 2：高风险行动的三明治结构——准入、受控执行、发布校验](../assets/08-护栏三明治-PRE-TOOL-POST.svg)

- **PRE（行动前准入）**：结构校验 → 身份/租户/对象权限 → 金额、频率、风险预算 → 黑名单与账户状态 → 对象版本新鲜度 → 幂等键 → 审批票据与当前参数仍一致。钩子只查一个字段的"点"要压成链，**先跑便宜、确定、最容易发现问题的**（结构 → 本地权限 → 参数阈值 → 对象版本 → 外部名单 → 人工审批 → 真执行）。教训型细节：金额阈值钩子在字段缺失时会放行，所以它前面必须再压一道 schema 检查。钩子自身崩溃默认拒绝（fail closed：判断不了就不能当成通过）；新策略先跑**影子模式**（完整执行但只记录"若生效会拦谁"，崩溃不阻断），拿命中率、误杀率、耗时换上线资格。PRE 里做参数规范化（字符串金额转整数、输入映射成稳定业务 ID）要同步保存"请求参数"与"有效参数"两份——嵌套对象要用深拷贝，否则事故后轨迹里的参数和真正执行的参数不是同一份，证据链断裂。等审批的半小时里余额可能已变：**审批通过 ≠ 现在仍可执行**，放行前必须重查依赖实时状态的那几道守卫。
- **TOOL（行动中约束）**：受控执行器必须是原始工具的**唯一入口**（每次敏感访问都检查、不可绕过、机制小到可验证）。"调用报错"不等于"外部操作失败"——银行已入账但返回超时、邮件已接收但确认前断连。所以执行状态至少五态：`NOT_STARTED / STARTED / SUCCEEDED / FAILED / UNKNOWN`；**UNKNOWN 不得立即重试**，先用同一幂等键去查外部真实结果：确认成功就补记，确认失败才重跑，查不清转人工。
- **POST（行动后校验）**：管住发布，不假装撤销。必须区分 `blocked_pre`（工具没运行）、`blocked_post`（原始结果不再发布，但外部影响可能已发生）、`compensated`（外部系统确认补偿成功）——"已标记需回滚"这个布尔值不会让钱退回来。原始输出与可发布输出分别留存。补偿至少有四步（发现→创建持久补偿任务→调用补偿工具→**确认外部系统已恢复**），四个状态不可混同；即使退款接口返回成功，也应再查支付平台的最终状态。最危险的事故是补偿失败后连补偿记录都被删了——业务仍是已支付，系统却忘了还欠一次退款。补偿必须是带重试预算、死信队列和人工核实的**持久状态机**。

三种绕过方式要背下来：**组合绕行**（读资料、写邮件、发邮件各自合法，把刚读的敏感资料写进外发邮件就越界——要看信息在整条行动链上的流动，在最终出口前拦截/冻结/升级审批）；**契约漂移**（工具升版新增字段，守卫还按旧契约检查——让工具接口、文档、守卫从同一份版本化契约生成，声明支持的 schema 区间，未知版本直接拒）；**补偿幻觉**（见上）。高风险行动的清单也因场景而异，但共性是：资金与退款、不可逆外部提交、账号权限变更、敏感信息外发、删除记录、跨租户数据复用、被多路依赖的单点操作——统一要求"稳定幂等键 + 执行前重读 + 外部回执 + 补偿流程 + 人审门"，并且**按副作用等级而非工具名决定控制强度**。

五层防线最后的嵌套次序：**规划执行选当前步骤 → 提示链生成并核验工件 → 最简工具集算本轮可见能力 → 工具调度做本次准入 → 护栏三明治包住高风险 handler**。任何一层都不能单独承担全部安全保证。

## 十、踩坑清单

1. 把"分析→执行→总结"四步清单当 Plan：没有目标标准、没有约束表、没有检查点，等于没写。
2. Prompt 里留着未定义的形容词，然后抱怨输出不稳定。
3. 硬约束只写进首轮对话，之后不再重申——长上下文里它会被冲走。
4. 只数总步数不数关键路径：并发的步骤被你排成了串行。
5. 把失败点当根因点，Replan 起点选浅了，错误结果被一路复用。
6. 中间结果不带"依赖了谁"，上游切 Invalid 时下游无法级联标脏。
7. 不记录已尝试路径与失败原因，计划在两个烂方案间振荡。
8. "要不要 Replan"和"怎么 Replan"塞进同一次模型调用。
9. 用 `while True` 裸循环，模型自己既当运动员又当裁判，没人给它喊停。
10. Checkpoint 存成聊天记录：能"接着聊"，不能"接着跑"。
11. 外部调用无幂等键、本地无动作账：恢复重放一次，副作用翻倍。
12. 工具描述当说明书写的，没写触发条件和互斥边界——113 个工具时模型只能瞎选。
13. 以为候选集治理靠 Prompt：可见工具数超过模型的注意力预算，这是数学，不是玄学。
14. 校验失败的出路只有"重试"或"抛异常"，没有降级链——最后变成人肉重试。
15. 后置护栏报了错就以为"撤销了"：POST 只能拦发布，撤不回外部世界。
16. 把"模型自评置信度"当放行依据；把三份同源判断当三份独立证据。
17. 复杂任务一把梭单链推理，或简单任务硬塞多路并行——两头都是钱。
18. 超时 = 没执行。这是分布式系统第一课，也是 Agent 事故榜常客。

## 十一、扩展阅读：Codex 是如何实现执行核心的

OpenAI 的 Codex CLI（开源仓库 `openai/codex`，Rust 实现）是一个没有"显式 Plan 对象"的生产级 Agent 执行核心——它把工程功夫全花在了**循环结构、工具分发、预算护栏与事件恢复**上，恰好是本篇观点的反面印证与正面示范。以下基于 main 分支 commit `44b857c`（2026-09-22）阅读整理，路径以 `codex-rs/` 为根。

![图 3：Codex 执行核心——三层循环、工具分发与护栏编排的调用链](../assets/09-Codex执行核心调用链.svg)

### 11.1 三层"任务 / 轮次 / 步"，事件流驱动

核心循环分三层：**任务级** `submission_loop()`（`core/src/session/handlers.rs:411`）消费 `Op` 枚举（`protocol/src/protocol.rs:584`：`TurnInput / Interrupt / ExecApproval / Compact / Shutdown`…）；**轮次级** `RegularTask::run()`（`core/src/tasks/regular.rs:104`）内 `loop { run_turn(...) }`；**步骤级** `run_turn()`（`core/src/session/turn.rs:163`）里的采样循环（`:423`）。三层的上下文各有各的生命周期：`RunningTask`（任务级，带 `CancellationToken`）、`TurnContext`（轮级冻结配置）、`StepContext`（每次采样的不可变快照：环境、MCP、工具路由）。

工具执行是**流水线并行**的：流式响应还没结束，`handle_output_item_done`（`stream_events_utils.rs:300`）就把工具 future 塞进 `in_flight: FuturesOrdered`（`turn.rs:2502`），流结束后按序 `drain` 写回历史；`build_prompt()` 里硬编码 `parallel_tool_calls: true`。对照本篇：这是一个**没有计划对象的 TAO**——"下一步"完全由模型每轮输出决定，但状态被摊进了显式的三层上下文里。

### 11.2 没有步数预算的循环

全仓 grep `max_steps / max_turns`，`core/src` 与 `protocol/src` **零命中**。`TurnState.tool_calls` 只做埋点计数，不参与熔断。那它靠什么收束？三个机制：

1. **token 水位线**：`context_window_token_status()`（`core/src/session/context_window.rs:26`）按三级阈值（压缩线/满窗线/缓冲线）驱动 `run_auto_compact`（`turn.rs:1443`）——**到线先压缩、不中止**，`CompactionReason / CompactionPhase`（`analytics/src/facts.rs:451`）把"为什么压、在哪个阶段压"记成事实。
2. **停止判定可被外部否决**：模型这一轮不再发工具调用即 `needs_follow_up == false`（`turn.rs:563`），但收尾前要过 `run_turn_stop_hooks`——钩子可以注入提示强制续跑（`stop_hook_active`），也可以强制终止。**终止权外置**（本篇 6.1 的 Maker/Checker）在这里以最轻的形态出现。
3. **传输层自愈**：`responses_retry.rs:50` 连接失败指数退避 5s→60s、流重连默认 5 次、超限降级 WS→HTTPS；exec 单命令默认 10 秒超时（`exec.rs:63`）。

另一处硬闸门在扇出：子代理最多 6 线程、最深 1 层（`config/mod.rs:251/261`），超了直接 `AgentLimitReached`——单条链的打转靠上下文预算收敛，**多路扇出必须数数封顶**。

### 11.3 工具分发：注册表 + 暴露面 + 双钩子

`ToolRouter`（`core/src/tools/router.rs:74`）把三件事拆开：`ToolSpec`（模型可见 schema，`tools/src/tool_spec.rs:22`）、`model_visible_specs`（本轮暴露集）、`CoreToolRuntime`（执行体，`core/src/tools/registry.rs:56`）。`ToolExposure` 枚举（`tools/src/tool_executor.rs:51`）是正交第四个维度：`Direct / Deferred / Hidden…`——开启 `search_tool` 时，直给工具整体换成"先 tool_search 再暴露"，**正是本篇 7.3 "系统有多少工具 ≠ 本轮看见多少工具"的产品级实现**。

分发链：`build_tool_call`（`router.rs:244`）→ `ToolCallRuntime::handle_tool_call`（`parallel.rs:76`）→ 并行闸门（`supports_parallel_tool_calls` 的取读锁并发，否则写锁串行，`parallel.rs:191`；MCP 仅 `read_only_hint` 可并发）→ `ToolRegistry::dispatch_any_with_state`（`registry.rs:516`）：计数 → 未注册工具返回 `RespondToModel("unsupported call")`（**把模型输出当不可信输入、但给它一次改正机会**——不 panic，降级成一条工具输出写回历史）→ pre hooks（可 Block、可改写参数）→ handler → post hooks（可否决结果、可注入反馈）。

### 11.4 护栏编排器：审批 → 沙箱 → 尝试 → 升级重试

`ToolOrchestrator::run()`（`core/src/tools/orchestrator.rs:122`）的文件头注释就是流程本身。审批策略 `AskForApproval`（`protocol/src/protocol.rs:969`，默认 `OnRequest`，另有 `UnlessTrusted / Granular / Never`）；命中 Starlark 规则引擎 `execpolicy`（`Decision = Allow / Prompt / Forbidden`，`execpolicy/src/decision.rs:9`）时按三态直接放行/转审批/禁止。沙箱 `SandboxPolicy`（`protocol/src/protocol.rs:1055`）按平台落地（macOS Seatbelt / Linux seccomp+bwrap+landlock / Windows RestrictedToken，`sandboxing/src/manager.rs:48`），默认 `ReadOnly`。第一次尝试失败且属沙箱拒绝时，**带着"要不要免沙箱重试"的审批请求再来一轮**（`proposed_execpolicy_amendment` 可把这次批准沉淀为永久规则）。风险判断三源合流：静态危险命令词法表（`shell-command/src/command_safety/is_dangerous_command.rs`）+ 规则引擎 + 可选的 Guardian 子代理评审（`guardian/`，产出 `SecurityRiskScore` 并落盘）——与本篇"廉价规则先兜、拿不准才问人/问模型"的级联同构。

### 11.5 rollout：事件溯源的上下文与恢复

执行历史不是聊天记录而是 `RolloutItem` 事件流（`history/src/lib.rs:170`：`ResponseItem / EventMsg / Compacted / TokenUsageRecord / WorldState / SecurityRiskScore…`），JSONL 追加写进 `~/.codex/sessions/YYYY/MM/DD/`（`rollout/src/recorder.rs:1723`）。恢复走 `resume_thread_from_rollout` → `RolloutReconstruction`（`session/rollout_reconstruction.rs:12`）：重建模型历史、保留上下文、Guardian 检查点、上一轮设置与世界状态基线。两条工程细节值得抄：**每个终态事件（TurnComplete/TurnAborted）发出前先 `flush_rollout`**——注释写明客户端可能同步回读；崩溃的 daemon 场景有 `Op::RecoverTurn`（`protocol.rs:619`）把"已记录输入的单环境任务"捕获重放。

### 11.6 对照小结

| 本篇观点 | Codex 的实现证据 |
| --- | --- |
| Plan 可以是展示层产物而非控制契约 | 无计划对象参与调度；`update_plan` 只是展示工具（`tools/handlers/plan.rs`），Plan 模式仅切换提示词与交互能力 |
| 循环要有显式状态与可审计终止 | 三层上下文 + stop hooks + 事件溯源 |
| 预算优先于计数器 | 无步数闸门；token 水位线到线压缩优先于失败 |
| 候选集是架构问题 | ToolExposure + tool_search 的"先搜后露" |
| 提议-准入分离 | 注册表 + 双钩子 + Orchestrator 四段式 |
| UNKNOWN 不能盲目重试 | 审批可回写 execpolicy 规则，把一次例外沉淀为结构 |
| 扇出必须硬封顶 | agent_max_threads=6、agent_max_depth=1 |
| 恢复 = 重放事件而非回填消息 | RolloutItem / RolloutReconstruction |

它没做的同样有信息量：没有显式 DAG 与检查点级重跑（失败恢复粒度是"轮"而非"步"）、没有幂等账本（写副作用依赖沙箱与审批而非业务幂等键）。这两块空白，正是"编码类 Agent"（动作大多可在 git 工作区里重做）与"业务交易类 Agent"（出款不可重做）在架构上的分野。

## 总结

回到开头的问题，现在都有答案了：

- **第 10 步发现第 3 步错了**：区分失败点与根因点，沿依赖反向标脏，回到最近可信检查点做最小 Replan——前提是计划本来就是数据结构（三、四节）。
- **847 圈烧穿账单**：硬预算四件套 + 动作指纹检测 + 终止权外置。循环的收束不靠模型自觉，靠水位线与验证器（五、六节）。
- **113 个工具选错**：候选集治理是架构问题，L1/L2/L3 分层 + 描述工程 + 五段定位法逐层归因（七节）。
- **谎报完成**：模型只是提议者；完成要过硬证据。Codex 甚至把"停止"做成了可被钩子否决的评审点（十一节）。
- **崩了接着跑**：事件日志 + 快照 + 双账本，恢复是重放，不是回填（六节）。

一句话收束本篇的立场：**模型是引擎，循环才是整车。把"边想边做"翻译成状态、事件、闸门与账本，Agent 才从 demo 变成服务。**

## 思考题

1. 你手头最近一个 Agent 任务，如果按 G4C 检查它的计划：成功标准写了没有？约束有没有每轮重申？检查点密度是多少？缺哪一项最先出事？
2. 一条 12 步的链，每步准确率 97%。写出你的两个改进方案：一个把单步提到 99%，一个把关键路径压到 5 步。分别要花什么、能赚多少？
3. 给"用户中途追加一条只对当前子任务生效的约束"设计存储：它放在哪个状态里、每轮怎么注入、什么时候销毁？（对照 6.2 与 01 篇的约束表）
4. Codex 不做步数熔断、只靠 token 水位线收束。如果你的 Agent 跑的是按调用计费的第三方工具，这个取舍还成立吗？你需要补哪一道闸门？
