# 检索与 RAG：概率系统里的最小充分检索

很多人讲检索，开口就是"切块 + Embedding + 向量库 + Top-K + BM25 + Reranker"。这套词能证明你看过教程，证明不了你做过系统——因为生产里的检索问题，没有一个是这些词能回答的：

- 评审会上定死的"禁止使用 ORM"写进了向量库，六周后 Agent 照样导入了 ORM——它没删你的规则，只是**没看见**。
- ChunkSize 设 500 还是 800？你说"网上经验"，那 300 和 1500 为什么不行？
- 召回率涨了 5 个点，答案准确率反而掉了——钱花在哪了？
- 用户问"这台电脑适不适合写代码，适合的话哪买便宜"，你的系统把两件事的证据一次全查了——后半截查询可能根本不该发生。
- 线上反馈"检索正确率 92%"，用户却在点踩——到底哪个指标在撒谎？

这一篇把检索当成一条**知识供应链**来讲：写入侧要有批次和凭证，读取侧要分确定域和概率域，整条链路要在"最小充分"的目标下花预算。

---

## 一、完整链路：一条供应链，不是一次搜索调用

先把地图铺开。写入侧七步：**采集 → 解析 → 清洗 → 分片 → 补元数据 → 向量化/建索引 → 入库校验**；读取侧八步：**召回 → 过滤 → 合并去重 → 融合排序 → 业务规则调整 → 充分性判断 → 上下文组织 → 生成**。

三个容易被跳过的环节：

- **解析是单行道**。解析出错，后面的切割与检索几乎无法补救——条款、表格、代码注释被硬切开之后，模型看不出这段属于哪一章、哪一版、哪一条。OCR 的边界也要清醒：它只把字认出来，没有"读懂图"——流程图节点、箭头指向、统计图趋势，必须靠视觉模型输出结构化描述才可检索。某文档处理厂商干脆把定位从"RAG 框架"改口为"面向智能体的文档处理引擎"，就是把解析层点名为下游幻觉与断引用的源头。
- **入库校验是常被省略的最后一步**，四查：文档解析是否完整、Chunk 是否异常、向量是否全部生成成功、索引是否可查。
- **metadata 是必需品不是选配**。只存 `doc_id + text` 叫"太薄"——企业检索真正要用的是：生效日期、产品版本、地区、权限域、源负责人、文档状态。配套的三件数据结构值得照抄思路：
  - **源文档登记表**：`doc_id / source_uri / owner / permission_scope / effective_from / effective_to / source_hash / status`——知识源先于知识被管理；
  - **Chunk 记录**：`chunk_id / doc_id / index_version / chunk_hash / text / context（补写的语境）/ page / section / 生效期 / tenant_id / permission_scope`；`chunk_id` 用 `hash(doc_id + parser_version + chunker_version + chunk_index + text_hash)` 稳定生成，切块可复现、文档未变可跳过重处理；
  - **IndexManifest（索引清单）**：corpus 版本、解析器版本、切块器版本、embedding 模型与维度、构建时间、chunk 数、`golden_set_passed`——**没过回归的索引不许切线上**，别名蓝绿切换、随时回滚。

### 1.1 玩具与生产的分界线

拿五条判据量一下自己的系统：

1. 写入侧是不是被当软件资产管理（可发布、可灰度、可回滚、可审计、可版本化），还是只有读取侧"喂几段相似文本"；
2. 能否从一段答案反查到"**哪一版索引里的哪个 chunk、第几页哪一条**"；
3. 机械真值（id、批次、金额、单号）是确定性绑定的，还是让模型从召回文本里"读"出来的——后者是执行型 Agent 最高频的事故源；
4. 管不管**下线**：废止规则、过期口径、权限收紧的材料还躺在索引里答题，是"新文档没生效"类事故的经典根子；
5. 有没有评估闭环——没有的话，项目再复杂也会被看成玩具。

落地次序也有讲究：**先治理，后调参**。真实问题清单 + 正确证据表 → 知识源补 owner/版本/生效期/权限 → 定义 chunk schema、citation schema、index manifest → 建候选索引用 golden questions 回归 → 别名切换上线 → 接引用与 RetrievalTrace → 这之后才谈 Agentic RAG。上线前自查：抽 50 条真实问题，人工看它们对应的原始材料入库后的形态——解析对不对、表格行列关系留没留、chunk 能否追到页码条款号。这些问题答不上来，就还没到调 Top-K 的阶段。

## 二、Query Planning：先知道缺什么，再去查

### 2.1 要不要查、查什么

两个层次：设计期由开发者定"这一步要不要查"（可以和产品、甲方对齐）；运行期由 Agent 判"当前信息够不够"。总纲一句话：**让 Agent 缺什么就去查什么**——难点随之变成"怎么知道自己缺什么"。四步模板：

```text
1. 明确当前要做的判断（查询是手段，服务于某个判断或动作）
2. 推导该判断需要的证据（把"符合生产要求"细化成可查的点）
3. 区分已知与未知（已知的不再查）
4. 判断这个缺口是否值得查 —— 缺了不一定查：
   资源紧张、即将超时时可以不查，不查本身是一种降级
```

前提是目标已被识别（意图与 Goal Context 就绪）——直接拿用户原话检索，连代词都没消解，几乎不会有有效结果。

### 2.2 改写十二条

Query Rewrite 改的是表达，不改事实。可直接落进 Prompt 的规则表：

保留硬约束（预算上限、排除品牌、只能查当前租户）；提取软偏好（"稳定一点"翻译成可查可比的指标）；消除歧义（多义词、缩写、黑话、同名实体）；统一术语（口语换成数据源里的标准字段与关键词）；删除无关（情绪、寒暄、重复）；**从"复述问题"转向"描述信息缺口"**（不问"这个框架怎么样"，改查稳定性、恢复能力、生产案例）；补过滤条件（租户/项目/环境/时间范围）；**禁止擅自补事实**——可以补已确认的信息，不能为让 Query 显得完整而塞进没证据的实体、时间、结论；检查可执行性（索引存在吗、字段支持吗、权限够吗）；控制粒度（一次查询围绕一个明确缺口）；设置停止条件（只对迭代式有意义）；与输入规范化共用消解与量化基本功。

防 Query Drift 的核心就是"禁止擅自补事实"这一条：改写只做**补齐已确认信息**，不做**美化到看起来完整**。另一条硬红线来自反馈侧：用户明示的否定条件与硬约束必须贯穿召回、排序与输出，不允许被软偏好覆盖。

原始 Query 与改写 Query **并存而非替换**：改写不可逆，可能吃掉一个只共享某个强语义信号的表达；原句作为独立一路进候选池，与改写路一起做统一结构、去重与融合。

**HyDE**（假想文档）是补表达差的招：真实文档以陈述句写答案，用户以疑问句提问，两者向量上隔着表达层——先让模型生成一份"假想答案文档"，拿它去召回真实文档。注意两点：假想文档**不是证据**，只能用来定位相近材料；生成时避免写具体数字、版本号、确定性事实，防止虚构细节反过来污染召回。适用场景就两个：输入含糊信息量太少；用户表达与库存文本差异明显。

### 2.3 拆解、路由与查询空间

复杂问题怎么拆？5W1H 是现成的候选池（不是必须填满的表格）：What=对象与状态、Who=涉及主体、When=时间线、Where=卡在哪个系统/环节、Why=原因、How=执行到哪、各系统返回了什么。拆完顺手做第二件事：**建立子问题 ↔ 数据源的映射**（单号查订单系统、状态查退款记录、失败码查错误码文档、调用过程查日志与 Trace）。替代方法论：MECE、因果链（故障定位）、时间线（订单/审批）、实体关系（复杂关联），备一两套即可。

路由判据：某种信息只能由特定来源提供时，**用规则直接绑定，别让模型在几十个源里自由猜**；只有"这条信息可能存在于多处"时，才值得动态选路。

进阶认知：**可查询空间不是固定的，是随执行变化的**。查到渠道处理成功后，下一轮空间从退款域扩到支付域；看到银行错误码，就要把错误码文档、账户规则加进来；Agent 自己产出的可信中间产物（已确认事实、检查点结果、失败原因）也应回流进可查询空间。所以准确的表述不是"我有三个知识库"，而是"**我会按目标、已有证据与最新观察，动态收缩/扩展/切换查询空间**"。

索引多到放不下时，用"先检索索引、再检索数据"：第一趟查的是 **Index Profile**（索引名、适合解决什么、不适合解决什么、关键字段、查询方式、时效性、权威性、所需权限、更新频率），召回方式与内容检索同构（关键字/向量/标签/按域分区）。候选索引数还能动态编排：窗口大给 10-15 个，窗口紧给 3-5 个。

Query Set 内部要**制造差异**：下一轮不得复读上一轮；五个方向——加新实体关键词、加结构化条件、用上第一轮冒出的新术语、查能验证当前假设的证据、**主动查与当前结论相反的证据**防过早确认。去重发生在三处：候选合并、相似 Query 归并、高度重合的召回不全都进精排（相邻 chunk 可直接拼块，省掉 Overlap 重复）。

## 三、入库与 Chunk：边界画在语义断点上

### 3.1 三种切法

| 切法 | 优点 | 代价 |
| --- | --- | --- |
| 长度（+Overlap） | 稳定、易控、便宜 | 不懂内容，会把"定义+条件+案例"劈断；Overlap 缓解断裂但引入重复 |
| 语义（相似度阈值断开） | 块内主题集中 | 成本高、阈值不可移植；"语义相近"≠"业务上该收在一起" |
| 结构（标题/章节/列表/表格） | 保留逻辑关系，作者最推荐 | 吃解析质量——PDF 解析后层级经常丢 |

可背的混合范式：**结构定大边界、语义判内部边界、长度做最后兜底**。"语义切一定更好吗"——不一定：阈值不可移植、成本不可控、业务边界与语义边界经常错位；有结构可依时优先结构。收束原则一句：**不要按外观切，按它所表达的完整知识单元切。**

### 3.2 ChunkSize 的三步定法

报出 500/800/1000 这类裸数字的人，会被一句"为什么不是 300 或 1500"问穿。正确流程：

1. **统计业务里的"最小完整知识单元"有多长**：制度里"适用条件+处理规则+例外"不可拆；API 文档里方法说明、参数、返回值最好同块——初值从业务知识来，不从网上来；
2. **对齐用户问题粒度**：常问具体参数/错误码 → 偏小；常要方案解释/章节总结 → 偏大或上父子文档；
3. **测试集调参**：候选 256/512/800/1200，固定同一 Embedding、同一 Top-K、同一 Rerank 做对照；看"正确证据是否被召回、证据是否完整、重复多少、最终答案对不对、平均耗多少 token"，**不是看向量相似度数值**。

联动关系：块越小越需要更大 Top-K，块越大 Top-K 应降；ChunkSize 与 Overlap、Top-K、父子文档、窗口预算是一组参数——**选"多目标最均衡的一组"，不选"单指标最高的一组"**。

### 3.3 难切的三样：表格、图片、长列表

- **表格**：小表整表一块（带表名表头单位说明）；长表"表头+单行"键值化——不能只存"手机 A、3999、有货"，要写成"产品：手机 A；价格：3999；库存：有货"，让行脱离表格仍有完整含义；再不行表头+N 行一块、按业务实体切；跨页表格每块重复携带表头。**要聚合/筛选/排序的大表根本不该进向量库**——落结构化库用 SQL 或专用工具查。给检索用的还有一招：让模型对表格生成一份自然语言"解读"独立成块，命中解读后再回召原始表格。
- **图片**：图题图注附近正文绑成一块（图只是补充时）；视觉模型输出结构化描述供检索（流程节点、上下游、指标结论）；进阶是**原图与描述都存，文本负责召回，命中后把原图交给多模态模型当原始证据**；或原位留占位符+URL，展示时替换。

三类难切内容背后是同一个更大的命题：**异构来源分路入库，命中后统一成证据再进模型**。日志带时间与级别，归时序/关键词索引——向量检索在日志上最没用；表格与指标归结构化库，检索是查询不是相似度；PDF、网页才走 chunk+向量路。最终交给模型的是一张张统一格式的证据卡（来源、类型、时间、版本、定位符），模型负责的是**跨模态对齐**——把日志行的时间戳、表格里的行、PDF 里的条款对上同一条因果链。别把所有模态硬压进一个向量库："日志、SQL、PDF 一起进 Agent"的正确画面是多路检索加统一证据协议，不是一种 embedding 包打天下。
- **长列表**：按项分组但**每块重复携带标题**（单召回一项时模型才知道它在解决什么）；按语义分类聚合再切；建父子（整表为父、单项为子）；每项都超长就每项一块。

两个通用增强：**Contextual Retrieval**——每个 chunk 前补一段短上下文再进 embedding 与 BM25，公开数据示例里 top-20 检索失败率 5.7% → 1.9%（语境化+重排，相对降约 2/3）；适合强章节结构（条款/合同/法规）、上下文依赖强的 PDF、版本敏感的制度——但短而自包含的材料（产品卡片、单条 FAQ）收益有限，还会增加预处理成本与索引体积，**先抽真实查询做 A/B，不要全量改造**。另一手 **late chunking**：长上下文模型先整篇嵌入、pooling 前才切块，块天生带跨段语义，文档越长增益越大。

## 四、父子文档与层次检索

经典矛盾：块小召回准但只剩结论、丢了前提；块大信息全但噪声多还吃窗口。父子文档的六步机制：原文切大父块 → 父块切小子块 → **只对子块建向量** → 查询召回子块 → 顺 `parent_id` 找父块 → 注入父块给模型读。判据一句话：**子块解决"找得准"，父块解决"看得全"**——让最细的粒度去撞问题，让最合适的粒度去喂模型。

三项代价要讲出来才诚实：父块仍可能过大（命中一句灌进整章）；**父块重复**（Top-K 里五个子块指向同一父节点时必须对父去重，不是注入五次）；粒度问题没被消灭，只是从一个变成两个——层次结构没有消灭取舍，它只是把一次取舍换成了两次。

### 4.1 父块打分：名次聚合与偏差控制

错误做法是让父块直接继承最高分子块的分数——丢掉了"同一父块多个子块都相关"这个强信号。正确做法借倒数排名融合：`父块分 = Σ 1/(k + rank(子块))`。数值感受一下：甲父块命中第 2 和第 6 位两个子块，得分 ≈ 1/3 + 1/7；乙父块只命中第 1 位，得分 1/2——甲更靠前。防"父块越大越占便宜"的三件套：每个父块最多取排名最高的 3 个子块求和、后续子块加衰减、再叠加父块自身相关分、长度惩罚与重复惩罚。

### 4.2 两层不够就分层，关键是"按问题选粒度"

真实文档是多层的：手册=文档/章节/小节/段落/代码片段/配置项；制度=制度/模块/规则/适用条件/例外。节点存：正文、**摘要**、标题路径、向量、父指针、子指针、相邻节点——标题路径让一句孤立事实也能自报家门（属于售后/退款/无理由退换）。每层同时存原文与摘要，同一知识就有多个粒度表达：问得宽召高层摘要，问得细召底层事实，要解释再从事实向上补。注意**物理结构 ≠ 逻辑结构**：目录树属于写作的人，检索层次属于提问的人——可以保留原章节，另建一套面向检索的逻辑层次。

召回哪一层？映射表：事实/参数型 → 段落级；解释/原因型 → 小节级；总结/概览型 → 章节或文档级摘要；对比/综合型 → 多层并行。判层可以用规则也可以让模型判（出现"整体介绍/总结一下"偏高层，出现具体参数名/错误码偏低层）。三种策略：**始终底层起手**（简单稳定，但总结型问题用事实块拼概括很吃力）；**先小后大逐步上扩**（召底层→判充分→不够找父节点→再不够继续上→信息充分或触预算即停——按需扩展，代价是每轮判充分要调模型）；**多层并行召回统一重排**（适合复杂问题，成本最高）。实践折中：默认底层起手，按问题类型、充分性与剩余窗口决定是否上扩；明显总结型直接高层起手。决定层次的六个信号：问题粒度、当前证据够不够、要事实还是要背景、剩余窗口、允许的延迟与成本、任务处于查询/解释/总结/验证哪个阶段。

## 五、混合检索、融合与迭代

### 5.1 为什么单路必漏

向量找"意思相近"，不等于含答案——错误码、商品型号、接口名、版本号这类要求逐字命中的内容它不稳；关键字检索（BM25，经典的关键词相关性打分算法，倒排索引的标配排序）精确但换个说法就漏——文档写"退款"、用户说"原路返回"，字面零重合；图检索吃实体关系与多跳，但图谱构建维护贵，不是标配。分工一句：**向量吃语义、关键字吃精确、图吃关系**——任何单一检索器都在用自己的方式理解"相关"，所以任何单一检索器都会漏。多路（策略并行）与多源（数据源并行）在工程上是一件事：把不同通道的候选合并成一张列表。各路 Top-K 不必一致：向量噪声多可多召回，关键字命中集中可少召回，**别为了整齐给每路相同配额**。

### 5.2 融合链路与 RRF

标准顺序：并行召回 → **硬过滤**（权限、租户、时间、用户明示约束——它们决定"能不能留"，排序只决定"留下来谁在前"；用"分数置 0"冒充沉底是反范式，不如直接删）→ 合并去重 → 融合排序 → 业务规则调整（官方文档优先于论坛、当前版本优先历史、实时库优先旧摘要、用户确认事实优先）。

融合为什么用 RRF（Reciprocal Rank Fusion，倒数排名融合）：不同系统的分数像不同货币——向量 0.82、BM25 13.6、图可能只有名次，强行归一到 [0,1] 仍有语义陷阱（两个平台上的 8.0 不是同一个 8.0）。**名次才是硬通货**：`Σ 1/(k + rank)` 只吃名次；k 越大头腰差距越平、k 越小越强调头部。权重有两层含义：控制该路召回数量；控制该路在排序中的影响力（Weighted RRF）；权重本身可以是动态量，随当前步骤与剩余窗口调整。

### 5.3 迭代式检索：两条刹车

进入判据：复杂/多证据/根因型问题。根本原因是**第一次检索前你对问题的理解本就不完整**，只有看到第一批结果才知道还缺什么。第一轮的目标通常不是找全答案，而是拿到：涉及哪些实体、可能的原因方向、已确认的事实、还缺哪些关键信息。

每轮结束先判充分性（六问）：问题各部分都有证据了吗 / 当前结果能直接支撑结论吗 / 是不是只有结论没有原始数据 / 证据间冲突吗 / 缺时间、版本、对象限定吗 / **继续查还能拿到有效信息吗**。判定用结构化输出：`sufficient + known_facts[] + missing_evidence[]`——`missing_evidence` 就是下一轮的输入。每轮合并处理六件事：去重、相似降权、新旧版本冲突、跨源可信度、新结果是否真补缺口、目前覆盖了哪些证据。由此推出排序的动态性：一条内容的价值不在它有多相关，而在它**相对已拿到的那些有多新**。

退出条件分四类同时设：**效果类**（证据足以回答 / 最小回答原则先给最简答案再引导追问）；**边际类**（连续两轮没有新增有效证据——用新增证据数判定，一轮只多一两条就别再查）；**资源类**（查完可用源 / 最大轮数 / 时间、token、调用预算）；**澄清类**（缺口无法靠检索获得，只能问用户）。落地写法：最多 3 轮，但第 2 轮已充分就提前结束。防跑偏的锚：用"待确认事实清单"当 Anchor，每轮检查填了哪些槽——轮数不是目标，**持续拿到有效新信息才是目标**；循环的进度条是新增证据数，不是轮数。

与 Agentic RAG 的关系：迭代式检索是一种具体机制（没查够就继续查）；Agentic RAG 是系统形态（还决定要不要查、查哪个源、调什么工具、怎么验证证据、何时停）——迭代只是其中一个部件。拓扑视角：朴素 RAG 是"记忆×链式"的一次性流水线，加了"检索→评估→改写→再检索"回路后落在"记忆×循环"，CRAG / Self-RAG 是这条回路的两个实例。工程建议要诚实：**一般 Agent 项目不建议默认上迭代式检索**——只有检索本身就是项目卖点时才值得；讲方案时重点也不是"我们查三次"，而是整套退出与循环机制。

## 六、分路召回：红线不是"不够相关"，是"没轮到它出场"

先看一起事故的全部细节。某团队评审会上定死铁律"禁止使用 ORM，所有数据库操作必须写原生 SQL"，特意整理成一条记忆写入向量库，描述清晰。六周后，用户让 Agent"给报表模块写一个数据库访问层"——它照样导入了 ORM。翻召回日志：用户画像 0.71、库表结构 0.63 命中（阈值 0.45），**那条禁令相似度 0.38，被挡在门外**。系统无报错、无犹豫——对 Agent 来说，用不用 ORM 都是"写数据库代码"。归因一句话：**保命红线是被概率静默淹没的，不是被谁删掉的。**

![图 1：分路召回——写入四分类、读取四阶段、串行按优先级填预算](../assets/12-分路召回四阶段管线.svg)

0.38 不奇怪：embedding 把一句话编码成高维向量，里面是词语义信号的叠加。禁令的核心信号是"禁止"和"ORM"（专名，与"数据库/SQL/映射"间接共现）；任务描述的核心信号是报表、模块、写、访问、层——两句真正共享的强信号只有"数据库"，其余彼此正交，分数自然停在不高不低。**向量模型像一个只盯关键词的实习生**，翻了翻笔记觉得"大概相关吧，但没到必须提醒的程度"；而人类工程师会立刻意识到这个动作**触发**了那条禁令——人懂因果，懂规则会被哪个动作命中。

调阈值救不了：调高到 0.6，0.38 的约束进不来、0.5 的偏好也进不来；调低到 0.3，连接池配置、备份策略一起涌进来。阈值没有理论最优，跨领域跨模型还不可迁移。死结在于：**"该不该在场"这个问题，相似度这把尺子根本量不了**——约束类内容的召回是在场性问题，不是相似度问题。

### 6.1 两道防线：写入分类，读取分路

**写入侧**：`MemoryClassifier` 用轻量模型 + temperature=0 在写入瞬间四分类打标（别用正则匹配"禁止/必须"——既不懂语义也跨不了语言）：

| 类型 | 特征 | 处置 |
| --- | --- | --- |
| CONSTRAINT 约束 | 否定句为主，语义与任务正交 | `force_recall=true` + `trigger_conditions` |
| FACT 事实 | 当前状态，会被新事实覆写 | 稳定 `entity_id` 做 upsert |
| PREFERENCE 偏好 | 软性指导 | 不设 TTL |
| EPISODIC 情节 | 历史事件 | 只追加，带 `ttl_days` 衰减 |

**读取侧**四阶段管线：**S1 规则硬召回**（约束必须在场，完全不算余弦、不卡阈值——触发条件匹配就无条件进上下文，这是整条架构的灵魂）→ **S2 精确召回**（API 名、表名、错误码必须命中）→ **S3 向量语义 + 重排**（偏好/情节）→ **S4 实体图谱**（状态类返回最新值）。查询并行、合并串行：四通道同时发起，合并时严格按优先级逐阶段填 token 预算——**约束先抢窗口，剩下的才轮到偏好与细节**。

两个"但是"防止矫枉过正：无条件进入 ≠ 无脑全塞——约束带触发条件（`domain=database`），写前端时不该占数据库约束的预算；约束也要设帽（**不超过预算的 40%**）——几十条同域约束能把预算占满，Agent 只剩规矩没有事实照样干不好活。"宁可多占点 token"不等于"独占全部 token"。

### 6.2 边界与归责

哪些内容不该只靠向量：安全红线、组织规范、合规禁令（确定域）；产品代码、合同编号、错误码、条款号（精确匹配域）；批次状态、审批结果、本月数值（结构化状态，优先查业务系统）。事实、偏好、情节这类"大概相关就够"的软信息才归概率域。**把确定域扔进概率筛子，像用尺子量温度。**

一个必须讲清的边界：**硬召回只保证规则被看见，不保证模型一定遵守**。预算、起送量这类不可突破的业务边界，还要在工具层加确定性校验，并把高副作用动作标记为低可逆、强制幂等、执行前等人审——记忆负责让规则进入决策上下文，工具校验与人审负责阻止不可接受的动作真正发生。

还有一个已知的新失效点值得当思考题留给你：规则路依赖 `domain` 参数，而 domain 常由召回前一次 LLM 抽取——若把"给报表模块写数据库访问层"判成"报表"而非 database，database 触发条件的约束全部跳过，第一道防线形同虚设。需要设计"抽错也不至于全废"的兜底：多值宽口径注入、按动作类型而非名词触发、约束漏注入计入审计。

顺带一个反直觉数据提醒别迷信向量基建：某长对话记忆基准上，简单文件系统方案 74.0%，复杂向量记忆方案 66.9%——窗口动辄二十万 token、条目少于约 200 条时，把结构化文件直接塞进上下文让模型自己读，反而比向量截断更准（LLM 能理解"禁 ORM"与"数据库操作"的逻辑相关，向量库不能）。**先用最简方案，规模撞墙再上复杂基建。**

## 七、性能与成本：最小充分检索

### 7.1 端到端视角

检索性能不等于"查询引擎多少毫秒"。用户感知的是"我问完多久拿到靠谱答案"，要看全链路：改写 500ms + Embedding 100ms + ES 200ms + 向量 300ms + Rerank 600ms + 充分性判断 500ms——把向量从 300ms 优化到 150ms，对整体帮助远小于直觉；迭代式还是放大器，一轮不够整条链路翻倍。指标上盯**分位数与长尾**（均值 800ms 好看，P99 可能 3s；用户"记打不记吃"）；盯**木桶**（五个数据源四个 300ms、一个偶发 5s，傻等全部完成就被最慢的拖死——单源超时+部分结果可用）；盯**吞吐**（LLM Rerank 单看不慢，并发一上来就是瓶颈）；盯**单位答案成本**。

一条红线：**性能不能脱离准确率**。Top-K 从 50 砍到 3、删改写、跳 Rerank 换来 3s→500ms，那叫功能缩水不叫优化。用"带预算的指标"表达权衡：1 秒内 Recall@10 多少；2 秒预算下任务成功率多少；准确率降不超 1% 时延迟能降多少；同准确率下调用次数能否减半。

基础优化先做完再谈高级：索引与 Mapping 按实际查询条件设计；高频过滤条件（租户/权限/时间/类型）提前建索引——**能先把一百万缩到一万，就别拿一百万做向量检索**；Query 别又宽又贵；相似 Query 合并；同一 Query 同任务内不重复 Embedding；Top100 只用 Top10 就别召回 100。离线化原则：**在线延迟最好的解药，多半写在离线任务清单里**——切割、embedding、关键词、实体、标签、摘要全部入库期算好。

### 7.2 最小充分检索

主线思想：**不要试图一次解决用户提出的所有事；找出当前最小的、可独立完成的目标，只检索解决它所需的信息**。"最小"= 这个目标已经拆不动了；"充分"= 它虽小，做完能独立给用户产生价值——两者一体两面。自检句：如果我只完成这一件事，现在能不能给用户一个有意义的结果？

正例：用户"看看这台电脑适不适合写代码，适合的话哪买便宜"——第一个最小目标是"判断适不适合"，只查配置、需求、评价；若结论是不适合，后面的价格、优惠券、库存**一次都不用查**。反例（判据的另一半）："查上个月订单，然后算退款率"——"查订单"不是最小目标，它是中间步骤，查完就返回没有解决任何问题：**不要把过程步骤误认为用户目标**。

适用：探索式、多步骤、弱依赖任务（推荐、旅行规划、简历优化、数据分析）。不适用三类：拆不出独立目标的（用三年财报判断是否值得投资）；用户明确要求一次性交付的（"完整竞品分析报告"，每模块问"要不要继续"反而毁体验）；强依赖的（合同审查、故障根因——缺关键部分结论就变）。两个收益：**性能好**（很多后续检索根本没发生——最快的查询是没发生的查询）+ **交互好**（用户更早拿到第一批结果，还能据此改需求）。注意它不是"少查一点"，而是**缩小当前要解决的问题范围**；也是资源吃紧时的降级路径——即将超时且已能回答首要问题时，立刻中断迭代返回。

### 7.3 动态预算与缓存

Retrieval Budget 覆盖几个核心维度即可：剩余时间、最大轮次、最大 Query 数、最大数据源数、最大召回/Rerank 数、剩余 token。**升级阶梯**：简单问题单路直查 → 复杂点加混合与 Rerank → 第一轮不够才触发改写与迭代；**降级动作**：预算吃紧时减 Query、降 Top-K、砍数据源、跳过 LLM Rerank，用当前最好的结果完成回答。不预设固定策略，按当前状态决定下一步——先走最便宜的路，不够再逐级升，持续检查剩余预算。

缓存三层：**结果缓存**（同 Query+同过滤条件短时复用，跳过召回与 Rerank——注意先用改写结果查缓存，因为原话方差太大；key 用"改写后查询的向量"而不是改写文本，文本仍有"解决方案/解决思路"级抖动；命中回写、设过期）；**答案缓存**（FAQ/制度/产品说明这类稳定题，命中连生成一起省——但问题一旦依赖实时数据、画像、权限、上下文就容易返回过期错误答案：**优先缓存检索结果，谨慎缓存最终答案**）；**复用入库期派生结果**（第三层最便宜：全部离线预计算，在线只取用）。总纲：**能不查就不查，能少查就少查，能复用就复用；不够再逐步扩大范围。**

## 八、评估与反馈闭环

### 8.1 检索侧指标

Recall@K（有没有漏，最重要之一）、Precision@K（噪声水平）、Hit Rate@K（前 K 有一个正确即中）、MRR（第一个正确结果排哪）、NDCG（分级相关性×位置）、**证据覆盖率**（复杂问题必需证据被召回的比例）、**重复率**（Top-K 高相似占比，防窗口被同类内容占满）。

一个可加的自定义亮点——**检索结果编辑距离**：把标准结果当目标列表，算最少几步操作变成理想（插入=漏召回、删除=噪声、替换=部分相关、移动=名次不对、合并=重复块只供一份证据），各操作按业务定成本（缺必需证据 3、误导模型的错误结果更高、移动一位 1）——**缺文档比顺序不对更严重，所以成本不能全设一样**；医疗金融加重错误证据惩罚，复杂问答加重缺证据惩罚。局限：一题可能有多组合理答案，要标注多组可接受结果。它是 Recall/MRR/NDCG 的补充，不是唯一指标。

### 8.2 测试集与线上信号

离线样本最小字段：用户问题、标准相关文档、标准 chunk、相关性等级；不同版本链路定期跑对比。线上没有标准答案，采间接信号：无结果率、追加检索率、重新提问率、引用采用率、用户纠错率、人工抽检通过率。**别看整体平均值**——最朴素的系统也不会难看得离谱，想进一步必须挖长尾失败案例。评测手段分工组合：测试集管稳定回归、LLM as Judge 管语义化评估（它的"便宜"有三个前提：批量接口、低峰调用、用 mini 级模型）、专家管校准（不全量审，让专家写评审规则+抽样审核+校准 Judge）、用户反馈与 A/B 管真实收益验证；Pairwise（两个结果问哪个更好）比"给 83 分还是 87 分"可靠得多。

### 8.3 指标涨了体验崩了

任何单一指标都能骗人：平均轮数 3 升 5，可能是用户愿意聊，也可能是三轮能解决的事五轮没解决；点击率涨，可能只是新版本更爱推低价爆款。解法是**三组并看**：目标指标（下单转化）、过程指标（点击/加购）、**护栏指标**（退货率、用户纠正率——防止为刷分把系统带偏）。"下单转化 +8%、退货率持平、用户纠正率 −12%"比"满意度 +10%"可信得多。同一指标跨业务方向可以相反：轮数在陪伴类是正向、在客服是负向；教育 Agent 只看当下满意度会退化成直接给答案——要看后续相似题正确率、提示次数、独立完成率，有时"用户当下觉得麻烦"恰恰说明它在逼思考。

业务指标要**反推**：不从"我能采什么数据"出发，从"用户为什么用我的 Agent"出发——用户为什么来、觉得好用会做什么、觉得你蠢会做什么。所以指标体系除了正向还要有**负向**，且负向常常更有价值：用户懒得点赞，但被惹毛时会用行为投票。漏斗往下看了才算数：点击≠喜欢≠准确，停留、收藏、加购、下单，越往下越接近真实目标。

检索链路的归因顺序（回答"召回率涨了答案准确率反而降"）：四类归因定位——**没召回到→召回问题；召回到但被重排压下→重排问题；用了过期版本→知识源问题；材料没问题模型没采纳→推理/规划问题**。召回涨而答案降，最常见是重复率与上下文冗余上升（父块过大、相邻块未合并）——**进来的更多，但更脏**。归因的工程前提是 Trace 记录**决策链**而非调用链：每轮 Query、所用源与方式、召回结果、新增有效证据、已确认事实、未覆盖缺口、继续/停止的原因；RAG 型 Agent 优先盯**空结果率**（升高说明 Query 构造、索引或策略坏了）与**证据覆盖率**，外加上下文遗漏率、约束丢失率、降级触发率。内容不全量永久保存（数据量与隐私），按抽样请求/异常请求/短期分级留存。

### 8.4 错误样本回流

值得优先回流的强信号：点踩、要求重新生成、明说"不是这个意思"、同问题反复改问、多次 Replan、工具连续失败、Judge 明显低分、核心指标异常。还要**主动按指标找异常**：正常三四轮结束的场景里某批用户平均十五轮，整批抽出分析——回流不是等用户告诉你哪里错。

一条完整案例（可作模板）：用户明说不要某品牌却被推了，下一轮立刻反问 → 保存输入/Context/工具调用/输出/反馈 → 排查发现根因不在推荐算法，是那条硬约束在上下文压缩中被丢了 → 修 Context 管理 → Case 进测试集，此后每次改 Prompt/Context/模型都重跑。**回流最重要的价值：同一个坑尽量只踩一次。** 数据驱动迭代的完整表述：固定测试集，每次改 ChunkSize、路数、Top-K、RRF 权重、Rerank、迭代策略都重跑对比，下降就把 Bad Case 归因到具体环节——测试→发现→改→回归→对比→再迭代。更自动化的形态（评估子 Agent 周期读纠正率/Judge 分数/Replan 次数，自动抽会话、聚类、归因、生成新 Prompt 规则）**值得知道、生产慎用**：连"怎么算好"都还没解决，越自动化越容易朝错误方向狂奔——只优化轮数会让 Agent 学会故意一次不讲完，只优化下单率会让它偏爱低价爆款。现实形态是"部分自动化 + 人工决策"，且两道保险不可省：**护栏指标 + 人工审批**（System Prompt、工具权限、安全策略、资金操作的变更不许 Agent 自主改）。

收口三件套：**入库有创新、检索有创意、评估有闭环**——三者齐备才算完整方案；没有评测闭环的优化，只是"改动"的别名。

## 九、踩坑清单

1. 把 RAG 当读取侧的"搜索调用"，写入侧没有版本、没有 owner、没有下线预案。
2. metadata 只存 doc_id + text，生效期/权限/版本全靠模型猜。
3. 让模型从召回文本里"读"金额和 id——机械真值必须确定性绑定。
4. ChunkSize 抄网上数字，被问"为什么不是 300"当场卡壳。
5. 表格行脱离表头入库（"手机 A、3999、有货"），检索命中也读不懂。
6. 把该用 SQL 查的大表塞进向量库——聚合筛选排序不是相似度的活。
7. 父子文档只对子块建向量就完事，五个子块命中同一父块注入五次。
8. 用"分数置 0"冒充过滤——越界的结果该被清场，不该被排到最后。
9. 强行归一各路分数再加权——不同货币没有汇率，用名次。
10. 迭代式检索不设退出条件，或把"查三轮"当目标——进度条是新增证据数。
11. 把安全红线和干活知识倒进同一个向量池，让余弦决定保命条款在不在场。
12. 约束硬召回不设帽：规矩挤光全部预算，Agent 只剩纪律没有事实。
13. 硬召回之后就不管了——被看见≠被遵守，工具层校验和人审才是最后一道。
14. 性能优化脱离准确率——砍链路换来的低延迟叫功能缩水。
15. 答案缓存一把梭——依赖实时数据/权限/画像的问题，缓存就是过期答案发射器。
16. 只看平均值不看 P99 和长尾失败案例。
17. 汇报只报检索指标不报任务成功率——证明不了系统做得怎样。

## 十、扩展阅读：Codex 如何在"零向量"下做检索

OpenAI Codex CLI（`openai/codex`，commit `44b857c`，2026-09-22）给本篇提供了一个极端样本：**全仓库没有任何 embedding、余弦相似度、ANN 索引或 rerank**（穷举核对：`grep -riE "embedding|cosine|hnsw|faiss|rerank|similarity"` 在 Rust 代码里仅命中"嵌入式宿主"语义的 5 处，与向量无关；`Cargo.lock` 无任何向量库；30 个 SQLite migration 里没有 FTS 虚拟表）。它的检索面是四类东西的组合：**托管搜索、agentic search、元数据检索、渐进披露**。路径以 `codex-rs/` 为根。

![图 2：Codex 的四个检索面——零向量、词法 + agentic](../assets/14-Codex四个检索面.svg)

### 10.1 web_search：一个工具、两种回传协议

托管路径：`create_web_search_tool()`（`core/src/tools/hosted_spec.rs:14`）把 `WebSearchMode { Cached, Indexed, Live, Disabled }` 翻译成服务端开关，检索**在 OpenAI 服务端执行**；客户端流里只会收到 `ResponseItem::WebSearchCall { status, action }`（`protocol/src/models.rs:1190`）——它是"服务端替我干了什么"的**行为摘要**（query 或 URL），搜索结果本身不回客户端，也不进模型历史。独立路径 `web.run`（`ext/web-search/src/tool.rs:46`）才是标准三段式：query 侧用 `recent_input()`（`history.rs:19`，只取最近 2 条用户消息 + 其间 ≤1000 token 的助手文本）把上下文喂给检索后端；回传分两路——正文进 `FunctionCallOutput`（并打上 `contains_external_context()=true` 供审查），结构化结果**只走旁路**给 UI，不进模型上下文。对照本篇：**retriever 在谁手里，决定了你拿到的是证据还是日志**。

### 10.2 代码检索：零索引，把 ranking 拆成多轮廉价查询

全仓没有 `grep`/`search_files` 专用工具，代码检索完全等价于 `exec_command{ cmd: "rg ..." }`，约束只有一句 prompt（"搜文本/文件优先 rg，它比 grep 快得多"）。文件系统本身就是索引，**排序外包给模型的多轮决策**（grep → read → 再 grep），召回预算由 `max_output_tokens`（默认 10000）和进程侧 1 MiB `HeadTailBuffer`（保头保尾丢中段）兜底。为什么不上 embedding 索引？代码检索的 query 高度依赖上一步结果（"看这个函数被谁调用"），**静态索引服务不了交互式查询分解**。另有一条给人用的模糊文件检索（`file-search` crate，nucleo 子序列匹配，@ 提及补全）——人和模型各用各的检索面。

### 10.3 tool_search：把 RAG 用在"工具"这批文档上

这是全仓唯一真正的检索器：BM25（crates.io `bm25`），语料是**所有 Deferred 暴露的工具**，文档内容 = 工具名 + 名字分词 + 描述 + **递归展开的 JSON Schema 字段名与 description**（`tools/src/tool_search.rs:111`）。索引在每轮构建 ToolRouter 时经缓存复用，失效判定：不可变 handler 比 `Weak::ptr_eq`，动态 MCP 工具按值比元数据（描述变了就重建）。查询参数只有 `query + limit(默认 8)`；返回的不是文本证据而是**可执行能力**：`ToolSearchOutput` 携带 `defer_loading=true` 的 schema，模型下一轮直接调用——`router.rs:198` 放行"已被搜索命中"的 Deferred 工具。对照表几乎逐格成立：corpus=工具文档、index=BM25、top-k=limit、rerank 位=按 namespace 归并（`coalesce_loadable_tool_specs`）；唯一区别是 **retrieve→act 闭环，没有"生成前拼接"这一步**。工程红线也眼熟：空 query、limit=0 一律 `RespondToModel` 软错误——**retriever 的失败是对话内容，不是异常**。

### 10.4 渐进披露：每层目录都有独立预算闸门

AGENTS.md 是**零打分的确定性检索**：从 git 根到 cwd 逐级收集、`--- project-doc ---` 分隔、默认 32 KiB 预算顺序扣减截断（`core/src/agents_md.rs`）。Skills 三段式：目录阶段每行只有 name + 截断描述 + 定位符（metadata 预算 10000 token、单技能提示 8000B、描述截到 1024 字符）；触发靠"用户点名或任务明显匹配"；加载走 `skills.read` 分页游标——**选文件要窄，读入选文件要全**。MCP 资源是 list→read 两级跳转，`read_mcp_resource` 的契约明写"uri 必须来自上一步 list 的返回"。最有意思的是作者自己的克制：skill 侧已实现多字段 BM25/n-gram/RRF 一整排选择器，但**只在影子模式跑埋点**——模型可见目录不变；trait 注释写得很直白："不改变模型可见目录的前提下选择"。**先证明排序器优于模型自选，再上线检索**——这个决策顺序比任何技术选型都值得抄。

### 10.5 历史检索：ripgrep 扫 JSONL + SQLite 子串

跨会话"记忆"的检索栈：内容搜索用外部 `rg -l --fixed-strings --ignore-case` 扫 `sessions/*.jsonl`，命中路径集与 SQLite 列表分页取交集，snippet 只回填前 48 / 后 96 字符（服务人眼在 picker 里辨认，不是给模型拼证据）；元数据搜索是 `instr()` 子串匹配，不是 FTS 更不是向量；模型侧的 `list_threads / read_thread` 同样两级 + 分页。记忆候选的选取 SQL 干脆是**纯时效窗口**（`ORDER BY updated_at_ms DESC LIMIT`，`search_term: None`）。rollout JSONL 是唯一事实源，DB 只是可重建的加速视图。

### 10.6 对照与取舍

| 本篇观点 | Codex 的实现证据 |
| --- | --- |
| 能用最简方案就别上向量 | 全仓零 embedding，词法 + agentic 撑起生产 |
| 分路召回：确定域走规则路 | `ToolExposure` 枚举把"要不要占上下文"变成 per-tool 策略位 |
| 渐进披露 / P3 只挂 handle | Skills 与 MCP resources 的"目录+定位符"模式 |
| 检索预算先行 | 512KiB/10k token/32KiB/1MiB 每层独立闸门 |
| 召回失败要可归因 | 检索类错误全走 RespondToModel，可被模型自救 |
| ranking 可以外包给模型 | 代码检索多轮 rg；skill 排序器只跑影子模式 |
| 截断要诚实留痕 | HeadTailBuffer 丢中段但标注 omitted |

它没有做的同样清楚：**没有语义召回、没有融合排序、没有证据链管理**——因为编码域的知识源是文件系统与 git（天然带结构与新鲜度），不是十万份 PDF。换一个业务域（客服知识库、合规文档），这套"零向量"未必成立；但它会逼你回答本篇开头那个问题：**你的检索里，有多少复杂度其实只是"没人想清楚候选从哪来"的遮羞布？**

## 总结

这一篇把检索拆成了三层：

- **供应链层**：入库是资产管理（版本、生效期、权限、manifest、回归），不是往库里灌文本；
- **概率层**：多路召回、名次融合、迭代补证、充分性判断——承认相似度是概率的，所以"该不该在场"绝不能交给相似度；
- **经济层**：最小充分检索 + 动态预算 + 三层缓存——最快的查询是没发生的查询。

三条判据带走：**切块边界画在语义断点上；确定域走规则路，概率域走向量路；一切优化以"带预算的准确率"计价**。

2. 你的系统里有没有一条"ORM 禁令"式的约束？按 S1-S4 分路架构，它现在走的是哪条路？
