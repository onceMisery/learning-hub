## 一、为什么要做这个项目：背景与核心问题

这个仓库要解决的是三件具体的事，而不是"做一个看板"：

**1. 把一套现代前端技术栈塞进一个能跑的真实应用里。**
孤立的小 demo 不会暴露真问题：版本之间互相不兼容、构建配置牵一发动全身、桌面端主进程与页面属于两个完全不同的运行环境。这些只有在"能打包成安装包、能装上能卸载"的应用里才会出现。所以最终产物是 **2199 行源码 + 可安装的三平台包**，而不是若干片段。

**2. 验证"离线优先"这条路线能成立。**
没有后端、没有账号、断网可用，数据全部落在本地 IndexedDB。这条约束反过来决定了架构：既然本地就是数据的唯一真源，就不需要"服务端缓存"，于是数据层（Dexie）和状态层（Zustand）的分工必须划清楚——这也是第五节与第八节重点讲的东西。

**3. 用类型系统而不是约定去消灭一整类 bug。**
跨进程边界上，抛出的异常经过 IPC 之后只剩字符串，类型和堆栈都没了；渲染进程给主进程的数据也不可信。所以本项目统一用 `Result` 表达失败、用 zod 在边界上做运行时校验，让"会失败"这件事进入类型系统，而不是靠人记得写 `try/catch`。

因此这个项目的完成标准不是"功能多"，而是**每一处取舍都能说出为什么**：为什么是 Dexie 而不是 localStorage、为什么 UI 状态不进数据库、为什么拖拽用原生 HTML5 而不用 dnd-kit。答案集中在第五节（架构）、第八节（模块）、第十节（决策表），复盘和面试时最值得讲的也是这些。

## 三、功能特性（以 `src/` 实际实现为准）

### 3.1 看板与列

`Board` / `Column` / `Card` 三层模型，列靠 `order` 排序。`BoardView` 用 `useLiveQuery` 订阅 `columns`，`ColumnView` 各自订阅自己那一列的卡片——**按列订阅而不是整板订阅**，这样新增一张卡片只会重渲染对应的一列。

首次启动 `ensureSeed()` 在一个 `rw` 事务里写入看板、三列和 4 张示例卡片；已有数据则直接返回第一个看板 id，不会重复播种。

### 3.2 卡片

| 操作 | 入口 | 落地方式 |
| --- | --- | --- |
| 新增 | 列底部输入框，回车 | 构造完整 `Card` 对象 → `addCard` 命令 |
| 修改 | 点卡片 → 弹窗 | 标题 / 备注 / 标签 / 优先级 / 已完成，保存时记 `updateCard` 命令 |
| 删除 | 弹窗里的"删除" | 整张卡片存进 `removeCard` 命令，撤销时原样加回 |

标签输入是"逗号分隔的字符串"，由 `parseTags()` 切成数组（中英文逗号和空白都认）。优先级是 `0 | 1 | 2` 三档字面量类型，写错值编译期就报错。

### 3.3 拖拽排序

用原生 HTML5 Drag & Drop，不引第三方库。三个关键细节（都写在 `CardItem.tsx` 的注释里）：

- `dataTransfer` 里只放 `card.id`，不放序列化对象——拖放过程中读不到复杂数据
- `onDragOver` 必须 `preventDefault()`，否则浏览器根本不触发 `drop`
- 卡片上的 `onDrop` 要 `stopPropagation()`，否则事件冒泡到列上会再触发一次"追加到末尾"，一张卡片被处理两遍

落点是"插入位置"而不是"目标列"：拖到某张卡片上 → 插到它的位置；拖到列空白处 → 追加到末尾。

### 3.4 搜索与筛选

搜索框的值存在 Zustand（不持久化，搜索词不该被记住），过滤在 `BoardView` 里用 `useMemo` 做：标题、备注、标签拼成一个字符串后做大小写无关的子串匹配。

谓词抽成了纯函数 `matchesKeyword()`，数据库层的 `searchCards()` 和 UI 层的实时过滤**共用同一份规则**——否则迟早出现"搜索结果和列表对不上"的经典 bug。

**适用边界**：这是全量读取后内存过滤，O(n)。几百到几千条足够；上万条要换倒排索引或 Web Worker，见 [05 · 阶段4](./05-阶段4-Dexie本地数据层.md) 的"搜索的三条路线与取舍"。

### 3.5 三态主题

`system / light / dark` 三态，存在 Zustand 并 `persist` 到 localStorage。`useThemeEffect` 把结果落到 `<html data-theme>` 上；`system` 态会监听 `prefers-color-scheme` 的变化实时跟随。

### 3.6 撤销 / 重做

命令模式，四类命令（增 / 删 / 改 / 移），上限 50 步。Electron 走菜单快捷键，浏览器走键盘监听，两者互斥（详见 [11 · 撤销重做](./11-撤销重做与端到端测试.md)）。

按钮上的 tooltip 会显示下一步要撤销什么（`撤销：新增「xxx」`），因为"不知道会撤销掉什么"是撤销功能最劝退的地方。

### 3.7 导出 / 导入

导出为一份带 `version` 的快照 JSON；导入是**整库替换**，不是增量合并——本地数据本来就是"这一份"，替换语义最不容易出错。文件读写在主进程（渲染进程不碰 `fs`），读回来的内容先用 zod 校验再落库。

### 3.8 桌面外壳

无边框窗口 + 自绘标题栏（最小化 / 最大化 / 关闭走 IPC），应用菜单提供"新建卡片 `Ctrl/Cmd + N`"与撤销重做快捷键。窗口拖拽靠 CSS 的 `-webkit-app-region: drag`，按钮区域显式关掉，否则按钮点不动。

### 3.9 自动化测试

Vitest 单元测试 18 项（`fake-indexeddb` 提供 IndexedDB）+ Playwright 驱动真实 Electron 的端到端测试 6 项 + 三平台 CI。另有 `npm run capture` 走一遍核心路径并截图。

## 五、整体架构：数据怎么流

### 5.1 分层

```
┌──────────── 渲染进程（浏览器，无 Node 权限）────────────┐
│  features/   页面组件：BoardView / ColumnView / CardItem │
│  components/ 无业务通用组件                              │
│  store/      Zustand：只放 UI 状态（查询词 / 主题 / 筛选）│
│  history/    命令模式：撤销栈                            │
│  db/         Dexie schema 与全部数据库操作               │
│  api.ts      同一接口的宿主适配层                        │
└───────────────────────┬─────────────────────────────────┘
                        │  IPC（通道名 + zod 校验 + Result）
┌───────────────────────┴─────────────────────────────────┐
│  preload/    隔离世界：contextBridge 白名单              │
│  main/       主进程（Node）：窗口 / 菜单 / 文件对话框     │
└─────────────────────────────────────────────────────────┘
              shared/  两端共享：类型 · IPC 契约 · zod schema
```

三条不可破的边界：

1. `shared` 是跨进程契约的唯一真源，通道名与 schema 都从它导出，两端不许手写字面量
2. 渲染进程永远碰不到 `fs`，一切原生能力走 IPC，且主进程侧用 zod 校验入参
3. 主进程永远碰不到 DOM

### 5.2 一次操作走完的链路（以"新增卡片"为例）

1. 用户在列底部输入框回车 → `ColumnView` 构造完整的 `Card` 对象
2. 交给 `useHistoryStore.execute({ kind: 'addCard', ... })`：先 `applyDo` 写库，再压入 `past` 栈
3. Dexie 写入成功 → 数据库本身发生变化
4. `useLiveQuery` 订阅的查询自动重跑 → 该列重新渲染，`motion.li` 播放入场动画
5. 工具栏的"撤销"按钮因为 `past` 变长而可用，tooltip 显示 `撤销：新增「xxx」`

注意第 4 步：**没有任何一处手写"改完记得刷新"**。这是选 `useLiveQuery` 而不是 `useEffect + setState` 的全部理由。

### 5.3 数据存在哪

| 数据 | 存放位置 | 是否持久化 | 理由 |
| --- | --- | --- | --- |
| 看板 / 列 / 卡片 | Dexie（IndexedDB） | 是 | 业务真源，需要索引与事务 |
| 查询词 / 筛选 | Zustand | 否 | 一次性 UI 状态，下次打开不该还记得 |
| 主题 / 当前看板 | Zustand + `persist` | 是 | 用户偏好，要跨会话保持 |
| 撤销栈 | Zustand | **否** | 重开应用后数据可能已被别处改动，拿旧的反向操作去改新数据会写坏 |

## 八、核心模块的实现思路与关键逻辑

每节都给出文件位置，细节写在对应阶段文档里。

### 8.1 数据模型与索引（`src/shared/types.ts`、`src/renderer/db/db.ts`）

两个"为什么要这样定义"的点：

- **`done` 用 `0 | 1` 而不是 `boolean`**：IndexedDB 不能索引 boolean，而"已完成"是要被查询的字段
- **`priority` 用字面量联合 `0 | 1 | 2`**：写 `3` 编译期就报错，不需要运行时校验

索引字符串的第一个字段是主键，`[a+b]` 是复合索引，`*tags` 是多值索引（数组里每个元素都能被检索）：

```ts
this.version(1).stores({
  boards: 'id, name, createdAt',
  columns: 'id, boardId, order, [boardId+order]',
  cards: 'id, columnId, boardId, done, updatedAt, [boardId+columnId], *tags',
});
```

v2 加了 `priority` 字段，**必须给老数据回填**，否则旧卡片读出来是 `undefined`：

```ts
this.version(2).stores({ cards: '…, priority, …' }).upgrade(async (tx) => {
  await tx.table('cards').toCollection().modify((card: Card) => {
    if (typeof card.priority !== 'number') card.priority = 1;
  });
});
```

### 8.2 数据层操作（`src/renderer/db/operations.ts`）

全部数据库操作集中在这一个文件，组件不直接碰 `db`。两个必须理解的实现：

**移动卡片 = 整列重排**，包在一个事务里。中途失败要整体回滚，否则会出现两张卡片 `order` 相同、顺序随机漂移：

```ts
await db.transaction('rw', db.cards, async () => {
  const target = await db.cards.where('columnId').equals(toColumnId).sortBy('order');
  const rest = target.filter((item) => item.id !== cardId);
  rest.splice(insertAt, 0, { ...card, columnId: toColumnId });
  await db.cards.bulkPut(rest.map((item, index) => ({ ...item, order: index, updatedAt: timestamp })));
});
```

**导入快照 = 整库替换**，先 `clear()` 三张表再 `bulkPut()`，同样在一个 `rw` 事务里——导入到一半失败不能留下"半新半旧"的数据。

### 8.3 响应式渲染（`useLiveQuery`）

`BoardView` 订阅列、`ColumnView` 订阅本列卡片，粒度按列划分。一个容易踩的类型坑写在 `ColumnView.tsx` 注释里：默认值 `[]` 会被推断成 `never[]`，结果类型变成 `Card[] | never[]`，之后 `indexOf(card)` 会因参数被求交成 `never` 而报错。**显式给出两个泛型参数**即可：

```ts
const columnCards = useLiveQuery<Card[], Card[]>(
  () => db.cards.where('columnId').equals(column.id).sortBy('order'),
  [column.id],
  [],
);
```

### 8.4 撤销 / 重做（`src/renderer/history/`）

命令是**数据**而不是 `{ undo, redo }` 闭包，理由写在 `commands.ts` 顶部：数据可以在测试里直接断言（不必跑一遍数据库）、可序列化（将来做操作日志 / 协同时不用重写）、组件只负责"记录发生了什么"。

栈的上限 50 步，且**故意不套 `persist`**——撤销栈描述的是"本次会话做过什么"，重开应用后数据可能已被别处改动，拿旧的反向操作去改新数据会写坏。

已知边界（诚实说明，详见 [11](./11-撤销重做与端到端测试.md)）：删除后撤销只能复原到删除时的 `order`；跨列拖拽撤销后同列其它卡片的顺序可能差一位；连续拖 10 次要撤销 10 次。

### 8.5 跨进程 API（`api.ts` / `preload/` / `main/`）

同一份 `Api` 接口，两套实现：Electron 下由 preload 通过 `contextBridge` 注入，浏览器开发时降级到 `browserFallback`。业务代码只依赖接口，不依赖"我现在跑在哪个宿主里"。

- preload 只按白名单暴露方法，**绝不暴露 `ipcRenderer` 本身**
- 订阅类方法返回取消订阅函数，React 里 `useEffect(() => api.onMenuXxx(cb), [])` 就能自动清理
- 主进程侧所有入参先过 zod：`snapshotSchema.safeParse(payload)`，失败返回 `err(...)` 而不是抛异常

菜单 → 页面的通知用的是"新 token"而不是计数器：`api.onMenuNewCard(() => setFocusToken(newId()))`，下游组件看到 token 变化就聚焦输入框。

### 8.6 状态分层（`src/renderer/store/ui.ts`）

store 里只有四项：查询词、当前看板、主题、只看高优先级。**业务数据一份都不进 store**，否则会出现两份真相，同步成本极高。`persist` 只持久化"下次打开还想保持"的两项：

```ts
partialize: (state) => ({ activeBoardId: state.activeBoardId, theme: state.theme })
```

### 8.7 主题（`src/renderer/hooks/useTheme.ts`）

Tailwind v4 默认的 `dark:` 变体走 `prefers-color-scheme`，只能跟随系统；想要"系统 / 亮 / 暗"三态，就得用 `@custom-variant` 改写成匹配 `data-theme`，然后由 hook 把结果写到 `<html data-theme>`。`system` 态额外监听 `matchMedia` 的变化。

## 十、关键决策与取舍（重点）

| 决策点 | 可选方案 | 选了什么 | 为什么 |
| --- | --- | --- | --- |
| **本地存储** | localStorage / Dexie(IndexedDB) / SQLite | **Dexie** | localStorage 只有 5MB 且是同步 API（会卡 UI）、不能查询；SQLite 需要原生模块（ABI 匹配 + 打包复杂）。IndexedDB 容量按磁盘算、支持索引与事务，`useLiveQuery` 还能自动刷新 UI |
| **数据层刷新** | 手写 refresh / `useLiveQuery` | **useLiveQuery** | 手写意味着"每处写入都要记得刷新"，漏一处就是脏数据。liveQuery 订阅数据库本身，任何写入（包括另一个窗口）都自动反映 |
| **全局状态** | Redux Toolkit / Zustand / Context | **Zustand（只放 UI 状态）** | 真正需要跨页共享的只有"当前看板/筛选/主题"这几项；服务端/数据库数据不进 store，避免双份真相 |
| **拖拽** | HTML5 DnD / dnd-kit / Motion Reorder | **HTML5 DnD** | 依赖为零、代码 20 行、键盘可达性另做即可；dnd-kit 功能强（传感器、碰撞检测、无障碍）但多 30KB+ 与一层抽象。**适用边界**：需要触屏、嵌套拖拽、自动滚动时换 dnd-kit |
| **lint** | typescript-eslint / oxlint | **oxlint** | `typescript-eslint@8.70` 的 peer 是 `typescript <6.1.0`，与 TS 7 **不兼容**。oxlint 不依赖 TS 编译器 API，与 TS 7 无冲突且快一个数量级。类型问题交给 `tsc --noEmit` |
| **Electron 构建** | electron-vite / 手写 Vite 多入口 | **手写** | `electron-vite@5` 的 peer 是 `vite ^5` |
| **路由** | React Router / 不用 | **不用** | 单窗口单页应用，看板切换用状态而非 URL。加路由的时机：需要深链、多页面或分享链接时 |
| **服务端数据层** | TanStack Query / 不用 | **不用** | 离线优先应用里，数据真源在本地，没有"服务端缓存"要管。**什么时候该用**：接了真实后端 API，需要缓存/失效/重试/分页时 |
| **IPC 返回值** | 抛异常 / Result 类型 | **Result** | 异常跨进程后会丢失类型与堆栈，渲染进程只能拿到字符串；Result 让"失败"成为可被类型系统检查的分支 |
| **主题切换** | Tailwind 默认 `dark:` / 自定义变体 | **@custom-variant + data-theme** | v4 的 `dark:` 默认走 `prefers-color-scheme`，只能跟随系统；改成 data 属性后才有"系统/亮/暗"三态 |
| **动效载体** | `motion.li` 直接挂拖放 / 内部分层 | **内部分层** | Motion 组件自带 `onDragStart/onDragOver/onDrop`（它自己手势系统的回调），与 React 原生拖放事件签名冲突，会报类型不兼容 |

## 十一、实现过程中的难点

按"踩到的顺序"排列，症状与完整解法在 [09 · 排错手册](./09-排错手册.md)：

| 难点 | 症状 | 怎么过的 |
| --- | --- | --- |
| **TS 7 与生态不兼容** | `typescript-eslint` peer 冲突、`baseUrl` 被移除、非相对路径导入报错 | 换 oxlint；改用 `paths` + 相对导入；逐条记录在 09 的第 1 节 |
| **Vitest 5 默认 forks 池超时** | `[vitest-pool]: Timeout waiting for worker to respond` | 改 pool 配置，见 09 第 3 节 |
| **测试环境没有 IndexedDB** | `indexedDB is not defined` | `fake-indexeddb` 在 `tests/setup.ts` 里补上 |
| **`useLiveQuery` 的 `never[]` 推断** | `indexOf(card)` 参数被求交成 `never` | 显式写两个泛型参数 `useLiveQuery<Card[], Card[]>` |
| **Motion 与原生拖放签名冲突** | 把 `onDrop` 挂在 `motion.li` 上报类型不兼容 | 分层：`motion.li` 只管动画，原生拖放挂在内层 `div` |
| **拖放事件被处理两遍** | 拖到卡片上却跑到列尾 | 卡片 `onDrop` 里 `stopPropagation()` |
| **撤销快捷键触发两次** | 按一次 `Ctrl+Z` 撤销两步 | 菜单归主进程，`useHistoryShortcuts` 里 `if (window.api) return;` 让位 |
| **E2E 每次都从同一份数据起跑** | 种子数据只写一次，断言被历史数据干扰 | 主进程支持 `LUMEN_USER_DATA`，每个用例 `fs.mkdtempSync` 独立目录 |
| **Electron 起不来** | `Process failed to launch!` / `GPU process isn't usable` | 删掉注入的 `ELECTRON_RUN_AS_NODE`，加 `--no-sandbox --disable-gpu` |

## 十二、当前边界与后续可优化方向

**先说清楚现在没做什么**（按重要性排序，避免"看起来什么都有"）：

1. **列与看板不能增删改** —— 只有首次启动的种子数据（一个看板、三列）。`columns` / `boards` 的写操作只出现在播种与导入快照里
2. **撤销的精度** —— 删除后撤销只复原到删除时的 `order`；跨列拖拽撤销后同列顺序可能差一位；没有"合并同类操作"
3. **没有触屏与键盘拖拽** —— 原生 HTML5 DnD 在移动端不工作，键盘可达性也未做
4. **搜索是全量内存过滤** —— 上千条卡片后每次输入都要遍历
5. **单看板** —— `activeBoardId` 已经在 store 里预留，但还没有切换 UI

**可以继续往哪走**（按投入产出比，与 [10](./10-交付与验收清单.md) 第五节一致）：

1. 补上列 / 看板的增删改（命令模式已经就位，加两类命令即可）
2. 虚拟滚动（列内卡片上千时），顺带体会 `layout` 动画与性能的取舍
3. 触屏与无障碍：换 dnd-kit，用它的传感器与键盘支持
4. 搜索上量：倒排索引或 Web Worker 内建索引
5. 多看板 + 路由：引入 React Router，把选中项放进 URL
6. 接真实后端 + TanStack Query：体验"服务端缓存 vs 本地真源"的分层
7. 同步与冲突解决：outbox 队列 + `updatedAt` 比较 + 冲突 UI
8. 自动更新：`electron-updater` + 更新服务器
