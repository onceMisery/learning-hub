# 11 · 撤销/重做 与 端到端测试 + CI

## 学完你能做什么

- 给任意编辑器类功能加上可撤销的操作（而不是"删了就找不回来"）
- 说清撤销栈该记录什么、不该记录什么，以及为什么历史不能持久化
- 用 Playwright 驱动真实的 Electron 应用跑端到端测试
- 搭一条"质量门禁 + 三平台 E2E"的 CI 流水线

**前置**：阶段 3~7（组件、数据层、状态管理、Electron）。

---

## 一、撤销/重做：三条路线与取舍

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **快照栈** | 每次操作前把整个 state 深拷贝一份入栈 | 实现最简，撤销就是整体替换 | 内存随数据量线性增长；无法跨会话；无法表达"合并多次输入为一步" | 只适合数据量极小的场景 |
| **命令模式**（本项目） | 每次操作记一条"命令"（含正反两个方向所需的数据），撤销时执行反向命令 | 内存小、可测试、可序列化、能显示"撤销：删除「xxx」" | 每类操作要定义正反两个动作 | ✅ 推荐 |
| **事件溯源 / CRDT** | 只追加事件流，状态由事件重放得出 | 天然支持协同、时间旅行、跨会话历史 | 复杂度高一个数量级 | 只有做多人协同时才值得 |

**为什么选命令模式**：这是一个单机应用，不需要协同；但命令是"数据"而不是闭包，将来要加"操作日志面板"或"云端同步历史"时不用重写。

## 二、实现

### 2.1 命令定义（`src/renderer/history/commands.ts`）

```ts
export type HistoryCommand =
  | { kind: 'addCard';    label: string; card: Card }
  | { kind: 'removeCard'; label: string; card: Card }
  | { kind: 'updateCard'; label: string; id: string; next: CardPatch; prev: CardPatch }
  | { kind: 'moveCard';   label: string; id: string; from: Position; to: Position };

export async function applyDo(command: HistoryCommand): Promise<void> { /* 正向 */ }
export async function applyUndo(command: HistoryCommand): Promise<void> { /* 反向 */ }
```

关键取舍：

- **删除要存整张卡片**，只存 id 的话撤销时数据已经没了
- **修改要存 `prev` 快照**，否则撤销时得再查一次库——而且那时数据可能已被别的窗口改过
- **移动要存 `from` 的位置**（列 + 序号），光记"移动了"无法还原顺序

### 2.2 撤销栈（`src/renderer/history/store.ts`）

```ts
execute: async (command) => {
  await applyDo(command);
  set((state) => ({
    past: [...state.past, command].slice(-state.limit),
    future: [],           // 新操作后清空重做栈（编辑器通用约定）
  }));
},
undo: async () => { /* past 出栈 → applyUndo → 入 future */ },
redo: async () => { /* future 出栈 → applyDo → 入 past */ },
```

三个刻意的设计：

1. **上限 50 条**：每条命令带一份卡片快照，无限存既占内存又没意义
2. **不持久化**：历史描述的是"本次会话做过什么"。重开应用后数据可能已被别处改动，拿旧的反向操作去改新数据会写坏 —— 所以这个 store 不套 `persist`
3. **`execute` 先落库再入栈**：如果 DB 写入失败了，栈里就不该有一条撤销不了的记录

### 2.3 快捷键归谁管（容易踩的重复触发坑）

| 环境 | 由谁处理 | 原因 |
| --- | --- | --- |
| Electron | 主进程菜单加速键（`CmdOrCtrl+Z`）→ IPC → 渲染进程 | 菜单是原生行为，用户能在菜单里看到快捷键提示 |
| 浏览器（`npm run dev`） | `hooks/useHistoryShortcuts.ts` 监听 window | 没有菜单可用 |

两者**不能同时生效**，否则一次按键撤销两步。实现上：`useHistoryShortcuts` 里 `if (window.api) return;`（有 `window.api` 说明跑在 Electron 里，交给菜单）。

另外：焦点在 `input/textarea` 里时不劫持 `Ctrl+Z`——用户期望的是"撤销我刚打的字"。

### 2.4 已知边界（诚实说明）

- `removeCard` 的撤销是"原样加回整张卡片"，`order` 用的是删除时的值；若期间同列有其它插入，位置可能不精确
- 拖拽跨列后撤销，会回到原来的列与原序号，但同列其它卡片的 `order` 已被重排，顺序可能差一位
- 一次拖拽是一条命令；连续拖 10 次需要点 10 次撤销（没有做"合并同类操作"）

## 三、端到端测试（Playwright + Electron）

### 3.1 为什么用 Playwright 的 `_electron`

- 它驱动的是**真实的 Electron 进程**，测的是用户真正会用的那条链路（菜单、IPC、file:// 加载、IndexedDB）
- 不需要下载 Chromium/Firefox/WebKit（Electron 自带 Chromium），安装时加 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` 即可

### 3.2 三个必踩的坑（都写在 `tests/e2e/kanban.spec.ts` 顶部注释里）

| 坑 | 症状 | 解法 |
| --- | --- | --- |
| `ELECTRON_RUN_AS_NODE=1` 被注入 | `Process failed to launch!` | 传给 launch 的 `env` 里删掉这个变量 |
| 无显卡/无显示环境 | `GPU process isn't usable. Goodbye.` | `args: ['.', '--no-sandbox', '--disable-gpu']` |
| 共用 userData | 种子数据只在第一次写入，断言被历史数据干扰 | 主进程支持 `LUMEN_USER_DATA`，每个用例用 `fs.mkdtempSync` 建独立目录 |

为此主进程加了一行有独立价值的代码（顺便可做便携版）：

```ts
const customUserData = process.env['LUMEN_USER_DATA'];
if (customUserData) app.setPath('userData', customUserData);
```

### 3.3 用例与运行

```bash
npm run build && npm run build:main
npm run e2e
```

**预期输出**（实测）：

```
Running 6 tests using 1 worker
  ok 1 首次启动渲染三列与种子数据 (2.5s)
  ok 2 新增卡片后可撤销、可重做 (6.2s)
  ok 3 撤销栈为空时按钮禁用 (2.4s)
  ok 4 搜索按标题过滤 (5.0s)
  ok 5 刷新后数据仍在（本地持久化）(5.4s)
  ok 6 切换深色主题写入 data-theme (4.1s)
  6 passed (27.3s)
```

**验证方式**：故意把 `src/renderer/history/store.ts` 里的 `future: []` 改成保留 future，重跑会发现"新增卡片后可撤销、可重做"用例失败 —— 说明测试真的在测行为，不是摆设。

**两个测试写法要点**：

1. 统计卡片数要过滤掉退场动画中的元素（约 1 秒内还在 DOM 里）：
   ```ts
   page.locator('section li').evaluateAll(
     (nodes) => nodes.filter((n) => parseFloat(getComputedStyle(n).opacity) > 0.5).length,
   )
   ```
2. 定位按钮要 `exact: true`：卡片标题里也可能含"撤销"字样，否则 strict mode 报"匹配到 2 个元素"

## 四、CI（`.github/workflows/ci.yml`）

### 4.1 为什么拆成两个 job

| job | 内容 | 设计原因 |
| --- | --- | --- |
| `quality` | lint / typecheck / unit / build | 快（约 1~2 分钟）、便宜，失败要最早知道；只跑一个 ubuntu 就够 |
| `e2e` | 三平台跑真实桌面应用 | 慢（每个平台约 3~5 分钟）、需要安装 Electron；`needs: quality` 保证先过门禁再烧机时 |

### 4.2 关键配置

```yaml
env:
  PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD: '1'   # Electron 模式不需要浏览器
  ELECTRON_MIRROR: 'https://npmmirror.com/mirrors/electron/'  # 镜像兜底

- run: npm ci          # 而不是 npm install：锁文件为准，CI 结果可复现
- if: runner.os == 'Linux'
  run: xvfb-run -a npm run e2e            # Linux 无显示，需要虚拟 X server
- if: failure()
  uses: actions/upload-artifact@v4        # 失败时保留 test-results（含截图与错误上下文）
```

- `concurrency.cancel-in-progress`：同一 PR 多次推送只跑最新一次，省机时
- `fail-fast: false`：某个平台失败不取消其它平台，一次拿到全部平台的结论
- `cache: npm` + `npm ci`：有 lockfile，依赖可复现

### 4.3 本地模拟 CI

```bash
npm ci
npm run lint && npm run typecheck && npm test
npm run build && npm run build:main
npm run e2e
```

## 五、本阶段踩坑速查

| 症状 | 原因 | 修复 |
| --- | --- | --- |
| `strict mode violation: resolved to 2 elements` | 文本匹配到多个元素 | 加 `exact: true`，或用更唯一的定位器 |
| `Process failed to launch!` | `ELECTRON_RUN_AS_NODE` 或 electron 二进制缺失 | 删除该环境变量；`node node_modules/electron/install.js` 重装二进制 |
| `GPU process isn't usable` | 无显示环境 | `--disable-gpu --no-sandbox`，Linux 用 `xvfb-run` |
| 断言"卡片数量"总是偏多 | 退场动画期间元素仍在 DOM | 按 opacity 过滤或加长等待 |
| `useLiveQuery` 结果调用 `indexOf(x)` 报 "not assignable to never" | 默认值 `[]` 被推断成 `never[]`，结果类型成了 `Card[] \| never[]`，参数被求交成 `never` | 显式给两个泛型：`useLiveQuery<Card[], Card[]>(...)` |
| 撤销一次却回退了两步 | 菜单加速键与渲染进程监听同时触发 | 二选一（本项目：有 `window.api` 时渲染进程不处理） |
| 撤销后数据错乱 | 历史被持久化、跨会话重放 | 历史 store 不要套 `persist` |
