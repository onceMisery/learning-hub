# 前端系统学习路线图（Java 程序员转型版）

> 目标技术栈：TypeScript 7 · React 19 · Vite 8 · Tailwind CSS 4 · Framer Motion（Motion）13 · Zustand 5 · Dexie 4 · Electron 43
> 文档版本：2026-09（所有版本号与特性均以该时间点的官方发布为准）
> 起点假设：有 Java 开发经验，jQuery / HTML / CSS 有接触但不系统、不牢固

---

## 一、这份规划怎么用

1. **按阶段顺序推进**，每个阶段是一个独立文档，可单独阅读、单独验收。
2. 每个阶段都包含五个固定部分：**学习目标 → 核心知识点 → 本阶段技术栈内容 → 实践练习 → 自查清单**。
3. 每个阶段结束必须有一份**可运行的产出物**（不是笔记，是代码仓库）。跑不起来等于没学。
4. 时间预算按**每周投入 10 小时**（工作日 1h × 5 + 周末 5h）估算，总计约 **26~30 周**。若每周 20 小时可压缩到 14~16 周，但不建议低于 12 周——地基阶段压缩会导致后面反复返工。
5. **不要并行学多个阶段**。前端的痛点是"每个都懂一点、组合起来不会用"，串行推进 + 阶段末综合项目，效果远好于并行。

### 学习法建议（针对 Java 转前端的典型坑）

| 典型坑 | 对策 |
| --- | --- |
| 用 Java 的"类继承"思维写前端，组件层层继承 | 强制自己用**组合 + 数据驱动**，写 100 个组件后再回头总结 |
| 过度依赖 `any`，TypeScript 写成带类型的 JS | 每个阶段末统计 `any` 数量，要求逐阶段递减到 0 |
| 习惯 jQuery 的"选中 DOM → 改 DOM"命令式思维 | 阶段 2 专门做"去 jQuery 化"训练，建立状态驱动心智模型 |
| 只看不写，收藏一堆教程 | 每阶段代码量不低于 1500 行，且必须有 1 个完整小项目 |
| 环境问题卡半天就放弃 | 阶段 4 一次性把工具链（pnpm / Vite / TS / ESLint）标准化 |

## 二、版本矩阵（2026-09 现状）

这套栈在 2026 年发生了几次**架构级变化**，学习时必须用新认知，不要被过时教程带偏：

| 技术 | 目标版本 | 关键事实 | 对学习的影响 |
| --- | --- | --- | --- |
| **TypeScript** | 7.0（2026-07-08 GA） | 编译器整体从 TS 移植到 **Go**（代号 Corsa），全量类型检查 **8~12 倍加速**；`strict` **默认开启**；移除 `target: es5`、AMD/UMD/SystemJS、`moduleResolution: node10`；新增 `--checkers` 并行检查、`--singleThreaded`；语言服务改为 LSP | ① 一上来就按严格模式写，别养成宽松习惯；② 7.0 **没有稳定的编程式 API**，`typescript-eslint`、Vue/Svelte 模板类型检查等工具暂不可用，7.1（预计 2026-11）补齐；③ 如需 lint 的类型规则，可用 `@typescript/typescript6` 兼容包并存（`tsc6` 可执行文件） |
| **React** | 19.2（2025-10 发布） | 19 主线：Actions、`useActionState`、`useOptimistic`、`use()`、`useFormStatus`、ref 作为普通 prop、`ref` 回调清理函数；19.2 新增 `<Activity>`、`useEffectEvent`、`cacheSignal`、Performance Tracks、Partial Pre-rendering；`useId` 默认前缀从 `:r:` 改为 `r` | 学习以 19.2 为准；`useEffectEvent` 直接解决"依赖数组里塞多余值"的老问题；Compiler 1.0（2025-10-07 GA）已稳定，`useMemo/useCallback` 的定位发生根本变化 |
| **React Compiler** | 1.0（2025-10-07） | 构建期自动记忆化，官方数据：初始加载与导航最高约 12% 提升，部分交互约 2.5 倍 | 学会"先写正确、让编译器优化"的新写法，但仍要懂 `useMemo` 的原理（面试与调试需要） |
| **Vite** | 8.0（2026-03-12） | 打包器统一为 **Rolldown**（Rust），构建 10~30 倍加速；要求 Node **20.19+ / 22.12+**；`@vitejs/plugin-react` v6 改用 **Oxc** 做 Fast Refresh，不再依赖 Babel；新增 `devtools` 选项、`resolve.tsconfigPaths`、内置 `emitDecoratorMetadata`、SSR 支持 WASM、`server.forwardConsole` | 老教程里的 `esbuild` / `rollupOptions` 配置写法已被兼容层自动转换；新项目直接用默认配置即可 |
| **Tailwind CSS** | 4.3（2026-05-08） | **CSS-first 配置**：`@import "tailwindcss"` + `@theme` / `@utility` / `@custom-variant`，不再默认需要 `tailwind.config.js`；官方 Vite 插件 `@tailwindcss/vite`；4.3 增加滚动条样式、`zoom`、`tab-size`、更强的 `@variant`；4.2 起提供 `@tailwindcss/webpack` | v3 时代的 `tailwind.config.js` + `@tailwind` 指令写法已过时，别照抄旧教程 |
| **Motion（原 Framer Motion）** | 13.2（2026-09-02） | 2024-11 品牌更名为 **Motion**；新项目装 `motion` 包、从 `motion/react` 导入；`framer-motion` 包名仍在发布（同版本号）；13.0 移除 `@emotion/is-prop-valid` 可选依赖；13.1 增强 `Reorder`（多维/自动轴向/RTL）；`reducedMotion` 默认 `"never"` | 导入路径用 `motion/react`；涉及无障碍动效必须显式开启 `reducedMotion="user"` |
| **Zustand** | 5.x | 基于 `useSyncExternalStore`，要求 React **18+**；移除默认导出，必须 `import { create } from 'zustand'`；移除 `useStore` 的第二个 `equalityFn` 参数，改用 `zustand/react/shallow` 的 `useShallow`；`createWithEqualityFn` 移到 `zustand/traditional` | v4 教程里的 `create` 默认导入、`useStore(selector, shallow)` 写法在 v5 已失效 |
| **Dexie** | 4.x | IndexedDB 的 Promise 封装；`useLiveQuery`（`dexie-react-hooks`）实现响应式查询；支持 schema 版本迁移、`bulkGet/bulkPut`、复合索引、事务、Dexie Cloud（可选） | 用它替代 localStorage 做结构化本地存储；与 Electron 组合可做"离线优先桌面应用" |
| **Electron** | 43（2026-07-02） | Chromium **150.0.7871.46**、V8 **15.0**、Node **24.17.0**；启动性能优化（主进程 Node 启动快照、preload 编译为 V8 字节码）；**32 位平台支持终止**；新增通知管理 API、`globalShortcut.setSuspended()`、`app.configureWebAuthn()` 等 | 内部 Node 版本与本机 Node 版本要对齐管理；安全性（contextIsolation / sandbox / preload）是必修项 |

## 四、环境准备（阶段 0 完成）

### 必装

```bash
# 1. Node.js：Vite 8 要求 20.19+ 或 22.12+；建议直接上 24 LTS（与 Electron 43 内置 Node 24.17 对齐）
node -v   # >= 22.12.0

# 2. pnpm（比 npm 快、磁盘占用小，Vite 生态主流）
npm i -g pnpm
pnpm -v

# 3. Git + VS Code
# VS Code 扩展：
#   - TypeScript Native Preview（TypeScript 7 的语言服务）
#   - ESLint / Prettier
#   - Tailwind CSS IntelliSense
#   - Vitest Explorer
#   - Error Lens（错误即时可见）
```

### 仓库约定（从阶段 1 就养成）

```
frontend-journey/
├── stage-01-html-css/        # 每阶段一个独立目录，独立 README
├── stage-02-javascript/
├── ...
└── final-project/            # 阶段 11 综合项目
```

每个阶段目录至少包含：`README.md`（目标 + 收获 + 踩坑记录）、可运行源码、一份自查清单勾选结果。

### TypeScript 7 与 lint 工具链的兼容处理

TypeScript 7.0 尚未提供稳定编程式 API，重度依赖 `typescript-eslint` 类型规则的项目建议：

```bash
# 主编译器用 TS7
pnpm add -D typescript@7
# 需要类型感知 lint 时，用别名把 TS6 挂到 typescript 名下供工具使用（反之亦可）
pnpm add -D typescript@npm:@typescript/typescript6
```

学习阶段建议：**先用 TS7 的 `tsc --noEmit` 做类型检查，lint 先用非类型感知规则**，等 7.1 发布后再补齐。

## 七、阶段依赖关系与衔接说明

前面六个小节回答了"学什么、用什么版本、怎么验收"。这一节回答更关键的问题：**这些阶段之间谁依赖谁、从哪里进入、往哪里走、哪些可以跳过**。站点渲染器不支持 Mermaid，所以下面用 ASCII 流程图加一张依赖强度表来表达。

### 7.1 阶段依赖图（ASCII 流程图）

```text

   │  后续 5~10 全部跑在它搭的脚手架上（强依赖）
   ├──────────▶ 阶段 5  Tailwind CSS 4 ──▶ 阶段 6  React 19 核心
   │                                            │
   │                                            ▼
   │                                         阶段 7  React 19 进阶 + Zustand 5
```

整条路线可以切成四段，段与段之间是"强依赖、不可逆"，段内部分能力是"弱依赖、可跳"：

| 分段 | 包含阶段 | 性质 | 跳过后果 |
| --- | --- | --- | --- |
| 地基 | 1 → 2 → 3 | 强依赖链，缺一不可 | 后面学 React 会一直在"哪里改 DOM"的旧习惯里打转 |
| 主线 | 4 → 5 → 6 → 7 | 4 是后续所有阶段的载体，5/6/7 构成现代前端主体 | 没有 4 跑不起来；没有 6/7 不成型 |
| 差异化 | 8 / 9 / 10 | 弱依赖，按目标取舍 | 只影响"动效 / 离线 / 桌面"三选一能力，不影响主线 |
| 收口 | 11 | 依赖前面全部 | 综合实战串联此前所有产出物 |

### 7.3 每个阶段的三行衔接说明

每段都按「上一步交付什么 → 本阶段新增什么能力 → 交接到哪一篇」三行写清，链接指向真实存在的文档。

- **阶段 1 · 现代 HTML + CSS 地基**
  - 上一步交付：阶段 0 已跑通 Node / pnpm / VS Code，能新建 `index.html` 并在浏览器打开。
  - 本阶段新增：用语义化标签 + 设计令牌 + Flex/Grid/容器查询，搭出"对人和机器都可读"且响应式的静态页面（产出物是一份"死"的页面，内容写死在 HTML 里）。
  - 交接：把这份静态页面交给 [阶段 2](./02-JavaScript深度补强与去jQuery化.md)，用 JavaScript 让它"活"起来。

- **阶段 2 · JavaScript 深度补强与去 jQuery 化**
  - 上一步交付：一份纯静态响应式页面，内容写死在 HTML 里。
  - 本阶段新增：建立**状态驱动**的心智模型（数据 → 渲染函数 → DOM），补齐 JS 语言内核（执行机制、闭包、异步、模块），并彻底替换 jQuery 命令式写法（产出物：无依赖 Todo + jQuery→原生迁移报告）。
  - 交接：把这份状态交给 [阶段 3](./03-TypeScript从类型思维到工程实践.md) 加上类型约束。

- **阶段 3 · TypeScript 系统**
  - 上一步交付：一个无依赖、状态驱动的 Todo 应用，但变量和函数都没有类型。
  - 本阶段新增：用 TypeScript 7 的类型系统给状态与函数加约束，引入结构化类型、泛型、`strict` 默认开启（产出物：TS 重写版 Todo + 类型体操练习）。
  - 交接：TS 工程配置交给 [阶段 4](./04-Vite8与现代前端工程化.md) 标准化。

- **阶段 4 · Vite 8 与工程化**
  - 上一步交付：一份 TS 源码，但还靠手工 `tsc` 跑、无构建/测试/规范。
  - 本阶段新增：用 Vite 8（Rolldown）+ pnpm + ESLint + Vitest 搭出可复用的标准化脚手架（产出物：脚手架模板，后续阶段都基于它）。
  - 交接：脚手架承载 [阶段 5~10](./05-TailwindCSS4与样式系统.md) 的全部代码。

- **阶段 5 · Tailwind CSS 4**
  - 上一步交付：一个能构建、能测试、有规范的空工程。
  - 本阶段新增：CSS-first 的 Tailwind CSS 4 主题系统——设计令牌、响应式/暗色、组件抽象（产出物：设计令牌体系 + 组件样式库）。
  - 交接：样式能力交给 [阶段 6](./06-React19核心.md) 的组件开发直接复用。

- **阶段 6 · React 19 核心**
  - 上一步交付：设计令牌体系 + 组件样式库，但还没有 React 组件。
  - 本阶段新增：React 19 组件、状态、事件、Hooks、表单、Suspense、React Compiler（产出物：React 版 Todo/看板应用）。
  - 交接：核心能力交给 [阶段 7](./07-React19进阶与状态管理.md) 做多页面与全局状态。

- **阶段 7 · React 19 进阶与 Zustand 5**
  - 上一步交付：单页 React 应用，状态分散在各组件里。
  - 本阶段新增：并发特性、Actions、路由、数据请求、Zustand 5 全局状态、性能优化（产出物：多页面应用，含路由 + 全局状态 + 请求层）。
  - 交接：UI 能力交给 [阶段 8 / 9 / 10](./08-Motion13交互动效.md) 叠加差异化能力。

- **阶段 8 · Motion 13 动效**
  - 上一步交付：功能完整的多页面应用，但交互"硬"、缺少过渡。
  - 本阶段新增：Motion 13 动画、手势、布局动画、列表过渡、无障碍动效（弱依赖，属渐进增强，可跳）。
  - 交接：回到 [阶段 11](./11-综合实战与持续进阶.md) 之前可先补 9 / 10。

- **阶段 9 · Dexie 4 本地持久化**
  - 上一步交付：前端应用，数据只存在于内存，刷新即丢。
  - 本阶段新增：Dexie 4 + IndexedDB 结构化本地存储、`useLiveQuery` 响应式查询、离线优先（弱依赖，按需）。
  - 交接：离线数据层交给 [阶段 10](./10-Electron43桌面应用.md) 做桌面端持久化。

- **阶段 10 · Electron 43 桌面应用**
  - 上一步交付：Web 应用，只能在浏览器里运行。
  - 本阶段新增：Electron 43 桌面应用——主/渲染进程、IPC、安全模型、原生能力、打包更新（Web-only 可整篇跳过）。
  - 交接：桌面能力在 [阶段 11](./11-综合实战与持续进阶.md) 收口。

- **阶段 11 · 综合实战与持续进阶**
  - 上一步交付：各阶段零散的产出物。
  - 本阶段新增：全栈串联、架构分层、测试、CI、发布（产出物：完整作品级项目）。
  - 交接：完成即具备独立开发现代前端应用的能力。

### 7.4 为什么这条顺序不能乱

前端的"先后顺序"不是教材编排，而是因果链——前面没建立的能力，后面一定会以 bug 的形式回来找你。

- **地基段（1 → 2 → 3）不能跳**：阶段 2 的状态驱动没建立，阶段 6 学 React 会一直在"选中哪个 DOM 改"的旧习惯里打转；阶段 3 的类型思维没建立，阶段 4 的 `tsconfig` 你只会复制粘贴、看不懂报错。这三篇是"慢就是快"，压缩它们后面要花双倍时间返工。
- **主线段（4 → 5 → 6 → 7）不能并行**：阶段 4 的脚手架是所有后续阶段的载体，没它阶段 5~10 的代码没地方跑；阶段 6 的 React 19 核心没建立，阶段 7 的路由 / 全局状态 / 性能你接不住。可以"5 和 6 同期起手"，但不能"跳过 6 直接学 7"。
- **差异化段（8 / 9 / 10）可以跳，但不能乱序**：它们都建立在阶段 7 的多页面应用之上——Motion 给现成的 UI 加动效、Dexie 给现成的应用加本地存储、Electron 把现成的 Web 应用搬进桌面。先有"能跑的应用"再叠加，而不是反过来。
- **收口段（11）必须在最后**：它串联的是前面全部产出物，缺任何一篇都会在项目里留下空洞，综合实战也收不口。

### 7.5 怎么用这张依赖图做周计划

依赖图不是给你"看懂就行"，而是每周开局用来决定"这周该推哪一篇"的工具：

- 你当前停在阶段 N，下周就推 N 的下一强依赖篇；差异化段（8/9/10）只有当你明确"要做动效 / 要离线 / 要桌面"时才排进计划。
- 如果某周时间突增（比如放假有 20h），优先把主线段（4~7）往前赶，不要在差异化段上堆时间——主线没成型，差异化加了也接不住。
- 卡在某篇超过两周，先确认它是不是"可跳"的差异化能力；若是主线，回到它的上承篇重做最靠前的必做题，多半是地基有洞。
- 每推完一篇，回到 7.3 把它对应的"三行衔接"勾掉，确认"上一步交付 → 本阶段新增 → 交接到哪"三件事都发生了，再开下一篇。

## 八、四条学习路径裁剪建议

路线图是"完整版"，但不同人起点和目标不同。下面四条裁剪路径都建立在「地基 1~3 不可砍」的前提下，只是对主线与差异化能力做取舍。

### 8.1 只看 Web、不看桌面端（约 23~26 周）

跳过 [阶段 10 · Electron 43](./10-Electron43桌面应用.md)（整篇都不需要）。阶段 9 · Dexie 4 如果你确认不做离线存储也可以跳过，但**建议保留**——它是理解"客户端结构化存储"的关键，且和桌面端无关。其余 1~9 + 11 全做。M1 / M2 / M4 都能正常验收，只是 M3 少了"桌面端运行"这一项。

### 8.2 时间只有 12 周的最小路径（压缩但不可再砍）

12 周是底线，砍任何地基都会反复返工。建议这样排：

| 周次 | 做的内容 | 取舍说明 |
| --- | --- | --- |
| 1~1.5 | 阶段 1（只核心布局 + 响应式） | 容器查询/设计令牌过一遍即可，不追求作品级 |
| 2~3.5 | 阶段 2（只状态驱动 + 去 jQuery） | 语言内核抓事件循环/闭包/异步三块，其余略读 |
| 4~5.5 | 阶段 3（只 `strict` + 工具类型） | 泛型与工程配置够用即可 |
| 6~6.5 | 阶段 4（只 Vite 脚手架） | 一把搭好，ESLint/Vitest 留到阶段 11 补 |
| 7~10 | 阶段 6（React 19 核心，必做） | 这是最小路径的"主心骨"，不可省 |
| 11~12 | 阶段 7（只路由 + Zustand 5） | 多页面 + 全局状态跑通即可 |

跳过 5（用 CSS Modules 替代 Tailwind）、8、9、10、11。阶段 11 的综合项目用阶段 7 的产出物直接扩，不单独开 4 周。最小路径的脚手架可直接用官方模板起手：

```bash
# 最小路径：用 Vite 官方 React + TS 模板起手，省去阶段 4 的逐项配置
pnpm create vite@latest my-app --template react-ts
cd my-app
pnpm install
pnpm dev
```

### 8.3 已有 React 经验的跳读路径

如果你已经写过 React，但 JS/CSS/工程化基础不牢，重点补"底座"而非"框架"：

- 阶段 1：补 CSS 现代特性，尤其容器查询、设计令牌、`@layer`、`:has()`——很多 React 开发者 CSS 停留在 5 年前。
- 阶段 2：补原生 JS 与去 jQuery，React 开发者常见的弱点是"框架包一切、原生不会写"。
- 阶段 3：补类型思维（结构化类型、泛型、可辨识联合），不要只当带类型的 JS。
- 阶段 4：补工程化（Vite 8 / Rolldown、pnpm、ESLint、Vitest）。
- 阶段 5：补 Tailwind CSS 4 的 CSS-first 写法（`@theme` / `@utility`），别照抄 v3 教程。
- 阶段 6 / 7：**快进**——只读 React 19.2 新增并做对照练习：`use` / `useActionState` / `useOptimistic` / `useEffectEvent` / `<Activity>` / React Compiler，确认你写的代码和旧 `useMemo` 习惯的差异。
- 阶段 8~11：按需。

### 8.4 要补工程化短板的路径

如果你框架会用、但"工程化一塌糊涂"（构建慢、没测试、没规范、不敢动 CI），聚焦这三篇：

- [阶段 4 · Vite 8 与工程化](./04-Vite8与现代前端工程化.md)：Vite 8 / Rolldown、pnpm、ESLint、Vitest、Git 规范一次标准化。
- [阶段 7 · React 19 进阶与状态管理](./07-React19进阶与状态管理.md)：性能优化与架构分层。
- [阶段 11 · 综合实战与持续进阶](./11-综合实战与持续进阶.md)：测试 / CI / 发布全链路。

前置只需 [阶段 6](./06-React19核心.md) 速通，地基 1~3 如果已熟可直接跳。

四条路径的共同底线：阶段 1~3（地基）一篇都不能砍；阶段 6（React 19 核心）在"做前端"的路径里也一篇都不能砍。其余按需取舍之后，用阶段 11 的产出物反向校验——能独立跑起来、能讲清每一行为什么这么写，就算走完了这条路径。如果你不确定自己该走哪条，先按完整版推进，遇到明显冗余（比如确认不做桌面端）再砍阶段 10，比一开始精算更稳。

## 九、每周节奏建议（按每周 10 小时）

路线图的"10 小时/周"是总预算，但**怎么分配**比"总量够不够"更重要。前端是手艺活，读文档和写代码的比例失调一定会翻车。建议把每周 10 小时拆成三类活动：这个比例是经过多期学员验证的中位数——读太多会变成"收藏家"，写太多会变成"只会抄"。如果你发现自己总在读，把比例往写倾斜；总在写却总报错，往读倾斜。

| 活动 | 每周时长 | 做什么 | 为什么 |
| --- | --- | --- | --- |
| 读文档 | 2.5h | 读本周阶段文档、列知识点清单、标出要验证的概念 | 先建立"为什么"，再写代码才不会抄错 |
| 写代码 | 6h | 最小 demo + 阶段项目推进 + 进阶题 | 肌肉记忆只靠手写，读一百遍不如写一遍 |
| 复盘 | 1.5h | 踩坑记录、自查清单勾选、写 commit、定下周计划 | 把"会了"固化成"能复述"，否则两周就忘 |

典型一周的时间表（ASCII，单位小时）：

```text
周一(1.0h)  读文档：列出本周知识点清单，标出要验证的 2~3 个概念
周二(1.0h)  写最小 demo：把周一的概念各跑一个 20 行样例
周三(1.5h)  写代码：阶段项目推进（功能实现）
周四(1.5h)  写代码：阶段项目推进（继续）
周五(1.0h)  复盘：踩坑记录 + 自查清单勾选 + 写 commit
周六(3.0h)  集中开发：阶段项目主要功能块
周日(2.0h)  进阶题 + 整理笔记 + 下周计划 + 提交周总结
合计 10h
```

三条纪律（与附录的"每周时间模板"一致，这里强调"节奏"）：

1. **每天写的代码都能跑起来**——不留"明天再修"的坏状态，坏状态会滚雪球。
2. **每周至少提交 5 次**，commit message 写清"为什么"而不是"改了什么"。
3. **每阶段结束写一份 README**：目标 / 收获 / 踩坑 / 数据（耗时、体积、性能）。

一个典型的每周 Git 节奏，照着养成习惯即可：

```bash
# 周五：把本周成果拆成有语义的提交
git add -p
git commit -m "feat(stage-02): 用事件委托重写列表点击，去掉 jQuery"

# 周日：统一 push + 写周报（周报直接进阶段目录的 README）
git push origin main
```

### 9.1 一个典型学习周的产出示例

以阶段 2（JavaScript 深度补强）为例，按上面的节奏推进，一周结束你手上应该多出这些具体东西（这就是"10 小时花得值"的标志）：

- 1 个 `event-loop.js` demo，能跑出"微任务先于宏任务"的输出，并讲清原因；
- 1 个 `debounce-throttle.js`，不查文档手写防抖与节流；
- 阶段项目推进：Todo 的"新增 / 筛选"两个功能跑通，且状态只有一个修改入口；
- 1 份 commit 记录（≥5 次），message 写的是"为什么"而不是"改了什么"；
- 阶段 README 里自查清单新增 2~3 个勾，并记下 1 条踩坑。

如果一周结束你只有"读了两章、没写出能跑的代码"，说明读/写比例失衡了——下周把读文档压到 1.5h，把省下的时间挪去写。再以阶段 6（React 19 核心）为例：一周应多出 1 个 `counter.jsx`、1 个用 `useActionState` 的表单，以及阶段项目里"新增待办"功能跑通。判断标准始终一样：**有可运行代码 + 有勾选的自查**。

### 9.2 读文档时记笔记的模板

很多人"读了很多但说不出"，原因是只读不记。给每个阶段准备一份 `NOTES.md`，按这个骨架记，周末复盘时直接能用：

```text
# 阶段 N 笔记
## 本周概念清单
- 概念 A：一句话定义 + 为什么需要
- 概念 B：...
## 踩坑
- 现象 / 原因 / 修法
## 自查勾选
- [x] 已会项 / [ ] 待补项
## 下周计划
- 三个具体目标
```

记的时候只写"定义 + 为什么"，不抄文档原文——能用自己的话写出来的，才是真会了。

## 十、常见中断与恢复策略

学路线最容易死的不是"学不会"，是"停了两个月不知道从哪捡起来"。下面是一套可执行的恢复流程，核心是**别从头读、先找回手感**。

1. **定位断点**：看最后一次 commit 停在哪个阶段，以及该阶段 README 里自查清单的勾选状态——那比"我记得学到哪了"可靠。
2. **重温热身（0.5~1 周）**：不要从头重读。直接重做断点所在阶段"实践练习"里最靠前的必做题，手感回来最快。
3. **跳过已熟的**：自查清单里已经打勾的项不必重做，把时间花在没打勾的。
4. **环境复活**：停两个月依赖大概率过期，重装并核对版本仍在 2026-09 基准。
5. **降低重启阻力**：把周目标从 10h 降到 4h，先恢复节奏再加码——断点后最忌"一上来就冲 10h 然后第三天弃"。
6. **重读衔接段**：把"断点之后第一篇"的「一、本阶段在学习路径中的位置」重读一遍（上承 / 本阶段 / 下接），它一句话就能把你拉回上下文。

```bash
# 1. 找到断点：看最近 10 条提交落在哪个阶段
git log --oneline -10

# 2. 复活环境：pnpm 锁定版本重装（依赖锁文件保证版本一致）
pnpm install

# 3. 核对工具链版本仍在 2026-09 基准
node -v              # >= 22.12
pnpm -v
pnpm exec tsc --version   # 应为 TypeScript 7
pnpm exec vite --version  # 应为 Vite 8

# 4. 跑一下断点阶段的产出物，确认还能跑起来再继续
pnpm dev
```

### 10.1 恢复检查表

把上面的六步固化成一张表，回来第一天照着勾：

| 步骤 | 动作 | 完成标志 |
| --- | --- | --- |
| 1 定位 | `git log` + 看阶段自查清单勾选 | 知道停在哪一篇、哪些已会 |
| 2 热身 | 重做该篇最靠前的必做题 | 手感回来，不再怕打开编辑器 |
| 3 复活 | `pnpm install` + 核对版本 | `pnpm dev` 能起、版本在 2026-09 基准 |
| 4 降阻 | 周目标先降到 4h | 连续三天都在写，没弃 |
| 5 接上下文 | 重读下一篇衔接段 | 能说出"上承 / 本阶段 / 下接" |

> 停两个月不等于归零。地基（阶段 1~3）是肌肉记忆，回来很快；差异化能力（8~10）即使忘光也不影响主线。重点是把"断点之后第一篇"接上，而不是把前面全重来一遍。

## 十一、常见疑问（FAQ）

- **Q：我已经会一点 React，还需要从阶段 1 开始吗？** 取决于"会一点"是哪种：如果 CSS 现代特性（容器查询、设计令牌、`:has()`）不熟、原生 JS 写不利索，阶段 1~3 仍值得过一遍。具体走第八节「已有 React 经验的跳读路径」，别全跳。
- **Q：每天只有 1 小时、凑不出 10 小时怎么办？** 拉长到 40+ 周也可以，但**每天都写一点**比"周末突击 10 小时"有效得多。前端记忆衰减快，断一天就得多花半小时找回手感。
- **Q：TypeScript 7 没有稳定编程式 API，lint 怎么办？** 见第四节「环境准备」里的兼容处理：学习阶段先用 `tsc --noEmit` 做类型检查，lint 用非类型感知规则，等 7.1 再补。
- **Q：公司项目用的版本和这里不一致（比如还是 React 18 / Vite 5）？** 概念通用，写法差异看官方迁移指南。本路线以 2026-09 基准为准，遇到冲突以官方文档为准。
- **Q：学完能独立做项目吗？** 能。里程碑 M4 要求一个"可展示、可安装、有测试、有 CI"的完整项目，那就是你的作品集筹码。
- **Q：阶段之间能不能合并成一篇长文？** 不建议。每阶段独立文档是为了"单独阅读、单独验收"，合并会丧失进度感，也难做阶段性自查。
- **Q：卡在某个阶段、进度停滞了怎么办？** 先按附录第四节「遇到卡住时的处理流程」走 30 分钟上限原则；仍卡就跳到下一阶段"能跑的最小部分"，很多概念会在后面自然贯通。
- **Q：需要买服务器 / 域名才能学吗？** 不需要。阶段 1~10 全在本地跑；阶段 11 的"发布"用静态托管或桌面安装包即可，不强制自有服务器。
