## 三、核心概念详解

### 3.1 作品级项目的选题与范围控制

**是什么**：选题（scope）指你决定做一个什么项目、以及它的功能边界。范围控制（scope control）是用 **MoSCoW 法**（Must / Should / Could / Won't）把功能分级，确保 4 周内交付一个**完整但不臃肿**的作品。

**为什么需要**：Java 程序员转到前端最容易犯的错是「一上来就想做个大而全的系统」，结果第 3 周还在搭脚手架，最后什么都半成品。作品级项目的评判标准是「**一个能跑通的核心链路**」，不是功能数量。

**怎么用**。推荐选题 **Lumen Kanban——离线优先的桌面看板**，它天然覆盖本路线全部技术点且难度可控：

```text
选题 A（推荐）：Lumen Kanban —— 离线优先的桌面看板
核心链路（Must，必须交付）：
  - 多工作区 / 多看板 / 多列 / 卡片（标题、描述、标签、优先级、截止日）
  - 拖拽排序、撤销重做（命令模式 + 操作栈）
  - 本地全文搜索、筛选（可保存为「智能视图」）
  - 离线优先：Dexie 4 为真源，断网可用，后台同步（MSW 或 mock server）
  - 桌面能力：无边框窗口、菜单、托盘、全局快捷键、文件导入导出、通知、自动更新

Should（锦上添花）：日历视图、统计面板、多主题、动效、无障碍
Could（有余力再做）：图谱视图、协同编辑
Won't（本期不做）：服务端多用户协同、移动端
```

两个备选：**选题 B 个人知识库（PKM）**——Markdown 编辑器 + 双链 + 本地检索 + 图谱，编辑器与图谱难度更高；**选题 C 接口调试工具**——本地请求录制 + 可视化 + 脚本断言，偏工具属性。推荐选 A，因为覆盖面最全、风险最低。

**坑在哪**：

- 跳过「Must 分级」直接开写 → 中期发现核心链路没时间做，交付一堆边角功能。
- 选题 B/C 的编辑器/图谱实现难度远超预期，4 周可能连核心链路都跑不通。新手优先 A。

### 3.2 架构分层：UI / 状态 / 数据 / 原生与目录组织

**是什么**：架构分层（layering）是把代码按「职责」切层——UI 层（组件与页面）、状态层（Zustand 5 管 UI 状态）、数据层（Dexie 4 管持久化）、原生层（Electron 主进程）。依赖方向**单向**，下层不反向引用上层。

**为什么需要**：没有分层的 Electron 项目，组件里直接写 `ipcRenderer`、直接 `bulkPut`、直接调系统 API，三个月后没人敢改。单向依赖让「改数据层不影响 UI 层」，测试也能各自孤立。

**怎么用**。目录结构（Electron 多进程 + 按业务域切片）：

```text
src/
├── main/                  # Electron 主进程（原生层）
│   ├── windows/           # 窗口的创建与生命周期
│   ├── ipc/               # handler：校验 → 调用 service → 返回 Result
│   ├── services/          # 文件、更新、托盘、菜单等原生服务
│   └── bootstrap.ts
├── preload/               # contextBridge 暴露白名单 API（原生层桥接）
├── shared/                # 两端共享：IPC 通道、DTO、Result 类型、常量
└── renderer/src/
    ├── app/               # 应用入口、路由、Provider 装配、错误边界
    ├── pages/             # 路由级页面（薄）
    ├── features/          # 按业务域切片（board / card / search / sync / settings）
    │   └── board/
    │       ├── components/    # 该域的 UI 组件
    │       ├── hooks/         # 该域的逻辑
    │       ├── store.ts       # Zustand slice（仅 UI 状态）
    │       ├── api.ts         # 数据访问（Dexie / IPC）
    │       └── types.ts
    ├── components/ui/     # 通用无业务组件（Button / Dialog / ...）
    ├── lib/               # 纯函数工具（date、id、不可变辅助）
    ├── motion/            # 动效令牌与共享变体
    ├── styles/            # Tailwind 入口 + @theme 令牌
    └── types/             # 全局类型
```

**依赖方向（单向，禁止反向引用）**：`pages → features → components/ui → lib`；`features` 之间**不互相 import**（需共享就上提到 `lib` 或用事件）。

至少写 5 篇 **ADR（Architecture Decision Record）**，每篇含「背景 → 备选 → 决策 → 后果」：

```markdown
# ADR-001：状态归属

背景：服务端数据、UI 状态、持久化三种「状态」混在一起，难以测试。
备选：① 全用 Redux；② 全用 Zustand；③ 服务端数据用 Query、UI 用 Zustand、持久化用 Dexie。
决策：选 ③。服务端数据用 React Query（本项目用 Dexie LiveQuery 等效），UI 瞬时状态用 Zustand 5，持久化用 Dexie 4。
后果：组件不直接碰数据库；UI 状态与业务数据解耦；测试可分别针对 store 与 db。
```

其余 ADR：数据层 Dexie vs SQLite vs JSON 取舍、IPC 契约为什么用共享类型 + zod、Tailwind 令牌分层与 `@apply` 边界、测试策略比例。

**坑在哪**：

- `features` 之间互相 `import` → 循环依赖，架构腐化；共享逻辑必须上提到 `lib`。
- 把持久化逻辑写进组件 → 组件无法单测，且数据来源失去唯一真源。

### 3.3 端到端串联：把阶段 1~10 整合进一个 feature

**是什么**：端到端串联（end-to-end wiring）指一个业务功能从「用户操作 → UI 状态 → 数据持久化 → 桌面原生能力」全链路打通。下面用一个「新增卡片」的 feature 演示阶段 6（React）+ 阶段 9（Dexie）+ 阶段 10（Electron IPC）怎么拼起来。

**为什么需要**：前面每个阶段是孤立练习，真实项目里它们是同一链路的不同层。能把它们串起来，才算「会做产品」，而不是「会做若干片段」。

**怎么用**。数据层（阶段 9 的 Dexie，阶段 10 的导入导出桥）：

```ts
// features/board/api.ts —— 数据访问层，组件不直接碰数据库
import { db } from '../../../data/db';
import type { CardRecord } from '../../../data/db';

export async function addCard(input: { boardId: string; title: string }): Promise<CardRecord> {
  const card: CardRecord = {
    id: crypto.randomUUID(),
    boardId: input.boardId,
    title: input.title,
    done: false,
    updatedAt: Date.now(),
  };
  await db.cards.put(card); // Dexie 写入即本地真源；useLiveQuery 会自动刷新 UI
  return card;
}
```

状态层（阶段 7 的 Zustand 5，只放 UI 瞬时状态，如「正在拖拽哪张」）：

```ts
// features/board/store.ts
import { create } from 'zustand';

interface BoardUiState {
  draggingId: string | null;
  setDragging: (id: string | null) => void;
}
export const useBoardUi = create<BoardUiState>((set) => ({
  draggingId: null,
  setDragging: (id) => set({ draggingId: id }),
}));
```

UI 层（阶段 6 的 React 组件 + 阶段 9 的 `useLiveQuery` 响应式读）：

```tsx
// features/board/components/Board.tsx
import { useLiveQuery } from 'dexie-react-hooks';
import { db } from '../../../data/db';
import { addCard } from '../api';
import { useBoardUi } from '../store';

export function Board({ boardId }: { boardId: string }) {
  const cards = useLiveQuery(() => db.cards.where('boardId').equals(boardId).toArray(), [boardId]);
  const setDragging = useBoardUi((s) => s.setDragging);
  return (
    <section>
      {cards?.map((c) => (
        <article key={c.id} draggable onDragStart={() => setDragging(c.id)}>
          {c.title}
        </article>
      ))}
      <button onClick={() => addCard({ boardId, title: '新卡片' })}>新增</button>
    </section>
  );
}
```

桌面能力（阶段 10 的 preload 白名单，导出走主进程 `fs`）：`window.api.exportFile(...)` 见阶段 10 的 3.7、3.9。四层通过 `api.ts` 串联，组件只认 `api`，不认数据库也不认 IPC 细节。

**坑在哪**：

- 组件里直接 `db.cards.put` 跳过 `api.ts` → 数据访问逻辑散落各处，日后接同步/埋点时改到崩溃。统一走 `api.ts`。
- 把持久化数据塞进 Zustand → Zustand 是 UI 状态，刷新就丢；持久化必须交给 Dexie，Zustand 只放瞬时 UI 状态。

### 3.4 测试金字塔：Vitest 单测 + 组件测试 + Playwright E2E

**是什么**：测试金字塔（test pyramid）指按「数量与成本」分层——底层是大量**单元测试**（Vitest，测纯函数 / store / Dexie 逻辑），中层是**组件测试**（@testing-library/react，测用户行为），顶层是少量**E2E**（Playwright，测关键路径）。层数越往上越慢越贵，所以数量越少。

**为什么需要**：只写 E2E → 跑一次十分钟、一个改动能红一大片，没法快速定位；只写单测 → 各函数都对但拼起来崩。金字塔让「逻辑正确性」用便宜的单测覆盖，「用户真的能用」用少量 E2E 兜底。

**怎么用**。单元测试（用 `fake-indexeddb` 模拟 IndexedDB）：

```ts
// features/board/api.test.ts —— Vitest
import { describe, it, expect, beforeEach } from 'vitest';
import 'fake-indexeddb/auto';
import { db } from '../../../data/db';
import { addCard } from '../api';

beforeEach(async () => { await db.cards.clear(); });

describe('addCard', () => {
  it('写入后能被按 boardId 查到', async () => {
    const card = await addCard({ boardId: 'b1', title: '买菜' });
    const list = await db.cards.where('boardId').equals('b1').toArray();
    expect(list).toHaveLength(1);
    expect(list[0].id).toBe(card.id);
  });
});
```

组件测试（测用户可观察行为，不测内部 state）：

```tsx
// features/board/components/Board.test.tsx
import { render, screen, fireEvent } from '@testing-library/react';
import { Board } from './Board';

it('点新增按钮会出现一张卡片', () => {
  render(<Board boardId="b1" />);
  expect(screen.queryByText('买菜')).toBeNull();
  fireEvent.click(screen.getByText('新增'));
  expect(await screen.findByText('新卡片')).toBeInTheDocument();
});
```

E2E（只覆盖 5~8 条关键路径）：

```ts
// e2e/kanban.spec.ts —— Playwright
import { test, expect } from '@playwright/test';

test('启动 → 新建看板 → 加卡片 → 搜索 → 导出 → 重开验证持久化', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: '新建看板' }).click();
  await page.getByPlaceholder('卡片标题').fill('周报');
  await page.getByRole('button', { name: '新增' }).click();
  await expect(page.getByText('周报')).toBeVisible();
  // 重启应用，验证 Dexie 持久化还在
  await page.reload();
  await expect(page.getByText('周报')).toBeVisible();
});
```

**坑在哪**：

- 单测断言内部 state（如 `expect(store.getState().x)`）→ 重构即崩；应测**用户可观察行为**。
- E2E 覆盖所有路径 → 维护成本爆炸；只覆盖核心链路（建议 5~8 条）。

### 3.5 CI/CD：GitHub Actions 门禁与三平台发布

**是什么**：CI/CD（Continuous Integration / Continuous Delivery）是「提交即自动跑检查、合并即自动构建发布」。GitHub Actions 用 YAML 描述流水线：PR 时 `install → lint → typecheck → unit → build → e2e → 上传产物`；打 tag 时三平台矩阵构建 + 发 draft release。

**为什么需要**：本地「我电脑上能跑」不等于「别人能跑、CI 能跑」。门禁把类型错误、lint 错误、测试失败挡在合并前；三平台构建保证 Windows / macOS / Linux 都能出包，而不是你手测一个平台。

**怎么用**：

```yaml
# .github/workflows/ci.yml —— PR 门禁
name: CI
on: [pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint                 # ESLint
      - run: pnpm typecheck            # tsc --noEmit
      - run: pnpm test -- --coverage   # Vitest，覆盖率门禁
      - run: pnpm build                # Vite 8 构建
      - run: pnpm test:e2e             # Playwright
```

```yaml
# .github/workflows/release.yml —— 三平台构建（节选）
strategy:
  matrix: { os: [macos-latest, windows-latest, ubuntu-latest] }
steps:
  - run: pnpm install --frozen-lockfile
  - run: pnpm exec electron-forge make   # 产出当前平台安装包
  - uses: actions/upload-artifact@v4
    with: { path: out/make/** }           # 上传产物供发布步骤收集
```

本地提交前用 Husky 串一遍轻量检查：

```jsonc
// package.json
{
  "scripts": {
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:e2e": "playwright test",
    "build": "vite build"
  },
  "husky": {
    "hooks": {
      "pre-commit": "lint-staged" // prettier + eslint + tsc 只跑改动文件
    }
  }
}
```

**坑在哪**：

- CI 里漏跑 `tsc --noEmit` → 类型错误溜进主干，本地 ESLint 没覆盖到类型。
- 打包后才第一次跑生产构建 → 应**每周至少打一次包**，别等发版前才发现构建挂了。

### 3.6 性能预算与监控：Core Web Vitals 与包体积门禁

**是什么**：性能预算（performance budget）是给关键指标设「红线」，超标就 CI 失败。**Core Web Vitals** 是 Google 的三项用户体验指标：LCP（最大内容绘制）、INP（交互到下次绘制）、CLS（累计布局偏移）；包体积门禁则限制首屏 JS 的 gzip 大小。

**为什么需要**：「感觉有点卡」没法进 CI 断言，必须量化。预算把性能变成可回归测试的工程指标——某次提交让首屏 JS 涨了 80KB，CI 直接红，逼你当场处理而不是累积到上线。

**怎么用**。在 Vite 配置里用 `rollup-plugin-visualizer` 或 Vite 内置报告盯体积：

```ts
// vite.config.ts —— 构建后输出体积报告，CI 里断言首屏 gzip ≤ 200KB
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [
    react(),
    visualizer({ gzipSize: true, filename: 'dist/stats.html' }),
  ],
  build: {
    rollupOptions: {
      output: {
        // 把体积大的依赖（如 dexie、react）拆成独立 chunk，便于缓存与排查
        manualChunks: { vendor: ['react', 'react-dom'], data: ['dexie'] },
      },
    },
  },
});
```

```ts
// 渲染进程里量 Core Web Vitals（用 web-vitals 库上报到可观测系统）
import { onLCP, onINP, onCLS } from 'web-vitals';
onLCP((m) => report('lcp', m.value)); // 目标 ≤ 2.5s
onINP((m) => report('inp', m.value)); // 目标 ≤ 200ms
onCLS((m) => report('cls', m.value)); // 目标 ≤ 0.1
```

桌面冷启动预算（与阶段 10 的 3.12 协同）：`app.getAppMetrics()` 量启动耗时，目标是 `ready-to-show` ≤ 2s。

**坑在哪**：

- 只测「我本机快」不进 CI → 预算必须写成自动化断言，否则一定随时间腐化。
- 把 Dexie / React 打进主 bundle → 首屏体积失控；用 `manualChunks` 拆 vendor。

### 3.7 可观测性与错误上报

**是什么**：可观测性（observability）指「应用出问题时你能知道、能定位」。前端侧包括：错误上报（未捕获异常、Promise rejection、渲染错误边界）、日志（electron-log）、性能埋点（3.6）、崩溃上报（crashReporter）。

**为什么需要**：桌面应用跑在用户机器上，你不可能 SSH 进去看控制台。没有上报，用户报「偶尔白屏」你只能盲猜。可观测性把「偶发 bug」变成「有堆栈可查的事件」。

**怎么用**。渲染进程错误用错误边界 + 上报 SDK（如 Sentry）兜住：

```tsx
// app/ErrorBoundary.tsx —— React 错误边界，兜住渲染期异常
import { Component, type ErrorInfo, type ReactNode } from 'react';

export class ErrorBoundary extends Component<{ children: ReactNode }, { error: Error | null }> {
  state = { error: null as Error | null };
  static getDerivedStateFromError(error: Error) { return { error }; }
  componentDidCatch(error: Error, info: ErrorInfo) {
    // 上报到 Sentry / 自建收集端（注意脱敏，别带用户数据）
    reportError(error, info.componentStack);
  }
  render() { return this.state.error ? <h1>出错了，已记录</h1> : this.props.children; }
}
```

主进程崩溃与未捕获异常（阶段 10 的 3.13 延伸）：

```ts
// main/bootstrap.ts
import { crashReporter } from 'electron';
crashReporter.start({ submitURL: '', uploadToServer: false }); // 本地留堆栈
process.on('uncaughtException', (err) => reportError(err));    // 主进程兜底
```

**坑在哪**：

- 上报带用户敏感数据 → 隐私违规；上报前脱敏，且只在用户同意时开启。
- 只在渲染进程兜、忘了主进程 `uncaughtException` → 主进程崩了整窗消失，无任何痕迹。

### 3.8 文档与 README 写作

**是什么**：README 是项目的门面，要让一个陌生人 5 分钟内跑起来。好的 README 含：一句话定位、功能列表、技术栈、安装运行步骤、快捷键/功能说明、目录结构、测试与构建命令、已知限制。

**为什么需要**：作品级项目的读者是面试官/协作者/未来的你。仓库再好，README 写不清楚等于「没交付」——别人连怎么跑都不知道。文档能力本身也是工程素养的一部分。

**怎么用**（README 骨架，照着填）：

```markdown
# Lumen Kanban

离线优先的桌面看板应用（Electron 43 + React 19 + Dexie 4）。

## 功能
- 多看板 / 多列 / 卡片，拖拽排序、撤销重做
- 本地全文搜索与智能视图筛选
- 离线优先：断网可用，Dexie 为真源
- 桌面能力：无边框窗口、菜单、托盘、全局快捷键、导入导出、通知、自动更新

## 技术栈
React 19.2 · TypeScript 7 · Vite 8 · Tailwind CSS 4.3 · Zustand 5 · Dexie 4 · Electron 43

## 快速开始
\`\`\`bash
pnpm install
pnpm dev          # 开发模式（Vite HMR + Electron）
pnpm test         # 跑 Vitest 单测 + 组件测试
pnpm test:e2e     # Playwright E2E
pnpm exec electron-forge make   # 打当前平台安装包
\`\`\`

## 架构
主进程 / 渲染进程 / preload 三层分离；渲染进程内 UI → 状态(Zustand) → 数据(Dexie) 单向依赖。
详见 docs/adr/ 下的 5 篇 ADR。
```

**坑在哪**：

- README 只写「npm install && npm start」→ 缺 Node 版本、缺平台要求、缺测试命令，陌生人跑不通。把「我踩过的坑」写进 README 的 Troubleshooting。
- 文档与代码脱节（README 说有功能代码没实现）→ 面试一问就露馅；文档随代码一起 PR。

### 3.9 进阶方向地图

**是什么**：进阶方向地图（learning roadmap）是学完本路线后的「下一步去哪」。本路线覆盖的是现代前端主栈，但还有服务端、跨端、底层等多个方向值得按需深入。

**为什么需要**：前端版本迭代极快（本路线里 TS 7、React 19、Vite 8、Tailwind 4 都是架构级变更），学完不等于终点。有地图才不会「不知道学什么」或「被过时教程带偏」。

**怎么用**（按需取用，不要求全学）：

| 方向 | 内容 | 何时学 |
| --- | --- | --- |
| 类型系统深造 | 类型体操进阶、编译器 API（TS 7.1 后开放）、为库写类型 | 想做基础设施/库时 |
| React 服务端生态 | Server Components、Server Functions、Next.js / React Router 框架模式 | 做 Web 产品且需 SSR/SEO 时 |
| 测试与质量 | 测试策略设计、契约测试、可视化回归（Playwright 截图对比） | 团队规模变大时 |
| 性能工程 | Core Web Vitals 深挖、性能剖析、渲染管线、内存泄漏定位 | 遇到真实性能问题时 |
| 架构与设计系统 | Monorepo（pnpm + turbo）、组件库工程化、设计令牌跨平台 | 负责多个前端项目时 |
| 原生与跨端 | Rust/N-API 原生模块、Tauri 对比、移动端（React Native） | 桌面端有原生性能瓶颈时 |
| 后端补齐 | Node/Bun 服务端、API 设计、认证授权、数据库 | 需独立交付完整产品时 |
| 工程效能 | CI/CD 优化、构建性能、依赖治理、发布流程 | 团队提效需求明确时 |

**坑在哪**：

- 一上来贪多全学 → 样样浅；按「当前项目缺什么学什么」深入，比广撒网有效。
- 只看框架不补底层（HTTP、浏览器原理、构建工具链）→ 遇到非典型问题就卡死。

### 3.10 如何持续学习而不被版本迭代甩下

**是什么**：持续学习的方法论——建立「一手信息源 + 定期版本体检 + 复盘沉淀」的节奏，让版本迭代追着你走而不是甩下你。前端过期极快，这套习惯比多学一个框架重要。

**为什么需要**：二手文章通常滞后官方发布 3~6 个月，而本路线多个版本（TS 7 编译期提速 8~12 倍、Vite 8 换 Rolldown、React Compiler 自动记忆化）都是「架构级变更」，照旧教程会写出已被淘汰的代码。

**怎么用**（可落地的三点习惯）：

```bash
# 1) 版本体检脚本（每季度跑一次，比对 package.json 与实际最新 + 安全公告）
pnpm outdated            # 列出可升级的依赖及最新版本
pnpm audit               # 安全公告
# 2) 订阅一手源：TypeScript / React / Vite / Electron 官方博客与 CHANGELOG
# 3) 每完成一个项目写一篇复盘（技术决策 + 踩坑 + 数据佐证）
```

验证方法（判定某说法是否过时）：优先级 **官方文档 > 官方博客/Changelog > 近一年文章 > 其他**。遇到与 README 版本矩阵冲突的说法，以官方文档为准，并回来修正 `track.json` / README。

**坑在哪**：

- 用「2023 年博客」学 TS 7 / Vite 8 → 配置写法已废弃（如 `rollupOptions` 被 Rolldown 兼容层接管、Tailwind v3 的 `tailwind.config.js` 写法过时）。
- 只收藏不写 → 看完即忘；每阶段产出的代码 + 复盘才是真资产。

## 四、与 Java 经验的对照

| Java 世界的经验 | 前端的对应关系 | 注意差异 |
| --- | --- | --- |
| Maven / Gradle 多模块 | pnpm workspace / Monorepo（turbo） | 前端「模块」是 npm 包，不是 Maven 坐标；依赖用 semver 而非坐标锁版本 |
| JUnit / TestNG | Vitest（单测 + 组件测试） | 测试运行在 Node/jsdom 或真实浏览器，不是 JVM |
| Selenium / Cucumber E2E | Playwright E2E | 同样跑真实浏览器，但 API 更现代；只覆盖关键路径 |
| Spring Boot 应用 | Vite + React 应用（数据层 Dexie） | 没有「应用服务器」，产物是静态资源 + Electron 壳 |
| Jenkins / GitLab CI | GitHub Actions | YAML 描述流水线；矩阵构建跨平台更直白 |
| Log4j / SLF4J | `electron-log` + Sentry 上报 | 日志落 `userData`；前端错误需错误边界 + 进程兜底双保险 |
| JVM 性能（JFR / VisualVM） | Core Web Vitals + Performance 面板 + `app.getAppMetrics()` | 指标是 LCP/INP/CLS 与进程内存，不是 GC 停顿 |
| Micrometer / Prometheus 监控 | 前端可观测性（Sentry / 自建收集） | 用户端埋点，注意隐私脱敏 |
| jar / war 打包 | Electron 安装包（Forge/builder） | 三平台产物不同，需分别签名 |
| `javadoc` | README / 组件文档 / ADR | 文档即交付物，陌生人 5 分钟跑起来才算合格 |

## 五、实践练习

### 练习 1（必做）：脚手架与架构落地（6 小时）

**目标**：把阶段 1~10 的能力装进统一项目骨架，落实单向依赖与 5 篇 ADR。

**步骤**：

1. 初始化仓库：Vite 8 + TS 7 + React 19.2 + Tailwind 4.3 + Zustand 5 + Dexie 4 + Electron 43。
2. 按 3.2 的目录结构建 `main / preload / shared / renderer`，落实 `pages → features → components/ui → lib` 单向依赖。
3. 写 5 篇 ADR（状态归属、数据层、IPC 契约、Tailwind 令牌、测试策略）。
4. 把阶段 9 的 Dexie 层、阶段 10 的 IPC 与窗口接入。

**验收点**：`tsc --noEmit` 通过；`features` 间无循环依赖（用 `madge` 或 `ts-unused-exports` 检查）；5 篇 ADR 内容含「背景→备选→决策→后果」。

### 练习 2（必做）：核心链路端到端串联（10 小时）

**目标**：实现「看板 CRUD + 拖拽 + 搜索筛选 + 导入导出 + 桌面能力」完整跑通（对应 3.3）。

**步骤**：

1. 数据层：Dexie schema v1 + 迁移 + 导入导出（走主进程 `fs`）。
2. 看板 CRUD 与拖拽（阶段 8 的 Motion 13 做拖拽动画）。

5. 断网验证：关网后核心功能全部可用，重连后数据一致。

**验收点**：启动 → 新建看板 → 加卡片 → 拖拽排序 → 搜索 → 导出文件 → 重开应用数据仍在；断网时上述流程不报错。

### 练习 3（必做）：质量保障体系（8 小时）

**目标**：搭起测试金字塔 + 门禁 + 覆盖率阈值（对应 3.4、3.5）。

**步骤**：

1. Vitest 单测：`api.ts`、store、Dexie 逻辑（`fake-indexeddb`），覆盖率 ≥ 70%。
2. 组件测试：新增卡片、筛选、拖拽结果（用户行为路径）。
3. Playwright E2E：5~8 条关键路径（启动→新建→加卡→搜索→导出→重开验证）。
4. 可访问性：`axe` 自动扫描 + 键盘走查，无 serious 以上问题。
5. CI：GitHub Actions 跑 `lint → typecheck → test → build → e2e`，上传产物。

**验收点**：CI 全绿；单测覆盖率 ≥ 70%；E2E 覆盖 ≥ 5 条关键路径；`axe` 无 serious。

### 练习 4（必做）：发布工程（8 小时）

**目标**：三平台构建 + 签名 + 自动更新 + 发布页（对应 3.5、3.6）。

**步骤**：

1. Electron Forge / builder 打三平台安装包，配图标、应用 ID、协议。
2. 代码签名（Windows Authenticode / macOS Developer ID + notarization）。
3. 接入 `electron-updater`，本地静态服务器验证「检测→下载→安装重启」闭环。
4. 性能预算：首屏 JS ≤ 200KB(gzip)、INP ≤ 200ms、冷启动 ≤ 2s，写进 CI 断言。
5. 发布页：截图、功能说明、安装指引、更新日志。

**验收点**：三平台产物可下载安装；自动更新闭环验证一次；性能预算有 CI 断言；发布页 5 分钟能看懂怎么用。

### 练习 5（进阶）：可观测与文档（4 小时）

## 六、常见坑与自查清单

### 高频坑

- 一上来就写代码，跳过数据模型设计 → 中期大改 schema。
- `features` 之间互相 `import` → 循环依赖，架构腐化。
- 测试只测实现细节（断言内部 state）→ 重构即崩；应测用户可观察行为。
- E2E 覆盖所有路径 → 维护成本爆炸；只覆盖 5~8 条关键路径。
- CI 里没跑 `tsc --noEmit` → 类型错误溜进主干。
- 打包后才第一次跑生产构建 → 应每周至少打一次包。
- 签名/公证流程留到最后 → 预留 3~5 天处理证书问题。
- 忽视卸载与升级的向后兼容 → 老用户数据丢失（Dexie 迁移必须覆盖 v1→v2）。
- 把持久化数据塞进 Zustand → 刷新即丢；持久化交给 Dexie。
- 文档与代码脱节 → README 写的功能代码没实现，面试露馅。

### 结项自查清单（对应 README 里程碑 M4，可执行的验收清单）

逐条确认，全部打勾才算完成阶段 11：

- [ ] 应用可安装、可运行、可卸载，跨重启数据不丢（Dexie 持久化验证）。
- [ ] 断网状态下核心功能（增删改、搜索、筛选）全部可用。
- [ ] 全部核心操作可通过键盘完成，`axe` 无 serious 以上问题。
- [ ] 单测覆盖率 ≥ 70%，E2E 覆盖 ≥ 5 条关键路径，CI 全绿。
- [ ] 三平台产物可下载，自动更新验证过一次完整流程。
- [ ] 性能预算达标：首屏 JS ≤ 200KB(gzip)、INP ≤ 200ms、冷启动 ≤ 2s。
- [ ] 5 篇 ADR + 一篇技术复盘（做对/做错/下次怎么改，含数据）。
- [ ] README 能让陌生人在 5 分钟内跑起来（含 Node 版本与测试命令）。
- [ ] 错误边界 + 主进程兜底 + 崩溃上报已接入，主动报错能收到。
- [ ] 从阶段 1~10 的能力均在项目里有具体落点（UI/状态/数据/原生四层齐全）。
