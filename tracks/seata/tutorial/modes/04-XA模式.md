# XA 模式：两阶段提交

XA 是四种模式里最「传统」的。

它不让 Seata 生成 undo log，也不要求业务写 try/confirm/cancel。它把两阶段交给数据库的 XA 协议：一阶段 prepare，二阶段由数据库 commit 或 rollback。Seata 只负责在合适的时候告诉 RM「该 prepare 了」「该 commit 了」。

代价也很传统：行锁从 prepare 一直持有到二阶段结束，数据在 commit 之前不可见。

---

## 一、XA 在 Seata 里的位置

XA 分支的 `resourceId` 是数据源，不是 `actionName`。它的 RM 是 `ResourceManagerXA`，二阶段动作是 `xaResource.commit/rollback`，不是 undo 反向 SQL。

一个 XA 连接的生命周期：

```text
DataSourceProxyXA.getConnection()                 // :92
  → ConnectionProxyXA
    → setAutoCommit(false)                        // :170
      → branchRegister(XA)                        // :196
      → XA START(TMNOFLAGS)
    → 业务 SQL
    → close()                                     // :323
      → XA END(TMSUCCESS)
      → XA PREPARE
    → TC BranchCommit / BranchRollback
      → xaCommit / xaRollback
```

`ConnectionProxyXA.init()`（`:90`）要求物理连接的初始 `autoCommit=true`。如果连接池交给 Seata 的连接已经是 `autoCommit=false`，会直接抛 `IllegalStateException`。这是 XA 接入最常见的配置坑。

---

## 二、一阶段：注册、XA START、prepare

XA 的分支在 `setAutoCommit(false)` 时注册。这个时点不是随便选的：XA 需要 branchId 来构造 XA-Xid，而 branchId 是 TC 分配的。

`setAutoCommit(false)` 的顺序：

```text
1. branchRegister(XA, resourceId, xid)           // :196
2. XAXid = xid + branchId
3. xaResource.start(xaXid, TMNOFLAGS)            // :198
4. 业务 SQL
```

业务方法结束时，连接关闭，`close()` 里做两件事：

```text
close()
  → xaResource.end(xaXid, TMSUCCESS)             // XA END
  → xaResource.prepare(xaXid)                    // XA PREPARE
```

prepare 成功，数据已经写好但不可见，行锁由数据库持有。prepare 返回 `XA_RDONLY` 时，上报 `PhaseOne_RDONLY`；prepare 失败时，回滚并上报 `PhaseOne_PrepareFailed`。

这里有一个反直觉的点：**XA 的 prepare 成功，没有单独的 `PhaseOne_Done` 上报。** 代码里 XA 路径只上报 `PhaseOne_RDONLY` 和 `PhaseOne_PrepareFailed`，正常 prepare 完成后分支状态仍停在 `Registered`。TC 不会因此卡住，因为 XA 分支不能异步提交，全局提交时一定会发 `BranchCommitRequest`，由 RM 执行 XA commit。

---

## 三、二阶段：TC 驱动数据库提交

全局提交时，TC 给 XA 分支发 `BranchCommitRequest`。RM 侧 `ResourceManagerXA.finishBranch(true, ...)` 拿到 XA 连接，执行：

```java
xaResource.commit(xaXid, false);
```

`ConnectionProxyXA.commit()` 本身是空实现，只做状态校验；真正的 commit 发生在 `xaCommit()` 里。回滚同理，`xaRollback()` 先 `XA END(TMFAIL)`，再 `xaResource.rollback()`。

XA 的可见性由数据库保证：prepare 之后数据不可见，XA commit 之后才可见。这也是 XA 和 AT 最大的差别：AT 一阶段本地提交后数据就可见，XA 要等到二阶段。

XA 的失败处理有一套专门的状态：`XAER_NOTA` 表示数据库不认识这个 XA 分支（可能已经提交或回滚），TC 会把它当成可重试的特殊情况，而不是直接判失败。这个细节在跨库、跨资源管理器切换时很重要。

---

## 四、XA 的锁与可见性

XA 没有 TC 全局锁。`XACore` 没有覆写 `branchSessionLock`，全局锁只在 AT 里存在。

XA 的隔离完全靠数据库的 XA 行锁：

- `XA START` 之后，数据库开始持有行锁；
- `XA END` + `XA PREPARE` 之后，锁还在；
- `XA COMMIT` / `XA ROLLBACK` 之后，锁释放。

所以 XA 的锁持有时间比 AT 长。AT 在本地 commit 后就释放数据库行锁，只靠 TC 全局锁挡 Seata 写；XA 要一直锁到二阶段结束。

这也意味着 XA 不适合「长事务 + 高并发写同一行」的场景。锁等待会直接反映到业务延迟上。

---

## 五、XA 的失败面

**prepare 失败**：回滚 XA 分支，上报 `PhaseOne_PrepareFailed`，TC 走全局回滚。

**prepare 成功但 commit 失败**：数据库里留下 prepared 事务，锁不释放。TC 会重试 commit；如果一直失败，需要 DBA 介入清理 prepared 分支。

**XAER_NOTA**：数据库不认识这个 XA-Xid，可能是之前已经 commit/rollback，或者连接/资源管理器切换导致。TC 把它标成可重试的特殊状态，继续尝试。

**连接池把 autoCommit 改了**：`ConnectionProxyXA.init()` 直接抛异常。上层 `@Transactional`、连接池配置、代理顺序都可能提前把连接改成手动提交。

---

## 六、XA 和 AT 怎么选

| 维度 | XA | AT |
| --- | --- | --- |
| 回滚方式 | 数据库 XA rollback | undo log 反向 SQL |
| 数据可见性 | XA commit 后 | 本地提交后 |
| 锁 | 数据库 XA 行锁，持有到二阶段 | 本地行锁 + TC 全局锁 |
| 业务改造 | 几乎不改 | 几乎不改 |
| 数据库要求 | 支持 XA，连接池配置正确 | 有主键、SQL 可解析、建 undo_log |
| 典型问题 | prepared 事务、长锁、XAER_NOTA | 脏写、无主键、解析失败 |

如果业务不能接受中间态可见，XA 是更直接的选择；如果能接受，AT 的锁持有时间更短、生态更成熟。TCC 适合不能靠反向 SQL 还原的资源，Saga 适合长流程。

---

## 七、踩坑清单

- 连接池初始 `autoCommit=false`：`ConnectionProxyXA.init()` 直接抛异常。
- 以为 XA 的 prepare 成功会上报 `PhaseOne_Done`：代码里没有这个上报。
- 以为 XA 有 TC 全局锁：XA 只有数据库 XA 行锁。
- 用 XA 跑长事务：行锁持有到二阶段，锁等待会拖垮并发。
- prepare 成功后 commit 一直失败：数据库里留下 prepared 分支，必须人工清理。
- 把 XAER_NOTA 当永久失败：它可能是可重试的，要看 TC 的重试策略。
- XA 连接和普通连接混用同一个数据源：代理模式要选对。
