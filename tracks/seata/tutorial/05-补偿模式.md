# TCC、Saga、XA：三种把回滚交给别人的方式

优惠券服务用了 TCC。

全局事务回滚时，`cancel` 先到了；过了一会儿，`try` 才执行完。`cancel` 把券从「已核销」改回「未使用」，`try` 又把券锁成了「冻结」。全局事务已经结束，这张券却卡在冻结状态，谁也动不了。

开发查了半天，说 cancel 和 try 都加了判断，怎么会这样。问题不在判断，在于顺序：**TCC 默认不处理「cancel 比 try 先到」这种情况。** 框架只负责在二阶段调你的方法，方法内部怎么保证幂等、空回滚、反悬挂，是业务自己的事。

Seata 提供了三种「把回滚交给别人」的方式：TCC 交给业务方法，Saga 交给补偿链，XA 交给数据库。它们解决的是同一类问题，但把责任放在了完全不同的位置。

---

## 一、三条路，三种责任划分

先看一张总表。后面每一节都在解释这张表里的一行。

| 模式 | 谁持有锁 | 一阶段结束时数据可见吗 | 二阶段回滚由谁执行 | TC 在其中的角色 |
| --- | --- | --- | --- | --- |
| AT | TC 全局锁 + 本地数据库行锁 | 可见 | RM 用 undo log 生成反向 SQL | 协调分支、驱动提交/回滚 |
| TCC | 业务自己预留资源；框架没有全局锁 | 由 try 的实现决定 | 业务 `cancel` 方法 | 协调分支、调 confirm/cancel |
| Saga | 无框架锁；每个本地事务各自持锁 | 每个本地事务提交后可见 | Saga 引擎逆序调用补偿服务 | 只管全局生命周期，commit 可能是继续 forward |
| XA | 数据库 XA 行锁 | 不可见，直到二阶段 XA commit | 数据库执行 XA rollback | 协调分支、驱动 XA commit/rollback |

![图 1：TCC、Saga、XA 把回滚交给谁](../assets/05-三种补偿模式.svg)

先记住一个判断：**AT 和 XA 的回滚是「数据层」的，TCC 和 Saga 的回滚是「业务层」的。** 数据层回滚有数据库的锁和日志兜底，业务层回滚只能靠接口设计。

## 二、TCC：把两阶段写进业务接口

TCC 的三个方法，名字已经说明了职责：

```java
@TwoPhaseBusinessAction(name = "couponAction", commitMethod = "confirm", rollbackMethod = "cancel")
public boolean try(BusinessActionContext ctx, Long couponId) {
    // 预留资源：把券从 AVAILABLE 改成 FROZEN
}

public boolean confirm(BusinessActionContext ctx) {
    // 确认：把券从 FROZEN 改成 USED
}

public boolean cancel(BusinessActionContext ctx) {
    // 撤销：把券从 FROZEN 改回 AVAILABLE
}
```

### 2.1 分支在 try 之前就注册

TCC 的拦截器只看一眼当前上下文：不在全局事务里，或者当前是 Saga 分支，就直接放行。否则它会绑定 TCC 分支类型，进入 `ActionInterceptorHandler`。

真正的分支注册发生在业务 try 执行之前：

```text
TccActionInterceptorHandler.doInvoke()
  → ActionInterceptorHandler.proceed()
    → doTxActionLogStore()           // 向 TC 注册 TCC 分支
      → DefaultResourceManager.branchRegister(TCC, actionName, ...)
    → 执行业务 try
```

这个顺序和 AT 相反。AT 是先把 SQL 做完、本地提交前才注册；TCC 是先注册分支，再执行 try。因为 TCC 的二阶段没有 undo log 可查，TC 必须先知道这个分支存在，confirm/cancel 才有对象。

注册用的 `resourceId` 不是数据源，而是 `actionName`。同一个应用里，`actionName` 必须唯一；两个不同的 bean 用了同一个名字，启动时会直接报错。

### 2.2 confirm/cancel 是本地方法调用

TC 发来 `BranchCommitRequest` 后，RM 侧 `TCCResourceManager` 从 `TCCResource` 里拿出 `targetBean` 和 `commitMethod`，反射调用：

```java
ret = commitMethod.invoke(targetTCCBean, args);
```

它不会通过 RPC 再调一次业务服务。如果这个 bean 本身是 Dubbo 引用，那反射调用会走到远程；如果它是本地 Spring bean，confirm 就在当前进程执行。**TCC 的「二阶段」不是一次网络协调，而是一次方法调用。**

这也意味着 confirm/cancel 的失败处理很直接：方法返回 `false` 或抛异常，`TCCResourceManager` 返回 `PhaseTwo_CommitFailed_Retryable` 或 `PhaseTwo_RollbackFailed_Retryable`，TC 按重试策略再来一遍。

### 2.3 默认不处理幂等、空回滚和悬挂

`@TwoPhaseBusinessAction` 的 `useTCCFence` 默认是 `false`。不开 fence 时，`TCCResourceManager` 直接反射调用 cancel，不查任何状态表。

于是三种经典问题都要业务自己处理：

**空回滚**：try 还没执行，cancel 先到了。比如全局事务超时，TC 开始回滚，但 try 还在排队。cancel 收到的是一张还没冻结的券，它可能什么都不做，也可能误把一张正常券改坏。

**幂等**：TC 因为网络超时重发 cancel，cancel 被执行两次。如果 cancel 是「把冻结改成可用」，第二次执行时券已经是可用，可能又改出问题；如果 cancel 是「插入一条退款记录」，第二次会插两条。

**悬挂**：cancel 先执行完，try 后到。cancel 已经把资源释放了，try 又把资源锁住，全局事务却已经回滚。开头那个优惠券故障就是这种。

### 2.4 fence：用一张状态表把三种问题收掉

把 `useTCCFence` 打开，Seata 会在业务库里读写 `tcc_fence_log`：

```sql
CREATE TABLE tcc_fence_log (
  xid VARCHAR(128) NOT NULL,
  branch_id BIGINT NOT NULL,
  action_name VARCHAR(64) NOT NULL,
  status TINYINT NOT NULL,  -- 1 TRIED, 2 COMMITTED, 3 ROLLBACKED, 4 SUSPENDED
  gmt_create DATETIME(3) NOT NULL,
  gmt_modified DATETIME(3) NOT NULL,
  PRIMARY KEY (xid, branch_id)
);
```

状态只有四个：`TRIED`、`COMMITTED`、`ROLLBACKED`、`SUSPENDED`。fence 的所有行为都围绕这四个状态展开：

| 场景 | 表里已有状态 | fence 的动作 |
| --- | --- | --- |
| try 第一次执行 | 无 | 在同一本地事务里插入 `TRIED`，再执行业务 try |
| try 重复执行 | `TRIED` | 唯一键冲突，抛 `CommonFenceException`，阻止重复预留 |
| confirm 第一次 | `TRIED` | 执行业务 confirm，把状态改成 `COMMITTED` |
| confirm 重复 | `COMMITTED` | 直接返回 true，不重复执行 |
| cancel 第一次 | `TRIED` | 执行业务 cancel，改成 `ROLLBACKED` |
| cancel 重复 | `ROLLBACKED` / `SUSPENDED` | 直接返回 true |
| cancel 比 try 先到 | 无 | 插入 `SUSPENDED`，返回 true（空回滚） |
| try 在 cancel 之后到 | `SUSPENDED` | 插入 `TRIED` 撞唯一键，try 失败（反悬挂） |

关键在最后两行。cancel 先到又查不到记录时，fence 不执行任何业务逻辑，只插一条 `SUSPENDED` 作为墓碑；等 try 再来，唯一键把它挡在门外。这比「业务里判断券状态」可靠，因为它不依赖业务字段是否恰好能表达「曾经有一个 try 来过」。

fence 的代价也很明确：每次 try/confirm/cancel 都要多一次本地事务和一张表的读写；`SUSPENDED` 记录不会自动消失，需要配清理任务；它依赖 Spring 的数据源和事务模板，不是所有接入方式都能用。

## 三、Saga：一长串本地事务，加一条补偿链

Saga 的思路和 TCC 不一样。它不要求业务提供 try/confirm/cancel 三件套，而是把整个流程拆成一串状态，每个状态是一个本地事务，失败时按相反顺序调用补偿。

一个简单的下单 Saga 长这样：

```json
{
  "Name": "orderSaga",
  "StartState": "CreateOrder",
  "States": {
    "CreateOrder": {
      "Type": "ServiceTask",
      "ServiceName": "orderService",
      "ServiceMethod": "create",
      "CompensateState": "CancelOrder",
      "Next": "DeductStock"
    },
    "DeductStock": {
      "Type": "ServiceTask",
      "ServiceName": "stockService",
      "ServiceMethod": "deduct",
      "CompensateState": "RestoreStock",
      "Next": "Succeed"
    },
    "CancelOrder": {
      "Type": "ServiceTask",
      "ServiceName": "orderService",
      "ServiceMethod": "cancel"
    },
    "RestoreStock": {
      "Type": "ServiceTask",
      "ServiceName": "stockService",
      "ServiceMethod": "restore"
    },
    "Succeed": { "Type": "Succeed" }
  }
}
```

每个 `ServiceTask` 都是一个本地事务调用。扣库存失败时，Saga 引擎从已成功的状态栈里逆序弹出，找到对应的 `CompensateState`，逐个调用补偿。

### 3.1 失败不会自动触发补偿

这是 Saga 最容易被误解的地方。状态抛异常后，引擎只做一件事：看这个状态有没有配 `Catch`。

- 配了 `Catch`，并且 `Catch.Next` 指向一个 `CompensationTrigger` 状态，引擎才会开始补偿；
- 没配 `Catch`，异常往上抛，状态机进入失败，但不会自动补偿。

也就是说，补偿是一条显式的路由，不是框架的默认行为。你可以把它理解成「异常处理里手动调了一个补偿入口」，而不是「事务框架自动回滚」。

### 3.2 TC 的 commit 可能是「继续执行」

Saga 也用 TC，但用法很特别。

`SagaCore.doGlobalCommit()` 不会遍历真实分支，而是临时造一个 `branchId = -1` 的虚拟分支，发 `BranchCommitRequest`。RM 侧 `SagaResourceManager.branchCommit()` 收到后，调的是：

```java
StateMachineEngineHolder.getStateMachineEngine().forward(xid, null);
```

不是「提交本地事务」，是「把状态机继续往前推」。如果状态机还没跑完，TC 的 commit 会继续执行剩下的状态；如果已经成功结束，forward 直接返回 `PhaseTwo_Committed`。

回滚也一样：`SagaCore.doGlobalRollback()` 造一个 `branchId = -1` 的分支，`SagaResourceManager.branchRollback()` 调 `engine.compensate(xid, null)`，让引擎逆序补偿。

默认情况下，Saga 不会给每个状态注册分支（`client.saga.branchRegisterEnable=false`）。TC 眼里只有一个虚拟分支，真正的状态推进和补偿都在 Saga 引擎本地完成。这也是为什么 Saga 的 TC 会话看起来「分支很少」，但状态机可能已经跑了几十个状态。

### 3.3 中间状态对外可见

Saga 的每个状态都是独立的本地事务，提交后立刻可见。没有全局锁，也没有 XA 的 prepare 阶段。

这意味着：订单已经创建、库存还没扣的那几百毫秒里，别的请求能看到这张订单。如果你的业务不能接受这种中间态，要么在查询侧过滤，要么用 AT/TCC 把关键步骤的可见性收紧。

补偿也不是数据库回滚。`CancelOrder` 可能是「把订单状态改成已取消」，而不是「删除订单」；`RestoreStock` 可能是「加回库存」，而不是「把库存字段改回原值」。补偿是业务语义上的撤销，不是物理上的倒带。

### 3.4 补偿失败只能继续重试或人工

Saga 引擎的补偿状态本身也是一个 `ServiceTask`，它有自己的重试配置。补偿失败后，状态机进入补偿失败，TC 拿到 `PhaseTwo_RollbackFailed_Retryable`，按回滚重试策略继续发。

如果补偿方法本身不幂等，重试会把问题放大。Saga 不会替你检查「这个补偿是不是已经执行过」，这笔账要业务自己记。

有一个细节值得注意：Saga 状态机可以配 `RecoverStrategy=Forward`。全局事务超时回滚时，`SagaResourceManager.branchRollback()` 看到这个策略，会返回 `PhaseTwo_CommitFailed_Retryable`，让 TC 继续尝试 forward，而不是补偿。这是给「宁可继续往前跑，也不往回退」的长流程准备的，不是默认行为。

## 四、XA：把两阶段交给数据库

XA 是三种模式里最「传统」的。它不生成 undo log，也不要求业务写 confirm/cancel，而是把两阶段交给数据库的 XA 协议。

### 4.1 一阶段：注册、XA START、prepare

XA 的入口在 `ConnectionProxyXA.setAutoCommit(false)`：

```text
setAutoCommit(false)
  → branchRegister(XA)                 // 向 TC 注册 XA 分支
  → XAXid = xid + branchId
  → xaResource.start(xaXid, TMNOFLAGS) // XA START
  → 业务 SQL
```

注意，`ConnectionProxyXA.init()` 要求物理连接初始 `autoCommit=true`。如果连接池交给 Seata 的连接已经是 `autoCommit=false`，会直接抛 `IllegalStateException`。这是 XA 接入时很常见的配置坑。

业务方法结束时，连接关闭，`close()` 里做两件事：

```text
close()
  → xaResource.end(xaXid, TMSUCCESS)   // XA END
  → xaResource.prepare(xaXid)          // XA PREPARE
```

prepare 成功，数据已经写好但不可见，行锁由数据库持有。prepare 返回 `XA_RDONLY` 时，上报 `PhaseOne_RDONLY`；prepare 失败时，回滚并上报 `PhaseOne_PrepareFailed`。

这里有一个反直觉的点：**XA 的 prepare 成功，没有单独的 `PhaseOne_Done` 上报。** 代码里 XA 路径只上报 `PhaseOne_RDONLY` 和 `PhaseOne_PrepareFailed`，正常 prepare 完成后分支状态仍停在 `Registered`。TC 不会因此卡住，因为 XA 分支不能异步提交，全局提交时一定会发 `BranchCommitRequest`，由 RM 执行 XA commit。

### 4.2 二阶段：TC 驱动数据库提交

全局提交时，TC 给 XA 分支发 `BranchCommitRequest`。RM 侧 `ResourceManagerXA.finishBranch(true, ...)` 拿到 XA 连接，执行：

```java
xaResource.commit(xaXid, false);
```

`ConnectionProxyXA.commit()` 本身是空实现，只做状态校验；真正的 commit 发生在 `xaCommit()` 里。回滚同理，`xaRollback()` 先 `XA END(TMFAIL)`，再 `xaResource.rollback()`。

XA 的可见性由数据库保证：prepare 之后数据不可见，XA commit 之后才可见。这也是 XA 和 AT 最大的差别：AT 一阶段本地提交后数据就可见，XA 要等到二阶段。

XA 的失败处理有一套专门的状态：`XAER_NOTA` 表示数据库不认识这个 XA 分支（可能已经提交或回滚），TC 会把它当成可重试的特殊情况，而不是直接判失败。这个细节在跨库、跨资源管理器切换时很重要。

### 4.3 XA 的代价

XA 把一致性交给了数据库，代价也由数据库承担：

- 行锁从 prepare 一直持有到 commit/rollback，锁的持有时间比 AT 长；
- 数据库要支持 XA，连接池和驱动要正确配置；
- prepare 之后数据库宕机，恢复和清理比普通事务麻烦；
- TC 侧没有全局锁，跨资源的隔离完全靠数据库的 XA 锁。

## 五、同一笔订单，三种写法

把「下单 + 扣库存」用三种模式各写一遍，差别会很直观。

**AT**：业务代码只写 SQL，加一个 `@GlobalTransactional`。框架生成 undo log、抢全局锁、本地提交；失败时用 undo log 反向补偿。接入成本最低，但依赖主键、依赖 SQL 解析，脏写要靠 `SELECT ... FOR UPDATE` 或 `@GlobalLock` 防。

**TCC**：业务要写 try/confirm/cancel 三个方法，自己定义资源预留和释放。框架只负责按顺序调用。接入成本最高，但锁的粒度、资源的可见性完全由业务控制。适合金融、券、库存这类「不能靠反向 SQL 简单还原」的场景。

**Saga**：业务要写状态机定义和每个状态的补偿方法。每个本地事务立即提交，没有全局锁，适合长流程、跨系统、参与者多的场景。代价是中间态可见，补偿是业务语义而不是数据库回滚。

**XA**：业务代码几乎不用改，靠数据库 XA 保证强一致。适合已经支持 XA、且能接受较长锁持有时间的场景。跨数据库、跨云厂商时，XA 的兼容性和运维成本要提前验证。

选型时先问三个问题：

1. 数据能不能靠反向 SQL 还原？能，优先 AT；不能，考虑 TCC。
2. 中间态能不能被业务看见？不能，XA 或 TCC；能，Saga 也可以。
3. 失败时更怕「回滚不干净」还是更怕「流程卡住」？前者选 TCC/XA，后者选 Saga + 人工补偿。

## 六、踩坑清单

- TCC 不开 fence，却假设框架会处理空回滚、幂等和悬挂：这三种情况默认全是业务责任。
- TCC 的 confirm/cancel 里做远程调用，却没做超时和重试：TC 重试会把远程调用放大。
- TCC 的 `actionName` 在不同 bean 上重复：启动时直接报错，或者更糟，confirm 调到了错误的 bean。
- Saga 以为失败会自动补偿：没有配 `Catch.Next=CompensationTrigger`，异常只会让状态机失败。
- Saga 的补偿方法不幂等：TC 回滚重试会重复执行补偿，制造新的数据。
- Saga 的 `RecoverStrategy=Forward` 被当成默认行为：它只在超时回滚时生效，而且会让 TC 继续 forward，不是常规路径。
- XA 的连接池初始 `autoCommit=false`：`ConnectionProxyXA.init()` 直接抛异常。
- 以为 XA 的 prepare 成功会向 TC 上报 `PhaseOne_Done`：代码里没有这个上报，别拿分支状态判断 prepare 是否完成。
- 用 AT 的「全局锁」思维理解 XA：XA 没有 TC 全局锁，隔离靠数据库 XA 锁。
