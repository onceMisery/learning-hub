# 服务发现可插拔化

配置中心解决「配置从哪来」，服务发现解决「TC 在哪」。

Seata 的客户端只知道一个逻辑事务组名（`tx-service-group`），不知道 TC 的 IP。它要先把这个组名映射到集群名，再从注册中心拿到地址列表，最后建 Netty 连接。这一串动作里，注册中心是可插拔的：file、Nacos、Eureka、Redis、ZK、Consul、etcd3、SOFA、seata namingserver、raft，各有各的实现。

---

## 一、Registry SPI：工厂、Provider、Service

入口是 `RegistryFactory`：

```text
RegistryFactory.getInstance()
  → 读 registry.type（默认 file）
  → EnhancedServiceLoader.load(RegistryProvider.class, type)
    → provider.provide()
      → RegistryService
```

`RegistryProvider` 是 SPI 接口，每个实现用 `@LoadLevel(name=...)` 标类型名。`RegistryService` 定义 `register`、`unregister`、`subscribe`、`unsubscribe`、`lookup`、`close`。

`RegistryType` 枚举里有：

```text
File / Raft / ZK / Redis / Nacos / Eureka / Consul
Etcd3 / Sofa / Custom / Seata
```

`Seata` 就是 seata namingserver。`Raft` 是 TC 集群内部用的基于 raft 元数据的发现。

客户端通常只配一个注册中心；服务端可以用 `MultiRegistryFactory` 配多个（逗号分隔），同时往多个注册中心注册。这是「客户端单注册、服务端多注册」的设计。

客户端通常只配一个注册中心；服务端可以用 `MultiRegistryFactory` 配多个（逗号分隔），同时往多个注册中心注册。这是「客户端单注册、服务端多注册」的设计。

## 二、vgroup mapping：组名不是地址

`tx-service-group` 是一个逻辑组名，不是地址。客户端先读：

```text
service.vgroupMapping.<tx-service-group> = <cluster-name>
```

`RegistryService.getServiceGroup(key)` 就是读这个键。然后按 cluster 名去注册中心查地址。

如果你把 `tx-service-group` 配成 `my_tx_group`，但没配 `service.vgroupMapping.my_tx_group`，客户端会拿不到 cluster，也就 lookup 不到 TC。默认配置里会注入 `default_tx_group → default` 和 `my_test_tx_group → default`，但生产环境不要依赖这些默认值。

`TransactionServiceGroup` 在 2.x 里没有对应的类，它只是「配置键前缀 + txServiceGroup 字符串」的组合。看到文档里这个词，不要去找一个叫 `TransactionServiceGroup` 的 Java 类。

## 三、file 注册中心不是注册中心

`FileRegistryServiceImpl` 的 `register`、`unregister`、`subscribe` 全是空实现。`lookup` 只做一件事：解析配置里的 grouplist：

```text
service.<cluster>.grouplist = 127.0.0.1:8091,127.0.0.1:8092
```

所以 file 模式没有服务注册、没有订阅、没有健康检查。它只是「从本地配置里读一组固定地址」。

这也意味着 file 模式不适合多 TC 动态扩缩容：加一台 TC，要改所有客户端的配置文件并重启。它适合本地开发和固定地址的小集群。

---

## 四、namingserver：HTTP 的 TC 注册中心

`seata` 类型的注册中心是 namingserver。它不是一个通用服务注册中心，只服务 Seata 的 TC 节点。

客户端：

- `register`：HTTP `POST /naming/v1/register`；
- `lookup`：HTTP `GET /naming/v1/discovery?vGroup=...`；
- `subscribe`：标准 `subscribe(String, NamingListener)` 是空实现，真正生效的是自定义的 `subscribe(NamingListener, String vGroup)`。

服务端 `namingserver` 是一个 Spring Boot Web 应用，默认端口 8081，`NamingController` 提供 register/unregister/discovery/watch 端点。心跳阈值 90 秒、周期 60 秒，配置在 `application.yml`。

在 raft 模式下，`handleMetadata()` 只保留 `LEADER && term >= 当前 term` 或 `MEMBER` 的节点。TC 注册时，raft leader 注册为 `LEADER`，follower 注册为 `FOLLOWER`；follower 不等于 `MEMBER`，所以被过滤掉。这就是「raft 模式只发现 leader」的实现方式——不是显式判断 `FOLLOWER`，而是白名单过滤。

## 五、客户端怎么拿到地址并重连

`TmNettyRemotingClient` / `RmNettyRemotingClient` 初始化时调 `initReconnect(group, failFast)`：

```text
NettyClientChannelManager.doReconnect()
  → getAvailServerList(group)
    → RegistryFactory.getInstance().lookup(group)
      → RegistryService.lookup()
```

拿到地址列表后，逐个建连；成功的地址写进 `refreshAliveLookup` 缓存。发送请求时从 `aliveLookup` 里按负载均衡选一个。

除了启动时的重连，还有一条定时重连：启动 60 秒后，每 10 秒执行一次 `clientChannelManager.reconnect(group)`。TC 扩缩容、leader 切换、网络抖动，都靠这条线把地址列表刷新回来。

File registry 的 lookup 失败会被刻意静默（`NettyClientChannelManager` 里对 file 类型不抛异常），因为 file 的地址是静态的，失败通常是配置缺失，不是网络问题。

## 六、raft 模式的发现

raft 模式有两套「发现」：

**服务端内部**：`RaftRegistryServiceImpl` 从 raft 元数据里取节点；`aliveLookup` 只返回 leader，`refreshAliveLookup` 还会把 leader 自身从 alive 列表里滤掉，避免客户端连到自己。

**客户端外部**：通过 namingserver 或 raft registry 拿到 leader 地址。leader 换了，namingserver 的 `term` 会更新，客户端重新 lookup 后拿到新 leader。

这也是为什么 raft 模式下客户端要能处理 `NotRaftLeader`：请求可能短暂打到旧 leader，TC 会拒绝，客户端要重新 lookup 或重连。

---

## 七、踩坑清单

- 把 `tx-service-group` 当地址：它只是组名，要先经过 vgroup mapping。
- 没配 `service.vgroupMapping.<group>`：lookup 不到 cluster，客户端连不上 TC。
- 以为 file 注册中心会动态发现：它只读 grouplist，没有注册和订阅。
- 把 namingserver 当通用注册中心：它只服务 Seata TC，端点是 `/naming/v1/*`。
- raft 模式下把请求发到 follower：会收到 `NotRaftLeader`，客户端要重新 lookup。
- 服务端配多个注册中心，客户端只配一个：客户端只会从自己配的那个拿地址，两个注册中心的数据要一致。
- 改了 TC 地址但客户端没重连：检查 60s/10s 的定时重连是否在跑。
