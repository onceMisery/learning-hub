# 事务管理器 TM：只做决定，不做数据

TM 这个名字很容易让人误解。

它不执行 SQL，不写 undo_log，也不碰数据库连接。它只做三件事：开始一笔全局事务、在业务结束时决定提交还是回滚、在跨服务调用时把 XID 带过去。

真正让 TM 显得复杂的是「它站在所有代理的最外层」：Spring 的 AOP、事务传播、超时、重试、失败回调都挂在这层。数据操作是 RM 的事，TM 只负责把「这笔事务该怎么结束」这个决定做对。

---

## 一、TM 的入口：一个自动代理器

Spring 里，`@GlobalTransactional` 不是靠一个普通的 `@Around` 切面生效的，而是靠 `GlobalTransactionScanner`。它继承 `AbstractAutoProxyCreator`，在 bean 初始化后判断要不要代理：

```text
GlobalTransactionScanner.wrapIfNecessary()             // :307
  → DefaultInterfaceParser.parserInterfaceToProxy()
    → GlobalTransactionalInterceptorHandler
```

`GlobalTransactionScanner` 在 `afterPropertiesSet()` 里先初始化 TM 客户端（`TMClient.init`），再初始化 RM 客户端（`RMClient.init`）。这也说明一个应用可以同时是 TM 和 RM：发起全局事务的服务，自己也可能是一个分支。

真正的方法拦截在 `GlobalTransactionalInterceptorHandler.doInvoke()`（`:148`）。它判断当前方法有没有 `@GlobalTransactional`，有就交给 `handleGlobalTransaction()`（`:188`），后者构造一个 `TransactionalExecutor`，交给 `TransactionalTemplate.execute()`。

**自调用不会走代理。** 同一个类里 `this.method()` 调用带注解的方法，Spring 代理不参与，TM 不会 begin，XID 也不会出现。这是 TM 层最常见的「注解没生效」原因。

## 二、TransactionalTemplate：TM 的发动机

`TransactionalTemplate.execute()`（`:180`）把一次全局事务拆成固定的几步：

```text
1. 取当前事务 / 根据传播级别决定是否新建
2. beginTransaction（只有 Launcher 真正发 begin）
3. 执行业务方法
4. 正常返回 → commitTransaction
5. 抛异常 → completeTransactionAfterThrowing（按 rollbackOn 决定回滚还是提交）
6. finally 恢复被挂起的外层事务、清理 hook
```

它不是简单的 try/catch。每一步都有对应的 `TransactionHook`：`beforeBegin`、`afterBegin`、`beforeCommit`、`afterCommit`、`beforeRollback`、`afterRollback`、`afterCompletion`。这些 hook 用 `TransactionHookManager` 的 ThreadLocal 管理，Launcher 结束时清空。

`completeTransactionAfterThrowing()`（`:318`）会看 `TransactionInfo.rollbackOn(exception)`：

- 异常在回滚规则里，调 `rollbackTransaction()`；
- 不在回滚规则里，反而走 `commitTransaction()`。

所以「业务抛了异常，全局事务一定回滚」是错的。`@GlobalTransactional` 支持 `rollbackFor` / `noRollbackFor`，最终看的是规则。

## 三、Launcher 与 Participant：TM 也有两种身份

`GlobalTransactionContext.getCurrent()` 会看当前线程有没有 XID：

- 没有 XID：返回 null，`TransactionalTemplate` 走 `getCurrentOrCreate()`，创建 `Launcher`，由它向 TC 发 begin；
- 有 XID：创建一个 `Participant`，它只是「加入已有全局事务」，不再发 begin。

Participant 的 begin/commit/rollback 都是 no-op。`DefaultGlobalTransaction.begin()` 一进来就判断 `role != Launcher`，直接 `assertXIDNotNull()` 后返回；commit/rollback 同样忽略。

这解释了一个常见现象：下游服务也加了 `@GlobalTransactional`，但它的 commit 不会去 TC 提交整笔全局事务。**只有发起方是 Launcher，其他参与者只负责本地分支。**

`REQUIRED` 是默认传播级别：有 XID 就加入，没有就新建。`REQUIRES_NEW` 则相反：先挂起外层 XID，再 `GlobalTransactionContext.createNew()` 创建一个新的 Launcher，向 TC 申请新的 XID。`NOT_SUPPORTED` 挂起外层后无事务执行；`SUPPORTS` 有就加入、没有就裸跑；`MANDATORY` 没有 XID 直接抛异常；`NEVER` 有 XID 抛异常。

挂起的实现比很多人想的轻：

```java
public SuspendedResourcesHolder suspend(boolean clean) {
    String xid = RootContext.getXID();
    if (xid != null) {
        RootContext.unbind();
        return clean ? null : new SuspendedResourcesHolder(xid);
    }
    return null;
}
```

`SuspendedResourcesHolder` 里只有 XID。`resume()` 也只是把 XID 重新 bind 回当前线程。**它不挂起 JDBC 连接、不挂起本地事务、不挂起 undo 上下文。** 所以 `REQUIRES_NEW` 在 Seata 里是「新的全局事务」，但本地资源是否隔离，取决于你上层 Spring 事务和连接池的配置。

## 四、begin / commit / rollback 到底做了什么

`DefaultGlobalTransaction.begin()`（`:235`）的顺序是：

```text
1. 记录 createTime
2. 非 Launcher 直接返回
3. 校验当前线程没有 XID
4. transactionManager.begin(null, null, name, timeout)
5. status = Begin
6. RootContext.bind(xid)
```

注意 `applicationId` 和 `transactionServiceGroup` 传的是 `null`。TC 从连接上下文里补齐这两个值。XID 由 TC 的 `GlobalSession` 生成，TM 只是接收并绑定。

commit 时，`DefaultGlobalTransaction.commit()`（`:300`）会按 `client.tm.commitRetryCount`（默认 5）重试 `transactionManager.commit(xid)`。它只对 RPC 异常重试；TC 返回的状态码是不是 `Committed`，它不在这里判断。`TransactionalTemplate` 会看 `tx.getLocalStatus()`，只有 `Finished`、`TimeoutRollback*`、`RollbackRetrying` 等特定状态才会造异常。

rollback 同样有重试（`client.tm.rollbackRetryCount`，默认 5），但模板无论回滚成败都会抛 `TransactionalExecutor.ExecutionException`，用 `RollbackFailure` / `Rollbacking` / `RollbackDone` 区分结果。

## 五、超时和失败回调

全局超时默认 60 秒：`@GlobalTransactional.timeoutMills` 的默认值来自 `DefaultValues.DEFAULT_GLOBAL_TRANSACTION_TIMEOUT`，也可以配 `client.tm.defaultGlobalTransactionTimeout`。

TM 侧在提交前会再做一次本地超时判断：

- 本地已经超时：不再发 `GlobalCommitRequest`，直接走回滚；
- 本地没超时，但 TC 已经因为超时改成 `TimeoutRollbacking`：TC 返回该状态，模板抛 `TransactionExceptionCode.TransactionTimeout`。

失败回调在 `GlobalTransactionalInterceptorHandler` 里分派给 `FailureHandler`：

- `onBeginFailure`：begin 失败；
- `onCommitFailure`：commit 失败；
- `onRollbackFailure`：rollback 失败；
- `onRollbacking`：还在回滚中。

默认实现 `DefaultFailureHandlerImpl` 会用时间轮在 10 秒后重新查一次全局状态。它不是「再提交一次」，而是「确认 TC 那边到底走到哪了」。

## 六、四个常见误解

**误解一：TM 负责所有分支。** TM 只发全局决议；分支注册、锁、undo 都是 RM 做的。

**误解二：`REQUIRES_NEW` 会挂起本地连接。** 它只挂起 XID。本地连接、Spring 事务、undo 上下文都没有被挂起；如果外层本地事务还开着，内层可能复用同一个连接。

**误解三：TM 重试等于事务重试。** commit/rollback 重试只是 RPC 重试；TC 返回一个「非 Committed」状态时，TM 不一定会重发。真正的二阶段重试在 TC 的调度线程里。

**误解四：加了注解就一定走 TM。** 自调用、私有方法、final 方法、没被 Spring 管理的 bean，都可能绕过代理。注解只是标记，代理才是入口。

## 思考题

1. 一个 `@GlobalTransactional(propagation = REQUIRES_NEW)` 的内层方法，和外层方法用的是同一个数据库连接吗？XID 呢？undo 上下文呢？
2. 下游服务也加了 `@GlobalTransactional`，它的 commit 会不会把整笔全局事务提交掉？为什么？
3. TM 的 commit 重试和 TC 的提交重试，分别重试的是什么？两者能不能互相替代？
4. 如果业务异常不在 `rollbackFor` 里，`TransactionalTemplate` 会走提交还是回滚？这个行为在什么场景下容易误伤？
