# 事务协调者 TC：状态机、会话和那把锁

先把一个常见误解拆掉。

很多人把 TC 想成一个「分布式数据库协调器」：以为它拿着几个库的连接，在那边替业务执行 prepare/commit。不是。TC 不碰业务表，也不执行你的 SQL。它只做三件事：生成 XID、维护全局/分支会话、决定下一步该提交还是回滚。

业务数据在 RM 手里，TC 手里是账本。它记错一笔账，业务数据不会当场坏；它把账本丢了，恢复时就会出大事。

---

## 一、TC 内部是两层，不是一层

`seata-server` 收到请求后，先到 `DefaultCoordinator`，再到 `DefaultCore`。

`DefaultCoordinator` 负责「接入与调度」：

- 继承 `AbstractTCInboundHandler`，把 Netty 请求翻译成 begin / branchRegister / commit / rollback；
- 套一层 `LimitRequestDecorator` 做限流；
- 持有超时扫描、异步提交、提交重试、回滚重试这几个调度线程；
- 在 raft 模式下换成 `RaftCoordinator`，非 leader 直接拒绝写请求。

`DefaultCore` 负责「全局状态机」：

- 用 `CORE_MAP` 按 `BranchType` 持有 `ATCore`、`TccCore`、`SagaCore`、`XACore`；
- 全局的 begin / commit / rollback 在这里改 `GlobalSession`；
- 分支注册、分支提交、分支回滚按分支类型选对应的 core。

`AbstractCore` 则是四种模式共享的骨架：查会话、加会话锁、建 `BranchSession`、调 `branchSessionLock`、发二阶段请求。`ATCore` 只覆写「注册时抢全局锁」和「lockQuery」，`TccCore`/`SagaCore`/`XACore` 不抢 TC 全局锁。

这个分层很关键：**协调器管调度，core 管状态，lock manager 管行锁。** 三件事不要混在一起看。

## 二、一次请求怎么进 TC

以 `GlobalBeginRequest` 为例：

```text
NettyRemotingServer
  → ServerOnRequestProcessor.onRequest()
    → DefaultCoordinator.onRequest()                 // :798
      → AbstractTCInboundHandler.handle()            // :58
        → DefaultCoordinator.doGlobalBegin()         // :321
          → DefaultCore.begin()                      // :222
            → GlobalSession.begin()                  // :237
              → SessionHolder.getRootSessionManager().onBegin()
```

XID 不是在 TM 生成的，而是在 `GlobalSession` 构造时生成的：

```java
this.transactionId = UUIDGenerator.generateUUID();
this.xid = XID.generateXID(transactionId);
```

格式是 `ip:port:transactionId`。TC 返回给 TM 之后，TM 把它绑到 `RootContext`；后续分支注册、提交、回滚都带着这个字符串。

分支注册走的是另一条链：

```text
DefaultCoordinator.doBranchRegister()                 // :369
  → DefaultCore.branchRegister()                      // :105
    → AbstractCore.branchRegister()                   // :87
      → SessionHolder.lockAndExecute(globalSession)
        → branchSessionLock()                         // :110
          → ATCore.branchSessionLock()                // :57（AT 才抢全局锁）
        → globalSession.addBranch()
```

commit/rollback 的入口在 `DefaultCoordinator` 的 `doGlobalCommit()` / `doGlobalRollback()`，最终都会落到 `DefaultCore` 的 `commit()` / `rollback()`。

## 三、TC 记的账：全局会话、分支会话、全局锁

`GlobalSession` 是根账本，字段里有 XID、应用 ID、事务组、事务名、超时、状态、开始时间、分支列表。`BranchSession` 是参与者账本，记录 branchId、resourceId、branchType、状态、clientId、applicationData、lockKey。

全局锁是另一本账，不放在 `GlobalSession` 里：

- file 模式：`FileLocker` 的 `LOCK_MAP`，resourceId → table → 128 个 bucket → pk → 持有者；
- db 模式：`lock_table`，row_key 主键；
- redis 模式：`SEATA_GLOBAL_LOCK*` / `SEATA_ROW_LOCK_*`；
- raft 模式：leader 本地锁 + raft 任务复制释放。

`AbstractCore.branchRegister` 的顺序是：先 `SessionHolder.lockAndExecute` 锁住全局会话，再校验状态，再建分支、抢锁、加分支。锁全局会话是为了防止同一个 XID 同时被两个请求改状态；抢行锁是为了防止两个 XID 改同一行。

`GlobalSession.changeGlobalStatus()` 在状态进入回滚态时，会顺带把锁状态改成 `Rollbacking`。这样后面的 AT 事务来抢锁时，`FileLocker` 里的 `previousLockBranchSession.getLockStatus() == Rollbacking` 会让它快速失败，而不是傻等。

---

## 四、分支类型决定「谁抢锁」

`DefaultCore.branchRegister()` 按请求里的 `branchType` 选 core；`branchCommit()` / `branchRollback()` 按 `branchSession.getBranchType()` 选 core。

| 分支类型 | core | 是否抢 TC 全局锁 | 二阶段动作 |
| --- | --- | --- | --- |
| AT | `ATCore` | 是，逐行 `putIfAbsent` | 异步删 undo / 反向 SQL |
| TCC | `TccCore` | 否 | 反射调 confirm / cancel |
| Saga | `SagaCore` | 否 | `engine.forward` / `engine.compensate` |
| XA | `XACore` | 否 | 数据库 XA commit / rollback |

只有 AT 覆写了 `branchSessionLock`。这不是说 TCC/Saga/XA 不需要锁，而是它们的锁由别处负责：TCC 靠业务预留资源，Saga 靠本地事务，XA 靠数据库 XA 行锁。TC 的全局锁只解决 AT 的「本地已提交、全局还没决议」这段窗口。

## 五、二阶段：TC 只发指令，不改数据

全局提交时，`DefaultCore.commit()` 先 `close()` 会话，阻止新分支注册，然后看能不能异步提交。AT 分支的 `canBeCommittedAsync()` 恒为 true，于是：

1. 把状态改成 `AsyncCommitting`；
2. 调 `globalSession.clean()` 释放全局锁；
3. 向 TM 返回 `Committed`。

真正的 `BranchCommitRequest` 由 `handleAsyncCommitting()` 在后台逐分支发送。RM 收到后，AT 分支入队即返回 `PhaseTwo_Committed`，undo_log 由 RM 自己的定时任务删。TC 收到成功，删分支；分支清空后 `endCommitted()`。

全局回滚时，`DefaultCore.rollback()` 把状态改成 `Rollbacking`，按 `getReverseSortedBranches()` 逆序发 `BranchRollbackRequest`。每个分支的回滚结果回来，成功的删分支，可重试的留在列表里下一轮再发，不可重试的结束会话。

所以 TC 的二阶段不是「它去改数据」，而是「它决定谁在什么时候改数据」。**数据操作永远在 RM 侧。**

## 六、超时、重试和 leader

TC 有三条每秒跑的调度线：

- `timeoutCheck`：扫 `Begin` 会话，超时改成 `TimeoutRollbacking`；
- `handleRetryRollbacking`：扫回滚重试状态，继续发 `BranchRollbackRequest`；
- `handleRetryCommitting` / `handleAsyncCommitting`：扫提交重试 / 异步提交状态，继续发 `BranchCommitRequest`。

`server.maxCommitRetryTimeout` 和 `server.maxRollbackRetryTimeout` 默认都是 `-1`，也就是不设上限。回滚一直失败，全局锁就一直不放；这是为了保证不在数据没回滚干净时让新事务进来。

raft 模式下，只有 leader 处理事务。`RaftCoordinator.exceptionHandleTemplate()` 会检查当前节点是不是 leader，不是就返回 `NotRaftLeader`。新 leader 上任后 `SessionHolder.reload(..., RAFT, false)`：旧 `Begin` 保守改成 `RollbackRetrying`，`Committing` / `AsyncCommitting` 补一次 `clean()`，`Rollbacking` 继续回滚。具体见 [Raft 集群与高可用](../server/03-Raft与高可用.md)。

## 七、四个容易搞错的点

**TC 不持有业务数据。** 它只持有会话和锁。TC 的磁盘/数据库/raft 日志坏了，影响的是「事务走到哪了」，不是业务表本身。

**TC 返回 `Committed` 不等于二阶段完成。** AT 的提交是异步的；这个状态只承诺「不会再回滚」。

**全局锁在 commit 受理时就释放。** 不是等所有分支二阶段完成。`GlobalSession.unlockBranch()` 会跳过 `Committing` / `CommitRetrying` / `AsyncCommitting` 三种状态，避免重复释放。

**非 AT 分支的 `lockQuery` 默认返回 true。** `AbstractCore.lockQuery()` 直接返回 true；RM 基类 `AbstractResourceManager.lockQuery()` 却返回 false。两个默认值方向相反，接 TCC/Saga/XA 时不要拿 AT 的锁语义去套。

## 思考题

1. TC 返回 `Committed` 时，分支提交和 undo 删除分别进行到哪一步？如果此时 TC 宕机，恢复后会继续做什么？
2. 为什么只有 AT 需要 TC 的全局锁？TCC 和 XA 的锁分别在哪里？它们的锁能挡住谁？
3. `AbstractCore.lockQuery()` 返回 true、`AbstractResourceManager.lockQuery()` 返回 false，这两个默认值分别服务于什么场景？
4. raft 新 leader 把旧 `Begin` 改成 `RollbackRetrying` 时，TM 之后发来的 commit 会得到什么状态？业务应该怎么处理？
