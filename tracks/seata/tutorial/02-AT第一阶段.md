# AT 一阶段：一条 UPDATE 怎么变成 undo log 和一把全局锁

库存服务报了一个错：`Global lock acquire failed xid = ... branchId = ...`。

开发的第一反应是「更新语句是不是没加索引」。可日志里明明白白写着 `update stock set count = count - 1 where id = 100`，影响行数 1，SQL 早就执行成功了。报错发生在 `commit()`。

这就是 AT 最反直觉的地方：**业务 SQL 先执行，全局锁后拿。** 你以为冲突会在 update 那一行挡住你，实际上 SQL 已经把数据改了，本地事务也开着，直到提交前才去 TC 抢锁，抢不到再重试。重试 30 次、每次 10 毫秒还抢不到，才抛异常。

这一章就把一条 UPDATE 从进入代理到本地提交的这段路走完。

---

## 一、代理链：SQL 从哪一步开始被看见

先看对象关系。业务代码拿到的 `DataSource` 不是数据库驱动给的那个，而是 Seata 包了一层的 `DataSourceProxy`。从它开始，一路都是代理：

```text
DataSourceProxy.getConnection()
  → ConnectionProxy
    → StatementProxy / PreparedStatementProxy
      → ExecuteTemplate.execute()
        → SQLVisitorFactory.get(sql, dbType)     // Druid 解析
          → UpdateExecutor / InsertExecutor / DeleteExecutor / SelectForUpdateExecutor
```

`ExecuteTemplate` 的第一行很关键：

```java
if (!RootContext.requireGlobalLock() && BranchType.AT != RootContext.getBranchType()) {
    return statementCallback.execute(statementProxy.getTargetStatement(), args);
}
```

不在全局事务里，也没有 `@GlobalLock`，这条 SQL 就直接走原生 Statement。代理装上了，不代表每条 SQL 都会被 Seata 接管；它只在全局事务或全局锁上下文里才介入。

进入全局事务后，SQL 会先被 Druid 解析成 `SQLRecognizer`。解析成功，按 SQL 类型选执行器；解析失败，退化成 `PlainExecutor`，也就是原样执行，不生成镜像、不注册分支。这个降级很安静，日志里不一定有醒目的提示。存储过程、某些数据库方言、动态拼接得面目全非的 SQL，都可能走到这里。**「SQL 被执行了，但没进事务」有一半是这么来的。**

## 二、镜像不是整行快照

拿这条 SQL 举例：

```sql
UPDATE stock SET count = count - 1 WHERE id = 100;
```

Seata 在业务 SQL 前后各做一次查询，生成两份镜像：

```text
beforeImage:
SELECT id, count FROM stock WHERE id = 100 FOR UPDATE;
-- (100, 10)

业务 SQL:
UPDATE stock SET count = count - 1 WHERE id = 100;

afterImage:
SELECT id, count FROM stock WHERE id = 100;
-- (100, 9)
```

这里有一个很多人以为是「整行快照」的地方：**默认只抓被更新的列和主键**。`client.undo.onlyCareUpdateColumns` 默认是 `true`，所以上面只查了 `id` 和 `count`，不会把 `stock` 表的 `version`、`updated_at`、`warehouse_id` 一起拍下来。

这个默认值是有意的。整行快照会让 undo log 变大，回滚时还会把别人改过的列一起覆盖回去。只抓参与本次更新的列，undo SQL 就只还原这几列，副作用小。

代价是：**undo log 不是一份完整的行备份。** 如果一条 SQL 更新了 `count`，另一个不走 Seata 的进程同时改了 `status`，回滚只会把 `count` 改回去，`status` 保持后者写入的值。Seata 不会替你恢复它没抓过的列。

三种 SQL 的镜像规则不一样：

| SQL | beforeImage | afterImage | 锁键取自 |
| --- | --- | --- | --- |
| UPDATE | 按 WHERE 条件查，带 `FOR UPDATE`，取更新列 + 主键 | 按主键回查，取同样的列 | afterImage |
| DELETE | 按 WHERE 条件查，带 `FOR UPDATE`，取所有列 | 空 | beforeImage |
| INSERT | 空 | 按主键回查插入列 + 主键 | afterImage |

UPDATE 和 DELETE 的 beforeImage 都带 `FOR UPDATE`，这不是为了全局锁，而是为了拿住本地数据库的行锁，防止在「查镜像」和「改数据」之间被别的本地事务插进来。这个本地锁会一直持有到本地事务提交。

INSERT 没有 beforeImage，因为插入前那一行不存在。它的主键从哪来？SQL 里写了就用 SQL 里的值；自增主键靠 JDBC 返回的 generated keys。拿不到主键，afterImage 就建不出来，这条 INSERT 没法回滚。**AT 的表必须有主键**，不是建议，是硬要求。

## 三、五次数据库访问，一条时间线

把一条 UPDATE 在 AT 里的实际动作按时间排开，是五次数据库访问加一次 RPC：

```text
1. SELECT ... FOR UPDATE        // beforeImage，拿本地行锁
2. UPDATE stock SET ...         // 业务 SQL
3. SELECT ... WHERE id = 100    // afterImage，按主键回查
4. RPC: BranchRegister          // 向 TC 抢全局锁（在本地 commit 之前）
5. INSERT INTO undo_log ...     // 写回滚日志（同一个本地事务）
6. COMMIT                       // 本地事务提交，数据对外可见
```

第 1 步到第 3 步在 `AbstractDMLBaseExecutor.executeAutoCommitFalse()` 里完成：先 `beforeImage()`，再 `statementCallback.execute()`，再 `afterImage()`，最后 `prepareUndoLog()`。注意，这时候 undo log 还只在内存里，没写库。

第 4 步发生在 `ConnectionProxy.processGlobalTransactionCommit()`：

```java
private void processGlobalTransactionCommit() throws SQLException {
    try {
        register();                                  // 向 TC 注册分支、抢全局锁
    } catch (TransactionException e) {
        recognizeLockKeyConflictException(e, context.buildLockKeys());
    }
    try {
        UndoLogManagerFactory.getUndoLogManager(this.getDbType()).flushUndoLogs(this);
        targetConnection.commit();                   // 本地提交
    } catch (Throwable ex) {
        report(false);
        throw new SQLException(ex);
    }
    if (IS_REPORT_SUCCESS_ENABLE) {
        report(true);                                // 上报 PhaseOne_Done
    }
}
```

顺序是死的：**先注册分支和抢全局锁，再写 undo log，再本地提交，最后上报。** 这四步里任何一步失败，处理方式都不一样：

- 抢锁失败：`LockConflictException`，按 `client.rm.lock.retryTimes` / `retryInterval` 重试，默认 30 次、10 毫秒一次；
- 写 undo log 失败：本地事务回滚，向 TC 上报 `PhaseOne_Failed`；
- 本地提交失败：同上，数据没提交，undo log 也随本地事务回滚；
- 上报失败：数据已经提交了，TC 那边还认为分支是 `Registered`。这时要靠 TC 的超时扫描或后续重试把状态补上。

第 6 步之后，数据对其他会话可见。全局事务还没结束，但 AT 的一阶段已经做完了。

## 四、分支为什么在 commit 时才注册

这是 AT 和 TCC 的又一个分叉点。

TCC 在 try 之前就注册分支：框架要先让 TC 知道「这个参与者准备干活了」，confirm/cancel 才有对象。Saga 默认连每个 state 的分支都不注册。AT 选择在本地提交前才注册，原因有两个。

第一，AT 要收集锁键。一条业务方法里可能执行了十几条 SQL，分布在同一张表的不同行上。如果每条 SQL 都发一次 `BranchRegisterRequest`，网络开销不说，TC 的锁表也要被写十几次。Seata 的做法是在 `ConnectionContext` 里按 Savepoint 攒锁键，提交前 `buildLockKeys()` 一次性去重、拼成一个字符串，发一次 RPC。

锁键长这样：

```text
stock:100
stock:100,101,102
order_item:1_a,2_b          // 复合主键用 _ 连接
```

同一个资源、不同表的锁键用 `;` 拼起来。TC 收到之后按行拆开，逐行去抢。

第二，AT 的锁是「提交锁」，不是「执行锁」。它要保护的是「本地事务提交」和「全局事务决议」之间的窗口，不是 SQL 执行本身。放到提交前拿，锁的持有时间最短。

这也解释了一个常见现象：两个全局事务并发更新同一行，后一个的 update 语句可能也会成功，因为本地数据库的行锁会先让它们排队；真正报错的是后一个的 `commit()`。如果后一个用的是自动提交模式（`autoCommit=true`），Seata 会把它改成手动提交，在 `executeAutoCommitTrue()` 里把「执行 + 提交」包在锁重试策略里。所以从业务代码看，报错位置还是 `executeUpdate()`，但内部已经是 commit 阶段了。

## 五、全局锁到底锁了什么

TC 侧的锁不是数据库锁，它锁的是一个字符串：`资源 ID + 表名 + 主键`。

file 模式下，`FileLocker` 的结构是：

```text
resourceId → tableName → 128 个 bucket → pk → 持有锁的 BranchSession
```

每个分支持有一个 `lockHolder`，记录自己拿过哪些 bucket 里的哪些 pk。抢锁时逐行 `putIfAbsent`；只要有一行被别人占了，就把这个分支本次已经拿到的锁全部释放，返回失败。这个「整批释放」很重要：它避免了半个分支持锁、半个分支不持锁的中间状态。

db 模式下，这把锁落在 `lock_table` 里，`row_key` 是主键，`xid` 和 `branch_id` 记录持有者。redis 模式下落在 `SEATA_GLOBAL_LOCK*` 系列 key 上。raft 模式下，锁在 leader 本地，释放通过 raft 任务复制。

但不管哪种存储，它都只拦得住**同样来抢这把锁的 Seata 写操作**。一条不走代理的 SQL、一个直连数据库的脚本、一个没有 `DataSourceProxy` 的数据源，都能直接改这行数据。全局锁不是数据库约束，它没有数据库层面的强制力。

那怎么保证读到的数据不是别人一阶段提交、随后又回滚的脏数据？Seata 的默认隔离级别是读未提交。要在 AT 里拿到接近读已提交的行为，得在事务开始时用代理执行 `SELECT ... FOR UPDATE`，把要改的行先查一遍。`SelectForUpdateExecutor` 会在拿到本地行锁之后，向 TC 查一次全局锁：

- 如果别人持有全局锁，释放本地锁、睡一会、重查；
- 如果没人持有，继续往下走。

这样读到的数据，要么是对方已经全局提交的，要么是对方已经回滚完的，不会读到一个「稍后会被回滚」的中间值。代价是每条要改的行多一次 `SELECT ... FOR UPDATE` 和一次 TC 查询。

`@GlobalLock` 是这条路的轻量版：只查全局锁，不注册分支、不写 undo log，适合「我要读一下这行，确认没有全局事务正在改它」的场景。

## 六、只读、无主键和批量

**只读 SQL 不产生分支。** `ConnectionProxy.register()` 的第一行是 `if (!context.hasUndoLog() || !context.hasLockKey()) return;`。没有 undo log，就没有分支。一个全局事务里查了二十张表，TC 那边可能一个分支都没有。这不是 bug，是设计：读操作不需要回滚。

**无主键的表没法用 AT。** 镜像按主键回查，锁键按主键构造，undo 按主键定位。没有主键，这三件事都做不了。Seata 会在构建镜像或锁键时抛错，而不是悄悄降级。给业务表加主键，是接入 AT 的前置条件。

**批量更新会生成多个锁键，但仍然只注册一个分支。** `UPDATE stock SET count = count - 1 WHERE id IN (100, 101, 102)` 的 beforeImage 会查出三行，锁键是 `stock:100,101,102`，一次 RPC 带走。undo log 里也会有三行镜像，回滚时按主键逐行还原。

**解析不了的 SQL 会退化成 `PlainExecutor`。** 这是最隐蔽的坑。业务 SQL 执行成功，本地事务也提交了，但 Seata 没生成镜像、没抢锁、没注册分支。等全局回滚时，TC 根本不知道这条 SQL 存在。上线前把「哪些 SQL 走了代理、哪些退了原生」打成日志或指标，比出事之后再猜要省事得多。

## 七、踩坑清单

- 以为 update 成功就代表分支注册成功：注册发生在 commit 前，冲突也在 commit 前才暴露。
- 表没有主键，或者联合主键里包含可空列：镜像和锁键都建不起来。
- 用 `ONLY_CARE_UPDATE_COLUMNS=false` 抓了整行，回滚时把别人改的列也覆盖回去，制造新的脏写。
- 一条 SQL 解析失败，退化成 `PlainExecutor`，业务无感知，回滚时这条 SQL 不在账上。
- 在全局事务里用 `SELECT ... FOR UPDATE` 却没走代理：本地锁拿到了，TC 的全局锁没查，脏读窗口还在。
- 以为全局锁能拦住所有并发写：不走 Seata 的写入可以直接穿过。
- 把大事务拆成很多小 SQL，锁键攒了几百个，一次 `BranchRegisterRequest` 超过传输上限：注册失败，整个分支回滚。

## 思考题

1. 一条 UPDATE 更新了 3 行，undo log 里有几份行镜像？锁键里有几个主键？
2. 业务方法里先 `SELECT` 再 `UPDATE`，`SELECT` 没加 `FOR UPDATE`。另一个全局事务在两步之间改了同一行并回滚，你的 `UPDATE` 会读到什么？undo log 记的 beforeImage 是什么？
3. 为什么 Seata 要求 AT 的表必须有主键？如果没有主键，能不能用「所有列」当条件来替代？
4. 你的系统里有哪些 SQL 会解析失败、退化成 `PlainExecutor`？如果不知道，怎么在一周内把它们找出来？
