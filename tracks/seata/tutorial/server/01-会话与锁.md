# 会话与锁管理

TC 的账本有两层：一层是「事务走到哪了」，另一层是「哪一行被谁占着」。

前者是会话，后者是锁。两者都由 TC 管理，但存储、生命周期、释放时机完全不同。把它们混在一起看，就会得出「commit 返回了锁一定放了」「回滚失败锁一定没了」这类错误结论。

---

## 一、会话管理：一个 XID 的全部状态

`SessionHolder` 是 TC 的会话入口。启动时按 `store.session.mode` 加载对应的 `SessionManager`：

| 模式 | 实现 | 会话在哪 |
| --- | --- | --- |
| file | `FileSessionManager` | 内存 + 本机 WAL |
| db | `DataBaseSessionManager` | `global_table` / `branch_table` |
| redis | `RedisSessionManager` | `SEATA_GLOBAL_*` 等 key |
| raft | `RaftSessionManager` | leader/follower 内存 + raft log |

`SessionHolder.init()` 之后，`findGlobalSession()` 和 `lockAndExecute()` 是所有请求的公共入口。`lockAndExecute()` 会锁住 `GlobalSession` 内部的 `ReentrantLock`，执行回调，再在 finally 里解锁。

这个锁不是全局行锁，它只防止同一个 XID 的会话被并发修改。比如 TC 正在处理 commit，另一个线程同时给它加分支，必须串行。

`GlobalSession` 里存的是：

- XID、transactionId、applicationId、transactionServiceGroup；
- transactionName、timeout、beginTime、status；
- branchSessions 列表；
- 会话级别的锁、生命周期监听器。

`BranchSession` 里存的是：

- branchId、xid、transactionId、resourceId、branchType；
- status、clientId、applicationData；
- lockKey、lockStatus、lockHolder。

一个全局会话可以有很多分支；每个分支持有自己抢到的锁。会话结束时，分支要逐个删；锁要按分支释放。

## 二、状态机：哪些状态能跳，哪些不能

`GlobalSession.changeGlobalStatus()` 是唯一改全局状态的地方。它先让 `SessionManager.onStatusChange()` 落库，再把内存状态改掉，最后通知生命周期监听器。

`SessionStatusValidator` 会拦住「提交态 ↔ 回滚态」的互跳。比如 `Committing` 不能直接变 `Rollbacking`；要回滚，必须先走到一个允许回滚的中间态。这个校验是为了防止 TC 在并发/重试时把一笔已经决定提交的事务又回滚掉。

`SessionLifecycle` 定义了完整的生命周期回调：

```text
onBegin / onStatusChange / onAddBranch / onRemoveBranch
onLockBranch / onUnlockBranch / onEnd
```

file/db/redis/raft 的 `SessionManager` 在这些回调里做各自的持久化。比如 db 模式在 `onStatusChange` 里更新 `global_table.status`，在 `onAddBranch` 里插 `branch_table`；raft 模式把回调封装成 raft task，等多数派提交后再改内存。

## 三、锁管理：RowLock 和 LockManager

`LockManager` 的接口很窄：`acquireLock`、`releaseLock`、`isLockable`、`cleanAllLocks`、`updateLockStatus`。

`AbstractLockManager` 负责把 `lockKey` 拆成 `RowLock` 列表。`lockKey` 的格式是：

```text
tableName:pk1,pk2,pk3
composite_table:pk1_a,pk2_b
```

每个 `RowLock` 只包含表名和主键。具体的存储由 `Locker` 实现决定：

- `FileLocker`：`LOCK_MAP`，resourceId → table → 128 个 bucket → pk → `BranchSession`；
- `DataBaseLocker`：`lock_table`，`row_key` 主键，`status` 0/1；
- `RedisLocker`：`SEATA_GLOBAL_LOCK*` / `SEATA_ROW_LOCK_*`；
- `RaftLocker`：leader 本地锁 + raft 任务复制释放。

`FileLocker.acquireLock()` 逐行 `putIfAbsent`。如果某一行已经被别的分支占了，它会把当前分支本次已经拿到的锁**全部释放**，再返回失败。这个「整批释放」是为了避免半个分支持锁、半个分支不持锁的中间状态。

`AbstractLockManager` 还负责把 `lockKey` 里的复合主键拆成 `RowLock`。复合主键用 `_` 连接；如果主键值本身包含 `,` 或 `_`，锁键就会歧义。Seata 在 `buildLockKey()` 里对非法字符做了校验，接入时不要用带这些字符的业务主键。

## 四、锁的释放时机：三个容易讲错的地方

**AT 提交：锁在 commit 受理时释放，不是二阶段完成后。**

`DefaultCore.commit()` 在把状态改成 `AsyncCommitting` 后立刻 `globalSession.clean()`。`clean()` 调 `releaseGlobalSessionLock()`；`GlobalSession.unlockBranch()` 会跳过 `Committing` / `CommitRetrying` / `AsyncCommitting` 三种状态，避免重复释放。

所以 TM 收到 `Committed` 时，全局锁已经放了，但分支的 `BranchCommitRequest` 可能还没发，undo_log 也可能还在。

**回滚：锁在回滚成功后释放。**

分支逐个 `BranchRollback`，成功的删分支并解锁；全部成功后 `endRollbacked()` → `globalSession.end()`，`end()` 对两阶段成功状态先 `clean()` 再删会话。

**回滚失败：默认不释放锁。**

`endRollbackFailed()` / `endCommitFailed()` 走到 `end()`，只有 `server.rollbackFailedUnlockEnable=true` 才 `clean()`。默认是 `false`。这是刻意保护：回滚没完成之前，不能让新事务改这行，否则谁也不知道最终该是什么值。

这解释了为什么一个回滚失败的分支会一直占着全局锁，后面的业务一直报锁冲突。它不是「锁泄漏」，是「数据还没回滚干净」。

## 五、会话锁 vs 全局行锁

两个锁经常被混为一谈：

| 锁 | 在哪 | 锁什么 | 什么时候释放 |
| --- | --- | --- | --- |
| 会话锁 | `GlobalSession` 内部 `ReentrantLock` | 同一个 XID 的会话修改 | `lockAndExecute` 回调结束 |
| 全局行锁 | `LockManager` | resource + table + pk | AT 提交受理时 / 回滚成功后 |

会话锁只在 TC 进程内生效，用来串行化同一个 XID 的请求；全局行锁跨 TM/RM，用来防止两个 XID 改同一行。两者不是一回事。

`BranchSession` 里的 `lockHolder` 只记录这个分支拿过哪些 bucket 的哪些 pk，方便回滚/结束时批量释放。它不参与跨进程协调。

---

## 六、踩坑清单

- 以为 commit 返回后全局锁一定放了：AT 是放了，但 TCC/Saga/XA 本来就没有 TC 全局锁。
- 以为回滚失败会自动放锁：默认不放，`rollbackFailedUnlockEnable=false`。
- 把 `GlobalSession` 的会话锁当成分布式锁：它只在本 TC 进程内有效。
- 锁键里用带 `,`/`_` 的主键值：锁键解析会歧义，Seata 会校验并报错。
- file 模式多 TC 共享会话：每个 TC 各有一份 sessionMap，锁也各有一份。
- 只看 `lock_table` 判断锁：file/redis/raft 模式的锁不在 `lock_table` 里。
- 回滚失败后手工删锁但不校准数据：下一次重试会把错误数据再写一遍。

## 思考题

1. 同一笔全局事务的两个请求同时到 TC，一个 commit、一个 branchRegister，谁会等谁？靠哪个锁串行化？
2. AT 提交时全局锁已经释放，但 undo_log 还在。此时另一个全局事务改同一行，会发生什么？
3. 回滚失败后默认不释放全局锁，这个行为保护了什么？如果改成释放，可能造成什么数据问题？
4. file 模式和 db 模式的「会话锁」和「全局行锁」分别存在哪里？多 TC 部署时哪些能共享，哪些不能？
