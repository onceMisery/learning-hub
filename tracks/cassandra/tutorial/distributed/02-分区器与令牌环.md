# 分区器与令牌环：一行数据摊给谁

先看一个业务同学撞墙的现场。他往 `users` 表插了 id=47 的阿福，接着想按名字反查：`SELECT * FROM users WHERE name = '阿福2'`。cqlsh 直接回了一句 `Cannot execute this query as it might involve data filtering`——除非在句尾加 `ALLOW FILTERING` 才肯跑，而加上之后全表扫描，5 亿行的表直接跑不动。他不服气：`WHERE id = 47` 明明毫秒出结果，凭什么换个列就不行？

差别不在 SQL 引擎的优化器，在数据摊位的方式上：**Cassandra 只认识一个「门牌号」——分区键**。`id` 是分区键，驱动和协调者能就地算出这行数据住在哪几台机器上，直接上门；`name` 只是普通列，没人知道「叫阿福2 的行」散落在哪些节点，只能挨家挨户问（全表扫描）。这个「算出摊位」的规则，就是本章的主角：分区器 + 令牌环。看懂它，你会知道为什么建表的第一件事是围着查询设计分区键——分错键，后面全是修补不回来的扫描。

全章继续跟 id=47 走，把它「算」到机器上：

```text
贯穿全章的一次定位（沿用全轨道口径）：
5 个节点 node1~node5，keyspace demo，RF=3

第 1 步  分区键 id=47（字节串 "47"）
第 2 步  murmur3 哈希 → token ≈ -9.0×10^18（64 位有符号数，本值示意）
第 3 步  token 落环，从它顺时针数 3 个节点：
         node2 → node4 → node5
第 4 步  写入/读取这行，协调者只找这三台 —— node1 与它无关

第 5 章说过：node4 挂了，剩下 node2、node5 照样凑齐 QUORUM(2)。
本章回答：这个名单当初是怎么算出来的。
```

## 一、主键的三层：分区键、聚簇列、普通列

CQL 的 `PRIMARY KEY` 不是一层，是三层各管一件事：

```sql
-- 一张表两种主键设计，摊法完全不同
CREATE TABLE users (                       -- 单列分区键
  id int PRIMARY KEY, name text, age int
);
CREATE TABLE events (                      -- 复合分区键 + 聚簇列
  tenant text, device_id int, ts timestamp,
  PRIMARY KEY ((tenant, device_id), ts)
) WITH CLUSTERING ORDER BY (ts DESC);
```

- **分区键**（`id`；或 `(tenant, device_id)` 整体）：参与哈希算 token 的只有它。同一分区键的所有行落同一个节点、在盘上物理相邻——**分区是数据移动和存储的最小单位**。
- **聚簇列**（`ts`）：分区内按它排序。查「tenant=A、device=47 最近一小时」只需要读一个分区内的一段——这是 Cassandra 范围查询唯一的高效形态：**分区内有序，分区间无序**。
- **普通列**（`name`）：既不参与定位也不参与排序。按它过滤 = 在分区内逐行翻找，`ALLOW FILTERING` 就是引擎在跟你说「这个条件我没法用来定位，只能暴力筛」。

类比：一张楼栋分布表。分区键是「楼栋号」——先靠它定位到唯一的楼；聚簇列是「门牌排序」——进了楼按顺序找房号；普通列是「住户姓名」——想按姓名找人，只能挨户敲门。Cassandra 高效的查询永远是「先定楼、再按序取一段」。

拿两张表各查一次，感受一下「能不能定位」的差别：

```text
举例：三个查询，三种命运（events 表：PRIMARY KEY ((tenant, device_id), ts)）

① SELECT ... WHERE tenant='A' AND device_id=47 AND ts > '2026-10-01'
   分区键齐了（定位到楼）、ts 是聚簇列（楼内取一段）→ 高效，只碰一个分区
② SELECT ... WHERE tenant='A'
   分区键只给了一半：(tenant, device_id) 整体才是分区键
   → 不知道 device_id，就得把租户 A 的所有分区逐个问 → 扫描
③ SELECT ... WHERE name='阿福2'（users 表）
   name 连主键都不是 → ALLOW FILTERING，逐行筛
能不能高效，在建表那天就定死了——这就是「查询驱动建模」。
```

还有一个容易被忽略的物理事实：**同一个分区的所有行，永远在同一个节点、同一批 SSTable 里连续存放**。分区是磁盘上和内存里的最小搬运单位——第 3 章会看到 SSTable 以分区为单位顺序铺开，第 14 章会看到节点间搬数据也按分区段流式传输。一个分区多大，直接决定一次「读一个分区」要搬多少字节。

CQL 还留了一个自查工具：`token()` 函数（`cql3/functions/TokenFct.java:33`），能直接算并显示任意分区键的 token——建表后拿它验证「这两行会不会挤在同一个分区」，是数据建模时的常备动作。

## 二、分区器：把任意字节串变成环上一个点

「算 token」的规则叫分区器（partitioner）。集群只有一个分区器，建集群时定死、不可改——换了它，所有数据的摊位全部重算，等于换了一个集群。出厂默认写在 `conf/cassandra.yaml:420`：

```yaml
partitioner: org.apache.cassandra.dht.Murmur3Partitioner
```

它对分区键做的事，源码里就三步（`dht/Murmur3Partitioner.java`）：

1. **哈希**：`getHash`（`:404-414`）调 `MurmurHash.hash3_x64_128(key, 0, 0, hash)`——对分区键的字节做 MurmurHash3 x64 128 位变体，种子 0，取回两个 64 位；
2. **取半**：`getToken`（`:315-317`）拿 `hash[0]` 包成 `LongToken`——**token 就是那个 64 位有符号整数**，取值范围 [-2^63, 2^63-1]；
3. **包装**：`decorateKey`（`:102-105`）把「原始键 + token」打包成 `DecoratedKey`（接口在 `db/DecoratedKey.java`，7.0 已移到 db 包下）——之后引擎内部排序、比较、路由用的都是它，原始键反而退居二线。

两个边角值得知道：空分区键返回 `MINIMUM`（token 环的零点，`:318-319`）；Murmur3 是**非加密**哈希——它追求快和雪崩（输入差一位、输出面目全非），不追求抗碰撞攻击，这对摊数据恰好是正确的取舍。类比：给每行数据的门牌做「掷骰子定位」——骰子要快、要公平（分布均匀），不需要防作弊。

把 "47" 的旅程摊开成一张分步表，每步都能在源码里对上号：

```text
举例：id=47 的哈希分步（数值示意，规则来自源码）
第 0 步  分区键字节串："47" → 0x34 0x37（两个字节）
第 1 步  MurmurHash.hash3_x64_128(0x34 0x37, 种子=0)
         → 产出 hash[0]、hash[1] 两个 64 位（我们只用第一个）
第 2 步  token = hash[0] ≈ -9.0×10^18（64 位有符号，示意值）
第 3 步  DecoratedKey = (token, "47")——从此引擎只拿 token 比大小
换一个键立刻体会到「雪崩」：
token("48") ≈ +7.2×10^18——输入只差一个字节，输出从 -9 跳到 +7，
中间隔了大半个环。没有局部性，正是均匀性的来源。
```

为什么不用 MD5/SHA？三个理由：快一个数量级；64 位空间对亿级集群的碰撞概率足够低（2^63 ≈ 9.2×10^18 的空间里随机放 10^12 个键，碰撞期望约 10^24 分之一量级，可以忽略——「生日悖论」在这里帮忙而不是添乱）；雪崩性质保证相邻的键（`user_1`、`user_2`）落在环上毫不相干的位置——**数据均匀不靠键的分布，靠哈希把任何分布都打均匀**。

## 三、令牌环与副本选择：顺时针数 RF 个

token 的全序天然画成一个环：把 [-2^63, 2^63-1] 首尾相接，每个节点认领环上若干个点，一行数据的 token 落在环上，**从它顺时针遇到的头 RF 个节点，就是这行数据的全部副本**。环的秩序由 `Token` 的全序保证（`dht/Token.java:43`：`abstract class Token implements RingPosition<Token>`——环位置是一个可比较的类型，这是整个机制的数学地基）。

拿 id=47 算一遍（数值示意，机制与源码一致）：

```text
举例：id=47 的副本定位（无 vnode 的简化环，5 节点各认领 1 个 token）
环（按 token 升序，首尾相接）：
  node5(-22.1) → [token(47)=-9.0] → node2(+3.7) → node4(+11.2) → node1(+18.9) → 回到 node5

从 -9.0 顺时针数 3 个：node2 → node4 → node5    ← RF=3 的自然副本
node1 排第 4，与这行数据无关——不是它不称职，是环上的座次决定的。

换个键验证：token(id=48)=+7.2 落在 node2 与 node4 之间
  顺时针数 3 个：node4 → node1 → node5
  同一张表，id=47 和 id=48 的副本名单差了两台——哈希打散到什么程度，可见一斑。
```

这套「顺时针取 RF 个」的算法在复制策略里（`locator/AbstractReplicationStrategy.java:55` 是它们的共同基类），两种常用策略只是「在哪个圈里顺时针」不同：

- **SimpleStrategy**（`locator/SimpleStrategy.java:54`，`calculateNaturalReplicas` 在 `:82-89`）：不区分机房，全环顺时针数 RF 个。演示集群的 keyspace demo 用的就是它；
- **NetworkTopologyStrategy**（`locator/NetworkTopologyStrategy.java:73`，`calculateNaturalReplicas` 在 `:217-221`）：**每个数据中心独立算**——DC1 攒够 RF1 个、DC2 攒够 RF2 个；同 DC 内还尽量把副本摊到不同机架（rack），避免一个机架断电带走多份副本。生产环境一律用它。

拿一个双机房的生产配置把 NTS 算一遍：

```text
举例：NetworkTopologyStrategy，DC1 副本 2、DC2 副本 1
CREATE KEYSPACE prod WITH replication =
  {'class': 'NetworkTopologyStrategy', 'DC1': 2, 'DC2': 1};

id=47 的定位分两个圈各自数：
  DC1 的环（只有 DC1 的节点参与）：node2 → node4          ← 攒够 2 个，停
  DC2 的环（只有 DC2 的节点参与）：node9                  ← 攒够 1 个，停
最终名单 = {node2, node4, node9}——5 节点演示集群外加一个想象中的 DC2。
机房意义：DC1 整体掉电，DC2 里仍有 1 份可读可写（降级但不丢）；
rack 意义：DC1 内两副本尽量分属不同机架，一个机架断电最多丢一份。
```

注意一个要害：**名单是纯函数**——输入（分区键、环状态、策略、RF）一样，输出必然一样，不依赖任何「当时谁空谁忙」的运行时信息。所以协调者每次读写都现场重算一遍（第 10 章），所有节点算出的名单完全一致，不需要互相打听「数据你放哪了」。这也是第 5 章 node4 挂掉后 node1 能立刻改道的原因：名单算法是本地的，只有「跳过谁」来自 gossip。

顺带一个 7.0 的重要变化：老版本里管环的类叫 `TokenMetadata`（`locator/TokenMetadata.java`），master 上这个类已经不在了——环、节点目录、schema 统一收进 `tcm/ClusterMetadata.java:102`（`:113` 的 `directory`、`:114` 的 `tokenMap`，由 CEP-21 的集群元数据服务管理）。读老资料遇到 TokenMetadata 时，把它理解成「ClusterMetadata 里管环的那部分」即可。

## 四、vnodes：一个节点 16 段，均匀靠洗牌

简化环里每节点认领 1 个 token，有个致命弱点：node4 挂掉时，它那一段的流量全部压给顺时针下一个节点——**单点段太大**。现实的集群每节点认领一小把 token，叫虚拟节点（vnode）。出厂默认在 `conf/cassandra.yaml:42`：

```yaml
num_tokens: 16
```

每节点 16 段，5 节点就是环上 80 段交错洗牌。效果：node4 挂掉，它 16 个小段的数据分别由**不同的**顺时针邻居接手，负载被摊成 16 份而不是压垮一个倒霉蛋；新节点入环接走的也是 16 个小段，来自不同贡献者。类比：不要把家当装进一辆货车（一个 token），拆成 16 个行李箱分给 16 辆车——翻一辆，只丢 1/16 的运力。

老资料常写「num_tokens=256」，为什么新版默认降到 16？段越多越均匀，但每一段都是一份独立的开销：repair 要按段对账、流式传输按段起任务、索引按段建。256 段时这些按段计费的操作贵到离谱（这是 3.x 时代 repair 慢的主因之一），于是 4.0 起默认 16，均匀性缺口改由**智能分配**补：`allocate_tokens_for_local_replication_factor: 3`（`conf/cassandra.yaml:59`，默认已启用）让新节点入环时不是随机掷 16 个 token，而是由 `BootStrapper` 的 `allocateTokens`（`dht/BootStrapper.java:270-291`，委托 `TokenAllocation.allocateTokens`）挑「能让 RF=3 视角下各节点负载最均衡」的 16 个位置——**少而准的段，替代多而随机的段**。

```text
举例：随机 16 段 vs 智能分配 16 段（示意，负载 = 持有 token 段的份额）
随机分配：5 节点负载 = 19% / 21% / 18% / 24% / 18%（最坏与最好差 6 个点）
智能分配：5 节点负载 = 20.2% / 19.9% / 20.1% / 19.8% / 20.0%
代价：智能分配要求同一时刻只有一个节点在加入（否则互相看不到对方的计算）。

按段计费的账（为什么 256 贵）：
repair 对账的单位是「段区间 × 副本对」：
  16 段/节点 × 5 节点 = 80 段 → 每次 repair 约 80 个对账区间
  256 段/节点 × 5 节点 = 1280 段 → 16 倍的区间数、16 倍的 Merkle 树与流式任务
均匀性收益却边际递减：80 段的方差已经不大，1280 段只是锦上添花。
```

vnode 还悄悄改写了「失败接盘」的粒度。单 token 时代 node4 挂掉，它那一段 100% 压给顺时针下一个节点；16 段时代，每一段的顺时针下家各不相同——16 个邻居各接 1/16，等于把故障流量做了负载均衡。第 14 章讲 bootstrap/decommission 时会看到，搬数据也是按这 16 段分别流式传输的。

## 五、分区的大小与形态：一个不可拆的槽

把前面四节拧成一句工程判断：**一个分区 = 一个不可拆的槽**。哈希环决定了它放在谁家，主键设计决定了它有多大——而它的大小，从建表起就注定了读写、修复、搬运的全部代价形态。

users 表是「一分区一行」的形态：id=47 一个分区只有一行，读写都是一个最小单元，谁也不挨谁。events 表是「一分区多行」的形态：租户 A 的设备 47 之下可以挂百万条事件——它们永远在一起，一起被读、一起被修、一起被搬。两种形态没有优劣，只有匹配不匹配：

| 形态 | 典型表 | 读的形态 | 风险 |
| --- | --- | --- | --- |
| 一分区一行 | users（id 主键） | 点查，一个分区一个小单元 | 键本身倾斜时热点集中在少数分区 |
| 一分区多行 | events（(tenant, device_id)+ts） | 一把取出一段时序，局部性极好 | 分区无上限地长大 → 「大分区」 |

大分区为什么是灾难？顺着本轨道已有的线索数一遍：读侧，一个分区在 SSTable 里是连续存放的（第 3 章），读一个大分区等于搬一大段连续字节，还要在 memtable 里完整持有它的最新版本（第 2 章）；修复侧，反熵对账的粒度是 token 段（第 13 章），一个超大分区让「只传差异」退化成「整段重传」；搬运侧，节点入环/退场按分区段流式传输（第 14 章），大分区让任务粒度失衡——一个任务顶别人一百个。唯一的解法在建模：**把大实体拆成多个分区键**（按时间窗切段、按桶散列），让哈希环有机会把它摊开。

最后回到开头那个 `ALLOW FILTERING` 报错。现在可以完整说清它为什么「might involve data filtering」：Cassandra 的执行模型里，能用来**定位**的只有分区键、能用来**裁剪范围**的只有聚簇列前缀，剩下的条件统统要拿到数据之后逐行判断。报错不是引擎能力差，是它在提示「这个查询没有用上你能提供的定位信息」——修它的方式通常不是加索引（第 11 章的 SAI 另说），而是改主键设计，让查询条件重新变成定位信息。

```text
举例：同一个需求的两种建模，命运分岔
需求：按名字查用户。
坏建模：PRIMARY KEY (id)，按 name 查 → ALLOW FILTERING 全表扫。
好建模：PRIMARY KEY ((name_bucket), name, id)——名字先哈希成 128 个桶，
       查询带 name_bucket=hash('阿福2') AND name='阿福2' → 定位到桶内一小段。
代价：好建模要多维护一个桶列——又回到那句话：建模围着查询转。
```

## 六、和 RocksDB 摆在一起看：键空间怎么摊

RocksDB 不需要分区器——它是单机库，键空间天然就是一根全序数轴，`comparator` 定义这根轴的刻度，所有数据都在一个进程的内存里排座次。「摊给谁」这个问题在它的世界里不存在：**只有一个「谁」，就是本进程**。把两边摆在一起，摊法的差异会同时解释很多行为差异：

| 维度 | RocksDB | Cassandra |
| --- | --- | --- |
| 键空间形状 | 一根全序数轴（comparator 定刻度） | 一个哈希环（partitioner 把键投影到环上） |
| 「摊给谁」 | 不存在：单进程 | 顺时针 RF 个节点，哈希决定 |
| 均匀性靠什么 | 不需要（单机） | murmur3 雪崩 + vnode 洗牌 + 智能分配 |
| 范围扫描 | 全库有序，任意范围一把梭 | 分区内有序；跨分区 = 多台机器散射 |
| 热点键 | 无此概念（都在一台机器上） | 一个分区 = 一个不可拆的槽，热键会烧坏单节点 |
| 改排序规则 | 重开库换 comparator | 不可能：partitioner 建集群时定死 |

最深的差异在**有序性花在哪**。RocksDB 把全库有序当作 LSM 的地基——顺序写盘、顺序归并、迭代器一路扫过去，有序是它的性能来源。Cassandra 故意放弃了全局有序，换来「均匀」：哈希把任何键分布都打匀，任何一台机器都只承担 1/N。代价是跨分区的范围查询变成散射（`WHERE token(id) > X AND token(id) < Y` 按环序扫，不按业务序；按业务列的范围查干脆做不了）——所以 Cassandra 的数据建模永远是「查询驱动」：想清楚按什么查，再把那什么设成分区键。RocksDB 用户转过来最容易栽的就是这一步：把 B+ 树时代「随便建索引、随便范围查」的习惯带进来。

一句话收束：**RocksDB 用一根数轴换顺序的世界，Cassandra 用一个环换均匀的世界；数轴上范围是免费的，环上均匀是免费的——各付各的账。**

## 这一章留下的线索

- **主键三层**：分区键定位到节点、聚簇列在分区内排序、普通列只能暴力筛（`ALLOW FILTERING` 的由来）；`token()` 函数可自查摊位（`cql3/functions/TokenFct.java:33`）；
- **分区器建集群定死**：murmur3 → 64 位 token（`dht/Murmur3Partitioner.java:315-317`、`:404-414`），DecoratedKey = 原始键 + token；非加密哈希换速度与雪崩；
- **顺时针数 RF 个**：SimpleStrategy 全环数（`:82-89`），NetworkTopologyStrategy 每 DC 独立数 + rack 均摊（`:217-221`）；环秩序由 `Token` 全序保证（`dht/Token.java:43`）；
- **vnode 16 段 + 智能分配**：失败负载摊 16 份；`allocate_tokens_for_local_replication_factor`（yaml:59）+ `BootStrapper.allocateTokens` 用「少而准」替代 3.x 的「多而随机」；
- **名单是纯函数**：输入一样输出必然一样，不依赖运行时负载——所有节点各自重算、结果天然一致，「跳过谁」才交给 gossip；
- **一个分区 = 一个不可拆的槽**：大分区让读、修、搬全部按整段付费，唯一解法是建模时把大实体拆成多个分区键；
- **7.0 的环管账本换了主人**：TokenMetadata 已移除，`ClusterMetadata`（`tcm/ClusterMetadata.java:102`）的 directory/tokenMap 接管——老资料要带着这个映射去读。

下一章把「三个副本」用起来：写入要几个确认、读取问几个人，才叫「一致」——[一致性与副本：三个副本几个确认](../distributed/03-一致性与副本.md)。
