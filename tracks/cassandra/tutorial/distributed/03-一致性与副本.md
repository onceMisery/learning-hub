# 一致性与副本：三个副本几个确认

先看一个面试现场。候选人从 MySQL 转 Cassandra 两年，简历上写着「熟悉 Cassandra 调优」。面试官只问了一句：你们的写入用的一致性级别是什么？答：QUORUM。又问：为什么是 QUORUM，不是 ONE？答：……因为文档说 QUORUM 更安全。追问：node4 挂掉的时候，QUORUM 写还能成功吗？CL=ALL 呢？——他卡住了。他知道调这些参数，但说不清每个参数背后到底向谁多要了一份承诺。

这不是背参数的问题。Cassandra 把「一致性」做成了**每次请求自带的一个旋钮**：同一行数据、同一个集群，你可以一条请求只要 1 个副本确认（ONE），下一条要 2 个（QUORUM），再下一条要全部 3 个（ALL）。旋钮拧到哪，决定了这笔写要等多久、挂几台还能活、读到的数据有多新。看懂这个旋钮的刻度表、它在写路径和读路径上各怎么执行、以及它和副本数 RF 之间那个著名的 `W+R>RF` 不等式，上面三个追问就都有了答案。

全章继续跟那行数据走，集群和术语与前两章完全一致：

```text
贯穿本章的一行数据与请求（沿用全轨道口径）：
集群：node1 ~ node5，keyspace demo，RF=3
id=47 这一行：副本名单 {node2, node4, node5}（第 6 章顺时针数出来的）
UPDATE users SET name = '阿福2' WHERE id = 47;   ← 本章反复用的那笔写
SELECT name FROM users WHERE id = 47;            ← 本章反复用的那次读

关键数字：RF=3，QUORUM = ⌊3/2⌋+1 = 2
node4 于 14:00:00 卡死（第 5 章 phi=8.0 在 14:00:18~:20 确认它 DOWN）
```

一句话预告结论：QUORUM 写 + QUORUM 读，3 个副本里写等 2 个、读凑 2 个，两边必然在至少 1 个副本上相遇——这就是「必见新值」的数学保证。

## 一、一致性级别：每次请求自带的旋钮

先纠正一个常见误解：**CL（Consistency Level）不是集群配置，是请求参数**。集群配置里定的是 RF（每个 keyspace 放几份副本，`conf/cassandra.yaml` 里建 keyspace 时写死）；CL 是客户端在每条 CQL 请求里附带的，同集群同表，每条都可以不一样。类比：RF 是「一个快递发几份拷贝」，CL 是「这一单你要几个签收人回话才算送到」——发几份是仓库的规矩，等几个签收是这一单寄件人的脾气。

CL 的全部刻度都定义在一个枚举里（`db/ConsistencyLevel.java:37-52`）。每个刻度翻译成一个数：**blockFor——这笔请求要等几个副本回话**（`db/ConsistencyLevel.java:138-179`）。拿 RF=3 的 demo 集群把常用档位算一遍：

| CL | blockFor（RF=3 时） | 计算规则 | 语义一句话 |
| --- | --- | --- | --- |
| ANY | 1 | 特殊：hint 也算（`db/ConsistencyLevel.java:145-146`） | 只要协调者接了单并留下 hint 就算成功，0 个真实副本确认也行 |
| ONE / LOCAL_ONE | 1 | 固定 1（`:142-144`） | 任意 1 个副本回话即成功；LOCAL_ONE 限定本 DC 的那 1 个 |
| TWO / THREE | 2 / 3 | 固定（`:147-150`） | 字面意思，很少用 |
| QUORUM | 2 | ⌊RF/2⌋+1（`:96-99`） | 过半数副本确认；RF=3 时是 2 |
| LOCAL_QUORUM | 2（本 DC 内） | 本 DC 的过半数（`:101-111`） | 跨 DC 部署时只等本 DC 过半，避免跨洋往返 |
| EACH_QUORUM | 每 DC 各自过半，加总（`:163-175`） | NTS 专用 | 写路径可用的「每个机房都过半」；读路径不支持 |
| ALL | 3 | 全部副本（`:156-157`） | 一个都不能少；可用性最差、一致性最强 |

两个容易踩的坑。第一，**ANY 不能用于读**——读一个「可能只存在于 hint 里」的值没有意义，`validateForRead` 直接拒绝（`db/ConsistencyLevel.java:220-227`）。第二，QUORUM 的「2」不是拍脑袋：过半数意味着任何两个「过半集合」必然相交，第五节靠的就是这条。

```text
举例：同一个 keyspace，三条请求各拧各的旋钮
INSERT ... （CL=ONE）     → 等 1 个 ack，node2 回话即返回
INSERT ... （CL=QUORUM）  → 等 2 个 ack，node2+node4 回话才返回
INSERT ... （CL=ALL）     → 等 3 个 ack，node5 不回话就一直等（或超时）
RF 是 keyspace 的属性（3 份），CL 是每条请求的属性（1/2/3 随时换）。
```

demo 集群是单 DC，但生产部署几乎都是多机房，这时 LOCAL_* 和 EACH_QUORUM 才真正登场。多 DC 下复制策略换成 NetworkTopologyStrategy，每个 DC 各有各的 RF，quorum 也按 DC 各算各的（`db/ConsistencyLevel.java:101-111`）：

```text
举例：2 个 DC（dc1、dc2 各 RF=3）时各档 blockFor 的账
QUORUM       全体过半：⌊6/2⌋+1 = 4 → 至少跨 2 个 DC 等回话，含一次跨洋往返
LOCAL_QUORUM 只看本 DC：⌊3/2⌋+1 = 2 → 远端 dc2 的 3 份照样写，只是不等它们
EACH_QUORUM  每 DC 各过半再相加：2 + 2 = 4（写专用，读不支持）
选型直觉：同城多机架用 QUORUM；异地多活用 LOCAL_QUORUM 保延迟；
要让「每个机房此刻都过半」才安心的写（如金融扣款）用 EACH_QUORUM。
```

还有一点值得单说：谁在替你「数回话」。不同 CL 用的计数器不一样——普通档位用 WriteResponseHandler，LOCAL_* 换成只数本 DC 回话的 DatacenterWriteResponseHandler，EACH_QUORUM 用逐 DC 盯账的 DatacenterSyncWriteResponseHandler（三者由 `locator/AbstractReplicationStrategy.java:103-114` 按 CL 分发，类在 `service/DatacenterWriteResponseHandler.java:34`、`service/DatacenterSyncWriteResponseHandler.java:42`）。同一个「倒计时」骨架，换的是「哪些回话算数」的口径。

## 二、写路径：等几个 ack 才放行

协调者（比如 node3）把副本名单算出来 {node2, node4, node5} 之后，写请求进入 `StorageProxy.mutate`（`service/StorageProxy.java:978`）。它先做一次「够不够人」的体检：活副本数 ≥ blockFor 吗？不够直接抛 `UnavailableException`（`locator/ReplicaPlans.java:143、191-203`），一个字节都不发。够，则给这笔写配一个**响应处理器**——一个从 blockFor 开始倒计时的计数器（`service/WriteResponseHandler.java:56`），每个副本的 ack 让它减一，减到 0 就唤醒等着的调用方（`:73-74`）。等待有期限：默认 10 秒（`conf/cassandra.yaml:1396`），超时抛 WriteTimeoutException（`service/AbstractWriteResponseHandler.java:130-145`）。

拿那笔 `UPDATE users SET name='阿福2' WHERE id=47` 在三个档位下各走一遍：

```text
举例：同一笔 UPDATE 在三档 CL 下的确认过程（副本 {node2, node4, node5}）
CL=ONE    倒计时 1：node2 ack（1ms 级）→ 归零 → 返回成功
          node4/node5 的 ack 此刻还在网络上飞，但没人等它们
CL=QUORUM 倒计时 2：node2 ack → 1；node4 ack → 0 → 返回成功
          node5 是「写不阻塞」的第三份：它迟早会应用，但不挡这次返回
CL=ALL    倒计时 3：node2、node4、node5 必须全部回话，一个都不许缺席
```

注意 CL=QUORUM 那行的最后一点：**没等到 ack 的副本不影响写成功**。Cassandra 的写从不因「个别副本慢」而失败，多余的副本异步追平——追不上的，靠下一节的 hint 或第 13 章的修复兜底。这是它和同步复制系统的根本区别。

现在把第 5 章的故障接进来。14:00:00 node4 卡死，18 秒后 phi=8.0 触线，全集群把它标 DOWN。再写 id=47：

```text
举例：node4 挂掉之后，同一笔写在各档位下的命运
活副本 = {node2, node5}，共 2 个
CL=ONE     体检 2 ≥ 1 ✓ → node2 ack → 成功（用户无感）
CL=QUORUM  体检 2 ≥ 2 ✓ → node2+node5 ack → 成功（QUORUM 的设计冗余在这里兑现）
CL=ALL     体检 2 < 3  ✗ → UnavailableException，请求立即失败，等都不等
```

CL=ALL 的失败发生在**发请求之前**——`ReplicaPlans` 的体检发现活人不够凑 blockFor，直接拒绝。这不是 bug 是语义：ALL 承诺「3 份都写成了」，2 份写成不配叫成功。反过来，CL=ONE/QUORUM 在一台宕机时依然可用，正是副本数减一致性级别那部分冗余（RF − blockFor = 1 或 2 台）在扛。

还有一个边角：如果体检通过、请求发出去了，某个副本中途才挂怎么办？失败回调会数失败数，一旦「失败数 + blockFor > 候选副本数」，提前判定这笔写凑不齐，立刻失败返回，不再干等 10 秒超时（`service/AbstractWriteResponseHandler.java:383-384`）。

```text
举例：三种「写失败」的报错，含义各不相同
UnavailableException：发请求前就发现活人不够（node4 挂掉 + CL=ALL 即此列）
WriteTimeoutException：等满 10s（write_request_timeout）没凑够 ack——
                      注意：超时 ≠ 没写上，node2 可能已应用，属于「未知结果」
WriteFailureException：副本明确回失败（磁盘满等），失败数使凑齐无望
排障口诀：Unavailable 换 CL 降档可救；Timeout 先查副本延迟再重试（要幂等）；
Failure 看失败原因字段。三种异常都带着 received/blockFor 两个数，直接告诉你差几个。
```

再澄清一个常见误会：**「等 2 个 ack」不等于「只发给 2 个副本」**。普通（无 transient 副本的）keyspace，写会发给全部 3 个副本，只是倒计时归零就返回、不等第 3 个（`locator/ReplicaPlans.java:647-681` 的 writeNormal：无 transient 时联络人 = 全部副本）。所以 CL=ONE 的写通常也是「三份都发、一份回话就走」，第 3 个副本大概率已经应用了——上一节「没等到的副本异步追平」，多数时候连「追」都不需要，只是没等它确认。真正的「少发再补发」（cheap quorum 备份，`service/AbstractWriteResponseHandler.java:430-464`）只在 transient 复制等特殊配置下才会用到。

## 三、hinted handoff：副本挂了，协调者替它记账

node4 挂掉期间，它名下的那份数据谁来补？答案是协调者先写一张**欠条**（hint）。hint 的内容就三个字段：完整的 Mutation、开欠条的时间、涉及表里最小的 gc_grace（`hints/Hint.java:61-68`）——记 gc_grace 是为了别在很久以后把已经清掉的墓碑又「复活」回来（`:46-59` 的注释把这条血泪史写得很清楚）。欠条写在协调者本地的一个目录里（不是内存），node4 回魂后由后台线程每 10 秒调度一轮派发（`config/CassandraRelevantProperties.java:318` 的 `cassandra.hint_dispatch_interval_ms=10000`），把攒的欠条挨张兑现。

但欠条不是万能的，能不能写给谁有门槛（`service/StorageProxy.java:3000-3021`）：hinted_handoff 要开着（默认开，`conf/cassandra.yaml:68`）；目标不能是临时副本、不能是自己；**目标节点的累计宕机时间不能超过 max_hint_window，默认 3 小时**（`conf/cassandra.yaml:80`、`config/Config.java:124`）。3 小时这条线的逻辑：node4 挂超过 3 小时，欠条可能已经攒到天文数字，而且第 13 章的反熵修复反正要全量对账——与其派发一堆积压欠条撞上正在跑的 repair，不如让 repair 一次算总账。

```text
举例：node4 挂掉 40 分钟期间，一笔 CL=QUORUM 的写怎么走完整流程
14:40  协调者 node3 发写：node2 ack、node5 ack → 2/2 成功返回
       node4 的那份没有发出 → shouldHint 检查：宕机 40min < 3h ✓ → 写一张 hint
       关键：这张 hint 不计入 ack，写成功靠的是 node2+node5，hint 只是善后
14:41  node4 重启回来，gossip 宣布 UP
14:41+ 后台派发线程（10s 一轮）找到给 node4 的欠条 → 补投那笔 UPDATE
       node4 应用后，三个副本重新一致；hint 出账
若 node4 挂了 4 小时：超过 3h 窗口，新欠条不再写，缺口留给 repair
```

最后是 ANY——最宽松也最容易被误解的一档。CL=ANY 的 blockFor 是 1，而这个「1」可以由一张 hint 来充当：连一个真实副本都没确认，只要 hint 落了盘，协调者就自己给响应处理器发一个 ack（`service/StorageProxy.java:3390-3392`，代码注释原话「Notify the handler only for CL == ANY」）。更极端的场景：所有副本都超时，`mutate` 的兜底逻辑会给全部副本补写 hint 然后返回成功，trace 里那句「Wrote hints to satisfy CL.ANY after no replicas acknowledged the write」（`service/StorageProxy.java:1075`）说的就是它。ANY 换来的是极端可用性，代价是**这笔写此刻在任何副本上都还不存在**——读它要等 hint 派发完，集群边角里它最弱。

hint 也不是没有风险面，两个边界值得记牢。其一，欠条记在协调者本地磁盘：协调者自己要是这期间炸了且盘没找回，欠条随之蒸发——所以 ANY 的「成功」是三层里最脆的一层（副本盘 < 协调者盘 < 都没有）。其二，欠条可能**重放**（node4 反复横跳时同一笔写派发多次），这无害——Cassandra 的写按时间戳取最新，重复应用同一笔 UPDATE 是幂等的（第 1 章的 last-write-wins 在这里替 hint 兜了底）。

## 四、读路径：一份数据带路，摘要对账

写是「等几个 ack」，读复杂一点：要凑 R 个回话，但又不想让每个副本都把整行数据传回来。Cassandra 的做法是**1 份 data + 其余 digest**：协调者从副本名单里挑 1 个副本要完整数据（数据带路），其余要摘要（`service/reads/AbstractReadExecutor.java:182-194`，默认只发 1 个 data 请求）。摘要是把整行数据压成一个 MD5 哈希（`db/Digest.java:43-45` 的 `forReadResponse` 用 MD5，`db/ReadResponse.java:230-235` 的 makeDigest）——行内容一样，哈希必然一样；差一个字节都不一样。

协调者收到 R 份回话后对账（`service/reads/DigestResolver.java:105-127`）：所有摘要和 data 那份的摘要逐个比。全一致 → 直接返回数据，无事发生。**任何一份摘要对不上 → 触发读修复（read repair）**（`service/reads/AbstractReadExecutor.java:449-452`）：协调者向落后的副本发补齐的写。7.0 的读修复策略就两档（`service/reads/repair/ReadRepairStrategy.java:29-47`）：NONE（不修）和 BLOCKING（默认，`schema/TableParams.java:460`）。BLOCKING 意味着修复写没发完，这次读不返回（`service/reads/repair/BlockingReadRepair.java:75-79` 的注释自称「Classic read repair」）。

```text
举例：一次 CL=QUORUM 读 id=47 在「node4 落后」时的完整过程
发起：data → node2；digest → node4、node5（1 份带路 + 2 份对账）
回话：node2 的 data {name='阿福2', ts=1005}；node5 摘要一致；node4 摘要 ≠
对账：node4 还停在 {name='阿福', ts=1001}——它上周宕机 40 分钟欠的那笔
修复：BLOCKING 读修复：协调者把 ts=1005 的更新补写给 node4，等写完成
返回：客户端拿到新值；副产品是 node4 被顺手抹平（读路径兼职修数据）
```

读修复是 Cassandra「最终一致」里「最终」的加速器：每次读到不一致就顺手修一份，热点数据的分歧活不过几次读。但它是**机会主义**的——没人读的数据不会因此被修，那个兜底是第 13 章的反熵修复（repair），两套机制分工明确：读修复管「读到的」，repair 管「全部的」。

```text
举例：同一行 id=47，两种 CL 读法的差别（node4 落后、node2/node5 已新）
CL=ONE 读：只问 1 个副本——问到 node2 → 新值'阿福2'；问到 node4 → 旧值'阿福'
           还不触发读修复（没有第二份摘要可对）——快，但赌人品
CL=QUORUM 读：1 data + 2 digest → 必然发现 node4 的摘要不合 → 修它 → 返回新值
           慢一个对账回合，换来「返回的一定是多数派版本」+顺手抹平落后者
一句话：ONE 读返回「某一个副本的世界」；QUORUM 读返回「多数派对过账的世界」。
```

顺带一句：读超时和写一样有默认 5 秒的期限（`conf/cassandra.yaml:1388`），凑不齐 R 个回话抛 ReadTimeoutException（`service/reads/ReadCallback.java:218-219`）。另外 CL=ONE 的读只问 1 个副本，没有对账（`db/ConsistencyLevel.java:292-295` 的 needsReconciliation 对 ONE 返回 false）——它读到的就是那一个副本的世界。

data 这一份给谁也有讲究：协调者会挑「最可能快」的副本（动态嗅探器按历史延迟排序，同 rack 优先），慢的副本只被要求出摘要。再进一步是**推测重试**（speculative retry）：如果 data 副本迟迟不回，超时会触发「再问一个副本」的补枪，别让一次读吊死在最慢的人手里——执行器分 NeverSpeculating / Speculating 两类（`service/reads/AbstractReadExecutor.java:276、305`），策略由表的 `speculative_retry` 属性定。这一机制和 CL 正交：它改变「问几个人」，不改变「等几个回话」。

## 五、W+R>RF：可推导的一致性

现在把旋钮拧到最有用的位置。设写等 W 个确认（W = 写的 blockFor）、读凑 R 份回话（R = 读的 blockFor）、副本共 RF 份。鸽笼原理一条：**如果 W+R > RF，那么「参与写确认的副本集合」和「参与读的副本集合」至少共享 1 个副本**——读必然碰到一个「见过最新写」的副本，对账后返回新值。这就是 QUORUM 名字的由来：W=R=⌊RF/2⌋+1 时 2⌊RF/2⌋+2 > RF 恒成立。RF=3 时把常用组合摆开：

| 写 CL（W） | 读 CL（R） | W+R vs RF=3 | 读到新值？ |
| --- | --- | --- | --- |
| ONE（1） | ONE（1） | 2 ≤ 3 | 不保证 |
| ONE（1） | QUORUM（2） | 3 ≤ 3 | 不保证（差一点） |
| QUORUM（2） | ONE（1） | 3 ≤ 3 | 不保证（差一点） |
| QUORUM（2） | QUORUM（2） | 4 > 3 | **保证** |
| ALL（3） | ONE（1） | 4 > 3 | **保证**（写全成了，谁都能读） |
| ONE（1） | ALL（3） | 4 > 3 | **保证**（读全部，必有已应用者） |

注意中间那两行「3 ≤ 3」：W+R 恰好等于 RF 也不行，交集可能为空。举例拆穿它：CL=ONE 写只有 node2 确认（W 集合 = {node2}），CL=QUORUM 读恰好选中 node4+node5（R 集合），交集为空——node2 那份新值没人看到，node4/node5 一对账「旧值一致」，返回旧值。

```text
举例：最终一致的窗口到底有多宽（CL=ONE 写 → 立刻 CL=QUORUM 读）
14:40:00.000  写 CL=ONE：node2 应用新值并 ack → 客户端收到成功
              此刻 node4、node5 还没收到这笔写（毫秒级的网络+排队）
14:40:00.005  读 CL=QUORUM：data→node4、digest→node2/node5（谁先回不保证）
              若凑成的是 node4+node5：两边都是旧值 '阿福'，摘要一致
              → 对账通过 → 返回 '阿福'——写明明成功了，读到旧值！
窗口边界：从「最后一个副本应用完成」那一刻起，任何 QUORUM 读必得新值
窗口宽度：正常毫秒级；副本卡顿/GC/宕机时拉长到 hint 派发完（分钟级）
```

这个窗口不是缺陷，是 CL=ONE 的**合同条款**：它只承诺「1 个副本有了」，从不承诺「处处可读」。要关掉窗口，把组合挪进 W+R>RF 那几行即可——代价是每次读写都多等副本回话。工程上常见的折中：写 QUORUM + 读 ONE（牺牲一致性换读延迟，靠读修复兜底），或写 QUORUM + 读 QUORUM（教科书组合）。没有免费的午餐，只有明码标价的菜单。

两个补充提醒。第一，**W+R>RF 的保证以「同一份 RF 名单」为前提**：LOCAL_QUORUM 写只保证本 DC 过半，配一个跨 DC 的 QUORUM 读时，两边数的不是同一群人，交集论证不能直接套用——跨档位混搭时宁可保守。第二，这个「必见新值」说的是**读到之后**：QUORUM 读返回新值靠的是对账时新值的时间戳胜出（last-write-wins），如果并发有两笔写，胜者由时间戳决定——W+R>RF 给的是「读必见已确认的最新写」，不是线性一致的「读己之写对并发写也排序」，后者要 LWT（轻量事务），不在本章射程。

## 六、和 RocksDB 摆在一起看：写成功到底保证了什么

把两边「写返回 OK 的那一瞬间」放到显微镜下，保证的东西完全不同。RocksDB 是单机库，没有副本概念，「一致性」是**进程内**的：一次写返回时，要么 WAL 里已有这条记录（disableWAL=false 默认开），要么调用方主动放弃了这份保证。它的「确认」是磁盘语义：`WriteOptions::sync` 默认 **false**（`include/rocksdb/options.h:2713`），注释写得很直白——false 相当于一次 `write()` 系统调用，进程崩了不丢、机器崩了可能丢；true 才相当于 `write()+fdatasync()`（`:2697-2710`）。Cassandra 的「确认」是**网络语义**：W 个副本各自在自己的节点上完成了写，每个副本内部又有自己的 commitlog 档位（periodic 默认 10 秒刷盘，见第 2 章）——「副本 ack」和「副本掉电不丢」之间还隔着一层。

| 维度 | RocksDB | Cassandra |
| --- | --- | --- |
| 副本概念 | 无，单机一份 | RF 份，按令牌环摊开 |
| 写成功的定义 | WriteBatch 进了 WAL + MemTable | W 个副本各自回了 ack |
| 「确认」对应什么 | fsync 与否（`options.h:2713` 默认 false） | R/W 个副本回话（`db/ConsistencyLevel.java:138`） |
| 掉电丢写的窗口 | sync=false：OS 缓冲区在就丢 | 每副本内部 commitlog periodic 的 10s 窗口 |
| 节点故障时写 | 不适用（进程没了就没了） | RF−W 台冗余：QUORUM 挂 1 台照写，ALL 挂 1 台即 Unavailable |
| 数据不新的窗口 | 同步可见（单机有序） | W+R≤RF 时存在读到旧值的时间窗 |
| 兜底机制 | WAL 回放 | hinted handoff（3h 窗口）+ 读修复 + repair |

两边在各自的世界里做的是同一道算术：**用多等多少换多少保证**。RocksDB 的旋钮是 sync 开关——多等一次 fsync，换掉电不丢；Cassandra 的旋钮是 CL——多等 R−1 个副本回话，换必见新值。区别在于前者的「等待对象」是一块盘，后者的等待对象是分布在不同机柜里的几台机器——所以前者的档位是微秒级差价，后者的档位是「可用性 vs 新旧程度」的系统设计题。顺带一提，Cassandra 每个副本内部恰恰就是一个 RocksDB 式的 LSM 引擎（第 2~4 章拆过），commitlog_sync 档位就是嵌在「副本 ack」里面的第二层旋钮：一笔 QUORUM 写真实含义是「2 个副本的 LSM 引擎各自按自己的 commitlog 档位收下了这笔写」。

```text
举例：一句「写成功了」在两边的完整翻译
RocksDB（sync=false）：这条记录已在 WAL 的 OS 缓冲区 + MemTable 里，
  进程崩不丢；机器断电可能丢。没有第二份拷贝，也就没有「别的节点」的事。
Cassandra（CL=QUORUM）：node2 与 node4 各自「收下了这笔写」——
  各自的收法又是 periodic commitlog（10s 窗口）+ MemTable。
  node5 可能已应用未确认，也可能正拿着一张 hint 等派发。
两边都有窗口，只是窗口开在不同的墙上：一个是单机的掉电窗口，
一个是多副本之间的传播窗口。参数名不同，学的却是同一门课——
「返回 OK」永远只对你在配置里选定的那一级故障有约束力。
```

## 这一章留下的线索

- **CL 是请求的属性不是集群的**：RF 在 keyspace 上定死，CL 每条请求随时换；blockFor 把 CL 翻译成「等几个回话」（`db/ConsistencyLevel.java:138-179`），RF=3 时 ONE/QUORUM/ALL = 1/2/3；
- **写 = 倒计时归零**：WriteResponseHandler 从 blockFor 倒数（`service/WriteResponseHandler.java:56`），减到 0 返回成功；活副本 < blockFor 在发请求前就被 `ReplicaPlans:143` 的体检拦成 UnavailableException——node4 挂掉时 QUORUM 照常、ALL 即拒；
- **hint 是欠条不是确认**：副本挂了协调者写一张 {Mutation, 时间, gcgs} 的欠条（`hints/Hint.java:61`），默认只给 3 小时内的宕机写（`conf/cassandra.yaml:80`）；唯独 CL=ANY 把 hint 也当 ack（`service/StorageProxy.java:3390`）；
- **读 = 1 data + R−1 digest 对账**：摘要用 MD5（`db/Digest.java:43`），不一致触发 BLOCKING 读修复（默认，`schema/TableParams.java:460`）——读路径兼职把落后的副本顺手抹平；
- **W+R>RF 是唯一的数学承诺**：QUORUM+QUORUM（4>3）必见新值；ONE 写后立刻 QUORUM 读存在读到旧值的窗口，宽度从毫秒到 hint 派发完。

下一章换一个视角看同一笔写：`UPDATE users SET name='阿福2' WHERE id=47` 这句 CQL 文本从网络到达后，怎么被拆词、建树、校验，最终变成这一章反复出现的那件行李 Mutation——[CQL3 解析与执行：从 CQL 到 Mutation](../query/01-CQL3解析与执行.md)。

## 思考题

1. 业务方要求「写入成功后任何读都必须看到新值」，但吞吐敏感。RF=3 下你会给他推荐哪组 CL 组合？如果把 RF 升到 5，QUORUM 的 blockFor 变成多少、能容忍几台宕机？（提示：W+R>RF 的组合表；⌊5/2⌋+1=3。）
2. node4 和 node5 同时宕机（3 个副本只剩 node2 活着），各档 CL 的写分别什么命运？CL=ANY 的写在什么时候会真正丢？（提示：ReplicaPlans 体检；ANY 的 hint 若在 3h 窗口内、协调者也挂了且磁盘没了，欠条随之蒸发。）
3. 为什么 hint 要记 gcgs 字段？假如不记，一个两个月后才派发的 hint 可能造成什么事故？（提示：`hints/Hint.java:46-59` 注释里的「复活已删除数据」场景与 gc_grace 的关系。）
4. 读修复（BLOCKING）和反熵 repair 都能消除副本分歧，为什么两套都要？只留读修复会怎样？（提示：没人读的数据靠谁抹平；读修复是机会主义，repair 是全量巡检——第 13 章展开。）
