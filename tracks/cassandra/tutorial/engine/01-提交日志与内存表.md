# 提交日志与内存表：先记账，再落内存

凌晨两点，机房闪断，node2 掉电重启。值班工程师盯着启动日志：`Replaying CommitLog …` 后面滚出一个数字，几秒后服务起来了，`users` 表 id=47 那行数据安然无恙。他事后越想越不对：上一章不是说「写成功不等于在磁盘上」吗？内存断电就没，SSTable 又还没 flush，Cassandra 凭什么默认敢不等落盘就回你一个 OK？

凭两本账和一条规矩。两本账：一本全节点共用的追加流水账 CommitLog——每笔写入先在这里落笔，断电了凭它重演；一本每张表各一份的内存账 Memtable——真正提供服务的地方。一条规矩：**内存账 flush 落盘时，在盘上记住「我这份账覆盖到流水账的哪个位置」**。有了这个书签，恢复时就不用重演整本流水账，只演没落账的那几页。这一章把两本账和这条规矩都拆开——上一章那句「先追加 CommitLog，再写 Memtable」里的每个词都会有了源码坐标。

全章继续跟 id=47 走，外加一次恰到好处的崩溃：

```text
贯穿全章的两次写入与一次崩溃（接着第 1 章的集群）：
t1  INSERT INTO users (id,name,age) VALUES (47,'阿福',31);   ← 记入 CommitLog 段 1
t2  UPDATE users SET name='阿福2' WHERE id=47;               ← 也记在段 1
t3  users 的 Memtable 满 → flush 出 SSTable-00001            ← 段 1 自此可回收
t4  INSERT INTO users (id,age) VALUES (48,'大壮',28);        ← 记入新段 2
t5  node2 掉电崩溃
恢复 = 只回放段 2（段 1 的数据已经在 SSTable-00001 里，按书签跳过）
```

## 一、CommitLog：全节点共用的一本流水账

CommitLog 在一个节点里只有一份，是个真单例：`public static final CommitLog instance`（`db/commitlog/CommitLog.java:80`），类声明在 `db/commitlog/CommitLog.java:76`。不管哪张表、哪个 keyspace 的写入，都挤进同一本账。它提供的写入口只有一个 `add(Mutation)`（`db/commitlog/CommitLog.java:301`）：把整个 Mutation 序列化，在当前段里划一块地，写进内容，再补两个 CRC 校验值——长度一个、内容一个（`:314-326`），磁盘上读到哪坏到哪都查得出来。

账本的物理形态是一串段文件：当前在写的那个叫 `allocatingFrom`（`db/commitlog/AbstractCommitLogSegmentManager.java:95`），它是活动段队列（`:87` 的注释写明「队尾是分配写的那个」）的尾巴。写满 32MiB（出厂默认 `commitlog_segment_size: 32MiB`，`conf/cassandra.yaml:691`，Java 侧同默认在 `config/Config.java:483`）就换下一个：`advanceAllocatingFrom`（`:298`）把队尾推进到新段。每个段带一个全局递增的 id（`db/commitlog/CommitLogSegment.java:132`），文件名里就带着它。

类比：这是一台**收银机的连号纸带**。所有柜员（所有表）往同一卷纸带上打流水，写满一卷换新卷；每笔流水自带序号和校验，纸带断了能对出来。它不管「这行数据属于哪张表的主账」，只管「今天每一笔都别丢」。

```text
举例：t1、t2 两笔写入在 CommitLog 里长什么样
段 1（CommitLog-4-0000000000000001，容量 32MiB）
├── [pos= 8192] Mutation: keyspace=demo, users, id=47, name='阿福', age=31, ts=1001
└── [pos= 9408] Mutation: keyspace=demo, users, id=47, name='阿福2',        ts=1005
每笔 = 长度+CRC + 内容+CRC；顺序追加，不改前文。
t4 的 id=48 写不进段 1 的剩余空间吗？能，但那时段 1 已被 flush 触发回收，
新写入自然落到段 2 —— 见第四节。
```

```text
举例：node2 的 commitlog 目录在 t4 之后长什么样
/var/lib/cassandra/commitlog/
├── CommitLog-4-0000000000000001.log   ← 段 1：id=47 的两笔（已 flush，可回收）
└── CommitLog-4-0000000000000002.log   ← 段 2：当前在写（allocatingFrom）
文件名里的 0000000000000001/0000000002 就是段的递增 id（CommitLogSegment.java:132）；
恢复时按这个 id 从小到大排着读（recoverSegmentsOnDisk，第五节）。
```

段的生命周期只有三种结局：写满滚动、被 flush 推着回收、或者被复用——回收回来的文件直接当新段用，连磁盘空间都不重新分配。这是 CommitLog 延迟低的另一个细节：正常运转时它几乎不新建文件，只在一小撮文件之间循环；每个段头部还有描述块（版本、段 id、参数），恢复时靠 id 排序、靠段内 CRC 自证完整，可以放心逐段读。

段文件还有个「按配置变形态」的机关：建段时按配置挑实现——加密用 EncryptedSegment、压缩用 CompressedSegment、直接 I/O 用 DirectIOSegment，默认的 mmap 模式则用 MemoryMappedSegment（`db/commitlog/AbstractCommitLogSegmentManager.java:123-145`）。内存映射正是 periodic 档敢「写完就返回」的底气：追加只是写进映射缓冲，落盘交给后台那一拍。开了压缩或加密，这笔账就要改成显式写文件，行为不变、路径不同——排查写入延迟时值得先看一眼这两个配置。

注意一个对比记忆点：**RocksDB 的 WAL 也是一个库一份**，但 Cassandra 这本账的特殊之处在于它被**所有表共用**——users 表和几十张别的表的流水混在同一段里，靠「每笔自带表 id」区分。这直接决定了后面 flush 和恢复的玩法。

最后拆一笔 `add` 的内部分工，三步都有名字：`segmentManager.allocate` 在当前段里划出空间（`db/commitlog/AbstractCommitLogSegmentManager.java:271` 是抽象方法，标准实现就是往 `allocatingFrom` 的缓冲里划）、`alloc.markWritten` 标记内容写完（`db/commitlog/CommitLog.java:334`）、最后 `executor.finishWriteFor(alloc)`（`db/commitlog/CommitLog.java:337`）把这笔交给 sync 服务——periodic 档它直接返回，batch 档它就在这里等落盘。也就是说「等不等盘」这个分岔点，就藏在 add 的最后一步。

## 二、两种 sync 档位：写返回到底等不等磁盘

「记账」和「把账拍到磁盘上」是两件事。拍盘的档位由 `commitlog_sync` 决定（`conf/cassandra.yaml:665`，字段在 `config/Config.java:476`），CommitLog 构造时按它三选一：periodic、batch、group（`db/commitlog/CommitLog.java:119-127`）。

**periodic（默认档）**：写线程把内容交给内存映射缓冲就返回，由后台线程定期 fsync。`PeriodicCommitLogService`（`db/commitlog/PeriodicCommitLogService.java:26`）把 sync 间隔设为配置值（`:32`，出厂 `commitlog_sync_period: 10000ms`，`conf/cassandra.yaml:667`；旧配置名 `commitlog_sync_period_in_ms` 已废弃改名，见 `config/Config.java:480-481`）。写线程平时不等（`maybeWaitForSync`，`:36-45`），只有同步落后太多才被摁住等一下。另有条 100ms 的标记刷新节奏（`db/commitlog/AbstractCommitLogService.java:57`），让「读盘的人」能更快看到新数据，它不是 fsync。

**batch（不丢档）**：`BatchCommitLogService`（`db/commitlog/BatchCommitLogService.java:22`）让每笔写在自己返回前 `awaitDiskSync`（`:36-43`）——确认这笔真到了盘上才回 OK。慢，但崩溃零丢失。

还有个较新加入的 **group 档**（`db/commitlog/GroupCommitLogService.java:27`）：像 batch 一样等落盘，但攒一个小窗口的写合并成一次 fsync，是两档之间的折中。本节不展开。

periodic 档里还有个容易误会的细节：100ms 一跳的**标记（marker）**不是 fsync。它只是定期更新段内「已写到哪」的标记，让恢复程序和读段文件的人能更快定位新数据；真正决定数据安全线的是 10s 一拍的 fsync。两拍并存在 `AbstractCommitLogService` 里：marker 间隔（`:57` 的常量 100ms）与 sync 间隔（`:78` 的 `syncIntervalNanos`）各走各的。

```text
举例：batch 档下同一条写的时间线（对照 periodic）
periodic：追加映射缓冲（~微秒）→ 返回 OK；fsync 由后台 10s 一拍
batch：  追加 → requestExtraSync 催 sync 线程（BatchCommitLogService.java:40）
         → awaitDiskSync 等这笔的 CRC 真正落盘（:41）→ 才返回 OK
         → 延迟多了一个磁盘往返（普通 SSD ~0.1ms，云盘可能 1ms+）
         → 换来的是「返回即落盘」，崩溃零丢失窗口
两档没有谁更高级：一个是明码标价「可能丢 10s」，一个是明码标价「每次多等一趟盘」。
```

选档的判断一句话：**能接受丢一个窗口的，用 periodic 换吞吐；一条都不能丢的，要么 batch，要么客户端自己把确认拉满再返回**。很多团队的实际选择是 periodic + 把 commitlog 放在独立的高速盘上，把「最坏丢 10s」的窗口也尽量收窄。

顺带一提：三档都是 CommitLog 内部的选择，上层写路径（`Keyspace.apply` 那条线）完全无感——改配置不用改代码，这正是把「记账」单独做成一层的好处。

```text
举例：periodic 10s 意味着最坏丢多少
磁盘在 t=100.00s 完成了一次 fsync，此后写入只进了内存缓冲；
t=107.5s 掉电。重启后：
├── 段内已有内容还在（写进映射缓冲的部分，取决于 OS 是否刷出）——不可依赖
└── 依赖线：100.00s 之后 fsync 过的数据保证在；最坏丢 100.00s → 107.5s 的写入
换句话说：periodic 档的「丢数据窗口」= commitlog_sync_period（10s）。
业务如果一条都不能丢，要么 batch，要么客户端自己等 LWT/确认副本数拉满。
```

## 三、Memtable：每张表一本的内存账

上一章已经见过顺序：副本本地 `Keyspace.apply` 的注释写明「先追加到全局 CommitLog，再更新 memtable」（`db/Keyspace.java:437-438`）；具体在写处理器的 `beginWrite`（`db/CassandraKeyspaceWriteHandler.java:42`）里，第一步就是 `addToCommitLog`（`:53`，最终调 `db/CassandraKeyspaceWriteHandler.java:99` 的 `CommitLog.instance.add`）。顺序反了会怎样？先写内存、后记日志，日志还没落笔进程挂了，内存里的数据就成了没凭据的孤本——所以这个顺序是硬性的。

Memtable 本身在 7.0 的 master 上是个**接口**：`db/memtable/Memtable.java:60`。默认实现是跳表账本 `SkipListMemtable`（`db/memtable/SkipListMemtable.java:68`），由出厂的 `MemtableParams` 指定（`schema/MemtableParams.java:99`：`DEFAULT_MEMTABLE_FACTORY = SkipListMemtableFactory.INSTANCE`）；另一套按分区组织的 `TrieMemtable`（`db/memtable/TrieMemtable.java:91`）是 5.0 起的新账本，跟盘上的 BTI 格式配套，细节留给第 4 章，这里一句话带过。内存从哪来由 `memtable_allocation_type` 管（出厂 `heap_buffers`，`conf/cassandra.yaml:886`，枚举与默认在 `config/Config.java:625`、`:1383-1387`）。

类比：CommitLog 是收银机的连号纸带（一卷，全店共用），Memtable 是**每个柜员手里的小账本**（一表一本）。流水先上纸带是为了保命，账本才是顾客问「我的账」时翻的地方。

每本新账本「出生时就带着书签」：创建 Memtable 的工厂方法要求传入 `commitLogLowerBound`——「从流水的哪个位置开始记我」（`db/memtable/Memtable.java:82-88`），这个值就是上一本账的上界。所以整条链是自动咬合的：账本 1 的上界 = 账本 2 的下界，flush 按账本顺序推进时，书签自然一段一段向前挪，不需要额外的对账步骤。

```text
举例：t1、t2 两笔写入之后，node2 手里的世界
CommitLog 段 1：两笔流水（上一节的 pos=8192、pos=9408）
Memtable（users 表）：两个跳表节点
├── (id=47) → cell name='阿福'  ts=1001, cell age=31 ts=1001
└── (id=47) → cell name='阿福2' ts=1005        ← 同一分区两个版本并存
t4 之后新添：(id=48) → cell age=28 ts=2001
读 id=47 时从新到旧问：先见 ts=1005 的 name —— 这就是上一章读拼接的内存版。
```

同一分区的多个版本在 Memtable 里**并存不合并**——Cassandra 不做原地更新，合并推迟到读时拼接和压实。跟 RocksDB 的 memtable 一比你会发现思路一样、粒度不同：RocksDB 按 user_key 排序、seq 藏在内部键里；Cassandra 按分区键聚簇，cell 各自带时间戳。

Memtable 也回答了一个上一章留下的问题：为什么「写成功立刻可读」？因为读路径第一站就是这本内存账——id=47 的最新版本此刻就住在 Memtable 里，根本不用碰盘。等它 flush 成 SSTable 之后，数据「换了个住址」，读路径改从 SSTable 拿，行为不变。

它自己也有膨胀的上限：内存账本吃的是 JVM 堆（或按 `memtable_allocation_type` 换成堆外），攒得太肥会把整个节点拖进 GC 长停顿。所以「什么时候封账 flush」在 Cassandra 里是全局要操心的事——这笔账怎么算、flush 跟不上写入会发生什么，留在第 3 章展开，这一章只要知道「满了就 switchMemtable」这个动作即可。

## 四、flush：落账时记住自己读到哪

Memtable 攒到体量就该落盘了。入口是 `ColumnFamilyStore` 的 `switchMemtable`（`db/ColumnFamilyStore.java:1080`）：先把当前账本「封账」——切出一个新 Memtable 接客，旧的转成只读排队等写盘（判满与排队的策略细节在第 3 章）。封账的动作叫 `switchOut`（`db/memtable/AbstractMemtableWithCommitlog.java:55`）：从这一刻起这本账不再收新写入，并把它对应的 CommitLog 上界钉死（`:60`），因为流水的下一段归下一本账。

真正写盘时，flush 程序做一件大事：**把这本账覆盖的 CommitLog 区间写进 SSTable 的元数据**。写 SSTable 的工厂方法里带着一对位置——`new IntervalSet<>(flushSet.commitLogLowerBound(), flushSet.commitLogUpperBound())`（`db/memtable/Flushing.java:248`，`createFlushWriter` 在 `:233`），这对值最终存进 SSTable 统计块的 `commitLogIntervals` 字段（`io/sstable/metadata/StatsMetadata.java:62`）。类型就是 `db/commitlog/CommitLogPosition.java:35` 定义的（段 id + 段内偏移，`:45`、`:47`；这个概念在老版本里叫 ReplayPosition，新版类名改成了 CommitLogPosition，指的还是同一个书签）。flush 收尾时再通知 CommitLog「这些区间我落好了」：PostFlush 阶段调 `CommitLog.instance.discardCompletedSegments`（`db/ColumnFamilyStore.java:1199-1204`），CommitLog 遍历活动段把对应表标干净（`db/commitlog/CommitLogSegment.java:559` 的 `markClean`），整段没人要了就可回收或复用（`db/commitlog/CommitLogSegment.java:615` 的 `isUnused`）。

```text
举例：书签怎么把段 1 变成可回收
t3 时刻：users 的 Memtable 里躺着 id=47 的两个版本（ts=1001、1005）
  它覆盖的流水区间 = 段1:pos0 ～ 段1:pos9408
flush 完成 → SSTable-00001 的元数据记着 commitLogIntervals=[段1:0, 段1:9408]
PostFlush → discardCompletedSegments(users, 段1:0, 段1:9408)
  → 段 1 里 users 的账全清了；如果段 1 里其他表也都清了 → 整段回收
t4 的 id=48 写进新段 2 —— 它在 flush 之前不存在的位置，属于「没落账的部分」
```

这就是「先记账再落账」省 fsync 的全部秘密：**记账是追加，便宜；落账时把书签夹在盘上，恢复时才不用从头翻流水**。书签是「每表各自记」的——所以混在同一卷纸带上的几十张表，谁 flush 到哪互不拖累；整段回收的条件是所有表都越过了这段区间。

把 flush 的完整动作按顺序列一遍，它是本章最值得背下来的一段流程：

```text
举例：flush 的五步（对应源码坐标）
① 封账   switchMemtable（ColumnFamilyStore.java:1080）
         切新 Memtable 接客，旧账本转只读排队
② 钉上界 switchOut（AbstractMemtableWithCommitlog.java:55）
         旧账本覆盖的流水区间钉死，此后新写归下一本账
③ 写盘   Flushing.createFlushWriter（Flushing.java:233）
         顺序写出一本 SSTable-00001
④ 夹书签 IntervalSet(lower, upper)（Flushing.java:248）
         写进 SSTable 元数据 commitLogIntervals（StatsMetadata.java:62）
⑤ 报账   PostFlush → discardCompletedSegments（ColumnFamilyStore.java:1199-1204）
         CommitLog 把对应表标干净（markClean），整段无人认领则回收
```

还要强调一点：书签是**区间**，不是单点。因为多张表混记一卷账，users 表的区间是「段1:0 ～ 段1:9408」，隔壁表可能是「段1:800 ～ 段1:13000」——彼此交叠、各记各的。`CommitLogPosition` 是个「段 id + 段内偏移」的二维坐标（`db/commitlog/CommitLogPosition.java:45`、`:47`），比较大小先比段 id 再比偏移，这正是它能当区间端点的原因。

## 五、崩溃恢复：按书签跳过已落盘的

节点重启，`CommitLog.start`（`db/commitlog/CommitLog.java:141`）拉起服务，恢复入口是 `recoverSegmentsOnDisk`（`db/commitlog/CommitLog.java:183`）：把 commitlog 目录里的段文件按 id 从小到大排，挨个读。但读之前先算「该从哪开始读」——这是 `CommitLogReplayer.construct`（`db/commitlog/CommitLogReplayer.java:115`）的活：对每张表，从它的活 SSTable 元数据里收集 `commitLogIntervals`（`persistedIntervals`，`:338`），汇成「已落盘区间表」`cfPersisted`（`:118-121` 的循环），再取所有表都没覆盖到的最早位置当全局回放起点（`:183` 的 `firstNotCovered`）。回放时每读到一笔 Mutation，先问一句「这笔所在的位置在已落盘区间里吗」（`:306-313`，注释原话：跳过「already been flushed」的），在就丢弃，不在才重新 apply 进 Memtable。

```text
举例：t5 崩溃后 node2 的恢复过程
盘上有：段 1、段 2；SSTable-00001 元数据：commitLogIntervals=[段1:0, 段1:9408]
construct：users 已落盘 = 段1 全部；其他表若有更晚的书签则取更晚的
全局起点 = 所有表都没覆盖的最早位置（这里 = 段 2 开头附近）
回放：
├── 段 1 的 id=47 两笔 → 位置落在已落盘区间 → 跳过（数据在 SSTable 里）
└── 段 2 的 id=48     → 不在任何区间 → 重新 apply → 回到 Memtable
结果：id=47 从 SSTable 读，id=48 从 Memtable 读，一页流水都没丢。
```

「全局起点」其实是个粗筛，真正的裁决在每笔写入上。它取的是各表书签里最早的那个结束点（`db/commitlog/CommitLogReplayer.java:375-381` 的 `firstNotCovered`），作用是「从哪开始读段文件不至于白读」；具体某笔 Mutation 落不落回内存，仍由它所属表的已落盘区间逐笔判断（`:306-313`）。极端例子最能看清这两层的分工：

```text
举例：两张表的书签一新一旧
users   ：[段1:0, 段1:9408]        ← flush 过
sessions：空                       ← 一本都没 flush 过
firstNotCovered = min(段1:9408, NONE) = NONE → 从头读所有段
逐笔裁决：段 1 里 users 的笔 → 跳过；段 1/2 里 sessions 的笔 → 全部回放
结论：全局起点省的是「读段文件」的工夫，兜底的是「逐表判断」的准确。
```

回到开头的值班现场，现在那行 `Replaying CommitLog` 后面的数字也有名字了：它是 `replayedCount`——真正被捡回 Memtable 的 Mutation 计数（`db/commitlog/CommitLogReplayer.java:83`，逐笔累加在 `:318`，最后随恢复结果返回在 `:273`）。这个数越大，说明崩溃时「没落账的流水」越多：它不该是常态的大数，如果每次重启都回放出上万笔，多半是 flush 跟不上写入，该去查的是 flush，不是 CommitLog。

段文件也不总是完好的：掉电可能让最后一笔只写了一半。回放器对此有容忍处理——`replayPath` 带着 `tolerateTruncation` 参数逐段读（`db/commitlog/CommitLogReplayer.java:188-191`），读到 CRC 对不上的残笔就停在该段，前面的照常回放。第一节里那两个 CRC 校验值，此刻派上的正是这个用场：**它们把「半笔」和「整笔」区分开了**，恢复才敢在损坏处利落地停下，而不是把坏数据也放进内存账。

对照第二章的丢数据窗口，恢复的边界现在完整了：**periodic 档下，最后 10 秒里没被 fsync 的流水才是真正的丢失区间**，再之前的哪怕还没 flush，也能从段文件里演回来。RocksDB 的恢复思路同源，但省掉了书签——因为它一个库只有一棵 LSM，WAL 与 memtable 一一对应，全量回放就行；Cassandra 几十张表共用一卷账，必须靠书签精确到表地跳。

两个工程细节补在后面。其一，回放是「重新 apply」，不是「原样重演」：回放的 Mutation 走普通写路径进 Memtable，但**不再记 CommitLog**——`apply` 的 `writeCommitLog` 参数传的是 false（`db/commitlog/CommitLogReplayer.java:325`），这段流水本来就在账上，重记一遍只会把段文件越滚越多。其二，书签随账本走：SSTable 被压实合并成新 SSTable 后，新文件的元数据会合并继承各输入的 `commitLogIntervals`，所以恢复时的 `persistedIntervals` 只认「本机产生的 SSTable」（`db/commitlog/CommitLogReplayer.java:346-348` 用 `originatingHostId` 过滤）——别的节点 streaming 过来的 SSTable 和本机流水账没有关系，它们的区间是负值（`CommitLogPosition.NONE`，`db/commitlog/CommitLogPosition.java:43`），天然被忽略。

## 六、和 RocksDB 摆在一起看：两本崩溃保险账

| 维度 | RocksDB WAL | Cassandra CommitLog |
| --- | --- | --- |
| 账本粒度 | 一个库一份，与列族/树的对应由实现内部维护 | 一个节点一份，所有表混记，靠每笔自带表 id 区分 |
| 文件组织 | 单文件按 32KB 块分片（`db/log_format.h:54`） | 32MiB 一段滚动成串（`conf/cassandra.yaml:691`） |
| 写侧组织 | 组提交：leader 收编同车写、整车一次 fsync（`db/db_impl/db_impl_write.cc:1210`） | 各写线程 allocate 到共享段，sync 由后台线程按档位做 |
| fsync 时机 | 跟随每次 WriteBatch 提交（`sync=true` 时至多一次/批） | periodic 10s 一档 / batch 每笔一档 / group 折中 |
| 丢数据窗口 | `sync=true` 不丢；`false` 时靠 OS 刷盘，窗口不定 | periodic = commitlog_sync_period（10s）；batch = 0 |
| 崩溃恢复 | 全量回放 WAL 到 memtable（`db/db_impl/db_impl_open.cc:1237`） | 按 SSTable 书签（CommitLogPosition）跳过已落盘区间再回放 |

组提交和段共享是两种「攒大 I/O」的路数：RocksDB 在**进入 WAL 之前**排队凑车，一次系统调用带走一批并发写；Cassandra 让大家**直接写进同一卷账**，把攒批的活交给后台 sync 线程的节拍。前者把延迟做成可预期的「一批一 fsync」，后者把写入延迟压到最低（不等盘），代价是必须发明书签机制来对付恢复。

丢数据窗口的换算也值得摆在一起：RocksDB 关 `sync` 时丢多少取决于 OS 何时刷页缓存，说不准；开 `sync` 则批批不丢但每批付一次 fsync。Cassandra 把这事做成了明码标价的配置——periodic 10s 就是「最多丢 10 秒」，batch 就是「0 丢失、写延迟上一个台阶」。对运维来说，后者更吵但更好算账。而恢复那一侧的差异是结构性的：单库全量回放（RocksDB）简单粗暴，多表共享账本（Cassandra）就必须有 ReplayPosition 这个发明——这也是为什么 Cassandra 的 SSTable 元数据里长着 `commitLogIntervals` 这个别家没有的字段。

还有一个隐藏的共同点值得点破：两本账的**回收都由 flush 推着走**。RocksDB 的 WAL 文件要等对应 memtable flush 完才进 obsolete 队列；Cassandra 的段要等所有表的 `markClean` 越过整段才回收。谁都不能「日志写完就删」——在 flush 交出书签之前，日志就是数据本体。所以观察任何一家 LSM 系统的磁盘水位，commitlog/WAL 目录的大小都和 flush 的健康度直接挂钩：这个目录只涨不掉，八成是 flush 卡了，而不是日志写得太多。

## 这一章留下的线索

- **一本流水账 + 每表一本内存账**：CommitLog 是节点级单例、全表共用、只追加；Memtable 每表一份，默认跳表实现，TrieMemtable 是 5.0 起的新账本；
- **写顺序是硬性的**：先 `CommitLog.instance.add` 再写 Memtable，顺序反了崩溃时会留下没凭据的数据（`db/Keyspace.java:437-438`）；
- **sync 有档位**：periodic（默认，10s 一拍、最坏丢 10s）/ batch（每笔等盘、0 丢失）/ group（窗口折中）——出厂默认值写在 `conf/cassandra.yaml:665、:667`；
- **flush 夹书签**：SSTable 元数据里的 `commitLogIntervals` 记住这份账覆盖的流水区间，flush 后对应段可回收；
- **恢复按书签跳**：CommitLogReplayer 收集各表书签，只回放没落账的部分——这是「敢不等 fsync 就返回」的底气。

下一章看落账的产物：SSTable 这个不可变账本在盘上怎么组织、几十本 SSTable 怎么被后台压缩慢慢并账——[SSTable 与压缩：磁盘上的不可变账本](../engine/02-SSTable与压缩.md)。
