# 原生协议传输：CQL 消息的线路形态

先看一个抓包现场。一个工程师怀疑驱动到 Cassandra 之间「话太多」，在客户端机器上 `tcpdump port 9042`：屏幕上滚过的全是二进制，一个字都读不懂；他只想回答一个朴素的问题——那句 `UPDATE users SET name='阿福2' WHERE id=47` 在线上到底长什么样、有几个字节、一条 TCP 连接上同时挤了多少句查询。隔壁组用 RocksDB 的同事凑过来看了一眼，说了句扎心的：我们根本没有这种包，Put 就是一次函数调用。

不是他抓包姿势不对，而是他没看过 Cassandra 的「方言说明书」：原生协议（native protocol）。驱动与节点之间说的不是文本、不是 JSON，而是一套二进制帧——每条消息装在一个固定 9 字节头的信封里，靠信封上的小字段区分「这是查询、那是结果、这盏是心跳」。看懂这套线路形态，抓包屏上的乱码会变成一张可读的消息清单；而「为什么 Cassandra 每次调用都比嵌入式引擎多几笔固定的税」，也能在这一层找到最直观的账本。

全章跟一条连接走，口径与全轨道一致：

```text
贯穿本章的一次会话（字节数为示意量级，便于心算）：
客户端 cqlsh → node3（native transport 端口 9042），一条 TCP 连接，协议 v5
OPTIONS(9B) → SUPPORTED(约119B) → STARTUP(33B) → READY(9B) → QUERY(59B) → RESULT(13B)
负载：UPDATE users SET name='阿福2' WHERE id=47（39 字符 = 43 个 UTF-8 字节，ts=1005）
协调者：node3 客串（第 1 章）；副本名单 {node2, node4, node5} 在下一章才用上
协议支持：v3/v4/v5 正式版，v6 为 beta（transport/ProtocolVersion.java:48-51）
```

一句话预告结论：线路形态三件事——**9 字节信封统一包装、stream id 一条连接多路复用、握手谈妥压缩再干活**；而这一切在 RocksDB 那边对应的是零——没有信封、没有号、没有握手。

---

## 一、信封：9 字节头 + body，一切消息的统一包装

原生协议是**帧式二进制协议**：任何一条消息，线上形态都是一个固定头加一段身体。头的样子就画在源码注释里（`transport/Envelope.java:52-59`），一共 9 字节（`Header.LENGTH = 9`，`transport/Envelope.java:139`）：

| 字段 | 宽度 | 装什么 | 人话类比 |
| --- | --- | --- | --- |
| version | 1B | 版本 + 方向：最高位 0=请求、1=应答，低 7 位协议号 | 快递面单上的「寄/收」标记 |
| flags | 1B | 位标志：0x01 压缩、0x02 追踪、0x04 自定义负载、0x08 警告、0x10 beta | 面单上的加急/保价贴纸 |
| stream | 2B | 流水号，请求和它的应答戴同一个号 | 取餐号 |
| opcode | 1B | 消息类型编号 | 包裹种类 |
| length | 4B | body 的字节数 | 包裹重量 |

类比起到了：**消息是货，信封是面单**。收件方（服务器）先读 9 字节面单：看 opcode 知道这是寄件还是查件，看 length 知道还要再收多少字节的货，看 stream 知道这票货该记在谁头上。解码代码就是照这张表逐字节取的（`transport/Envelope.java:238-251`：1 字节 version、1 字节 flags、2 字节 stream、1 字节 opcode、4 字节 length，一个大端序走到底）。顺带一个小历史：v1/v2 时代的头只有 8 字节（stream 只占 1 字节），所以解码器至今保留着旧格式分支来给老驱动回个明白的错误（`transport/Envelope.java:98-103`）。

opcode 一共 17 种，全表在 `transport/Message.java:91-109`。常用的记两打就够用：

| opcode | 名称 | 方向 | 什么时候出现 |
| --- | --- | --- | --- |
| 5 / 6 | OPTIONS / SUPPORTED | 请求/应答 | 探路与心跳：问「你会什么」 |
| 1 / 2 | STARTUP / READY | 请求/应答 | 开工：报版本、谈压缩 |
| 3 / 14 / 15 / 16 | AUTHENTICATE / AUTH_* | 混合 | 密码认证时的额外两轮 |
| 7 / 8 | QUERY / RESULT | 请求/应答 | 干活：一句 CQL 与它的结果 |
| 9 / 10 | PREPARE / EXECUTE | 请求 | 干活的另一种形态（第 8 章的缓存主角） |
| 13 / 11 / 12 | BATCH / REGISTER / EVENT | 请求/应答 | 批量写、订阅与服务器主动推送 |

```text
举例：那句 UPDATE 的 QUERY 帧，byte 账算给你看（示意量级）
查询文本 39 字符 → UTF-8 43 字节：36 个 ASCII 字符（UPDATE users SET name=' WHERE id=47
等）各 1 字节 + '阿'、'福' 两个汉字各 3 字节 + '2' 1 字节 = 36+6+1 = 43。
body = [long string 查询文本] + [short 一致性级别] + [byte flags]
     = (4 + 43) + 2 + 1 = 50 字节
信封 = 9 + 50 = 59 字节
服务器回的 RESULT（RESULT.Void）：body = [int kind=1] = 4 字节，共 13 字节
（kind 枚举在 transport/messages/ResultMessage.java:55-62：VOID=1、ROWS=2…）
一次 UPDATE 往返的「话费」≈ 59 + 13 = 72 字节，外加 TCP/IP 头各 40 字节。
```

再给一个抓包视角的礼物——这 59 字节的**前 9 个字节**长什么样（v5 握手期/legacy 形态，逐字段对着上面的表读）：

```text
05 00 00 01 07 00 00 00 32 │ 00 00 00 2b U P D A T E ...
│  │  │     │  │           │ └ 4 字节：长度 0x2b = 43（查询文本）
│  │  │     │  │           └ body 开头
│  │  │     │  └ 1 字节：opcode 0x07 = QUERY
│  │  │     └ 2 字节：stream 0x0001 = 1 号
│  └  1 字节：flags 0x00 = 无压缩无追踪
└  1 字节：version 0x05 = v5 请求方向（应答最高位变 1，如 0x85）
服务器回 RESULT 1 号：85 00 00 01 08 00 00 00 04 —— 0x85 应答+版本5，opcode 8，body 4 字节。
```

这个「算账」能力是排障基本功：怀疑驱动在传大字段时，抓包对一对 length 就知道谁胖；怀疑心跳太勤时，数一数 OPTIONS 帧的频率。

## 二、stream id：一条 TCP 连接怎么同时跑一百句查询

如果一条连接同一时刻只能挂一句查询，高并发就得开几百条 TCP——每条连接三次握手、拥塞窗口从零爬起、内核读写缓冲各一份，全是成本。Cassandra 的解法轻得惊人：**信封上那 2 字节的 stream 字段就是全部基础设施**。客户端发出请求时自己编个号，服务器应答时**原样带回**——spec 第 2.4.1.3 节写得很硬：请求用 X 号，应答保证也是 X 号。

类比：奶茶店取餐号。你先点了 1 号单，接着又点 2 号、3 号，哪杯先做好叫哪杯——不需要开三个柜台，也没有柜台会因为你同时下三单而混乱。约束只有一条：**在途的号不能重**。2 字节有符号数，正号段一共 32768 个；负号段留给服务器主动推送（EVENT 消息固定用 -1，比如「新节点上线了」「schema 变了」这类广播）。

```text
举例：一条连接上的三路并发（stream id 的复用）
t0  发 QUERY stream=1 → SELECT ... WHERE id=47   （id=47 名单 {node2,node4,node5}）
t0  发 QUERY stream=2 → SELECT ... WHERE id=48   （id=48 名单 {node4,node1,node5}）
t0  发 QUERY stream=3 → SELECT ... WHERE id=49
t1  收 RESULT stream=2   ← 2 号先回：两组名单不同、副本快慢不同，乱序是常态
t2  收 RESULT stream=3
t3  收 RESULT stream=1   ← 1 号最后交付；交付后 1 号回收，
                            下一句查询可以重新用 stream=1
任何时刻：在途号互不相同；已应答的号立即可复用。
```

服务器侧的配合同样简单：解帧是流式的，字节不够一个整信封就先攒着（`transport/Envelope.java:395-407` 等齐 9 字节头和 length），凑够一条吐一条。TCP 只是字节流，「消息边界」由协议自己负责切割。第 8 章结尾那句「驱动怎么多路复用」的答案就落在这一节：**不在网络层做文章，就是信封带号**。

有人会问：为什么不像很多服务那样直接上 HTTP/2，天然就有多路复用？因为这里要的是**每条消息 9 字节的固定税和零文本解析**。HTTP 一句最简单的请求头也是几百字节起步，还要啃文本；对一个可能每秒每连接发几万条消息的数据库协议，头越小、解析越傻越快越好。EVENT 用负号段也是同一个思路的服务端配合：服务器主动推的「拓扑变了」「schema 变了」不占客户端的号（客户端先 REGISTER=11 订阅感兴趣的事件类型），推过来不与任何在途请求混淆。

## 三、连接的一生：OPTIONS → SUPPORTED → STARTUP → READY → QUERY

一条连接从三次握手到第一句查询，要走一段固定的开场舞。服务器侧的状态机在 `transport/ServerConnection.java:84-122`：连接刚建立时处于未初始化阶段，只认 OPTIONS 和 STARTUP 两种消息，其余一律 ProtocolException「Unexpected message, expecting STARTUP or OPTIONS」拒之门外。

```text
① 客户端 → OPTIONS    （9 字节，body 空）        「你会什么？」
② 服务器 → SUPPORTED  （约 119 字节，示意）      回一张能力清单：
     CQL_VERSION → 3.4.8（第 8 章的方言版本）
     COMPRESSION → snappy、lz4（装了 snappy 库才有它）
     PROTOCOL_VERSIONS → 3/v3、4/v4、5/v5、6/v6-beta
     清单由 transport/messages/OptionsMessage.java:62-79 现场拼装
③ 客户端 → STARTUP    （33 字节起，示意）        「我要用 v5；CQL 版本 3.0.0；
                                                   压缩选 lz4（可选项）」
④ 服务器 → READY      （9 字节，body 空）        点头开工；若节点配了密码认证，
                                                   这一步换成 AUTHENTICATE，
                                                   再走 AUTH_RESPONSE/AUTH_SUCCESS
⑤ 客户端 → QUERY stream=1 ……（从此进入正题）
```

SUPPORTED 那约 119 字节也能心算：`[string map]` 编码 = 4 字节条目数 + 每条（2 字节键长 + 键文 + 4 字节列表长 + 各值自带 2 字节长度），三个条目 CQL_VERSION/COMPRESSION/PROTOCOL_VERSIONS 拼出约 110 字节 body，加信封 9 字节。STARTUP 的合法选项有四个（`transport/messages/StartupMessage.java:48-53`）：CQL_VERSION 必填、COMPRESSION 可选，另有 DRIVER_NAME/DRIVER_VERSION（服务器拿来记 `system.clients` 表和做版本护栏）和 THROW_ON_OVERLOAD；最小 STARTUP 只带 CQL_VERSION 一项算出 33 字节，现代驱动多报身份字段也就五六十字节。要不要认证的分岔在 `transport/messages/StartupMessage.java:137-167`：认证器不设防就直接回 READY（`:167`），设防则回 AUTHENTICATE 进两轮挑战。

v5 还有一处新设计必须知道：**握手四步不穿「帧衣」，READY 之后才换装**。v5 给信封外面包了一层带校验的帧——6 字节头（3 字节长度+自包含位、3 字节 CRC24）+ 载荷 + 4 字节 CRC32，单帧载荷最大 128KiB，大信封自动拆成帧序列（spec 第 2.1、2.2 节）。切换点在源码里写得很清楚：STARTUP 版本 ≥ V5 时，服务器把 READY 发出去**之后**才重配管线换新帧格式（`transport/InitialConnectionHandler.java:115-125` 走 configureModernPipeline；v4 及更早走 `transport/PipelineConfigurator.java:405-416` 的 legacy 管线，信封裸跑、压缩做在信封 flags 上）。抓包看到「前几条消息一个样、READY 之后变了个样」，不是乱码，是换装。

把开场舞的总账也算了（连接建立好、第一句 UPDATE 干完，线路上一共过了多少字节）：

```text
举例：一次完整会话的线路账（示意量级）
OPTIONS      9 B    ← 客户端出
SUPPORTED  119 B    ← 服务器回（能力清单三件套）
STARTUP     33 B    ← 客户端出（最小形态：只带 CQL_VERSION）
READY        9 B    ← 服务器回
QUERY       59 B    ← 我们的 UPDATE
RESULT      13 B    ← RESULT.Void
─────────────────
合计约 242 字节，其中「有用的负载」只有查询文本 43 字节。
多路复用把这笔开场费摊到这条连接的余生上——这也是连接池要长连的根本原因：
一次握手 242 字节 × 每秒重建一万条连接，就是每秒 2.4MB 的纯礼数开销。
```

## 四、压缩、体积上限与 Netty 管线：服务器这边怎么接货

**压缩：谈拢了才有，且分两种形态。** 压缩不是默认开的——STARTUP 里带 COMPRESSION 选项才算数。两种形态对着记：

| | v4 及以前（信封级） | v5（帧级） |
| --- | --- | --- |
| 压缩对象 | 整个信封 body | 帧载荷（一条信封可能拆多帧） |
| 开关位置 | 信封 flags 的 0x01 位 | 帧头 compressed length 置 0 表示不压 |
| 可选算法 | snappy（`transport/Compressor.java:57`）、lz4（`:150`） | 仅 lz4（`transport/PipelineConfigurator.java:391-393`） |
| 握手消息 | STARTUP 永不压缩（`transport/Envelope.java:567-570`） | 天然免疫（握手根本不穿帧衣） |

lz4 实现有个值得一看的细节：压缩输出的前 4 字节先写原始长度、大端序（`:175-178`），注释专门解释「native protocol 整个是大端，这里放小端就是给客户端实现者埋雷」——解压端凭这 4 字节一次分配对缓冲，不用边解边扩。另一个护栏：解压前校验声明的原始长度，超过帧上限就当非法帧拒掉（`transport/Compressor.java:44-51`），防止恶意小帧解出巨型缓冲。v5 帧层还允许逐帧选择压不压——小帧不压反而省 CPU，这一点和「小包不值得压」的常识一致。

**体积上限：单帧 16MiB 把门。** `native_transport_max_frame_size` 出厂默认 16MiB（`config/Config.java:354-355`，`conf/cassandra.yaml:1102` 注释示例同值）。超限的请求不进执行栈：解码器进 discard 模式把已收字节全丢、继续吞掉后续字节直到够数，然后报「Request is too big」（`transport/Envelope.java:444-455、497`）。所以「一条 20MiB 的 BLOB 能不能写进去」的答案在服务端这个配置，不在驱动侧调参。

**Netty 管线：这一切的搬运系统。** 监听者是 `transport/Server.java:72` 的 Server，底层是 Netty：一把 EventLoop 轮转组（Linux 用 epoll、否则 NIO，`transport/Server.java:108-111`）负责全部连接的字节收发；每条新连接装配一条 handler 流水线（`transport/PipelineConfigurator.java:252-291`：连接数限流 → 空闲检查 → 信封编码器 → 握手处理器）。信封解出后，请求从 EventLoop 交给 **Native-Transport-Requests 线程池**执行（`transport/Dispatcher.java:62-65`），EventLoop 立刻回去收下一句——收货与干活分家，一句慢查询不会堵死同连接的其他 stream。零拷贝一句话：body 从网络缓冲解出后以**切片引用**在管线里传递（`transport/Envelope.java:464` 的 `buffer.slice`，不复制内容），缓冲来自池化分配器（`transport/CBUtil.java:67` 的 PooledByteBufAllocator），能不搬的字节一个都不多搬。

## 五、心跳与空闲：连接怎么保持「活着」

TCP 连接放着不动，中间的防火墙、负载均衡可能悄悄把它回收；驱动发现时，一批在途查询全部报错。这一层有三道防线，一道协议内、两道协议外：

| 防线 | 机制 | 成本 | 出处 |
| --- | --- | --- | --- |
| 协议心跳 | OPTIONS 随时可发（含握手后） | 9B + 约 119B ≈ 130 字节/来回 | spec 2.3.1 注记；`transport/messages/OptionsMessage.java:62` |
| 服务器裁剪 | idle 超时掐线（默认关） | 配了才生效 | `config/Config.java:147-148`（默认 0ms）；`transport/PipelineConfigurator.java:264-275` |
| TCP 保活 | SO_KEEPALIVE | 内核级、小时级 | `conf/cassandra.yaml:1167`（rpc_keepalive 默认 true） |

心跳为什么选 OPTIONS 而不是发明一个 HEARTBEAT opcode？因为它「本来就允许随时发、应答小、无副作用」——一个 9 字节小信封换回一个 SUPPORTED，跟人没事抬手看表一个意思：证明这条胳膊还能动。`native_transport_idle_timeout` 出厂默认 **0 = 不裁剪**（yaml 示例给 60s，`conf/cassandra.yaml:1125`）；一旦配成正数，静默超时的连接被 IdleStateHandler 直接关闭，日志里会写「Closing client connection after timeout」——排障时看到这句话先查这个配置，再查中间设备。

这一层最常见的三类「现场」，对症下药表：

| 抓包/日志现象 | 第一嫌疑 | 去哪查 |
| --- | --- | --- |
| 批量查询同一瞬间全报连接错误 | 空闲连接被中间设备/裁剪掐了 | idle 超时与防火墙 timeout 谁更小；驱动心跳间隔 |
| 日志刷「Request is too big」 | 单请求超过帧上限 | `native_transport_max_frame_size`（默认 16MiB）与 BLOB 尺寸 |
| 握手期直接被拒「Unexpected message」 | 客户端没先 STARTUP 就发 QUERY，或版本不受支持 | `transport/ServerConnection.java:84-85` 状态机与 PROTOCOL_VERSIONS 清单 |

最后补一句**驱动侧连接池**（各家实现不同，不展开）：驱动对集群每个节点各养一小池连接——常见一池专门跑未准备语句、一池跑已准备语句，再叠加每条连接的 stream id 号域。第 8 章的 prepared 缓存在服务器端省解析的钱，连接池在客户端省握手的钱，stream id 在线路层省连接的钱——三件事一起把「每句话的固定成本」摊薄。

## 六、和 RocksDB 摆在一起看：进程内调用 vs 网络往返

| 维度 | Cassandra | RocksDB |
| --- | --- | --- |
| 调用形态 | 网络消息：QUERY 帧 → 节点 → RESULT 帧 | 进程内函数调用：`db->Put(...)`（`include/rocksdb/db.h:582`） |
| 「查询语言」的载体 | 二进制协议，17 种 opcode，握手/心跳/认证一套礼数 | C++ API 本身，没有协议、没有握手 |
| 序列化 | 每次调用参数编码成帧、结果编码回帧 | 没有：键值就是 `Slice` 字节片（`include/rocksdb/db.h:582-584`），指针对象直传 |
| 多路复用 | stream id（2 字节、正号段 32768 路） | 不需要——调用就是压栈出栈 |
| 状态保活 | 心跳 + idle 裁剪 + TCP 保活三道防线 | 无连接概念，谈不上保活 |
| 一次 UPDATE 往返 | ≈72 字节线路话费 + 两端编解码 CPU | 0 字节线路开销 |
| 这一层特有的故障 | 连接断、超时、协议版本不匹配、帧超限 | 不存在这一层 |

那笔「最直观的账」现在能算清了。同样是把 id=47 的名字改成「阿福2」：

```text
举例：一次改动在两边的过路费（量级示意）
RocksDB：Put("47", value) → WAL 追加 + MemTable 插入，微秒级；
          全程零编码、零握手、零线路字节。
Cassandra：装帧(50B body) → TCP → 解帧 → 第 8 章解析流水线 → 副本确认(第 7/10 章)
          → 结果装帧(13B) → TCP → 驱动解帧。
          序列化 + 网络 + 反序列化，三笔税一次不落；
          同机部署走 127.0.0.1 也一样收——不过网卡，但过整条编解码流水线。
再补一层跨节点的账：协调者把写摊给副本时，Mutation 还要再序列化一次跨节点传输
（service/StorageProxy.java:1853 发送前预序列化缓存，就是给这笔税省成本）。
```

这就是「嵌入式 vs 服务化」在账面上的区别：服务化换来的是多客户端共享、多副本容灾与横向扩缩——第 5~7 章的那些能力；付出的是每一次调用的固定过路费。抓包现场那位工程师最后在报告里写的话可以做这节的收束：**RocksDB 的每次调用是递一次扳手，Cassandra 的每次调用是寄一次快递——快递系统能寄到别的城市，但哪怕同城同楼，也要走一遍面单。**

## 这一章留下的线索

- **一切消息 = 9 字节信封 + body**：version/flags/stream/opcode/length 五字段（`transport/Envelope.java:52-59、139`），17 种 opcode 全表在 `transport/Message.java:91-109`，QUERY=7、RESULT=8；
- **stream id 是多路复用的全部秘密**：请求带号、应答还号、在途不重号（正号段 32768 路，负号段留给 EVENT）；一条 TCP 连接养活整个连接池的话务量；
- **连接生命周期是固定开场舞**：OPTIONS/SUPPORTED 探路 → STARTUP 报身份谈压缩 → READY（或认证两轮）→ QUERY；v5 在 READY 之后给信封外加 CRC 帧衣（`transport/InitialConnectionHandler.java:115-125`），单帧载荷上限 128KiB；
- **压缩与体积上限**：v4 信封级 snappy/lz4、v5 帧级仅 lz4；`native_transport_max_frame_size` 默认 16MiB（`config/Config.java:354-355`），超限进 discard 模式；
- **心跳 = OPTIONS**（9 字节买一个来回），服务器 idle 裁剪默认关闭（`config/Config.java:147-148`）——对照 RocksDB：这几层保活在进程内调用里一个都不存在；
- **一次会话 242 字节、其中有用负载 43 字节**：这就是连接池必须长连、驱动拼命摊薄固定成本的由来。

下一章把全线接通：QUERY 到达 node3 之后，协调者怎么把一笔写摊给 3 个副本、把一次读凑成 data+digest 对账、node4 卡死之后两条流水线各走什么分支——[读写路径：Coordinator 的两条流水线](../query/03-读写路径.md)。

## 思考题

1. 一条连接上客户端把正号段用满（32768 路在途），驱动再发一句查询会发生什么？如果它把还在途的 1 号重发给第二个请求，结果怎么张冠李戴？（提示：spec 2.4.1.3「在途号不重」约束；负号段留给谁、EVENT 为什么固定 -1。）
2. `native_transport_max_frame_size` 保持默认 16MiB，业务要写 20MiB 的 BLOB：服务器侧进入什么模式？客户端会看到一个错误帧还是一条废连接？（提示：`transport/Envelope.java:444-455` 的 discard 逻辑——错误是丢弃完成后才报的。）
3. 为什么 v5 把压缩从信封 flags 挪到帧层、且只留 lz4？（提示：帧层压缩对握手消息天然免疫；lz4 解压只要知道原始长度就能一次分配缓冲——`transport/Compressor.java:175-178` 那 4 字节为什么必须放大端。）
4. 应用与 Cassandra 同机部署、走 127.0.0.1:9042，「网络税」省掉了吗？三笔税（序列化/网络/反序列化）哪几笔还在？再想想：把 Cassandra 换成嵌入应用的 RocksDB，第 5~7 章的哪些能力会随之消失？（提示：本章第六节的账本 + 各章开头的定位。）
