# 读写路径：Coordinator 的两条流水线

先回到 14:00 的机房。node4 在 14:00:00 卡死（第 5 章），phi=8.0 让四个观察者在 14:00:18~:20 各自把它标成 DOWN。值班工程师盯着面板看到了三件事：普通写（CL=QUORUM）的成功率纹丝不动，平均延迟只多了几毫秒；`SELECT ... WHERE id=47` 这类点查偶尔慢半拍但照样返回；只有一批 CL=ALL 的对账作业齐刷刷报了 Unavailable。他翻遍了第 2 章到第 8 章，每一章都能解释一小块——本地引擎、故障判定、定位、确认档位、CQL 装箱——但没有一章能把三件事连成一个故事。

这一章就是那个故事的总装车间。前面所有部件在第 8 章结尾交货的两件行李——Mutation（写）和 ReadCommand（读）——到这里被接上最后的配送链：**StorageProxy 的写流水线与读流水线**。谁是协调者、发给谁、发几份、等几份、等不到怎么办、收到指令的副本在本地怎么干活，本章一次讲完。读懂它，上面三件「怪事」会翻转成三句台词：写多出一份由 hint 垫付、读少了一个副本刚好还凑得齐 QUORUM、ALL 缺一份就事前拒绝。

全章走两单，口径与全轨道一致：

```text
贯穿本章的两单（keyspace demo，RF=3，CL=QUORUM，blockFor=2）：
写单：UPDATE users SET name='阿福2' WHERE id=47（ts=1005，第 8 章装箱成一件 Mutation）
      场景 A：健康集群，名单 {node2, node4, node5} 全活
读单：SELECT name, age FROM users WHERE id=47（点查 ReadCommand）
      场景 B：node4 DOWN 之后，活名单只剩 {node2, node5}
两条流水线的总入口：service/StorageProxy.java:978（mutate）与 :2176（read）
```

## 一、会师：StorageProxy 是两条流水线的总调度台

第 8 章说过，任何节点都能客串协调者（Coordinator）——这次还是 node3。客串的意思是：**协调者不是常设岗位，而是「谁接到请求谁担任」的临时角色**；每一笔请求独立轮到一次。这与单机引擎完全不同：RocksDB 的 DBImpl 是进程里唯一的常驻单例（`db/db_impl/db_impl.h:221`），而 Cassandra 里「调度台」是每个节点各有一份的 StorageProxy，接到活就干，干完继续当普通节点。

把前八章的部件按两条流水线重新点名，会师表如下：

| 来自哪章 | 部件 | 在写流水线里干啥 | 在读流水线里干啥 |
| --- | --- | --- | --- |
| 第 8 章 | Mutation / ReadCommand | 写的行李（一个分区一次完整修改） | 读的问询单 |
| 第 6 章 | 令牌环 + 定位链 | token≈-9.0×10^18 → 名单 {node2,node4,node5} | 同一个名单，只是按「活」过滤 |
| 第 5 章 | gossip 的活/死判定 | node4 DOWN 的本地结论，决定走 hint 分支 | 候选池里划掉 node4 |
| 第 7 章 | CL/blockFor/响应处理器 | 等几个 ack（QUORUM=2） | 凑几份回话（R=2） |
| 第 7 章 | hinted handoff | 挂掉的副本写欠条 | ——（读没有 hint） |
| 第 2~4 章 | CommitLog/Memtable/SSTable | 副本本地的落地引擎 | 副本本地的取数引擎 |

类比一下「客串」：RocksDB 像自家车库——DBImpl 这个老管家常驻进程，谁要存取都找他；Cassandra 像快递分拣站——包裹到谁手里，谁就当场客串分拣员，按墙上同一张规则表（StorageProxy 每节点一份同样的代码）办事。好处是没有单点，坏处是「分拣规则」人人要会，本章讲的就是这张规则表。

两条流水线的骨架先立起来（细节随后两节展开）：

```text
写：mutate(:978) → performWrite(:1732 算名单+配处理器) → sendToHintedReplicas(:1827 分发+欠条)
    → 副本端 Keyspace.apply(:437 先 CommitLog 后 Memtable) → handler.get() 等满 2 个 ack
读：read(:2176) → fetchRows(:2652) → getReadExecutor(:196 选执行器)
    → executeAsync(:181 1 data + 其余 digest) → 对账 → (不一致才)读修复 → 返回
```

一个容易忽略的写读不对称先摆在这：**写发给全部 3 个副本**（第 7 章：writeNormal 选择器，`locator/ReplicaPlans.java:647-681`），只是不等第 3 个；**读只联系 blockFor=2 个**（`locator/ReplicaPlans.java:891`：contacts = 前 blockFor 个活候选）。写图「多发的都是白赚的冗余」，读图「少发的都是省下的带宽」——方向相反，各有算计。

```text
举例：同一行 id=47 在两条流水线里的联络人（健康集群，QUORUM=2）
写：发给 {node2, node4, node5} 全部 3 个，等 2 个 ack（第 7 章「等 2 ≠ 只发 2」）
读：只联系 snitch 评分前 2 名——data 给最快的 node2，digest 给次一名；
    第 3 名（通常是跨机架的 node5）这一单根本不上场，除非推测补发。
一句话：写按「名单」发、按「档位」等；读按「档位」选人、按「对账」收。
```

## 二、写流水线：从 mutate 到本地 CommitLog 的五站

先把五站的分工表钉在墙上（后面逐站展开）：

| 站 | 谁在忙 | 输入 → 输出 | 关键源码 |
| --- | --- | --- | --- |
| ① 接单分装 | 协调者 | 一批 Mutation → 各配一个处理器 | `service/StorageProxy.java:978` |
| ② 分发欠条 | 协调者 | 名单 → 活副本收件 + 死副本欠条 | `service/StorageProxy.java:1827` |
| ③ 本地落地 | 每个活副本 | Mutation → CommitLog + Memtable | `db/Keyspace.java:437` |
| ④ 等确认 | 协调者 | blockFor 个 ack → 放行/超时 | `responseHandler.get():1006` |
| ⑤ 失败善后 | 协调者 | 超时 → ANY 兜底 hint / 记账抛异常 | `service/StorageProxy.java:1009-1042` |

**第一站：接单与分装。** `StorageProxy.mutate`（`service/StorageProxy.java:978`）拿到一批 Mutation（单条语句通常就一件），逐件交给 `performWrite`（`:1732`）。performWrite 干三件事：算副本名单（`:1744`，ReplicaPlans.forWrite + writeNormal——无 transient 副本时联络人=全部副本）、按 CL 配响应处理器（`:1752`，QUORUM 配 WriteResponseHandler，内部从 blockFor=2 倒数，第 7 章拆过）、把活交给发送站（`:1754`）。

**第二站：分发与欠条。** `sendToHintedReplicas`（`service/StorageProxy.java:1827`）遍历名单里的**每一个**副本，活死分四路：自己（node3 不在 id=47 名单里，本单跳过）、同 DC 活副本直接发（`:1927`）、跨 DC 活副本找一台中转、**死副本**先给处理器记一笔 expired（`:1904`，不等它了），再问 shouldHint——宕机 ≤ 3h 就写一张 hint 欠条（`:1915-1916`，第 7 章：字段 {Mutation, 时刻, gcgs}，10s 一轮派发）。发送前还有个细节：Mutation 先预序列化缓存（`:1853`），同一件行李发三份只编码一次——第 9 章那笔序列化税在这里交得尽量省。

**第三站：副本本地落地。** 活副本收到 MUTATION 消息，入口是 `db/MutationVerbHandler.java:52`，落进 `Keyspace.apply`（`db/Keyspace.java:437`）——注释一句话写明纪律：**先记全局 CommitLog，再更新 Memtable 与索引**。实现在两行：`beginWrite` 追加 CommitLog 段（`:549`，内部 `db/CassandraKeyspaceWriteHandler.java:42-53`），拿到落盘凭据后 `cfs.getWriteHandler().write` 进 Memtable（`:579`）。这正是第 2 章拆过的本地写路径——远看是分布式分发，近看每台机器跑的都是第 2 章那套「先保命再落内存」。

**第四站：等确认。** 每个副本干完活回一个 ack。协调者的处理器从 2 倒数（`service/StorageProxy.java:1006-1007` 的 `responseHandler.get()`），减到 0 放行返回客户端；等不满就抛 WriteTimeout。**第五站：失败善后。** 若 CL=ANY 且超时，协调者把整批 Mutation 兜底写成 hint（`:1009-1014`）——第 7 章的「ANY 欠条也算数」就是这条分支。

```text
举例：场景 A 的写单全程（健康 3 副本、等 2；时间为示意量级）
t0.0ms  node3 收到 QUERY 帧（第 9 章），第 8 章装箱 Mutation{demo, key=47, ts=1005}
t0.2ms  算名单 {node2,node4,node5}；配 WriteResponseHandler（blockFor=2）
t0.3ms  预序列化；三路并发发出（node2/node4/node5 各一份）
t1.5ms  node2 落地：CommitLog 追加 → Memtable(name='阿福2'@1005)，回 ack
t1.9ms  node4 落地，回 ack → 2/2 归零，返回客户端成功
t2.6ms  node5 落地，ack 迟到（没人等它）——三份最终都写上，只是承诺只做到 2 份
任何一台此刻断电：CommitLog 里已有这行（第 2 章），重启回放补回来。
```

再补一笔 14:00 之后的同一单（node4 已 DOWN）——值班面板上「写成功率纹丝不动」的完整解释：

```text
举例：node4 DOWN 后的写单（场景 B 的写法）
名单不变 {node2,node4,node5}；遍历 contacts 时 node4 已被 gossip 标死：
  → 响应处理器先记 expired（StorageProxy.java:1904）：这一份不等了
  → shouldHint ✓（宕机 40min < 3h 窗口）→ 写一张 hint 欠条在 node3 本地（:1915-1916）
  → node2、node5 照常收件落地 → 2/2 归零，返回成功
node4 回魂后：10s 一轮的派发把欠条兑现（第 7 章）——写的可用性由活副本顶住，
一致性由 hint 追平；只有 CL=ALL 在事前就被体检拦下（Unavailable）。
```

## 三、读流水线：一条 SELECT 的 data + digest 对账

**第一站：接单选执行器。** `StorageProxy.read`（`service/StorageProxy.java:2176`）把 ReadCommand 交给 `fetchRows`（`:2652`），后者为每条命令造一个读执行器：`AbstractReadExecutor.getReadExecutor`（`service/reads/AbstractReadExecutor.java:196`）。执行器有三种，选哪个由**表属性 speculative_retry** 决定（`:204`）：

| 执行器 | 什么时候补发 | 触发条件（speculative_retry） | 默认？ |
| --- | --- | --- | --- |
| NeverSpeculating（`:276`） | 永不 | NONE；或候选数=联络数（没得补，`:216-222`） | 兜底档 |
| Speculating（`:305`） | 慢了才补发一台 | PERCENTILE / CUSTOM（默认 99p，`schema/TableParams.java:452`） | **出厂默认** |
| AlwaysSpeculating（`:378`） | 每单先多发一台 | ALWAYS | 追求极限尾延迟时 |

**第二站：算名单（读的规则与写不同）。** `ReplicaPlans.forRead`（`locator/ReplicaPlans.java:891`）：候选 = 活副本按 snitch 评分排序（`:930-932`）；**contacts = 前 blockFor 个**（ALWAYS 再+1）。QUORUM=2，健康的名单里只联系 2 台。

**第三站：1 data + 其余 digest。** `executeAsync`（`service/reads/AbstractReadExecutor.java:181-191`）：contacts 里**第一台发 data 请求**（拿完整数据），**其余发 digest 请求**（只要 MD5 摘要，`db/Digest.java`——第 7 章拆过：整行压成一个指纹）。QUORUM=2 就是 1 data + 1 digest。

**第四站：对账。** 执行器构造时就已把三件帮手装配好（`service/reads/AbstractReadExecutor.java:90-92`）：ReadRepair（修）、DigestResolver（对）、ReadCallback（等）。到齐后 `DigestResolver.responsesMatch`（`service/reads/DigestResolver.java:105-127`）把摘要互相比：全一致 → data 那份直接返回，完事；不一致 → 进入**第五站：读修复**。`DataResolver`（`service/reads/DataResolver.java:63`）向其余副本补发 data 请求，拼出按时间戳裁决的最新版本（ts 大者胜，1005 覆盖 1001），`BlockingReadRepair`（`service/reads/repair/BlockingReadRepair.java:75-79`，注释自称「Classic read repair」）把落后的副本补写齐、**修完才返回**——默认 BLOCKING（`schema/TableParams.java:460`）就是「宁可这单慢，不让账烂着」。等待的闹钟是 ReadCallback（超时抛 ReadTimeoutException，`service/reads/ReadCallback.java:218-219`）。

```text
举例：场景 B 的读单全程（node4 DOWN 后，活名单 {node2,node5}）
候选池：{node2, node5}（gossip 判死，node4 出局）——共 2 个 = blockFor 2，刚好够，
        连「补发一台」的余量都没有：getReadExecutor 里候选数==联络数时直接退化成
        NeverSpeculating（AbstractReadExecutor.java:216-222，还记一笔「想推测没得推测」）
t0.0ms  data → node2（snitch 评分第一）；digest → node5
t1.8ms  node2 回完整行 {阿福2, 31}；node5 回 16 字节 MD5 摘要
t2.1ms  对账：node2 的 data 摘要 == node5 的 digest → 一致，直接返回
        （若不一致：补发 data 给 node5 → 时间戳拼版 → BLOCKING 补写 → 才返回）
        若 node2 卡住：99p 推测想补发 node4——已 DOWN，只能等 ReadTimeout 5s
```

## 四、本地那一站：副本收到 ReadCommand 之后

写流水线的「本地站」第二节已经看过（MutationVerbHandler → Keyspace.apply → CommitLog/Memtable）。读的本地站值得单独走一遍，因为它把第 2~4 章的存储引擎接回来了：副本收到 READ 请求，入口 `db/ReadCommandVerbHandler.java:50`，核心两行在 `doRead`（`:56-66`）：`command.executeLocally(controller)` 取数、`createResponse` 打包回信。

executeLocally 一路下钻（`db/ReadCommand.java:520`）→ `queryStorage`（`db/SinglePartitionReadCommand.java:556`）→ **`queryMemtableAndDisk`（`:727`）**——名字就是流程：先问 Memtable（最新的账），再问磁盘上的 SSTable 集合，把同键的多个版本**按时间戳归并**，第一个到的最新版本算数。写读两个本地站并排看，会发现它们就是第 2 章的一体两面：

| | 写的本地站 | 读的本地站 |
| --- | --- | --- |
| 入口 | MutationVerbHandler（`db/MutationVerbHandler.java:52`） | ReadCommandVerbHandler（`db/ReadCommandVerbHandler.java:56-66`） |
| 第一落点 | CommitLog 追加（`db/Keyspace.java:549`） | 当前 Memtable 查询 |
| 第二落点 | Memtable 插入（`db/Keyspace.java:579`） | SSTable 逐本从新到旧（第 4 章索引定位） |
| 裁决规则 | 同 ts 内容相同，重放无害 | 时间戳大者胜（1005 > 1001） |

```text
举例：node2 处理 data 请求（id=47）时的查找顺序（呼应第 2~4 章）
① 当前 Memtable：name='阿福2'@1005 还没 flush？→ 命中，直接带路
② （若已 flush）逐本 SSTable 从新到旧问：第 4 章的索引先二分定位分区，
   布隆过滤器裁掉不可能的本，行索引块里取行
③ 多处命中（旧值 1001 在 SSTable、新值 1005 在 Memtable）→ 按 ts 归并，1005 胜
④ digest 请求同路走一遍，最后把整行压成 MD5 回给协调者（只回指纹不回数据）
副本端没有「协调者」这个概念——它眼里只有一件本地活，这是 Cassandra 无中心结构的微观体现。
```

## 五、超时、失败与重试：客户端该不该再发一次

三种异常，语义完全不同，排障口诀是**事前、事中、事外**：

| 异常 | 时机 | 含义 | 客户端动作 |
| --- | --- | --- | --- |
| UnavailableException | 发请求**前** | 活副本 < blockFor，压根没发（`locator/ReplicaPlans.java:143`） | 降档重试（QUORUM→ONE）或放弃 |
| WriteTimeoutException | 等 ack **中** | 发出去了，blockFor 个没凑齐（`service/StorageProxy.java:1009-1031` 记账抛出） | 可以重试——见下面的幂等账 |
| ReadTimeoutException | 等回话**中** | data+digest 没凑齐 R 份（`service/reads/ReadCallback.java:218-219`） | 可以重试，读天然幂等 |

等待的时长：读 `read_request_timeout` 出厂 5s（`conf/cassandra.yaml:1388`）；写有个值得记录的细节——**代码默认与出厂配置不一致**：`config/Config.java:159-160` 的代码默认是 2000ms，而随包发布的 `conf/cassandra.yaml:1396` 明确写 `write_request_timeout: 10s` 覆盖它。用默认 yaml 的集群实际是 10s；自研配置中心只带 Config 默认值的嵌入场景才是 2s。引用时两个都标，别被「网上说 2s」和「面板显示 10s」打架搞糊涂。

排障时这些等待落在哪条线程上？`nodetool tpstats` 的 Native-Transport-Requests（第 9 章的收货线程池）、ReadStage/MutationStage（副本本地干活）各行一账：协调者热还是副本热、队列堵还是真在算，一眼分层。写流水线卡 MutationStage 多半是 CommitLog 磁盘吃紧（第 2 章）；读流水线卡 ReadStage 先看 SSTable 层数与缓存命中（第 3~4 章）——两条流水线把前面各章的「本地病」全都会聚到协调者的延迟直方图里，反着查回去就是排障路径。

**写超时为什么敢重试：幂等账。** 这笔写带着协调者的微秒时间戳（第 8 章 `cql3/Attributes.java:85`，我们的示意值 ts=1005）。重试重放的是同一件 Mutation、**同一个 ts**：副本按「时间戳大者胜」归并，同一 ts 的同一内容重放 N 次，盘上还是那一份——后写的不覆盖先写的，因为 ts 相同内容相同。所以普通写的重试是安全的（**计数器写例外**：CounterMutation 不带这语义，得走读改写）。这也是把「写流水线」设计成「可重放的分发」的红利：每一站都没副作用，重放无害。

```text
举例：写超时后的重放（示意）
第一次：node2 ack ✓，node4 网络抖动没赶上 10s → WriteTimeout(received=1, blockFor=2)
客户端重试：同一句 UPDATE → 协调者重新取时钟？不——驱动重发同一语句文本，
  新请求会拿新 ts=1006。两个 ts 的同内容写最终归并时 1006 > 1005，胜出的是同一份内容。
  真正的「同 ts 重放」发生在系统内部：hint 派发、读修复、commitlog 回放——
  它们重放的都是当初那件 Mutation 原件（ts=1005），重放多少遍都无害。
```

**speculative retry 一句话收尾**：表属性（默认 99p）只作用于读——等不到就补发一台额外副本抢答；写侧另有 additional_write_policy（同默认 99p，`schema/TableParams.java:453`）管 cheap quorum 的补发。两者都是「用多余流量买尾延迟」，第 7 章的档位表负责「等几份」，这里负责「等多久还不死心」。

## 六、和 RocksDB 摆在一起看：两条流水线的并排账

把第 1 章的 RocksDB「写 4 步 / 读 4 步」与本章两条流水线并排放：

| 步 | Cassandra 写流水线 | RocksDB 写流水线（第 1 章口径） | Cassandra 多出什么 |
| --- | --- | --- | --- |
| 1 | mutate 接单、算名单（:978/:1732） | ① WriteBatch 组包（`include/rocksdb/write_batch.h:64`） | 名单计算、响应处理器配置 |
| 2 | 分发全副本 + hint 欠条（:1827） | ——（没有分发这回事） | **网络分发 + 死副本欠条** |

并排读出的三层差异：**本地站几乎同构**（WAL↔CommitLog、Memtable↔Memtable、逐层找新——这是第 2 章就立下的对应）；**多出来的三笔全在协调层**——网络分发（发给谁）、确认计数（等几份）、副本拼接（谁新算谁）；**角色模型完全不同**——RocksDB 的 DBImpl 是进程内唯一常驻单例，Cassandra 的协调者是每笔请求临时客串的角色，调度台（StorageProxy）每个节点一份、人人可当。最后一句总账：**单机引擎把全部智力花在本地一层的排序与归并上，分布式引擎在同样的本地层外面再包一层「发、等、拼」的物流系统**——读写路径的复杂度，就是物流系统的复杂度。

```text
举例：同一行改动在两条账上的成本（示意）
RocksDB：Put ①→④ 全在进程内，一趟函数调用的微秒级，等的人只有调用线程。
Cassandra：写五站（分发 3 份 + 等 2 份 ack）≈ 毫秒级；读五站（1 data + 1 digest
          + 对账）同量级；多出的毫秒全部花在「发、等、拼」上。
买到的是：node4 卡死 40 分钟，读写照常成功——这 40 分钟的可用性，
就是物流系统每天在付的那几毫秒换来的。
```

## 思考题

1. node4 DOWN 之后，第 7 章说写「仍发给全部 3 个副本」、本章说读「只联系 2 个」。为什么写多发、读少发？（提示：多发的写对后续读是白赚的冗余；少发的读省的是带宽与摘要对账的份子钱——各自的成本落在谁头上。）
2. 场景 B 的读单里，如果 node2 处理 data 请求时恰好卡了 6 秒：99p 推测想补发，补谁？结果是什么异常？（提示：`service/reads/AbstractReadExecutor.java:216-222`——候选池里已没有未联络的活副本；`read_request_timeout` 5s。）
3. 客户端把一句 UPDATE 发了两遍（应用层重试），第二遍的 ts 和第一遍相同吗？「同 ts 重放无害」的保护罩住的是系统内部重放还是客户端重试？（提示：`cql3/Attributes.java:85` 每次请求各取各的时钟；hint/读修复/回放才是重放原件。）
4. 同一行数据：RocksDB 写它的第 ③④ 步与 Cassandra 副本本地的两站几乎一一对应，为什么 Cassandra 还要在外面再包一层「发、等、拼」？（提示：三个副本的容灾与扩容能力就长在这一层——把这一层拆掉，剩下的是什么？）
