# CQL3 解析与执行：从 CQL 到 Mutation

先看一个线上现场。凌晨两点，值班工程师被慢查询告警叫醒：一个服务的 P99 写延迟从 3ms 飙到 40ms。查了存储、查了网络，都没问题。最后发现是那天上线的新代码——每一次写都用**字符串拼接**裸发 CQL，而不是预处理语句：集群在为每一条写请求现场做一次「拆词、建语法树、校验表结构」。几千 QPS 乘上每个请求多出的这一段 CPU，协调者节点直接热了。改成 prepared statement，P99 回到 3ms。他想不通：不就是少拼了个字符串吗，凭什么差这么多？

因为一句 CQL 从网络到达，到真正碰数据，要走完一整条流水线：**协议解析 → CQL 解析（词法+语法）→ 语句对象化与语义校验 → 生成 Mutation/ReadCommand → 交给存储层**。这条流水线每一段都有价格，而 prepared statement 的本事是让中间最贵的几段只付一次钱。看懂每一站产出的「中间形态」——token、AST、语句对象、Mutation——上面那个案子和今后所有的 CQL 疑难杂症，都能对号入座。

全章继续跟那两句话走，口径与前几章完全一致：

```text
贯穿本章的两句 CQL（沿用全轨道口径）：
UPDATE users SET name = '阿福2' WHERE id = 47;    ← 写：第 7 章反复确认的那笔
SELECT name, age FROM users WHERE id = 47 LIMIT 1; ← 读：点查形态
集群：node1~node5，keyspace demo，RF=3，客户端 CL=QUORUM
协调者这次轮到 node3（第 1 章：任何节点都能客串）
id=47 的副本名单 {node2, node4, node5}——本章结尾正好接上第 7 章
```

一句话预告结论：一句 CQL 的终点不是「执行了 SQL」，而是变成一件叫 Mutation 的行李（写）或 ReadCommand 的问询单（读），交到第 7 章的副本确认流程手里。

## 一、入口：QueryProcessor 是唯一的柜台

客户端驱动发来的原生协议消息（QUERY / PREPARE / EXECUTE，第 9 章拆字节）最终都被路由到同一个柜台：`cql3/QueryProcessor.java:112` 的 QueryProcessor，全集群每节点一个单例（`:119`）。它自己声明支持的方言版本是 CQL 3.4.8（`:114`）。柜台的办事流程是一个固定三连（`cql3/QueryProcessor.java:302-312`）：

1. **authorize**：查权限——这个角色对这张表有没有写的权利；
2. **validate**：语义体检——表存在吗、列存在吗、类型对得上吗；
3. **execute**：交给语句对象自己执行，返回结果。

注意这个三连的输入已经是一个**CQLStatement 对象**，不是文本。也就是说，「文本变对象」这件事发生在更早的一站（下一节）。CQLStatement 是全部语句的公共接口（`cql3/CQLStatement.java:32`），两大门派都实现它：

| 门派 | 代表语句 | 改的是什么 | 执行形态 |
| --- | --- | --- | --- |
| DDL | CREATE/ALTER KEYSPACE、TABLE、INDEX | 集群元数据 | 提交进元数据日志，全集群共识后生效（第 14 章展开） |
| DML | SELECT / INSERT / UPDATE / DELETE / BATCH | 数据本身 | 生成 Mutation/ReadCommand，走第 7 章的副本确认 |
| 辅助 | USE / TRUNCATE / 登录授权类 | 会话状态 / 权限 | 多数在协调者本地处理 |

门派往下再分具体语句类：SelectStatement（`cql3/statements/SelectStatement.java:161`）、ModificationStatement（`cql3/statements/ModificationStatement.java:149`，UPDATE/INSERT/DELETE 的共同基类）。这张分法直接决定了你排障时的第一问：**报错发生在元数据层还是数据层？**前者看 schema 变更日志，后者看本章与第 7、10 章的读写路径。

柜台还兼职记账：每次执行都会推进 regular/prepared 两类计数器（`cql3/QueryProcessor.java:927` 的 preparedStatementsExecuted），配合每档 CL 的延迟直方图——凌晨那类「P99 飙升」，先用 `nodetool tpstats` 和这些指标分辨是解析热了还是存储慢了，方向完全不同。

```text
举例：同一个柜台，三种消息的不同走法
QUERY "UPDATE ..."（一次性语句）→ 现场解析出语句对象 → 三连执行 → 丢弃
PREPARE "UPDATE ..."           → 现场解析出语句对象 → 编号入库 → 返回 id
EXECUTE <id>（带参数）          → 按 id 取出缓存的对象 → 绑参数 → 三连执行
凌晨那个事故的根由：第一种走法把「解析」塞进了每一次写的临界路径。
```

## 二、解析：从字符流到语法树

解析这一站分两步，对应编译器课本里的词法和语法。Cassandra 的语法规则不用手写，用 ANTLR 生成：仓库里放的是语法描述文件——`src/antlr/Cql.g:20` 只有一句 `grammar Cql` 和 `import Parser,Lexer`（`:25`），真正的规则在两个子文件里：`src/antlr/Lexer.g:20`（词法，字符流切成 token）和 `src/antlr/Parser.g:20`（语法，token 流归约成树）。构建时 ANTLR 生成 CqlParser/CqlLexer 两个 Java 类，所以你在源码树里 grep 不到它们——生成的代码不进仓库。

关键规则的行号值得记：`Parser.g:236` 的 cqlStatement 列出全部语句种类的岔路口，往下 `Parser.g:310` selectStatement、`Parser.g:564` insertStatement、`Parser.g:632` updateStatement、`:668` deleteStatement——每条规则的动作代码里直接 `new` 出对应的 Raw 语句对象。入口在 QueryProcessor：`getStatement`（`cql3/QueryProcessor.java:950`）调 `parseStatement`（`:986`），后者一行就是流水线的接力棒：`CQLFragmentParser.parseAnyUnhandled(CqlParser::query, queryStr)`（`:991`）。

```text
举例：UPDATE users SET name = '阿福2' WHERE id = 47; 的两步解析
词法（Lexer.g）：字符流 → 10 个 token（句尾分号另计，不算语义 token）
  [UPDATE] [users] [SET] [name] [=] ['阿福2'(字符串字面量)] [WHERE] [id] [=] [47(整数)]
语法（Parser.g:632 updateStatement 规则）：
  token 流按规则归约 → 一棵小树，根是 UpdateStatement.ParsedUpdate（Raw）
  树上挂着：表名 users、SET 列表 [(name ← '阿福2')]、WHERE (id = 47)、无 USING 子句
此刻一切都是「字面量」：47 还是个 token，没变成 int；表还不查，只是个名字。
```

把那棵树画出来（示意），每个节点最终都会成为 Raw 对象里的一个字段：

```text
UpdateStatement.ParsedUpdate（Raw）
├── name      : "users"            ← 还只是字符串，没对到 TableMetadata
├── updates   : [ Operation{ column: "name",
│                            value: Term.Raw('阿福2') } ]
├── where     : Relation{ name: "id", op: EQ, value: Term.Raw(47) }
└── attrs     : Attributes{ timestamp: null, ttl: null }   ← USING 子句没写就是空
```

词法和语法各自会拦下一类错，报错长相完全不同，值得各认一次脸：

```text
举例：两类报错的分界
SELECT FROM users;
→ 词法/语法错误 SyntaxException：规则归约不下去，报「Failed parsing statement」
  （QueryProcessor.java:999 的兜底文案）——句子本身不合法
SELECT nonexistent_col FROM users WHERE id = 47;
→ 语义错误 InvalidRequestException：句子合法，但 prepare/validate 阶段查表发现
  没有这一列——句子合法但对象不存在
一句话：SyntaxException 怪写法，InvalidRequestException 怪世界。
```

Raw（`CQLStatement.Raw`）到「真」语句的最后一跳也在 `getStatement` 里：`statement.prepare(clientState)`（`cql3/QueryProcessor.java:958`）。这一步开始查表——按表名找到 TableMetadata，把列名对到具体列定义，把绑定标记 `?` 登记成带类型的 BindMarker。**语法错误在解析时报（SyntaxException），而「表不存在」「列不存在」在 prepare/validate 阶段报（InvalidRequestException）**——分清这两类报错，排障时能少走一半弯路。

## 三、预处理语句：解析一次，绑定千次

现在正式回答凌晨的案子。PREPARE 消息到达后，QueryProcessor 走一遍完整解析，然后把语句对象存进一个缓存，钥匙是**这句话的 MD5**：`computeId` 把 keyspace 名与查询文本拼接后取 MD5（`cql3/QueryProcessor.java:843-847`，MD5 的实现在 `utils/MD5Digest.java`），返回给客户端作 statement id。缓存的容量按字节计费（Caffeine 加权缓存，`cql3/QueryProcessor.java:123、143-148`）。之后客户端每次 EXECUTE 只带 id 和参数值，协调者从缓存取出对象、把值填进 BindMarker（绑定与数量校验在 `processPrepared`，`cql3/QueryProcessor.java:909-928`）——**词法、语法、表结构解析统统只做一次**，之后每次执行付的只是绑定加执行的钱。

一个等价的生活类比：裸发 CQL 像每次都把「去超市买一瓶酱油，要生抽，500ml」这句话从头念给一个新店员听，他每次都要理解一遍；prepared 像办了张「常购单 7 号」——第一次说清楚存档，之后进门喊「7 号」+ 付钱就行。店员（协调者）的脑力（解析 CPU）只花在你第一次建档上。

```text
举例：裸发 vs 预处理，每 1000 次写各付什么账
裸发 QUERY ×1000：1000 次（词法 + 语法归约 + 查表元数据 + 绑定 + 执行）
PREPARE 1 次 + EXECUTE ×1000：1 次全价 + 1000 次（查缓存 + 绑定 + 执行）
省下的正是 P99 从 40ms 到 3ms 的那段：每条语句省的是解析的 CPU 与分配。
```

预处理的第二重价值是**防注入**。绑定参数从协议消息里以二进制值传输，从不参与语法解析——`'阿福2' OR 1=1` 这类 payload 只会成为一个字符串**值**，永远不可能被切成 token 影响语法树。字符串拼接的裸发没有这道墙，这也是为什么「拼接 SQL」在任何数据库里都是反面模式。

两个工程细节别踩坑。其一，id 是**文本的哈希**：两个客户端对同一句 CQL 用的 keyspace 不同，id 也不同（4.0.2 起的行为，`cql3/QueryProcessor.java:117` 标注了分界版本）；语句文本变一个空格，就是另一个 id，缓存里多躺一份。其二，预处理的校验结论会**过期**：PREPARE 时表有 name 列，之后 ALTER 删了它——EXECUTE 时会在 validate 阶段翻车，客户端要准备重新 PREPARE 的逻辑。

绑定本身也有讲究。占位符 `?` 按出现顺序编号，EXECUTE 消息里按序带值；数量不匹配当场拒绝——「there were %d markers(?) in CQL but %d bound variables」（`cql3/QueryProcessor.java:916-920`）。值在绑定后还要过类型校验：id 列是 int，传个字符串进来在 marshal 阶段就报错，到不了存储层。分区键列的绑定还有专属优化——驱动能只发分区键值、由协调者现算 token（`cql3/CQLStatement.java:47` 的 getPartitionKeyBindVariableIndexes 声明了这套索引）。

```text
举例：一次 EXECUTE 的完整行李
客户端发来：statementId=MD5("demoUPDATE users SET name=? WHERE id=?")
            values=['阿福2'(text), 47(int)]
协调者：查缓存命中 → 对象里的两个 BindMarker 各领一个值
       → id=47 marshal 成 int 通过 → 走 authorize/validate/execute 三连
       → （下一节）装箱成 Mutation
若 values 顺序颠倒 ['47', 阿福2]：第二个 marker（id，int 列）拿到 '阿福2'
  → 类型校验失败，InvalidRequestException——顺序也是协议的一部分。
```

## 四、修改语句的终点：一件叫 Mutation 的行李

UPDATE 的执行从 `ModificationStatement.execute`（`cql3/statements/ModificationStatement.java:708`）进入：无条件的更新走 `executeWithoutCondition`（`:724`），先把 CL 校验掉（ANY 不能写 counter、SERIAL 不能直接用，见第 7 章），然后干两件事——`getMutations` 生成修改（`:739-745`），`StorageProxy.mutateWithTriggers` 发出去（`:748`）。**从这里开始，笔交给第 7 章**：StorageProxy 按 token 算副本名单 {node2, node4, node5}，配响应处理器等 2 个 ack——正是上一章拆过的流程。

`getMutations`（`cql3/statements/ModificationStatement.java:961`）产出的是 Mutation（`db/Mutation.java:68`）。**一个 Mutation = 一个分区的一次完整修改**，这是它的法律定义。字段就三样（`:76-80`）：keyspace 名、DecoratedKey（分区键+token，第 6 章的老朋友）、以及一张表 → PartitionUpdate（分区级更新包，`db/partitions/PartitionUpdate.java:108`）的映射。

```text
举例：UPDATE users SET name='阿福2' WHERE id=47 装箱成 Mutation
keyspaceName : "demo"
key          : DecoratedKey{ key=bytes("47"), token≈-9.0×10^18 }   ← 第 6 章
modifications: { users 表 → PartitionUpdate{
                   分区键 47 的一行：
                     name 列 ← '阿福2'，单元时间戳 ts（协调者微秒时钟，
                     未写 USING TIMESTAMP 时取当前时刻，Attributes.getTimestamp，
                     cql3/Attributes.java:85；示意沿用全轨道的 ts=1005） }
WHERE id=47 只有一个分区键 → 恰好一个 Mutation；
一条 IN(47,48) 会拆成两个 Mutation；BATCH 把多个 Mutation 装一趟车。
下一站 StorageProxy.mutateWithTriggers（:748）→ 第 7 章的 blockFor 倒计时。
```

为什么中间形态偏偏是「分区粒度的行李」？因为它是全集群的**最小运费单位**：协调者按它的 key 算名单、把它原样发给每个副本、副本把它整个 apply 进自己的 LSM 引擎（第 2 章）、hint 把它整个存起来（第 7 章 `hints/Hint.java:66` 的第一个字段就是它）、repair 按分区对账它的内容。CQL 的语法怎么变（USING TTL、批处理、条件更新），最终都收敛到这件标准行李上——上层百花齐放，下层一个接口。

同门三兄弟装进 Mutation 的东西略有不同，值得各认一眼：UPDATE 装的是新列值（上面的例子）；INSERT 装的是整行（本质是 UPDATE 的「全部列都给」形态）；DELETE 装的是**墓碑**——「name 列在 ts 时刻删除」的特殊单元（第 3 章拆过 gc_grace 与它的恩怨）。三者的时间戳规则一致：不写 USING TIMESTAMP 就取协调者时钟的微秒值（`cql3/Attributes.java:85`），写了就尊重用户——这也是 last-write-wins 的「写」到底比什么：比的就是行李上这个 ts。

```text
举例：三兄弟的行李对照（都是 id=47 这个分区）
UPDATE users SET name='阿福2' WHERE id=47
  → { key=47, cells: [name ← '阿福2' @ts] }
DELETE name FROM users WHERE id=47
  → { key=47, cells: [name ← 墓碑 @ts] }          ← 删除也是一次「写」
DELETE FROM users WHERE id=47
  → { key=47, 分区级墓碑 @ts }                     ← 整行连锅端
BATCH 把上面任意几件打成 List<Mutation> 一趟发——批内同分区的多句由批语句的
收集器按分区合并去重（cql3/statements/BatchStatement.java:359 的 getMutations），
单条语句改多个分区（WHERE id IN ...）则由语句自己的收集器摊开成多件。
```

## 五、查询执行：从 SELECT 到 ReadCommand

SELECT 走另一条岔路：`SelectStatement.execute`（`cql3/statements/SelectStatement.java:369`）最终调 `getQuery`（`:470-506`）把「想要什么」翻译成读命令。翻译的核心是一次分流（`:501-506`）：WHERE 能**唯一定位分区**（分区键全给了等值条件，比如 id=47）→ 生成 SinglePartitionReadCommand（`db/SinglePartitionReadCommand.java:98`，点查形态，创建入口 `:196`）；分区键没给全或要扫多个分区 → PartitionRangeReadCommand（范围扫描，成本完全不同量级）。两者的公共抽象是 ReadCommand（`db/ReadCommand.java:127`）——读侧的「问询单」，写着分区键、要哪些列、过滤条件、上限。问询单交给 `StorageProxy.read`（`service/StorageProxy.java:2176`）后，就进入第 7 章的 1 data + R−1 digest 流程。

LIMIT 家族和 ALLOW FILTERING 的语义值得单独记，因为它们决定「问询单有没有资格被生成」：

| 子句 | 语义 | 一句话 |
| --- | --- | --- |
| LIMIT n | 全结果集最多取 n 行 | 到量即停，协调者统一记账（`cql3/statements/SelectStatement.java:487` 的 DataLimits） |
| PER PARTITION LIMIT n | 每个分区最多取 n 行 | 宽表场景给每个键封顶，字段在 `:182` |
| ALLOW FILTERING | 允许引擎放弃「必须能定位」的坚持 | 第 6 章见过：WHERE 落在非分区键上，引擎警告后才肯逐行筛（`cql3/restrictions/StatementRestrictions.java:81-84` 的警告文案） |

```text
举例：三个 SELECT 的三种命运
SELECT ... WHERE id=47                    → SinglePartitionReadCommand：直奔 3 副本之一
SELECT ... WHERE id IN (47,48)            → 两个点查命令，并行发
SELECT ... WHERE name='阿福2'             → 引擎拒绝：name 定不了位；加 ALLOW FILTERING
                                            后变成「逐分区扫完再筛」——被允许，不被祝福
```

大结果集还有一道与 LIMIT 平行的闸门：**分页（paging）**。驱动设了 fetch size（协议参数）后，ReadCommand 被切成一页一页地执行，协调者记住「翻到哪了」（分页状态随结果返回，下一页带上）——LIMIT 管的是「最多取多少」，分页管的是「一次运多少」，两个上限独立生效。聚合（count、sum）与排序（ORDER BY，只允许聚簇列）在 SelectStatement 的执行器里完成，不改变底层命令的形态：数据按问询单取回来，再在协调者内存里算。

读路径也一样有「三连」之外的舞台：`executeInternal` 系列（`cql3/statements/SelectStatement.java:673-678`）是本地直查变体，系统表自检和 DESCRIBE 用它——不碰副本确认，直接读本节点的 LSM。这提醒我们 CQL 语句对象是**可复用的执行计划**，往哪个执行器里放，就跑哪条路径。

最后一句带过函数：CQL 里能写的 `now()`、`token(id)`、`toTimestamp()`、聚合 `count(*)` 都住在 `cql3/functions/` 包（原生函数与用户自定义函数 UDF/UDA 同一框架，`cql3/functions/TokenFct.java:33` 的 token() 第 6 章用过）。它们在解析期被识别为函数调用、在校验期解析到具体实现、在执行期取值——是语句树上的叶子节点，不是独立的执行阶段。

## 六、和 RocksDB 摆在一起看：API 层的厚与薄

同样一句「把 id=47 的名字改成 阿福2」，两边的入口厚度天差地别。RocksDB 的「查询语言」就是 C++ API：`DB::Put` / `DB::Get`（`include/rocksdb/db.h:778`），批量写用 WriteBatch（`include/rocksdb/write_batch.h:64`）。调用方传的是**已经结构化的参数**——键是字节串、值是字节串，没有文本、没有词法、没有「表」和「列」的概念要校验。一切解析在**编译期**已经完成：C++ 编译器替你查了函数签名，序列化格式是你自己的代码写死的。Cassandra 收到的则是一段**运行时文本**，必须现场经历三层翻译，每层都有耗时量级：协议层解帧（第 9 章，微秒级）、CQL 词法+语法（这章第二节，几十微秒级且随语句复杂度增长）、语义校验与对象化（查表元数据，微秒级）——prepared statement 砍掉的正是中间两层在重复请求上的开销。

| 维度 | RocksDB | Cassandra |
| --- | --- | --- |
| 接口形态 | C++ API（编译期绑定） | CQL 文本 + 原生协议（运行时解析） |
| 解析层 | 无：Put/Get 直接进写路径 | 词法 → 语法 → 语义 → 语句对象，四道工序 |
| 「一条写」的形态 | WriteBatch（字节串集合） | Mutation（一个分区的一次完整修改） |
| 重复执行的成本 | 每次都一样（无解析可言） | 裸发每次全价；prepared 只付绑定+执行 |
| 防注入 | 不适用（无文本协议） | 绑定参数绕过语法层，天然免疫 |
| 查询能力 | Get / 迭代器（按键有序） | WHERE/IN/LIMIT/函数/索引（第 11 章 SAI） |

「预处理语句」翻译到 RocksDB 的世界，就是**直接调 API**：编译期已经把「做什么」定死，运行时只传「参数」。RocksDB 天生住在预处理的世界里，Cassandra 的 prepared 只是把 CQL 用户拉回这个世界。厚的 API 层换来的是另一件东西：客户端可以是任何语言、语句可以是动态生成的、权限和校验有统一的执行点——这是数据库服务与嵌入式库的分界线。选型时记住这笔账：要 SQL 语义和多语言客户端，就得付解析层的钱（并且老老实实用 prepared）；只有KV 且进程内调用，RocksDB 让你从出生就免单。

```text
举例：一笔「改 id=47 的名字」在两边的耗时构成（量级示意）
RocksDB 进程内调用：
  Put() → WAL 追加 + MemTable 插入 ≈ 微秒级，没有「翻译」这一站
Cassandra 裸发 CQL：
  协议解帧（~微秒）→ 词法+语法（几十微秒，随语句长度涨）→ 语义校验（查元数据，
  ~微秒）→ Mutation 装箱 → 副本确认（毫秒级，网络主导）
  前三站在低负载时无感，高 QPS 下乘出来就是凌晨的 40ms P99
Cassandra prepared：
  EXECUTE → 缓存取出 + 绑定（微秒）→ Mutation 装箱 → 副本确认
  前三站只剩半站——这就是「少拼了个字符串」值多少钱
注意：毫秒级的副本确认（第 7 章）才是延迟大头，解析层只在「叠加高并发」时
显形——别把两层的病吃错药。
```

## 这一章留下的线索

- **QueryProcessor 是唯一柜台**：QUERY/PREPARE/EXECUTE 三种消息殊途同归到 `cql3/QueryProcessor.java:112`，语句执行固定三连 authorize → validate → execute（`:302-312`）；
- **解析 = 词法 + 语法**：语法在 `src/antlr/` 三件套（Cql.g 入口 + Lexer.g + Parser.g，生成代码不进仓库），updateStatement 规则在 `Parser.g:632`，产物是 Raw 语句对象，`prepare()` 一跳查表成名（`cql3/QueryProcessor.java:950-958`）；
- **prepared 的钥匙是 MD5**：`computeId` = MD5(keyspace+文本)（`:843`），解析一次、绑定千次，还顺带防注入——凌晨的 P99 案子就是少了它；
- **Mutation 是最小运费单位**：一个 Mutation = 一个分区的一次完整修改（`db/Mutation.java:68`），UPDATE id=47 装箱后交 `StorageProxy.mutate`（`cql3/statements/ModificationStatement.java:748`），无缝衔接第 7 章的 blockFor；
- **读的分水岭是「能不能定位」**：分区键给全 → SinglePartitionReadCommand 点查（`cql3/statements/SelectStatement.java:501-506`）；给不全 → 范围扫描或 ALLOW FILTERING 的逐行筛——LIMIT 只管到量即停，不降低定位成本。

下一章下到线路上看：QUERY/EXECUTE 这些消息在 TCP 字节流里长什么样、驱动怎么多路复用——[原生协议传输：CQL 消息的线路形态](../query/02-原生协议传输.md)。

## 思考题

1. 把应用从裸发 CQL 迁到 prepared statement，P99 通常立竿见影。但语句缓存是按「文本+keyspace」计 MD5 的，一个 ORM 动态拼出 10 万种不同文本的语句，prepared 还划算吗？缓存会怎样？（提示：`cql3/QueryProcessor.java:143-148` 的按字节加权上限与逐出日志。）
2. `SELECT * FROM users WHERE age > 30 ALLOW FILTERING` 在 5 节点小集群能跑，搬到 500 节点大集群为什么可能拖垮协调者？ALLOW FILTERING 改变了哪些环节的成本归属？（提示：第 6 章「定位链只认分区键」与本章 `cql3/statements/SelectStatement.java:501-506` 的分流。）
3. `UPDATE users SET name='阿福2' WHERE id IN (47,48,49)` 会生成几个 Mutation？如果 47/48/49 的副本名单各不相同（第 6 章算过 47 与 48 差两台），StorageProxy 要等几组 ack？（提示：每个 Mutation 独立算名单、独立配响应处理器。）
4. 同样是「批量写」，RocksDB 的 WriteBatch 和 Cassandra 的 BATCH 语句在原子性承诺上有什么差别？（提示：WriteBatch 是一次库调用的原子单位；Cassandra 批内语句按分区合并成多个 Mutation，各自走第 7 章的一致性确认——「批次原子性」到底指哪一层。）
