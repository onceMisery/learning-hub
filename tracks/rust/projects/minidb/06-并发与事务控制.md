## 1. 要解决的问题与设计权衡

### 1.1 三个不同层次的"并发"

讨论并发前必须先分清层次，因为它们需要完全不同的手段：

| 层次 | 场景 | 本项目的手段 |
|------|------|-------------|
| **多线程共享一个引擎** | 服务器里多个连接同时读写 | `Arc<RwLock<Engine>>` |
| **多进程访问一个目录** | 两个 `minidb-server` 指向同一个 `--dir` | `LOCK` 文件（模块五） |
| **异步任务里的并发** | tokio 里上万个连接 | Actor + channel（模块七） |

本模块讲第一层。注意它和第三种手段**不能混用**：`std::sync::RwLock` 的守卫**不能跨 `.await` 持有**，这是模块七的第 2 号坑。

### 1.2 权衡一：怎么保护共享状态？

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **一把大锁**（本项目） | `Arc<RwLock<Engine>>`，整个引擎一把锁 | 实现简单、绝不会死锁、语义清晰 | 吞吐上不去；合并时全阻塞 |
| 细粒度锁 | 索引一把锁、每个段一把锁、写游标一把锁 | 并发度高 | 锁顺序、死锁、可重入性全是坑 |
| 无锁结构 | `dashmap::DashMap`、原子变量 | 读完全不阻塞 | 只适合索引这种局部状态；涉及磁盘 I/O 的部分锁不住 |
| **Actor / 消息传递** | 单线程持有引擎，其他人发消息 | 根本不需要锁；天然串行 | 多一次消息拷贝；需要专门的线程 |

本项目**两种都实现了**，正好可以对比：

- `SharedEngine`（stage7）= 一把大锁 + 读写分离，同步服务器用它；
- `EngineHandle`（stage8）= Actor + channel，异步服务器用它。

**为什么教学项目要展示两种？** 因为在 Rust 里，"用锁"和"不用锁"的取舍发生了根本变化：

- Java 里不用锁几乎等于"等着出 bug"，所以默认就是加锁；
- Rust 里"把状态交给一个线程独占"是**类型系统保证**的方案——`Engine` 不需要是 `Sync` 的，只要 `Send`（能搬进那个线程）就行。这让 Actor 方案的成本大幅下降。

### 1.3 权衡二：`RwLock` 还是 `Mutex`？

读多写少的场景直觉上应该用 `RwLock`。但要小心三个反直觉的事实：

1. **`RwLock` 的读锁也不便宜**。它要维护读者计数，是**一次原子写操作**，会引发缓存行在核之间弹跳（cache line ping-pong）。在"读操作极短"的场景下，`RwLock` 可能比 `Mutex` **还慢**。
2. **写锁饿死**（writer starvation）：读者不断进来时，写者可能长时间拿不到锁。Linux 的 `pthread_rwlock` 默认是读者优先，`std::sync::RwLock` 的实现则依赖平台。
3. 本项目的读操作**包含磁盘 I/O**（`GET` 会 `read_at`），临界区很长——这种情况下 `RwLock` 的价值才真正体现出来：8 个读者可以并行做磁盘 I/O。

**判断标准**：临界区越短，`Mutex` 越合适；临界区越长（尤其是有 I/O），`RwLock` 越合适。

### 1.4 权衡三：锁的粒度放在哪一层？

这是本模块**最实用**的一节。看 `concurrency_demo` 的实测：

| 做法 | 结果 |
|------|------|
| 8 线程 × 1000 次 `GET` + `SET`（两条命令分别加锁） | 最终值 **1078 / 8000**，丢失 86.5% |
| 8 线程 × 1000 次「加锁 → `GET` → `SET` → 解锁」 | 最终值 **8000** ✅ |

**关键认识**：锁本身没有错，错的是**加锁的粒度与"原子操作的边界"不匹配**。

单条 `SET` 是原子的（写锁独占）；但"`GET` 然后 `SET`"是一个**跨越两条命令的业务操作**，引擎不知道它们应该绑在一起。所以要么：

- 在**应用层**加锁（示例的做法，代价是完全串行）；
- 要么让引擎提供**单命令完成**的原子操作（`INCR`、`CAS`）——这才是 Redis/etcd 的做法。

模块"事务"的边界就在这里，见 1.5。

### 1.5 "事务"到底在哪？—— ACID 逐项对照

这是本模块最需要说清楚的事：**minidb 有"原子性"，但没有"事务"。**

| ACID | 本项目的情况 | 说明 |
|------|-------------|------|
| **A 原子性** | ✅ **单条命令**原子；❌ 多条命令之间无原子性 | 单条 `SET` 由写锁保护，中间不可能被插入；`GET`+`SET` 是两次独立加锁 |
| **C 一致性** | ✅ 单键层面 | 索引与磁盘始终一致（崩溃后由重放重建）；没有跨键约束（本来也没有 schema） |
| **I 隔离性** | ✅ 每条命令 **serializable**；❌ 跨命令无隔离 | 写锁独占 ⇒ 单命令之间不可能互相看到中间态 |
| **D 持久性** | ⚠️ 弱 | 默认不 fsync，断电丢最后几秒（模块五 1.3） |

**"原子性"在这里其实有两层含义，不要混淆：**

1. **并发原子性**（别的线程看不到中间态）——靠锁保证 ✅
2. **崩溃原子性**（断电后不会留下半个写入）——靠 append-only + CRC + 截断保证 ✅（`concurrency_demo` 场景 D 验证了单键写入不会撕裂）

两者都成立，但都只覆盖**单条命令**。

### 1.6 隔离级别对照

把 minidb 放进数据库的经典框架里看：

| 隔离级别 | 本项目是否达到 | 原因 |
|---------|--------------|------|
| Read Uncommitted | ✅ | 不存在"未提交"概念 |
| Read Committed | ✅ | 每条命令独立生效 |
| Repeatable Read | ❌ | 同一连接两次 `GET k` 之间，别的线程可以改 `k` |
| Serializable | ❌（跨命令） | 需要 `MULTI`/`EXEC` 之类的机制 |

要达到 Serializable，需要引入：

- **乐观并发控制**：每条记录带版本号，`SET k v <version>` 版本号不匹配就失败（≈ CAS / etcd 的 `mod_revision`）；
- 或者 **MVCC**：读者拿快照，写者不阻塞读者（PostgreSQL/CockroachDB 的做法）；
- 或者 **命令批处理**：`MULTI ... EXEC` 一次性在写锁内执行（Redis 的做法，但 Redis 的 `MULTI` 不是真正的事务——出错不会回滚）。

**这是练习 1 的方向。**

## 2. 关键数据结构

### 2.1 `SharedEngine` —— 可以 `clone` 的引擎句柄

```rust
#[derive(Clone)]
pub struct SharedEngine {
    inner: Arc<RwLock<Engine>>,
}
```

三层包装，每层各司其职：

| 层 | 作用 | Java 对照 |
|---|------|----------|
| `Engine` | 真正的数据（索引、文件句柄） | 普通对象 |
| `RwLock<..>` | 互斥与读写分离 | `ReadWriteLock` |
| `Arc<..>` | 原子引用计数，允许多个所有者 | `AtomicReference` + 计数 |

`#[derive(Clone)]` 在这里**只增加引用计数**（一次原子加法），**不拷贝引擎**。这和 Java 里 `clone()` 通常意味着深拷贝的直觉完全不同——`SharedEngine::clone()` 是廉价操作，可以随便调用。

**为什么必须 `Arc`？** 因为 `thread::spawn(move || …)` 要求闭包捕获的东西**活得够久**（`'static`）。借用局部变量的引用活不过当前函数，`Arc` 通过"共享所有权"解决了这个问题。

**为什么 `Arc` 不能直接改数据？** `Arc<T>` 只给你 `&T`（共享不可变）。要改就必须内部可变性——`RwLock` / `Mutex` / 原子类型。这就是 Rust 的核心设计：**共享不可变，可变不共享**。

### 2.2 `Send` 与 `Sync` —— 编译期的线程安全证明

```rust
// 简化定义（真实定义是 unsafe auto trait）
pub unsafe auto trait Send {}   // T 的所有权可以转移到另一个线程
pub unsafe auto trait Sync {}   // &T 可以同时被多个线程持有
```

它们是 **auto trait**：编译器根据类型的字段**自动推导**，你不用手写。

| 类型 | `Send` | `Sync` | 说明 |
|------|--------|--------|------|
| `i32`、`String`、`Vec<T>`（T: Send） | ✅ | ✅ | 普通数据 |
| `File`、`TcpStream` | ✅ | ✅ | OS 句柄，跨线程安全 |
| `Rc<T>` | ❌ | ❌ | 非原子引用计数，多线程下计数会错 |
| `Arc<T>`（T: Send+Sync） | ✅ | ✅ | 原子计数 |
| `RefCell<T>` | ✅ | ❌ | 运行时借用检查，非原子 |
| `Mutex<T>` / `RwLock<T>`（T: Send） | ✅ | ✅ | 内部可变性 + 互斥 |
| `*const T` 裸指针 | ❌ | ❌ | 编译器一无所知 |

**这里的关键价值**：在 Java 里，"这个对象能不能跨线程用"是一个**运行时的祈祷**——`ArrayList` 跨线程写会不会出问题？会，但编译器不管，只有线上报警才知道。在 Rust 里，这是一个**编译期的证明**：不满足 `Send`/`Sync` 就编译失败，错误信息还会精确指出是哪个字段不满足。

### 2.3 `PoisonError` —— 锁中毒

```rust
let guard = self.inner.read().unwrap_or_else(std::sync::PoisonError::into_inner);
```

**中毒（poisoning）** 是 Rust 独有的机制：如果一个线程在**持锁期间 panic**，锁会被标记为"中毒"，后续 `lock()` 返回 `Err(PoisonError)`。

它在告诉你：**上一个持锁者死在了临界区中间，数据可能处于不一致状态。**

Java 完全没有对应的机制：`synchronized` 块里抛出 Error 之后锁照样释放，状态坏没坏没人知道。

三种处理策略：

| 策略 | 代码 | 适用 |
|------|------|------|
| 相信数据仍可用 | `.unwrap_or_else(PoisonError::into_inner)` | 本项目：引擎操作基本不会 panic，且 panic 通常发生在 I/O 前 |
| 当做致命错误 | `.expect("锁中毒")` | 数据一致性不可让步的场景 |
| 修复后清除中毒 | `rwlock.clear_poison()` | 你能确定状态已恢复 |

**本项目选择第一种**，并且值得质疑：如果 `compact()` 在持写锁时 panic，索引可能处于"已切换到新段、但 `frozen` 没更新"的半死状态，此时继续服务可能导致错误结果。生产代码更倾向于"中毒即拒绝服务并重启"。

### 2.4 `Arc<AtomicBool>` —— 停止信号

```rust
pub fn spawn_compactor(&self, every: Duration) -> (Arc<AtomicBool>, JoinHandle<()>) {
    let stop = Arc::new(AtomicBool::new(false));
    let stop_clone = Arc::clone(&stop);
    // …
    while !stop_clone.load(Ordering::Relaxed) { /* … */ }
}
```

Java 里这个标志必须是 `volatile`；Rust 里用 `AtomicBool` + 显式 `Ordering`，内存序是**写进代码里**的而不是靠关键字暗示。

`Relaxed` 在这里够用：我们只要求"最终能看到 `true`"，不要求它和其他内存操作有顺序关系。如果需要"停止时同时发布一些数据"，就要用 `Release`/`Acquire`。

## 3. 核心代码路径

### 3.1 加锁的两个私有方法

```rust
fn with_read<F, R>(&self, f: F) -> R
where
    F: FnOnce(&Engine) -> R,
{
    let guard = self.inner.read().unwrap_or_else(std::sync::PoisonError::into_inner);
    f(&guard)
}

fn with_write<F, R>(&self, f: F) -> R
where
    F: FnOnce(&mut Engine) -> R,
{
    let mut guard = self.inner.write().unwrap_or_else(std::sync::PoisonError::into_inner);
    f(&mut guard)
}
```

**为什么把它们做成私有？** 这是本模块最重要的设计决策：

> **锁的获取与释放被关在这两个函数里，外部代码根本拿不到 `RwLock`，也就不可能忘记解锁、不可能跨函数持有、不可能用错锁。**

`guard` 是局部变量，函数返回时离开作用域 → `Drop` → 自动解锁。**在 Rust 里"忘记解锁"是不可能的**，而 Java 里必须写 `try/finally`。

`FnOnce(&Engine) -> R` 这个签名也很讲究：

- `FnOnce` 而不是 `Fn`：闭包可以**移动**捕获的变量进去（比如把 `Command` 消费掉）；
- `&Engine` / `&mut Engine`：闭包只能干锁允许的事，编译器保证读锁下拿不到 `&mut`。

对比 Java 的写法：

```java
lock.readLock().lock();
try {
    return handler.apply(engine);
} finally {
    lock.readLock().unlock();   // 忘了这行就是灾难
}
```

### 3.2 `apply_cmd` —— 自动选择读锁/写锁

```rust
pub fn apply_cmd(&self, cmd: Command) -> Response {
    if is_read_only(&cmd) {
        self.with_read(|e| apply_read(e, cmd))
    } else {
        self.with_write(|e| apply(e, cmd))
    }
}

fn is_read_only(cmd: &Command) -> bool {
    matches!(cmd, Command::Get { .. } | Command::Exists { .. }
               | Command::Keys { .. } | Command::Ping)
}
```

这是"读多写少场景用 `ReadWriteLock`"的标准套路。三个值得注意的点：

1. **`matches!` 宏**：`matches!(expr, Pattern)` 返回 `bool`，比写 `match` + `=> true/false` 简洁得多。
2. **`Command::Exists` 用的是读锁，但它内部实际上读了值**（模块三坑 1）——读锁下读值是安全的，只是浪费了一次磁盘 I/O。
3. **`Compact` 走写锁**：这意味着一次合并会阻塞**所有**请求，包括读（模块四坑 7）。

### 3.3 `spawn_compactor` —— 后台合并线程

```rust
pub fn spawn_compactor(&self, every: Duration) -> (Arc<AtomicBool>, JoinHandle<()>) {
    let stop = Arc::new(AtomicBool::new(false));
    let stop_clone = Arc::clone(&stop);
    let handle = {
        let this = self.clone();
        thread::spawn(move || {
            while !stop_clone.load(Ordering::Relaxed) {
                thread::sleep(every);
                let ratio = this.with_read(super::engine::Engine::garbage_ratio);
                if ratio > 0.3 {
                    this.with_write(|e| {
                        if let Err(err) = e.compact() {
                            log::error!("合并失败: {err}");
                        }
                    });
                }
            }
        })
    };
    (stop, handle)
}
```

几个 Rust 特有的点：

- **`move` 闭包是必须的**：闭包可能比当前函数活得久，借用局部变量会导致悬垂引用。少了 `move` 编译器会报 `E0373: closure may outlive the current function`。Java 的 lambda 只要求 effectively final，捕获的是**引用**，对象被多线程共享的状态没人管。
- **`this = self.clone()`**：把 `SharedEngine`（内部是 `Arc`）克隆一份**移进**线程。注意这里如果直接 `move ||` 捕获 `self`（`&self`），生命周期又不够——所以先 `clone()` 出一个 `'static` 的所有权。
- **`thread::sleep(every)` 在循环开头**：意味着第一次检查也要等 `every`。如果希望启动时立刻检查一次，把 `sleep` 移到循环末尾。
- **返回 `(stop, handle)`**：调用方 `stop.store(true)` 然后 `handle.join()`——优雅停止。注意 `sleep` 期间不会响应停止信号，最坏要等 `every` 才退出。

**这里有一个 TOCTOU（检查-执行之间时间差）**：

```rust
let ratio = this.with_read(garbage_ratio);   // ① 读锁，读完就放了
if ratio > 0.3 {
    this.with_write(|e| e.compact());        // ② 重新拿写锁
}
```

① 和 ② 之间锁被释放了，别的线程可能又写入、也可能已经合并过了。后果：可能多合并一次（无害，只是浪费 I/O）。但如果判断条件换成"必须精确执行一次"的操作，这就是 bug。

**修复**：把判断也放进写锁里：

```rust
this.with_write(|e| {
    if e.garbage_ratio() > 0.3 {
        if let Err(err) = e.compact() { /* … */ }
    }
});
```

代价：每次轮询都要拿一次写锁（会短暂阻塞读者）。轮询间隔较大时（比如 60 秒）完全可以接受。

### 3.4 阻塞式服务器：每连接一线程

```rust
pub fn bind_blocking(addr: &str, engine: SharedEngine) -> Result<(SocketAddr, JoinHandle<()>)> {
    let listener = TcpListener::bind(addr)?;
    let local = listener.local_addr()?;
    let handle = thread::spawn(move || {
        for stream in listener.incoming() {
            match stream {
                Ok(s) => {
                    let eng = engine.clone();
                    thread::spawn(move || {
                        if let Err(e) = handle_conn(s, &eng) {
                            log::debug!("连接结束: {e}");
                        }
                    });
                }
                Err(e) => log::error!("accept 失败: {e}"),
            }
        }
    });
    Ok((local, handle))
}
```

- `TcpListener::bind("127.0.0.1:0")` 里的 `:0` 让 OS 分配端口，再用 `local_addr()` 取回来——这是**测试里拿端口的标准技巧**。
- 每连接一个 OS 线程的开销：默认栈 2 MB（虚拟内存，按需提交），所以几千连接能扛，但不如异步方案（模块七）。
- `handle_conn` 里 `stream.try_clone()` 把 socket 复制成两个句柄（`dup`），一个读一个写——因为 Rust 要求 `&mut` 才能写，而 `BufReader` 需要独占读端。

## 4. 边界情况清单

| 情况 | 行为 | 评价 |
|------|------|------|
| 多线程写**不同**键 | 全部成功，不丢 | ✅ 写锁保证 |
| 多线程写**同一**键（纯 `SET`） | 最后写入者胜，不会撕裂 | ✅ 单键原子 |
| 多线程「读 → 改 → 写」同一键 | **丢失更新**（实测丢 86.5%） | ❌ 无事务 |
| 合并期间的请求 | 全部阻塞（写锁独占） | ⚠️ 长时间停顿 |
| `KEYS` 一个大前缀 | 持有读锁直到扫描完成，写者被挡住 | ⚠️ 见坑 6 |
| 持锁期间 panic | 锁中毒，后续 `lock()` 返回 `Err` | ⚠️ 本项目选择继续服务 |
| 同一线程重复取写锁 | **死锁**（`RwLock` 不可重入） | ❌ 见坑 3 |
| 两个进程打开同一目录 | 第二个失败（LOCK 文件） | ✅ 模块五 |
| 引擎被 `close()` 后继续使用 | 编译不过（`close(self)` 消费所有权） | ✅ |
| `clone()` 一个 `SharedEngine` | 只加引用计数，指向同一个引擎 | ✅ 注意不是"复制一份数据" |

## 5. 常见坑

### 坑 1：一把大锁 = 吞吐天花板

`apply_cmd` 无论读写都要经过同一把锁。写入路径包含**磁盘 I/O**，所以写锁的持有时间是毫秒级——这意味着 QPS 上限大约是 `1000 / 平均写耗时`。

实测参考：`write_throughput_smoke` 是一个 `#[ignore]` 的性能冒烟测试（断言 `qps > 1000`），
用 `cargo test --release -- --ignored --nocapture` 跑。你可以复制它、改造成多线程版本，
会发现 8 线程的 QPS **并不比单线程高**——写锁把它们串行化了。

**优化方向**（练习 3）：按 key 哈希分片（sharding），每个分片一个独立的 `Engine` + 独立的数据目录。这是 Redis Cluster、RocksDB column family 的思路。

### 坑 2：`spawn_compactor` 的 TOCTOU

见 3.3。判断和操作之间锁被释放了。

### 坑 3：`RwLock` 不可重入，同线程重复加锁 = 死锁

```rust
// ❌ 死锁
engine.with_write(|e| {
    // 假设某个函数内部又对同一个 SharedEngine 取了写锁
    engine.with_write(|e2| { /* … */ });   // 永久阻塞
});
```

`std::sync::RwLock` **不是可重入锁**。Java 的 `synchronized` 是可重入的（同一线程可以再次进入），`ReentrantReadWriteLock` 也是——这个差异会让 Java 开发者意外中招。

**防范**：`with_read` / `with_write` 是**私有**的，外部拿不到锁，从而把重入的可能性限制在模块内部——这是封装带来的安全。如果你要自己加类似的辅助函数，务必保持这个约定。

### 坑 4：以为读锁能提升写吞吐

读锁只让**读**并发。写仍然是完全串行的。如果你的负载是写密集（比如日志采集），`RwLock` 相对 `Mutex` 毫无收益，还多付了原子操作的成本。

### 坑 5：锁中毒被静默吞掉

`unwrap_or_else(PoisonError::into_inner)` 让"上一个线程死在临界区"这件事被完全忽略。见 2.3。

### 坑 6：`KEYS` 持读锁做全索引扫描

```rust
fn keys(&self, prefix: &str) -> Result<Vec<String>> {
    let mut out: Vec<String> = self.index.keys()
        .filter(|k| k.starts_with(prefix)).cloned().collect();
    // …
}
```

`KEYS` 是 O(索引大小) 的，而且**全程持有读锁**。100 万个键的库上执行一次 `KEYS`，写者会被挡住几十毫秒甚至更久。

Redis 的 `KEYS` 是禁用的（生产用 `SCAN`），原因正是如此。本项目没有 `SCAN`，是个已知缺陷。

### 坑 7：跨 `.await` 持有 `std::sync` 的锁

这是模块七的重点，这里先提醒：

```rust
// ❌ 在 async 里
let guard = engine.inner.write().unwrap();
some_io().await;    // 任务挂起，但锁没释放 → 别的任务拿同一把锁 → 死锁
drop(guard);
```

`tokio` 的 worker 线程会被这个挂起的任务占住，最终整个线程池卡死。

### 坑 8：没有 `INCR`，应用层计数必错

`concurrency_demo` 的场景 B 就是这个坑。**不要**在应用层做「读 → 加 → 写」，要嘛加锁，要嘛让引擎提供原子操作。

Redis 之所以把 `INCR`、`HINCRBY`、`LPUSH` 做成单命令，根本原因就是这个——**把原子性的边界放在引擎内部**。

## 6. 性能考量

### 6.1 锁竞争的模型

设：单个写操作的临界区耗时 `t`（含磁盘 I/O），N 个线程。

- 无竞争（N=1）：吞吐 = `1/t`
- 完全串行（锁竞争饱和）：吞吐仍然是 `1/t`，但延迟变成 `N·t/2`（排队）
- 有读有写时：`RwLock` 让读并行，吞吐 = `读吞吐 + 写吞吐`

**关键结论**：加锁不会提升吞吐上限，只会**降低延迟的可预测性**和**增加 CPU 争用**。真正的吞吐提升必须靠**减少临界区**或**分片**。

### 6.2 减少临界区的三个做法

1. **把 I/O 移出临界区**：在锁外读文件，锁内只改索引。难，因为索引与文件位置耦合。
2. **双缓冲 / 影子结构**：写操作先在锁外准备好数据，锁内只做一次指针交换。
3. **分片**：按 `hash(key) % N` 分到 N 个独立引擎，锁冲突降低 N 倍。

### 6.3 分片的具体做法（练习 3 提示）

```rust
pub struct ShardedEngine {
    shards: Vec<SharedEngine>,   // 每个 shard 一个独立的数据目录
}

impl ShardedEngine {
    fn shard_for(&self, key: &str) -> &SharedEngine {
        // 注意：std 的 DefaultHasher 每次进程启动种子不同！
        // 分片必须用**确定性**的哈希（如 FxHash / 自己实现 FNV），否则重启后 key 找不到了。
        let h = stable_hash(key);
        &self.shards[(h % self.shards.len() as u64) as usize]
    }
}
```

**这里有一个极易踩的坑**：`std::collections::hash_map::DefaultHasher` 用了随机种子（SipHash 的 keys 每次进程随机），**跨进程/重启不稳定**。分片哈希必须自己实现（FNV-1a、FxHash、xxhash 都行）。Rust 的随机种子是为了防止 HashDoS 攻击，代价就是你不能拿它做持久化相关的哈希。

### 6.4 内存序的成本

`Arc` 的 `clone()` / `drop()` 是原子操作（约 20~100 个周期，核多时更贵）。在极热的路径上（比如每个请求都 `clone()` 一次 `SharedEngine`），这会有可测量的开销。

优化：把 `SharedEngine` 放在连接上下文里**只 clone 一次**，之后复用。

### 6.5 与 Java 的对照

| 场景 | Java | Rust |
|------|------|------|
| 读多写少 | `ReadWriteLock` + try/finally | `RwLock` + 作用域守卫 |
| 高并发 Map | `ConcurrentHashMap`（分段锁/CAS） | `Arc<RwLock<HashMap>>` 或 `DashMap` |
| 计数 | `AtomicLong` / `LongAdder` | `AtomicU64` / 分片原子 |
| 线程池 | `ExecutorService`（JDK 自带） | 需要自己搭，或用 `rayon` / `tokio` |
| 线程安全证明 | `@ThreadSafe` 注解（约定） | `Send`/`Sync`（编译期） |
| 忘记解锁 | 靠 finally，忘了就死锁 | 不可能忘记 |
| 锁中毒 | 无此概念 | `PoisonError` |

## 7. 动手验证

### 7.1 跑通示例

**务必用 release**（debug 下场景 B 慢且结果更随机）：

```bash
cargo run --release --example concurrency_demo
```

输出（实测，场景 B 的数字每次运行都不同）：

```text
线程数 8，每线程 1000 次操作

=== A. 8 个线程各写 100 个不同的键 ===
写入后键数: 800（期望 800）
✅ 写锁让每次 SET 独占引擎，所以不会丢

=== B. 8 个线程对同一个键做「读 → +1 → 写」===
期望: 8000
实际: 1078
丢失: 6922 次更新（86.5%）
⚠️  每次运行的数字都不一样 —— 这正是竞态的特征
   原因：minidb 没有多命令事务，GET + SET 不是一个原子操作

=== C. 用一把应用层的 Mutex 包住整个读改写 ===
期望: 8000
实际: 8000
✅ 正确了 —— 但也退化成完全串行，吞吐和单线程差不多

=== D. 并发写同一个键，读到的一定是完整的值吗？===
读线程共读了 412 次，其中读到「撕裂 / 混合」的值: 0 次
✅ 单条 SET 是原子的：不会读到一半旧值一半新值
   （写锁独占 + 一次 write_all，读线程要么看到写前、要么看到写后）

全部断言通过 ✅
```

**请把 A、B、D 三个结果放在一起看**，它们共同定义了本项目的并发语义：

- **A**：不同键并发写 → 不丢（写锁保证了"不互相破坏"）
- **D**：同一键并发写 → 不撕裂（单命令是原子的）
- **B**：同一键的读改写 → **丢更新**（跨命令不原子）

只说"线程安全"是不够的，必须说清**哪些操作序列**是安全的。

### 7.2 验证读锁是并发的

```bash
cargo test --lib stage7_concurrent::tests::read_locks_are_shared -- --nocapture
# test stage7_concurrent::tests::read_locks_are_shared ... ok
```

这个测试起 4 个线程各做 100 次 `GET`。如果用 `Mutex`，它们会完全串行；用 `RwLock` 则并行通过。想"看见"这个差异，可以把 `RwLock` 临时换成 `Mutex` 再计时。

### 7.3 验证协议错误不会杀掉连接

```bash
cargo test --lib stage7_concurrent::tests::protocol_error_does_not_kill_connection
# test stage7_concurrent::tests::protocol_error_does_not_kill_connection ... ok
```

对比 Java：如果 handler 里抛出未捕获异常，线程直接死掉（或交给 `UncaughtExceptionHandler`），连接就断了。Rust 里 `Result` 强制你在**出问题的地方**就地处理。

### 7.4 亲手触发一次编译错误

取消 `src/stage7_concurrent.rs` 里反例 1 的注释，然后：

## 8. 练习

1. **（事务）实现 `INCR` 命令**：在引擎内部完成「读 → 解析 → 加 1 → 写」，走写锁。加一个测试：8 线程各 `INCR` 1000 次，最终值必须正好 8000，且不需要应用层加锁。
2. **（事务）实现乐观并发控制**：给 `Location` 加一个 `version` 字段，新增 `CAS key expected_version new_value` 命令，版本不匹配时返回 `Response::Error`。这是 etcd / ZooKeeper 的核心机制。
3. **（性能）实现分片引擎**（6.3）：8 个分片，用**确定性**哈希（自己实现 FNV-1a，不要用 `DefaultHasher`）。对比分片前后 8 线程写入的吞吐。
4. **（正确性）修复坑 2 的 TOCTOU**：把 `spawn_compactor` 里的判断移进写锁。
5. **（正确性）实现 `SCAN`**（坑 6）：分页返回键，每页持锁一次，避免长时间占住读锁。
6. **（健壮性）处理锁中毒**（坑 5）：把 `unwrap_or_else(PoisonError::into_inner)` 换成一个显式的策略枚举（`Ignore` / `Panic` / `Recover`），并写一个测试证明"持锁 panic 之后行为符合策略"。
7. **（思考）** Actor 方案（模块七）也能解决场景 B 的丢失更新吗？它和"加锁"的差异在哪？（提示：Actor 只能串行化**单条命令**，不能串行化"两条命令的序列"。）
