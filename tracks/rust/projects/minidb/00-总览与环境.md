# minidb 模块精讲 · 总览与环境

> **这一系列按模块组织，不按语言特性组织。**
> 每一篇回答四个问题：**这个模块要解决什么问题 → 有哪些备选方案和为什么选了这个 → 代码里具体怎么走 → 边界、坑和性能账怎么算。**
> 目标是让你照着能把每个模块自己实现一遍，而不是读完知道"大概是这样"。

---

## 0. 这一系列怎么读

### 0.1 模块地图

一个 Bitcask 引擎可以切成七块，每块有清晰的问题边界（另有 00 总览、08 实验手册两篇辅助）：

```
                    ┌──────────────────────────────────────┐
   客户端请求 ─────▶│  模块七  协议层与服务器                │  07
                    │  Command/Response ↔ 文本行；接入        │
                    └──────────────┬───────────────────────┘
                                   │ Command
                    ┌──────────────▼───────────────────────┐
                    │  模块六  并发与"事务"边界              │  06
                    │  谁可以并发、谁必须串行、原子性到哪一层 │
                    └──────────────┬───────────────────────┘
                                   │ &Engine / &mut Engine
   ┌───────────────────────────────▼───────────────────────────────┐
   │  模块一  实例与启动（Engine::open 全流程）                      │  01
   ├───────────────────────────────────────────────────────────────┤
   │  模块三  索引与查询  │  模块四  删除与合并  │  模块五  崩溃恢复  │ 03/04/05
   │  HashMap<String,    │  墓碑、垃圾记账、    │  重放、截断、     │
   │  Location>          │  段滚动、compaction │  manifest 推断    │
   ├───────────────────────────────────────────────────────────────┤
   │  模块二  文件格式与落盘（帧格式、CRC、fsync 策略）              │  02
   └───────────────────────────────────────────────────────────────┘
                                   │
                              磁盘上的 .log / manifest.json / LOCK
```

依赖方向很干净：**上层只依赖下层的公开函数，下层完全不知道上层的存在**。模块二（帧格式）是最底下的地基，模块一（启动）是第一个把所有东西串起来的流程。

### 0.2 建议的阅读 / 实现顺序

如果你想**自己实现一遍**，按这个顺序来。每一步都能独立验证，不会写到一半卡死：

| 顺序 | 做什么 | 对应篇 | 完成后能验证什么 |
|------|--------|--------|------------------|
| 1 | 写帧编解码 + CRC，能用 `xxd` 看懂自己写出的字节 | 02 | `frame_roundtrip` 测试 |
| 2 | 起一个单文件 append-only 日志 + 内存索引，做到重启后数据还在 | 01 / 03 | 关掉进程再打开，`GET` 还有值 |
| 3 | 加墓碑删除 + 重放时截断坏尾巴 | 04 / 05 | 手动往文件尾部塞半个帧，重开后好数据不丢 |
| 4 | 加段滚动 + manifest + 合并 | 04 | 反复覆盖同一个键，看磁盘占用下降 |
| 5 | 加目录锁 + 统计 + 配置 | 01 | 第二个进程打不开同一目录 |
| 6 | 加并发（锁或 Actor）+ 服务器 | 06 / 07 | 多线程写 N 条，一条不丢 |

配套的单文件参考实现是 `examples/mini_kv.rs`（约 200 行、只依赖标准库，与本文同一目录）。**建议先读它再读模块篇**——它把上面第 1~3 步压缩到一个文件里，读完你对主干就有直觉了。

```bash
cargo run --example mini_kv
```

### 0.3 每篇的固定结构

| 小节 | 回答什么 |
|------|----------|
| **问题与权衡** | 为什么需要这个模块；有哪些备选方案，各自代价是什么，为什么最后选了这个 |

## 1. 项目定位与代码索引

### 1.1 这是什么，不是什么

一个 **Bitcask 风格的嵌入式 KV 存储引擎**。核心思想一句话：

> **磁盘上只做 append-only 日志追加；内存里只有一个「键 → 记录位置」的哈希索引。**

**是**：

- `SET / GET / DEL / EXISTS / KEYS <prefix> / PING / COMPACT`
- append-only WAL + 崩溃恢复（半包截断、CRC32 校验）
- 多段滚动 + 段合并
- 目录锁、manifest 原子更新、统计指标
- 多线程并发安全；同步线程版 + tokio 异步版两种 TCP 服务器

**不是**（每一条都是另一个 300+ 行的主题）：

- 事务与 MVCC、SQL 解析层 → 见第 06 篇的"为什么没有事务"
- LSM-Tree / B+Tree（哈希索引不支持范围查询）
- 主从复制、分片、TTL、压缩

### 1.2 源码地图

| 文件 | 行数 | 承载的模块 |
|------|------|-----------|
| `src/error.rs` | ~135 | 贯穿全部：错误类型 `KvError` 与 `Result<T>` 别名 |
| `src/engine.rs` | ~290 | 模块一（对外 API）、模块六（`apply`/`apply_read` 读写分家） |
| `src/stage6_compact.rs` | ~580 | 模块一（open/roll）、模块三（index/get）、模块四（compact）、模块五（replay） |
| `src/stage5_wal.rs` | ~610 | 模块二（帧格式、CRC、位置读取）、模块三（单段版索引） |
| `src/stage7_concurrent.rs` | ~340 | 模块六（`SharedEngine`、后台合并、阻塞服务器） |
| `src/stage8_async.rs` | ~280 | 模块六（Actor）、模块七（tokio 服务器） |
| `src/stage3_protocol.rs` | ~320 | 模块七（命令与响应的编解码） |
| `src/stage4_traits.rs` | ~350 | 抽象层 `trait KvStore`（模块三/四的接口契约） |
| `src/stage2_inmem.rs` | ~235 | 内存版实现（理解所有权/借用的最小样本） |
| `src/bin/minidb-cli.rs` | ~90 | CLI 入口 |
| `src/bin/minidb-server.rs` | ~57 | 异步服务器入口 |

### 1.3 全局 Java → Rust 对照

后面每一篇都会用到这张表，先放在这里当索引：

| 关注点 | Java / JVM | Rust / Cargo |
|--------|-----------|--------------|
| 构建文件 | `pom.xml` | `Cargo.toml` |
| 依赖锁定 | 一般不锁 | `Cargo.lock`（二进制项目必须提交） |
| 模块 | 目录即包 | 目录 ≠ 模块，`mod` 必须显式声明 |
| 可见性 | 默认 package-private | 默认私有，显式 `pub` |
| 错误处理 | 异常、`throws`、`getCause` | `Result<T,E>`、`?`、`source()` |
| 空值 | `null` / `Optional<T>` | `Option<T>`（enum，零额外开销） |
| 抽象 | `interface`，永远动态分发 | `trait`，默认静态分发 |
| 泛型 | 类型擦除，不能是 primitive | 单态化，可以是 `u64` |
| 资源管理 | `try-with-resources` / `finally` | `Drop`（RAII） |
| 并发容器 | `ConcurrentHashMap` | `Arc<RwLock<HashMap>>` |
| 线程安全 | `@ThreadSafe`（约定） | `Send` / `Sync`（编译期证明） |
| 异步 | JDK 自带线程池、虚拟线程 | 标准库**没有**运行时，需选 tokio |
| 序列化 | Jackson（反射） | serde（编译期生成） |
| 测试 | JUnit + Mockito | `#[test]` + `#[cfg(test)]` |
| 基准 | JMH | `criterion` / `#[ignore]` 冒烟测试 |

## 2. 环境搭建

### 2.1 安装 rustup

```bash
# macOS / Linux
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"

# Windows
winget install Rustlang.Rustup
```

> **Windows 必看**：Rust 默认用 MSVC 工具链，需要 **Microsoft C++ 生成工具**（约 4 GB）。
> 没装的话报错是 `linker 'link.exe' not found`，装完要**重开终端**。

验证：

```bash
$ rustc --version && cargo --version
rustc 1.98.1 (48a229cea 2026-09-01)
cargo 1.98.1 (797e8a9bc 2026-08-05)
```

本项目 MSRV 是 **1.75**，不低于它就能编译。

### 2.2 编辑器

VS Code + `rust-lang.rust-analyzer`。推荐配置：

```jsonc
{
  "editor.formatOnSave": true,
  "[rust]": { "editor.defaultFormatter": "rust-lang.rust-analyzer" },
  "rust-analyzer.check.command": "clippy",          // 写代码时就看到 lint
  "rust-analyzer.inlayHints.typeHints.enable": true // 显示推导出的类型
}
```

> **学 Rust 早期一定打开 inlay hints**：你会看到编译器推导出的每一个类型，这是理解生命周期和泛型最快的路径。

### 2.3 依赖逐个说明

```toml
[dependencies]
serde      = { version = "1", features = ["derive"] }
serde_json = "1"
thiserror  = "2"
clap       = { version = "4", features = ["derive"] }
tokio      = { version = "1", features = ["rt-multi-thread", "net", "io-util", "sync", "macros", "time", "signal"] }
log        = "0.4"
env_logger = "0.11"

[dev-dependencies]
tempfile = "3"
```

| 依赖 | 为什么需要 | Java 对照 | 备注 |
|------|-----------|-----------|------|
| `serde` + `serde_json` | manifest 读写、WAL 的调试 dump | Jackson / Gson | derive 宏**编译期生成代码**，无反射 |
| `thiserror` | 错误类型派生 `Display` + `source()` | 手写异常继承树 | 只在**库**用；应用层用 `anyhow` |
| `clap` | CLI 参数解析 | picocli | 零反射；会增加编译时间 |
| `tokio` | 异步运行时 | `ExecutorService` | **Rust 标准库不带运行时**；只开需要的 features |
| `log` + `env_logger` | 日志门面 + 实现 | SLF4J + logback | 库只依赖 `log`，二进制才 `env_logger::init()` |
| `tempfile` | 测试用临时目录 | `@TempDir` | 只在 `[dev-dependencies]` |

### 2.4 Cargo.toml 里值得注意的三段

**`[[bin]]` —— 一个 crate 多个可执行文件**

```toml
[[bin]]
name = "minidb-cli"
path = "src/bin/minidb-cli.rs"
```

≈ `exec-maven-plugin` 的 `mainClass`。Cargo 约定 `src/bin/*.rs` 自动成为可执行文件，显式声明只是为了取名（`minidb-cli` 而不是 `minidb_cli`）。

**`[profile.release]`**

```toml
[profile.release]
lto = true
codegen-units = 1
panic = "abort"
```

Maven 里没有对应物（JVM 靠 JIT）。代价是 **release 构建很慢**，日常开发别用。

**`[lints]` —— 质量门禁前置到编译期**

```toml
[lints.rust]
unsafe_code  = "forbid"   # 全 crate 禁用 unsafe
missing_docs = "warn"

[lints.clippy]
pedantic         = { level = "warn", priority = -1 }
clone_on_ref_ptr = "warn"  # 禁止把 clone() 当创可贴
ptr_arg          = "warn"  # 提醒用 &str 而不是 &String
```

≈ SpotBugs / Checkstyle 的 `failOnViolation`，但写进了构建文件而不是 CI 脚本。

> 自己起项目时**先别开 `pedantic`**，它会一次报几百条。先跑默认 `cargo clippy`，习惯了再加。

## 3. 贯穿全部：错误类型

先认识 `src/error.rs`，后面每篇都会用到它。

```rust
pub type Result<T> = std::result::Result<T, KvError>;

#[derive(Debug, Error)]
pub enum KvError {
    #[error("I/O 失败: {0}")]
    Io(#[from] io::Error),

    #[error("键不存在: {key}")]
    KeyNotFound { key: String },

    #[error("协议错误: {0}")]
    Protocol(String),

    #[error("数据文件损坏: {reason}（已截断到 offset {truncated_at}）")]
    Corrupted { reason: String, truncated_at: u64 },

    #[error("存储已关闭")]
    Closed,

    #[error("序列化失败: {0}")]
    Serialization(#[from] serde_json::Error),
}
```

**三个设计点：**

1. **用 enum 而不是 trait + 实现类** —— 调用方可以**穷尽匹配**，编译器会检查。Java 里只能 `catch (Exception e)` 一把梭。
2. **变体携带结构化数据** —— `KeyNotFound { key }` 而不是把信息拼进 message。错误是给程序处理的，不是给日志 grep 的。
3. **`#[from]` 让 `?` 能自动转换** —— `File::open(...)?` 一行搞定 `io::Error → KvError`，等价于 Java 的 `catch (IOException e) { throw new KvException(e); }`，而且是编译期生成的。同时 `thiserror` 会把被包装的错误接进 `source()` 链（≈ `getCause`）。

> **分界线**：库定 enum，应用层（bin）用 `anyhow`。这样调用方能穷尽匹配，应用层又不用为每种错误写一个变体。
