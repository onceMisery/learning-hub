## 2. 实验 ①：从零实现最小 Bitcask

```bash
cargo run --example mini_kv
```

`examples/mini_kv.rs` 是一个**约 200 行、只依赖标准库**的单文件 Bitcask，包含：

- append-only 日志 + 内存哈希索引
- 重启重放
- CRC32 校验
- 墓碑删除
- 一个自验证的 demo

它也**不需要 Cargo**——可以直接 `rustc examples/mini_kv.rs -o mini_kv && ./mini_kv`。

### 为什么值得先做这个

模块一到七讲的是"minidb 这个项目怎么实现的"，而 mini_kv 讲的是"Bitcask 这个**思想**最小可以长什么样"。看完它你会发现，模块二到四的所有复杂度（分段、manifest、目录锁、垃圾记账）都是**工程优化**，核心思想只有三行：

```text
写：append 到文件末尾，索引记下 (offset, len)
读：按索引里的 offset 去文件里读
重启：从头扫一遍文件，重建索引
```

### 实验任务

1. 读一遍 `mini_kv.rs`，不看 minidb 的源码，自己默写一遍。
2. 给它加一个功能：**段滚动**（写满 N 字节就换文件）。
3. 对比你写的和 `stage6_compact.rs` 的差异，看看自己漏了哪些边界情况。

### 真实踩过的两个坑（都写在文件注释里）

- **Windows 上 append 模式句柄没有 `FILE_WRITE_DATA`**，`set_len` 报 `PermissionDenied (os error 5)`。解决：用 `read + write` 打开，写入前 `seek(SeekFrom::End(0))`。
- **读帧时遇到 `val_len == u32::MAX`（墓碑）不能直接 `vec![0; val_len]`**——那会试图分配 4 GiB。必须先判断哨兵值。

## 3. 实验 ②：帧格式与 CRC

```bash
cargo run --example frame_format
```

输出（已实测）：

```text
=== 1. 编码一条记录 ===
key = "name", value = "minidb"
帧长度 = 26 字节
  00000000  4d 44 42 31 04 00 00 00 06 00 00 00 6e 61 6d 65  |MDB1........name|
  00000010  6d 69 6e 69 64 62 3d 2d 01 90                    |minidb=-..|
逐字段：
  magic   = [4d, 44, 42, 31]  ("MDB1")
  key_len = [04, 00, 00, 00]  (= 4)
  val_len = [06, 00, 00, 00]  (= 6)
  key     = [6e, 61, 6d, 65]  ("name")
  value   = [6d, 69, 6e, 69, 64, 62]  ("minidb")
  crc32   = [3d, 2d, 01, 90]
解码回来：key=name, value=Some("minidb"), consumed=26

=== 2. 墓碑（删除标记）===
val_len = [ff, ff, ff, ff]  (= u32::MAX = 墓碑)
帧长度 = 20 字节（比上面少 6 字节的 value）
  00000000  4d 44 42 31 04 00 00 00 ff ff ff ff 6e 61 6d 65  |MDB1........name|
  00000010  ed 5c 8c 17                                      |.\..|

=== 3. 篡改 value 的一个字节 ===
原字节 6d → 现字节 92
  ✅ 被检出：校验和不匹配

=== 4. 模拟断电，砍掉尾部 3 个字节 ===
  ✅ 被检出：长度不足，需要 24 字节 @ offset 22，实际只有 23 字节

=== 5. 空 value ≠ 墓碑 ===
空 value：val_len = [00, 00, 00, 00]  (= 0)
墓碑    ：val_len = [ff, ff, ff, ff]  (= u32::MAX)

全部断言通过 ✅
```

**请重点核对第 5 项**：空字符串（`SET k ""`）和"已删除"（`DEL k`）是**两个不同的语义**，用 `val_len = 0` 和 `val_len = u32::MAX` 区分。这是哨兵值设计的关键——如果你用 `0` 表示删除，就没法存空值了。

**用真实数据文件验证**：

```bash
cargo run --bin minidb-cli -- --dir /tmp/f --exec "SET name minidb"
xxd /tmp/f/000000001.log
# 00000000: 4d44 4231 0400 0000 0600 0000 6e61 6d65  MDB1........name
# 00000010: 6d69 6e69 6462 3d2d 0190                minidb=-..
```

磁盘上的字节和示例程序输出**完全一致**——这就是"格式即契约"的意思。

## 4. 实验 ③：垃圾与合并

```bash
cargo run --example gc_demo
```

完整输出见模块四 7.1。核心数字：

```text
2000 次写入  → 59800 字节，垃圾占比 99.0%
删除 5 个键  → 59910 字节（+110，墓碑也要占空间）
执行合并     → 450 字节，回收 59460 字节（99.2%）
```

### 实验任务

1. 把 `HOT_KEYS` 改成 1、`ROUNDS` 改成 10000，看垃圾占比怎么变。
2. 在合并**之前**手动改一个字节，看合并会不会报错。（提示：`read_at` 会返回 `Corrupted`。）
3. 把 `SEGMENT_MAX_BYTES` 改成 1 KiB，观察多次段滚动后目录里有多少个段文件。

## 5. 实验 ④：崩溃恢复

```bash
cargo run --example recovery_demo
```

完整输出见模块五 7.1。五个场景：

| 场景 | 破坏 | 结果 |
|------|------|------|
| A | 尾部半帧 | 5 条记录全在，131 → 125 字节 |
| B | 中间改 1 字节 | 只剩 2 条，125 → 50 字节 |
| C | 删 manifest | 靠扫描目录恢复，5 条全在 |
| D | 残留 LOCK | 拒绝打开 |
| E | 写入后不关闭 | 数据在内核，进程崩溃不丢；断电会丢 |

### 实验任务

1. **复现坑 1（模块五）**：手工构造"rename 已完成、旧段已删除、manifest 未更新"的目录状态，然后 `open()`，观察数据是不是真的全没了。然后实现修复（`save_manifest` 前移到删旧段之前），再验证一次。
2. 把场景 B 的受害记录改成**最后一条**（下标 4），看恢复结果有什么不同。（答案：只丢最后一条，前 4 条保住——因为截断发生在坏帧起点。）
3. 给场景 A 加一个变体：追加**完整的** 6 字节 + 一个合法帧，看会不会被当成有效数据。（答案：会，因为它是一个完整的合法帧 —— 这说明"崩溃后残留的合法数据会被接受"。）

## 6. 实验 ⑤：并发与丢失更新

```bash
cargo run --release --example concurrency_demo
```

完整输出见模块六 7.1。核心对比：

| 场景 | 结果 |
|------|------|
| A 并发写不同键 | 800/800 ✅ |
| B 并发读改写同一键 | **1078/8000**（丢 86.5%）❌ |
| C 加应用层锁 | 8000/8000 ✅ |
| D 并发写同一键 | 0 次撕裂 ✅ |

### 实验任务

1. 把 `THREADS` 从 8 改成 2，看 B 的丢失率怎么变。（答案：降低，但**不会变成 0**——只要有两个线程就可能交错。）
2. 把 B 的循环改成 `for _ in 0..100`，重复跑 10 次，看结果是否稳定。（答案：不稳定——这正是竞态的特征，也是"偶发 bug 最难查"的原因。）
3. **实现 `INCR` 命令**（模块六练习 1），然后去掉应用层锁重跑 B，验证结果变成 8000。

## 8. 实验 ⑦：压测

### 8.1 内置的性能冒烟测试

```bash
cargo test --release -- --ignored --nocapture
# 写入 20000 条耗时 ...，约 ... ops/s
```

它断言 `qps > 1000`。这个测试的价值不在于数字，而在于**它提醒你必须用 `--release`**——debug 构建 Rust 可能慢 10~50 倍。

### 8.2 用 `hyperfine` 做端到端对比

```bash
# 安装：cargo install hyperfine
hyperfine --warmup 3 \
  "target/release/minidb-cli --dir /tmp/b1 --exec 'SET a 1'" \
  "target/release/minidb-cli --dir /tmp/b2 --exec 'GET a'"
```

注意每次 `--exec` 都要重新 `open()` 并重放整个库，所以测得的主要是**启动开销**。要测纯写入吞吐得用长连接压测（自己写个客户端，或者用 `redis-benchmark` 的简化版）。

### 8.3 用 `criterion` 做微基准

```toml
[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }
```

```rust
// benches/engine_bench.rs
fn bench_set(c: &mut Criterion) {
    let dir = tempfile::tempdir().unwrap();
    let mut e = Engine::open(dir.path()).unwrap();
    c.bench_function("set", |b| {
        b.iter(|| e.set("k", b"v".to_vec()).unwrap());
    });
}
criterion_group!(benches, bench_set);
criterion_main!(benches);
```

`criterion` ≈ JMH：自动做预热、统计、回归检测，还能生成 HTML 报告。

### 8.4 观测工具

| 想看什么 | Linux | Windows |
|---------|-------|---------|
| 进程做了哪些系统调用 | `strace -c -e trace=write,fsync,pread64` | Process Monitor（看 `WriteFile` / `FlushFileBuffers`） |
| I/O 量 | `pidstat -d 1`、`iostat -x 1` | 资源监视器 |
| 火焰图 | `perf record` + `cargo flamegraph` | Windows Performance Analyzer |
| 分配次数 | `valgrind --tool=callgrind` | — |

**最有用的一招**：`strace -c` 统计系统调用次数。如果你看到每次 `GET` 有 4 次 `pread64`，就知道该做模块三 6.2 讲的"减少系统调用"优化了。

## 9. 一次请求的完整旅程（全篇串联）

以 `GET user:42` 为例，从网络到磁盘再回到网络：

```text
① TCP 字节流
   ↓ BufReader 按 \r\n 分帧（模块七 3.4）
② "GET user:42" 文本
   ↓ tokenize → 零拷贝切片 → Command::parse（模块七 3.1）
③ Command::Get { key: "user:42" }
   ↓ is_read_only → true → 走读锁（模块六 3.2）
④ RwLock 读守卫
   ↓ apply_read → Engine::get（模块三 3.2）
⑤ 索引查找 index.get("user:42") → Location { seg: 3, offset: 8192, len: 40 }
   ↓ 命中？没命中就直接返回 None
⑥ 段句柄表 frozen.get(&3) → &File
   ↓ read_frame_at(file, 8192)（模块二 3.3）
⑦ 位置读取：pread(8192, 40) → 40 字节
   ↓ 校验魔数、算 CRC32、比对（模块二 3.2）
⑧ Frame { key: "user:42", value: Some(...), consumed: 40 }
   ↓ Response::from_result → Response::Value(Some(v))
⑨ 编码成 "$8\r\n......\r\n"（模块七 3.3）
   ↓ writer.write_all + flush
⑩ TCP 字节流回到客户端
```

每一步对应一个模块。**当你能不看源码把这十步说出来，这套东西就是你的了。**

## 10. 从教学项目到生产引擎，还差什么

按"必须 / 应该 / 可选"三档列出。这不是 TODO 清单，而是**理解差距的地图**。

### 10.1 必须（否则不能用于任何真实场景）

| 缺口 | 为什么 | 怎么补 |
|------|--------|--------|
| **崩溃安全** | 模块五坑 1：`compact()` 在删旧段后才写 manifest，崩溃会**静默丢全部数据** | `save_manifest` 前移到删除之前 |
| **多进程锁** | `create_new` 的 LOCK 在 `kill -9` 后残留，必须人工删 | 用 `flock`（`fs2` crate），内核自动释放 |
| **二进制安全** | 模块七坑 2：`from_utf8_lossy` 会破坏非 UTF-8 的 value | `encode` 改成写 `Vec<u8>` |
| **请求大小上限** | 模块七坑 3：一个无换行的超大请求能 OOM | 限制行长度、参数个数、连接数 |
| **fsync 策略** | 断电会丢最后几秒写入 | 提供 `SyncPolicy` 配置 + 组提交 |

### 10.2 应该（否则规模一大就出问题）

| 缺口 | 为什么 | 怎么补 |
|------|--------|--------|
| **hint 文件** | 启动时间 O(数据量)，100 GB 的库要几分钟 | 合并时顺带写 `key → (seg, offset, len)` |
| **增量合并** | 全量合并的停顿随数据量线性增长 | 按垃圾占比选段、分代合并 |
| **合并移到后台** | `Engine::set` 的内联检查让普通写入突然卡几秒（模块四 1.5） | 只打标记，由后台线程执行 |
| **孤儿文件清理** | `*.compacting`、删除失败的段会一直占磁盘 | `open()` 时清理 + `pending_delete` 列表 |
| **记账准确性** | 多段场景下 `live_bytes` 高估，导致合并触发过晚（模块四坑 2） | 改成全局结算 |
| **`SCAN` 替代 `KEYS`** | `KEYS` 持读锁做全索引扫描（模块六坑 6） | 分页返回 |
| **背压** | 无界 channel 会让队列无限增长（模块七坑 8） | 有界 channel + `-ERR busy` |

### 10.3 可选（让它变成"真正的数据库"）

| 方向 | 说明 |
|------|------|
| **压缩** | value 用 zstd/lz4 压缩，省 50%+ 空间和 I/O。注意要能按记录单独解压 |
| **事务** | `MULTI`/`EXEC` 批处理，或 MVCC 快照读（模块六 1.6） |
| **原子操作** | `INCR`、`APPEND`、`CAS`（带版本号）——把原子性边界放进引擎 |
| **过期（TTL）** | 索引里存过期时间，读时判断，合并时清理 |
| **复制** | 主节点把 WAL 流式发给从节点——Bitcask 的 append-only 让这件事异常简单 |
| **备份** | 因为段是**不可变**的，硬链接 + 快照即可（Bitcask 的经典优势） |
| **Bloom filter** | 避免"查不存在的键"也要读一次磁盘 |
| **分片** | 按 key 哈希分到多个引擎（模块六 6.3），注意要用**确定性**哈希 |
| **监控** | QPS、P99 延迟、垃圾占比、合并次数/耗时、截断事件 |

### 10.4 这些"差距"里最有价值的一条

**不可变的段文件**。因为段一旦冻结就不再修改，所以：

- 备份 = 硬链接当前所有段 + 之后新增的段（无需停机）；
- 复制 = 把新段文件发出去（无需解析）；
- 校验 = 后台慢慢扫，不影响前台；
- 并发读 = 天然安全（没人改它）。

这是 LSM 系相对 B-tree 系的核心优势之一，也是理解 RocksDB、Cassandra、ClickHouse 诸多设计的钥匙。

## 11. 常见错误速查

| 症状 | 可能的原因 | 去哪看 |
|------|-----------|--------|
| `数据目录已被占用` | 上次异常退出，LOCK 残留 | 模块五 3.4 / 场景 D |
| `数据文件损坏: ...（已截断到 offset N）` | 上次崩溃留下半帧，或介质位翻转 | 模块五 3.3 |
| `找不到段 N` | 索引指向的段没登记进 `frozen` | 模块四 3.4 ⑦ |
| `PermissionDenied (os error 5)` | Windows 上 `set_len` 用了只读句柄 | 模块二坑 3 |
| 写入很慢 | 触发了内联全量合并 | 模块四 1.5 |
| `GET` 返回 `$-1` 但键明明写过 | 被删了；或合并后被截断了 | 模块四 1.4 / 模块五场景 B |
| 多线程计数不对 | 读改写不是原子的 | 模块六场景 B |
| 服务卡住不动 | async 里阻塞了 worker；或跨 `.await` 持 `std` 锁 | 模块七坑 4 |
| 编译报 `cannot be sent between threads safely` | 用了 `Rc` 而不是 `Arc`；或类型不 `Send` | 模块六 2.2 |
| 编译报 `closure may outlive the current function` | 闭包忘了 `move` | 模块六 3.3 |

## 13. 最后的话

这套文档从"文件里第几个字节是什么"讲到"十万连接怎么扛"，看起来很多，但核心其实只有三个思想：

1. **只追加（append-only）** → 顺序写 + 崩溃只需截断尾部；
2. **索引在内存，数据在磁盘** → 一次读就能拿到值，代价是内存要装得下所有 key；
3. **合并（compaction）偿还垃圾** → 用写放大换空间放大。

剩下的（CRC、manifest、目录锁、读写锁、Actor、长度前缀协议）都是围绕这三条的**工程细节**——重要，但不要被它们淹没。

如果你要继续往下走，建议的顺序是：

1. 先修模块五坑 1（崩溃安全），这是唯一会**静默丢数据**的问题；
2. 实现 hint 文件（启动时间）；
3. 把合并移到后台（延迟尖峰）；
4. 实现 `INCR` 和 `CAS`（原子性边界）；
5. 然后才考虑压缩、复制、事务这些"更像数据库"的东西。
