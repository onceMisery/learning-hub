# 模块二：数据文件格式与落盘策略

> **这一篇回答**：一条 `SET k v` 最终在磁盘上长什么样？为什么不用 JSON？为什么校验和放在尾部？什么时候数据才算"真的存住了"？

---

## 1. 要解决的问题与设计权衡

### 1.1 磁盘格式要满足的四件事

| 要求 | 为什么 |
|------|--------|
| **能快速判断边界** | 文件是一串无分隔的字节，读的时候必须知道"下一条记录从哪开始" |
| **能检测损坏** | 断电会写出半截记录；磁盘也会位翻转。必须能发现，而不是把垃圾当数据 |
| **能表达"删除"** | append-only 日志不能回头改，删除只能追加一条特殊记录 |
| **能安全地读不可信数据** | 磁盘上的字节可能是坏的。解析时的每一次分配都要有上限 |

### 1.2 权衡一：文本格式 vs 二进制帧

先排除一个看似诱人的方案：**JSON Lines**（每行一条 JSON）。

```jsonl
{"op":"set","key":"name","value":"minidb"}
```

| | JSON Lines | 二进制帧（本项目） |
|---|-----------|------------------|
| 100 字节的值占用 | 300+ 字节（数字要写成文本，二进制要转义） | 约 116 字节（12 头 + key + value + 4 尾） |
| 解析成本 | 每次要解析数字、处理转义、建 DOM | 几次 `from_le_bytes` |
| 二进制安全 | 要 base64/转义，值再膨胀 33% | 原生支持任意字节 |
| 人类可读 | ✅ `cat` 就能看 | ❌ 需要工具 |
| 调试 | 直接 | 需要 dump 工具 |

**选二进制，但保留了一条调试后路**：`WalEngine::dump()` 用 serde_json 把二进制 WAL 转成可读 JSON。

> **这是 Rust 项目里 serde 最常见的定位：热路径手写二进制，调试路径用 serde。**
> ≈ Java 里只在 DEBUG 日志里开 Jackson。

### 1.3 权衡二：定长头 + 变长体

```
┌──────────┬───────────┬───────────┬──────┬───────┬─────────┐
│ magic 4B │ key_len 4B│ val_len 4B│ key  │ value │ crc32 4B│
└──────────┴───────────┴───────────┴──────┴───────┴─────────┘
 定长 12B 头                                        定长 4B 尾
```

**为什么头要定长？** 因为读的时候你不知道这条记录有多长——必须先读一个固定大小的头部，才能知道后面要读多少。定长头让"找到下一条记录"变成一次 `offset + HEADER_LEN` 的加法。

**为什么尾也要定长？** 校验和放尾部才能覆盖前面的所有字段（包括变长的 key 和 value）。放头部就得先知道 body 长度才能算，鸡生蛋问题。

### 1.4 权衡三：删除怎么表示

两个方案：

| 方案 | 做法 | 权衡 |
|------|------|------|
| **`Option<u32>`** | 帧里加 1 字节 tag，表示 `Some(len)` 还是 `None` | 语义清晰，但定长帧里多占 1 字节；而且 Rust 的 `Option<u32>` 在内存里是 8 字节（对齐），序列化时要手动处理 |
| **哨兵值 `u32::MAX`**（本项目） | `val_len == u32::MAX` 表示墓碑 | 零额外开销，代价是"合法的 value 长度不能是 `u32::MAX`" |

```rust
const TOMBSTONE: u32 = u32::MAX;
```

选哨兵的理由：**单条记录最大 64 MiB（`MAX_RECORD`）**，离 `u32::MAX`（4 GiB）差了 64 倍，永远不会撞。用 1 字节 tag 换一个永远不会发生的限制，不划算。

> 注意这个哨兵**同时也参与了长度计算**：墓碑帧的 `consumed` 只算 `HEADER_LEN + key_len + FOOTER_LEN`，value 部分为 0。

### 1.5 权衡四：落盘策略（durability 三档）

这是最容易出生产事故的地方。写完 `write_all` 之后，数据其实只到了 **OS page cache**：

| 档位 | 做法 | 进程崩溃 | 机器断电 | 单次成本 |
|------|------|---------|---------|---------|
| **1. 不 sync** | 只 `write_all` | 不丢 | **丢** | ~0 |
| **2. `sync_data()`** | 刷数据不刷元数据 | 不丢 | 基本不丢（文件长度可能不准） | 中 |
| **3. `sync_all()`** | `fsync`，连 inode 元数据一起落盘 | 不丢 | 不丢 | 约 0.1~1 ms |

```rust
pub fn sync(&mut self) -> Result<()> {
    self.writer.sync_all()?;   // ≈ FileChannel.force(true)
    Ok(())
}
```

本项目的策略：

- **写路径**：只 `write_all`（档位 1），把持久性交给 OS
- **关闭时**：`close(self)` 和 `Drop` 都走 `sync_all()`（档位 3）

> **生产引擎通常反过来**：默认档位 1（每次 fsync 会让写吞吐下降 1~2 个数量级），提供显式的 `sync` 命令让调用方按需升级。本项目在关闭时 fsync 是为了教学上的"确定性"——你跑完 `cargo run` 关掉终端，数据一定在盘上。

## 2. 关键数据结构与常量

### 2.1 常量

```rust
// src/stage5_wal.rs
const MAGIC: [u8; 4] = *b"MDB1";      // 魔数，≈ class 文件的 0xCAFEBABE
const HEADER_LEN: usize = 12;          // magic(4) + key_len(4) + val_len(4)
const FOOTER_LEN: usize = 4;           // crc32
const MAX_RECORD: usize = 64 << 20;    // 64 MiB，防御性上限
const TOMBSTONE: u32 = u32::MAX;       // 墓碑哨兵
```

`MAX_RECORD` 单独拿出来当常量，而不是写在函数体里——因为**它是解析不可信数据时的唯一闸门**（见 4.4）。

### 2.2 帧布局逐字段

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 4 | `magic` | `[u8;4]` = `b"MDB1"` | 快速判断"这里是不是一条合法记录" |
| 4 | 4 | `key_len` | `u32` **小端** | key 的字节数 |
| 8 | 4 | `val_len` | `u32` **小端** | value 的字节数；`u32::MAX` = 墓碑 |
| 12 | `key_len` | `key` | UTF-8 字节 | |
| 12+key_len | `val_len` | `value` | 任意字节 | 墓碑时不存在 |
| 末尾 | 4 | `crc32` | `u32` 小端 | 覆盖 `[0, 12+key_len+val_len)` |

**为什么用固定小端（`to_le_bytes` / `from_le_bytes`）而不是平台字节序？** 因为数据文件要能跨机器拷。用 `to_ne_bytes`（平台序）的话，在大端机器上写的文件拿到 x86 上就读错了。x86/ARM 都是小端，所以小端也是事实标准。

### 2.3 `Frame` —— 解码后的内存表示

```rust
pub(crate) struct Frame {
    pub(crate) key: String,
    pub(crate) value: Option<Vec<u8>>,   // None = 墓碑
    pub(crate) consumed: u64,            // 该帧占用的总字节数（含头尾）
}
```

字段是 `pub(crate)` 而不是 `pub`：**帧格式是内部实现细节**，不应该出现在这个 crate 的公开 API 里，但同 crate 的 `stage6_compact` 需要访问。≈ Java 的 package-private。

`consumed` 是重放时能"跳到下一条"的关键：

```rust
pos += frame.consumed;
```

## 3. 核心代码路径

### 3.1 编码：`encode_frame`

```rust
pub(crate) fn encode_frame(key: &str, value: Option<&[u8]>) -> Vec<u8>
```

**参数**：
- `key: &str` —— 借用，不需要所有权（只读）
- `value: Option<&[u8]>` —— `None` 表示墓碑

**返回值**：`Vec<u8>`，一帧的完整字节。

```rust
pub(crate) fn encode_frame(key: &str, value: Option<&[u8]>) -> Vec<u8> {
    // ① 长度转换：用 try_from + expect，而不是 `as`
    let key_len = u32::try_from(key.len()).expect("key 长度超过 4 GiB");
    let val_len = value
        .map_or(TOMBSTONE, |v| u32::try_from(v.len()).expect("value 长度超过 4 GiB"));

    // ② 一次性预分配，避免 Vec 多次扩容（≈ new ArrayList<>(cap)）
    let cap = (HEADER_LEN + FOOTER_LEN) + key.len() + value.map_or(0, <[u8]>::len);
    let mut buf = Vec::with_capacity(cap);

    // ③ 按顺序写入
    buf.extend_from_slice(&MAGIC);
    buf.extend_from_slice(&key_len.to_le_bytes());
    buf.extend_from_slice(&val_len.to_le_bytes());
    buf.extend_from_slice(key.as_bytes());
    if let Some(v) = value {
        buf.extend_from_slice(v);
    }

    // ④ 校验和覆盖 header + key + value（不包含自己）
    let crc = crc32(&buf);
    buf.extend_from_slice(&crc.to_le_bytes());
    buf
}
```

**① 为什么用 `try_from` 而不是 `as`？**

`usize as u32` 在 64 位平台上是**静默截断**——一个 5 GiB 的 value 会变成 `705032704`，写下去就是一个"看起来完全合法"的错误长度，恢复时要么读到垃圾，要么被判损坏。Java 的 `(int) longValue` 也是静默的，这是同一类漏洞。

`try_from(...).expect(...)` 把"不可能发生"变成"发生了就明确 panic 并告诉你原因"。

**② `Vec::with_capacity`** —— 已知最终长度，一次性分配。`Vec` 的倍增扩容策略在这里会多分配约 1 倍内存 + 多次 `memcpy`。

**④ CRC 覆盖范围** —— 头 + key + value，**不含 crc 字段本身**。这是标准做法：校验和字段自己不能参与自己的计算。

### 3.2 CRC32：查表在编译期生成

```rust
const fn build_crc_table() -> [u32; 256] {
    let mut table = [0u32; 256];
    let mut i = 0u32;
    while i < 256 {
        let mut c = i;
        let mut k = 0;
        while k < 8 {
            c = if c & 1 != 0 { 0xEDB8_8320 ^ (c >> 1) } else { c >> 1 };
            k += 1;
        }
        table[i as usize] = c;
        i += 1;
    }
    table
}

static CRC_TABLE: [u32; 256] = build_crc_table();

fn crc32(data: &[u8]) -> u32 {
    let mut c = 0xFFFF_FFFFu32;
    for &b in data {
        c = CRC_TABLE[((c ^ u32::from(b)) & 0xFF) as usize] ^ (c >> 8);
    }
    c ^ 0xFFFF_FFFF
}
```

**`const fn` + `static` 的组合是 Rust 的拿手好戏**：256 项的表在**编译期**算好，直接进二进制的只读段，运行期零初始化成本。Java 里只能写 `static {}` 初始化块（运行期算）或硬编码一个 256 行的数组（丑）。

`while` 而不是 `for` 的原因：`const fn` 里对迭代器的支持有限（早期版本），`while` 循环是最稳的写法。

### 3.3 解码：`read_frame_at`

```rust
pub(crate) fn read_frame_at(file: &File, offset: u64) -> Result<Frame>
```

**参数**：
- `file: &File` —— **不可变借用**就够了，因为用的是位置读取（不修改文件游标）
- `offset: u64` —— 段内字节偏移

**返回值**：`Result<Frame>`；任何一步不对就返回 `KvError::Corrupted { reason, truncated_at }`。

**逐步拆解：**

```rust
// ① 读 12 字节头
let mut header = [0u8; HEADER_LEN];
match read_exact_at(file, &mut header, offset) {
    Ok(()) => {}
    Err(e) if e.kind() == io::ErrorKind::UnexpectedEof => {
        // 读到文件末尾 / 只读到一半 → 视为损坏，调用方会截断
        return Err(KvError::Corrupted { reason: "头部不完整".into(), truncated_at: offset });
    }
    Err(e) => return Err(e.into()),
}

// ② 魔数校验
if header[..4] != MAGIC {
    return Err(KvError::Corrupted { reason: "魔数不匹配".into(), truncated_at: offset });
}
let key_len = u32::from_le_bytes([header[4], header[5], header[6], header[7]]) as usize;
let val_len = u32::from_le_bytes([header[8], header[9], header[10], header[11]]);

// ③ 防御性检查：长度字段来自磁盘，不可信
let value_bytes = if val_len == TOMBSTONE {
    None
} else {
    let n = usize::try_from(val_len).unwrap_or(usize::MAX);
    if n > MAX_RECORD {
        return Err(KvError::Corrupted {
            reason: format!("记录长度异常: {n}"),
            truncated_at: offset,
        });
    }
    Some(n)
};
if key_len > MAX_RECORD {
    return Err(KvError::Corrupted { reason: "key 长度异常".into(), truncated_at: offset });
}
```

**③ 是整段代码里最重要的防御**。想想如果不做这个检查会发生什么：一个损坏的 `val_len` 是 `0xFFFF_FFFF`（但不是 TOMBSTONE 的情况不存在）或者是 `4000000000`，`vec![0u8; 4_000_000_000]` 会：

- 要么 OOM 被杀；
- 要么在 64 位机器上"成功"分配 4 GB 虚拟内存，然后 OOM killer 找上门。

**读不可信数据时，每一个来自外部的长度字段都必须有上限检查**——这是 C/C++ 时代无数缓冲区溢出漏洞的根因。Rust 在类型层面已经拦掉了大部分越界，但这个"长度合理性"的边界要自己守。

```rust
// ④ 按"基址 + 偏移"读 body，全程不依赖文件游标
let mut cursor = offset + HEADER_LEN as u64;

let mut key_buf = vec![0u8; key_len];
read_exact_at(file, &mut key_buf, cursor).map_err(|_| KvError::Corrupted {
    reason: "key 不完整".into(), truncated_at: offset,
})?;
cursor += key_len as u64;

let value = match value_bytes {
    Some(n) => {
        let mut v = vec![0u8; n];
        read_exact_at(file, &mut v, cursor).map_err(|_| KvError::Corrupted {
            reason: "value 不完整".into(), truncated_at: offset,
        })?;
        cursor += n as u64;
        Some(v)
    }
    None => None,
};

// ⑤ 读 CRC 并校验
let mut crc_buf = [0u8; FOOTER_LEN];
read_exact_at(file, &mut crc_buf, cursor).map_err(|_| KvError::Corrupted {
    reason: "校验和不完整".into(), truncated_at: offset,
})?;

let mut check = Vec::with_capacity(HEADER_LEN + key_len + value_bytes.unwrap_or(0));
check.extend_from_slice(&header);
check.extend_from_slice(&key_buf);
if let Some(v) = &value { check.extend_from_slice(v); }

let expected = u32::from_le_bytes(crc_buf);
if crc32(&check) != expected {
    return Err(KvError::Corrupted { reason: "校验和不匹配".into(), truncated_at: offset });
}

// ⑥ key 必须是合法 UTF-8
let key = String::from_utf8(key_buf)
    .map_err(|_| KvError::Corrupted {
        reason: "key 不是合法 UTF-8".into(), truncated_at: offset,
    })?;

Ok(Frame { key, value, consumed: frame_len(key_len, value_bytes) })
```

**⑥ 是"二进制安全"的边界**：value 可以是任意字节（包括 `\r\n`、非 UTF-8），但 **key 必须是 UTF-8**，因为它是 `HashMap<String, _>` 的键。这是一个明确的设计约束，不是疏漏。

### 3.4 位置读取：`read_exact_at`

```rust
pub(crate) fn read_exact_at(file: &File, buf: &mut [u8], offset: u64) -> io::Result<()> {
    #[cfg(unix)]
    {
        use std::os::unix::fs::FileExt;
        read_loop(|b, off| file.read_at(b, off), buf, offset)
    }

    #[cfg(windows)]
    {
        use std::os::windows::fs::FileExt;
        read_loop(|b, off| file.seek_read(b, off), buf, offset)
    }

    #[cfg(not(any(unix, windows)))]
    {
        use std::io::{Read, Seek, SeekFrom};
        let mut f = file;
        f.seek(SeekFrom::Start(offset))?;
        f.read_exact(buf)
    }
}

fn read_loop<F>(read_at: F, buf: &mut [u8], offset: u64) -> io::Result<()>
where F: Fn(&mut [u8], u64) -> io::Result<usize>,
{
    let mut filled = 0usize;
    while filled < buf.len() {
        let n = read_at(&mut buf[filled..], offset + filled as u64)?;
        if n == 0 {
            return Err(io::Error::new(io::ErrorKind::UnexpectedEof, "读取到文件末尾"));
        }
        filled += n;
    }
    Ok(())
}
```

**为什么必须有这个函数？** 见坑 2（`try_clone` 共享游标）。

**为什么参数是 `&File` 而不是 `&mut File`？** 因为位置读取不修改文件游标。这个签名差异带来一个巨大的好处：**多个读操作可以并发调用，连 `RwLock` 的读锁都不需要**。类型系统直接把"这个是安全的"写进了签名。

**`read_loop` 为什么必要？** `read_at` 不保证一次读满（和 `Read::read` 一样可能部分返回）。`read_exact` 的语义是"要么读满要么报错"，所以必须循环补齐。

### 3.5 写入路径：`append`

```rust
fn append(&mut self, key: &str, value: Option<&[u8]>) -> Result<Location> {
    let bytes = frame::encode_frame(key, value);
    let offset = self.active_pos;
    self.active_writer.write_all(&bytes)?;      // 一次 write(2) 写完一帧
    self.active_pos += bytes.len() as u64;
    Ok(Location { seg: self.active_id, offset, len: bytes.len() as u64 })
}
```

**一次 `write(2)` 写完一帧**，加上 append 模式（`O_APPEND`）的原子性，保证：

1. 不会出现"写了一半"的中间态被其他读者看到（内核保证 append 的原子性直到某个 size，通常 4KB 以内；本项目单帧上限 64 MiB 其实**超过了 O_APPEND 的原子保证范围**——这是一个理论上的边界，见 4.5）
2. 多进程 append 同一文件不会互相覆盖

**注意 `write_all` 而不是 `write`**：`write` 可能只写一部分就返回，`write_all` 内部循环直到写完。

## 4. 边界情况

| 情况 | 处理 | 说明 |
|------|------|------|
| **空的 value**（`SET k ""`） | `val_len = 0`，与墓碑区分开 | ✅ 空字符串是合法值，不是删除 |
| **key 含非 ASCII** | `key.as_bytes()` 按 UTF-8 字节写，`key_len` 是**字节数不是字符数** | ✅ 关键：`len()` 是字节数，中文 key 一个字 3 字节 |
| **value 含 `\r\n` / 非 UTF-8** | 原样写入，`String::from_utf8_lossy` 只在 encode 响应时用于显示 | ✅ 二进制安全 |
| **key 不是合法 UTF-8** | `read_frame_at` 返回 `Corrupted` | ⚠️ API 层面不可能发生（`&str` 参数），只在文件损坏时出现 |
| **key/value 超过 4 GiB** | `try_from().expect()` panic | ⚠️ 实际上 `MAX_RECORD = 64 MiB` 会先拦住解析侧 |
| **单条记录超过 64 MiB** | 写入侧不拦！解析侧报 `Corrupted` | ⚠️ 见下 |
| **损坏的长度字段** | `MAX_RECORD` 检查拦住 | ✅ 防止 `vec![0; 4GB]` |
| **文件被截断到一半** | `read_exact_at` 返回 `UnexpectedEof` → `Corrupted` | ✅ 恢复路径会截断 |
| **位翻转（值变了但长度对）** | CRC32 检测到 | ✅ |
| **磁盘满** | `write_all` 返回 `Err` | ✅ 但内存索引可能不一致，见模块四坑 |

### 4.5 一个理论边界：O_APPEND 的原子性上限

POSIX 规定 `O_APPEND` 的写入是原子的，但**没有规定上限**；实际实现通常保证到 `PIPE_BUF`（4 KiB）或文件系统块大小。本项目 `MAX_RECORD = 64 MiB`，单帧远超这个范围——**如果真的写 64 MiB 的记录，多进程 append 理论上可能交错**。

真实引擎的做法是：`MAX_RECORD` 设小（通常 1~16 MiB），或者干脆用**独占写进程 + 显式 offset**（不用 O_APPEND）。

> 本项目是单写者模型（模块六会讲：写锁 / Actor 串行化），所以实践中不会触发。但这是一个值得知道的限制。

## 5. 常见坑

### 坑 1：活跃段不能用 `BufWriter`（本项目真实踩过）

```rust
// ❌ 本能写法
active_writer: BufWriter<File>,
```

**症状**：刚 `set` 完立刻 `get`，读到旧数据甚至 EOF，然后被判成"数据损坏"。

**根因**：活跃段同时被两种操作使用——

- **写**：`write_all` 追加到末尾
- **读**：`get` 按索引里的 offset 随机读

一旦加了用户态缓冲，`write_all` 的数据还在 `BufWriter` 的缓冲区里，文件上根本没有；此时按 offset 读就会读到 EOF 或旧内容。

**正解**：活跃段直接用 `File`，把写入合并交给 **OS page cache**——`write(2)` 本身就是进内核缓存的，速度远比想象中快。

```rust
// ✅
active_writer: File,
```

> 这个坑在 Java 里一模一样（`BufferedWriter` 混用 `RandomAccessFile`）。
> 区别是：**Java 会静默返回旧数据/半截数据，Rust 会明确报 `Corrupted`。** 后者的"吵闹"是优点。

### 坑 2：`File::try_clone()` 不是独立的游标

```rust
// ❌ 错误的心智模型："clone 一份句柄，各自 seek"
let a = file.try_clone()?;
let b = file.try_clone()?;
// a 和 b 共享同一个文件偏移量！
```

`try_clone` 底层是 `dup(2)` / `DuplicateHandle`，**新旧句柄共享同一个文件偏移量**。多线程各自 `seek` 会互相踩，表现出来是**随机**出现「魔数不匹配」「校验和不匹配」——这种"偶发的玄学错误"是最难查的一类。

**正解**：位置读取（`read_at` / `seek_read`），见 3.4。对应 Java 的 `FileChannel.read(ByteBuffer, position)`。

> 模块一的 `open` 里用了 `try_clone()`，但那里是**启动阶段的单线程代码**，克隆出的句柄只做一次顺序重放，所以安全。这两处不矛盾：**能确定单线程时用 clone 没问题，运行时多线程一律用位置读取。**

### 坑 3：Windows 上 `set_len` 需要写权限

```rust
// ❌ 在 Windows 上：PermissionDenied (os error 5)
let file = File::open(path)?;      // 只读
file.set_len(truncated_at)?;       // 炸
```

只读句柄（或 append 句柄，它只申请了 `FILE_APPEND_DATA`）没有 `FILE_WRITE_DATA`，`set_len` 会被拒。**Linux 上不报错**——所以这个 bug 只在 Windows CI 上暴露。

**正解**：截断时临时开一个写句柄。

```rust
// ✅
let writable = OpenOptions::new().write(true).open(path)?;
writable.set_len(truncated_at)?;
writable.sync_all()?;
```

### 坑 4：`usize as u32` 的静默截断

见 3.1 的 ①。永远用 `u32::try_from(n)` 并显式处理失败。

### 坑 5：忘了 `flush`

`write_all` 之后如果不 `sync_all`，数据在 page cache 里——**进程崩溃不丢，机器断电丢**。这是档位 1，不是 bug，但你要知道自己选了哪一档。

## 6. 性能考量

### 6.1 单次写入的成本构成

```
SET k v  →  encode_frame（1 次堆分配 + CRC 计算）
         →  write_all（1 次系统调用，进 page cache）
         →  index.insert（1 次哈希 + 可能的 rehash）
```

**热点是 CRC 和系统调用**，不是内存拷贝。

### 6.2 CRC32 的成本

- 查表法 CRC32 约 **1~3 GB/s**（取决于实现和 CPU）
- 编译期生成表：启动零成本
- 对小 value（< 1 KB）来说，CRC 的开销和一次 `memcpy` 同量级

**如果要更快**：换 `xxhash`（`twox-hash` crate，约 10 GB/s）或硬件 CRC32 指令（x86 的 `crc32c`）。代价是校验强度下降（xxhash 不是为错误检测设计的，虽然实践中够用）。

### 6.3 fsync 的成本

实测数量级（SSD）：

| 操作 | 典型耗时 |
|------|---------|
| `write_all`（进 page cache） | ~1 μs |
| `sync_all()`（SSD） | 0.1 ~ 1 ms |
| `sync_all()`（HDD） | 5 ~ 20 ms |

**fsync 比 write 贵 100~1000 倍**。这就是为什么生产引擎默认不 fsync。

如果想要"既安全又快"，标准答案是**组提交（group commit）**：把 N 次 fsync 合并成 1 次——见第 08 篇的扩展方向。

### 6.4 OS page cache 是你最好的朋友

本项目不用 `BufWriter` 却不慢，靠的就是 page cache：

- `write(2)` 进内核缓存后立即返回，不等待磁盘；
- 内核负责合并写、预读、回刷；
- 刚写的数据立刻可读（缓存命中）。

**代价**：你失去了对"什么时候真的落盘"的精确控制。这就是为什么需要 `sync_all`。

### 6.5 可优化方向

| 方向 | 收益 | 代价 |
|------|------|------|
| **复用编码缓冲区** | 消除每次 `Vec::with_capacity` | 需要一个可复用的 scratch buffer，写路径要重构 |
| **`bytes::Bytes` 零拷贝值** | `get` 不再拷贝 value | 要改 trait 签名，值需要引用计数 |
| **mmap 读路径** | 消除 read 系统调用和一次拷贝 | 失去对页面淘汰的控制，P99 可能抖动 |
| **组提交** | 写吞吐提升 1~2 个数量级 | 需要一个后台 fsync 线程 + 等待队列 |
| **批量写**（一次 write 多帧） | 减少系统调用 | 需要攒批，增加延迟 |

### 7.1 用示例程序看真实字节

```bash
cargo run --example frame_format
```

输出（节选）：

```text
=== 1. 编码一条记录 ===
key = "name", value = "minidb"
帧长度 = 26 字节
  00000000  4d 44 42 31 04 00 00 00 06 00 00 00 6e 61 6d 65  |MDB1........name|
  00000010  6d 69 6e 69 64 62 3d 2d 01 90                    |minidb=-..|

逐字段：
  magic   = [4d, 44, 42, 31]  ("MDB1")
  key_len = [04, 00, 00, 00]  (= 4)
  val_len = [06, 00, 00, 00]  (= 6)

解码回来：key=name, value=Some("minidb"), consumed=26

=== 2. 墓碑（删除标记）===
val_len = [ff, ff, ff, ff]  (= u32::MAX = 墓碑)
帧长度 = 20 字节（比上面少 6 字节的 value）
  00000000  4d 44 42 31 04 00 00 00 ff ff ff ff 6e 61 6d 65  |MDB1........name|
  00000010  ed 5c 8c 17                                      |.\..|

=== 3. 篡改 value 的一个字节 ===
原字节 6d → 现字节 92
  ✅ 被检出：校验和不匹配

  ✅ 被检出：长度不足：需要 4 字节 @ offset 22，实际只有 23 字节

=== 5. 空 value ≠ 墓碑 ===
空 value：val_len = [00, 00, 00, 00]  (= 0)
墓碑    ：val_len = [ff, ff, ff, ff]  (= u32::MAX)
```

**从 26 这个数字能直接验证格式**：`12（头）+ 4（key）+ 6（value）+ 4（尾）= 26`。墓碑帧 `12 + 4 + 0 + 4 = 20`。

第 4 步的报错信息值得注意：**"长度不足：需要 4 字节 @ offset 22"**。这是 `read_frame_at` 里每一处切片都要先检查长度的体现——没有一个 `buf[cursor..cursor+n]` 是裸写的。少了这道检查，半包就不是"可恢复的损坏"，而是 panic。
