# 模块四：删除（墓碑）与合并压缩

> 对应源码：`src/stage6_compact.rs`
> 对应示例：`examples/gc_demo.rs`
> 前置：模块二（帧格式）、模块三（索引）

---

## 1. 要解决的问题与设计权衡

### 1.1 问题的起点：append-only 只增不改

模块二定下了"只追加"的写入策略，它带来了顺序写的高性能和崩溃的简单性，但也带来一个必然结果：

**同一个 key 写 100 次，磁盘上就有 100 条记录，其中 99 条是垃圾。**

`SET k v1` … `SET k v100` 之后，索引里 `k` 只指向最后一条（模块三讲过），但前 99 条仍然躺在段文件里占着空间。这些记录被称为**垃圾（garbage / dead data）**，清理它们的过程叫**合并压缩（compaction / merge）**。

这是所有 LSM 系引擎（Bitcask、LevelDB、RocksDB、Cassandra）共有的核心机制，区别只在于"怎么合并、合并哪些、什么时候合并"。

### 1.2 删除怎么表示？三种方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 原地删除 | 找到记录，从文件中间挖掉 | 立即释放空间 | 破坏 append-only；要移动后续所有字节；崩溃会撕裂文件 |
| B. **墓碑** | 追加一条"k 已删除"的特殊记录 | 保持 append-only；崩溃安全；实现简单 | 空间不立即释放；读路径要识别墓碑 |
| C. 索引标记 + 重写 | 索引里标 deleted，靠合并回收 | 不占磁盘 | 重启后标记丢失，必须落盘成墓碑——其实就是 B |

**本项目选 B**。理由和前文一致：append-only 带来的好处（顺序写、崩溃后只需截断尾部）远大于代价，而代价可以靠合并来偿还。

墓碑的编码方式是模块二讲过的 `val_len = u32::MAX` 哨兵值：

```text
普通记录: [MDB1][key_len][val_len][key][value][crc32]
墓碑    : [MDB1][key_len][0xFFFFFFFF][key][crc32]     ← 没有 value 区
```

用 `val_len` 的一个特殊值表达删除，好处是**不需要在格式里新增字段**，解码逻辑只需要一个分支。

### 1.3 权衡一：删除要不要立即回收空间？

不要。原因有三：

1. **回收需要重写文件**，而重写一个 1 GiB 的段不是"删一条记录"该付的代价（它应该由后台合并批量摊销）。
2. **立即回收就要移动后续字节**，之后的 offset 全部失效，索引要整体更新——索引里存的是 `(seg, offset, len)`（模块三），移动数据等于索引全量失效。
3. **崩溃安全**：任何原地修改都可能出现"改了一半断电"的中间态。追加则只有"写完了"和"没写"两种状态。

代价是：**删除一个键，磁盘占用反而会略微增加**（多了一条墓碑记录）。这在 `gc_demo` 里有实测数字。

### 1.4 权衡二：墓碑什么时候能真正丢掉？

这是本模块**最容易被误解**的一点，请务必想清楚。

考虑这个场景：

```text
段 1: [SET k = v1]
段 2: [DEL k]        ← 墓碑
```

如果我现在**只合并段 1**，把 `k = v1` 重写进新段、然后删掉段 1——会发生什么？段 2 的墓碑还在，索引里 `k` 被墓碑 remove 掉了，看起来没问题。

但如果**只合并段 2**呢？我扫描段 2，看到墓碑，于是"丢掉"它，新段里没有 `k` 的墓碑。然后删掉段 2。段 1 里 `k = v1` 还在——下次重放段 1 时，`k` **复活了**。

> **规则：只有当"所有可能包含该 key 旧记录的段"都被纳入同一次合并时，墓碑才能被丢弃。**

本项目的 `compact()` 采用最简单的策略：**一次性合并所有段**（frozen 全部 + 活跃段）。既然旧记录全部被扫进新段、旧文件全部删除，墓碑就可以安全地整个丢掉——不存在"被遗漏的旧记录会复活"的可能。

这也是为什么 `gc_demo` 里合并后墓碑标记数从 5 变成 0，而重启后 `GET hot-00` 依然是 `None`。

如果你以后实现**增量合并**（只合并垃圾占比最高的几个段，这是生产引擎的常见做法），就必须把所有墓碑**原样搬进新段**，直到某一次合并覆盖了它的所有旧记录为止。RocksDB 里的 `snapshot`、Cassandra 的 `tombstone_gc` 处理的正是这个复杂度。

### 1.5 权衡三：什么时候触发合并？

三个可选时机：

| 时机 | 实现 | 问题 |
|------|------|------|
| 同步触发（每次写入后检查） | `set()` 末尾判断 | 合并是 O(数据量) 的重活，会卡住写入 |
| 后台线程定时检查 | `spawn_compactor`（模块六） | 需要额外线程，但写入路径不受影响 |
| 完全手动 | 暴露 `compact()` 给用户 | 忘记调用就空间爆炸 |

本项目实际上有**四个**触发点，分散在两层里：

| 触发点 | 位置 | 是否真的被调用 |
|--------|------|--------------|
| `SegmentEngine::maybe_compact()` | `stage6_compact.rs:276` | ❌ **定义了但没有任何调用方**（死代码） |
| `SegmentEngine::compact()` | `stage6_compact.rs:292` | ✅ 通过 `Engine::compact()` 暴露，对应 `COMPACT` 命令 |
| **`Engine::set()` 末尾的内联检查** | `engine.rs:141` | ✅ **每次写入后同步检查并合并** |
| `SharedEngine::spawn_compactor()` | `stage7_concurrent.rs:109` | ✅ 后台线程定时检查（模块六） |

**最容易被忽略的是第三条**——`Engine::set` 里有这么一段：

```rust
pub fn set(&mut self, key: &str, value: impl Into<Vec<u8>>) -> Result<()> {
    Stats::incr(&self.stats.sets);
    self.inner.set(key, value.into())?;
    // 写后检查是否需要合并
    if self.inner.garbage_ratio() >= self.config.compact_threshold {
        Stats::incr(&self.stats.compactions);
        self.inner.compact()?;      // ← 同步全量合并，就在写路径上
    }
    Ok(())
}
```

这意味着：**一次普通的 `SET` 可能突然变成一次全库重写**。这是本项目最大的延迟尖峰（tail latency）来源，也是 1.5 节表格里"同步触发"那一行的真实写照——它确实被实现了，而且默认开启。

实测：起一个服务器，`SET name "minidb server"` → `DEL name` → `SET k2 v2`，最后这一步触发了合并，数据目录从 `000000001.log` 变成 `000001002.log` + 空的新活跃段 `000001003.log`（模块七 7.1 有完整的协议交互记录）。

注意 `Engine::delete()` **没有**这个检查——所以"反复删除"不会触发合并，只有写入会。

触发条件是**垃圾占比**：

```rust
const COMPACT_THRESHOLD: f64 = 0.3;   // 垃圾超过 30% 就合并

pub fn maybe_compact(&mut self) -> Result<bool> {
    if self.garbage_ratio() < COMPACT_THRESHOLD {
        return Ok(false);
    }
    self.compact()?;
    Ok(true)
}
```

阈值背后的权衡（**空间放大 vs 写放大**）：

- **阈值太低**（如 5%）：合并非常频繁，每次都要重写全库 → **写放大**严重。极端情况：反复覆盖一个键，每写几次就重写一遍全部数据，磁盘写入量是逻辑写入量的几十倍。
- **阈值太高**（如 90%）：空间被垃圾长期占据，磁盘可能先撑爆 → **空间放大**严重。
- **30%** 是一个经验折中：最坏情况下磁盘占用约为有效数据的 `1 / (1 - 0.3) ≈ 1.43` 倍。

真实系统还会加**最小间隔**（两次合并之间至少间隔 N 秒）和**合并速率限制**，避免在写入高峰时反复触发。

### 1.6 权衡四：全量合并 vs 增量合并

| | 全量合并（本项目） | 增量合并（RocksDB/Bitcask 生产实现） |
|---|---|---|
| 实现复杂度 | 低：一次重写所有段 | 高：要选段、要搬迁墓碑、要处理多代 |
| 单次停顿 | 长：O(有效数据量) | 短：只处理被选中的段 |
| 峰值磁盘占用 | 需要额外 1 份有效数据的空间 | 只需被选中段的空间 |
| 写放大 | 高 | 低 |

Bitcask 原论文的 merge 是**逐段**进行的（保留多个段、合并其中一部分），本项目简化成了全量——这是教学上的取舍，读代码时别忘了这一点。

## 2. 关键数据结构

### 2.1 垃圾记账：两个计数器

```rust
pub struct SegmentEngine {
    // … 其他字段见模块一 …
    index: HashMap<String, Location>,
    dead_bytes: u64,   // 已被覆盖/删除、但仍占着磁盘的字节数
    live_bytes: u64,   // 当前有效记录占用的字节数
}
```

`garbage_ratio()` 就是从这两个数算出来的：

```rust
pub fn garbage_ratio(&self) -> f64 {
    let total = self.dead_bytes + self.live_bytes;
    if total == 0 {
        return 0.0;
    }
    self.dead_bytes as f64 / total as f64
}
```

**为什么不直接比较"文件大小之和"与"有效数据大小"？**

因为那样每次调用都要 `stat` 一遍所有段文件（系统调用）。记账法是 O(1) 的：每次 `set`/`delete` 时增量更新两个计数器。代价是**记账逻辑本身可能有 bug**（见 5.2），而 `stat` 法永远正确——这是一对典型的性能/正确性权衡。

注意 `#[allow(clippy::cast_precision_loss)]`：`u64 → f64` 在超过 `2^53` 时会丢精度，但"占比"只需要两位有效数字，这里明确接受这个误差。Rust 逼你**显式承认**这个取舍（Java 里 `long → double` 是静默的）。

### 2.2 `Location` —— 记账的最小单位

```rust
#[derive(Debug, Clone, Copy)]
struct Location {
    seg: u64,     // 段 id（文件名去掉 .log 后的数字）
    offset: u64,  // 段内字节偏移
    len: u64,     // 整帧长度（头 + key + value + crc）
}
```

`len` 是记账的关键：一条记录从"有效"变成"垃圾"时，`dead_bytes += len; live_bytes -= len`。

它是 `Copy` 的（12 字节，比指针还小），所以 `index.insert()` / `read_at(*loc)` 都是按位拷贝，没有引用计数的开销。Java 里这只能是一个小 `record` 或 `long` 编码——多一次对象分配。

### 2.3 合并产物的命名

```rust
let new_id = self.active_id + 1 + 1000;                      // 例如 1 → 1002
let tmp_path = self.dir.join(format!("{new_id:09}.log.compacting"));
let final_path = Self::seg_path(&self.dir, new_id);          // 000001002.log
```

- **为什么要跳 +1000？** 为了避免合并产物的 id 与将来滚动出来的新段 id 撞车。合并后还要再开一个新的活跃段（`fresh_id = new_id + 1 = 1003`），如果直接用 `active_id + 1`，就会出现"新活跃段的 id 与刚被删掉的旧段 id 相同"的混乱。
- **为什么临时文件叫 `*.log.compacting` 而不是 `*.tmp`？** 后缀 `.compacting` 让"这是一次未完成的合并"这件事自解释；同时它在目录扫描时不会被当成段（扫描只认 `.log` 结尾，见模块一 `load_manifest`）。

## 3. 核心代码路径

### 3.1 调用链总览

```text
delete(key)
  └─ index.remove(key)            取出旧 Location（没有就直接返回 None，不写墓碑）
     ├─ read_at(old_loc)          读出旧值（为了返回给调用方）
     ├─ append(key, None)         写墓碑帧
     └─ 记账: dead += old.len + tomb.len;  live -= old.len

set(key, value)
  ├─ should_roll()?  → roll()     活跃段超过 1 MiB 就冻结、开新段
  ├─ append(key, Some(value))      追加记录
  └─ 记账: 若覆盖了旧值 → dead += old.len; live -= old.len; 然后 live += new.len

maybe_compact()
  └─ garbage_ratio() >= 0.3 ?  → compact()

compact()
  ├─ 1. sync 活跃段
  ├─ 2. 收集并排序 index 里的所有 key
  ├─ 3. 逐个 read_at(旧位置) → 写进临时文件（跳过读不到/已删的）
  ├─ 4. flush + fsync 临时文件
  ├─ 5. rename（原子替换）
  ├─ 6. 删除所有旧段文件、重建 frozen / 活跃段
  └─ 7. 重置记账 + 保存 manifest
```

### 3.2 删除：`fn delete`

```rust
fn delete(&mut self, key: &str) -> Result<Option<Vec<u8>>> {
    let Some(loc) = self.index.remove(key) else {
        return Ok(None);
    };
    let old = self.read_at(loc)?;
    // 墓碑也要落盘，否则重启后键会"复活"
    let tomb = self.append(key, None)?;
    self.dead_bytes += loc.len + tomb.len;
    self.live_bytes -= loc.len;
    Ok(old)
}
```

逐步分析：

| 行 | 作用 | 为什么这么做 |
|---|------|-------------|
| `let Some(loc) = … else { return Ok(None) }` | 键不存在 → 直接返回 | **不写墓碑**。否则反复 `DEL` 一个不存在的键会无限积累垃圾。这是 `let-else`（Rust 1.65+），比 `match` 更顺手 |
| `index.remove(key)` | 从索引移除 | 立即生效：之后的 `GET` 走 `index.get()` 分支，直接返回 `None`，**不需要读磁盘**。墓碑是给"重启后重建索引"用的 |
| `read_at(loc)?` | 读出旧值 | 为了满足 trait 的语义（`delete` 返回被删的值，≈ Java `Map.remove`）。代价：一次额外的磁盘读 |
| `append(key, None)` | 写墓碑 | `None` → 编码时 `val_len = u32::MAX` |
| `dead += loc.len + tomb.len` | 记账 | 旧记录变垃圾，**墓碑本身也算垃圾**（它只是数据，不是空间） |
| `live -= loc.len` | 记账 | 旧记录不再是有效数据 |

**注意顺序**：先 `read_at` 再 `append`。如果反过来，`append` 可能触发段滚动……不过 `append` 里其实没有滚动检查（只有 `set` 有），这是实现上的一个不一致，见 5.4。

### 3.3 段滚动：`should_roll` / `roll`

```rust
const SEGMENT_MAX_BYTES: u64 = 1024 * 1024;   // 1 MiB，方便测试触发

fn should_roll(&self) -> bool {
    self.active_pos >= SEGMENT_MAX_BYTES
}

fn roll(&mut self) -> Result<()> {
    self.active_writer.sync_all()?;                                  // ①
    let old_id = self.active_id;
    let reader = File::open(Self::seg_path(&self.dir, old_id))?;     // ②
    self.frozen.insert(old_id, reader);

    let new_id = old_id + 1;
    let f = OpenOptions::new().create(true).read(true).append(true)
        .open(Self::seg_path(&self.dir, new_id))?;                   // ③
    self.active_writer = f;
    self.active_id = new_id;
    self.active_pos = 0;
    self.save_manifest()?;                                           // ④
    log::info!("段滚动: {old_id} -> {new_id}");
    Ok(())
}
```

- ① 滚动前先 `fsync`：确保冻结的段数据已经真正落盘。
- ② **以只读方式重新打开旧段**并放进 `frozen`。注意这里开了一个**新句柄**，而不是复用 `active_writer`——因为 `active_writer` 是 `append` 模式打开的（没有 `FILE_WRITE_DATA` 之外的读能力？实际上 `append(true)` 在 Linux 上可读，但语义上不保证随机读），而历史段只需要随机读。
- ③ 新活跃段同样用 `create(true).read(true).append(true)`：`read` 是为了 `read_at` 能读刚写进去的数据。
- ④ 持久化 manifest：段集合变了，必须让下次启动知道有哪些段。

**为什么需要分段的思考**：如果只有一个无限增长的段文件，合并时就只能全量重写；分成多个段后，可以实现"只合并老的段，新写入不受影响"的增量合并（本项目没做，但结构已经支持）。另外段也是删除旧文件、回收空间的粒度单位。

### 3.4 合并：`fn compact` —— 逐段分析

这是本模块的核心函数。每一步都标注了"此时断电会怎样"。

```rust
pub fn compact(&mut self) -> Result<u64> {
    if self.index.is_empty() {
        return Ok(0);
    }
    self.active_writer.sync_all()?;                          // ①
    let reclaimed = self.dead_bytes;
    let new_id = self.active_id + 1 + 1000;
    let tmp_path = self.dir.join(format!("{new_id:09}.log.compacting"));

    let mut keys: Vec<String> = self.index.keys().cloned().collect();
    keys.sort();                                             // ②

    let mut new_index: HashMap<String, Location> = HashMap::with_capacity(keys.len());
    {
        let file = File::create(&tmp_path)?;                 // ③
        let mut w = BufWriter::new(file);
        let mut pos = 0u64;

        for key in &keys {
            let old_loc = self.index[key];
            if let Some(value) = self.read_at(old_loc)? {    // ④
                let bytes = frame::encode_frame(key, Some(&value));
                w.write_all(&bytes)?;
                new_index.insert(key.clone(), Location { seg: new_id, offset: pos, len: bytes.len() as u64 });
                pos += bytes.len() as u64;
            }
        }
        w.flush()?;                                          // ⑤
        w.get_ref().sync_all()?;
    } // ← w 离开作用域，Drop 关闭文件

    let final_path = Self::seg_path(&self.dir, new_id);
    fs::rename(&tmp_path, &final_path)?;                     // ⑥

    let old_ids: Vec<u64> = self.frozen.keys().copied().collect();
    let old_active = self.active_id;
    self.frozen.clear();
    self.live_bytes = 0;
    for id in old_ids {
        let _ = fs::remove_file(Self::seg_path(&self.dir, id));
    }
    let _ = fs::remove_file(Self::seg_path(&self.dir, old_active));

    self.frozen.insert(new_id, File::open(&final_path)?);    // ⑦

    let fresh_id = new_id + 1;
    let f = OpenOptions::new().create(true).read(true).append(true)
        .open(Self::seg_path(&self.dir, fresh_id))?;
    self.active_writer = f;
    self.active_id = fresh_id;
    self.active_pos = 0;

    self.index = new_index;
    self.dead_bytes = 0;
    self.live_bytes = Self::seg_path(&self.dir, new_id).metadata()?.len();
    self.save_manifest()?;                                   // ⑧
    log::info!("合并完成，回收 {reclaimed} 字节");
    Ok(reclaimed)
}
```

#### ① 合并前先 `sync_all`

```rust
self.active_writer.sync_all()?;
```

**为什么必须先落盘？** 因为合并要"读旧段、写新段、删旧段"。如果旧数据还在 OS page cache 里没落盘，而新段已经写完并删除了旧文件——此时断电，旧数据丢了、新数据也可能没落稳，就真的丢数据了。

（本项目活跃段没有 `BufWriter`，所以不需要 `flush`；如果加了缓冲，这里必须是 `flush()` **然后** `sync_all()`——只 `flush` 只是把用户态缓冲交给内核，不保证落盘。）

#### ② 为什么要对 key 排序？

```rust
let mut keys: Vec<String> = self.index.keys().cloned().collect();
keys.sort();
```

`HashMap` 的迭代顺序**不确定**（Rust 的 `HashMap` 用随机种子的 SipHash，每次运行顺序都可能不同）。排序带来两个好处：

1. **可重现**：同样的输入，合并出来的字节完全一样——对测试、对 `cmp` 两个数据目录、对排查问题都极其重要。
2. 让写入新段的顺序稳定，便于观察。

**代价**：按字典序写 = 按原段的**随机顺序**读，合并过程变成随机 IO（见第 6 节的性能讨论）。

#### ③–⑤ 写临时文件

用 `BufWriter` 包装——这里**可以**用缓冲，因为这个文件只写不读，写完才被别人用。

`File::create` 是 `write(true).create(true).truncate(true)`：如果上次崩溃留下同名临时文件，会被直接覆盖。

`sync_all()` 之后才 rename，保证新段内容先于"新段存在"这件事持久化。

#### ⑥ `rename` —— 唯一的原子操作

```rust
fs::rename(&tmp_path, &final_path)?;
```

同一文件系统内，`rename` 是**原子**的（POSIX 保证，Windows 的 `MoveFileEx` 同理）：不存在"文件存在但内容只有一半"的中间态。

这是整个合并崩溃安全性的支点。如果在 rename 之前断电：临时文件是垃圾（`*.compacting`，不会被扫描成段），旧数据完好。如果在 rename 之后断电：新段是完整的，旧段还没删，下次启动会看到"新段 + 旧段"都在——靠 manifest 决定谁是有效的（本项目 manifest 里的 `frozen` 列表在 ⑧ 才更新，所以**恢复时会同时重放旧段和新段**，因为都还在；虽然会多读一遍，但结果正确，因为新段的记录覆盖旧段。见第 5 节坑 3）。

#### ⑦ 合并产物必须登记进 `frozen`

```rust
self.frozen.insert(new_id, File::open(&final_path)?);
```

**这是合并逻辑里最容易漏的一步。** 如果漏掉，索引已经指向 `seg = new_id`，但 `read_at` 会在 `frozen` 里找不到它，报 `Corrupted { reason: "找不到段 1002" }`——而且是在**下一次读**才炸，离出错的地方很远，非常难查。

顺带一提：合并出来的段是**只读**的（以 `File::open` 打开），所以必须放进 `frozen`，不能当活跃段用。之后另开一个 `fresh_id` 的活跃段。

#### ⑧ 重新记账 + 保存 manifest

```rust
self.dead_bytes = 0;
self.live_bytes = Self::seg_path(&self.dir, new_id).metadata()?.len();
```

新段里只有有效记录，所以 `dead = 0`，`live = 新段文件大小`。这里**用 `stat` 的实际大小覆盖计数器**——等于每次合并后做一次对账，把之前记账可能积累的误差清零。这是一个很实用的设计：增量记账负责快速判断，全量对账负责防止误差无限累积。

### 3.5 重放时的记账：`replay_segment`

```rust
fn replay_segment(
    file: &File,
    seg_id: u64,
    index: &mut HashMap<String, Location>,
    path: &Path,
) -> Result<(u64, u64)> {
    // …
    while pos < len {
        match frame::read_frame_at(file, pos) {
            Ok(f) => {
                let loc = Location { seg: seg_id, offset: pos, len: f.consumed };
                if f.value.is_some() {
                    if let Some(old) = index.insert(f.key, loc) {
                        dead += old.len;
                        live = live.saturating_sub(old.len);
                    }
                    live += f.consumed;
                } else {
                    if let Some(old) = index.remove(&f.key) {
                        dead += old.len;
                        live = live.saturating_sub(old.len);
                    }
                    dead += f.consumed;
                }
                pos += f.consumed;
            }
            // … 损坏处理见模块五 …
        }
    }
    Ok((dead, live))
}
```

两点值得注意：

1. **为什么是自由函数而不是方法？** 因为它需要 `&mut index`，而 `index` 是 `self` 的字段。如果写成 `fn replay(&mut self, ...)`，调用时就会同时借用 `self.index`（可变）和 `self.frozen`（不可变），触发借用冲突。把"只操作 index 的部分"拆成自由函数，是绕过借用检查最干净的办法之一。Java 开发者会本能地写成 private 方法，在 Rust 里这常常编译不过。

2. **`saturating_sub` 而不是 `-`**：旧记录可能在**另一个段**里，本段的 `live` 计数里根本没有它，直接减会下溢。debug 模式下整数溢出会 panic（Java 的 `long` 会静默回绕），`saturating_sub` 明确保留"减到 0 为止"的语义。

   但这也埋下了一个记账偏差，见 5.2。

## 4. 边界情况清单

| 情况 | 行为 | 是否正确 |
|------|------|---------|
| 删除不存在的键 | 返回 `Ok(None)`，**不写墓碑** | ✅ 避免垃圾无限积累 |
| 删除后立刻 `GET` | 返回 `None`（索引里已移除，不读磁盘） | ✅ |
| 删除后 `KEYS` | 不出现在结果里 | ✅ |
| 删除后重启 | 重放墓碑 → `index.remove` → 仍然是 `None` | ✅ |
| 合并后墓碑消失 | 被删键不会复活（旧记录所在段已全部删除） | ✅ |
| **只合并部分段时丢墓碑** | 被删键会复活 | ❌ 本项目不做增量合并，规避了 |
| 对空库调用 `compact()` | `index.is_empty()` → 直接返回 `0` | ✅ 避免创建一个空段 |
| 合并期间断电（rename 前） | 临时文件残留，旧数据完好 | ✅ 只浪费磁盘 |
| 合并期间断电（rename 后、删旧段前） | 新旧段同时在，重放时新段覆盖旧段 | ✅ 结果正确，只是多读 |
| 反复 `SET` 同一个键使活跃段超限 | `set()` 里检查 `should_roll` → 滚动 | ✅ |
| 反复 `DEL` 使活跃段超限 | **不滚动**（`delete` 里没检查） | ⚠️ 见 5.4 |
| 段文件大小恰好等于阈值 | `>=` 触发滚动 | ✅ |
| 合并产物的 id 溢出（`u64`） | 实际不可能（每秒滚 1000 段也要 5 亿年） | — |

## 5. 常见坑

### 坑 1：以为删除会释放空间

**现象**：`DELETE` 之后 `df` 没变化，甚至文件还大了一点。

**原因**：删除是追加墓碑。

**怎么判断该合并了**：`garbage_ratio()`。`gc_demo` 里删 5 个键后磁盘从 59800 → 59910 字节，**增加了 110 字节**（5 条墓碑 × 22 字节）。

### 坑 2：多段场景下 `live_bytes` 会**高估**（真实存在的行为）

考虑这个序列：

```text
段 1: SET k = <100 字节的记录>
（滚动）
段 2: SET k = <10 字节的记录>
```

重放时：

- 段 1：`live += 100` → 本段贡献 `live = 100`
- 段 2：`index.insert` 返回旧 `Location{len: 100}` → `live = live.saturating_sub(100)` = **0**（本段的 live 是 0，扣不动，额度被丢弃）→ `live += 10` → 本段贡献 `live = 10`

全局 `live_bytes = 100 + 10 = 110`，而真实有效数据只有 **10 字节**。

**后果**：`garbage_ratio = dead / (dead + live)` 被**低估**（分母虚高）→ `maybe_compact()` 触发得比预期晚 → 空间放大比配置的阈值更严重。

**为什么没炸？** 因为高估是"安全方向"的错误：最坏是晚点合并，不会像低估那样导致 `live_bytes -= old.len` 下溢 panic。

**怎么修**（练习 3）：把记账从"每段的局部账"改成"全局账"——`replay_segment` 不要自己 `saturating_sub`，而是把 `(key, 旧长度, 新长度)` 记到一个全局的 `dead_bytes`/`live_bytes` 里统一结算；或者干脆在 `open()` 结束时用"所有段大小之和 − Σ(live 记录长度)"重新算一遍。

### 坑 3：漏掉 `frozen.insert(new_id, ...)`（前文已述）

索引指向新段、句柄表没有它 → 下一次读报 `找不到段 1002`。

### 坑 4：`delete` 里没检查段滚动

`set()` 开头有 `if self.should_roll() { self.roll()?; }`，`delete()` 没有。后果：如果你的工作负载是"大量删除"，活跃段会超过 `SEGMENT_MAX_BYTES` 而不滚动。

这在功能上不致命（段大一点而已），但会让"段大小有上界"这个不变量失效，而增量合并、备份、段级校验都依赖这个不变量。

**修复**（一行）：把 `delete()` 开头也加上滚动检查。

### 坑 5：合并期间的错误处理用了 `let _ =`

```rust
for id in old_ids {
    let _ = fs::remove_file(Self::seg_path(&self.dir, id));
}
```

删不掉旧段（比如 Windows 上句柄没关干净、或者没权限）被**静默忽略**。结果：磁盘空间没回收，`garbage_ratio()` 却被重置为 0 → 引擎以为自己是干净的，再也不会合并 → **空间泄漏**。

生产实现应该把失败的文件记进一个 `pending_delete` 列表，下次启动时重试。

### 坑 6：把回收量当成磁盘变化量

`compact()` 返回的 `reclaimed` 是**记账里的 `dead_bytes`**，不是"磁盘少了多少"。

本项目因为总是全量合并，`59910 - 450 = 59460` 恰好等于 `reclaimed`。但如果将来改成增量合并，两者就会不一致（因为旧段可能没被删、记账可能有偏差）。要做监控的话，直接 `stat` 目录大小更可靠。

### 坑 7：合并是同步的，会阻塞所有请求

`compact(&mut self)` 需要独占访问。在模块六的 `SharedEngine` 里它走的是**写锁**，意味着合并期间所有读请求都在等。

对一个 1 GiB 的库，一次全量合并可能要几秒到几十秒——这在生产上是不可接受的停顿。解法见第 6.4 节。

**更糟的是**：`Engine::set()` 里的内联检查（1.5 节）让这个停顿**出现在普通写入路径上**。客户端视角就是"平时 0.1 ms 的 SET，偶尔卡 3 秒"。

**怎么观测**：用 `Engine::stats().snapshot().compactions` 看合并次数；或者给 `SET` 打点，看 P99/P999 延迟。如果 P99 和 P999 差两个数量级，几乎一定是这个原因。

**修复方向**：把内联检查改成"标记需要合并"，由后台线程真正执行（即 `spawn_compactor` 的做法），或者加最小间隔 + 合并速率限制。

## 6. 性能考量

### 6.1 合并的成本模型

一次全量合并的耗时 ≈

```text
T ≈ N × (一次随机读 + 一次 CRC 计算) + L × (顺序写) + fsync
```

其中 `N` = 索引里的键数，`L` = 有效数据总量。

关键观察：**主导项是 N 次随机读**，不是顺序写。因为：

- 写是顺序的（追加到一个新文件），现代磁盘顺序写 ~500 MB/s；
- 读是随机的（key 按字典序排，而记录在段里按写入顺序排，两者毫无关联），机械盘随机读 ~100 IOPS，SSD ~10 万 IOPS。

`gc_demo` 的合并跑了 20 个键，几乎瞬间完成；但如果键数是 1000 万，即使有 SSD，随机读也会让合并变成分钟级。

### 6.2 优化一：按 offset 排序而不是按 key 排序

**这是本项目最值得做的一个优化**（练习 1）。

如果按 `(seg, offset)` 排序遍历，读取就变成**顺序扫描**——段文件本身就是按写入顺序排的，顺序扫一遍就能拿到所有记录，而且扫描顺序天然满足"后写覆盖先写"的语义，直接用扫描结果覆盖索引即可，**连 `index` 查找都省了**。

代价：合并输出的键顺序变成"按写入顺序"而不是字典序，牺牲了输出的可重现性（可以用"先按 offset 扫描、再按 key 排序写出"两步走，但那就又回到随机读了——不过这时随机读发生在**内存**里，因为值已经读出来了）。

### 6.3 优化二：hint 文件

Bitcask 在合并时顺便写一个 **hint 文件**，里面存 `key → (seg, offset, len)`。下次启动时直接读 hint 建索引，不必扫描数据文件。

代价：hint 文件自己也要保持一致性（写完要 fsync、崩溃要能识别）。收益：启动时间从 O(数据量) 降到 O(键数)，对大库是数量级的提升。

本项目的 `manifest.json` 只存了段列表，没有 hint——这是留给读者的练习（练习 4）。

### 6.4 优化三：增量合并 + 后台线程

不要一次重写全库，而是：

1. 按"垃圾占比"给段排序，选最脏的几个；
2. 只合并这几个段；
3. 合并期间用**读写锁**让读请求继续走旧段，写请求进新活跃段；
4. 合并完成后，用一次极短的写锁切换索引、删除旧段。

RocksDB 的 compaction、Cassandra 的 `SizeTieredCompactionStrategy` 都是这个思路的工业级实现。

本项目的 `spawn_compactor()`（模块六）只做到了"后台定时触发"，合并本身仍然是全量 + 独占的。

### 6.5 写放大

设有效数据量为 `L`，垃圾占比阈值为 `t`，则每次合并要重写约 `L / (1 - t)` 字节（`t = 0.3` 时约 1.43 L）。如果平均每写 `L` 字节就产生足够触发一次合并的垃圾，那么**写放大系数 ≈ 1.43**。

对比：B-tree（如 InnoDB）的写放大来自页分裂和 double-write buffer，通常更高；LSM 的写放大来自多层合并，可能是 `10×` 以上。Bitcask 因为只有一层，写放大是这几种里最低的之一——**代价是必须把全部索引放在内存**。

### 6.6 磁盘峰值占用

合并期间，新旧数据**同时在磁盘上**。全量合并的峰值 ≈ `2 × 有效数据 + 垃圾`。所以：

> 磁盘剩余空间必须大于有效数据量，否则合并会失败。

生产引擎会检查剩余空间，不足时拒绝合并并告警（而不是写到一半报 `ENOSPC`）。

## 8. 练习

1. **（性能）把 `compact()` 改成按 `(seg, offset)` 顺序扫描**而不是按 key 排序随机读。用 10 万个键、`cargo run --release` 对比合并耗时。
2. **（正确性）实现增量合并**：只合并 `frozen` 里垃圾最多的段，并把**墓碑原样搬进新段**。写一个测试：只合并部分段后，被删的键**不能**复活。
3. **（记账）修复 5.2 的 `live_bytes` 高估**：把 `replay_segment` 的局部 `saturating_sub` 改成全局结算，写一个跨段覆盖的测试验证 `garbage_ratio()` 与"1 − 有效字节/总字节"一致。
4. **（启动优化）实现 hint 文件**：合并时写 `<seg>.hint`，`open()` 时优先读它。测启动时间的变化。
5. **（鲁棒性）给 `delete()` 补上段滚动检查**，并加一个"连续删除导致段超限"的测试。
6. **（运维）实现孤儿文件清理**：`open()` 时删除所有 `*.compacting`；再实现 `pending_delete` 列表，让删除失败的旧段在下次启动时重试。
7. **（思考）** 如果合并过程中写入请求不断进来（并发场景），新写的数据应该进哪个段？合并完成后，这段时间写入的记录会丢吗？（提示：看 `compact()` 最后重建活跃段的时刻。）
