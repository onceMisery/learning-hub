> 对应源码：`src/stage3_protocol.rs`、`src/stage7_concurrent.rs`（阻塞服务器）、`src/stage8_async.rs`（异步服务器）、`src/bin/minidb-server.rs`
> 前置：模块三（命令执行）、模块六（并发）

## 1. 要解决的问题与设计权衡

### 1.1 协议层要满足什么

从模块三我们知道引擎提供的是 `get/set/delete/keys` 这类 Rust 函数。要让它能被网络上的客户端访问，中间还差一层**协议**，负责：

1. **编解码**：把字节流 ↔ 结构化命令/响应互相转换；
2. **分帧**：TCP 是字节流，没有消息边界——必须定义"一条命令到哪里结束"；
3. **错误处理**：客户端发来垃圾数据时，回一个错误而不是让连接或进程挂掉；
4. **可扩展**：加一个新命令不能破坏老客户端。

### 1.2 权衡一：文本协议 vs 二进制协议

| | 文本（本项目、Redis RESP、HTTP/1.1） | 二进制（MySQL、gRPC、Kafka） |
|---|---|---|
| 可调试性 | ✅ `nc` + 肉眼就能排查 | ❌ 需要专用工具 |
| 实现成本 | 低 | 高（要处理字节序、版本、对齐） |
| 解析性能 | 慢（要扫描、要分配） | 快（直接 `memcpy` 结构体） |
| 体积 | 大 | 小 |
| 演进 | 容易加字段 | 需要版本号 + 兼容规则 |

本项目选**文本 + 二进制安全的逃生口**：普通命令用文本行，遇到可能含 `\r\n` 的二进制值就用长度前缀（`$<len>\r\n<bytes>\r\n`）。这正是 Redis RESP 的设计。

### 1.3 权衡二：RESP 风格的行协议 vs 完全自定义

本项目的响应编码是 RESP 的简化版：

| 类型 | 编码 | 例子 |
|------|------|------|
| 简单字符串 | `+<text>\r\n` | `+OK\r\n`、`+PONG\r\n` |
| 错误 | `-ERR <msg>\r\n` | `-ERR 协议错误: 未知命令: NOPE\r\n` |
| 整数 | `:<n>\r\n` | `:1\r\n`、`:0\r\n` |
| 批量字符串 | `$<len>\r\n<bytes>\r\n` | `$5\r\nworld\r\n` |
| 空值 | `$-1\r\n` | `$-1\r\n` |
| 数组 | `*<n>\r\n` + n 个元素 | `*1\r\n$4\r\nname\r\n` |

**为什么用 `$<len>` 而不是直接写文本？** 因为 value 是 `Vec<u8>`，**可能包含 `\r\n`**。如果直接写，客户端无法区分"值里的换行"和"响应结束"。长度前缀让协议变成**二进制安全**的。

**为什么不全程二进制？** 因为教学价值：`nc` 连上去敲 `PING` 就能看到 `+PONG`，这种即时反馈对理解系统至关重要。

### 1.4 权衡三：怎么分帧（处理粘包/半包）

TCP 不保留消息边界。客户端发两次 `SET a 1` 和 `SET b 2`，服务端可能一次收到两条（粘包），也可能先收到 `SET a` 的半个（半包）。

| 方案 | 做法 | 本项目 |
|------|------|--------|
| **分隔符** | 读到 `\r\n` 算一条 | ✅ 命令用这个 |
| **长度前缀** | 先读 N 字节的头，得知长度 | ✅ 二进制值用这个 |
| 固定长度 | 每条消息固定 N 字节 | ❌ 浪费且 inflexible |
| 关闭连接表示结束 | 一条连接只发一条 | ❌ 太贵 |

本项目的命令用 `\r\n` 分隔，靠 `BufReader::read_line` / `lines().next_line()` 处理——**半包和粘包由 `BufReader` 自动处理**，这是本项目最省事的设计决策之一。

代价（见坑 3）：**没有长度上限**，一个不发 `\r\n` 的恶意客户端能让服务端内存爆炸。

### 1.5 权衡四：同步服务器 vs 异步服务器

| | 阻塞式（每连接一线程） | 异步（tokio） |
|---|---|---|
| 并发模型 | 1 连接 = 1 OS 线程 | 1 连接 = 1 任务（几百字节状态机） |
| 1 万连接的内存 | ~20 GB（2 MB 栈 × 1 万） | ~几十 MB |
| 上下文切换 | 内核调度，~1~2 μs | 用户态调度，~100 ns |
| 代码复杂度 | 低（顺序写就行） | 高（`async` 传染、不能阻塞） |
| 阻塞 I/O | 随便用 | **绝对禁止** |

本项目**两种都实现了**，这是刻意的教学安排：

- `stage7_concurrent::bind_blocking` —— 阻塞式，代码最好读；
- `stage8_async::bind_async` —— tokio，支持上万连接。

### 1.6 权衡五：异步里怎么访问"会阻塞的引擎"

引擎的 `get` 会做磁盘 I/O（可能几毫秒），`compact` 甚至要几秒。在 tokio 里直接调用会**卡住整个 worker 线程**。

三个方案：

| 方案 | 做法 | 问题 |
|------|------|------|
| `tokio::sync::Mutex` 包引擎 | 像模块六那样加锁 | 磁盘 I/O 仍然发生在 worker 线程上，只是解决了数据竞争，没解决阻塞 |
| `spawn_blocking` | 每次请求丢进阻塞线程池 | 可行，但线程池大小有限，且引擎状态的生命周期不好管 |
| **Actor：专用线程 + channel** | 一个 OS 线程独占引擎，别人发消息 | ✅ 本项目采用 |

**Actor 为什么最合适？**

- 引擎**永远只被一个线程持有** → 根本不需要锁；
- async 侧 `.await` 一个 `oneshot`，**不占住 worker 线程**；
- 引擎不需要是 `Sync`，只要 `Send`（能搬进那个线程）——Rust 的类型系统让这个方案的成本极低。

Java 对照：这就是 Akka/Erlang 的 actor，或者 `Executors.newSingleThreadExecutor()` + `CompletableFuture`。差别是 Rust 用类型系统保证"引擎不会被两个线程同时拿到"。

## 2. 关键数据结构

### 2.1 `Command` —— 代数数据类型

```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub enum Command {
    Set { key: String, value: Vec<u8> },
    Get { key: String },
    Delete { key: String },
    Exists { key: String },
    Keys { prefix: String },
    Ping,
    Compact,
    Quit,
}
```

这是 **ADT 里的和类型**：一个 `Command` 要么是 `Set`，要么是 `Get`，不能同时是多个。Java 17+ 要用 `sealed interface` + 一堆 `record` 才能等价建模。

**为什么这比"一个 Map<String, Object>"好？** 因为 `match` 的**穷尽性是编译期强制**的。加一个新命令后，所有 `match cmd` 的地方都会编译失败，逼你处理好它。Java 里 `switch` 忘了 default 分支要到运行期才炸。

`value: Vec<u8>` 而不是 `String`：KV 存储必须能存任意二进制。Java 里通常用 `byte[]`，但它是可变的——`Vec<u8>` 的所有权语义让"谁拥有这块数据"清晰。

### 2.2 `Response` —— 用 `Option` 消灭 `null`

```rust
pub enum Response {
    Ok,
    Value(Option<Vec<u8>>),   // None = nil（键不存在）
    Bool(bool),
    Keys(Vec<String>),
    Error(String),            // 客户端可见的错误，不是服务崩溃
    Pong,
}
```

`Value(Option<Vec<u8>>)` 值得单独说：

- 外层 `Option` 表示"键不存在"，编码成 `$-1`；
- Java 里这个位置通常是 `null`，客户端 `response.getValue().length` 直接 NPE；
- Rust 里客户端**必须**匹配 `Some/None`，否则编译不过。

`Error(String)` 是**业务错误**而不是异常——它被编码成 `-ERR ...` 回给客户端，连接继续可用（模块六的 `protocol_error_does_not_kill_connection` 测试验证了这点）。

### 2.3 Actor 的消息

```rust
enum Msg {
    ReadOnly(Command, oneshot::Sender<Response>),
    Write(Command, oneshot::Sender<Response>),
    Shutdown,
}

#[derive(Clone)]
pub struct EngineHandle {
    tx: Sender<Msg>,   // std::sync::mpsc::Sender
}
```

- 为什么分成 `ReadOnly` 和 `Write` 两个变体？因为 actor 线程里可以用 `apply_read(&engine, ...)`（只读，不需要 `&mut`）。虽然单线程下没有实际区别，但这个分类保留了"只读命令"的语义，也方便以后改成读写分离。
- `oneshot::Sender<Response>`：每个请求带一个"回信信封"，actor 处理完把响应塞回去。
- `EngineHandle` 内部只有一个 `Sender`，所以它是 `Send + Sync` 的，可以随便 `clone()` 进 `tokio::spawn` 的任务。

## 3. 核心代码路径

### 3.1 解析：`Command::parse`

```rust
pub fn parse(line: &str) -> Result<Self> {
    let mut tokens = tokenize(line);
    let Some(first) = tokens.next() else {
        return Err(KvError::Protocol("空命令".into()));
    };

    match first.to_ascii_uppercase().as_str() {
        "SET" => {
            let key = require(tokens.next(), "SET 缺少 key")?;
            let value = require(tokens.next(), "SET 缺少 value")?;
            Ok(Self::Set { key: key.to_owned(), value: value.as_bytes().to_vec() })
        }
        "GET" => Ok(Self::Get { key: require(tokens.next(), "GET 缺少 key")?.to_owned() }),
        // …
        "KEYS" => Ok(Self::Keys { prefix: tokens.next().unwrap_or("").to_owned() }),
        other => Err(KvError::Protocol(format!("未知命令: {other}"))),
    }
}
```

几个点：

- **`let-else`**（`let Some(first) = … else { return … }`）：Rust 1.65+ 语法。比 `match` 紧凑，且编译器保证后续 `first` 一定有值。
- **`to_ascii_uppercase()`**：命令名大小写不敏感。注意它返回 `String`，所以后面要 `.as_str()`。
- **`require(...)?`**：参数缺失时返回**结构化错误**而不是 panic。它的签名 `fn require<'a>(token: Option<&'a str>, msg: &str) -> Result<&'a str>` 明确写了"返回值的借用来自 `token`"——两个输入都是引用时，编译器无法猜你想返回哪一个，必须写明生命周期。Java 里没有这个概念（GC 管着）。
- **`to_owned()`**：`tokenize` 返回的是**切片**（零拷贝），但 `Command` 要拥有数据（要跨线程、要落盘）。这是 Rust 里最常见的动作：**解析时零拷贝，构造时拿所有权**。
- **`other => Err(...)` 兜底是必须的**：`&str` 有无限种可能，编译器无法证明穷尽。对比：对 `Command` 这种有限 enum 做 `match` 时，编译器**允许你不写兜底**并要求穷尽。

### 3.2 分词：`tokenize`

```rust
fn tokenize(line: &str) -> impl Iterator<Item = &str> {
    // 手写的单趟扫描分词器，支持引号：SET msg "hello world"
    let chars = line.char_indices();
    let mut out: Vec<&str> = Vec::new();
    let mut start: Option<usize> = None;
    let mut in_quotes = false;
    // …
}
```

**为什么不用 `split_whitespace()`？** 因为它不认引号，`SET msg "hello world"` 会被切成三段，`SET` 只拿到 `"hello`。

**注意函数注释里"零分配"的说法要打个折扣**：它确实不为每个 token 分配 `String`（返回的是 `&str` 切片），但内部还是 `Vec::with_capacity` 了——准确说是"**零字符串分配**"。Java 的 `String.split()` 每次都新建一堆 `String`，压力全给 GC。

**已知限制**：引号内部**没有转义**。`SET m "a\"b"` 会在第二个引号处提前结束。要支持的话得处理 `\"`（练习 1）。

### 3.3 编码：`Response::encode`

```rust
pub fn encode(&self) -> String {
    match self {
        Self::Ok => "+OK\r\n".to_owned(),
        Self::Value(Some(v)) => {
            let mut out = format!("${}\r\n", v.len());
            out.push_str(&String::from_utf8_lossy(v));
            out.push_str("\r\n");
            out
        }
        Self::Value(None) => "$-1\r\n".to_owned(),
        Self::Bool(true) => ":1\r\n".to_owned(),
        Self::Keys(keys) => {
            let mut out = format!("*{}\r\n", keys.len());
            for k in keys {
                let _ = fmt::Write::write_fmt(&mut out, format_args!("${}\r\n{k}\r\n", k.len()));
            }
            out
        }
        Self::Error(msg) => format!("-ERR {msg}\r\n"),
        Self::Pong => "+PONG\r\n".to_owned(),
    }
}
```

- `Keys` 里用 `write!` 往 `String` 追加，而不是 `out = out + &format!(...)`——后者每次循环都分配一个新 `String`（≈ Java 里用 `StringBuilder.append` 而不是 `s = s + x`）。
- 返回值是 `String` 而不是写进 `&mut impl Write`：教学版为了简单。生产实现应该写进复用的缓冲区（见 6.2）。

### 3.4 阻塞服务器：`bind_blocking` + `handle_conn`

```rust
fn handle_conn(stream: TcpStream, engine: &SharedEngine) -> Result<()> {
    let mut reader = BufReader::new(stream.try_clone()?);
    let mut writer = stream;
    let mut line = String::new();

    loop {
        line.clear();                       // 复用缓冲区，避免每行都分配
        let n = reader.read_line(&mut line)?;
        if n == 0 { break; }                // 客户端断开
        let resp = engine.apply_line(line.trim_end());
        writer.write_all(resp.encode().as_bytes())?;
        writer.flush()?;
        if matches!(resp, Response::Ok) && line.trim().eq_ignore_ascii_case("QUIT") {
            break;
        }
    }
    Ok(())
}
```

- **`stream.try_clone()`**：同一个 socket 既要读又要写。Rust 要求 `&mut` 才能写，而 `BufReader` 要独占读端，所以 `dup` 出两个句柄。
- **`line.clear()` 在循环开头**：复用同一个 `String` 的缓冲区。100 万条命令只分配一次。
- `read_line` 返回 0 = EOF = 客户端断开。
- `line.trim_end()` 去掉 `\r\n`（`trim_end` 会去掉所有尾部空白，包括空格——对 `KEYS ` 这种"带尾随空格的空前缀"是必要的）。
- **`writer.flush()` 是必须的**。这里 `writer` 是裸 `TcpStream`（不带 `BufWriter`），理论上不需要 flush，但写上是防御性的好习惯——如果哪天有人加了 `BufWriter`，这行就救了你一命。

### 3.5 异步服务器：`EngineHandle::send`

```rust
pub async fn send(&self, cmd: Command) -> Result<Response> {
    let (resp_tx, resp_rx) = oneshot::channel();
    let msg = if is_read_only(&cmd) { Msg::ReadOnly(cmd, resp_tx) } else { Msg::Write(cmd, resp_tx) };

    // 如果 actor 线程已经退出，send 会失败——这是"引擎已关闭"的信号
    self.tx.send(msg).map_err(|_| crate::error::KvError::Closed)?;

    // 这里 await 的是 tokio 的 oneshot，**不会阻塞线程**
    resp_rx.await.map_err(|_| crate::error::KvError::Closed)
}
```

**为什么 `std::sync::mpsc` 的 `send` 不会卡住 reactor？**

因为 `std::sync::mpsc::channel()` 是**无界** channel，`send` 永不阻塞。而且 actor 线程一直挂在 `recv()` 上等着，消息几乎立刻被取走。

⚠️ **这个推理有一个前提**：如果哪天把它换成 `sync_channel(n)`（有界），`send` 就会在队列满时阻塞，然后把 tokio 的 worker 线程卡死。改代码时务必注意。

**`resp_rx.await` 才是关键**：这是 `tokio::sync::oneshot` 的 `await`，任务被挂起、线程让给其他任务——不占 worker。

### 3.6 Actor 线程

```rust
pub fn spawn_engine_actor<P: AsRef<Path>>(dir: P) -> Result<(EngineHandle, JoinHandle<()>)> {
    let dir: PathBuf = dir.as_ref().to_path_buf();
    // 先在**当前线程**打开引擎（这样 open 失败能立刻返回 Err，不用跨线程传错误）
    let engine = Engine::open(&dir)?;
    let (tx, rx) = channel::<Msg>();

    let handle = thread::spawn(move || {
        let mut engine = engine;
        loop {
            match rx.recv() {
                Ok(Msg::ReadOnly(cmd, resp)) => {
                    let r = apply_read(&engine, cmd);
                    let _ = resp.send(r);
                }
                Ok(Msg::Write(cmd, resp)) => {
                    let r = apply(&mut engine, cmd);
                    let _ = resp.send(r);
                }
                Ok(Msg::Shutdown) => {
                    if let Err(e) = engine.close() { log::error!("关闭引擎失败: {e}"); }
                    break;
                }
                Err(_) => break,   // 所有发送端都 drop 了 → 退出
            }
        }
    });

    Ok((EngineHandle { tx }, handle))
}
```

- **先在当前线程 `Engine::open`**：这样打开失败（比如目录被占用）能立刻返回 `Err`，不用设计"跨线程传错误"的机制。这是一个很实用的小技巧。
- `let _ = resp.send(r)`：如果客户端已经断开（oneshot 的接收端被 drop），发送会失败——**忽略即可**，因为没人要这个响应了。客户端侧的 `resp_rx.await` 会得到 `Err` 并转成 `KvError::Closed`。
- `Err(_) => break`：所有 `EngineHandle` 都被 drop 了（程序退出），`recv` 返回错误，actor 退出。

### 3.7 关闭序列

```rust
// src/bin/minidb-server.rs
let (handle, actor_thread) = spawn_engine_actor(&cli.dir)?;
let addr = bind_async(&cli.addr, handle.clone()).await?;
// …
tokio::signal::ctrl_c().await?;          // 等待 Ctrl-C
handle.shutdown();                        // 通知 actor 关闭引擎
let _ = tokio::task::spawn_blocking(move || actor_thread.join()).await;
```

三步缺一不可：

1. `ctrl_c().await` —— `#[tokio::main]` 里 await 信号 future，不阻塞其他任务。≈ Java 的 `Runtime.addShutdownHook()`。
2. `handle.shutdown()` —— 发 `Msg::Shutdown`，让 actor **在它自己的线程里**执行 `engine.close()`（flush + 保存 manifest + 释放 LOCK）。
3. `spawn_blocking(...).await` —— **等** actor 线程真的结束。少了这一步，进程可能在 `close()` 完成前就退出，导致 manifest 没写、LOCK 残留。

`join()` 是阻塞调用，所以在 async 里必须用 `spawn_blocking` 包一层——这正是 1.6 节说的"阻塞 I/O 要隔离"。

## 4. 边界情况清单

| 情况 | 行为 | 评价 |
|------|------|------|
| 空行 | `Err(Protocol("空命令"))` → `-ERR ...` | ✅ |
| 未知命令 | `-ERR 协议错误: 未知命令: NOPE` | ✅ 连接继续可用 |
| 参数缺失（`SET a`） | `-ERR 协议错误: SET 缺少 value` | ✅ |
| 值里含空格（引号包裹） | `SET m "hello world"` ✅ | ✅ `$11\r\nhello world\r\n` |
| 值里含 `\r\n` | 命令侧无法表达（`\r\n` 就是分隔符） | ⚠️ 见坑 1 |
| 二进制值（非 UTF-8） | 命令侧无法表达；响应侧用 `from_utf8_lossy` **会替换成 `U+FFFD`** | ❌ 见坑 2 |
| `KEYS` 不带前缀 | 等价于 `KEYS ""`，返回全部键 | ✅ |
| 键不存在 | `$-1\r\n`（不是错误） | ✅ |
| 客户端断开 | `read_line` 返回 0 → 关闭连接 | ✅ |
| `QUIT` | 阻塞版：回 `+OK` 后断开；异步版：**不支持**，只能靠断开连接 | ⚠️ 见坑 6 |
| 超长行（无 `\r\n`） | 一直读，直到内存耗尽 | ❌ 见坑 3 |
| 引擎已关闭后发命令 | `send` 失败 → `KvError::Closed` | ✅ |

## 5. 常见坑

### 坑 1：命令侧不是二进制安全的

响应侧用 `$<len>` 解决了二进制安全，但**命令侧没有**：`SET` 的 value 是从一行文本里切出来的，无法包含 `\r\n`。

要真正支持二进制值，必须改成 RESP 的数组形式：

```text
*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n
```

这是练习 2。

### 坑 2：`Response::encode` 用 `from_utf8_lossy` 会破坏二进制

```rust
out.push_str(&String::from_utf8_lossy(v));
```

如果 value 不是合法 UTF-8（比如图片），`from_utf8_lossy` 会把非法字节替换成 `U+FFFD`，**但 `$<len>` 里写的还是原始长度**——客户端按长度读，拿到的却是被改写过的字节。

**这是一个真实的数据损坏 bug**。修复：直接写字节而不是转 `String`：

```rust
// 伪代码：encode 应该往 Vec<u8> 里写
out.extend_from_slice(format!("${}\r\n", v.len()).as_bytes());
out.extend_from_slice(v);
out.extend_from_slice(b"\r\n");
```

前提是 `encode()` 的返回类型从 `String` 改成 `Vec<u8>`（练习 3）。

### 坑 3：没有请求大小上限

`read_line` 会一直读到 `\r\n`。一个恶意（或 buggy）客户端发送 10 GB 无换行的数据，服务端会把它们全部读进内存 → OOM。

生产实现必须有：

```rust
const MAX_LINE: u64 = 64 * 1024;
// 用 take(MAX_LINE) 限制读取，或者用 read_until 并检查长度
```

同理还要限制：**单连接数、单连接速率、单命令参数个数**。

### 坑 4：在 async 里做阻塞 I/O

`src/stage8_async.rs` 里有一段注释专门讲这个：

```rust
//     std::thread::sleep(Duration::from_secs(1));       // ❌ 阻塞整个 worker
//     tokio::time::sleep(Duration::from_secs(1)).await; // ✅ 正确
```

同理，`std::sync::Mutex` 在 async 里**跨 `.await` 持锁**是禁止的：任务挂起时锁没释放，另一个任务再拿同一把锁就会**死锁整个线程池**。

正确做法三选一：
1. 缩短临界区，不在持锁时 `.await`；
2. 用 `tokio::sync::Mutex`；
3. 用消息传递（本项目的 Actor 方案）。

### 坑 5：忘记 `flush`

`writer.write_all(...)` 之后必须 `flush()`。tokio 的 `write_all` 也是先写进缓冲。

### 坑 6：异步版不处理 `QUIT`

阻塞版有这段：

```rust
if matches!(resp, Response::Ok) && line.trim().eq_ignore_ascii_case("QUIT") { break; }
```

`handle_conn`（async 版）里**没有**——`QUIT` 会返回 `+OK` 然后继续循环，直到客户端断开连接才退出。功能上不算致命（客户端会自己关），但协议不一致会让测试困惑。

### 坑 7：`is_read_only` 在两个文件里各写了一遍

`stage7_concurrent.rs` 和 `stage8_async.rs` 各有一个一模一样的 `fn is_read_only`。这是**重复代码**，改一个忘一个就会行为不一致。

修复：抽到 `stage3_protocol.rs` 里，做成 `Command::is_read_only(&self)` 方法。注意 `stage3_protocol.rs:296` 已经有一个类似的判断（`Command::Set {..} | Delete {..} | Compact => true`，语义是"需要写锁"）——**三处逻辑应该合并成一个**。

### 坑 8：无界 channel 没有背压

`channel::<Msg>()` 是无界的。如果客户端发请求的速度超过 actor 处理速度（比如全是磁盘 I/O），消息队列会无限增长 → 内存爆炸，且延迟越来越高但**没有任何信号告诉客户端"我忙不过来了"**。

生产实现应该用 `sync_channel(N)`（有界）+ 超时，满时返回 `-ERR busy`。但注意坑：有界 channel 的 `send` 会阻塞（见 3.5）。

## 6. 性能考量

### 6.1 每连接一线程的内存成本

| 连接数 | 线程栈（默认 2 MB 虚拟内存） | 实际提交物理内存 |
|--------|---------------------------|-----------------|
| 1 000 | 2 GB 虚拟 | ~几十 MB（栈按需提交） |
| 10 000 | 20 GB 虚拟 | ~几百 MB |
| 100 000 | 200 GB 虚拟 | ❌ 线程表/调度器先撑不住 |

虚拟内存不是主要问题，**调度开销**才是：1 万个线程在内核里来回切换，光上下文切换就吃掉了大部分 CPU。

tokio 的任务是**用户态状态机**（几百字节），1 万个连接的总开销是几十 MB，调度是用户态的（~100 ns vs ~1~2 μs）。

### 6.2 每次响应都分配一个 `String`

`Response::encode()` 返回 `String`，意味着每条响应至少一次堆分配。在 10 万 QPS 下这是 10 万次/秒的分配 + 释放。

**优化**：让 `encode` 写进一个复用的缓冲区：

```rust
pub fn encode_into(&self, buf: &mut Vec<u8>) {
    buf.clear();
    match self { /* … */ }
}
```

连接处理循环里持有这个 `buf`，每次复用。这是 Redis、Nginx 等高性能服务器的标准做法。

### 6.3 零拷贝的机会

当前路径上每个请求有这些拷贝：

```text
socket → BufReader 缓冲 → line: String → tokenize 切片 → Command 的 String/Vec（to_owned）
                                                        → Response::encode 的 String → socket
```

可以省掉的：

1. `line` 的 `String` → 用 `BytesMut` + 引用计数，命令解析完直接归还；
2. `encode` 的 `String` → 6.2 的复用缓冲；
3. 大 value 的 `to_vec()` → 用 `Bytes` 做引用计数共享（Redis 的 `robj` 也是这个思路）。

但要注意：**过早优化会毁掉代码的可读性**。对教学项目，先把 2 做了（收益最大、改动最小）。

### 6.4 流水线（pipelining）

当前是"读一条 → 处理 → 写回 → 读下一条"的严格串行。客户端可以在一个 RTT 里发 10 条命令，服务端一次 `read` 拿到全部——`BufReader` 会自动把它们拆开，但**响应是一条一条写回的**，多占了缓冲区。

更好：一次读完缓冲区里所有完整的行，批量处理，批量写回。Redis 的 pipeline 就是这个优化，能把 QPS 提升 5~10 倍（网络往返是主要成本时）。

### 6.5 引擎才是瓶颈，不是协议

做完上面所有优化之前，请先测量：**单次 `GET` 的成本主要是磁盘 I/O + CRC + 锁竞争**，协议解析通常只占个位数百分比。

用 `cargo test --release -- --ignored --nocapture` 跑 `write_throughput_smoke`，再对比 `nc` 压测的 QPS，就能知道时间花在哪。

## 7. 动手验证

### 7.1 起服务器，用真实客户端观察协议

```bash
cargo build --release --bin minidb-server
./target/release/minidb-server.exe --dir /tmp/srvdemo --addr 127.0.0.1:6399
```

另开一个终端，用任何 TCP 客户端（`nc`、`telnet`、Python `socket` 都行）逐条发送。实测结果：

```text
>>> PING
<<< '+PONG\r\n'

>>> SET name "minidb server"
<<< '+OK\r\n'

>>> GET name
<<< '$13\r\nminidb server\r\n'

>>> EXISTS name
<<< ':1\r\n'

>>> KEYS
<<< '*1\r\n$4\r\nname\r\n'

>>> DEL name
<<< '$13\r\nminidb server\r\n'

>>> GET name
<<< '$-1\r\n'

>>> NOPE
<<< '-ERR 协议错误: 未知命令: NOPE\r\n'

>>> SET k2 v2
<<< '+OK\r\n'
```

几个值得核对的点：

- **`SET name "minidb server"` 成功**：引号内的空格被保留，值长度 13。这验证了 `tokenize` 的引号处理。
- **`GET name` 返回 `$13`**：`minidb server` 正好 13 字节，长度前缀和实际内容对得上。
- **`DEL name` 返回 `$13\r\nminidb server\r\n`**：删除返回**被删掉的值**（≈ Java `Map.remove`）。
- **删除后 `GET` 返回 `$-1`**：nil，不是错误。
- **未知命令返回 `-ERR` 后连接依然可用**：最后一条 `SET k2 v2` 仍然成功。

顺带观察数据目录，你会发现最后一步触发了一次合并（模块四 1.5 讲的内联检查）：

```text
$ ls /tmp/srvdemo
000001002.log   000001003.log   LOCK   manifest.json

$ cat /tmp/srvdemo/manifest.json
{"version":1,"active_id":1003,"frozen":[1002]}
```

一个"只写了两条记录"的库，段 id 已经跳到 1002/1003——这就是 `compact()` 里 `new_id = active_id + 1 + 1000` 的效果。

### 7.2 用 `--exec` 单命令模式（不用起服务器）

```bash
cargo run --bin minidb-cli -- --dir /tmp/cli --exec "SET a 1"
cargo run --bin minidb-cli -- --dir /tmp/cli --exec "GET a"
cargo run --bin minidb-cli -- --dir /tmp/cli --exec "KEYS "
```

### 7.3 跑通服务器测试

```bash
cargo test --lib stage7_concurrent::tests::tcp_server_roundtrip
# test stage7_concurrent::tests::tcp_server_roundtrip ... ok

cargo test --lib stage8_async

```

`async_server_roundtrip` 是一个完整的端到端测试：起 actor + 起服务器 + 用 `TcpStream` 连进去 + 走一遍协议。

### 7.4 验证 Ctrl-C 优雅关闭

启动服务器，发几条命令，然后按 `Ctrl-C`：

```text
^C
INFO  engine actor 线程退出
```

观察数据目录：`LOCK` 应该被删除（说明 `Drop` 正常跑了），`manifest.json` 应该是新的。

如果 `LOCK` 还在，说明关闭路径有问题——回头看 3.7 的三步是不是少了 `spawn_blocking(join)`。

## 8. 练习

1. **（协议）给 `tokenize` 加转义支持**：让 `SET m "a\"b"` 能正确解析。注意要同时处理 `\\`。
2. **（协议）实现 RESP 风格的多段请求**：把命令侧也改成 `*3\r\n$3\r\nSET\r\n...`，让 value 支持任意二进制。这是同时解决坑 1 的必要改动。
3. **（正确性）修复坑 2**：把 `Response::encode` 的返回类型改成 `Vec<u8>`，去掉 `from_utf8_lossy`。写一个测试：存入 `vec![0xFF, 0xFE]`，取回的字节必须完全相同。
4. **（健壮性）修复坑 3**：给 `handle_conn` 加行长度上限（比如 64 KiB），超了就回 `-ERR line too long` 并关闭连接。
5. **（重构）修复坑 7**：把三处 `is_read_only` 合并成 `Command::is_read_only()` 方法。
6. **（运维）实现背压**（坑 8）：把 channel 换成 `sync_channel(1024)`，满时返回 `-ERR busy`。注意 `send` 会阻塞，要用 `try_send` 或者放在 `spawn_blocking` 里。
7. **（性能）实现 6.2 的缓冲区复用**：把 `encode()` 改成 `encode_into(&mut Vec<u8>)`，用 `criterion` 测一下分配次数的变化。
8. **（性能）实现流水线**（6.4）：一次读多条命令批量处理，压测对比 QPS。
9. **（思考）** Actor 方案下，`compact()`（可能耗时几秒）会让所有请求排队。你会怎么解决？（提示：把合并也拆成消息；或者让合并"让出"——每处理 N 条记录就检查一次队列。）
