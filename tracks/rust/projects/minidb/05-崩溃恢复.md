## 1. 要解决的问题与设计权衡

### 1.1 崩溃不是异常，是常态

写存储引擎时，"程序会不会崩"不是一个问题——**它一定会崩**。要区分的是崩的方式：

| 崩溃类型 | 数据在哪 | 后果 |
|---------|---------|------|
| **进程崩溃**（panic、`kill -9`、OOM） | 用户态缓冲区 | OS 会回收进程内存；**已经 `write()` 的数据在内核 page cache 里，不丢** |
| **整机断电 / 内核 panic** | 内核 page cache | 没有 `fsync` 的数据**会丢** |
| **磁盘满（ENOSPC）** | — | 写入返回错误，但已有数据可能处于半写状态 |
| **介质损坏 / 位翻转** | 已落盘的扇区 | 只能靠**校验和**发现，无法自动修复 |
| **文件系统元数据损坏** | 目录项 | 文件"消失"或长度不对，需要扫描重建 |

好的设计不是"避免崩溃"，而是**让每一种崩溃都有一个确定的、可接受的结果**。本模块的全部内容就是这件事。

### 1.2 两个不同的目标

- **持久性（Durability）**：已经**确认成功**的写入，崩溃后还在。
- **可恢复性（Recoverability）**：崩溃后引擎**能重新打开**，即使丢了一部分数据，也不能"整个库不可用"。

这两个目标经常冲突。比如：一个严格保证持久性的引擎，在发现任何不一致时拒绝启动（fail-fast），可恢复性就差；一个总是能启动的引擎，可能悄悄丢数据，持久性就差。

**本项目的取舍**：优先保证可恢复性——遇到损坏就**截断到最后一个完整帧**，宁可丢掉尾部数据也要能起来。

### 1.3 权衡一：fsync 的频率

`write()` 返回只意味着"数据交给了内核"，不意味着"数据在磁盘上"。中间隔着：

```text
用户态缓冲(BufWriter) → 内核 page cache → 磁盘控制器缓存 → 盘片
       flush()              fsync()            FUA/屏障
```

| 档位 | 做法 | 进程崩溃 | 断电 | 吞吐 |
|------|------|---------|------|------|
| 0 | 只 `write()` | ✅ 不丢 | ❌ 丢几秒 | 最高 |
| 1 | 定时 `fsync`（如每秒） | ✅ | ⚠️ 丢 1 秒 | 高 |
| 2 | **每次写都 `fsync`** | ✅ | ✅ 不丢 | 低（HDD 上 ~100 倍差距） |
| 3 | 每次写 `fsync` + 电池/UPS + 禁用磁盘缓存 | ✅ | ✅ | 最低 |

**本项目在档位 0~1 之间**：`set()` / `delete()` **完全不 fsync**，只在三个时机 `sync_all()`：

```rust
fn roll(&mut self) -> Result<()> {
    self.active_writer.sync_all()?;   // 段滚动时
    // …
}
pub fn compact(&mut self) -> Result<u64> {
    self.active_writer.sync_all()?;   // 合并前
    // …
}
impl Drop for SegmentEngine {
    fn drop(&mut self) {
        if let Err(e) = self.active_writer.sync_all() { /* … */ }  // 关闭时
    }
}
```

**这意味着**：进程崩溃不丢数据（内核还在），但**断电会丢失"上次 fsync 之后的所有写入"**。对一个教学项目这是合理的（代码简单、性能好）；对生产系统，至少要提供"每次写 fsync"的可配置项（见 6.3）。

注意 `Drop` 里的 fsync **只能记日志不能返回错误**——因为 `drop()` 没有返回值。这就是为什么还要有显式的 `close(self) -> Result<()>`：**优雅关闭要能报错，兜底关闭只能尽力而为**。Java 里 `try-with-resources` 的 `close()` 能抛异常，但 `finalize()` 也不能——同样的道理。

### 1.4 权衡二：重放 vs 检查点

崩溃后怎么重建内存索引？

| 方案 | 做法 | 启动时间 | 复杂度 |
|------|------|---------|--------|
| **重放日志**（本项目） | 扫描所有段，逐帧填索引 | O(数据量) | 低：逻辑只有一层 |
| 检查点 + 增量重放 | 定期把索引快照落盘，只重放快照之后的日志 | O(增量) | 中：需要 LSN、需要处理"快照写了一半" |
| **ARIES**（MySQL/PostgreSQL） | undo/redo + LSN + 模糊检查点 | O(增量) | 高：三阶段恢复（分析/重做/撤销） |

**为什么 Bitcask 可以用最笨的重放？** 三个原因：

1. **日志就是数据**，不是"数据的变更记录"——没有"重做"这一步，扫描一遍自然得到最新状态。
2. **没有事务**，所以不需要 undo——不存在"执行了一半需要回滚的事务"。
3. **只有一层**，没有多层合并，所以重放是线性的。

对比 InnoDB：它的 redo log 记录的是"页的物理修改"，必须配合数据页 + LSN + 事务状态才能恢复，所以 ARIES 那套复杂度是**必需的**。理解这一点，比记住 ARIES 的三个阶段更有价值。

代价是**启动时间随数据量线性增长**。位翻转/扫描优化见模块一和 6.1。

### 1.5 权衡三：发现损坏之后怎么办？

`read_frame_at` 返回 `Err(Corrupted)` 时，有三种选择：

| 选择 | 后果 |
|------|------|
| 拒绝启动 | 最安全，但整个库不可用 ❌ |
| **截断到坏点**（本项目） | 坏点之后全部丢失，但引擎能起来 ✅ |
| 跳过坏帧、继续 | 听起来最好，但**变长帧做不到** ❌ |

**为什么"跳过"做不到？** 帧是变长的：

```text
[MDB1][key_len][val_len][key][value][crc32]
```

如果 `val_len` 那 4 个字节本身就是被损坏的（比如从 6 变成 60000），你根本不知道这条记录有多长，也就**不知道下一条记录从哪个字节开始**——无法重新同步（resync）。

对比：MySQL 的 binlog、Kafka 的消息都有魔数 + 长度，**理论上**可以扫描下一个魔数来 resync，但那样可能"同步"到某个 value 内容里恰好出现的魔数字节上，反而制造出假记录。Kafka 的 `log scanner` 就是在"跳过"和"截断"之间做了很多工程权衡。

**本项目选截断**，代价是：`recovery_demo` 的场景 B 实测——第 3 条记录坏了，第 4、5 条也一起没了。

### 1.6 权衡四：目录锁怎么实现

两个进程同时打开同一个数据目录会怎样？两个 `active_writer` 同时 append、两套索引、两个 `compact()`
同时删文件——结果是数据损坏。必须互斥。

| 方案 | 实现 | 崩溃后 |
|------|------|--------|
| `LOCK` 文件 + `create_new(true)`（本项目） | 创建成功 = 拿到锁 | **锁残留**，必须人工删除 |
| `LOCK` 文件 + 写 pid，启动时检查 pid 存活 | 同上 + 检查 | 可自动恢复（pid 复用时有误判风险） |
| OS 级 `flock` / `LockFileEx` | `fs2` crate | **内核自动释放**，最可靠 |
| 都不做 | — | 静默损坏 |

本项目用最简单的第一种，示例里场景 D 会演示它的行为。生产应该用 `flock`（模块一坑 1 也提过）。

## 2. 关键数据结构

### 2.1 `KvError::Corrupted` —— 携带"截断点"

```rust
#[error("数据文件损坏: {reason}（已截断到 offset {truncated_at}）")]
Corrupted {
    reason: String,
    truncated_at: u64,
},
```

这个设计的关键在于：**错误不只是"出错了"，还携带了"错在哪、可以安全恢复到哪"**。

`truncated_at` 是"最后一个完整帧的结束偏移"——恢复逻辑拿到它就知道该 `set_len(truncated_at)`。

对比 Java 的 `throw new IOException("file corrupted")`：所有信息都挤在一个字符串里，调用方只能靠解析文本或者放弃处理。这是 Rust 错误设计的典型优势：**错误是结构化数据，可以被程序消费**。

`reason` 则给人看：

```text
长度不足，需要 24 字节 @ offset 22，实际只有 23 字节
校验和不匹配
魔数不匹配: [0, 0, 0, 0]
```

### 2.2 `Frame` —— 解码结果

```rust
pub struct Frame {
    pub key: String,
    pub value: Option<Vec<u8>>,   // None = 墓碑
    pub consumed: u64,            // 这一帧总共占多少字节
}
```

`consumed` 是重放循环的"步进量"：`pos += f.consumed`。没有它，调用方就要自己算 `12 + key_len + val_len + 4`，而算错一步就会错位——**把长度信息作为解码结果的一部分返回**，是避免这类 bug 的好习惯。

`value: Option<Vec<u8>>` 用 `None` 表示墓碑，让"忘记处理删除"变成编译期的 `Option` 检查而不是运行时的逻辑错误。

### 2.3 `Manifest` 与 `LOCK`

```rust
const MANIFEST_VERSION: u32 = 1;

#[derive(Debug, Serialize, Deserialize)]
struct Manifest {
    version: u32,       // 格式版本，不匹配就拒绝加载（≈ serialVersionUID）
    active_id: u64,     // 当前活跃段 id
    frozen: Vec<u64>,   // 已冻结的只读段 id（应升序）
}
```

**Manifest 是"加速启动的缓存"，不是数据的真相。** `recovery_demo` 的场景 C 会证明：删掉它，数据一样能恢复（靠扫描目录）。

这个定位决定了 manifest 的所有设计：

- 它**可以丢**（丢了能重建）；
- 但它**不能骗人**（如果它指向一个不存在的段，就会静默丢数据——见坑 1）；
- 写入必须原子（tmp + rename）。

## 3. 核心代码路径

### 3.1 `open()` 的恢复流程

```rust
pub fn open(dir: impl AsRef<Path>) -> Result<Self> {
    let dir = dir.as_ref().to_path_buf();
    fs::create_dir_all(&dir)?;                                    // ①

    let lock = OpenOptions::new().write(true).create_new(true)
        .open(dir.join("LOCK")).map_err(|e| {                     // ②
            if e.kind() == io::ErrorKind::AlreadyExists {
                KvError::Protocol(format!("数据目录已被占用: {}", dir.display()))
            } else {
                KvError::Io(e)
            }
        })?;

    let manifest = Self::load_manifest(&dir)?;                    // ③

    let mut frozen = BTreeMap::new();
    let mut index: HashMap<String, Location> = HashMap::new();
    let mut dead_bytes = 0u64;
    let mut live_bytes = 0u64;

    for seg_id in manifest.frozen.iter().copied() {               // ④
        let path = Self::seg_path(&dir, seg_id);
        let file = File::open(&path)?;
        let (d, l) = replay_segment(&file, seg_id, &mut index, &path)?;
        dead_bytes += d;
        live_bytes += l;
        frozen.insert(seg_id, file);
    }

    let active_path = Self::seg_path(&dir, manifest.active_id);   // ⑤
    let active_file = OpenOptions::new().create(true).read(true).append(true)
        .open(&active_path)?;
    let active_clone = active_file.try_clone()?;
    let (d, l) = replay_segment(&active_clone, manifest.active_id, &mut index, &active_path)?;
    dead_bytes += d;
    live_bytes += l;
    let active_pos = active_clone.metadata()?.len();              // ⑥

    Ok(Self { /* … */ })
}
```

| 步 | 关键点 |
|---|--------|
| ① | `create_dir_all` 是幂等的：目录已存在不报错。这让 `open()` 同时承担"创建"和"打开"两个语义 |
| ② | `create_new(true)` = `O_CREAT \| O_EXCL`，**原子**的"不存在才创建"。这是文件锁的经典技巧 |
| ③ | 见 3.2 |
| ④ | **按 `manifest.frozen` 的顺序**重放。顺序至关重要：段必须按 id 升序，后写的段才能覆盖先写的段 |
| ⑤ | 活跃段用 `create(true)` 打开——**文件不存在就创建**。这既支持首次启动，也埋了一个坑（见坑 1） |
| ⑥ | **在重放之后**才取长度。这是对的：重放可能截断了尾部，`metadata().len()` 必须反映截断后的真实长度，否则下一条记录会写在垃圾后面，中间留下一个空洞 |

第 ⑥ 步的顺序是最容易写错的地方之一。如果写成：

```rust
let active_pos = active_file.metadata()?.len();   // ❌ 先取长度
replay_segment(&active_clone, …)?;                // 再重放（可能截断）
```

那么崩溃恢复后 `active_pos` 会比真实文件长度大，新记录被写在一个"洞"后面，段文件中间出现一段垃圾——下次重放读到那里就会报 `魔数不匹配` 并**把洞之后的所有数据一起截掉**。

### 3.2 `load_manifest`：两条分支

```rust
fn load_manifest(dir: &Path) -> Result<Manifest> {
    let path = dir.join("manifest.json");
    if path.exists() {
        let file = File::open(path)?;
        let m: Manifest = serde_json::from_reader(BufReader::new(file))?;
        if m.version != MANIFEST_VERSION {
            return Err(KvError::Corrupted { /* … */ });
        }
        return Ok(m);
    }

    // 目录里已有 .log 但没有 manifest → 扫描文件名推断段 id
    let mut ids: Vec<u64> = fs::read_dir(dir)?
        .filter_map(std::result::Result::ok)
        .filter_map(|e| {
            let name = e.file_name().to_string_lossy().into_owned();
            name.strip_suffix(".log")?.parse::<u64>().ok()
        })
        .collect();
    ids.sort_unstable();
    let active_id = ids.pop().unwrap_or(1);
    Ok(Manifest { version: MANIFEST_VERSION, active_id, frozen: ids })
}
```

分支一（有 manifest）：直接反序列化，先校验 `version`。版本不匹配直接拒绝，避免"用 V2 的代码去解释 V1 的字段"这种灾难。

分支二（无 manifest）：扫描目录，把所有能被解析成 `u64` 的 `.log` 文件名收集起来，**排序后取最大值当活跃段**，其余当冻结段。

几个细节：

- `strip_suffix(".log")?.parse::<u64>().ok()`：用 `?` 和 `ok()` 把"不是 .log"和"解析失败"都静默跳过。这也顺带忽略了 `*.log.compacting`（后缀是 `.compacting`，`strip_suffix(".log")` 失败）——正是这个特性让崩溃留下的半成品不会被当成段。
- `unwrap_or(1)`：空目录时活跃段从 1 开始。
- **注意这条分支的重要性**：它让"manifest 丢失"变成一个可恢复的故障，而不是致命错误。`recovery_demo` 场景 C 验证了这一点。

### 3.3 `replay_segment`：恢复的主循环

```rust
fn replay_segment(
    file: &File,
    seg_id: u64,
    index: &mut HashMap<String, Location>,
    path: &Path,
) -> Result<(u64, u64)> {
    let len = file.metadata()?.len();
    let mut pos = 0u64;
    let mut dead = 0u64;
    let mut live = 0u64;

    while pos < len {
        match frame::read_frame_at(file, pos) {
            Ok(f) => {
                let loc = Location { seg: seg_id, offset: pos, len: f.consumed };
                if f.value.is_some() {
                    if let Some(old) = index.insert(f.key, loc) {
                        dead += old.len;
                        live = live.saturating_sub(old.len);
                    }
                    live += f.consumed;
                } else {
                    if let Some(old) = index.remove(&f.key) {
                        dead += old.len;
                        live = live.saturating_sub(old.len);
                    }
                    dead += f.consumed;
                }
                pos += f.consumed;
            }
            Err(KvError::Corrupted { truncated_at, .. }) => {
                log::warn!("段 {seg_id} 在 offset {truncated_at} 处损坏，已截断");
                let writable = OpenOptions::new().write(true).open(path)?;
                writable.set_len(truncated_at)?;
                writable.sync_all()?;
                break;
            }
            Err(e) => return Err(e),
        }
    }
    Ok((dead, live))
}
```

**循环不变式**：`pos` 永远指向一个"帧的边界"。成立的原因是初始 `pos = 0`，且每次只前进 `f.consumed`（一个完整帧的长度）。一旦某次解码失败，不变式被破坏且无法恢复，所以直接 `break`。

**两个分支的语义**：

- 普通记录：`index.insert(key, loc)`。`HashMap::insert` 返回旧值——这正是"覆盖"的语义，**新值自然覆盖旧值**，因为段是按 id 升序重放的。
- 墓碑：`index.remove(&key)`。删除在重放时是"从索引里抹掉"，而不是"标记"。

**损坏分支的三个动作**：

1. `log::warn!`——恢复是"悄悄丢数据"的操作，**必须留下痕迹**。生产系统应该把这个事件计数并告警。
2. `set_len(truncated_at)`——把半截帧剁掉。
3. `break`——不再尝试继续（1.5 节讲过为什么）。

**为什么要用 `OpenOptions::new().write(true).open(path)` 重新打开一个句柄？**

因为段文件平时是**只读**打开的（`File::open`），而 `set_len` 需要写权限。在 Linux 上，只读写模式下 `ftruncate` 会失败（`EINVAL`）；在 Windows 上会报 `PermissionDenied (os error 5)`。所以必须临时换一个可写句柄。

这个坑在跨平台开发时特别烦人：Linux 上可能"碰巧"能过（取决于打开方式），Windows 上必炸。

另外注意 `write(true)` **不带** `truncate(true)`——`OpenOptions` 默认是追加/覆盖到已有内容，不会清空文件。如果手滑加了 `.truncate(true)`，打开文件的一瞬间整个段就没了。

### 3.4 关闭：`close()` 与 `Drop`

```rust
pub fn close(self) -> Result<()> {
    self.active_writer.sync_all()?;
    self.save_manifest()?;
    drop(self);
    Ok(())
}

impl Drop for SegmentEngine {
    fn drop(&mut self) {
        if let Err(e) = self.active_writer.sync_all() {
            log::error!("关闭时 sync 失败: {e}");
        }
        drop(self.lock.take());                       // 先关句柄
        let _ = fs::remove_file(self.dir.join("LOCK")); // 再删文件
    }
}
```

`close(self)` **消费所有权**——调用之后你手上就没有这个引擎了，编译器保证不会出现 use-after-close。Java 里 `close()` 之后还能继续用对象（然后得到一个 `IOException: Stream closed`）。

`Drop` 里的顺序很重要：

```rust
drop(self.lock.take());                        // ① 关闭文件句柄
let _ = fs::remove_file(self.dir.join("LOCK")); // ② 删除文件
```

**Windows 不允许删除一个仍被打开的文件**（Linux 可以）。顺序反了就会得到 `PermissionDenied`，锁文件残留，下次启动打不开。`Option::take()` 把 `File` 移出（同时获得所有权）、`drop()` 立刻关闭它——这正是 `lock: Option<File>` 这个看起来多余的包装存在的理由（模块一讲过）。

### 3.5 `save_manifest` 的原子写

```rust
fn save_manifest(&self) -> Result<()> {
    let m = Manifest { /* … */ };
    let tmp = self.dir.join("manifest.json.tmp");
    {
        let mut f = BufWriter::new(File::create(&tmp)?);
        serde_json::to_writer(&mut f, &m)?;
        f.flush()?;
        f.get_ref().sync_all()?;
    } // ← f 离开作用域，Drop 自动关闭文件（≈ try-with-resources）
    fs::rename(tmp, self.dir.join("manifest.json"))?;
    Ok(())
}
```

标准配方：**写临时文件 → flush → fsync → rename**。

- `flush()` 把 `BufWriter` 的用户态缓冲交给内核；
- `sync_all()` 确保落盘；
- `rename` 原子替换。

崩溃时：要么看到旧的 manifest，要么看到新的，**绝不会看到写了一半的 JSON**。

**缺失的一步**：rename 之后应该 `fsync` **父目录**。否则在某些文件系统（ext4 默认 `data=ordered`）上，崩溃后可能出现"目录项没更新"——文件是新的但目录还是旧的。生产代码要补：

```rust
fs::rename(&tmp, &final_path)?;
if let Ok(d) = File::open(&self.dir) { let _ = d.sync_all(); }  // fsync 目录
```

## 4. 崩溃矩阵：每个时刻断电会发生什么

这张表是本章的核心，建议你照着源码一行一行对。

| # | 崩溃时刻 | 磁盘状态 | 重开结果 |
|---|---------|---------|---------|
| 1 | `set()` 之前 | 无变化 | ✅ 无影响 |
| 2 | `write_all()` 写了一半 | 尾部半帧 | ✅ 截断，之前的数据都在 |
| 3 | `write_all()` 完成，未 `sync` | 数据在 page cache | ✅ 进程崩溃不丢；⚠️ 断电丢失 |
| 4 | `roll()` 中：`frozen.insert` 后、`save_manifest` 前 | 新段文件已建（空），manifest 还是旧的 | ✅ 回退到旧活跃段；新段文件残留（空） |
| 5 | `roll()` 中：新段已写入数据、`save_manifest` 前 | 新段有数据，manifest 还是旧的 | ⚠️ **新段数据被忽略**（manifest 没登记它）。文件残留 |
| 6 | `compact()`：写临时文件中 | `*.compacting` 残留 | ✅ 旧数据完好，临时文件是垃圾 |
| 7 | `compact()`：rename 后、删旧段前 | 新旧段都在，manifest 还是旧的 | ⚠️ **见坑 1：会丢失全部数据** |
| 8 | `compact()`：删完旧段、`save_manifest` 前 | 只有新段，manifest 还是旧的 | ⚠️ **见坑 1：会丢失全部数据** |
| 9 | `compact()`：`save_manifest` 后 | 全新状态 | ✅ 正常 |
| 10 | `save_manifest`：写 tmp 中 | manifest.json.tmp 残留 | ✅ 旧 manifest 有效 |
| 11 | `save_manifest`：rename 后、fsync 目录前 | 新 manifest 已就位 | ✅ 通常正常（极端情况见 3.5） |
| 12 | 任意时刻 + 介质位翻转 | 某个扇区内容变了 | ⚠️ CRC 检出 → 从坏点截断（1.5 节） |

第 7、8 行是本项目的**真实缺陷**，下面详细说。

## 5. 常见坑

### 坑 1（严重）：`compact()` 在删除旧段之后才保存 manifest

看 `compact()` 的最后几步：

```rust
fs::rename(&tmp_path, &final_path)?;                 // ① 新段就位

for id in old_ids {
    let _ = fs::remove_file(Self::seg_path(&self.dir, id));   // ② 删掉所有旧段
}
let _ = fs::remove_file(Self::seg_path(&self.dir, old_active));

self.frozen.insert(new_id, File::open(&final_path)?);          // ③ 内存状态更新
let fresh_id = new_id + 1;
self.active_writer = /* 打开新活跃段 */;
self.active_id = fresh_id;
self.index = new_index;

self.save_manifest()?;                                          // ④ 最后才落盘
```

如果在 ② 之后、④ 之前断电：

- 磁盘上：新段 `000001002.log` **完整存在**（450 字节有效数据），旧段**已被删除**；
- `manifest.json` 里写着：`active_id = 1, frozen = []`（旧的）；
- 重开时：`open()` 读旧 manifest → 打开 `000000001.log`，而它是用 **`create(true)`** 打开的 → **文件不存在，于是创建一个空文件**；
- 新段 `000001002.log` 存在，但 manifest 没登记它 → **被完全忽略**；
- 结果：**数据全没了，而且没有报错**。

这是最糟糕的一类 bug：静默数据丢失。

**修复**：把 `save_manifest()` **移到删除旧段之前**：

```rust
fs::rename(&tmp_path, &final_path)?;

// ↓ 先把"新状态"落盘，再去动旧文件
self.frozen.clear();
self.frozen.insert(new_id, File::open(&final_path)?);
let fresh_id = new_id + 1;
self.active_writer = /* 打开新活跃段 */;
self.active_id = fresh_id;
self.save_manifest()?;          // ← 关键：先持久化

// ↓ 现在删旧段就安全了：manifest 已经指向新段
for id in old_ids { let _ = fs::remove_file(…); }
let _ = fs::remove_file(Self::seg_path(&self.dir, old_active));
```

这样崩溃后：manifest 指向新段 → 重开正常；旧段可能残留 → 变成孤儿文件，需要在 `open()` 时清理（manifest 里没列的 `.log` 文件都是孤儿）。

**这个坑的通用教训**：任何"删除旧数据"的操作，都必须在"新数据的元数据已持久化"**之后**执行。这条规则在 `save_manifest` 的 tmp+rename、`compact` 的临时文件、`roll` 的顺序里反复出现。

### 坑 2：活跃段用 `create(true)` 打开，会掩盖"段不存在"

```rust
let active_file = OpenOptions::new().create(true).read(true).append(true).open(&active_path)?;
```

`create(true)` 让"首次启动"和"打开已有段"共用一行代码，但也让"manifest 说有个段、实际没有"变成**静默创建空文件**而不是报错。

更安全的做法是让 manifest 的 `active_id` 对应的文件必须存在，不存在就报 `Corrupted`——把"数据丢了"变成"启动失败并明确报错"，而不是"启动成功但库是空的"。

### 坑 3：`manifest.frozen` 的顺序没有被校验

代码注释写着 `/// 已冻结的只读段 id（升序）`，但 `load_manifest` 读出来之后**没有排序、也没有校验**。

如果 manifest 因某种原因写成了 `[3, 1, 2]`，重放顺序就错了——段 1 的记录会覆盖段 3 的记录，恢复出**错误的数据**，而且不会有任何报错。

**修复**（一行）：`manifest.frozen.sort_unstable();` 放在 `open()` 里重放之前。或者更严格：`assert!(frozen.windows(2).all(|w| w[0] < w[1]))`，不满足就报 `Corrupted`。

### 坑 4：`set_len` 需要写权限（跨平台）

已在 3.3 讲过。症状是 Windows 上报 `PermissionDenied (os error 5)`，而同样的代码在 Linux 上可能正常。

### 坑 5：以为 `write()` 成功就是持久化了

`recovery_demo` 场景 E 证明：写入后不关闭，文件里**已经能看到数据**（36 字节），所以"进程崩溃不丢"。但这**不等于**持久化——断电就没了。

判断标准只有一个：**有没有 `fsync`**。

### 坑 6：截断是"静默丢数据"，没有告警

`replay_segment` 里只有一句 `log::warn!`。如果你的库很大，某次崩溃后静默丢了几万条记录，而没人看日志，这个损失会被掩盖很久。

生产系统应该：把"截断事件"记进一个持久化的计数器/事件日志，并在启动时上报（比如写到 `RECOVERY.log` 或直接告警）。

### 坑 7：`Drop` 里不能返回错误

`drop()` 没有返回值，所以 `sync_all()` 失败只能 `log::error!`。这意味着**优雅关闭路径（`close()`）和兜底路径（`Drop`）的行为不同**：

- `close()`：`sync_all()` 失败 → 返回 `Err`，调用方能感知并处理；
- `Drop`：失败 → 只记日志，调用方（如果有）已经拿不到结果。

所以：**重要的关闭流程一定要显式调用 `close()`，不能只依赖 `Drop`。**

## 6. 性能考量

### 6.1 启动时间 = O(数据量)

`recovery_demo` 的基线：5 条记录 125 字节，重放瞬间完成。按比例外推：

| 数据量 | 重放耗时（SSD，顺序读 ~500 MB/s） | 说明 |
|--------|--------------------------------|------|
| 10 MB | ~20 ms | 无感 |
| 1 GB | ~2 s | 可接受 |
| 100 GB | ~200 s | **不可接受** |

再加上建索引的哈希计算（每个 key 一次 SipHash），实际会更慢。

三个优化（详见模块一 7.2 和模块四 6.3）：

1. **hint 文件**：合并时顺带写 `key → (seg, offset, len)`，启动时直接读 hint，不扫数据文件。
2. **索引快照**：定期把 `HashMap` 序列化落盘，只重放之后的新段。
3. **并行重放**：多个段之间可以并行（但要注意顺序覆盖的语义——只有"段之间无重叠 key"或者"按段顺序合并结果"才安全）。

### 6.2 fsync 的成本

一次 `fsync` 在机械盘上是 ~10 ms（一转的时间），在 SSD 上是 ~0.1 ms。如果每次写都 fsync：

- HDD：~100 写/秒（对比不 fsync 时的 10 万+/秒，差 3 个数量级）
- SSD：~1 万写/秒

所以"每次写 fsync"通常是不可接受的，生产系统普遍用**组提交（group commit）**：把一批写入攒起来，一次 fsync 确认整批。MySQL 的 `innodb_flush_log_at_trx_commit=2`、PostgreSQL 的 `commit_delay` 都是这个思路。

### 6.3 可配置的持久性

一个实用的设计是把 fsync 策略做成配置项（模块一提到 `Config` 目前没被真正使用，正好派上用场）：

```rust
pub enum SyncPolicy {
    Never,                          // 最快，断电丢数据
    Every(Duration),                // 定时 fsync（后台线程）
    EveryWrite,                     // 最慢，最安全
}
```

本项目现在等价于 `Never` + "在 roll/close/compact 时 sync"。

### 6.4 CRC 的成本

重放时要对**每个字节**算 CRC32。用查表法（本项目在编译期生成 256 项的表）大约是 1 GB/s 量级，通常不是瓶颈。瓶颈在 I/O 和哈希。

### 6.5 恢复时的内存峰值

重放时 `index` 要装下所有 key。1 亿个 32 字节的 key，光索引就要 ~10 GB 内存。**这是 Bitcask 模型的硬约束**：索引必须放得进内存。RocksDB 的 SST + Bloom filter 就是为了突破这个限制。

## 8. 练习

1. **（严重，必修）修复坑 1**：把 `compact()` 里的 `save_manifest()` 移到删除旧段之前，并在 `open()` 里清理"manifest 未登记的 `.log` 文件"。写一个测试：在 rename 之后、删旧段之前"崩溃"（用 `std::process::abort()` 或者手工构造目录状态），验证数据不丢。
2. **（正确性）修复坑 3**：在 `open()` 里对 `manifest.frozen` 排序并校验升序。
3. **（健壮性）修复坑 2**：让 `open()` 在 "manifest 指向的段文件不存在" 时报 `Corrupted` 而不是静默创建空文件。
4. **（持久化）实现 `SyncPolicy`**（6.3），加一个 `Every(Duration)` 的后台 fsync 线程。写一个"写入后立刻断电"的测试很难，但可以用 `strace`/Process Monitor 确认 `fsync` 确实被调用了。

6. **（启动优化）实现 hint 文件**（模块四 6.3），对比 100 万条记录时启用前后的启动耗时。
