# 模块一：数据库实例与启动流程

> **这一篇回答**：`Engine::open("./data")` 这一行背后到底发生了什么？磁盘上的三个文件（`LOCK` / `manifest.json` / `NNNNNNNNN.log`）是怎么变成一个可用引擎的？

---

## 1. 要解决的问题与设计权衡

### 1.1 open() 要同时满足五件事

一个存储引擎的"打开"操作远比听起来复杂。它必须同时做到：

| 要求 | 含义 |
|------|------|
| **幂等** | 目录不存在就创建；存在就恢复；重复打开同一目录（不同进程）要被拒绝 |
| **可恢复** | 上次可能是正常关闭，也可能是 `kill -9`，甚至机器断电。两种都得能起来 |
| **自描述** | 光看目录里的文件，要能推断出"哪些段是历史、哪个段在写入" |
| **互斥** | 两个进程同时写同一个目录 = 数据损坏。必须在 open 阶段挡住 |
| **不丢数据** | 恢复完成后，所有已确认写入的键值对都必须可读 |

最关键的一条是**互斥**——它是唯一"必须在 open 阶段就失败"的检查，因为一旦放两个进程进去，后面所有正确性假设都塌了。

### 1.2 权衡一：索引落盘 vs 重启重放

索引（`HashMap<String, Location>`）是引擎的心脏，重启时必须重建。两个方案：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 索引落盘** | 关闭时把索引写成 `index.snapshot`，启动时直接读 | 启动快 | ① 快照是**随机写**，比顺序 append 慢得多<br>② 快照本身可能写一半 → 又要给快照做校验和恢复，套娃<br>③ 快照会过期：写快照后又有新写入，仍要重放增量 |
| **B. 重启重放**（本项目） | 索引不落盘，启动时顺序扫描所有段重建 | ① 恢复路径只有一条，**不可能和运行时状态不一致**<br>② 纯顺序读，非常快<br>③ 实现简单，没有套娃 | 启动时间 ∝ 数据总量 |

**选 B 的根本理由不是性能，是正确性**：多一份持久化状态就多一处"它可能损坏"的地方。Bitcask 原始论文也是这个选择。

> 代价在[性能考量](#7-性能考量)里算账。真实引擎（RocksDB）后来加了 manifest + 检查点来缩短恢复时间，但思想一致：**增量状态优先从日志重放，而不是单独维护第二份真相**。

### 1.3 权衡二：目录锁用什么

| 方案 | 机制 | 崩溃后是否自动释放 | 需要额外依赖 |
|------|------|-------------------|-------------|
| **`create_new` 占位文件**（本项目） | `O_EXCL` 原子创建 `LOCK` 文件 | ❌ **不会**，锁文件残留 | 无 |
| **OS 级 flock** | `flock(2)` / `LockFileEx` | ✅ 进程退出内核自动释放 | `fs2` / `file-lock` |
| **写 pid + 存活性检查** | 锁文件里写 pid，启动时检查该 pid 是否活着 | 部分 | 无 |

本项目选 `create_new`，注释里明确写了"生产环境请用 `fs2::FileExt::try_lock_exclusive`"。**这是教学取舍：省一个依赖，换一段需要你自己补的作业。**

### 1.4 权衡三：manifest 存在 vs 每次扫描目录

| 方案 | 做法 | 权衡 |
|------|------|------|
| **扫描推断** | `fs::read_dir` 找所有 `.log`，排序后最后一个是活跃段 | 不需要额外文件，但**丢失了"哪些段被合并过"的信息**；而且段号是 9 位定宽，字典序 = 数值序，正好可以排序 |
| **manifest.json**（主） | serde 持久化 `{version, active_id, frozen}` | 显式、可扩展（以后加字段只要改 version），但多一个需要原子更新的文件 |

本项目**两个都做了**：优先读 manifest，读不到就扫描推断（向后兼容老数据）。多一层兜底的成本很低，收益是"手删 manifest 也不会丢数据"。

## 2. 关键数据结构

### 2.1 `Engine` —— 对外门面

```rust
// src/engine.rs
pub struct Engine {
    inner: SegmentEngine,   // 真正的存储实现（组合，不是继承）
    stats: Stats,           // 原子计数器
    config: Config,         // 运行期配置
    started_at: Instant,    // 用于 uptime()
}
```

**组合而不是继承**：`Engine` 持有 `SegmentEngine`，只转发想暴露的方法。Rust 没有 `extends`，也就没有"父类改了子类崩"的问题。

`Engine` 本身**不持有任何磁盘资源**——所有句柄都在 `SegmentEngine` 里。这让 `Engine::close(self)` 只要转调 `self.inner.close()` 即可，编译器保证关闭后无法再用。

### 2.2 `SegmentEngine` —— 真正持有资源的东西

```rust
// src/stage6_compact.rs
pub struct SegmentEngine {
    dir: PathBuf,

    /// 已冻结的历史段的**读句柄**。
    /// BTreeMap 而不是 HashMap：段必须按 id 升序重放（后写的覆盖先写的），
    /// 有序容器把这个语义写进了类型里，也让 frozen.keys() 天然有序。
    frozen: BTreeMap<u64, File>,

    /// 活跃段 id（唯一可写的段）
    active_id: u64,

    /// 活跃段的写句柄。刻意**不用** BufWriter，原因见模块二。
    active_writer: File,

    /// 活跃段当前写入位置（字节）。等于文件大小，但避免每次 stat。
    active_pos: u64,

    /// 键 → 记录位置。整个引擎的心脏。
    index: HashMap<String, Location>,

    /// 已废弃（被覆盖/删除）但仍占着磁盘的字节数
    dead_bytes: u64,
    /// 有效数据占用的字节数
    live_bytes: u64,

    /// 目录锁句柄。用 Option 包一层是为了在 Drop 里**先关闭再删除**
    /// （Windows 不允许删除仍被打开的文件，顺序搞反就报"拒绝访问"）。
    lock: Option<File>,
}
```

**三个字段的设计意图值得单独说：**

**① `frozen: BTreeMap<u64, File>`** —— 用有序容器不是随手写的。重放必须按段号升序（后面的覆盖前面的），`BTreeMap` 让这个语义**由类型保证**，而不是靠"记得 sort"。同时 `save_manifest` 里 `self.frozen.keys().copied().collect()` 天然就是有序的 `Vec<u64>`。

**② `active_writer: File` 单独一个字段，不在 `frozen` 里** —— 活跃段是唯一可写的，读写模式都不同（append 模式打开）。把它和只读段分开，权限边界就清晰了：历史段用 `File::open`（只读），活跃段用 `append(true)`。

**③ `lock: Option<File>`** —— `Option` 不是因为"可能没有锁"，而是为了 `Drop` 里能 `self.lock.take()` 把句柄移出来 drop 掉，**然后**再删文件。这是 Windows 的硬约束。

### 2.3 `Location` —— 索引的值

```rust
#[derive(Debug, Clone, Copy)]
struct Location {
    seg: u64,     // 段号
    offset: u64,  // 段内字节偏移
    len: u64,     // 记录总字节数（含头尾），用于垃圾记账
}
```

`Copy` 是关键：索引里的值会被频繁复制出哈希表，`Copy` 让它变成一次 24 字节的栈上拷贝，没有引用计数也没有借用。

`len` 字段看起来冗余（读的时候用不到），但它**是垃圾记账的基础**：覆盖写时 `dead_bytes += old.len`，删除时 `dead_bytes += loc.len + tomb.len`。没有它就算不出 `garbage_ratio()`，也就不知道什么时候该合并。

### 2.4 `Manifest` —— 落盘的自描述信息

```rust
#[derive(Debug, Serialize, Deserialize)]
struct Manifest {
    version: u32,     // 格式版本，≈ Java 的 serialVersionUID
    active_id: u64,   // 哪个段是活跃的
    frozen: Vec<u64>, // 哪些段是历史（升序）
}

const MANIFEST_VERSION: u32 = 1;
```

只有三个字段，但**version 是必须的**：格式一变，旧的 manifest 必须被拒绝而不是被误读。`load_manifest` 里的检查：

```rust
if m.version != MANIFEST_VERSION {
    return Err(KvError::Corrupted {
        reason: format!("manifest 版本不匹配: {} != {MANIFEST_VERSION}", m.version),
        truncated_at: 0,
    });
}
```

### 2.5 `Config` —— 配置（以及一个真实缺陷）

```rust
#[derive(Debug, Clone)]
pub struct Config {
    pub segment_max_bytes: u64,   // 段滚动阈值
    pub compact_threshold: f64,   // 触发合并的垃圾占比
}

impl Default for Config {
    fn default() -> Self {
        Self { segment_max_bytes: 64 * 1024 * 1024, compact_threshold: 0.3 }
    }
}
```

> ⚠️ **已知缺陷（值得你自己去修）**：`Config::segment_max_bytes` **声明了、有默认值、但从来没有被读取过**。
> 段滚动阈值实际由 `stage6_compact.rs` 里的常量决定：
> ```rust
> const SEGMENT_MAX_BYTES: u64 = 1024 * 1024;  // 1 MiB
> fn should_roll(&self) -> bool { self.active_pos >= SEGMENT_MAX_BYTES }
> ```
> 同理，`Config::compact_threshold` 只被 `Engine::set` 用到，而 `SegmentEngine::maybe_compact()` 用的是自己的常量 `COMPACT_THRESHOLD: f64 = 0.3`。
>
> **根因**：`Engine::with_config` 把 `config` 存进了 `Engine`，但**没有往下传给** `SegmentEngine::open`。这类"配置看着生效其实没生效"的问题在生产里很常见，而且**不会报错、不会失败，只是行为不符合预期**。

## 3. 核心代码路径：`Engine::open` 逐步拆解

### 3.1 调用链总览

```
Engine::open(dir)
└─ Engine::with_config(dir, Config::default())
   └─ SegmentEngine::open(dir)
      ├─ fs::create_dir_all(&dir)                    // ① 建目录
      ├─ OpenOptions::new().write(true)
      │      .create_new(true).open("LOCK")          // ② 抢目录锁
      │      .map_err(AlreadyExists → Protocol)      //
      ├─ Self::load_manifest(&dir)                   // ③ 读/推断 manifest
      │   ├─ 有 manifest.json → serde_json::from_reader + 版本校验
      │   └─ 没有            → fs::read_dir 扫描 .log 推断
      ├─ for seg_id in manifest.frozen:              // ④ 打开并重放历史段
      │   ├─ File::open(seg_path)                    //    只读句柄
      │   ├─ replay_segment(&file, seg_id, &mut index, &path)
      │   └─ frozen.insert(seg_id, file)
      ├─ OpenOptions::new().create(true).read(true)
      │      .append(true).open(active_path)         // ⑤ 打开活跃段
      ├─ active_file.try_clone()                     // ⑥ 克隆一个句柄用于重放
      ├─ replay_segment(&active_clone, active_id, &mut index, &active_path)
      ├─ active_pos = active_clone.metadata()?.len() // ⑦ 截断后的真实长度
      └─ Ok(Self { .. })
```

### 3.2 ① 建目录

```rust
let dir = dir.as_ref().to_path_buf();
fs::create_dir_all(&dir)?;
```

`create_dir_all` 是幂等的（已存在不报错），所以"首次启动"和"再次启动"走同一条路径——**open 不需要区分这两种情况**，这是好设计的标志。

注意参数签名 `dir: impl AsRef<Path>`：调用方可以传 `&str`、`String`、`PathBuf`、`&Path`，一份代码全覆盖。≈ Java 里写重载，但这里靠泛型单态化，没有装箱。

### 3.3 ② 抢目录锁

```rust
let lock = OpenOptions::new()
    .write(true)
    .create_new(true)                    // 关键：文件已存在则失败，且是原子的
    .open(dir.join("LOCK"))
    .map_err(|e| {
        if e.kind() == io::ErrorKind::AlreadyExists {
            KvError::Protocol(format!("数据目录已被占用: {}", dir.display()))
        } else {
            KvError::Io(e)
        }
    })?;
```

**为什么用 `Protocol` 而不是 `Io`？** 语义上这不是"I/O 故障"，而是"你用错了"——应该给调用方一个明确的、可展示的信息，而不是让它看到 `File exists (os error 17)`。

**`create_new` 的原子性来自 `O_EXCL`**：内核保证"检查存在 + 创建"是一步完成的，两个进程同时调用只会有一个成功。这是整个互斥机制的全部基础。

> 但 `O_EXCL` 有个致命弱点：**进程被 `kill -9` 时不会释放**。`LOCK` 文件会残留，下次 open 直接失败。这就是为什么 3.7 的边界处理很重要，也是为什么生产要用 flock。

### 3.4 ③ 加载 manifest（两条分支）

```rust
fn load_manifest(dir: &Path) -> Result<Manifest> {
    let path = dir.join("manifest.json");
    if path.exists() {
        let file = File::open(path)?;
        let m: Manifest = serde_json::from_reader(BufReader::new(file))?;
        if m.version != MANIFEST_VERSION { /* → Corrupted */ }
        return Ok(m);
    }

    // 兜底：目录里有 .log 但没有 manifest → 扫描文件名推断
    let mut ids: Vec<u64> = fs::read_dir(dir)?
        .filter_map(std::result::Result::ok)
        .filter_map(|e| {
            let name = e.file_name().to_string_lossy().into_owned();
            name.strip_suffix(".log")?.parse::<u64>().ok()
        })
        .collect();
    ids.sort_unstable();
    let active_id = ids.pop().unwrap_or(1);   // 最大的当活跃段；空目录就是 1
    Ok(Manifest { version: MANIFEST_VERSION, active_id, frozen: ids })
}
```

**几个细节：**

- `serde_json::from_reader` 而不是 `from_str`：直接从 `BufReader` 流式反序列化，**不需要先把整个文件读进 String**。≈ Jackson 的 `objectMapper.readValue(inputStream, T.class)`。
- `?` 在 `filter_map` 的闭包里也能用——`strip_suffix` 返回 `Option`，`?` 让"去掉后缀失败"直接跳过这一项。这是 Rust 的 `?` 同时支持 `Option` 和 `Result` 的好处。
- **段文件名 9 位定宽（`format!("{id:09}.log")`）不是审美选择**：它让"字典序 = 数值序"，于是 `sort_unstable()` 得到的就是时间序。如果你用 `format!("{id}.log")`，`"10.log" < "9.log"`，恢复顺序就错了——**这是一个非常隐蔽的数据正确性 bug**。

### 3.5 ④ 重放历史段

```rust
for seg_id in manifest.frozen.iter().copied() {
    let path = Self::seg_path(&dir, seg_id);
    let file = File::open(&path)?;                       // 只读
    let (d, l) = replay_segment(&file, seg_id, &mut index, &path)?;
    dead_bytes += d;
    live_bytes += l;
    frozen.insert(seg_id, file);
}
```

**为什么 `replay_segment` 是自由函数而不是方法？**

这是 Rust 里最典型的一次"被借用检查器逼着改设计"。本能写法是把它写成 `SegmentEngine` 的私有方法：

```rust
// ❌ 编译不过
fn replay_segment(&mut self, seg_id: u64) -> Result<..> {
    let file = self.frozen.get(&seg_id);   // 不可变借用 self
    // ... 同时又要
    self.index.insert(key, loc);           // 可变借用 self
}
```

两个借用冲突。改用自由函数，把需要的部分**显式列进参数**，借用就清晰了：

```rust
fn replay_segment(
    file: &File,                              // 只读句柄
    seg_id: u64,                              // 段号
    index: &mut HashMap<String, Location>,    // 只有索引是可变的
    path: &Path,                              // 截断时需要重新打开
) -> Result<(u64, u64)>                       // (新增垃圾, 新增有效字节)
```

> **这个模式在 Rust 里非常常见**：当你同时需要一个结构体的两个字段（一个只读一个可变）时，把逻辑拆成自由函数，参数里只借用真正需要的部分。比 `RefCell`（把检查推到运行期）和整体 `clone`（有开销）都好。
> 详细过程见模块五的[重放实现](#)。

### 3.6 ⑤⑥⑦ 打开活跃段

```rust
let active_path = Self::seg_path(&dir, manifest.active_id);
let active_file = OpenOptions::new()
    .create(true).read(true).append(true)
    .open(&active_path)?;

let active_clone = active_file.try_clone()?;
let (d, l) = replay_segment(&active_clone, manifest.active_id, &mut index, &active_path)?;
dead_bytes += d;
live_bytes += l;
let active_pos = active_clone.metadata()?.len();
```

**为什么这里可以安全地使用 `try_clone()`？**

`try_clone()` 底层是 `dup(2)`，**新旧句柄共享同一个文件偏移量**——在运行时多线程 seek 会互相踩（模块二详细讲）。但这里是**启动阶段的单线程代码**，克隆出来的句柄只用来重放（顺序读），之后就不用了。所以安全。

不过要注意：重放时 `replay_segment` 内部可能截断文件，截断用的是**另开的写句柄**，不用这个 clone。所以 clone 的游标始终是 0，`read_at` 位置读取也不依赖游标。

**`active_pos` 为什么取 `metadata().len()` 而不是重放结束时的 `pos`？**

`replay_segment` 返回的 `(dead, live)` 里没有位置信息。取文件长度是最直接的。关键在于**顺序**：`replay_segment` 内部如果截断了坏尾巴，会 `set_len`，而 `metadata()` 是 `fstat`，返回的是**实时的**文件长度。所以这行必须放在重放**之后**——顺序反了就会把 `active_pos` 设成包含坏数据的长度。

### 3.7 关闭与 `Drop`

```rust
impl Drop for SegmentEngine {
    fn drop(&mut self) {
        if let Err(e) = self.active_writer.sync_all() {
            log::error!("关闭时 sync 失败: {e}");
        }
        drop(self.lock.take());                          // 先关句柄
        let _ = fs::remove_file(self.dir.join("LOCK"));  // 再删文件
    }
}
```

**`take()` + `drop()` 的顺序是 Windows 的硬约束**：不先关句柄就删文件，报 `PermissionDenied`（Linux 允许，所以这个 bug 在 Linux 上永远不会暴露——典型的跨平台陷阱）。

还有显式关闭：

```rust
pub fn close(self) -> Result<()> {
    self.active_writer.sync_all()?;
    self.save_manifest()?;
    drop(self);
    Ok(())
}
```

**为什么有了 `Drop` 还要 `close(self)`？** 因为 `drop(&mut self)` **不能返回错误**。如果 fsync 失败，你没有任何办法通知调用方，数据就静默丢了。分工是：

- `Drop`：尽力而为的清理（关句柄、删锁），**不能报错**
- `close(self)`：必须成功的收尾（flush + fsync + 存 manifest），**能报错**

`self` 被消费，所以编译器保证**关闭后无法再使用**——比 Java 的 `IllegalStateException("connection closed")` 运行期检查强得多。

## 4. 边界情况清单

| 情况 | 会发生什么 | 是否符合预期 |
|------|-----------|-------------|
| **目录不存在** | `create_dir_all` 创建，`active_id = 1`，空索引 | ✅ 首次启动正常路径 |
| **目录存在但为空** | 同上 | ✅ |
| **已有进程占用** | `create_new` 失败 → `KvError::Protocol("数据目录已被占用")` | ✅ 正确拒绝 |
| **上次 `kill -9`** | `LOCK` 残留 → open 失败 | ⚠️ 需要人工删 `LOCK`；生产应改用 flock |
| **manifest.json 不存在** | 扫描 `.log` 推断，最大号当活跃段 | ✅ 手删 manifest 不丢数据 |
| **manifest 版本不匹配** | `KvError::Corrupted`，**拒绝启动** | ✅ 宁可拒绝也不误读 |
| **manifest 里的段文件被删** | `File::open(seg_path)?` → `KvError::Io` → 启动失败 | ⚠️ 不优雅但安全（不会静默丢数据） |
| **活跃段尾部损坏** | `replay_segment` 截断，`active_pos` 取截断后长度 | ✅ 见模块五 |
| **磁盘满** | `write_all` 返回 `Err` → 向上传播 | ✅ 但内存索引可能已改动，见模块四的坑 |
| **无写权限** | `create_dir_all` 或 `create_new` 失败 → `KvError::Io` | ✅ |
| **并发 open 同一目录** | 一个成功一个失败（`O_EXCL` 原子） | ✅ |

## 5. 常见坑

### 坑 1：把 `create_new` 锁当成生产级互斥

`O_EXCL` 创建的文件**不会在进程崩溃时自动释放**。生产环境要么：

- 用 `fs2::FileExt::try_lock_exclusive`（OS 级 flock，进程退出内核自动释放）；
- 要么把 pid 写进 `LOCK`，open 时检查该 pid 是否还活着（要处理 pid 复用）。

### 坑 2：段文件名不补零

```rust
dir.join(format!("{id}.log"))      // ❌ "10.log" < "9.log"，恢复顺序错
dir.join(format!("{id:09}.log"))   // ✅ 定宽，字典序 = 数值序
```

这个 bug **不会报错**，只会在段号过 9 之后静默地让旧数据覆盖新数据。

### 坑 3：忘了 `Drop` 里"先关句柄再删文件"

Linux 允许删除打开的文件，Windows 不允许。只在本机开发会漏掉，CI 在 Windows 上才炸。

### 坑 4：以为 `Engine::with_config` 真的把配置传下去了

见 [2.5](#25-config--配置以及一个真实缺陷)。`segment_max_bytes` 是死配置。

### 坑 5：把重放逻辑写成方法，然后和借用检查器搏斗

正解是拆成自由函数（见 [3.5](#35-重放历史段)）。**不要**为了绕过它上 `RefCell`——那会让 `SegmentEngine` 变成 `!Sync`，模块六的并发就全完了。

## 7. 性能考量

### 7.1 启动时间 = O(数据总量)，而且是全量读

`replay_segment` 调用 `read_frame_at`，后者会把**整个帧（含 value）读进内存**再校验 CRC。所以：

```
恢复时间 ≈ 数据总量 / 磁盘顺序读吞吐 + CRC 计算开销
```

1 GiB 数据、磁盘 500 MB/s → 约 2 秒纯 IO，加上 CRC32（约 1 GB/s）再加 1 秒。**这个量级对嵌入式场景可以接受，对大库不行。**

### 7.2 三个优化方向（按性价比排序）

| 优化 | 做法 | 收益 | 代价 |
|------|------|------|------|
| **恢复时跳过 value** | 帧头增加 `frame_len` 字段，重放时只读 header + key，按 `frame_len` 直接跳到下一帧 | 恢复 IO 从"全量"降到"头 + key"，通常 **90%+** | 帧格式变更（version +1），value 的 CRC 覆盖不到（要改成分段校验或接受风险） |
| **并行重放多段** | 历史段之间互不依赖，可以多线程并发重放再合并索引 | 多核线性加速 | 索引合并要处理"后段覆盖前段"，需要按段号有序归并 |
| **检查点** | 定期把索引快照落盘，恢复时只重放增量 | 恢复时间 O(增量) | 回到 1.2 权衡 A：多一份状态就多一处可能损坏 |

> **本项目的选择是"不做优化，但把优化点留在明处"**。这也是 `MINIDB` 这类教学项目的价值：你看得见代价在哪。

### 7.3 内存占用

索引 `HashMap<String, Location>`：

```
每条目 ≈ key.len() + 24 (String) + 24 (Location) + HashMap 开销约 30~50%
```

1000 万个 16 字节的 key ≈ **约 700 MB**。这是 Bitcask 的硬约束：**内存必须装得下全部 key**。RocksDB 之所以用 LSM，很大程度就是为了突破这个限制。

### 7.4 文件句柄数

`frozen` 里每个段一个 `File`。段多了句柄就多。生产实现通常：

- 用 LRU 缓存句柄，超出就关闭（读时再打开）；
- 或者用 mmap（模块二会提）。

## 8. 练习

1. **修掉死配置**：把 `Config::segment_max_bytes` 真正接进 `SegmentEngine`。需要给 `SegmentEngine::open` 加一个 `Config` 参数（或新增 `open_with_config`），把 `SEGMENT_MAX_BYTES` 常量改成字段。注意 `tests/` 里的调用点都要跟上。
2. **让锁可自愈**：把 pid 写进 `LOCK` 文件，`open` 时如果 `create_new` 失败就读出 pid 检查该进程是否还活着；不活着就抢占并覆盖。**思考**：pid 复用怎么办？（提示：Linux 可以再存启动时间 `/proc/<pid>/stat` 字段 22；更稳的方案还是 flock。）
