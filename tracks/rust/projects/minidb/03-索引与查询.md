# 模块三：索引构建与查询路径

> **这一篇回答**：`GET user:1` 从一行文本到返回字节，中间经过了几次哈希、几次系统调用？索引为什么"不落盘"却不会丢？为什么 `KEYS ""` 在大库上是个危险操作？

---

## 1. 要解决的问题与设计权衡

### 1.1 问题的本质

append-only 日志有个致命问题：**同一个 key 的最新值在哪，从文件上看不出来**。写 100 次 `user:1`，文件里就有 100 条记录，只有最后一条有效。如果查询要靠扫文件，那复杂度就是 O(总记录数)——完全不可用。

所以必须有一个"键 → 最新记录位置"的映射。这就是索引。

### 1.2 权衡一：索引里存什么

| 方案 | 索引类型 | 查询成本 | 内存 | 备注 |
|------|---------|---------|------|------|
| **存值本身** | `HashMap<String, Vec<u8>>` | O(1)，不落盘 | 和数据量成正比 | 内存爆炸；而且重启要重建索引时得从哪来？ |
| **存文件偏移**（本项目） | `HashMap<String, Location>` | O(1) + 1 次磁盘读 | 只和 key 数量成正比 | ✅ |
| **存偏移 + 长度** | 同上的 `Location{seg, offset, len}` | 同上 | 多 8 字节/条 | `len` 用于垃圾记账，不存就算不出 `garbage_ratio` |

**关键洞察**：索引存**位置**而不是**数据**，代价是每次查询多一次磁盘读，收益是内存占用从 O(数据量) 降到 O(key 数量)。这是 Bitcask 的全部精髓。

`len` 字段看起来对查询没用，但它是**模块四垃圾记账的基础**：覆盖写时 `dead_bytes += old.len`。

### 1.3 权衡二：索引落盘 vs 重启重放

见[模块一 1.2](./01-实例与启动.md)——本项目选重放。这里补充查询侧的推论：

> **索引是磁盘数据的"缓存视图"，不是独立真相。**
> 所以它**永远不可能"和磁盘不一致"**——因为它就是从磁盘推出来的。唯一的失效场景是"磁盘数据变了但索引没更新"，而这只可能发生在写入路径上（由写锁/Actor 串行化保证）。

这个性质极大简化了正确性推理：**你不需要为索引设计任何一致性协议**。

### 1.4 权衡三：`HashMap` vs `BTreeMap`

| | `HashMap` | `BTreeMap` |
|---|-----------|-----------|
| 点查 | **O(1)** | O(log n) |
| 范围查询 | ❌ 不支持 | ✅ 支持 |
| 前缀扫描 | O(n) 全表扫 | O(log n + k) |
| 内存 | 较低（但有负载因子浪费） | 较高（节点开销） |
| 迭代顺序 | **不确定** | 有序 |

选 `HashMap` 的理由：**Bitcask 的核心场景是点查**（`GET k`），而且内存里必须装下全部 key，`HashMap` 更省。

代价有两个，都在代码里留下了痕迹：

1. **不支持范围查询** —— 这是 Bitcask 的硬限制，不是实现偷懒。想要 `RANGE a z` 就得换 BTreeMap + SSTable（LSM 的路子）。
2. **迭代顺序不确定** —— 所以 `keys()` 必须 `sort()`，否则测试不可重复（见坑 2）。

### 1.5 权衡四：key 的类型

`HashMap<String, Location>` 用的是 `String`（拥有所有权）而不是 `&str`（借用）。

**为什么？** `&str` 是借用，意味着索引里的键必须指向别处活着的数据——那就得引入生命周期参数 `HashMap<&'a str, Location>`，整个 `SegmentEngine` 都被 `'a` 传染。而且磁盘读出来的 key 是新建的 `String`，借用给谁？

> **Rust 的通用经验：结构体里存字符串默认用 `String`。** 想省一次分配而用 `&'a str`，代价是整个类型被生命周期参数污染。`Cow<'a, str>` 只在明确的"大部分时候借用"场景才划算。

## 2. 关键数据结构

### 2.1 索引本体

```rust
// src/stage6_compact.rs，SegmentEngine 的字段
index: HashMap<String, Location>,
```

```rust
#[derive(Debug, Clone, Copy)]
struct Location {
    seg: u64,     // 段号：决定用哪个 File 句柄
    offset: u64,  // 段内字节偏移：传给 read_frame_at
    len: u64,     // 记录总字节数：垃圾记账用
}
```

`#[derive(Copy)]` 很关键：`self.index.get(key)` 返回 `Option<&Location>`，读出来要拷贝一份传给 `read_at(*loc)`。有 `Copy` 就是一次 24 字节的栈拷贝，没有就得多一次借用。

### 2.2 段句柄表

```rust
frozen: BTreeMap<u64, File>,   // 历史段的只读句柄
active_id: u64,                // 活跃段号
active_writer: File,           // 活跃段的读写句柄（append 模式）
```

**查询时选句柄的规则**：`loc.seg == active_id` 用 `active_writer`，否则去 `frozen` 里找。找不到 → `Corrupted`。

### 2.3 `trait KvStore` —— 查询的契约

```rust
pub trait KvStore: Send + Sync {
    fn get(&self, key: &str) -> Result<Option<Vec<u8>>>;
    fn set(&mut self, key: &str, value: Vec<u8>) -> Result<()>;
    fn delete(&mut self, key: &str) -> Result<Option<Vec<u8>>>;
    fn keys(&self, prefix: &str) -> Result<Vec<String>>;
    fn compact(&mut self) -> Result<u64>;

    // 默认方法
    fn exists(&self, key: &str) -> Result<bool> { Ok(self.get(key)?.is_some()) }
    fn batch_set(&mut self, pairs: &[(String, Vec<u8>)]) -> Result<()> { /* 逐条 set */ }
}
```

**注意 `get(&self, ...)` 而 `set(&mut self, ...)`** —— 接口层面就区分了读写。编译器天然知道哪些调用需要独占访问，这是模块六能做"按命令选读锁/写锁"的前提。

`InMemKv`（内存版）和 `SegmentEngine`（磁盘版）都实现了它，所以上层代码可以对两者无差别调用。

## 3. 核心代码路径

### 3.1 索引构建（概述，详见模块五）

索引只在两个地方被修改：

| 时机 | 代码 | 效果 |
|------|------|------|
| **启动重放** | `replay_segment` 里 `index.insert(key, loc)` / `index.remove(&key)` | 从磁盘重建 |
| **运行时写入** | `set` 里 `index.insert`、`delete` 里 `index.remove` | 增量更新 |

```rust
// 重放时（模块五详解）
if f.value.is_some() {
    if let Some(old) = index.insert(f.key, loc) {
        dead += old.len;                    // 旧记录变垃圾
        live = live.saturating_sub(old.len);
    }
    live += f.consumed;
} else {
    if let Some(old) = index.remove(&f.key) {
        dead += old.len;
        live = live.saturating_sub(old.len);
    }
    dead += f.consumed;                     // 墓碑本身就是垃圾
}
```

**`index.insert` 返回旧值**这一点被用到了极致：返回值里有 `old.len`，正好用来累加 `dead_bytes`。Rust 的 `HashMap::insert` 返回 `Option<V>`，Java 的 `Map.put` 也返回旧值——语义一致，但 Rust 这里直接把它接进了垃圾记账的公式里，零额外查找。

### 3.2 点查：`GET`

调用链：

```
Engine::get(&self, key)
├─ Stats::incr(&self.stats.gets)                 // 计数（Relaxed 原子加）
└─ self.inner.get(key)                           // KvStore::get
   └─ SegmentEngine::get(&self, key)
      ├─ self.index.get(key)  → Option<&Location>
      │   └─ None → return Ok(None)              // 键不存在，不是错误
      └─ self.read_at(*loc)
         ├─ 选 File 句柄（active or frozen）
         └─ frame::read_frame_at(file, loc.offset)?.value
```

#### `Engine::get`

```rust
pub fn get(&self, key: &str) -> Result<Option<Vec<u8>>> {
    Stats::incr(&self.stats.gets);
    self.inner.get(key)
}
```

**参数 `&self` 而不是 `&mut self`** —— 查询不修改任何状态（除了原子计数器），所以只需要共享借用。这直接决定了模块六里 `GET` 可以走**读锁并发执行**。

**返回 `Result<Option<Vec<u8>>>` 的双重语义**：
- `Ok(None)` —— 键不存在。这是**正常的业务分支**，不是错误（≈ Java `Map.get` 返回 `null`，但类型显式）
- `Err(...)` —— 真的出事了（IO 故障、数据损坏）

#### `SegmentEngine::read_at` —— 段句柄选择

```rust
fn read_at(&self, loc: Location) -> Result<Option<Vec<u8>>> {
    let file: &File = if loc.seg == self.active_id {
        &self.active_writer
    } else {
        self.frozen
            .get(&loc.seg)
            .ok_or_else(|| KvError::Corrupted {
                reason: format!("找不到段 {}", loc.seg),
                truncated_at: loc.offset,
            })?
    };
    Ok(frame::read_frame_at(file, loc.offset)?.value)
}
```

**三点：**

1. **没有 clone 句柄**。`read_frame_at` 用位置读取（`read_at`），不修改文件游标，所以传 `&File` 就够了。多个读者同时调用这个函数是**天然安全**的——这是索引能支撑并发读的前提（模块六会用到）。
2. **`ok_or_else` 而不是 `ok_or`** —— 惰性构造。`ok_or(KvError::Corrupted{...})` 会**每次都**构造那个 String，`ok_or_else` 只在真的出错时才构造。这类微优化在热路径上值得。
3. **"找不到段"被归类为 `Corrupted`** —— 因为它意味着索引和磁盘状态不一致，属于数据层面出问题，不是单纯的 I/O 故障。

#### `read_frame_at` 的调用次数

这是查询路径上**最重要的性能事实**：

```rust
read_exact_at(file, &mut header, offset)?;        // 系统调用 ①  12 字节
read_exact_at(file, &mut key_buf, cursor)?;       // 系统调用 ②  key
read_exact_at(file, &mut v, cursor)?;             // 系统调用 ③  value
read_exact_at(file, &mut crc_buf, cursor)?;       // 系统调用 ④  4 字节
```

**一次 `GET` = 4 次 `pread` 系统调用**（如果 value 为空则是 3 次）。

为什么分成这么多次？因为帧格式是"定长头 + 变长体 + 定长尾"，必须先读头才知道 body 有多长。

**优化方向很明确**（见 6.2）：读完 header 后用一次 `read_exact_at` 把 `key + value + crc` 一起读出来，4 次降到 2 次。

### 3.3 前缀扫描：`KEYS <prefix>`

```rust
fn keys(&self, prefix: &str) -> Result<Vec<String>> {
    let mut out: Vec<String> = self.index
        .keys()
        .filter(|k| k.starts_with(prefix))
        .cloned()
        .collect();
    out.sort_unstable();
    Ok(out)
}
```

**复杂度 O(n)** —— 必须遍历整个索引。这是哈希索引的硬伤：`KEYS` 在大库上会扫几百万个 key。

**`sort_unstable()` 是必须的，不是可选的**：`HashMap` 的迭代顺序不确定（而且每次运行都可能不同）。不排序的话：

- 测试结果不可重复（今天过的测试明天挂）
- 客户端看到乱序结果

> `sort_unstable` 比 `sort` 快一点（不保证相等元素的相对顺序，可以用更快的排序算法），这里元素互不相等所以无所谓。

### 3.4 `EXISTS` —— 一个真实的实现缺陷

```rust
// src/engine.rs
/// 判断键是否存在（走索引，不读值——避免无谓 IO）。
pub fn exists(&self, key: &str) -> Result<bool> {
    Ok(self.get(key)?.is_some())
}
```

**文档注释说"不读值——避免无谓 IO"，但实现调用了 `get()`，而 `get()` 会把整个 value 从磁盘读出来。** 注释和实现不一致。

正确做法是加一个只看索引的方法：

```rust
// ✅ 修复：只查索引，零磁盘 IO
pub fn exists(&self, key: &str) -> Result<bool> {
    Ok(self.inner.contains_key(key))   // SegmentEngine 新增方法
}
```

```rust
// SegmentEngine
pub fn contains_key(&self, key: &str) -> bool {
    self.index.contains_key(key)
}
```

**这个缺陷为什么值得单独讲：**

1. **它不会报错、不会失败，只是"比应该的慢"** —— 这类问题在生产里最难发现
2. **注释比实现更"正确"** —— 说明作者知道该怎么做，实现时漏了
3. **`exists` 是高频操作**（很多 ORM/业务代码会先 exists 再 get）—— 一次多余的磁盘读在热点路径上是实打实的开销

> 顺带说：模块一里 `Config::segment_max_bytes` 是"配置没接上"，这里是"注释和实现不符"。**两个都是"不报错但行为不对"的缺陷**，这类 bug 只能靠读代码发现，编译器和 lint 都帮不了你。

### 3.5 惰性迭代：`iter()`

```rust
pub fn iter(&self) -> impl Iterator<Item = Result<(String, Vec<u8>)>> + '_ {
    let mut keys: Vec<&String> = self.index.keys().collect();
    keys.sort();
    keys.into_iter().map(move |k| {
        let loc = self.index[k];
        match self.read_at(loc) {
            Ok(Some(v)) => Ok((k.clone(), v)),
            Ok(None) => Err(KvError::KeyNotFound { key: k.clone() }),
            Err(e) => Err(e),
        }
    })
}
```

**两个 Rust 特性在这里同时发挥作用：**

1. **`impl Iterator` 返回位置** —— 调用方可以用 `.map()` `.filter()` `.take()` 组合，编译后通常内联成一个手写循环。而且**换实现不破坏 API**。
2. **`+ '_` 生命周期** —— 表示"这个迭代器借用了 `self`"，所以**不能比 `self` 活得久**。编译器保证你不会把一个还在借用引擎的迭代器逃逸出去。

Java 的 `Stream` 做不到"借用检查"：你必须自己保证流没被逃逸出去。

**惰性是真的**：

```rust
let first: Vec<_> = e.iter().take(1).collect();
assert_eq!(first.len(), 1);   // 只处理了一个元素，没有读整个库
```

### 3.6 对比：内存版的 `scan_prefix`

`stage2_inmem.rs` 里有一个**返回借用**的扫描：

```rust
pub fn scan_prefix<'k>(&'k self, prefix: &'k str)
    -> impl Iterator<Item = (&'k str, &'k [u8])> + 'k
{
    self.inner.iter()
        .filter(move |(k, _)| k.starts_with(prefix))
        .map(|(k, v)| (k.as_str(), v.as_slice()))
}
```

**零拷贝**：返回 `&'k [u8]` 而不是 `Vec<u8>`，没有任何内存复制。

**为什么磁盘版做不到？** 因为磁盘版的值来自 `read_frame_at`，那一帧解码出来的 `Vec<u8>` 是**新分配的**，必须交出所有权——它没有"别处活着的原始数据"可以借用。

> 这正是模块二提到的"零拷贝值（`bytes::Bytes`）"优化方向：让读出来的 buffer 带引用计数，`get` 就能返回 `Bytes` 而不是 `Vec<u8>`，多次读取共享同一份内存。

## 4. 边界情况

| 情况 | 行为 | 说明 |
|------|------|------|
| **键不存在** | `Ok(None)` | 业务正常分支，不是错误 |
| **键被删过（有墓碑）** | `index.get` 返回 `None` → `Ok(None)` | ✅ 删除是 `index.remove`，查不到 |
| **空前缀 `KEYS ""`** | `starts_with("")` 恒真 → 返回全部键 | ⚠️ **全表扫描 + 全量收集**，大库会 OOM |
| **记录在历史段** | `read_at` 从 `frozen` 取句柄 | ✅ |
| **记录刚写入还没 fsync** | page cache 命中，可读 | ✅ 进程崩溃数据还在 |
| **`loc.seg` 不在 `frozen` 也不等于 `active_id`** | `KvError::Corrupted { reason: "找不到段 N" }` | ⚠️ 索引与磁盘不一致，通常是合并逻辑漏登记（见模块四坑） |
| **key 含非 UTF-8** | API 层不可能（`&str` 参数） | ✅ |
| **value 是空字节** | `Ok(Some(vec![]))` | ✅ 和"不存在"区分开 |
| **并发读同一个 key** | 位置读取，天然安全 | ✅ |
| **读时正在合并** | 写锁/Actor 串行化保证不会并发 | ✅ 模块六 |

## 5. 常见坑

### 坑 1：`EXISTS` 读了值

见 [3.4](#34-exists--一个真实的实现缺陷)。注释说"不读值"，实现读了。

### 坑 2：忘了给 `keys()` 排序

```rust
// ❌ 结果顺序不确定，测试会偶发失败
self.index.keys().filter(..).cloned().collect()

// ✅
out.sort_unstable();
```

`HashMap` 的迭代顺序在不同运行之间都可能变化（Rust 的 `RandomState` 每次启动用不同的种子，这是**有意的安全设计**，防止 HashDoS 攻击）。

### 坑 3：以为索引需要"同步"到磁盘

索引**永远不落盘**。它的唯一来源是重放。所以：

- 不要试图在 `close()` 里序列化索引；
- 不要担心"索引会不会和磁盘不一致"——除非你的写入路径有 bug。

### 坑 4：`KEYS` 在大库上会打爆内存

`keys()` 返回 `Vec<String>`，全量收集。1000 万个 key 就是几百 MB 的一次性分配。

生产实现应该返回**迭代器** + 分页（`SCAN cursor COUNT 100`，Redis 就是这么做的）。

### 坑 5：把 `iter()` 的结果逃逸出 `self` 的生命周期

```rust
// ❌ 编译不过：迭代器借用了 engine，engine 在这里就被 drop 了
fn bad(engine: &Engine) -> impl Iterator<Item = ..> {
    engine.inner_iter()   // 假设存在
}
```

`+ '_` 明确写了"这个迭代器借用了 self"，编译器会拦住。**这正是 `iter()` 签名里写 `+ '_` 的价值**——不写的话编译器也会推导，但写出来是自文档化的。

## 6. 性能考量

### 6.1 点查的成本模型

```
GET k  =  1 次哈希查找（内存，~50ns）
       +  4 次 pread 系统调用（~1μs each，page cache 命中）
       +  CRC32 计算（value 大小 / 1~3 GB/s）
       +  1 次 Vec 分配 + 拷贝（value 大小）
```

**热点是系统调用次数和内存拷贝**，不是哈希。

### 6.2 优化一：减少系统调用（4 → 2）

当前 `read_frame_at` 分 4 次读。改成：

```rust
// ① 读 header（12 字节，必须，因为不知道 body 长度）
read_exact_at(file, &mut header, offset)?;
let key_len = ..; let val_len = ..;

// ② 一次读完 key + value + crc
let total = key_len + value_bytes.unwrap_or(0) + FOOTER_LEN;
let mut rest = vec![0u8; total];
read_exact_at(file, &mut rest, offset + HEADER_LEN as u64)?;
// 然后在 rest 上切分
```

**收益**：系统调用减半，小 value 场景点查 QPS 提升 30%~50%。

**代价**：要多一次 `total` 的总和拷贝吗？不会——`rest` 就是最终 buffer 的一部分，切分后 key/value 各自 `to_vec()` 或（配合 `Bytes`）直接切片。

### 6.3 优化二：一次分配而非三次

当前 `read_frame_at` 分配了 4 个 buffer：`header`、`key_buf`、`v`、`crc_buf`，还有 `check`（用于 CRC）。

理想情况：分配**一个** `Vec<u8>` 装整帧，所有字段都是它的切片。这需要先把整帧读出来，又回到"先知道长度"的问题——所以**帧头自带总长度**（模块二练习 1）是这两个优化的共同前置。

### 6.4 索引内存占用

```
每条 ≈  key.len() + 24 (String: ptr+len+cap)
      + 24 (Location: 3 × u64)
      + HashMap 条目开销（约 8~16 字节）
      + 负载因子浪费（默认 0.75 → 约 33% 空槽）
```

**估算公式**：`总内存 ≈ key 数量 × (平均 key 长度 + 64) × 1.4`

| key 数量 | 平均 key 16 字节 | 估算内存 |
|---------|-----------------|---------|
| 100 万 | 16 B | ≈ 112 MB |
| 1000 万 | 16 B | ≈ 1.1 GB |
| 1 亿 | 16 B | ≈ 11 GB ❌ |

**这是 Bitcask 的硬约束：内存必须装得下全部 key。** 超过几千万 key 就该考虑 LSM（RocksDB）了。

### 6.5 前缀扫描的复杂度

`KEYS prefix` 是 **O(总 key 数)**，不是 O(匹配数)。

| 优化 | 做法 | 代价 |
|------|------|------|
| 换成 `BTreeMap` 索引 | 前缀扫描变 `range(prefix..prefix_end)`，O(log n + k) | 点查从 O(1) 变 O(log n)，内存增加 |
| 额外维护前缀索引 | `HashMap<String前缀, Vec<key>>` | 写入路径变慢，内存翻倍 |
| **分页 SCAN** | 返回迭代器 + cursor，客户端分批取 | 接口变更；本项目没做 |

### 6.6 顺序 vs 随机

Bitcask 的读是**随机读**（索引指向任意 offset）。在 HDD 上随机读约 100 IOPS，在 SSD 上约 10 万 IOPS。

**这就是为什么 SSD 时代 Bitcask/LSM 才流行起来** —— 同样的设计放在 HDD 上，随机读会成为瓶颈。

## 7. 动手验证

### 7.1 观察查询路径

```bash
RUST_LOG=debug cargo run --bin minidb-cli -- --dir /tmp/q --exec "PING" 2>&1 | head
```

想真正看到"几次系统调用"，可以用系统工具：

```bash
# Linux
strace -c -e trace=pread64 cargo run --bin minidb-cli -- --dir /tmp/q --exec "GET name"

# Windows（用 Process Monitor 观察 ReadFile）
```

你会看到 4 次读——对应 3.2 的分析。

### 7.2 验证"键不存在"不是错误

```rust
#[test]
fn get_missing_returns_none() {
    let kv = InMemKv::new();
    assert_eq!(kv.get("nope"), None);
    assert!(!kv.contains("nope"));
}
```

```bash
cargo run --bin minidb-cli -- --dir /tmp/q --exec "GET not-exist"
# $-1          ← nil，不是 -ERR
cargo run --bin minidb-cli -- --dir /tmp/q --exec "EXISTS not-exist"
# :0
```

`$-1` 是 RESP 的 nil，`:0` 是布尔假。**两者都不是错误响应**。

### 7.3 验证索引只存位置

```bash
# 写 100 次同一个 key
for i in $(seq 1 100); do
  cargo run -q --bin minidb-cli -- --dir /tmp/q --exec "SET hot value-$i" > /dev/null
done

# 文件大小持续增长（100 条记录都还在）
ls -l /tmp/q/*.log

# 但查询只返回最后一条
cargo run --bin minidb-cli -- --dir /tmp/q --exec "GET hot"
# $8
# value-100
```

**文件里有 100 条记录，索引只有 1 个条目指向最后一条。** 这就是"垃圾"的来源——模块四会讲怎么回收。
