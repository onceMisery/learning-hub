# 写给 Java 程序员的 Rust 入门（七）：测试调试与质量工具

> 本文是系列第七篇。前面我们已经学完 Rust 的语言核心和常用生态，这一篇进入日常工程实践：怎么写测试、怎么组织测试文件、怎么 mock、怎么调试、怎么用 `rustfmt` 和 `clippy` 保持代码质量。Java 程序员可以把这一篇理解成 JUnit + Mockito + SpotBugs + Maven test + IDE debugger 的 Rust 版本。

## 一、Cargo 测试模型

Java 项目通常用 JUnit：

```text
src/main/java
src/test/java
mvn test
```

Rust 的测试由 Cargo 内置支持，不需要额外测试框架：

```text
src/
  lib.rs
  main.rs
tests/
  api_test.rs
Cargo.toml
```

常用命令：

```bash
# 运行全部测试
cargo test

# 只编译测试，不运行
cargo test --no-run

# 运行名字里包含 parser 的测试
cargo test parser

# 显示 println! 输出
cargo test -- --nocapture

# 单线程运行测试，排查共享资源问题时有用
cargo test -- --test-threads=1
```

**Java 程序员注意**：Rust 的测试会先编译测试目标。很多错误在测试运行前就被类型系统、借用检查器、trait bound 拦住了，这和 Java 里“编译过了但运行测试才炸”不太一样。

还有一个容易忽略的默认行为：`cargo test` 会并行跑多个测试。JUnit 过去很多项目默认串行，Rust 这里反过来。如果多个测试共用同一个临时文件、端口、环境变量或全局状态，很容易 flaky。排查时可以先跑：

```bash
cargo test -- --test-threads=1
```

更好的做法是每个测试用独立临时目录、随机端口，或者把共享状态包进测试 fixture 里。

## 二、单元测试

Rust 的单元测试通常放在被测代码同一个文件里，用 `#[cfg(test)]` 隔离：

```rust
pub fn add(left: i32, right: i32) -> i32 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn add_two_numbers() {
        assert_eq!(add(2, 3), 5);
    }
}
```

对应 Java：

```java
class CalculatorTest {
    @Test
    void addTwoNumbers() {
        assertEquals(5, Calculator.add(2, 3));
    }
}
```

常用断言：

```rust
assert!(value > 0);
assert_eq!(actual, expected);
assert_ne!(left, right);
panic!("should not reach here");
```

`assert_eq!` 会在失败时打印左右两边，所以自定义类型通常要派生 `Debug` 和 `PartialEq`：

```rust
#[derive(Debug, PartialEq)]
struct User {
    id: u64,
    name: String,
}
```

Rust 没有 JUnit 那种内置的 `@BeforeEach` / `@AfterEach`。常见写法是普通辅助函数加 Drop guard：

```rust
struct TestDir(tempfile::TempDir);

impl Drop for TestDir {
    fn drop(&mut self) {
        // 需要额外清理时放这里；TempDir 自己也会清理目录
    }
}

fn setup() -> TestDir {
    TestDir(tempfile::tempdir().unwrap())
}
```

测试 panic：

```rust
fn divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("division by zero");
    }
    a / b
}

#[test]
#[should_panic(expected = "division by zero")]
fn divide_by_zero_panics() {
    divide(10, 0);
}
```

**Java 程序员注意**：`#[test]` 是属性宏，类似 JUnit 的 `@Test`，但它在编译期生效。Rust 测试函数默认不需要 `pub`。

## 三、测试 Result 和错误路径

Rust 测试函数可以返回 `Result`，这样就能用 `?`：

```rust
use std::num::ParseIntError;

fn parse_port(input: &str) -> Result<u16, ParseIntError> {
    input.parse()
}

#[test]
fn parse_valid_port() -> Result<(), ParseIntError> {
    let port = parse_port("8080")?;
    assert_eq!(port, 8080);
    Ok(())
}
```

测试错误分支：

```rust
#[test]
fn parse_invalid_port_returns_error() {
    let result = parse_port("abc");

    assert!(result.is_err());
}
```

更推荐把错误类型也断言清楚：

```rust
#[derive(Debug, PartialEq)]
enum ConfigError {
    MissingHost,
    InvalidPort,
}

fn validate(host: &str, port: u16) -> Result<(), ConfigError> {
    if host.is_empty() {
        return Err(ConfigError::MissingHost);
    }
    if port == 0 {
        return Err(ConfigError::InvalidPort);
    }
    Ok(())
}

#[test]
fn empty_host_is_rejected() {
    let error = validate("", 8080).unwrap_err();
    assert_eq!(error, ConfigError::MissingHost);
}
```

**Java 程序员注意**：Java 测异常通常用 `assertThrows`。Rust 里可恢复错误不是异常，而是 `Result` 的 `Err`，所以测试重点是 `Err` 的类型和值。

## 四、集成测试

集成测试放在项目根目录的 `tests/` 下，每个文件会被编译成独立 crate：

```text
my_app/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    └── user_service_test.rs
```

`src/lib.rs`：

```rust
pub fn normalize_name(name: &str) -> String {
    name.trim().to_lowercase()
}
```

`tests/user_service_test.rs`：

```rust
use my_app::normalize_name;

#[test]
fn normalize_name_trims_and_lowercases() {
    assert_eq!(normalize_name(" Alice "), "alice");
}
```

运行某个集成测试文件：

```bash
cargo test --test user_service_test
```

**Java 程序员注意**：`tests/` 里的测试只能访问 crate 的公开 API，不能访问私有函数。这很像从另一个 Maven module 调用你的库。单元测试可以测私有细节，集成测试应该测公开行为。

## 五、测试目录中的公共辅助代码

多个集成测试共享辅助函数时，可以建 `tests/common/mod.rs`：

```text
tests/
├── common/
│   └── mod.rs
├── user_api_test.rs
└── order_api_test.rs
```

`tests/common/mod.rs`：

```rust
pub fn test_user_json() -> &'static str {
    r#"{"id":1,"name":"Alice"}"#
}
```

测试里使用：

```rust
mod common;

#[test]
fn parse_user_json() {
    let json = common::test_user_json();
    assert!(json.contains("Alice"));
}
```

不要直接写 `tests/common.rs`，否则 Cargo 会把它当成一个独立集成测试目标。

## 六、Mock 与依赖替换

Java 里常用 Mockito：

```java
UserRepository repo = mock(UserRepository.class);
when(repo.findById(1L)).thenReturn(Optional.of(user));
```

Rust 更常见的方式是通过 trait 抽象依赖，然后在测试里实现一个 fake：

```rust
#[derive(Debug, Clone, PartialEq)]
struct User {
    id: u64,
    name: String,
}

trait UserRepository {
    fn find_by_id(&self, id: u64) -> Option<User>;
}

struct UserService<R> {
    repo: R,
}

impl<R: UserRepository> UserService<R> {
    fn get_name(&self, id: u64) -> Option<String> {
        self.repo.find_by_id(id).map(|user| user.name)
    }
}

struct FakeUserRepository;

impl UserRepository for FakeUserRepository {
    fn find_by_id(&self, id: u64) -> Option<User> {
        if id == 1 {
            Some(User { id, name: "Alice".to_string() })
        } else {
            None
        }
    }
}

#[test]
fn get_name_returns_user_name() {
    let service = UserService { repo: FakeUserRepository };

    assert_eq!(service.get_name(1), Some("Alice".to_string()));
}
```

如果你确实需要 Mockito 风格的 mock，可以用 `mockall`：

```toml
[dev-dependencies]
mockall = "0.13"
```

```rust
use mockall::automock;

#[automock]
trait Clock {
    fn now_millis(&self) -> u64;
}

fn is_expired(clock: &dyn Clock, deadline: u64) -> bool {
    clock.now_millis() > deadline
}

#[test]
fn expired_when_now_is_after_deadline() {
    let mut clock = MockClock::new();
    clock.expect_now_millis().return_const(2000_u64);

    assert!(is_expired(&clock, 1000));
}
```

**Java 程序员注意**：Rust 不鼓励到处 mock 具体类型。更自然的做法是把外部依赖收敛到小 trait，然后测试业务逻辑时传 fake。这样比 Mockito 的运行时代理更显式，也更容易被编译器检查。

## 七、异步测试

Tokio 提供 `#[tokio::test]`：

```toml
[dev-dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

```rust
async fn fetch_user_name(id: u64) -> String {
    format!("user-{id}")
}

#[tokio::test]
async fn fetch_user_name_returns_name() {
    let name = fetch_user_name(7).await;
    assert_eq!(name, "user-7");
}
```

需要控制时间时启用 `test-util`：

```toml
tokio = { version = "1", features = ["macros", "rt", "time", "test-util"] }
```

```rust
#[tokio::test(start_paused = true)]
async fn timeout_can_be_tested_without_waiting() {
    use tokio::time::{sleep, Duration};

    sleep(Duration::from_secs(60)).await;
}
```

**Java 程序员注意**：异步测试不要在 async 函数里调用阻塞方法，比如 `std::thread::sleep`。用 `tokio::time::sleep`，否则会阻塞运行时工作线程。

## 八、文档测试

Rust 文档注释里的代码也能被测试：

```rust
/// Adds two numbers.
///
/// ```
/// let result = my_app::add(2, 3);
/// assert_eq!(result, 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

运行：

```bash
cargo test
```

文档测试会一起执行。

这类似 Java 里的 README 示例 + 单元测试合体。好处是文档不会悄悄过期。

## 九、格式化：rustfmt

Java 项目可能用 google-java-format，Rust 官方提供 `rustfmt`：

```bash
cargo fmt
```

检查是否已经格式化：

```bash
cargo fmt --check
```

CI 里常用：

```bash
cargo fmt --all --check
```

**Java 程序员注意**：Rust 社区对格式分歧很小，基本默认交给 `rustfmt`。不要在格式上浪费团队讨论时间。

## 十、静态分析：clippy

Clippy 类似 SpotBugs、Error Prone、SonarLint：

```bash
cargo clippy
```

CI 中把 warning 当错误：

```bash
cargo clippy --all-targets --all-features -- -D warnings
```

常见建议：

```rust
// clippy 会建议用 is_empty()
if names.len() == 0 {
    println!("empty");
}
```

改成：

```rust
if names.is_empty() {
    println!("empty");
}
```

局部允许 lint：

```rust
#[allow(clippy::too_many_arguments)]
fn create_user(
    id: u64,
    name: String,
    email: String,
    age: u8,
    active: bool,
) {
    // 示例代码
}
```

**Java 程序员注意**：不要一上来全局关闭 clippy。Rust 的很多 lint 是经验沉淀，初学时 clippy 其实是很好的老师。

## 十一、调试与 backtrace

运行时 panic 默认只显示简短信息：

```bash
cargo run
```

打开 backtrace：

```bash
RUST_BACKTRACE=1 cargo run
```

Windows PowerShell：

```powershell
$env:RUST_BACKTRACE=1
cargo run
```

如果要更完整：

```bash
RUST_BACKTRACE=full cargo test
```

IDE 调试方面：

- VS Code：`rust-analyzer` + CodeLLDB。
- IntelliJ IDEA / CLion：Rust 插件。
- 命令行：Linux/macOS 用 `lldb` 或 `gdb`，Windows 可用 Visual Studio 调试工具链。

**Java 程序员注意**：Rust 没有 JVM 那种统一运行时，所以调试更接近 native 程序。好消息是 debug 构建默认保留调试信息，断点、变量查看、调用栈都能正常工作。

### 在 IntelliJ IDEA 里调试 Rust

如果你习惯 IDEA，Rust 调试大致是这个流程：

1. 安装 Rust 插件。打开 `Settings | Plugins | Marketplace`，搜索并安装 `Rust`。
2. 配好 Rust 工具链。打开 `Settings | Languages & Frameworks | Rust`，确认能识别到 `rustc`、`cargo` 和标准库。
3. Windows 或 Linux 上还要安装 `Native Debugging Support` 插件；macOS 通常不用额外装。
4. 用 IDEA 打开包含 `Cargo.toml` 的项目目录，不要只打开单个 `.rs` 文件。
5. 在代码行号左侧点断点，然后点击 `main` 函数、测试函数或 Cargo target 旁边的运行图标，选择 `Debug`。

调试普通程序时，IDEA 本质上是在帮你跑类似这样的命令：

```bash
cargo run
```

调试测试时，可以直接点测试函数左侧的图标选择 `Debug`，相当于带调试器跑：

```bash
cargo test test_name
```

如果需要命令行参数、环境变量或工作目录，打开 `Run | Edit Configurations...`，新增或编辑 Cargo 配置：

- `Command` 写 `run`、`test`、`run --bin server` 之类的 Cargo 命令。
- `Working directory` 指向项目根目录。
- `Environment variables` 可以加 `RUST_BACKTRACE=1`、`RUST_LOG=debug`。

Windows 上最容易踩的是调试器和工具链不匹配：

| Rust 工具链 | 调试器 | 常见情况 |
|-------------|--------|----------|
| `stable-x86_64-pc-windows-msvc` | LLDB | 默认安装 Rust 时常见，适合配 Visual Studio Build Tools |
| `stable-x86_64-pc-windows-gnu` | GDB | 需要 MinGW/GDB 环境 |

如果看到类似 `GNU debugger cannot be used with MSVC Rust toolchain` 的错误，不是代码问题，而是调试器选错了。到 `Settings | Build, Execution, Deployment | Debugger` 里切 Rust 调试器，或者用 `rustup show` 看当前工具链后统一切换：

```bash
rustup show
rustup default stable-x86_64-pc-windows-msvc
```

还有几个调试时的实际经验：

- 优先调试 debug 构建。release 构建优化后，变量可能被内联或优化掉，看起来像"变量不存在"。
- `String`、`Vec`、`HashMap`、`Option`、`Result` 这类 Rust 类型需要 pretty-printer/renderers 才好看；如果变量窗口很难读，检查 IDEA 的 Rust debugger renderer 设置。
- panic 现场最好同时开 `RUST_BACKTRACE=1`，断点调试和调用栈信息配合看，比只看 panic 文本快很多。
- 调异步代码时，断点会停在线程池工作线程上，不一定像 Java 单线程 demo 那样顺。先看当前任务的调用栈，再看 `tracing` 日志。

## 十二、日志与测试输出

应用里建议用 `tracing`：

```toml
[dependencies]
tracing = "0.1"
tracing-subscriber = "0.3"
```

```rust
use tracing::{info, warn};

fn main() {
    tracing_subscriber::fmt::init();

    info!("server starting");
    warn!("using default config");
}
```

测试时显示输出：

```bash
cargo test -- --nocapture
```

如果测试很多，建议不要依赖肉眼看日志判断结果，把关键行为写成断言。

## 十三、CI 质量门禁

一个 Rust 项目的基础质量门禁通常是：

```bash
cargo fmt --all --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo doc --no-deps
```

如果项目包含多个 crate，放在 workspace 根目录运行：

```bash
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
```

对应 Java：

| Java | Rust |
|------|------|
| `mvn test` | `cargo test` |
| `mvn -DskipTests package` | `cargo build --release` |
| google-java-format | `cargo fmt` |
| SpotBugs / Error Prone | `cargo clippy` |
| Javadoc | `cargo doc` |
| Jacoco | `cargo llvm-cov` 或 tarpaulin |

## 十四、覆盖率

Rust 标准工具链不内置覆盖率报告，常用 `cargo-llvm-cov`：

```bash
cargo install cargo-llvm-cov
cargo llvm-cov
cargo llvm-cov --html
```

生成 HTML 报告后会放在 `target/llvm-cov/html`。

**Java 程序员注意**：覆盖率不是目标，只是信号。Rust 代码的很多类型错误无法通过测试覆盖率体现，因为它们根本无法编译。

## 十五、Java 程序员注意事项总结

### 测试组织

- 单元测试放在源码文件的 `#[cfg(test)] mod tests` 中。
- 集成测试放在 `tests/` 目录，只能访问公开 API。
- 文档示例可以直接成为文档测试。

### Mock

- 优先用 trait + fake，而不是到处 mock 具体类型。
- `mockall` 可以提供 Mockito 风格体验，但不要滥用。
- 依赖边界越小，测试越容易写。

### 质量工具

- `cargo fmt` 相当于官方格式标准。
- `cargo clippy` 是 Rust 项目的基础 lint。
- `cargo check` 是日常开发最快的反馈循环。

### 调试

- panic 不是异常处理机制，打开 `RUST_BACKTRACE=1` 看调用栈。
- 异步测试要用异步运行时提供的测试宏。
- 不要用日志代替断言。

## 小结

这一篇补齐了 Rust 项目的质量工具链：

- **cargo test**：内置测试框架，支持单元测试、集成测试、文档测试。
- **trait + fake**：Rust 里最自然的依赖替换方式。
- **mockall**：需要 Mockito 风格 mock 时的选择。
- **tokio::test**：异步测试入口。
- **rustfmt**：统一格式化。
- **clippy**：静态分析和最佳实践提示。
- **backtrace/debugger**：定位 panic 和 native 调试问题。
