# 写给 Java 程序员的 Rust 入门（十二）：部署与发布

> 本文是系列第十二篇。Java 服务通常以 jar、Docker 镜像或 Kubernetes workload 形式发布。Rust 的部署体验很不一样：它可以编译成一个独立二进制，启动快、镜像小、运行时依赖少。这一篇讲 release 构建、配置、Docker、多平台编译、GitHub Actions 和线上运行注意事项。

## 一、从 jar 到单文件二进制

Java：

```bash
mvn package
java -jar target/app.jar
```

Rust：

```bash
cargo build --release
./target/release/app
```

核心差异：

| Java | Rust |
|------|------|
| 需要 JVM | 不需要 JVM |
| jar 通常不是独立可执行文件 | release 二进制可直接执行 |
| 启动有类加载和 JIT warmup | 启动快 |
| 镜像常包含 JRE | 镜像可以很小 |
| 运行时优化 | 编译期优化 |

**Java 程序员注意**：Rust release 构建才代表真实部署性能。不要用 debug 构建做性能评估。

## 二、Release Profile

`Cargo.toml`：

```toml
[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1
strip = true
panic = "abort"
```

常见取舍：

| 配置 | 好处 | 代价 |
|------|------|------|
| `opt-level = 3` | 性能更好 | 编译更慢 |
| `lto = "thin"` | 体积和性能更好 | 编译更慢 |
| `codegen-units = 1` | 优化更充分 | 并行编译减少 |
| `strip = true` | 二进制更小 | 调试符号减少 |
| `panic = "abort"` | 体积更小 | panic 不展开栈 |

服务端项目常用 `lto = "thin"`。如果你需要保留 crash 调试信息，不要过早 strip。

## 三、配置管理

Java 常见 `application.yml`。Rust 服务更常用环境变量：

```rust
#[derive(Debug, Clone)]
pub struct Config {
    pub bind_addr: String,
    pub database_url: String,
}

impl Config {
    pub fn from_env() -> anyhow::Result<Self> {
        Ok(Self {
            bind_addr: std::env::var("BIND_ADDR")
                .unwrap_or_else(|_| "0.0.0.0:8080".to_string()),
            database_url: std::env::var("DATABASE_URL")?,
        })
    }
}
```

部署时：

```bash
BIND_ADDR=0.0.0.0:8080 \
DATABASE_URL=postgres://postgres:postgres@db/app \
./app
```

如果配置多，可以用 `config` crate，把文件和环境变量合并。

## 四、日志输出

容器环境里建议输出到 stdout/stderr，让平台采集：

```rust
use tracing_subscriber::EnvFilter;

pub fn init_tracing() {
    tracing_subscriber::fmt()
        .with_env_filter(
            EnvFilter::try_from_default_env()
                .unwrap_or_else(|_| "info,my_app=debug".into()),
        )
        .json()
        .init();
}
```

运行：

```bash
RUST_LOG=info,my_app=debug ./app
```

对应 Java：

| Java | Rust |
|------|------|
| Logback XML | tracing-subscriber 初始化 |
| `LOG_LEVEL` | `RUST_LOG` |
| MDC | tracing span 字段 |
| JSON appender | `.json()` |

## 五、Docker 多阶段构建

一个普通 Dockerfile：

```dockerfile
FROM rust:1.80-bookworm AS builder
WORKDIR /app

COPY Cargo.toml Cargo.lock ./
COPY src ./src

RUN cargo build --release

FROM debian:bookworm-slim
WORKDIR /app

RUN useradd -m appuser
COPY --from=builder /app/target/release/todo-api /usr/local/bin/todo-api

USER appuser
ENV RUST_LOG=info
EXPOSE 8080

CMD ["todo-api"]
```

构建运行：

```bash
docker build -t todo-api:latest .
docker run --rm -p 8080:8080 todo-api:latest
```

**Java 程序员注意**：Rust 镜像不需要 JRE。运行层只要有你的二进制和必要系统库即可。

上面这个 Dockerfile 能用，但有个 Rust 项目很常见的痛点：改一行业务代码，Docker 可能重新编译全部依赖。`cargo-chef` 可以把“依赖编译”和“业务代码编译”拆开缓存：

```dockerfile
FROM rust:1.80-bookworm AS chef
RUN cargo install cargo-chef --locked
WORKDIR /app

FROM chef AS planner
COPY . .
RUN cargo chef prepare --recipe-path recipe.json

FROM chef AS builder
COPY --from=planner /app/recipe.json recipe.json
RUN cargo chef cook --release --recipe-path recipe.json
COPY . .
RUN cargo build --release --locked

FROM gcr.io/distroless/cc-debian12
COPY --from=builder /app/target/release/todo-api /usr/local/bin/todo-api
USER nonroot:nonroot
ENV RUST_LOG=info
EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/todo-api"]
```

内部服务频繁构建时，这个差异很明显。我以前最烦的就是 Docker 里冷编译 Rust 依赖，CI 时间一下子被拉长；`cargo-chef` 基本就是为这个问题准备的。

## 六、更小的静态二进制

Linux 上可以编译 musl 静态链接版本：

```bash
rustup target add x86_64-unknown-linux-musl
cargo build --release --target x86_64-unknown-linux-musl
```

Dockerfile 可以用 Alpine、scratch 或 distroless，但要注意：

- OpenSSL 依赖可能让静态链接复杂。
- reqwest 可选择 `rustls-tls` 减少 OpenSSL 问题。
- DNS、证书、时区文件在极小镜像里要额外处理。
- 如果你不是强制静态链接，`gcr.io/distroless/cc-debian12` 往往比 scratch 更省心：有 glibc 运行环境，攻击面又比 debian-slim 小。

依赖建议：

```toml
reqwest = { version = "0.12", default-features = false, features = ["json", "rustls-tls"] }
```

极简镜像不是越小越好。证书、DNS、时区、glibc/musl 兼容性、漏洞扫描和排障便利性都要一起看。

## 七、GitHub Actions CI

`.github/workflows/ci.yml`：

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Install Rust
        uses: dtolnay/rust-toolchain@stable
        with:
          components: rustfmt, clippy

      - name: Cache cargo
        uses: Swatinem/rust-cache@v2

      - name: Format
        run: cargo fmt --all --check

      - name: Clippy
        run: cargo clippy --all-targets --all-features -- -D warnings

      - name: Test
        run: cargo test --all-features

      - name: Build
        run: cargo build --release
```

对应 Maven CI：

```bash
mvn verify
```

Rust 通常拆成 `fmt`、`clippy`、`test`、`build` 四个门禁。

## 八、发布二进制

如果是 CLI 工具，可以用 GitHub Release 发布多平台二进制：

```bash
cargo build --release
tar -czf mytool-x86_64-linux.tar.gz target/release/mytool
```

常见目标：

| 平台 | target |
|------|--------|
| Linux glibc | `x86_64-unknown-linux-gnu` |
| Linux musl | `x86_64-unknown-linux-musl` |
| macOS Intel | `x86_64-apple-darwin` |
| macOS Apple Silicon | `aarch64-apple-darwin` |
| Windows | `x86_64-pc-windows-msvc` |

跨平台编译可以用：

- GitHub Actions matrix。
- `cross`。
- 各平台原生 runner。

## 九、健康检查和优雅关闭

Web 服务至少提供：

```text
GET /health
GET /ready
```

`/health` 表示进程活着，`/ready` 表示依赖也可用，例如数据库连接正常。

优雅关闭：

```rust
async fn shutdown_signal() {
    tokio::signal::ctrl_c()
        .await
        .expect("failed to install Ctrl+C handler");
}
```

axum：

```rust
axum::serve(listener, app)
    .with_graceful_shutdown(shutdown_signal())
    .await?;
```

Kubernetes 里要配：

- `livenessProbe`
- `readinessProbe`
- `terminationGracePeriodSeconds`

## 十、部署前清单

发布前检查：

```bash
cargo fmt --all --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo build --release
```

服务配置：

- 端口通过环境变量配置。
- 日志输出到 stdout/stderr。
- 错误响应不泄露内部细节。
- 数据库迁移有明确流程。
- health/readiness endpoint 可用。
- 容器以非 root 用户运行。
- 依赖安全扫描通过。

## 小结

这一篇讲了 Rust 的发布链路：

- `cargo build --release` 生成可部署二进制。
- release profile 控制性能、体积和调试能力。
- 容器镜像可以比 Java/JRE 镜像更小。
- GitHub Actions 中常见门禁是 fmt、clippy、test、build。
- 配置和日志更偏环境变量 + stdout。
- 生产服务需要健康检查、优雅关闭和依赖安全扫描。

Rust 部署最舒服的地方是简单：一个二进制，一个配置环境，一套清晰的启动参数。少了 JVM 和容器魔法，也少了很多运行时不确定性。
